## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายว่าทำไมต้องมี **loopback** และมันทำงานในเคอร์เนลอย่างไร (ผ่านสแต็ก TCP/IP แต่ไม่ออกการ์ดเครือข่าย)
2. แยก **localhost** (ชื่อ), **127.0.0.1** (ที่อยู่), **127.0.0.0/8** (บล็อก) และ **::1** (IPv6) ออกจากกัน และอธิบายบทบาทของไฟล์ **hosts**
3. อ่าน **ตารางเส้นทาง (routing table)** และอธิบายกฎ **longest prefix match** ที่เคอร์เนลใช้เลือกเส้นทาง
4. อธิบายว่า **default gateway** คือ default route (`0.0.0.0/0`) และเครื่องใช้ ARP หา MAC ของเกตเวย์อย่างไร
5. ตั้งค่า gateway ด้วย `ip route` / Netplan (Linux) และ PowerShell / `ncpa.cpl` (Windows) พร้อมรู้ว่าอันไหนถาวร
6. อธิบายผลของการ **bind** บริการที่ `127.0.0.1` เทียบกับ `0.0.0.0` และวินิจฉัยอาการ *refused* / *unreachable* / *timeout* ได้
7. ชี้ความเสี่ยงด้าน Security ที่เกี่ยวกับ localhost และ gateway (SSRF, ไฟล์ hosts ถูกแก้, ARP spoofing เกตเวย์)

## สรุปสั้น (TL;DR)

- **Loopback** คืออินเทอร์เฟซเสมือน (`lo`) ที่ทำให้เครื่อง "ส่งถึงตัวเอง" ได้ แพ็กเก็ตไม่ออกการ์ดเครือข่าย แต่ยังผ่านสแต็ก TCP/IP ในเคอร์เนล
- **localhost** เป็นแค่ *ชื่อ* ที่ระบบแปลงเป็น `127.0.0.1` (IPv4) หรือ `::1` (IPv6) ส่วนทั้งบล็อก `127.0.0.0/8` วนกลับเครื่องเราหมด
- ทุกครั้งที่ส่งแพ็กเก็ต เคอร์เนลเปิด **ตารางเส้นทาง** แล้วเลือกแถวที่ **prefix ยาวที่สุด** ที่ตรงกับปลายทาง
- **Default gateway** = แถว `0.0.0.0/0` ที่ใช้เมื่อไม่มีแถวอื่นตรง เป็นเราเตอร์ที่ต้องอยู่ **ในซับเน็ตเดียวกับเรา**
- บริการที่ bind ที่ `127.0.0.1` คนอื่นใน LAN เข้าไม่ได้ ถ้าต้องการให้เข้าได้ ใช้ `0.0.0.0` (แต่ต้องมีไฟร์วอลล์/การยืนยันตัวตน)

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | สิ่งที่เทียบได้ |
|---|---|
| พูดกับตัวเองในห้อง ไม่ต้องใช้โทรศัพท์หรือไปรษณีย์ | loopback: ข้อมูลวนอยู่ในเครื่อง |
| ชื่อเล่น "ตัวฉัน" ที่ทุกคนในบ้านรู้ว่าหมายถึงใคร | `localhost` ชื่อที่แปลงเป็น 127.0.0.1 |
| สมุดโทรศัพท์ส่วนตัวที่ดูก่อนสมุดหน้าเหลือง | ไฟล์ `hosts` (ตรวจก่อน DNS) |

| ยามหน้าซอยที่ "ไม่รู้จักบ้านเลขที่นี้ ฉันฝากต่อให้" | default route |
| ป้ายบอกทางที่ใช้ป้ายระบุที่สุดก่อน (เช่น "ห้องน้ำ" ชนะ "ชั้น 2") | longest prefix match |

## 1. ทำไมต้องมี loopback: ปัญหาตั้งต้น

นักพัฒนารันเว็บเซิร์ฟเวอร์ทดสอบบนแล็ปท็อป ถอดสาย LAN ปิด Wi-Fi แล้วเปิด `http://localhost:8080` หน้าเว็บยังขึ้นทันที

โปรแกรมสองตัว (เบราว์เซอร์กับเว็บเซิร์ฟเวอร์) ในเครื่องเดียวกันมักสื่อสารกันด้วย **socket** เดียวกับที่ใช้ข้ามเครือข่าย ถ้าโปรแกรมต้องเขียนวิธีคุยแยกสำหรับ "ในเครื่อง" กับ "ข้ามเครื่อง" ทุกโปรแกรมจะซับซ้อน ระบบปฏิบัติการจึงให้ **ที่อยู่พิเศษ** ที่ใช้ API เดิมทุกอย่าง แต่เคอร์เนลรู้ว่า "ปลายทางคือฉันเอง" แล้วส่งกลับเข้าตัวเอง นี่คือ **loopback**

### 1.1 กลไกภายใน: วนกลับที่ไหน

Linux มีอินเทอร์เฟซเสมือนชื่อ `lo` (บน Windows เป็นไดรเวอร์ Software Loopback Interface) มันไม่มีฮาร์ดแวร์ ฟังก์ชัน "ส่งออก" ของมันทำอย่างเดียวคือ **เอา buffer เดิมใส่กลับเข้าคิวรับของเคอร์เนล**

> **ความแม่นยำ:** บางตำราสรุปว่า loopback "ข้ามสแต็ก TCP/IP ทั้งหมด" ซึ่งไม่ถูกนัก ข้อมูลยังผ่าน TCP และ IP ในเคอร์เนลครบ สิ่งที่ข้ามคือชั้น link ฮาร์ดแวร์ (การ์ด สายสัญญาณ สวิตช์) จึงไม่มีการสูญหายจากสัญญาณ และมักข้ามขั้นตอนอย่างการคำนวณ checksum หรือการแตก segment ที่ออกแบบมาเพื่อสายจริงด้วย (ขึ้นกับรุ่นเคอร์เนล) ส่วน Windows ใช้กลไกต่างกันเล็กน้อย แต่หลักการเดียวกันคือไม่ออกการ์ด

### 1.2 ทำไม MTU ของ lo ถึงใหญ่

บน Linux `lo` มักมี `mtu 65536` เทียบกับ Ethernet ทั่วไป `1500` เพราะไม่มีสายจริงที่ต้องจำกัดขนาดเฟรม ผลคือแพ็กเก็ตน้อยลงมาก ลองคำนวณการส่งข้อมูล 1 GB (10⁹ ไบต์) โดย header IP+TCP รวม 40 ไบต์

| อินเทอร์เฟซ | MTU | ข้อมูลต่อแพ็กเก็ต (MSS) | จำนวนแพ็กเก็ตโดยประมาณ |
|---|---|---|---|
| Ethernet | 1,500 | 1,460 | 10⁹ ÷ 1,460 ≈ **684,932** |
| loopback | 65,536 | 65,496 | 10⁹ ÷ 65,496 ≈ **15,269** |

ต่างกันราว 45 เท่า (ตัวเลขนี้ตรวจด้วยการคำนวณจริง; ค่า MTU เป็นค่าเริ่มต้นทั่วไป ขึ้นกับเครื่อง) นี่คือเหตุผลหนึ่งที่การวัดความเร็วด้วย `localhost` ให้ตัวเลขสูงเกินจริง ห้ามนำไปใช้ประเมินประสิทธิภาพเครือข่ายจริง

**ความหน่วง:** ping ผ่าน loopback มักได้ราว หลักสิบถึงหลักร้อย µs เทียบกับ LAN ราว 0.2–1 ms (ค่าประมาณ ขึ้นกับเครื่อง)

## 2. localhost, 127.0.0.1, 127.0.0.0/8 และ ::1 ต่างกันอย่างไร

| คำ | คืออะไร | หมายเหตุ |
|---|---|---|
| `localhost` | **ชื่อ** (hostname) | ไม่ใช่ที่อยู่ ต้องแปลงก่อนใช้ |
| `127.0.0.1` | **ที่อยู่** IPv4 | ค่าที่ระบบตั้งให้ `lo` โดยปริยาย |
| `127.0.0.0/8` | **บล็อก** | IETF สงวนทั้ง 16,777,216 ที่อยู่ (127.0.0.0 – 127.255.255.255) |
| `::1` | ที่อยู่ IPv6 loopback | ที่อยู่เดียว (`::1/128`) ไม่ใช่บล็อก |

**ทำไมทั้งบล็อก /8 วนกลับ ไม่ใช่แค่ .1:** กฎการจัดเส้นทางผูกกับ *prefix* ไม่ใช่ที่อยู่เดียว เคอร์เนลมีแถว `127.0.0.0/8 dev lo` แถวเดียว ที่อยู่ใดที่ขึ้นต้น 127 จึงตรงแถวนี้หมด ผลคือใช้ `127.0.0.2`, `127.45.2.99` ได้เหมือนกัน (บน Linux) ซึ่งมีประโยชน์เช่นให้หลายบริการทดสอบฟังพอร์ตเดียวกันคนละที่อยู่ในเครื่องเดียว ข้อควรรู้: การออกแบบนี้ "เปลือง" ที่อยู่ไป 1/256 ของ IPv4 ทั้งหมด (ยืนยันได้จาก 2²⁴ ÷ 2³² = 1/256) แต่เป็นมรดกที่แก้ไม่ได้แล้ว

### 2.1 แล้ว "localhost" กลายเป็นที่อยู่ได้อย่างไร

ก่อนเปิดการเชื่อมต่อ ระบบต้อง **แปลงชื่อเป็นที่อยู่ (name resolution)** ลำดับโดยทั่วไป: ไฟล์ **hosts** ก่อน แล้วค่อยถาม DNS (บน Linux ลำดับกำหนดใน `/etc/nsswitch.conf` ส่วน Windows มีตัวแปลงในตัว)

```text
# Linux/macOS: /etc/hosts
127.0.0.1   localhost
::1         localhost
```

Windows: ไฟล์อยู่ที่ `C:\Windows\System32\drivers\etc\hosts` (รุ่นใหม่บรรทัด localhost มักเป็นคอมเมนต์ เพราะระบบแปลง `localhost` ในตัวเองอยู่แล้ว)

**ข้อควรระวังที่พบบ่อย:** `localhost` อาจแปลงเป็น **ทั้ง `::1` และ `127.0.0.1`** โปรแกรมบางตัวลอง `::1` ก่อน ถ้าเว็บเซิร์ฟเวอร์ฟังเฉพาะ IPv4 (`127.0.0.1`) การเชื่อมต่อ `http://localhost` ที่ลอง `::1` ก่อนจะได้ *connection refused* ในขณะที่ `http://127.0.0.1` ใช้ได้ (ถ้าโปรแกรมไม่ fallback ไปลอง IPv4) นี่คืออาการ "localhost ใช้ไม่ได้แต่ 127.0.0.1 ใช้ได้" ที่ทำให้งงบ่อย

## 4. ตารางเส้นทาง (routing table): เคอร์เนลเลือกทางอย่างไร

ทุกแพ็กเก็ตที่ส่งออกจะถามคำถามเดียว: **"ปลายทางนี้ ต้องส่งออกอินเทอร์เฟซไหน และส่งให้ใคร"** คำตอบมาจาก **ตารางเส้นทาง** ซึ่งเป็นรายการของ `prefix → ทางออก`

```bash
$ ip route show
default via 192.168.1.1 dev eth0 proto static
127.0.0.0/8 dev lo scope link
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.50
```

| แถว | ความหมาย |
|---|---|
| `192.168.1.0/24 dev eth0 scope link` | ซับเน็ตของเราเอง **on-link** ปลายทางอยู่ในสายเดียวกัน ส่งตรง ARP หา MAC ปลายทาง |
| `127.0.0.0/8 dev lo` | บล็อก loopback ส่งเข้า lo |
| `default via 192.168.1.1 dev eth0` | **default route** ไม่มีแถวอื่นตรง ส่งให้เราเตอร์ 192.168.1.1 |

### 4.1 กฎ longest prefix match

บ่อยครั้งปลายทางหนึ่งตรง **หลายแถวพร้อมกัน** เช่น `192.168.1.20` ตรงทั้ง `192.168.1.0/24` และ `0.0.0.0/0` (default ตรงทุกที่อยู่เพราะ prefix ยาว 0 บิต) เคอร์เนลเลือก **แถวที่ prefix ยาวที่สุด** เพราะยิ่งยาว ยิ่งเฉพาะเจาะจง ลำดับบนล่างของตารางไม่สำคัญ

เหตุผลเชิงบิต: prefix /24 กำหนด 24 บิตแรกต้องตรง ส่วน /0 ไม่กำหนดบิตใดเลย ถ้า /24 ตรง แปลว่ามีข้อมูลเกี่ยวกับปลายทางนี้มากกว่า default ซึ่งเป็นแค่ทางสุดท้ายเมื่อไม่รู้อะไรเลย

**ลองเอง:** เลือกปลายทางต่างๆ ดูว่าแถวไหนตรง แถวไหนชนะ และลองปิด default route เพื่อดูว่าเกิดอะไรกับปลายทางบนอินเทอร์เน็ต

::route-lookup
::

**ข้อสังเกต:** `192.168.1.50` (IP ของเครื่องเราเอง) ตรงทั้ง `/32` และ `/24` ชนะที่ `/32` เพราะยาวกว่า จึงถูกส่งถึงตัวเองผ่าน lo แม้ระบุที่อยู่ของการ์ด eth0 ข้อเท็จจริงนี้ทำให้ `ping` ที่อยู่ IP ของตัวเองไม่ออกสายด้วย (บน Linux แถวนี้อยู่ในตาราง `local` ที่ดูด้วย `ip route show table local`)

## 5. Default gateway: ทางออกของซับเน็ต

### 5.1 ปัญหาตั้งต้น

เครื่องหนึ่งไม่มีทางรู้เส้นทางไปยังเซิร์ฟเวอร์นับพันล้านเครื่องบนอินเทอร์เน็ต มันรู้แค่ (1) ซับเน็ตของตัวเอง และ (2) เราเตอร์หนึ่งตัวที่ "รู้ทางต่อ" นั่นคือ **default gateway** ที่ปรากฏเป็นแถว `0.0.0.0/0` (ดูเรื่อง AND ระดับบิตและซับเน็ตในบทก่อน)

### 5.3 กฎทองของ gateway

> **เกตเวย์ต้องอยู่ในซับเน็ตเดียวกับเครื่อง** เพราะเครื่องต้อง ARP หา MAC ของเกตเวย์โดยตรง ถ้าเกตเวย์อยู่นอกซับเน็ต (AND แล้วไม่เท่ากับของเรา) เครื่องไม่รู้จะส่งเฟรมไปที่ MAC ไหน และระบบมักปฏิเสธการตั้งค่านั้น (Linux ตอบ `Nexthop has invalid gateway`)

ตัวอย่าง: เครื่อง `192.168.10.42/24` ตั้งเกตเวย์ `192.168.1.1` → `192.168.10.0/24` ≠ `192.168.1.0/24` ใช้ไม่ได้

### 5.4 ถ้าไม่มี default gateway

เครื่องยังคุยกับ **เครื่องในซับเน็ตเดียวกัน** ได้ตามปกติ (ใช้แถว on-link) แต่ปลายทางอื่นใดนอกซับเน็ตจะไม่ตรงแถวใดเลย เคอร์เนลตอบ **`Network is unreachable`** ทันที (ไม่ใช่รอแล้ว timeout) ลองเลือก "ไม่มี default route" ในสื่อด้านบนแล้วเลือก `1.1.1.1` ดู

### 5.5 หลาย gateway ได้ไหม

บนเครื่องที่มีหลายการ์ด (เช่น LAN + Wi-Fi) แต่ละการ์ดอาจมี default route ของตัวเอง เคอร์เนลเลือกอันที่ **metric ต่ำสุด** (ตัวเลขยิ่งต่ำยิ่งต้องการ) เป็นหลัก ปัญหาคลาสสิกคือสองการ์ดมี default gateway พร้อมกัน แล้วทราฟฟิกออกผิดทาง แนวปฏิบัติ: ให้เครือข่ายหนึ่งการ์ดมี default gateway เพียงหนึ่ง และใช้เส้นทางเฉพาะ (static route) สำหรับอีกเครือข่าย

## 7. bind: ทำไม localhost ถึงกันคนอื่นออก

บริการเครือข่ายเลือก **ที่อยู่ที่จะรับฟัง (bind address)** ก่อนเปิดพอร์ต ซึ่งกำหนดว่า *จากอินเทอร์เฟซไหน* ถึงเข้าถึงได้

| Bind address | ใครเชื่อมต่อได้ | ตัวอย่างการใช้ |
|---|---|---|
| `127.0.0.1` | **เฉพาะโปรแกรมในเครื่องเดียวกัน** | ฐานข้อมูลที่เว็บแอปเครื่องเดียวกันใช้, เซิร์ฟเวอร์ dev |
| `192.168.1.50` (IP การ์ดเดียว) | เฉพาะที่เข้าทางการ์ดนั้น | บริการที่ตั้งใจเปิดให้เฉพาะเครือข่ายนั้น |
| `0.0.0.0` (ทุก IPv4) | **ทุกอินเทอร์เฟซ** รวม LAN และอินเทอร์เน็ตถ้าไม่มีไฟร์วอลล์ | เว็บเซิร์ฟเวอร์สาธารณะ |
| `::` (ทุก IPv6) | ทุกอินเทอร์เฟซแบบ IPv6 (ปกติรับ IPv4 ด้วยตามการตั้งค่า) | เหมือนกัน |

**เหตุผลเชิงกลไก:** เมื่อมีแพ็กเก็ตเข้ามา เคอร์เนลจับคู่ (IP ปลายทาง, พอร์ตปลายทาง) กับ socket ที่ listen อยู่ socket ที่ bind `127.0.0.1:5432` จับเฉพาะแพ็กเก็ตที่ IP ปลายทางเป็น `127.0.0.1` ซึ่งมีแต่โปรแกรมในเครื่องเดียวกันที่ส่งมาได้ (แพ็กเก็ตจากเครื่องอื่นมี IP ปลายทางเป็น `192.168.1.50` ไม่ตรง) จึงถูกตอบ RST หรือทิ้ง ดูรายละเอียด socket และ 4-tuple ในบทพอร์ต

ตรวจด้วยคำสั่ง (อ่านอย่างเดียว):

```bash
ss -tln          # Linux: ดู address:port ที่ listen ถ้าเห็น 127.0.0.1:xxxx = เฉพาะในเครื่อง, 0.0.0.0:xxxx หรือ *:xxxx = ทุกอินเทอร์เฟซ
netstat -an | findstr LISTENING      # Windows
```

## 8. มุมมองด้าน Security

| ประเด็น | กลไก | การป้องกัน |
|---|---|---|
| **ถือว่า localhost = ปลอดภัย** | บริการบางตัว (ฐานข้อมูล, แผงควบคุม) ไม่ตรวจสอบตัวตนถ้าเรียกจาก 127.0.0.1 แต่มัลแวร์หรือผู้ใช้อื่นในเครื่องก็ส่งจาก 127.0.0.1 ได้ | ใส่การยืนยันตัวตนแม้ในเครื่อง, จำกัดผู้ใช้ด้วยสิทธิ์ไฟล์/ unix socket |
| **SSRF (Server-Side Request Forgery)** | ผู้โจมตีหลอกให้เซิร์ฟเวอร์ส่งคำขอไปที่ `http://127.0.0.1:...` หรือ `169.254.169.254` เพื่ออ่านบริการภายในที่ไม่เปิดสู่ภายนอก | ตรวจและบล็อกปลายทางที่เป็น loopback / link-local / private หลังแปลงชื่อแล้ว, ใช้ allowlist, ปิดการ redirect |
| **ไฟล์ hosts ถูกแก้** | มัลแวร์เพิ่มบรรทัด `1.2.3.4 bank.example` ทำให้ชื่อเว็บธนาคารชี้ไปเซิร์ฟเวอร์ปลอม โดยไม่ผ่าน DNS | ตรวจสิทธิ์ไฟล์ hosts, เฝ้าดูการเปลี่ยนแปลง (FIM), ตรวจใบรับรอง TLS ของเว็บ |
| **เปิดบริการด้วย 0.0.0.0 โดยไม่ตั้งใจ** | ฐานข้อมูลที่ควรเป็น 127.0.0.1 ถูกตั้งเป็น 0.0.0.0 และไม่มีรหัสผ่าน อินเทอร์เน็ตสแกนเจอ | ตรวจด้วย `ss -tln`, ไฟร์วอลล์ default deny, bind เฉพาะที่จำเป็น |
| **DNS rebinding** | โดเมนของผู้โจมตีแปลงเป็น IP ภายนอกก่อน แล้วสลับเป็น 127.0.0.1 ให้เบราว์เซอร์ของเหยื่อเรียกบริการ localhost | บริการ localhost ตรวจ `Host` header, ใช้ token, เบราว์เซอร์สมัยใหม่เริ่มจำกัดการเข้าถึงเครือข่ายส่วนตัว |
| **ARP spoofing เกตเวย์** | ผู้โจมตีใน LAN ส่ง ARP ปลอมบอกว่า MAC ของเขาคือ 192.168.1.1 ทราฟฟิกทั้งหมดที่จะออกนอกซับเน็ตจึงผ่านเครื่องเขาก่อน (man-in-the-middle) | Dynamic ARP Inspection บนสวิตช์, ใช้ HTTPS/VPN, ตรวจ MAC ของเกตเวย์ด้วย `arp -a` |
| **Rogue DHCP แจก gateway ปลอม** | เซิร์ฟเวอร์ DHCP เถื่อนแจก default gateway เป็นเครื่องผู้โจมตี | DHCP snooping บนสวิตช์ (รายละเอียดในบทถัดไป) |
| **แพ็กเก็ตปลอมแหล่งที่มา 127.0.0.1 จากสาย** | ผู้โจมตีส่งแพ็กเก็ตที่ระบุต้นทาง 127.0.0.1 มาทางการ์ดจริงเพื่อหลอกให้เชื่อว่ามาจากในเครื่อง | ระบบที่ถูกต้องทิ้งแพ็กเก็ตที่อ้างต้นทาง 127/8 ที่มาจากการ์ดภายนอก (martian packets / `rp_filter`) |

**หลักคิด:** localhost คือ *ขอบเขตของเครื่อง* ไม่ใช่ขอบเขตของ *ความน่าเชื่อถือ* และ gateway คือ *จุดผ่านของทราฟฟิกทั้งหมด* ใครคุมได้ก็เห็นทราฟฟิกได้

| `ping 127.0.0.1` ไม่ผ่าน | สแต็ก TCP/IP ของเครื่องมีปัญหา | ไม่ได้เกี่ยวกับสายหรือเครือข่ายภายนอก เพราะไม่ออกการ์ด ตรวจไดรเวอร์/สแต็ก, ไฟร์วอลล์ที่บล็อก ICMP, ซอฟต์แวร์ความปลอดภัย, ลอง reset สแต็ก (`netsh int ip reset`) |
| `localhost:3000` ใช้ไม่ได้ แต่ `127.0.0.1:3000` ใช้ได้ | `localhost` แปลงเป็น `::1` ก่อน แต่เซิร์ฟเวอร์ฟังแค่ IPv4 | ตรวจ `ss -tln` ว่าฟัง `127.0.0.1` หรือ `::1` แก้โดยให้ฟังทั้งสอง หรือเรียกด้วย 127.0.0.1 |
| `Connection refused` ที่ `127.0.0.1:8080` | ไม่มีโปรแกรมฟังพอร์ตนั้น | เคอร์เนลตอบ RST ทันที (ไม่ใช่ timeout) ตรวจว่าโปรแกรมรันอยู่และพอร์ตถูก |
| เพื่อนในออฟฟิศเข้าเว็บ dev ของเราไม่ได้ แต่เราเข้าได้ | เซิร์ฟเวอร์ bind `127.0.0.1` | ตรวจ `ss -tln` ถ้าเห็น 127.0.0.1:พอร์ต ให้ bind ที่ 0.0.0.0 หรือ IP การ์ด และเปิดพอร์ตในไฟร์วอลล์ (ผู้อื่นเรียกด้วย IP การ์ดของเรา ไม่ใช่ localhost) |
| เข้าเครื่องในออฟฟิศได้ แต่เข้าอินเทอร์เน็ตไม่ได้ | ไม่มีหรือผิด default gateway | `Network is unreachable` ทันที = ไม่มี default route; ping IP ภายนอก (เช่น 1.1.1.1) ไม่ได้ แต่ ping เกตเวย์ได้ = ปัญหาเลยเกตเวย์ไป (ISP, NAT) ตรวจ `ip route` / `route print` |
| ping เกตเวย์ไม่ได้ แต่สายและ Wi-Fi ปกติ | เกตเวย์ไม่อยู่ในซับเน็ตเดียวกัน หรือเกตเวย์ล่ม | คำนวณ (IP AND mask) เทียบกับเกตเวย์ ดูตาราง ARP (`arp -a`) ว่ามี MAC ของเกตเวย์ไหม ถ้าเป็น `incomplete` แปลว่าเกตเวย์ไม่ตอบ ARP |
| อินเทอร์เน็ตช้าหรือผ่านเส้นทางแปลก หลังต่อ VPN หรือเปิดสองการ์ด | มีหลาย default route | ดูแถว default ทั้งหมด เปรียบ metric (`route print`, `ip route`) ปิดการ์ดที่ไม่ต้องใช้ หรือปรับ metric |
| ตั้ง gateway ด้วยมือแล้วรีบูตหาย (Linux) | ตั้งด้วย `ip route` ซึ่งเป็นการแก้ตารางในเคอร์เนลชั่วคราว | บันทึกใน Netplan/NetworkManager แล้ว apply |
| เปิดเว็บไซต์หนึ่งแล้วไปผิดหน้า ทั้งที่ DNS ปกติ | ไฟล์ hosts มีบรรทัดชี้ชื่อนั้นเอง | ตรวจไฟล์ hosts (ถูกตรวจก่อน DNS) ลบบรรทัดที่ไม่รู้จัก และสแกนมัลแวร์ |

## 11. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: เครื่อง 192.168.10.42/24 gateway 192.168.10.1 เปิดไฟล์แชร์ที่ 192.168.10.55 แพ็กเก็ตไปทางไหน"}
**ส่งตรงไปที่ 192.168.10.55 ในซับเน็ตเดียวกัน** (ARP หา MAC ของ .55 แล้วส่งเฟรมไปเลย) ไม่ผ่านเกตเวย์ เพราะ (192.168.10.55 AND mask) = 192.168.10.0 เท่ากับของเครื่องเรา จึงเป็น on-link ไม่ใช่ loopback และไม่ใช่การทิ้ง
::

::reveal{question="ข้อ 2: ทำไมทั้งบล็อก 127.0.0.0/8 วนกลับ ไม่ใช่แค่ 127.0.0.1"}
เพราะตารางเส้นทางมีแถวเดียว `127.0.0.0/8 dev lo` ซึ่งตรงทุกที่อยู่ที่ 8 บิตแรกเป็น 127 เคอร์เนลตัดสินด้วย prefix ไม่ใช่ที่อยู่เดี่ยว ผลคือ 127.45.2.99 วนกลับเช่นกัน (บน Linux) ส่วน 127.0.0.1 เป็นเพียงค่ามาตรฐานที่ถูกกำหนดให้การ์ดเสมือน
::

::reveal{question="ข้อ 3: ถ้าตั้ง default gateway เป็นที่อยู่นอกซับเน็ต จะเกิดอะไร"}
เครื่องไม่มีทาง ARP หา MAC ของเกตเวย์ได้ (เกตเวย์ไม่ได้อยู่บนสายเดียวกัน) ระบบปฏิบัติการจึงมักปฏิเสธการตั้งค่า (เช่น Linux `Nexthop has invalid gateway`) หรือยอมให้ตั้งแต่ใช้งานไม่ได้ ผลคือออกนอกซับเน็ตไม่ได้ แต่คุยกับเครื่องในซับเน็ตเดียวกันยังได้
::

::reveal{question="ข้อ 4: เครื่องมี default gateway หลายตัวพร้อมกันได้ไหม"}
ได้ในทางเทคนิค (เช่น สองการ์ดคนละ gateway) แต่เคอร์เนลเลือกใช้แถวที่ **metric ต่ำที่สุด** (ถ้า metric เท่ากันพฤติกรรมขึ้นกับระบบ) การมีหลาย default route ทำให้ทราฟฟิกออกผิดทางได้ แนวปฏิบัติคือให้มี default gateway ที่ใช้จริงเพียงหนึ่งตัวต่อเครื่อง
::

::reveal{question="ข้อ 5: ทำไมบริการที่ bind 127.0.0.1 เครื่องอื่นใน LAN จึงเชื่อมต่อไม่ได้"}
เคอร์เนลจับคู่แพ็กเก็ตที่เข้ามากับ socket ด้วย IP ปลายทาง+พอร์ต แพ็กเก็ตจากเครื่องอื่นมี IP ปลายทางเป็น IP ของการ์ดเรา (เช่น 192.168.1.50) ไม่ใช่ 127.0.0.1 จึงไม่ตรงกับ socket ที่ bind ไว้ และแพ็กเก็ตที่ระบุปลายทาง 127.0.0.1 ก็ไม่ถูกส่งออกสายจากเครื่องอื่นอยู่แล้ว (เราเตอร์ไม่ส่งต่อ 127/8) ถ้าต้องการให้เข้าได้ ต้อง bind 0.0.0.0 หรือ IP การ์ด
::

::reveal{question="ข้อ 6: ตารางมี 0.0.0.0/0, 10.0.0.0/8 และ 10.1.0.0/16 ส่งไป 10.1.5.9 เคอร์เนลเลือกแถวไหน เพราะอะไร"}
ตรงทั้งสามแถว เลือก **10.1.0.0/16** เพราะ prefix ยาวที่สุด (16 > 8 > 0) คือเฉพาะเจาะจงที่สุด ไม่ขึ้นกับลำดับในตาราง
::

::reveal{question="ข้อ 7: ทำไม 'Network is unreachable' ต่างจาก 'Request timed out' ในเชิงกลไก"}
**unreachable:** เคอร์เนลเครื่องเราหาแถวในตารางเส้นทางไม่เจอ (เช่น ไม่มี default route) จึงปฏิเสธทันทีโดยไม่ส่งอะไรออกสาย **timeout:** มีเส้นทางและส่งแพ็กเก็ตออกไปจริง แต่ไม่มีคำตอบกลับ (เซิร์ฟเวอร์ปิด ไฟร์วอลล์ทิ้งเงียบ เราเตอร์ไม่มีทางต่อ ฯลฯ) สองอาการชี้ไปคนละจุด: ตารางเครื่องเรา vs ที่ไหนสักแห่งตามทาง
::

::reveal{question="โจทย์ 1: ส่ง 1 GB ผ่าน Ethernet MTU 1,500 กับ loopback MTU 65,536 (header IP+TCP 40 ไบต์) ใช้แพ็กเก็ตต่างกันกี่เท่า"}
MSS Ethernet = 1,500 − 40 = 1,460 → 10⁹ ÷ 1,460 ≈ **684,932** แพ็กเก็ต · MSS loopback = 65,536 − 40 = 65,496 → 10⁹ ÷ 65,496 ≈ **15,269** แพ็กเก็ต · อัตราส่วน ≈ **44.9 เท่า** (ตรวจด้วยการคำนวณจริง; ค่าประมาณเพราะไม่นับ option ใน header และขนาดจริงขึ้นกับเครื่อง)
::

::reveal{question="โจทย์ 2: ตาราง default via 10.0.0.1, 10.0.0.0/24 on-link, 10.0.1.0/24 via 10.0.0.254 เครื่องมี IP 10.0.0.30 ส่งไป 10.0.1.77 และ 10.0.0.200 และ 8.8.8.8 ผ่านทางไหน"}
**10.0.1.77:** ตรง /24 ของ 10.0.1.0 (prefix 24) และ default (prefix 0) → เลือก /24 → ส่งให้ next hop **10.0.0.254** · **10.0.0.200:** ตรง 10.0.0.0/24 → **on-link ส่งตรง** (ARP หา .200) · **8.8.8.8:** ไม่ตรงแถวเฉพาะ → **default via 10.0.0.1** สังเกตว่าเกตเวย์ทั้งสอง (.254 และ .1) อยู่ในซับเน็ต 10.0.0.0/24 เดียวกับเรา ตามกฎทองของ gateway
::

::reveal{question="โจทย์ 3: ผู้ใช้บอก ผมเปิด http://localhost ไม่ได้ ได้ connection refused แต่ http://127.0.0.1 ขึ้น คุณจะตรวจอะไรเป็นลำดับ"}
(1) `ss -tln` ดูว่าเซิร์ฟเวอร์ฟัง `127.0.0.1:80` หรือ `[::1]:80` · (2) ตรวจว่า `localhost` แปลงเป็นอะไร (`ping -4 localhost` เทียบ `ping -6 localhost`, ดูไฟล์ hosts) · (3) ถ้าเซิร์ฟเวอร์ฟังแค่ IPv4 แต่ `localhost` ถูกลอง `::1` ก่อน นั่นคือสาเหตุ แก้ได้โดยให้เซิร์ฟเวอร์ฟังทั้งสองแบบ หรือเรียกด้วย 127.0.0.1 · อาการ refused (ไม่ใช่ timeout) บอกว่ามีเส้นทางถึง แต่พอร์ตนั้นไม่มีใครฟังในที่อยู่นั้น
::

## 12. แบบฝึกหัด (ลงมือทำจริง)

ใช้กับเครื่องของคุณเอง คำสั่งอ่านอย่างเดียว

1. **ตรวจ loopback:** `ping -c 3 127.0.0.1` (Linux) หรือ `ping -n 3 127.0.0.1` (Windows) สังเกตเวลาตอบที่ต่ำมาก แล้วลอง `ping 127.45.2.99` (ตอบได้เพราะอยู่ในบล็อก 127/8 บน Linux/ส่วนใหญ่ของ Windows)
2. **แยกชื่อกับที่อยู่:** `ping localhost` ดูว่าแปลงเป็น `::1` หรือ `127.0.0.1` แล้วลอง `ping -4 localhost` และ `ping -6 localhost` เทียบกัน
3. **อ่านไฟล์ hosts:** เปิดดู `/etc/hosts` หรือ `C:⧵Windows⧵System32⧵drivers⧵etc⧵hosts` (แค่อ่าน) มีบรรทัดใดบ้าง และเข้าใจว่าแต่ละบรรทัดชี้ชื่อไปที่ไหน
4. **หา default gateway:** `ip route | grep default` หรือ `ipconfig | findstr Gateway` จดค่า แล้วตรวจว่าเกตเวย์อยู่ในซับเน็ตเดียวกับ IP ของคุณ (คำนวณ AND กับ mask)
5. **ให้เคอร์เนลเลือกทางให้ดู:** `ip route get 1.1.1.1`, `ip route get 127.0.0.1`, `ip route get <IP เครื่องอื่นใน LAN>` (Linux) เทียบกับสื่อ route-lookup ด้านบน บน Windows ใช้ `route print -4` แล้วหาแถวด้วยตัวเองตามกฎ longest prefix match
6. **ดูการ bind:** `ss -tln` (Linux) หรือ `netstat -an | findstr LISTENING` (Windows) หาบริการที่ฟังที่ `127.0.0.1` (เฉพาะในเครื่อง) เทียบกับ `0.0.0.0` / `*` (ทุกอินเทอร์เฟซ) ใครเปิดสู่เครือข่ายอยู่บ้าง
7. **ดู ARP ของเกตเวย์:** `arp -a` หรือ `ip neigh` หา MAC ของเกตเวย์ จดไว้ แล้วเทียบอีกครั้งภายหลัง (ถ้า MAC ของเกตเวย์เปลี่ยนโดยไม่มีเหตุ อาจเป็นสัญญาณ ARP spoofing)

::reveal{question="แนวคำตอบ"}
(1) เวลาตอบมักต่ำกว่า 1 ms มาก เพราะไม่ออกการ์ด · (2) ระบบมักแปลง localhost ได้ทั้ง ::1 และ 127.0.0.1 ผลแรกที่ใช้ขึ้นกับระบบ · (3) ไฟล์ hosts ปกติมีน้อยบรรทัด บรรทัดแปลกที่ชี้โดเมนจริงไปที่ IP แปลก = ควรสงสัย · (4) เกตเวย์ปกติเป็นที่อยู่แรกหรือสุดท้ายของซับเน็ต (เช่น .1 หรือ .254) แต่ไม่จำเป็นเสมอไป · (5) 1.1.1.1 ควรออก `via <gateway>`, 127.0.0.1 ควรเป็น `local ... dev lo`, เครื่องใน LAN ควรไม่มี `via` · (6) บริการฐานข้อมูลบนเครื่องส่วนตัวควรอยู่ที่ 127.0.0.1 ถ้าเห็นเปิด 0.0.0.0 โดยไม่ตั้งใจ ให้ตรวจไฟร์วอลล์และการยืนยันตัวตน · (7) `incomplete` ใน ip neigh แปลว่า ARP ไม่ได้รับคำตอบ
::

## 13. สรุป

- **Loopback** (`lo`, 127.0.0.0/8, ::1) ให้เครื่องคุยกับตัวเอง ข้อมูลผ่านสแต็ก TCP/IP ในเคอร์เนลแต่ไม่ออกการ์ดเครือข่าย จึงไม่มี ARP ไม่มีสัญญาณหาย และ MTU ใหญ่ (65,536)
- **localhost** เป็นชื่อ ถูกแปลงด้วยไฟล์ **hosts** ก่อน DNS เป็น 127.0.0.1 หรือ ::1 ระวังกรณีลอง IPv6 ก่อนแต่เซิร์ฟเวอร์ฟังแค่ IPv4
- เคอร์เนลเลือกทางด้วย **ตารางเส้นทาง** และกฎ **longest prefix match** (ยาวที่สุดชนะ ไม่เกี่ยวกับลำดับ)
- **Default gateway** คือแถว `0.0.0.0/0` ต้องอยู่ซับเน็ตเดียวกับเรา เครื่องจะ ARP หา MAC ของ *เกตเวย์* ส่วน IP ปลายทางยังเป็นของจริง
- ไม่มี default route → ออกนอกซับเน็ตไม่ได้ (`Network is unreachable` ทันที) แต่คุยกับเพื่อนบ้านในซับเน็ตได้
- ตั้งค่าบน Linux ด้วย `ip route` (ชั่วคราว) หรือ Netplan (ถาวร) บน Windows ด้วย PowerShell หรือ `ncpa.cpl`
- bind `127.0.0.1` = เฉพาะในเครื่อง, `0.0.0.0` = ทุกอินเทอร์เฟซ
- Security: อย่าถือว่า localhost ปลอดภัย (SSRF, DNS rebinding), ระวังไฟล์ hosts ถูกแก้, เกตเวย์เป็นเป้าของ ARP spoofing และ rogue DHCP
- บทถัดไป: DHCP, DNS และ NAT ที่แจก IP/gateway และแปลงที่อยู่โดยอัตโนมัติ
