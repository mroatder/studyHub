## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายว่า **ping** ใช้ ICMP Echo Request/Reply ทำงานอย่างไร (รวมขั้น ARP ก่อนส่ง) และอ่านค่า TTL, RTT, packet loss, jitter ได้
2. แยกข้อความผิดพลาดของ ping ให้ออกว่าชี้สาเหตุต่างกัน (Unreachable จากใคร, Timeout, TTL expired, Network is unreachable)
3. อธิบายกลไก **traceroute** ที่ใช้ TTL หมดอายุและ ICMP Time Exceeded เพื่อไล่หาเราเตอร์ทีละฮอป
4. อ่านผล traceroute โดยไม่สรุปผิดจากเครื่องหมาย `*`, ค่าหน่วงที่พุ่งกลางทาง และเส้นทางไป-กลับที่ต่างกัน
5. ใช้ **nslookup** ถามระเบียน DNS ชนิดต่างๆ จากเซิร์ฟเวอร์ที่เลือก และแยก NXDOMAIN, SERVFAIL, timeout
6. เรียงลำดับการวินิจฉัยจากล่างขึ้นบนด้วยสามเครื่องมือ และรู้ว่าแต่ละขั้น *พิสูจน์* อะไรและ *ไม่พิสูจน์* อะไร
7. ระบุผลกระทบด้าน Security (ping sweep, ICMP tunneling, ข้อมูลโครงสร้างเครือข่ายที่รั่ว, DNS recon) และเหตุที่ไม่ควรบล็อก ICMP ทั้งหมด

## สรุปสั้น (TL;DR)

- **ping** = ถามว่า "ได้ยินไหม" ด้วย ICMP Echo แล้ววัดเวลาไป-กลับ (RTT) · ตอบ = ถึงกันได้อย่างน้อยในชั้น IP · *ไม่ตอบ ≠ ล่ม* เพราะ ICMP มักถูกกรอง
- **traceroute / tracert** = ส่งแพ็กเก็ตที่ TTL=1, 2, 3, … ให้เราเตอร์แต่ละตัวทิ้งแล้วตอบ ICMP Time Exceeded กลับ เราจึงรู้ว่าฮอปที่ n คือใคร
- **nslookup** = ถามเซิร์ฟเวอร์ DNS ตรงๆ ว่าชื่อนี้ชี้ไปไหน แยกปัญหา "ชื่อ" ออกจากปัญหา "เครือข่าย"
- วินิจฉัยเป็นบันได: ลิงก์ → ตัวเอง (127.0.0.1) → เกตเวย์ → IP นอก → DNS → บริการจริง จุดแรกที่ล้มคือเบาะแสแรก
- **ข้อควรจำ:** ทั้งสามเครื่องมือทดสอบชั้นล่าง ถ้าทุกอย่างผ่านแต่แอปยังพัง ปัญหาอยู่ชั้นบน (บริการ, ใบรับรอง, ไฟร์วอลล์ระดับพอร์ต)

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | สิ่งที่เทียบได้ |
|---|---|
| ตะโกนว่า "ได้ยินไหม" ในอุโมงค์แล้วจับเวลาจนเสียงสะท้อนกลับ | ping: Echo Request/Reply และ RTT |
| ส่งพัสดุทดลองที่เขียนว่า "ให้ทิ้งเมื่อผ่านจุดคัดแยกครบ 1 จุด" แล้วขอใบแจ้งจากจุดนั้น ทีละจำนวนจุดเพิ่มขึ้น | traceroute: TTL หมดอายุ → Time Exceeded |
| จุดคัดแยกบางแห่งไม่ตอบใบแจ้งเพราะนโยบายองค์กร แต่พัสดุจริงยังผ่านไปได้ | `*` กลางเส้นทางที่ฮอปถัดไปยังตอบ |
| โทรถามเลขทะเบียนที่สมุดโทรศัพท์ (ไม่ได้โทรหาตัวบุคคล) | nslookup: ถามเฉพาะสมุดรายชื่อ ไม่ได้ทดสอบว่าปลายทางรับสาย |
| หมอไล่ตรวจจากชีพจร → ปอด → อวัยวะ ไม่ข้ามขั้น | บันไดวินิจฉัยล่างขึ้นบน |

## 1. ปัญหาตั้งต้น: ต้องการ "เครื่องมือถามตอบ" ที่ง่ายที่สุด

เมื่อผู้ใช้บอกว่า "เปิดเว็บไม่ได้" มีจุดที่เป็นไปได้หลายสิบจุดเรียงกัน: สาย → การ์ด → IP → เกตเวย์ → ISP → เส้นทาง → DNS → เซิร์ฟเวอร์ → พอร์ต → แอป เราต้องการเครื่องมือที่ *ตัดตัวเลือกออกครึ่งหนึ่ง* ทีละขั้น และต้องง่ายพอที่ทุกระบบมีติดมาด้วย ซึ่งเป็นที่มาของสามเครื่องมือนี้

| เครื่องมือ | คำถามที่ตอบ | ใช้โปรโตคอลอะไร |
|---|---|---|
| `ping` | ปลายทางตอบไหม ช้าเท่าไร หายไหม | ICMP Echo (ชั้น 3) |
| `traceroute` / `tracert` | แพ็กเก็ตผ่านเราเตอร์ตัวไหนบ้าง ไปหยุดที่ไหน | TTL + ICMP Time Exceeded |
| `nslookup` | ชื่อนี้ DNS ตอบว่าอะไร | DNS ผ่าน UDP/TCP พอร์ต 53 |

**ICMP** (Internet Control Message Protocol) เป็นโปรโตคอลรายงาน/ควบคุมที่ตัวหัวอยู่บน IP (หมายเลขโปรโตคอล 1) ไม่มีพอร์ต ไม่ใช่ TCP หรือ UDP เป็นเหตุผลที่ ping ไม่ได้พิสูจน์ว่าพอร์ตใดเปิด

## 2. Ping: ถามว่าได้ยินไหม

### 2.1 กลไก

ping สร้าง ICMP **Echo Request (type 8)** ใส่ตัวระบุ (identifier) เลขลำดับ (sequence) และข้อมูลทดสอบ ส่งผ่าน IP ปลายทางตอบ **Echo Reply (type 0)** กลับด้วยค่าเดิม ping จับเวลาระหว่างส่งกับรับ = **RTT** (round-trip time)

ก่อนส่งจริง ถ้าปลายทางอยู่ซับเน็ตเดียวกัน (หรือต้องส่งผ่านเกตเวย์) เครื่องต้องรู้ MAC ของฮอปถัดไปก่อน จึงมี **ARP** นำหน้า (บทสวิตช์/เกตเวย์) นี่คือเหตุที่ "Destination Host Unreachable" จากเครื่องเราเองมักหมายถึง ARP ไม่สำเร็จ

### 2.2 อ่านผลลัพธ์

```text
$ ping -c 4 192.168.1.1
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.812 ms
...
4 packets transmitted, 4 received, 0% packet loss, time 3062ms
rtt min/avg/max/mdev = 0.698/0.743/0.812/0.043 ms
```

| ค่า | ความหมาย | ใช้อ่านอะไร |
|---|---|---|
| `bytes` | ขนาดเนื้อ ICMP ที่ตอบ (Linux 64 = 56 + 8) | ขนาดแพ็กเก็ตทดสอบ |
| `icmp_seq` | เลขลำดับ | ข้ามเลข = ตอบไม่ครบ/สลับลำดับ |
| `ttl` | TTL ที่เหลือเมื่อตอบถึงเรา | ประมาณจำนวนฮอป (ดูด้านล่าง) |
| `time` | RTT ของแพ็กเก็ตนั้น | หน่วง/ความแออัด |
| `packet loss` | สัดส่วนที่ไม่กลับ | สัญญาณเสีย/แออัด/ถูกกรอง |
| `mdev` / jitter | ความแกว่งของ RTT | เสียง/วิดีโอแย่ถ้าแกว่งมาก (RTT เฉลี่ยดีก็ไม่พอ) |

ตัวอย่างคำนวณจากสี่ค่า RTT ข้างบน (0.812, 0.745, 0.698, 0.720 ms; ตรวจด้วยการคำนวณจริง): ค่าเฉลี่ย ≈ **0.744 ms** ค่าเบี่ยงเบนมาตรฐาน ≈ **0.043 ms** loss 1 ใน 4 ฉบับ = 25%

### 2.3 TTL บอกจำนวนฮอปคร่าวๆ

ระบบปฏิบัติการตั้ง TTL เริ่มต้นต่างกัน ที่พบบ่อยคือ **64** (Linux, macOS), **128** (Windows), **255** (อุปกรณ์เครือข่ายหลายยี่ห้อ) ตัวเลขที่เหลือตอนตอบกลับ = ค่าเริ่มต้นของ *ผู้ตอบ* ลบจำนวนเราเตอร์ที่ผ่านระหว่างทางกลับ เช่นได้ `ttl=54` จากเซิร์ฟเวอร์ Linux แสดงว่าทางกลับผ่านราว 64 − 54 = **10** ฮอป (ค่าเริ่มต้นปรับแต่งได้ และเส้นทางกลับอาจต่างจากเส้นทางไป)

### 2.4 RTT ต่ำสุดถูกกำหนดด้วยฟิสิกส์

แสงในเส้นใยแก้วเดินทางช้ากว่าสุญญากาศราว 1.5 เท่า ≈ 200,000 กม./วินาที ดังนั้นไป-กลับ 100 กม. ใช้อย่างน้อย ≈ 1 ms ตัวอย่างต่ำสุดตามระยะตรง (คำนวณจริง; ระยะทางสายจริงยาวกว่าเส้นตรง และยังมีเวลาประมวลผลของอุปกรณ์ จึงจริงจะสูงกว่านี้เสมอ)

| คู่เมือง | ระยะตรงโดยประมาณ | RTT ต่ำสุดตามทฤษฎี |
|---|---|---|
| กรุงเทพ – สิงคโปร์ | ≈ 1,430 กม. | ≈ 14 ms |
| กรุงเทพ – โตเกียว | ≈ 4,600 กม. | ≈ 46 ms |
| กรุงเทพ – ลอนดอน | ≈ 9,500 กม. | ≈ 95 ms |

ใช้ประโยชน์: ถ้า ping ไปเซิร์ฟเวอร์ในเมืองเดียวกันได้ 80 ms แสดงว่ามีอะไรผิดปกติ (คิวแออัด, เส้นทางอ้อมไปไกล) แต่ถ้า ping ไปลอนดอนได้ 60 ms ผิดแน่ เพราะต่ำกว่าฟิสิกส์ ซึ่งแปลว่าเซิร์ฟเวอร์นั้นอยู่ใกล้กว่าที่คิว (เช่น CDN) หรือชื่อโดเมนชี้ไปที่อื่น

### 2.5 ข้อความผิดพลาดแต่ละแบบชี้สาเหตุต่างกัน

| ข้อความ | ใครรายงาน | ความหมายเชิงกลไก |
|---|---|---|
| `Destination Host Unreachable` **จาก IP ของเราเอง** | เครื่องเรา | ARP หาฮอปถัดไปไม่เจอ (ตั้งเกตเวย์ผิด วงไม่ตรง สายมีปัญหา) |
| `Destination Host/Net Unreachable` **จาก IP ของเราเตอร์** | เราเตอร์ | เราเตอร์ตัวนั้นไม่มีเส้นทางไปปลายทาง (ICMP type 3) |
| `Network is unreachable` (Linux) | เครื่องเรา | ไม่มีเส้นทางเลยใน routing table (เช่นอินเทอร์เฟซดับ ไม่มี default route) |
| `Request timed out` / ไม่มีการตอบ | ไม่มีใคร | ถูกทิ้งเงียบ (ไฟร์วอลล์ DROP, ปลายทางปิด, ทางกลับหาย) ไม่รู้ว่าหายตรงไหน |
| `TTL expired in transit` | เราเตอร์กลางทาง | TTL หมดก่อนถึง มักเป็นลูปเส้นทาง หรือเป้าหมายไกลเกินตั้ง TTL ไว้ |
| `General failure` (Windows) | เครื่องเรา | ไดรเวอร์/อะแดปเตอร์มีปัญหา ไม่ใช่เครือข่ายภายนอก |

### 2.6 ลองเอง: บันไดวินิจฉัย

รันคำสั่งทีละขั้นกับโจทย์ที่ซ่อนสาเหตุไว้ ดูว่าขั้นแรกที่ล้มคือขั้นไหน แล้วทายสาเหตุ กด "สุ่มโจทย์ใหม่" เพื่อฝึกกับกรณีอื่น โดยเฉพาะคู่ที่ดูคล้ายกัน (DNS ไม่ตอบ เทียบ NXDOMAIN, และสายหลุด เทียบ เกตเวย์ผิด)

## 3. Traceroute: หาว่าแพ็กเก็ตผ่านใครบ้าง

### 3.1 ทำไมต้องมี และ TTL ช่วยอย่างไร

ping บอกว่าถึง/ไม่ถึง แต่ไม่บอก *หยุดตรงไหน* ทางแก้อาศัยกลไกที่มีอยู่แล้ว: เราเตอร์ทุกตัวลด **TTL** ทีละ 1 และถ้าเหลือ 0 ต้องทิ้งแพ็กเก็ตแล้วส่ง **ICMP Time Exceeded (type 11)** กลับไปหาต้นทาง (กลไกกันลูป จากบทที่ผ่านมา) traceroute จึง *จงใจ* ส่งแพ็กเก็ตที่ TTL ต่ำเกินไป ให้เราเตอร์ฮอปที่ n ตอบกลับมาแนะนำตัว

รายละเอียดที่ควรรู้

- ส่ง **โพรบละ 3 ครั้งต่อฮอป** จึงมี 3 ค่า RTT ต่อบรรทัด · ค่าสูงสุดเริ่มต้น 30 ฮอป (จึงสูงสุด 90 โพรบ)
- **Linux/macOS** ค่าเริ่มต้นส่ง UDP ไปพอร์ตสูง (เริ่ม ≈ 33434 แล้วเพิ่ม) ส่วน **Windows `tracert`** ส่ง ICMP Echo ใช้ `-I` ใน Linux เพื่อเปลี่ยนเป็น ICMP · บางเครือข่ายกรองต่างกัน จึงลองสลับชนิดโพรบถ้าผลแปลก
- ใช้ `-n` (Linux) หรือ `-d` (Windows) เพื่อไม่ทำ reverse DNS ของแต่ละฮอป เร็วกว่ามากและไม่ปนปัญหา DNS
- IP ที่แสดงมักเป็นที่อยู่ของ **อินเทอร์เฟซขาเข้า** ของเราเตอร์ ไม่ใช่ตัวตนทั้งตัว เราเตอร์ตัวเดียวมีหลาย IP

### 3.2 อ่านผลโดยไม่สรุปผิด

```text
 1  192.168.1.1   0.841 ms  0.722 ms  0.690 ms
 2  10.50.0.1     4.112 ms  3.988 ms  4.021 ms
 3  198.51.100.2 14.520 ms 14.310 ms 14.402 ms
 4  * * *
 5  * * *
```

เครื่องหมาย `*` คือไม่ได้รับตอบภายในเวลาที่กำหนด **มันบอกแค่ว่า "ไม่มี ICMP ตอบมาถึงเรา" ไม่ได้บอกว่าแพ็กเก็ตหาย** ต้องใช้กฎต่อไปนี้ตัดสิน

| ลักษณะที่เห็น | แปลว่า | เหตุผลเชิงกลไก |
|---|---|---|
| `*` ในฮอปกลาง แต่ **ฮอปถัดไปตอบปกติ** และถึงเป้าหมาย | ไม่ใช่ปัญหา | เราเตอร์ตัวนั้นถูกตั้งให้ไม่ตอบ ICMP Time Exceeded (จำกัดอัตราหรือกรอง) แต่ยังส่งต่อแพ็กเก็ตจริงตามปกติ |
| `*` ตั้งแต่ฮอป n ไปจนจบ | จุดที่ควรสงสัย | อาจเป็นเส้นทางขาด ณ ฮอป n ไม่มีทางไปต่อ หรือไฟร์วอลล์กรองโพรบ หรือ **ทางกลับของ ICMP ถูกบล็อก** (แพ็กเก็ตไปถึงแต่ตอบกลับมาไม่ได้) ต้องจับดูอีกฝั่งหรือลองโพรบชนิดอื่น |
| RTT พุ่งที่ฮอปกลางเท่านั้น แล้วฮอปถัดไปกลับต่ำ | มักไม่ใช่ปัญหา | เราเตอร์ตอบ ICMP ด้วย CPU (control plane) ซึ่งช้ากว่าการส่งต่อแพ็กเก็ตจริง (data plane) และอาจจำกัดอัตราตอบ |
| RTT พุ่งที่ฮอป n และ **คงสูงตั้งแต่ n ไปจนถึงปลายทาง** | มีคอขวด/ลิงก์ไกลที่ฮอป n | ค่าหน่วงเป็นสะสมตลอดเส้นทางที่เหลือ เช่นข้ามทวีป (ดูตัวเลข 2.4 ว่าสมเหตุผลทางฟิสิกส์ไหม) |
| บรรทัดเดียวแสดงหลาย IP | มีการกระจายโหลด (ECMP) | โพรบต่างตัวถูกเลือกไปคนละเส้นทางคู่ขนาน |
| เส้นทางไปกับกลับต่างกัน | เส้นทางไม่สมมาตร (asymmetric) | traceroute เห็นแต่ทาง *ไป* ของโพรบ ส่วนค่าเวลาปนทางกลับที่เราไม่เห็น |

**เครื่องมือใกล้เคียง:** `mtr` (Linux/macOS) และ `pathping` (Windows) ทำ traceroute ต่อเนื่องแล้วสถิติ loss/หน่วงต่อฮอป เหมาะกับปัญหาที่เป็นๆ หายๆ ซึ่ง traceroute ครั้งเดียวจับไม่ได้

## 4. Nslookup: ถาม DNS ตรงๆ

### 4.1 ทำไมต้องแยกการทดสอบชื่อออกมา

เครือข่ายเดินทางด้วยเลข IP แต่คนใช้ชื่อ ระหว่างสองอย่างมี DNS คั่น ถ้า DNS เสียแต่เครือข่ายปกติ อาการ "เข้าเว็บไม่ได้" เหมือนเครือข่ายล่มทุกอย่าง `nslookup` ช่วยให้ถามด้านชื่อโดยตรง จึงแยกสองกรณีนี้ออกจากกันได้ทันที (กลไก DNS ทั้งสายอยู่ในบทที่ 17)

### 4.2 ใช้เป็น

```text
$ nslookup fileserver.corp              ← ถามเซิร์ฟเวอร์ DNS ที่เครื่องตั้งไว้
$ nslookup fileserver.corp 8.8.8.8      ← ถามเซิร์ฟเวอร์ที่เราเลือกเอง
$ nslookup -type=mx example.com         ← ขอระเบียนชนิดอื่น
$ nslookup 93.184.216.34                ← ถามย้อนกลับ (PTR จาก IP เป็นชื่อ)
```

| ชนิดระเบียน | ใช้ทำอะไร |
|---|---|
| A / AAAA | ชื่อ → IPv4 / IPv6 |
| CNAME | ชื่อเล่น ชี้ไปอีกชื่อ |
| MX | เซิร์ฟเวอร์รับอีเมลของโดเมน (มีค่าลำดับความสำคัญ) |
| NS | เซิร์ฟเวอร์ที่ดูแลโซนของโดเมน (authoritative) |
| TXT | ข้อความ ใช้กับ SPF/DKIM/การยืนยันความเป็นเจ้าของโดเมน |
| PTR | IP → ชื่อ (reverse lookup) |

### 4.3 อ่านผล: ผลลัพธ์ต่างแบบ = สาเหตุต่างแบบ

| สิ่งที่เห็น | แปลว่า | การวินิจฉัย |
|---|---|---|
| ได้ `Name`/`Address` | DNS ตอบสำเร็จ | ตรวจว่า IP ตรงที่คาดไหม (ระเบียนเก่า?) |
| `NXDOMAIN` (Non-existent domain) | **เซิร์ฟเวอร์ตอบ** ว่าไม่มีชื่อนี้ | พิมพ์ชื่อผิด ระเบียนยังไม่สร้าง/ลบแล้ว โดเมนหมดอายุ หรือถามเซิร์ฟเวอร์ผิด เช่นชื่อภายในไปถาม 8.8.8.8 |
| `SERVFAIL` | เซิร์ฟเวอร์ตอบว่า *ทำไม่ได้* | ปลายน้ำล้ม เช่น authoritative server ดับ หรือ DNSSEC ตรวจไม่ผ่าน |
| `REFUSED` | เซิร์ฟเวอร์ปฏิเสธ | ไม่รับคำถามจากเรา (ACL) |
| `connection timed out; no servers could be reached` | **ไม่มีใครตอบเลย** | เซิร์ฟเวอร์ DNS ดับ ถึงไม่ได้ หรือพอร์ต 53 ถูกกรอง |
| `Non-authoritative answer` | ตอบจาก *แคช* ของ resolver | ไม่ใช่ปัญหา แค่บอกว่าไม่ได้ถามเจ้าของโซนโดยตรง (ค่ามีอายุตาม TTL) |

ความต่างของ NXDOMAIN กับ timeout สำคัญมาก: **NXDOMAIN แปลว่า DNS ทำงานดี** แต่ไม่มีข้อมูล ส่วน timeout แปลว่า DNS ไม่ทำงานหรือไปไม่ถึง

### 4.4 ข้อควรระวังเฉพาะของ nslookup

- nslookup ใช้ตัวแก้ชื่อของตัวเอง **ไม่ผ่านตัวแก้ชื่อของระบบปฏิบัติการ** ดังนั้นไม่เห็นผลของไฟล์ `hosts`, DNS suffix search list หรือกฎ DNS ตามโดเมน (เช่นกับ VPN) ที่ `ping ชื่อ` และเบราว์เซอร์ใช้ ถ้าสองฝั่งให้ผลต่างกัน นี่คือเหตุที่น่าสงสัยอันดับต้นๆ บน Windows ใช้ `Resolve-DnsName` และดู `ipconfig /displaydns`
- ในแวดวง Linux/ผู้ดูแลระบบ `dig` ให้ข้อมูลละเอียดกว่า (TTL, flag aa/ra, ส่วน authority) และ nslookup ถูกมองว่าเก่า แต่ยังติดมากับ Windows จึงรู้ไว้ใช้ได้
- **ตรวจ propagation:** เมื่อเปลี่ยนระเบียน ให้ถามหลาย resolver (8.8.8.8, 1.1.1.1, ของ ISP) และถามเซิร์ฟเวอร์ authoritative ตรง (หาด้วย `-type=ns` แล้วระบุเป็นอาร์กิวเมนต์ที่สอง) ถ้า authoritative ตอบใหม่แต่ resolver ตอบเก่า แสดงว่ายังรอแคชหมดอายุ (TTL) ไม่ใช่ระเบียนผิด · NXDOMAIN ก็ถูกแคชได้เช่นกัน (negative caching) ตามค่าที่โซนกำหนด

## 5. ลำดับวินิจฉัยเป็นบันได

หลักคือ *ทดสอบจากชั้นล่างขึ้นบน และใช้ IP ก่อนชื่อ* เพราะแต่ละขั้นตัดตัวเลือกด้านล่างทิ้งได้ (ถ้าขั้น n ผ่าน ขั้นก่อนหน้าไม่ต้องสงสัย)

| ขั้น | คำสั่ง | พิสูจน์อะไร | ไม่พิสูจน์อะไร |
|---|---|---|---|
| 0 | ดูไฟลิงก์ / `ip link` / `ipconfig` | ลิงก์ขึ้นไหม มี IP ไหม (169.254.x.x = DHCP ล้ม) | ลิงก์ขึ้น ไม่ได้แปลว่าใช้ได้ |
| 1 | `ping 127.0.0.1` | สแต็ก TCP/IP ของเครื่องทำงาน | **ไม่ได้ทดสอบการ์ดหรือสาย** (ข้ามการ์ดตามบท loopback) |
| 2 | `ping <เกตเวย์>` | ถึงวงเดียวกันได้ ARP ผ่าน IP/mask ถูก | เกตเวย์ไม่ตอบ ICMP ได้ ทั้งที่ส่งต่อได้ |
| 3 | `ping 8.8.8.8` | ออกอินเทอร์เน็ตได้ด้วย IP | บางเครือข่ายกรอง ICMP ออก |
| 4 | `nslookup <ชื่อ>` | DNS ที่ตั้งไว้ตอบถูก | ผ่านไม่ได้แปลว่าแอปจะใช้ผลเดียวกัน (hosts/suffix) |
| 5 | `ping <ชื่อ>` / `curl` ที่พอร์ตแอป | ถึงบริการจริง | `ping` ผ่านไม่ได้แปลว่า TCP พอร์ตนั้นเปิด |
| ถ้าผิด | `traceroute <IP นอก>` | ขาดหลังฮอปไหน | ดูหัวข้อ 3.2 ก่อนสรุป |

ถ้าทุกขั้นผ่านแต่ผู้ใช้ยังใช้งานไม่ได้ ปัญหาอยู่เหนือชั้นนี้: บริการดับ, ใบรับรอง TLS หมดอายุ, ไฟร์วอลล์ระดับพอร์ต, การยืนยันตัวตน ถึงเวลาจับแพ็กเก็ตดู (บทถัดไป)

## 6. มุมมองด้าน Security

| ประเด็น | กลไก | การป้องกัน / ข้อควรทำ |
|---|---|---|
| **Ping sweep / การสแกนหาเครื่องที่ยังอยู่** | ผู้โจมตี ping ทั้งซับเน็ตเพื่อรู้ว่ามีเครื่องไหนอยู่ (ARP ในวงเดียวกันยิ่งเร็ว) | ไฟร์วอลล์กรอง ICMP จากภายนอก (แต่ระวังข้อถัดไป), ตรวจจับด้วย IDS |
| **Traceroute เปิดเผยโครงสร้าง** | เห็น IP และชื่อ DNS ของเราเตอร์ ความสัมพันธ์ ISP ตำแหน่งที่ตั้ง | ตั้งชื่ออินเทอร์เฟซไม่เปิดข้อมูลภายใน, จำกัดการตอบ ICMP ที่ขอบเครือข่าย |
| **บล็อก ICMP ทั้งหมดทำให้เสียหาย** | ICMP type 3 code 4 (Fragmentation Needed) คือกลไกที่ PMTUD ใช้ค้นหา MTU ถ้าบล็อก เว็บบางแห่งเชื่อมต่อได้แต่ **ส่งข้อมูลขนาดใหญ่ค้าง** (อาการ handshake ผ่านแต่โหลดไม่ขึ้น) | อนุญาต ICMP ที่จำเป็น (type 3, type 11, echo ตามนโยบาย) ไม่บล็อกทั้งหมดแบบหยาบๆ |
| **Smurf / ICMP amplification** (ประวัติศาสตร์) | ส่ง ping ไปยังที่อยู่ broadcast โดยปลอมต้นทางเป็นเหยื่อ ทุกเครื่องในวงตอบเหยื่อ | ปัจจุบันเราเตอร์ปิด directed broadcast ตามค่าเริ่มต้น |
| **ICMP tunneling** | ซ่อนข้อมูลใน payload ของ echo เพื่อลอบส่งออก/คุมเครื่อง เมื่อไฟร์วอลล์ปล่อย ICMP | ตรวจ echo ที่ payload ใหญ่/ถี่ผิดปกติ จำกัดขนาดและอัตรา |
| **TTL เป็นลายนิ้วมือ** | ค่า TTL เริ่มต้น (64/128/255) เดาตระกูลระบบปฏิบัติการได้ | ไม่ใช่ความลับ แต่ไม่ควรพึ่งการซ่อน |
| **DNS reconnaissance** | ผู้โจมตีใช้ nslookup/dig หา NS, MX, TXT, ชื่อย่อยที่ลืมปิด และลอง zone transfer (AXFR) ขอโซนทั้งก้อน | จำกัด AXFR เฉพาะ secondary ที่อนุญาต อย่าเก็บข้อมูลอ่อนไหวใน TXT/ชื่อโฮสต์ |
| **DNS tunneling / ชื่อโดเมนแปลก** | ซ่อนข้อมูลในชื่อยาวๆ ของคำถาม DNS | ตรวจชื่อยาว/สุ่ม/จำนวนคำถามผิดปกติ |
| **ผลทดสอบถูกปลอมได้** | ผู้ควบคุมเส้นทางตอบ ICMP/DNS ปลอมได้ (cache poisoning, DNS hijack) | ใช้ DNSSEC/DoT/DoH, ยืนยันผลจากหลายแหล่ง |

**ข้อควรจำทางจริยธรรม:** ใช้ ping sweep/traceroute/ถามโซนกับเครือข่ายที่คุณดูแลหรือได้รับอนุญาตเท่านั้น การสแกนเครือข่ายผู้อื่นอาจผิดนโยบายหรือกฎหมาย

## 7. ตัวอย่างวิเคราะห์ปัญหา IT Support

| อาการ | สิ่งที่บอก | การวินิจฉัยเชิงกลไก |
|---|---|---|
| ping เกตเวย์ได้ "Unreachable จาก IP ของเรา" | ARP ไม่สำเร็จ | IP/mask/เกตเวย์ตั้งผิดวง, พอร์ตสวิตช์ผิด VLAN, สายหลวม ตรวจ `arp -a` ว่ามีรายการเกตเวย์ไหม |
| ping เกตเวย์ได้ แต่ ping 8.8.8.8 ไม่ได้ | ปัญหาเลยเกตเวย์ | ดู Unreachable จากเราเตอร์ (ไม่มีเส้นทาง) หรือ timeout (ถูกทิ้ง) แล้ว traceroute ดูหายหลังฮอปไหน และถามผู้ให้บริการ |
| ping 8.8.8.8 ได้ แต่เปิดเว็บด้วยชื่อไม่ได้ | DNS | `nslookup ชื่อ 8.8.8.8` ได้ = DNS ที่ตั้งไว้เสีย (เปลี่ยนชั่วคราวเพื่อยืนยัน) · NXDOMAIN = ชื่อผิด/ระเบียนหาย |
| nslookup ได้ IP แต่ `ping ชื่อ` หรือเบราว์เซอร์ไม่ได้ | ตัวแก้ชื่อของระบบต่างจาก nslookup | ไฟล์ hosts, DNS suffix, VPN split DNS, แคช DNS ของเครื่อง (`ipconfig /flushdns`) |
| ping เซิร์ฟเวอร์ไม่ตอบ แต่เว็บเข้าได้ | ICMP ถูกกรอง | ไม่ใช่ปัญหา ทดสอบที่พอร์ตจริงแทน (`curl`, `Test-NetConnection -Port`) |
| ping ผ่าน แต่เปิดเว็บแล้ว Connection refused | ถึงเครื่องแต่ไม่มีบริการฟัง | แก้ที่บริการ/พอร์ต ไม่ใช่เครือข่าย |
| ping RTT แกว่งมาก บางครั้งหาย | ลิงก์แออัดหรือสัญญาณไม่ดี | Wi-Fi: สัญญาณ/สัญญาณรบกวน, ลิงก์: duplex mismatch หรือสายเสีย ใช้ `ping -t`/`mtr` ดูต่อเนื่อง |
| traceroute `*` กลางทางแล้วถึงปลายทางได้ | ไม่ใช่ปัญหา | เราเตอร์กลางไม่ตอบ ICMP Time Exceeded ตามนโยบาย |
| traceroute `*` ตั้งแต่ฮอปหนึ่งถึงจบ | สงสัยจุดนั้นหรือหลังจุดนั้น | ลองโพรบชนิดอื่น (`-I`/`-T`) ตรวจจากอีกฝั่ง จับด้วย Wireshark ที่ปลายทางว่าโพรบถึงไหม |
| เว็บเชื่อมต่อได้แต่โหลดไฟล์ใหญ่ค้าง | MTU/PMTUD | ทดสอบ `ping -M do -s <ขนาด>` หา MTU จริง เช็กว่า ICMP type 3 ถูกกรองไหม |

## 9. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: ผู้ใช้เปิด intranet.corp ไม่ได้ ping intranet.corp ได้ Name or service not known แต่ ping 10.0.0.15 ได้ 4 ฉบับ สาเหตุคืออะไร"}
ปัญหาอยู่ที่การแปลงชื่อเป็น IP (DNS) ไม่ใช่เครือข่าย เพราะเข้าถึงด้วย IP ได้ ตรวจ DNS ที่เครื่องตั้งไว้และระเบียนของชื่อนั้น (nslookup)
::

::reveal{question="ข้อ 2: ทำไม traceroute บางครั้งขึ้น * ที่ฮอปกลางทาง แต่ฮอปถัดๆ ไปตอบปกติ"}
เราเตอร์ฮอปนั้นไม่ตอบ ICMP Time Exceeded (ตั้งนโยบายกรองหรือจำกัดอัตรา) แต่ยังส่งต่อแพ็กเก็ตจริงตามปกติ มิฉะนั้นฮอปถัดไปจะไม่ได้รับโพรบเลย `*` หมายถึงไม่มีตอบ ไม่ได้แปลว่าแพ็กเก็ตหาย
::

::reveal{question="ข้อ 3: Authoritative กับ Non-authoritative ใน nslookup ต่างกันอย่างไร"}
Authoritative คือตอบจากเซิร์ฟเวอร์ที่ดูแลโซนนั้นโดยตรง ส่วน Non-authoritative คือตอบจากแคชของ resolver ที่เคยถามมาก่อน ค่าอาจเก่าได้ถึงหมดอายุตาม TTL ไม่ได้แปลว่าผิด
::

::reveal{question="ข้อ 4: ทำไม ping เซิร์ฟเวอร์สำเร็จ แต่ HTTP ไปเซิร์ฟเวอร์เดียวกันหมดเวลา"}
ping ใช้ ICMP ไม่ได้ทดสอบ TCP พอร์ต 80/443 ไฟร์วอลล์อาจอนุญาต ICMP แต่ทิ้งพอร์ตแอป หรือบริการอาจไม่ฟัง (ถ้า refused) ทดสอบด้วย curl หรือ Test-NetConnection -Port และเทียบ timeout กับ refused
::

::reveal{question="ข้อ 5: ได้รับ ping reply ttl=54 จากเซิร์ฟเวอร์ Linux ประมาณกี่ฮอปทางกลับ และข้อจำกัดคือ"}
64 − 54 = 10 ฮอป ข้อจำกัด: ถือว่าค่าเริ่มต้นเป็น 64 (อาจไม่ใช่ ถ้า 128 จะเป็น 74 ฮอป ซึ่งไม่สมเหตุผล) และเส้นทางกลับอาจต่างจากทางไป
::

::reveal{question="ข้อ 6: ping กรุงเทพ–ลอนดอน (≈ 9,500 กม.) ได้ 40 ms ผิดปกติอย่างไร"}
RTT ต่ำสุดตามฟิสิกส์ ≈ 2 × 9,500 ÷ 200,000 = 0.095 วินาที = 95 ms (เส้นตรง ค่าประมาณ) 40 ms เร็วเกินไป ปลายทางจึงต้องอยู่ใกล้กว่านั้น เช่น CDN/anycast หรือชื่อชี้ไปที่อื่น
::

::reveal{question="ข้อ 7: nslookup ให้ IP ที่ถูกต้อง แต่เบราว์เซอร์ไปที่ IP เก่า เป็นไปได้เพราะอะไร"}
nslookup ใช้ตัวแก้ชื่อของตัวเองถามเซิร์ฟเวอร์ตรง ส่วนเบราว์เซอร์ใช้ตัวแก้ชื่อของระบบ (ผ่านไฟล์ hosts, แคช DNS ของเครื่อง, แคชเบราว์เซอร์, DNS ตามกฎ VPN) ตรวจ hosts ล้างแคช (ipconfig /flushdns) และใช้ Resolve-DnsName เพื่อเห็นสิ่งที่ระบบเห็น
::

::reveal{question="ข้อ 8: จะเช็กว่าระเบียน DNS ที่เพิ่งแก้ propagate แล้วหรือยังอย่างไร"}
หา NS ของโดเมน (nslookup -type=ns) แล้วถามเซิร์ฟเวอร์ authoritative ตรงเพื่อยืนยันว่าค่าใหม่ถูกต้อง จากนั้นถาม resolver สาธารณะหลายตัว (8.8.8.8, 1.1.1.1 ฯลฯ) ถ้า resolver ใดยังตอบค่าเก่า ให้รอตามค่า TTL เดิม เพราะแคชยังไม่หมดอายุ
::

::reveal{question="ข้อ 9: ทำไมการบล็อก ICMP ทั้งหมดที่ไฟร์วอลล์ขอบจึงอาจทำให้เว็บบางแห่งโหลดค้าง"}
เพราะ PMTUD อาศัย ICMP type 3 code 4 ที่เราเตอร์กลางทางส่งกลับเมื่อแพ็กเก็ตใหญ่เกิน MTU ที่ตั้ง DF ไว้ ถ้าถูกบล็อก ต้นทางไม่รู้ว่าต้องลดขนาด แพ็กเก็ตใหญ่ถูกทิ้งเงียบ handshake (แพ็กเก็ตเล็ก) ผ่านแต่ข้อมูลใหญ่ค้าง
::

::reveal{question="ข้อ 10: ลำดับตรวจเมื่อเครื่องใหม่ต่อสายแล้วเข้าเน็ตไม่ได้ ได้ IP 169.254.x.x"}
(1) ลิงก์ขึ้นไหม (2) 169.254.x.x = APIPA หมายถึง DHCP ไม่ตอบ จึงไม่ต้องไล่ DNS (3) ดูพอร์ตสวิตช์ว่าอยู่ VLAN ถูกไหม (4) DHCP server/relay ทำงานไหม (บท 17/18) (5) ตั้ง IP ชั่วคราวด้วยมือเพื่อแยกว่าเป็นเรื่อง DHCP หรือเครือข่าย แล้ว ping เกตเวย์
::

## 10. แบบฝึกหัด (ลงมือทำจริง)

ใช้กับเครื่องของคุณเอง คำสั่งอ่านอย่างเดียว

1. **วัดบันไดของคุณ:** รัน `ping 127.0.0.1` → ping เกตเวย์ของคุณ → `ping 8.8.8.8` → `nslookup example.com` จดว่าแต่ละขั้นผ่านและ RTT เท่าไร (หาเกตเวย์ด้วย `ip route` หรือ `ipconfig`)
2. **เทียบ RTT กับระยะ:** ping เว็บในประเทศกับต่างประเทศ (เช่น เซิร์ฟเวอร์ในสิงคโปร์/ยุโรป) แล้วเทียบกับตารางหัวข้อ 2.4 ว่าสมเหตุผลทางฟิสิกส์ไหม
3. **หาจำนวนฮอปจาก TTL:** ดู `ttl` ใน ping ไป 8.8.8.8 แล้วเทียบกับจำนวนบรรทัดของ `traceroute -n 8.8.8.8` / `tracert -d 8.8.8.8`
4. **ทดลอง traceroute สองแบบ:** บน Linux ลอง `traceroute -n` เทียบกับ `traceroute -n -I` ดูว่ามีฮอปที่เปลี่ยนจาก `*` เป็นตอบได้ไหม
5. **หา MTU เส้นทางของคุณ:** ลอง `ping -c 1 -M do -s 1472 8.8.8.8` (Linux) หรือ `ping -n 1 -f -l 1472 8.8.8.8` (Windows) แล้วลดขนาดลงเรื่อยๆ ถ้าไม่ผ่าน (ถ้า 1472 ผ่านคือ MTU 1500)
6. **ถาม DNS สองที่:** `nslookup example.com` เทียบ `nslookup example.com 8.8.8.8` และ `nslookup -type=ns example.com` แล้วถาม authoritative โดยตรง ดูว่าคำตอบตรงกันไหม และมีคำว่า Non-authoritative ไหม
7. **ทดสอบ NXDOMAIN:** `nslookup this-name-should-not-exist-12345.example.com` อ่านข้อความผิดพลาดแล้วเทียบกับกรณีระบุเซิร์ฟเวอร์ที่ไม่มีอยู่จริง (`nslookup example.com 192.0.2.1`) ที่ควรขึ้น timeout (192.0.2.0/24 เป็นช่วงสำหรับเอกสาร ไม่มีใครตอบ) อธิบายความต่าง

::reveal{question="แนวคำตอบ"}
(1) ผ่านทุกขั้นและเกตเวย์ RTT ต่ำกว่า 5 ms ในเครือข่ายบ้านปกติ · (2) RTT ต่างประเทศไม่ควรต่ำกว่าค่าต่ำสุดตามระยะ ถ้าต่ำกว่านั้น ปลายทางอาจเป็น CDN/anycast ใกล้คุณ · (3) จำนวนฮอปจาก TTL กับ traceroute ใกล้เคียงกันแต่ไม่จำเป็นต้องเท่ากัน ทางกลับอาจต่างและบางฮอปไม่ตอบ · (4) บางเครือข่ายตอบ ICMP แต่กรอง UDP หรือกลับกัน · (5) ถ้า 1472 ไม่ผ่าน ลองค่าที่ต่ำกว่า เช่น 1464 สำหรับ PPPoE (MTU 1492) · (6) คำตอบ IP ควรตรง ถ้า resolver ตอบ Non-authoritative แต่ authoritative ตอบ authoritative ตรงต่างกัน คือยังรอแคช · (7) NXDOMAIN ได้คำตอบทันทีจากเซิร์ฟเวอร์ ส่วนเซิร์ฟเวอร์ที่ไม่มีจริงจะ timeout นาน
::

## 11. สรุป

- **ping** ใช้ ICMP Echo (type 8/0) ผ่าน ARP ก่อนถ้าอยู่ใกล้ วัด RTT, loss, jitter; TTL ที่ตอบกลับบอกจำนวนฮอปทางกลับคร่าวๆ; RTT มีค่าต่ำสุดตามระยะทางฟิสิกส์
- ข้อความผิดพลาดชี้ต่างกัน: Unreachable **จากเรา** = ARP/ไม่มีเส้นทางในเครื่อง · จาก **เราเตอร์** = เราเตอร์ไม่มีเส้นทาง · timeout = ถูกทิ้งเงียบ ไม่รู้หายตรงไหน
- **traceroute** ใช้ TTL=1,2,3,… ให้เราเตอร์ทีละตัวตอบ ICMP Time Exceeded; `*` ไม่ได้แปลว่าหาย; RTT พุ่งกลางทางไม่ใช่ปัญหาถ้าฮอปถัดไปกลับปกติ; เส้นทางไปกับกลับอาจต่างกัน
- **nslookup** ถาม DNS ตรง: NXDOMAIN = DNS ทำงานแต่ไม่มีชื่อ · timeout = ไม่มีใครตอบ · Non-authoritative = ตอบจากแคช; nslookup ไม่ผ่านตัวแก้ชื่อของระบบ จึงอาจต่างจากเบราว์เซอร์
- วินิจฉัยเป็นบันไดล่างขึ้นบนและใช้ IP ก่อนชื่อ; ขั้นที่ผ่านทั้งหมดแต่แอปพังแปลว่าปัญหาอยู่ชั้นบน
- Security: ping sweep, ICMP tunneling, ข้อมูลโครงสร้างจาก traceroute, DNS recon/AXFR; อย่าบล็อก ICMP ทั้งหมด เพราะ PMTUD ต้องใช้ type 3
- ข้อจำกัด: ICMP มักถูกกรอง ผล ping/traceroute จึงไม่ใช่ความจริงของ TCP บริการ, ค่า TTL เริ่มต้นเป็นสมมติฐาน, และผล DNS จาก nslookup ไม่ใช่ทุกอย่างที่แอปเห็น
- บทถัดไป: เมื่อเครื่องมือเหล่านี้บอกว่าเครือข่ายปกติแต่แอปยังพัง ให้จับแพ็กเก็ตด้วย Wireshark ดูบทสนทนาจริง
