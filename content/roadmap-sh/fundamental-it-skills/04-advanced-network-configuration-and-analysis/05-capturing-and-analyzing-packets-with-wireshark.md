## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายเส้นทางของเฟรมจากสายสู่หน้าจอ Wireshark: การ์ดเครือข่าย → ไดรเวอร์ → ตัวกรอง BPF ในเคอร์เนล → libpcap/Npcap → dumpcap → GUI
2. อธิบายว่า **promiscuous mode** ทำอะไร และ *ทำไมบนเครือข่ายที่ใช้สวิตช์ มันมักยังไม่พอ* (ต้องใช้ SPAN/TAP, monitor mode)
3. อ่านไบต์ดิบ (hex) ของเฟรม Ethernet + IPv4 + TCP ด้วยมือ และตรวจ checksum ได้ถูก
4. แยก **capture filter (BPF)** ออกจาก **display filter** และเขียนตัวกรองที่พบบ่อยได้ รวมถึงกับดักของ `!=`
5. อ่าน TCP three-way handshake ใน Wireshark และอธิบายว่าเลข sequence แบบ *relative* คืออะไร
6. ใช้ **Follow Stream**, **tcpdump** และ **tshark** จับและวิเคราะห์ทราฟฟิกบนเซิร์ฟเวอร์ที่ไม่มีหน้าจอ
7. วินิจฉัย *connection refused*, *timeout (firewall drop)* และ *IP ซ้ำ* จากลายเซ็นของแพ็กเก็ต พร้อมคำนวณเวลา retransmission
8. ระบุความเสี่ยงด้าน Security และข้อควรระวังทางกฎหมาย/จริยธรรมของการดักจับ

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | สิ่งที่เทียบได้ |
|---|---|
| ถ่ายสำเนาจดหมายทุกฉบับที่ผ่านห้องไปรษณีย์ แล้วเก็บต้นฉบับส่งต่อตามปกติ | การจับแพ็กเก็ต: ได้สำเนา ไม่ขัดการส่งจริง |
| พนักงานไปรษณีย์ปกติรับเฉพาะจดหมายที่จ่าหน้าถึงห้องตัวเอง แต่สายตรวจสอบรับดูทุกฉบับ | โหมดปกติเทียบ promiscuous |
| ตั้งกฎ "ถ่ายสำเนาเฉพาะจดหมายจากบริษัท X" ก่อนเข้าตู้เก็บเอกสาร จดหมายอื่นไม่เคยเข้าตู้ | capture filter: ตัดทิ้งก่อนบันทึก |
| เก็บสำเนาทุกฉบับไว้ในตู้ แต่เวลาค้นหาก็แค่หยิบเฉพาะแฟ้มของบริษัท X ออกมาดู | display filter: ซ่อนตอนดู ของยังอยู่ |
| บันทึกเสียงโทรศัพท์ทั้งสายแล้วถอดความเป็นบทสนทนา | Follow Stream: ประกอบข้อมูลทีละแพ็กเก็ตกลับเป็นบทสนทนา |

## 1. ปัญหาตั้งต้น: ทำไมต้องดูถึงระดับแพ็กเก็ต

> **นึกภาพว่า:** ping บอกแค่ว่า "ไปรษณีย์ส่งถึงไหม" แต่ไม่บอกว่าซองหายตรงไหนหรือใครอ่านซองผิดภาษา เหมือนมีกล้องวงจรปิดที่ถ่ายทุกซองที่ผ่าน เราย้อนดูทีละใบได้ นั่นคือ Wireshark

เครื่องมือในบทที่ผ่านมาให้ *ผลสรุป* เช่น `ping` ตอบ/ไม่ตอบ `nslookup` ได้ IP หรือไม่ แต่คำถามอย่าง "ทำไมเว็บช้าเฉพาะบางครั้ง", "แอปบอกเชื่อมต่อไม่ได้ แต่ ping ได้" หรือ "ใครส่งทราฟฟิกแปลกๆ ออกไป" ต้องรู้ว่า *บนสายเกิดอะไรขึ้นจริงตามลำดับเวลา*

Wireshark เป็นตัววิเคราะห์โปรโตคอล (protocol analyzer): จับเฟรมดิบ แล้วใช้ตัวถอดรหัสโปรโตคอลนับร้อย (dissector) แปลงไบต์เป็นฟิลด์ที่อ่านได้ตามชั้น (Ethernet → IP → TCP → แอป) เหมือนที่เราเรียนเรื่อง encapsulation ในบท OSI

**ข้อจำกัดที่ต้องรู้ตั้งแต่ต้น:** Wireshark เห็นเฉพาะสิ่งที่ผ่าน *จุดที่คุณจับ* ถ้าคุณจับที่เครื่อง A ก็เห็นเฉพาะที่เข้า/ออก A (ไม่เห็นว่าแพ็กเก็ตหายที่ไหนกลางทางหลังจากออกจาก A ถ้าไม่จับอีกจุด) และถ้าข้อมูลเข้ารหัส (TLS, SSH) คุณเห็นแค่ส่วนหัวและขนาด ไม่เห็นเนื้อหา

## 2. การจับแพ็กเก็ตทำงานอย่างไร

> **นึกภาพว่า:** ยืนที่จุดตรวจแล้วถ่ายสำเนาซองทุกใบที่ผ่านหน้า ไม่ได้ฉีกซอง ไม่ได้เปลี่ยนเส้นทาง ซองต้นฉบับไปต่อตามปกติ

### 2.1 Promiscuous mode และเหตุที่มักไม่พอ

> **นึกภาพว่า:** ปกติพนักงานรับของที่หน้าห้อง รับเฉพาะซองที่จ่าหน้าถึงตัวเอง โหมด promiscuous คือขอรับทุกซองที่ผ่านหน้าห้อง แต่ถ้าสวิตช์ส่งซองให้เฉพาะห้องผู้รับ ซองคนอื่นก็ไม่ผ่านหน้าห้องเราอยู่ดี
>
> ```
> เห็นได้: ของเรา, broadcast, multicast
> เห็นไม่ได้ (บนสวิตช์): unicast ของเครื่องอื่น -> ต้อง SPAN / TAP
> ```

โดยปกติการ์ดเครือข่ายเปรียบเทียบ MAC ปลายทางของทุกเฟรมกับ MAC ตัวเอง (และ broadcast/multicast ที่สมัครไว้) ถ้าไม่ตรงก็ **ทิ้งในฮาร์ดแวร์** ซอฟต์แวร์ไม่เคยเห็น โหมด **promiscuous** สั่งการ์ดให้ส่งทุกเฟรมที่ *มาถึงการ์ด* ขึ้นไปให้เคอร์เนล

แต่คำว่า "มาถึงการ์ด" คือประเด็น จากบทสวิตช์: สวิตช์ส่งเฟรม unicast ไปเฉพาะพอร์ตของ MAC ปลายทาง ดังนั้นเสียบเครื่องของคุณเข้าสวิตช์แล้วเปิด promiscuous คุณเห็นแค่

- เฟรมของคุณเอง
- broadcast / multicast
- เฟรม unicast ที่สวิตช์ยัง flood (ปลายทางยังไม่เรียนรู้) ซึ่งเป็นช่วงสั้นๆ

เพื่อให้เห็นทราฟฟิกของเครื่องอื่น ต้องใช้วิธีเหล่านี้

| วิธี | ทำอย่างไร | ข้อควรระวัง |
|---|---|---|
| **จับที่ปลายทาง** | ติดตั้ง Wireshark/tcpdump บนเครื่องที่สนใจเอง | ง่ายที่สุด เห็นเฉพาะเครื่องนั้น |
| **SPAN / port mirroring** | ตั้งสวิตช์ให้สำเนาทราฟฟิกของพอร์ตหนึ่งไปอีกพอร์ตที่เสียบเครื่องวิเคราะห์ | กินทรัพยากรสวิตช์ ถ้าทราฟฟิกเกินแบนด์วิดท์พอร์ตปลายทางเฟรมจะหาย |
| **Network TAP** | อุปกรณ์คั่นสายที่แยกสำเนาสัญญาณ | เห็นครบ แม้ error ระดับล่าง แต่ต้องถอดสายชั่วคราว |
| **Wi-Fi monitor mode** | การ์ดฟังเฟรม 802.11 ทุกเฟรมในช่องโดยไม่ต้องเข้าร่วมเครือข่าย | ไม่ใช่ทุกการ์ด/ไดรเวอร์รองรับ (โดยเฉพาะบน Windows) ถ้าเป็น promiscuous บน Wi-Fi ที่เข้าร่วมเครือข่ายแล้วมักเห็นแค่ของ AP ตัวเอง และเฟรมที่เข้ารหัส WPA จะอ่านไม่ได้ถ้าไม่มีคีย์ |

### 2.2 เส้นทางของเฟรมจากสายสู่หน้าจอ

> **นึกภาพว่า:** สำเนาซองเดินทางผ่านการ์ด -> ไดรเวอร์ -> ตัวกรองในเคอร์เนล -> ไลบรารี -> หน้าจอ Wireshark แต่ละด่านทำงานต่างกันและตัวกรองด่านแรกตัดซองที่ไม่ต้องการทิ้งก่อนจะเปลืองแรง

คำอธิบายที่พบบ่อยว่าการจับแพ็กเก็ต "ข้าม socket ของระบบปฏิบัติการ" เป็นความจริงบางส่วน: โปรแกรมจับไม่ได้เป็นปลายทางของการเชื่อมต่อ มันขอสำเนาเฟรมจากเคอร์เนลที่ชั้นล่างกว่า socket แต่เฟรมยังผ่านไดรเวอร์และเคอร์เนลตามปกติ (ไม่ได้อ่านจากสายตรงโดยไม่ผ่านระบบ)

บน Windows ตัวจับคือ **Npcap** (ไดรเวอร์ + ไลบรารี) บน Linux/macOS คือ **libpcap** (ใช้กลไกอย่าง AF_PACKET) ตัวกรอง BPF ที่ทำงานในเคอร์เนลคือเหตุผลที่ capture filter ถูกกว่า display filter มาก

## 3. อ่านเฟรมดิบด้วยมือ

> **นึกภาพว่า:** ซองที่เปิดดูไบต์ต่อไบต์ ไบต์แรกๆ คือหน้าซองชั้นนอกสุด (Ethernet) ลึกเข้าไปคือที่อยู่ (IP) ลึกกว่านั้นคือพอร์ต (TCP) แต่ละช่วงมีตำแหน่งและความยาวตายตัวที่อ่านได้ด้วยมือ
>
> ```
> Ethernet 14 ไบต์ -> IP 20 ไบต์ -> TCP 20 ไบต์ -> ข้อมูล
> ```

Wireshark มีสามแผง: **Packet List** (หนึ่งแถวต่อแพ็กเก็ต), **Packet Details** (ต้นไม้ของแต่ละชั้น) และ **Packet Bytes** (hex + ASCII) คลิกฟิลด์ในแผงกลาง ไบต์ที่เกี่ยวข้องจะถูกไฮไลต์ในแผงล่าง

เพื่อให้เห็นว่า "ต้นไม้ฟิลด์" มาจากไบต์จริงอย่างไร ลองถอดเฟรม SYN ตัวอย่างนี้ (ขนาด 54 ไบต์ ข้อมูลตัวอย่างที่สร้างและคำนวณ checksum ด้วยโปรแกรมจริง ไม่ได้จับจากเครือข่าย; SYN ในโลกจริงมักมี TCP options ต่อท้ายทำให้ยาวกว่านี้)

```text
aa bb cc 00 00 01 aa bb cc 00 00 15 08 00                      ← Ethernet (14 ไบต์)
45 00 00 28 1c 46 40 00 40 06 26 f8 c0 a8 01 0f 5d b8 d8 22    ← IPv4 (20 ไบต์)
c8 22 00 50 1a 2b 3c 4d 00 00 00 00 50 02 fa f0 9e 74 00 00    ← TCP (20 ไบต์)
```

| ไบต์ | ฟิลด์ | ค่า | ความหมาย |
|---|---|---|---|
| `aa bb cc 00 00 01` | MAC ปลายทาง | ... :01 | เกตเวย์ (ฮอปถัดไป ไม่ใช่เว็บเซิร์ฟเวอร์) |
| `aa bb cc 00 00 15` | MAC ต้นทาง | ... :15 | เครื่องเรา |
| `08 00` | EtherType | 0x0800 | ข้างในคือ IPv4 (ARP คือ 0x0806) |
| `45` | Version + IHL | 4 และ 5 | IPv4, หัว 5 × 4 = 20 ไบต์ |
| `00 28` | Total Length | 40 | หัว IP 20 + หัว TCP 20 (ไม่มีข้อมูล) |
| `1c 46` | Identification | 0x1c46 | ใช้ประกอบชิ้นส่วนถ้ามี fragmentation |
| `40 00` | Flags + Fragment offset | DF=1 | ห้ามแบ่งชิ้น (Don't Fragment) |
| `40` | TTL | 64 | ค่าเริ่มต้นแบบ Linux |
| `06` | Protocol | 6 | TCP (UDP คือ 17, ICMP คือ 1) |
| `26 f8` | Header checksum | 0x26f8 | ตรวจได้ด้วยมือ (ด้านล่าง) |
| `c0 a8 01 0f` | IP ต้นทาง | 192.168.1.15 | |
| `5d b8 d8 22` | IP ปลายทาง | 93.184.216.34 | |
| `c8 22` | พอร์ตต้นทาง | 51234 | พอร์ตชั่วคราว (ephemeral) |
| `00 50` | พอร์ตปลายทาง | 80 | HTTP |
| `1a 2b 3c 4d` | Sequence number | 439,041,101 | เลขเริ่มต้นจริง (ISN) สุ่ม |
| `00 00 00 00` | Acknowledgment | 0 | ยังไม่ใช้เพราะธง ACK ไม่ตั้ง |
| `50` | Data offset | 5 | หัว TCP 5 × 4 = 20 ไบต์ |
| `02` | Flags | 0x02 | ตั้งแค่ SYN |
| `fa f0` | Window | 64,240 | ขนาดหน้าต่างรับที่โฆษณา |
| `9e 74` | TCP checksum | 0x9e74 | ครอบ pseudo-header + หัว TCP + ข้อมูล |

**ตรวจ checksum ของหัว IP ด้วยมือ (ผ่านการคำนวณจริงด้วยโปรแกรม):** แบ่งหัว 20 ไบต์เป็นคำ 16 บิต 10 คำ โดยใส่ช่อง checksum เป็น 0000 บวกกันแบบ one's complement (ส่วนที่ล้นเกิน 16 บิตให้พับกลับมาบวกท้ายสุด) แล้วกลับบิตทั้งหมดได้ `0x26f8` ผู้รับบวกทั้ง 10 คำ *รวม checksum* ผลต้องได้ `0xffff` (กลับบิตเป็น 0) ถ้าไม่ใช่แปลว่าหัวเสีย

**ข้อสังเกตสำคัญเรื่อง checksum offload:** บนเครื่องที่จับเอง Wireshark มักแสดง checksum ผิด (`[incorrect, should be ...]`) เฟรมขาออกเพราะการ์ดคำนวณ checksum *หลังจาก* เฟรมถูกสำเนาให้ตัวจับ ในขณะจับยังเป็นค่าที่ยังไม่ได้เติม ไม่ใช่เฟรมเสียจริง อย่าตกใจ และอย่าไล่แก้ผิดจุด

## 4. กรองข้อมูล: capture filter กับ display filter

> **นึกภาพว่า:** ตะแกรงสองชั้น ชั้นแรกกรองตอนถ่ายสำเนา (capture filter: ไม่ถ่ายก็ไม่มีข้อมูลนั้นอีก) ชั้นสองกรองตอนดูภาพที่ถ่ายเก็บไว้แล้ว (display filter: ซ่อนได้ เอากลับมาดูได้)

บนลิงก์ 10 Gbps ที่เต็มความเร็ว เฟรม 1,500 ไบต์วิ่ง ≈ 833,000 เฟรมต่อวินาที เทียบเป็นข้อมูล ≈ **75 GB ต่อนาที** (ตรวจด้วยการคำนวณจริง; ค่าเชิงทฤษฎีที่ลิงก์เต็ม ในงานจริงมักต่ำกว่า) จับทุกอย่างไม่ไหว นี่คือเหตุผลของ capture filter

| | Capture filter | Display filter |
|---|---|---|
| ทำงานเมื่อไร | ก่อนบันทึก (ในเคอร์เนล) | หลังบันทึก (ใน Wireshark) |
| เฟรมที่ไม่ผ่าน | **ถูกทิ้งถาวร** | ซ่อน ล้างตัวกรองแล้วกลับมา |
| ไวยากรณ์ | BPF (`host`, `port`, `net`, `tcp`) | ของ Wireshark ตามชื่อฟิลด์ (`ip.addr`, `tcp.flags.syn`) |
| ความสามารถ | จำกัด ดูเฉพาะหัวชั้นล่าง | ลึก ถึงฟิลด์ของโปรโตคอลชั้นแอป (`http.response.code`) |
| ต้นทุน | ต่ำมาก | สูงกว่า (ถอดรหัสทุกเฟรมก่อน) |

### 4.1 ลองเอง: ตัวกรองสองชั้น

> **นึกภาพว่า:** พิมพ์กฎแล้วดูว่าแพ็กเก็ตใบไหนผ่านชั้นไหน กฎสองชั้นใช้ภาษาคนละแบบ (BPF เทียบ display filter)

เลือก capture filter ก่อน (เฟรมที่ไม่ผ่านจะขีดฆ่า ✕ ถูกทิ้งถาวร) แล้วค่อยลอง display filter สังเกตว่าเปลี่ยน display filter กี่ครั้งก็เอาเฟรม ✕ กลับมาไม่ได้ จากนั้นลอง `ip.addr != 192.168.1.5` เทียบกับ `!(ip.addr == 192.168.1.5)` และสลับรุ่นของ Wireshark

::filter-lab
::

**สิ่งที่ควรสังเกต**

- เลือก capture `port 53` แล้วเปลี่ยน display เป็น `tcp.flags.syn == 1` ผลคือไม่เหลือสักแถว ทั้งที่ SYN เคยวิ่งผ่านสาย การรู้ลำดับของตัวกรองสองชั้นคือหัวใจของบทนี้
- เฟรม ARP (#10, #11) ไม่มีหัว IP ดังนั้นตัวกรอง `ip.addr == ...` ไม่มีวันตรง และ capture `host 192.168.1.5` ก็ไม่เก็บ ARP ของคนอื่น
- ใช้ `ip.addr != 192.168.1.5` ใน Wireshark ที่ใหม่กว่าจะให้ผลถูกตามสัญชาตญาณ แต่ถ้าไปเปิดบนรุ่นเก่าแล้วผลต่างกัน นั่นไม่ใช่บั๊กของคุณ

### 4.2 กับดักของ `!=` (ขึ้นกับรุ่น)

> **นึกภาพว่า:** "ไม่ใช่ซองจากห้อง 5" ฟังง่ายแต่ถ้าซองบางใบมีผู้ส่งสองคน (เช่น IP ซ้อนใน ICMP) คำว่า "ไม่ใช่" ตีความได้สองแบบ ผลต่างกันตามรุ่นของโปรแกรม

ฟิลด์ `ip.addr` ตรงกับ *ทั้งสองฝั่ง* (ต้นทางและปลายทาง) ของแพ็กเก็ต ดังนั้น `ip.addr != X` ใน Wireshark **เก่ากว่า 3.6** แปลว่า "มีอย่างน้อยหนึ่งฝั่งที่ไม่ใช่ X" แพ็กเก็ตจาก X ไปหาเครื่องอื่นจึงยัง *ตรง* (เพราะปลายทางไม่ใช่ X) ตัวกรองจึงไม่ได้ตัด X ออกอย่างที่คิด จาก 3.6 เป็นต้นมา `!=` ถูกนิยามใหม่ให้เป็นนิเสธของ `==` ซึ่งตัด X ออกจริง

ข้อแนะนำที่ถูกต้องทุกรุ่น: เขียน `!(ip.addr == X)` ให้ชัด เพราะหมายความเดียวกันในทุกรุ่นและอ่านเข้าใจง่าย (ตรวจเอกสารของรุ่นที่คุณใช้ ผมยืนยันจากหมายเหตุรุ่น 3.6 และ wiki ของ Wireshark ส่วนรุ่นหลังจากนั้นไม่ได้ตรวจทีละรุ่น)

### 4.3 ตัวอย่างตัวกรองที่ใช้บ่อย

> **นึกภาพว่า:** ชุดแม่แบบคำค้น "ซองจากบ้านนี้" "ซองถึงพอร์ต 443" "ซองของ DNS" ใช้เป็นจุดเริ่มแล้วปรับ

| Display filter | หมายถึง |
|---|---|
| `ip.addr == 192.168.1.50` | ต้นทางหรือปลายทางเป็นเครื่องนี้ |
| `ip.src == 192.168.1.50 && ip.dst == 8.8.8.8` | เฉพาะทิศทางนี้ |
| `tcp.port == 443 \|\| udp.port == 53` | HTTPS หรือ DNS |
| `tcp.flags.syn == 1 && tcp.flags.ack == 0` | เฉพาะ SYN เริ่มต้น ไม่รวม SYN-ACK |
| `http.response.code == 404` | เว็บตอบไม่พบไฟล์ |
| `dns.qry.name contains "example"` | หาคำถาม DNS ที่มีคำนี้ |
| `tcp.analysis.retransmission` | ตัวแยกวิเคราะห์ของ Wireshark ชี้ว่าเป็นการส่งซ้ำ |
| `tcp.analysis.flags` | แพ็กเก็ตที่ Wireshark ติดธงปัญหา (ซ้ำ, หาย, window เต็ม ฯลฯ) |

Capture filter (BPF) ที่พบบ่อย: `host 192.168.1.50`, `port 53`, `src net 10.0.0.0/24 and tcp port 80`, `not arp`

## 5. อ่าน TCP handshake

> **นึกภาพว่า:** สามประโยคก่อนคุยจริง: "ฉันอยากคุย เลขลำดับเริ่มที่ x" (SYN) "ได้ ของฉันเริ่มที่ y และฉันรับ x ถึงแล้ว" (SYN-ACK) "รับทราบ y" (ACK)
>
> ```
> SYN      Flags 0x002
> SYN-ACK  Flags 0x012  (0x02 + 0x10)
> ACK      Flags 0x010
> ```

ก่อน TCP ส่งข้อมูล ทั้งสองฝั่งต้อง *ตกลงเลข sequence ตั้งต้น (ISN)* ของกันและกัน ซึ่งเลือกสุ่มเพื่อกันการเดา/สวมรอยเชื่อมต่อ (บทโปรโตคอล) นี่คือที่มาของสามแพ็กเก็ตแรก ใช้ตัวกรอง `tcp.flags.syn == 1` เพื่อหาจุดเริ่ม

**Relative sequence number:** ค่าเริ่มต้นของ Wireshark ลบ ISN ออกให้เห็นเป็น 0, 1, 81 อ่านง่าย แต่เลขบนสายจริงคือ ISN สุ่มที่ใหญ่ถึง 32 บิต ถ้าจะเทียบกับล็อกของเครื่องอื่นหรือไฟล์ที่ส่งออก ให้ปิดตัวเลือก `tcp.relative_sequence_numbers` ในค่ากำหนดของโปรโตคอล TCP

เปิดต้นไม้ TCP จะเห็นแต่ละแพ็กเก็ตทำตามกฎเดียวกัน

- SYN: `Flags: 0x002 (SYN)` พอร์ตต้นทางเป็นพอร์ตชั่วคราว พอร์ตปลายทางเป็นพอร์ตบริการ
- SYN-ACK: `Flags: 0x012 (SYN, ACK)` = 0x02 + 0x10 และ `Ack` มากกว่า Seq ที่รับมา 1
- ACK: `Flags: 0x010 (ACK)` ธงเป็นบิตในไบต์เดียว จึงรวมค่าด้วยการบวกเลขฐานสิบหก

**ตรวจความเข้าใจกลางบท:** ผู้ดูแลจับแพ็กเก็ต 60 วินาทีบนเซิร์ฟเวอร์ที่ยุ่ง แล้วพิมพ์ `dns` ในช่อง display filter ต่อมาอยากดู SSH ที่เกิดในนาทีเดียวกันแต่รายการมีแต่ DNS ทำไม

::reveal{question="คำตอบ"}
display filter แค่ซ่อนแพ็กเก็ต ล้างช่องตัวกรองแล้ว SSH จะกลับมา (ถ้าตอนจับไม่ได้ตั้ง capture filter ไว้ตัดทิ้ง) ถ้าตั้ง capture filter `port 53` ไว้ตั้งแต่ก่อนจับ SSH จะไม่เคยถูกบันทึกและกู้คืนไม่ได้ ตัวเลือกที่ว่า Wireshark ลบแพ็กเก็ตเพื่อประหยัดที่ หรือ SSH ถูกแปลงเป็นเฟรมเสียเพราะเข้ารหัสนั้นผิด ทั้งคู่ไม่มีกลไกแบบนั้น
::

## 6. ประกอบบทสนทนาด้วย Follow Stream

> **นึกภาพว่า:** ซองหลายร้อยใบสลับกันมา Follow Stream คัดเฉพาะซองของสายสนทนาเดียวกันมาเรียงตามลำดับ อ่านเป็นบทสนทนาต่อเนื่องเหมือนบันทึกแชท

การโหลดหน้าเว็บหนึ่งหน้ากระจายเป็นหลายร้อยแพ็กเก็ตปนกับทราฟฟิกอื่น คลิกขวาที่แพ็กเก็ต TCP แล้วเลือก **Follow → TCP Stream** Wireshark จะ

1. ตั้ง display filter ให้เป็นการเชื่อมต่อนั้น (เช่น `tcp.stream eq 4`) ซึ่งระบุด้วย 4-tuple (IP/พอร์ตทั้งสองฝั่ง) จากบทพอร์ต
2. เรียงข้อมูลแอปตามเลข Seq (เลขนี้เองที่ทำให้ประกอบข้อมูลที่มาสลับลำดับ หรือส่งซ้ำ กลับเป็นสายไบต์ที่ถูกต้อง) และตัดหัว Ethernet/IP/TCP ทิ้ง
3. แสดงเนื้อหาในหน้าต่างใหม่ แยกสีตามทิศทาง (ค่าเริ่มต้น: ไคลเอนต์เป็นสีแดง เซิร์ฟเวอร์เป็นสีน้ำเงิน)

```text
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
```

ถ้าเป็นโปรโตคอลที่ไม่เข้ารหัส (HTTP, FTP, Telnet) คุณอ่านได้ทั้งหมด รวมถึงรหัสผ่านที่กรอกในฟอร์ม ถ้าเป็น TLS/SSH จะเห็นไบต์สุ่ม (ดูมุมมอง Security หัวข้อ 9 ว่าถอดรหัสได้อย่างไรเมื่อคุณเป็นเจ้าของปลายทาง)

**ไฟล์ .pcap ข้างใน:** มีหัวไฟล์ส่วนกลาง 24 ไบต์ ตามด้วยเรคคอร์ดต่อแพ็กเก็ต แต่ละเรคคอร์ดมีหัว 16 ไบต์ (เวลา, ความยาวที่บันทึก, ความยาวจริง) แล้วตามด้วยไบต์เฟรม ตัวอย่างคำนวณ: 100 เฟรมขนาด 74 ไบต์ ≈ 24 + 100 × (16 + 74) = **9,024 ไบต์** (ค่าที่ไม่ได้ตัดเฟรม รูปแบบ `.pcapng` ที่ Wireshark ใช้ใหม่กว่า มีบล็อกเสริมข้อมูลอินเทอร์เฟซและคอมเมนต์ จึงขนาดต่างเล็กน้อย)

## 8. วินิจฉัยความผิดปกติจากลายเซ็นของแพ็กเก็ต

> **นึกภาพว่า:** แต่ละปัญหาทิ้งรอยเท้าต่างกัน อ่านรอยเท้าแทนการเดา: ปฏิเสธทันที, เงียบแล้วส่งซ้ำ, หรือชื่อที่อยู่ซ้ำกัน

อาการที่ผู้ใช้เล่าแบบ "เชื่อมต่อไม่ได้" มีหลายกลไก แพ็กเก็ตแยกได้ว่าอันไหน

### 8.1 Connection refused: RST ทันที

> **นึกภาพว่า:** เคาะประตู แล้วมีคนตะโกนทันที "ไม่มีใครรับที่นี่!" ได้ยินเร็วมาก
>
> ```
> SYN ->
> <- RST,ACK   (เร็ว: เครื่องปลายทางมีชีวิต แต่ไม่มีโปรแกรมฟังพอร์ตนั้น)
> ```

```text
No.  Source      Destination  Protocol  Info
1    10.0.0.5    10.0.0.20    TCP       52100 → 8080 [SYN]
2    10.0.0.20   10.0.0.5     TCP       8080 → 52100 [RST, ACK] Seq=1 Ack=1
```

คำตอบกลับมา *ในเสี้ยววินาที* แปลว่า เส้นทางใช้ได้, ปลายทางเปิดอยู่, ไฟร์วอลล์ปล่อยผ่าน แต่ **ไม่มีโปรเซสฟังที่พอร์ตนั้น** (เคอร์เนลของปลายทางตอบปฏิเสธเอง) ต้องไปแก้ที่บริการ: หยุดอยู่, ฟังพอร์ตอื่น หรือ bind เฉพาะ 127.0.0.1 (บทลูปแบ็ก)

### 8.2 Timeout: SYN ซ้ำไม่มีคำตอบ

> **นึกภาพว่า:** เคาะประตูแล้วเงียบ เคาะอีกครั้งห่างขึ้นเรื่อยๆ (1, 2, 4, 8 วินาที ค่าเริ่มต้นแตกต่างตามระบบ) ไม่รู้ว่าไม่มีคนอยู่ หรือคนไม่ยอมเปิด
>
> ```
> SYN -> (เงียบ)   SYN -> (เงียบ)   SYN -> (เงียบ)   เว้นช่วงห่างขึ้นเรื่อยๆ
> ```

```text
No.  Time    Source      Destination  Info
1    0.000   10.0.0.5    10.0.0.20    52100 → 443 [SYN]
2    1.002   10.0.0.5    10.0.0.20    [TCP Retransmission] 52100 → 443 [SYN]
3    3.008   10.0.0.5    10.0.0.20    [TCP Retransmission] 52100 → 443 [SYN]
```

ไม่มีใครตอบเลย ไคลเอนต์รออัตราหมดเวลา (RTO ตั้งต้น ≈ 1 วินาที) แล้วส่งซ้ำโดยเพิ่มเวลารอเป็นสองเท่า (exponential backoff) บน Linux ค่า `tcp_syn_retries` มาตรฐานคือ 6 ครั้ง ส่งที่เวลา 0, 1, 3, 7, 15, 31, 63 วินาที แล้วยอมแพ้เมื่อครบ ≈ **127 วินาที** (คำนวณจากผลรวม 1+2+4+8+16+32 บวกการรอรอบสุดท้าย 64 วินาที; ค่าเริ่มต้นต่างกันตามระบบปฏิบัติการและการตั้งค่า) นี่คือเหตุที่เบราว์เซอร์ "หมุนอยู่นานมาก" แล้วค่อยขึ้นว่าหมดเวลา

ข้อควรระวัง: ไฟร์วอลล์ที่ตั้งเป็น REJECT จะให้ผลคล้าย refused (RST หรือ ICMP) ดังนั้น "RST ทันที" บอกว่ามีอุปกรณ์ *ตอบปฏิเสธ* ไม่ได้ยืนยันว่าเป็นบริการปลายทางเสมอไป ให้ดู TTL และ MAC ของแพ็กเก็ต RST ว่ามาจากปลายทางจริงหรืออุปกรณ์กลางทาง

### 8.3 IP ซ้ำ (ARP clash)

> **นึกภาพว่า:** สองคนในห้องเดียวกันอ้างเลขห้องเดียวกัน ถามหาห้อง 5 จึงมีสองคนตอบพร้อมกัน ผู้ถามเห็นคำตอบจากสอง MAC ต่างกัน

```text
ARP  42  Who has 192.168.1.1? Tell 192.168.1.50
ARP  42  192.168.1.1 is at 00:11:22:33:44:01
ARP  42  192.168.1.1 is at 00:aa:bb:cc:dd:99   [Duplicate IP address detected for 192.168.1.1]
```

ARP ถามด้วย broadcast ครั้งเดียว แต่มีสองเครื่องตอบว่า "IP นี้ที่ฉัน" Wireshark ตรวจจับและทำสีเตือนให้ ผลต่อผู้ใช้คือเน็ตหลุดๆ หายๆ เพราะตาราง ARP ของเครื่องลูกข่ายสลับระหว่างสอง MAC ตามคำตอบล่าสุด (สอดคล้องกับอาการ MAC flapping ในบทสวิตช์)

## 9. มุมมองด้าน Security และจริยธรรม

> **นึกภาพว่า:** กล้องที่ถ่ายทุกซองก็ถ่ายรหัสผ่านที่ไม่ได้เข้ารหัสได้ด้วย จึงจับเฉพาะเครือข่ายที่ได้รับอนุญาต และเก็บไฟล์ pcap เหมือนเอกสารลับ

| ประเด็น | กลไก | การป้องกัน / ข้อควรทำ |
|---|---|---|
| **ข้อมูลที่ไม่เข้ารหัสอ่านได้หมด** | HTTP, FTP, Telnet, SNMPv1/2c, POP3/IMAP แบบไม่เข้ารหัสส่งรหัสผ่านเป็นข้อความธรรมดา ใครอยู่บนเส้นทางหรืออยู่ในวงเดียวกันก็ Follow Stream เจอ | ใช้โปรโตคอลเข้ารหัส (HTTPS, SSH, SFTP, IMAPS) และบังคับ HTTPS |
| **TLS: เห็นอะไรได้บ้าง** | แม้เข้ารหัส ยังเห็น IP/พอร์ต, ขนาดและจังหวะแพ็กเก็ต และชื่อเว็บใน SNI ของ ClientHello (ยกเว้นเมื่อใช้ ECH) การวิเคราะห์ทราฟฟิกจากขนาด/เวลา (traffic analysis) เดาพฤติกรรมได้แม้ไม่มีเนื้อหา | ถือว่าเมตาดาต้ารั่วเสมอ ใช้ VPN/ECH ตามความเหมาะสม |
| **ถอดรหัส TLS ของเครื่องตัวเอง** | ตั้งตัวแปรสภาพแวดล้อม `SSLKEYLOGFILE` ให้เบราว์เซอร์เขียนคีย์เซสชันลงไฟล์ แล้วบอก Wireshark ใช้ไฟล์นั้น (Preferences → Protocols → TLS) ใช้ได้กับการเชื่อมต่อของเครื่องเราเท่านั้น และไม่ทำให้ TLS อ่อนลงสำหรับคนอื่น | เก็บไฟล์คีย์เป็นความลับ ลบหลังใช้ ไฟล์นี้ถอดรหัสทราฟฟิกเซสชันนั้นได้ทั้งหมด |
| **ไฟล์ .pcap คือข้อมูลอ่อนไหว** | อาจมีรหัสผ่าน โทเค็น คุกกี้ เซสชัน ข้อมูลส่วนบุคคล | ใช้ snaplen สั้น/capture filter เก็บเท่าที่จำเป็น ลบข้อมูลที่ใช้เสร็จ อย่าส่งไฟล์ให้ผู้อื่นหรือแปะใน public repo โดยไม่ตัดข้อมูล (Wireshark/editcap มีเครื่องมือตัด payload) |
| **การดักจับโดยไม่ได้รับอนุญาต** | หลายประเทศถือเป็นการดักรับข้อมูลโดยมิชอบ แม้เป็นเครือข่ายในที่ทำงานหรือ Wi-Fi สาธารณะ | จับเฉพาะเครือข่ายที่คุณเป็นเจ้าของหรือได้รับอนุญาตเป็นลายลักษณ์อักษร (ขอบเขตงานทดสอบเจาะระบบ) และตามนโยบายองค์กร ไม่ใช่คำแนะนำทางกฎหมาย ตรวจกฎหมายท้องถิ่นเสมอ |
| **ARP spoofing / การดักกลางทาง** | ผู้โจมตีส่ง ARP ปลอมให้ทราฟฟิกวิ่งผ่านตนเอง แล้วดักด้วยการจับแพ็กเก็ต | ใน Wireshark สังเกต ARP ตอบซ้ำๆ ที่ไม่มีคำถาม (gratuitous) และ Duplicate IP ป้องกันด้วย Dynamic ARP Inspection, DHCP snooping |
| **ตัวจับเองก็เป็นเป้า** | Wireshark เคยมีช่องโหว่ในตัวถอดรหัสโปรโตคอล การเปิดไฟล์ pcap ที่ไม่น่าเชื่อถือหรือจับบนเครือข่ายศัตรูเสี่ยงต่อการโจมตีผ่านเฟรมที่สร้างมาเฉพาะ | อัปเดตเป็นรุ่นล่าสุด อย่ารัน GUI ด้วยสิทธิ์ root (ใช้ dumpcap แยกสิทธิ์ตามค่าเริ่มต้น) วิเคราะห์ตัวอย่างน่าสงสัยในเครื่องแยก |
| **การใช้ฝั่งป้องกัน** | ตรวจ beaconing ไปยังเซิร์ฟเวอร์ควบคุม (ช่วงเวลาสม่ำเสมอผิดปกติ), DNS tunneling (ชื่อโดเมนยาวสุ่มจำนวนมาก), การสแกนพอร์ต (SYN จำนวนมากไปหลายพอร์ต), ข้อมูลไหลออกผิดปกติ | ใช้ `statistics → conversations/endpoints` ดูผู้คุยมากที่สุดก่อน |

## 12. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: โหมด promiscuous ต่างจากโหมดปกติอย่างไร และทำไมเปิดแล้วบนสวิตช์ยังไม่เห็นทราฟฟิกของคนอื่น"}
โหมดปกติการ์ดทิ้งเฟรมที่ MAC ปลายทางไม่ใช่ตัวเอง (ยกเว้น broadcast/multicast ที่สมัครไว้) ส่วน promiscuous ส่งทุกเฟรมที่มาถึงการ์ดขึ้นไปให้เคอร์เนล แต่สวิตช์ส่ง unicast ไปเฉพาะพอร์ตของปลายทางที่เรียนรู้แล้ว เฟรมของเครื่องอื่นจึงไม่ถึงการ์ดเราตั้งแต่แรก ต้องใช้ SPAN/TAP หรือจับที่ปลายทาง
::

::reveal{question="ข้อ 2: ทำไม capture filter ใช้ CPU น้อยกว่า display filter"}
capture filter คือโปรแกรม BPF ที่ทำงานในเคอร์เนล ตัดสินใจจากหัวชั้นล่างและตัดทิ้งก่อนคัดลอกเฟรมขึ้น user space ส่วน display filter ต้องให้ Wireshark ถอดรหัสโปรโตคอลทุกเฟรมเต็มต้นไม้ก่อนจึงเทียบฟิลด์ได้ (มีต้นทุนสูงกว่ามากเมื่อไฟล์ใหญ่)
::

::reveal{question="ข้อ 3: จับแล้วเห็น SYN ตามด้วย RST,ACK ในเวลา 1 มิลลิวินาที เทียบกับเห็น SYN ซ้ำที่ 0, 1, 3, 7 วินาที ไม่มีคำตอบ ต่างกันอย่างไรในเชิงสาเหตุ"}
RST ทันที: แพ็กเก็ตถึงปลายทางและมีคนตอบ แปลว่าเส้นทางและไฟร์วอลล์ผ่าน บริการไม่ได้ฟังพอร์ต (หรืออุปกรณ์กลางทางตั้ง REJECT) SYN ซ้ำเงียบ: ไม่มีใครตอบ มักเป็นไฟร์วอลล์ DROP, เส้นทางไม่ครบ, หรือเครื่องปลายทางดับ ต้องจับอีกฝั่งเพื่อแยกว่าหายก่อนหรือหลังถึงเซิร์ฟเวอร์
::

::reveal{question="ข้อ 4: ทำไม ip.addr != 10.0.0.1 ในรุ่นเก่าไม่ตัดแพ็กเก็ตของ 10.0.0.1 ออก และควรเขียนอย่างไรให้ปลอดภัยทุกรุ่น"}
เพราะ ip.addr ตรงกับทั้งต้นทางและปลายทาง และรุ่นก่อน 3.6 ตีความ != ว่ามีอย่างน้อยหนึ่งฟิลด์ไม่เท่ากัน แพ็กเก็ตจาก 10.0.0.1 ไปเครื่องอื่นจึงตรงเพราะปลายทางไม่ใช่ 10.0.0.1 เขียน !(ip.addr == 10.0.0.1) จะตัดออกถูกต้องทุกรุ่น
::

::reveal{question="ข้อ 5: คำนวณ ลิงก์ 10 Gbps เต็มความเร็ว เฟรม 1,500 ไบต์ จับทุกเฟรมนาน 1 นาทีได้ข้อมูลเท่าไร และใช้ BPF อย่างไรลดลง"}
10×10⁹ ÷ 8 × 60 ≈ 75 GB ต่อนาที (ค่าเชิงทฤษฎีที่ลิงก์เต็ม) ลดด้วย capture filter เฉพาะโฮสต์/พอร์ตที่สนใจ (เช่น host 192.168.1.50 and port 443) และตั้ง snaplen สั้นถ้าต้องการแค่หัวแพ็กเก็ต
::

::reveal{question="ข้อ 6: ใน handshake ถ้าเลขจริงบนสายของ SYN คือ Seq=439041101 SYN-ACK ต้องตอบ Ack เท่าไร และ Wireshark แสดงอะไร"}
Ack = 439041102 เพราะ SYN กิน 1 หน่วยของเลขลำดับ บนหน้าจอ Wireshark (โหมด relative) จะเห็น Seq=0 ใน SYN และ Ack=1 ใน SYN-ACK
::

::reveal{question="ข้อ 7: ทำไม Wireshark บนเครื่องที่จับเองมักขึ้น checksum ผิดในเฟรมขาออก ทั้งที่ใช้งานปกติ"}
checksum offload: การ์ดคำนวณ checksum ตอนส่งจริง แต่ตัวจับได้สำเนาก่อนขั้นนั้น จึงเห็นค่าที่ยังไม่ถูกเติม ไม่ใช่เฟรมเสียจริง ยืนยันได้โดยจับจากอีกเครื่อง/จุดบนสาย
::

::reveal{question="ข้อ 8: คำนวณ Linux ส่ง SYN ซ้ำตามค่า tcp_syn_retries=6 ใช้เวลารวมกี่วินาทีกว่าจะยอมแพ้ (RTO ตั้งต้น 1 วินาที)"}
ส่งที่ t=0, 1, 3, 7, 15, 31, 63 แล้วรออีก 64 วินาที ยอมแพ้ที่ ≈ 127 วินาที (ค่าเริ่มต้นขึ้นกับระบบ/การตั้งค่า)
::

::reveal{question="ข้อ 9: ผู้ใช้ส่งไฟล์ pcap ให้ทีมสนับสนุนในอีเมลเพื่อให้ช่วยดู ควรระวังอะไร"}
ไฟล์อาจมีรหัสผ่านที่ไม่เข้ารหัส คุกกี้ โทเค็น ข้อมูลส่วนบุคคล ควรจับด้วย capture filter ให้แคบ ตั้ง snaplen สั้นหรือตัด payload ก่อนส่ง ส่งผ่านช่องทางที่ปลอดภัย และลบเมื่อเสร็จงาน
::

::reveal{question="ข้อ 10: วางแผนวินิจฉัย ผู้ใช้ติดต่อเซิร์ฟเวอร์ภายในพอร์ต 8443 ไม่ได้ ลำดับการตรวจด้วยแพ็กเก็ตเป็นอย่างไร"}
(1) จับที่เครื่องผู้ใช้ด้วย filter host เซิร์ฟเวอร์ and port 8443 · (2) ถ้าไม่เห็น SYN ออกเลข ปัญหาอยู่ที่แอป/DNS/ตารางเส้นทางของเครื่องผู้ใช้ · (3) เห็น SYN แล้วได้ RST ทันที = ดูบริการที่เซิร์ฟเวอร์ (ฟังพอร์ต/อินเทอร์เฟซถูกไหม) · (4) SYN ซ้ำเงียบ = จับที่เซิร์ฟเวอร์ด้วย ถ้าไม่ถึง = ไฟร์วอลล์/เส้นทางกลางทาง ถ้าถึงแต่ไม่ตอบ = ไฟร์วอลล์ในเครื่องเซิร์ฟเวอร์ · (5) handshake ผ่านแต่แอปพัง = ดูชั้นแอปด้วย Follow Stream
::

## 13. แบบฝึกหัด (ลงมือทำจริง)

ใช้กับเครื่องของคุณเองบนเครือข่ายที่คุณมีสิทธิ์จับเท่านั้น

1. **จับ DNS ครบวงจร:** เปิด Wireshark เลือกอินเทอร์เฟซที่ใช้งาน เริ่มจับ แล้วเปิดเทอร์มินัลพิมพ์ `nslookup example.com` หยุดจับ ใส่ display filter `dns` หา query กับ response เปิด Domain Name System ดูส่วน Answers หา IPv4 และสังเกตพอร์ตต้นทางชั่วคราวเทียบพอร์ต 53
2. **แยก HTTP:** ขณะจับ รัน `curl -I http://neverssl.com` (เว็บทดสอบที่ไม่เข้ารหัส) กรอง `http` คลิกขวาที่ GET เลือก Follow → HTTP Stream อ่านส่วนหัวคำตอบ แล้วลองเทียบกับ `curl -I https://example.com` ว่า Follow Stream เห็นอะไร (ควรเห็นไบต์เข้ารหัส)
3. **จับด้วยบรรทัดคำสั่ง:** `sudo tcpdump -i any -c 25 -w dns_test.pcap udp port 53` (Linux/macOS) แล้วเรียก `nslookup` หรือเปิดเว็บจนครบ 25 เฟรม เปิด `dns_test.pcap` ใน Wireshark ยืนยันว่ามีแต่ DNS (บน Windows ใช้ Wireshark GUI ตั้ง capture filter `udp port 53` ในหน้าเลือกอินเทอร์เฟซ)
4. **ตรวจ handshake:** กรอง `tcp.flags.syn == 1` ตอนเปิดเว็บ หาสามแพ็กเก็ต คลิก SYN เปิดแผง Bytes ตรวจว่าไบต์ธงตรงกับ `0x02` ปิดตัวเลือก relative sequence numbers แล้วดูว่าเลขจริงเป็นอย่างไร
5. **วัด RTT:** จาก handshake คำนวณเวลา SYN → SYN-ACK เทียบกับค่า `ping` ไปเว็บเดียวกัน สองค่าควรใกล้เคียง
6. **ลองสร้างอาการ refused:** บนเครื่องตัวเอง `curl http://127.0.0.1:9` (พอร์ตที่ไม่มีใครฟัง) จับที่อินเทอร์เฟซ loopback (`Adapter for loopback traffic capture` บน Windows หรือ `lo` บน Linux) ดู SYN และ RST ที่ตอบกลับทันที
7. **ดูสถิติ:** เมนู Statistics → Conversations และ Protocol Hierarchy ดูว่าทราฟฟิกส่วนใหญ่ของคุณมาจากใคร และโปรโตคอลใดกินสัดส่วนสูงสุด

::reveal{question="แนวคำตอบ"}
(1) พอร์ตต้นทางเป็นเลขสูงสุ่ม (ephemeral) ปลายทาง 53 ส่วน Answers มี A record · (2) HTTP อ่านได้ครบ HTTPS ขึ้นเป็นไบต์สุ่ม · (3) ถ้า tcpdump ต้องใช้ sudo · (4) ธงใน SYN เท่ากับ 0x02 · เลขจริงเป็นเลขใหญ่หลักร้อยล้าน · (5) ต่างกันเล็กน้อยได้ เพราะ ping วัดไปกลับด้วย ICMP · (6) ได้ RST,ACK ทันทีในเวลาต่ำกว่าไม่กี่ไมโครวินาทีถึงมิลลิวินาที เพราะเป็นเคอร์เนลตัวเองตอบ · (7) ส่วนมากเป็น TLS/HTTPS และ DNS
::

## 14. สรุป

- **Wireshark/tcpdump** ให้ความเห็นระดับเฟรมที่เครื่องมืออย่าง ping ให้ไม่ได้ ทำงานด้วยการสำเนาเฟรมจากเคอร์เนล (libpcap/Npcap) โดยมีตัวกรอง BPF ในเคอร์เนลช่วยลดภาระ
- **Promiscuous** ทำให้การ์ดรับเฟรมของคนอื่น แต่สวิตช์ไม่ส่งมาให้ ต้องใช้ SPAN/TAP หรือจับที่ปลายทาง
- **Capture filter** ตัดทิ้งก่อนบันทึก (ถาวร) · **display filter** ซ่อนตอนดู (ย้อนกลับได้) · ใช้ `!(ip.addr == X)` แทน `!=` เพื่อไม่ขึ้นกับรุ่น
- อ่านเฟรมได้ตั้งแต่ไบต์: EtherType บอกชั้นถัดไป, IHL/Data offset บอกความยาวหัว, checksum ตรวจได้ด้วยการบวก one's complement
- **TCP handshake** คือการตกลง ISN ของสองฝั่ง; Seq/Ack นับไบต์; Wireshark แสดงเลขแบบ relative
- **ลายเซ็นของอาการ:** RST ทันที = บริการไม่ฟัง · SYN ซ้ำเงียบ (≈127 วินาทีบน Linux ค่าเริ่มต้น) = ถูกทิ้งกลางทาง · ARP ตอบสองคน = IP ซ้ำ
- **Security/จริยธรรม:** ข้อมูลไม่เข้ารหัสอ่านได้หมด, TLS ยังรั่วเมตาดาต้า, ไฟล์ pcap เป็นข้อมูลอ่อนไหว, จับเฉพาะเครือข่ายที่ได้รับอนุญาต
- ข้อจำกัด: เห็นเฉพาะจุดที่จับ, เนื้อหาเข้ารหัสอ่านไม่ได้, การจับบนเครื่องส่งเองมี checksum offload, และถ้าตัวจับตามไม่ทัน (dropped) ข้อสรุปจากไฟล์ผิดได้
- บทถัดไป (โมดูล 5): ตัวตนและการควบคุมการเข้าถึง เริ่มจาก authentication กับ authorization
