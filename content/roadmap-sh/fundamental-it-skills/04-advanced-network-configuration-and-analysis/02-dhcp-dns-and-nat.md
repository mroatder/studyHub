## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายว่าทำไม **DHCP** ต้องใช้ broadcast และไล่ฟิลด์/ข้อความของกระบวนการ **DORA** ได้ทีละขั้น พร้อมตอบว่าทำไม DHCPREQUEST ถึงเป็น broadcast
2. คำนวณ **T1 / T2** ของสัญญาเช่า (lease) และอธิบายว่าเครื่องทำอะไรในแต่ละช่วง รวมถึงเลือกอายุสัญญาให้เหมาะกับขนาด pool
3. อธิบายบทบาทของ **DHCP relay agent** และ **reservation** เมื่อ DHCP server อยู่คนละซับเน็ต
4. ไล่การแปลงชื่อของ **DNS** ตั้งแต่ root → TLD → authoritative แยก recursive กับ iterative และอธิบายบทบาทของ **แคชและ TTL**
5. อ่านและเลือกใช้ **resource record** (A, AAAA, CNAME, MX, NS, PTR, TXT, SOA) และรู้ข้อจำกัดของ CNAME
6. อธิบายว่า NAT บน Linux ใช้ **connection tracking** อย่างไร และแยก SNAT/MASQUERADE กับ DNAT ได้
7. ไล่ลำดับเหตุการณ์ตั้งแต่เสียบสายจนเปิดเว็บได้ว่าทั้งสามบริการทำงานต่อกันอย่างไร
8. วินิจฉัยอาการที่คล้ายกัน เช่น `169.254.x.x`, ping IP ได้แต่ชื่อไม่ได้, ได้ IP ผิดซับเน็ต และอธิบายการโจมตี **rogue DHCP**, **DNS cache poisoning** เทียบกับกลไกที่เรียน

## สรุปสั้น (TL;DR)

- **DHCP** ให้เครื่องที่ยัง *ไม่มี IP* ขอการตั้งค่าได้ จึงต้องเริ่มด้วย broadcast ผ่านสี่ข้อความ **DISCOVER → OFFER → REQUEST → ACK** และได้ IP แบบ *เช่า* ไม่ใช่ซื้อขาด
- สัญญาเช่ามี **T1 = 50%** (ต่อกับเซิร์ฟเวอร์เดิมแบบ unicast) และ **T2 = 87.5%** (broadcast หาใครก็ได้) หมดอายุแล้วต้องทิ้ง IP
- **DNS** คือฐานข้อมูลกระจายแบบลำดับชั้น คำตอบเดินทางจาก root → TLD → authoritative แต่ **แคช + TTL** ทำให้เกือบทุกครั้งไม่ต้องไปถึงข้างนอก
- **NAT** ที่ขอบเครือข่ายเก็บ *ตารางการเชื่อมต่อ* (connection tracking) เพื่อเขียนที่อยู่ขาออกและย้อนกลับขาเข้า (รายละเอียด PAT อยู่ใน[บทเรื่อง Public/Private IP](/roadmap-sh/fundamental-it-skills/03-core-computer-networking/04-public-and-private-ip-addresses))
- ทั้งสามเป็นเป้าโจมตีเพราะ *เชื่อใจกันโดยไม่ตรวจตัวตน*: rogue DHCP แจก gateway/DNS ปลอม, DNS poisoning ยัดคำตอบปลอมเข้าแคช

## เปรียบเทียบกับชีวิตจริง

ลองนึกถึงการเข้าพักโรงแรมแห่งใหม่ คุณเดินเข้าล็อบบี้ **โดยยังไม่มีห้อง** (ไม่มี IP) ตะโกนถามทั้งล็อบบี้ว่ามีใครให้ห้องบ้าง (DHCP DISCOVER) พนักงานเสนอห้องให้ (OFFER) คุณตอบรับเสียงดังให้ทุกคนได้ยินว่าเลือกของใคร (REQUEST) แล้วได้กุญแจ **เช่าเป็นคืน** (lease) กับป้ายบอกทางไปลิฟต์ (gateway) และโทรศัพท์ภายในของแผนกต้อนรับ (DNS)

พอจะโทรหาเพื่อน คุณไม่รู้เบอร์ห้อง รู้แต่ชื่อ จึงโทรถามแผนกต้อนรับ (DNS resolver) ซึ่งเปิดสมุดรายชื่อของตัวเอง (แคช) ถ้าไม่มีก็โทรถามสำนักงานใหญ่ต่อเป็นทอดๆ (root → TLD → authoritative) และพอโทรออกนอกโรงแรม สายออกใช้เบอร์กลางของโรงแรมเบอร์เดียว (NAT) ที่โอเปอเรเตอร์จดไว้ว่าสายนี้มาจากห้องไหน

## 1. ทำไมต้องมีสามบริการนี้: ปัญหาตั้งต้น

เครื่องหนึ่งจะคุยอินเทอร์เน็ตได้ต้องรู้ **ห้าอย่าง** ได้แก่ IP ของตัวเอง, subnet mask, default gateway, DNS server และ (ถ้ามี) ชื่อโดเมนสำหรับค้นหา ถ้ากรอกด้วยมือจะเกิดปัญหา

| ปัญหา | ถ้าไม่มีบริการ | บริการที่แก้ |
|---|---|---|
| ต้องตั้ง IP/gateway/DNS ทุกเครื่องด้วยมือ ผิดพลาดง่าย IP ซ้ำกัน | เครื่องหลักร้อยในออฟฟิศ ย้ายโต๊ะต้องตั้งใหม่ | **DHCP** |
| คนจำเลข IP ไม่ไหว และเลข IP เปลี่ยนได้ | ต้องพิมพ์ `93.184.216.34` แทนชื่อ | **DNS** |
| IPv4 มี ~4.3 พันล้านที่อยู่ ไม่พอให้ทุกอุปกรณ์ | เครื่องใน LAN ใช้ IP ส่วนตัวออกอินเทอร์เน็ตตรงๆ ไม่ได้ | **NAT** |

ทั้งสามจึงเป็น *ระบบอัตโนมัติ* ที่ติดตั้งในเราเตอร์บ้านเครื่องเดียวกัน แต่ในองค์กรมักแยกเป็นเซิร์ฟเวอร์คนละตัว และเข้าใจกลไกแต่ละอันแยกจากกันก่อนจะเห็นว่าทำงานประสานกันอย่างไร

## 2. DHCP: ขอ IP ตอนที่ยังไม่มี IP

### 2.1 ปัญหาไก่กับไข่

เครื่องที่เพิ่งต่อสายยัง **ไม่มี IP** จึงส่ง unicast หาเซิร์ฟเวอร์ไม่ได้ (ไม่รู้ที่อยู่ของมันด้วยซ้ำ) ทางแก้คือใช้ที่อยู่พิเศษสองค่า

- ต้นทาง `0.0.0.0` ("ฉันยังไม่มี IP")
- ปลายทาง `255.255.255.255` (limited broadcast: ทุกเครื่องในวง L2 เดียวกัน)

ข้อความวิ่งบน **UDP** พอร์ต **68** (client) → **67** (server) ใช้ UDP เพราะ TCP ต้องมี IP ที่ใช้ได้ก่อนจึงจะ handshake ได้ และเมื่อ DHCP ใช้ broadcast จึง **ข้ามเราเตอร์ไม่ได้** (เว้นแต่มี relay ดูหัวข้อ 2.5) แต่ละข้อความมีรหัสธุรกรรม **xid** (transaction ID) ให้จับคู่คำถามกับคำตอบ และ **chaddr** คือ MAC ของเครื่องที่ขอ (เซิร์ฟเวอร์ใช้ระบุตัวลูกข่าย)

**ทำไม REQUEST ต้องเป็น broadcast และใส่ server-id?** เพราะลูกข่ายอาจได้ OFFER จากหลายเซิร์ฟเวอร์ การ broadcast พร้อมบอกว่าเลือกใคร (option 54: server identifier) ทำให้ทุกเซิร์ฟเวอร์รู้ผลพร้อมกัน และคืนที่อยู่ที่กันไว้ให้ตัวเอง ถ้าเป็น unicast เซิร์ฟเวอร์ที่ไม่ได้ถูกเลือกจะไม่มีทางรู้ และจะกันที่อยู่ไว้จนเวลาของข้อเสนอหมด

### 2.3 ข้อมูลที่ DHCP แจกจริงอยู่ในไหน

ค่าตั้งค่าทั้งหมดเป็น **option** แบบ รหัส-ความยาว-ค่า ในข้อความ DHCP ตัวที่ต้องรู้

| Option | ความหมาย | ใช้ทำอะไร |
|---|---|---|
| 53 | ชนิดข้อความ | DISCOVER / OFFER / REQUEST / ACK / NAK / DECLINE / RELEASE |
| 1 | subnet mask | ให้เครื่องคำนวณว่าใครอยู่ซับเน็ตเดียวกัน |
| 3 | router (default gateway) | กลายเป็นแถว `0.0.0.0/0` ในตารางเส้นทาง |
| 6 | DNS server | ใครเป็น resolver ของเครื่อง |
| 15 | domain name | ต่อท้ายชื่อสั้นๆ เช่น `intranet` → `intranet.company.com` |
| 50 / 54 | requested IP / server identifier | ใช้ใน REQUEST ระบุข้อเสนอที่เลือก |
| 51 | lease time | อายุสัญญาเช่า (วินาที) |
| 58 / 59 | T1 / T2 | ถ้าไม่กำหนด ใช้ 50% และ 87.5% ของ lease |

**ผลต่อบทก่อนหน้า:** ค่า option 3 คือ default gateway ที่เราตั้งด้วยมือในบทที่ 16 ส่วน option 6 คือ DNS ที่หัวข้อ 3 จะใช้ ดังนั้น *ถ้า DHCP แจกผิด ทั้งการออกนอกซับเน็ตและการแปลงชื่อพังพร้อมกัน*

### 2.4 สัญญาเช่า: T1, T2 และการหมดอายุ

IP จาก DHCP คือ **สัญญาเช่า (lease)** มีอายุจำกัดเพื่อให้ pool นำที่อยู่ของเครื่องที่หายไปกลับมาใช้ใหม่ได้โดยไม่ต้องมีใครคอยเก็บ เครื่องจะไม่รอให้หมดจึงขอต่อ แต่ใช้ตัวจับเวลาสองตัว

| ตัวจับเวลา | เวลา (ปริยาย) | เครื่องทำอะไร |
|---|---|---|
| **T1** (RENEWING) | 50% ของ lease | ส่ง DHCPREQUEST แบบ **unicast** ไปเซิร์ฟเวอร์เดิม ถ้าได้ ACK นาฬิกาเริ่มนับใหม่ |
| **T2** (REBINDING) | 87.5% ของ lease | ถ้าเซิร์ฟเวอร์เดิมเงียบ ส่ง DHCPREQUEST แบบ **broadcast** ถามใครก็ได้ |
| **หมดอายุ** | 100% | ทิ้ง IP ทันที กลับไปเริ่ม DISCOVER ใหม่ |

ตัวอย่างสัญญา 24 ชั่วโมง: T1 = 24 × 0.5 = **12 ชั่วโมง**, T2 = 24 × 0.875 = **21 ชั่วโมง** ถ้าเซิร์ฟเวอร์เดิมล่มตั้งแต่ก่อน T1 เครื่องยังมีเวลาอีก 12 ชั่วโมงก่อนถึง T2 (ลองส่งซ้ำทุกครึ่งของเวลาที่เหลือ ครั้งแรกหลัง T1 ประมาณ 4.5 ชั่วโมง) เป็นกลไก *ทนต่อความล้มเหลวชั่วคราว* ที่ทำให้เซิร์ฟเวอร์ DHCP ล่มสั้นๆ ไม่กระทบผู้ใช้เลย

ลองเลื่อนเวลาในสื่อด้านล่าง ปิดสวิตช์ "เซิร์ฟเวอร์เดิมตอบ" แล้วเลื่อนไปที่ 50%, 90% และ 100% ดูว่าสถานะเปลี่ยนอย่างไร

#### เลือกอายุสัญญาอย่างไร: ความสมดุลระหว่าง pool กับทราฟฟิก

อายุสัญญา *ยาว* ลดข้อความต่ออายุแต่ที่อยู่ของเครื่องที่จากไปแล้วถูกกันไว้นาน *สั้น* คืนที่อยู่เร็วแต่ต้องต่ออายุบ่อย ลองคำนวณด้วยเหตุผลง่ายๆ (จำนวนที่อยู่ที่ถูกใช้ ≈ อัตราคนมาใหม่ × อายุสัญญา เมื่ออุปกรณ์ไม่ส่ง DHCPRELEASE ตอนจากไป เช่น มือถือที่เดินออกจากร้าน)

> **โจทย์ร้านกาแฟ:** pool 100 ที่อยู่, ลูกค้าใหม่เข้าชั่วโมงละ 40 เครื่อง (ค่าสมมติ) แต่ละเครื่องอยู่ไม่ถึงชั่วโมงแล้วไป
> - lease 8 ชั่วโมง → ที่อยู่ที่ถูกกันไว้ ≈ 40 × 8 = **320** > 100 pool เต็ม เครื่องใหม่ไม่ได้ IP
> - lease 1 ชั่วโมง → ≈ 40 × 1 = **40** < 100 พอดี

จึงเป็นเหตุผลที่ Wi-Fi สาธารณะมักตั้ง lease สั้นเป็นนาทีถึงชั่วโมง ส่วนเครือข่ายองค์กรที่เครื่องอยู่ประจำที่ตั้งเป็นวันได้ (ตัวเลขนี้เป็นการประมาณเชิงหลักการ ค่าจริงขึ้นกับพฤติกรรมของอุปกรณ์)

### 2.5 DHCP relay agent: เมื่อ DHCP server อยู่คนละซับเน็ต

broadcast ข้ามเราเตอร์ไม่ได้ แต่ในองค์กรมีหลายซับเน็ตและเซิร์ฟเวอร์ DHCP กลางเครื่องเดียว ทางแก้คือ **relay agent** (เรียกอีกอย่างว่า IP helper) บนเราเตอร์/สวิตช์ L3 ที่ซับเน็ตของลูกข่าย

### 2.6 Reservation และการตั้ง IP ถาวร

อุปกรณ์ที่ต้องได้ IP เดิมเสมอ (เครื่องพิมพ์, NAS, กล้อง) มีสองแนวทาง

| แนวทาง | วิธี | เหมาะเมื่อ |
|---|---|---|
| **DHCP reservation** | ตั้งในเซิร์ฟเวอร์ให้ MAC นี้ได้ IP นี้เสมอ | ต้องการบริหาร IP จากจุดเดียว เปลี่ยนค่าที่เดียว |
| **Static IP** | ตั้งที่ตัวอุปกรณ์เอง **นอกช่วง pool** | อุปกรณ์โครงสร้างที่ต้องทำงานแม้ DHCP ล่ม (เราเตอร์, เซิร์ฟเวอร์ DHCP เอง) |

ตัวอย่าง `/etc/dhcp/dhcpd.conf` ของ ISC DHCP

```text
subnet 192.168.1.0 netmask 255.255.255.0 {
    range 192.168.1.100 192.168.1.199;          # pool 100 ที่อยู่
    option routers 192.168.1.1;                 # option 3
    option domain-name-servers 192.168.1.1;     # option 6
    default-lease-time 28800;                   # 8 ชั่วโมง
    max-lease-time 86400;
}
host office-printer {
    hardware ethernet 00:11:22:33:44:55;
    fixed-address 192.168.1.50;                 # อยู่นอก range เพื่อไม่ชนกับ pool
}
```

> **กฎเหล็ก:** static IP ที่ตั้งด้วยมือ ต้องอยู่ *นอก* ช่วง `range` ของ pool ไม่เช่นนั้นเซิร์ฟเวอร์อาจเสนอที่อยู่นั้นให้เครื่องอื่น เกิด **IP ซ้ำ (IP conflict)** (ISC DHCP จะตรวจด้วย ping/ARP ก่อนเสนอในบางโหมด แต่ไม่ใช่ทุกซอฟต์แวร์ทำ)

### 2.7 เมื่อ DHCP ล้มเหลว: APIPA

ถ้า DISCOVER ไม่มีใครตอบหลังลองหลายรอบ Windows (และบางระบบ) กำหนดที่อยู่เองจาก `169.254.0.0/16` (APIPA/link-local) โดยสุ่ม แล้วใช้ ARP ตรวจว่าไม่ซ้ำ ที่อยู่นี้คุยได้เฉพาะเครื่องในวงเดียวกันที่ใช้ APIPA ด้วย **ไม่มี gateway** จึงออกอินเทอร์เน็ตไม่ได้ เห็น `169.254.x.x` = *"DHCP เอื้อมไม่ถึงหรือ pool เต็ม"* ไม่ใช่ปัญหาสายหลวมเสมอไป

## 3. DNS: สมุดโทรศัพท์แบบกระจายของอินเทอร์เน็ต

### 3.1 ทำไมไม่ใช้ไฟล์เดียว

ยุคแรกของอินเทอร์เน็ตใช้ไฟล์ `HOSTS.TXT` ไฟล์เดียวที่ทุกเครื่องดาวน์โหลดจากส่วนกลาง เมื่อเครือข่ายโตขึ้นก็เกิดปัญหา ไฟล์ใหญ่ขึ้นเรื่อยๆ ต้องแจกซ้ำถี่ ชื่อซ้ำกัน และ *มีจุดล้มเหลวจุดเดียว* **DNS** (ออกแบบปี 1983) แก้ด้วยสามแนวคิด

1. **ลำดับชั้น (hierarchy):** ชื่อเป็นต้นไม้ อ่านจากขวาไปซ้าย `www.example.com.` = root (`.`) → `com` → `example` → `www`
2. **การมอบหมาย (delegation):** แต่ละระดับ *มอบอำนาจ* ให้ผู้อื่นดูแลระดับล่าง จึงไม่มีใครถือฐานข้อมูลทั้งโลก
3. **แคช (caching):** คำตอบถูกจำตามเวลา **TTL** ลดภาระผู้ดูแลต้นทางได้มหาศาล

ผู้ดูแลแต่ละส่วนของต้นไม้เรียกว่า **zone** (ต่างจาก domain เล็กน้อย: zone คือส่วนที่เซิร์ฟเวอร์ชุดหนึ่งรับผิดชอบจริง ถ้า `example.com` มอบ `dev.example.com` ให้ทีมอื่น ก็เป็นอีก zone หนึ่ง) การมอบหมายเกิดจาก record **NS** ใน zone แม่ ที่ชี้ไปยัง name server ของ zone ลูก พร้อม **glue record** (A/AAAA ของ name server นั้น ใส่ไว้ใน zone แม่) เพื่อไม่ให้เกิดวงวน เช่น ถ้า name server ของ `example.com` ชื่อ `ns1.example.com` ต้องมี IP ให้ก่อนจึงจะถามมันได้

### 3.2 สองบทบาทของเซิร์ฟเวอร์ และสองรูปแบบการถาม

| บทบาท | หน้าที่ | ตัวอย่าง |
|---|---|---|
| **Stub resolver** | ตัวเล็กในระบบปฏิบัติการ ส่งคำถามต่อและรับคำตอบสุดท้าย | เครื่องเรา |
| **Recursive resolver** | ทำงานแทนเราจนได้คำตอบ แล้วแคชไว้ | เราเตอร์บ้าน, DNS ของ ISP, 1.1.1.1, 8.8.8.8 |
| **Authoritative server** | ถือข้อมูลจริงของ zone ตอบเฉพาะ zone ตัวเอง *ไม่ทำ* recursion ให้ใคร | server ที่ผู้ถือโดเมนเลือก |

- **Recursive query:** ลูกข่ายขอ "ตอบคำตอบสุดท้ายให้ที ไม่ต้องบอกว่าไปถามใครต่อ"
- **Iterative query:** resolver ถามแต่ละ server แล้วได้ "ฉันไม่รู้ แต่ลองไปถามคนนี้" (**referral**) แล้วถามต่อเอง

ในทางปฏิบัติ: เครื่องเรา→resolver เป็น recursive ส่วน resolver→root/TLD/authoritative เป็น iterative ลองสลับชื่อและสถานะแคชในสื่อนี้ แล้วเล่นทีละขั้น

::dns-resolver
::

สังเกตสามอย่าง (1) **แคชว่าง** ต้องถามข้างนอกสามครั้ง (2) ถ้า resolver จำ server ของ TLD ได้แล้วจะข้าม root (3) **ชื่อที่ไม่มีอยู่** ก็ถูกแคช (negative caching) เพื่อไม่ให้ถามซ้ำๆ

### 3.4 แคชและ TTL: หัวใจของประสิทธิภาพ

ทุกคำตอบมี **TTL** (วินาที) ที่ผู้ดูแล zone กำหนด resolver จะเก็บไว้และนับถอยหลัง เมื่อเหลือ 0 จึงถามใหม่ ทำให้เกิดทั้งข้อดีและข้อจำกัด

**ข้อดี (เชิงปริมาณ):** ใช้ค่าประมาณจากสื่อด้านบน: ตอบจากแคช ≈ 2 ms, ตอบเมื่อแคชว่าง ≈ 94 ms (2 + 20 + 30 + 40 + 2 ซึ่งเป็นค่าสมมติเพื่อเปรียบเทียบ)

| อัตราแคชโดน (hit rate) | เวลาตอบเฉลี่ย |
|---|---|
| 95% | 0.95 × 2 + 0.05 × 94 = **6.6 ms** |
| 99% | 0.99 × 2 + 0.01 × 94 ≈ **2.9 ms** |

(คำนวณจริงแล้ว) เพียงเพิ่ม hit rate จาก 95% เป็น 99% ลดเวลาเฉลี่ยลงกว่าครึ่ง นี่คือเหตุผลที่ TTL ไม่ควรสั้นเกินจำเป็น

**ข้อจำกัด:** เมื่อเปลี่ยน IP ของเซิร์ฟเวอร์ ผู้ใช้บางคนยังเห็น IP เก่าจนกว่า TTL จะหมดทั่วโลก แนวปฏิบัติคือ *ลด TTL ล่วงหน้า* (เช่นเหลือ 300 วินาที) ก่อนวันย้ายอย่างน้อยหนึ่งช่วง TTL เดิม แล้วย้าย แล้วค่อยปรับกลับ

**Negative caching:** ผลลบ (NXDOMAIN หรือ NODATA) ถูกแคชด้วย ตามค่าใน record **SOA** ของ zone (RFC 2308) ผู้ใช้ที่พิมพ์ชื่อผิดซ้ำๆ จึงไม่ต้องถามต้นทางทุกครั้ง แต่ก็หมายความว่าหากเพิ่งสร้าง record ใหม่ resolver บางตัวยังตอบ "ไม่มี" ต่ออีกพักหนึ่ง

**แคชมีหลายชั้น:** เบราว์เซอร์ → แคชของระบบปฏิบัติการ → resolver ของเราเตอร์ → resolver ของ ISP แต่ละชั้นมี TTL ของตัวเอง ดังนั้นอาการ "ล้างแล้วยังเห็นของเก่า" มักเกิดจากชั้นที่เรายังไม่ได้ล้าง

### 3.5 ชนิดของ resource record

| ชนิด | ความหมาย | ตัวอย่าง |
|---|---|---|
| **A** | ชื่อ → IPv4 | `www  A  93.184.216.34` |
| **AAAA** | ชื่อ → IPv6 | `www  AAAA  2606:2800:220:1::1` (ตัวอย่าง) |
| **CNAME** | ชื่อเล่น (alias) → *ชื่ออื่น* | `www  CNAME  server1.example.com.` |
| **MX** | เซิร์ฟเวอร์อีเมลของโดเมน พร้อมลำดับความสำคัญ | `@  MX  10 mail.example.com.` |
| **NS** | name server ที่ดูแล zone | `@  NS  ns1.example.com.` |
| **PTR** | IP → ชื่อ (reverse DNS) อยู่ใน `in-addr.arpa` | `10.2.0.192.in-addr.arpa  PTR  server1...` |
| **TXT** | ข้อความทั่วไป ใช้ยืนยันโดเมน, SPF, DKIM | `@  TXT  v=spf1 ...` |
| **SOA** | ข้อมูลหลักของ zone (เซิร์ฟเวอร์หลัก, serial, ค่า negative TTL) | หนึ่งแถวต่อ zone |

**ข้อควรระวังของ CNAME**

- ต้องชี้ไป **ชื่อ** ไม่ใช่ IP
- **ห้ามอยู่ร่วมกับ record อื่น** ที่ชื่อเดียวกัน จึงตั้ง CNAME ที่ *apex* ของโดเมน (`example.com` ตัวเปล่า) ไม่ได้ เพราะ apex ต้องมี SOA และ NS อยู่แล้ว (ผู้ให้บริการบางรายมีฟีเจอร์พิเศษ เช่น ALIAS/ANAME ที่ไม่ใช่ DNS มาตรฐาน)
- **ความหน่วง:** การไล่ตามชื่อเล่นต้องแปลงชื่อปลายทางอีกชั้น ถ้า authoritative ถือทั้งสองชื่อ มักส่งตอบมาพร้อมกันในข้อความเดียว จึงไม่ช้ากว่ามาก แต่ถ้าชื่อปลายทางอยู่ในอีก zone/ผู้ให้บริการ (เช่น ชี้ไปบริการ CDN) resolver ต้องถามเพิ่ม และ TTL ของสองชื่ออาจต่างกัน ซึ่งเป็นคำตอบของคำถามท้ายบทข้อ 2

### 3.6 การขนส่ง: UDP, TCP และ DNS แบบเข้ารหัส

- ปกติใช้ **UDP/53** เพราะคำถาม-ตอบเล็กและเร็ว (ข้อความ DNS ดั้งเดิมจำกัดที่ 512 ไบต์ ปัจจุบันขยายด้วย EDNS0)
- ถ้าคำตอบใหญ่เกินจนถูกตัด (บิต TC) จะลองใหม่ด้วย **TCP/53** รวมถึงการถ่ายโอน zone (AXFR)
- DNS ดั้งเดิม **ไม่เข้ารหัส** ผู้ดักฟังบนเส้นทางเห็นว่าเราถามชื่ออะไร ทางแก้คือ **DoT** (DNS over TLS, พอร์ต 853) และ **DoH** (DNS over HTTPS, พอร์ต 443) ซึ่งปกป้องการอ่านระหว่างเครื่องกับ resolver แต่ *resolver ยังเห็นทุกคำถาม* ไม่ได้ทำให้ไม่ระบุตัวตน

### 3.7 เครื่องเราแปลงชื่ออย่างไร ตามลำดับ

1. ไฟล์ **hosts** (`/etc/hosts` หรือ `System32/drivers/etc/hosts` บน Windows) ตามที่เรียนในบทก่อน
2. **แคชของระบบปฏิบัติการ** (Windows DNS Client, systemd-resolved)
3. ถาม resolver ที่ DHCP แจกมา (option 6) ลองตามลำดับถ้าตัวแรกเงียบ
4. ชื่อสั้นไม่มีจุด (เช่น `intranet`) จะถูกต่อท้ายด้วย **DNS suffix / search domain** (option 15) แล้วลองใหม่

## 4. NAT: ทบทวนและส่วนที่ต้องรู้ในงานดูแลระบบ

หลักการของ NAT/PAT (ตารางการแปล, พอร์ตชน, port forwarding, CGNAT) อธิบายละเอียดไว้แล้วใน[บทเรื่อง Public/Private IP](/roadmap-sh/fundamental-it-skills/03-core-computer-networking/04-public-and-private-ip-addresses) บทนี้เติมสิ่งที่ผู้ดูแลระบบเจอจริง

### 4.1 Connection tracking: หัวใจของ NAT แบบมีสถานะ

NAT ที่ใช้จริงเป็นแบบ **stateful** เคอร์เนล Linux (Netfilter) บันทึกทุกการเชื่อมต่อไว้ในตาราง **conntrack** ด้วยทั้งสองทิศ จึงรู้ว่าแพ็กเก็ตขาเข้าเป็นคำตอบของการเชื่อมต่อใด ตัวอย่างหนึ่งบรรทัด

```text
tcp 6 431999 ESTABLISHED src=192.168.1.10 dst=198.51.100.25 sport=51001 dport=443
    src=198.51.100.25 dst=203.0.113.5 sport=443 dport=60001 [ASSURED]
```

ครึ่งแรกคือทิศ *ไป* (ที่เครื่องในส่งออก) ครึ่งหลังคือทิศ *กลับ* ที่ที่อยู่ต่างไปเพราะแปลงแล้ว (ปลายทางขากลับคือ `203.0.113.5:60001`) ตัวเลข `431999` คือวินาทีที่เหลือก่อนแถวหมดอายุ ซึ่งสถานะ ESTABLISHED ตั้งค่าปริยายนานราว 5 วัน แต่ UDP หรือการเชื่อมต่อที่ยังไม่เสร็จสั้นกว่ามาก (ค่าจริงขึ้นกับเคอร์เนลและการตั้งค่า)

**ผลที่ตามมา**

- ตารางมีขนาดจำกัด เมื่อเต็ม แพ็กเก็ตใหม่ถูกทิ้ง (เห็น `nf_conntrack: table full, dropping packet` ใน log)
- การเชื่อมต่อที่เงียบนานเกินเวลา แล้วฝั่งหนึ่งส่งต่อ จะไม่ตรงแถวใด เซสชัน SSH ค้างจึงเป็นอาการคลาสสิกของ **timeout ของ NAT** (แก้ด้วย keepalive)
- เราเตอร์ที่แปลงแล้วจะ *ไม่รู้จัก* แพ็กเก็ตขาเข้าที่ไม่มีแถว จึงทิ้ง (นี่คือ "ไฟร์วอลล์โดยปริยาย" แต่ไม่ใช่ความปลอดภัยที่ออกแบบมา)

### 4.2 SNAT, MASQUERADE และ DNAT

| ชนิด | เขียนอะไร | ตำแหน่ง (Linux iptables) | ใช้เมื่อ |
|---|---|---|---|
| **SNAT** | ที่อยู่ *ต้นทาง* ของแพ็กเก็ตขาออก | POSTROUTING | ออกอินเทอร์เน็ตด้วย public IP คงที่ |
| **MASQUERADE** | เหมือน SNAT แต่ใช้ IP ปัจจุบันของอินเทอร์เฟซ | POSTROUTING | public IP เปลี่ยนได้ (DHCP/PPPoE) |
| **DNAT** | ที่อยู่ *ปลายทาง* ของแพ็กเก็ตขาเข้า | PREROUTING | port forwarding |

```bash
# ให้ทั้ง LAN ออกอินเทอร์เน็ตผ่าน eth0 (PAT)
sudo iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
# port forwarding: พอร์ต 8080 ของเราเตอร์ -> เว็บเซิร์ฟเวอร์ภายใน
sudo iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.200:80
```

ตัวเลข: public IP หนึ่งตัวมีพอร์ตต้นทางให้ใช้ราว 64,512 พอร์ต (1024–65535) ต่อปลายทาง (IP:พอร์ต) หนึ่งคู่ ถ้า ISP ใช้ CGNAT ให้ลูกค้า 100 รายแบ่ง IP เดียว จะเหลือเฉลี่ยราว 645 พอร์ตต่อราย (64,512 ÷ 100) ซึ่งเว็บที่เปิดหลายการเชื่อมต่อพร้อมกันอาจกินหมดได้ (ตัวเลขคำนวณจริง การจัดสรรจริงขึ้นกับผู้ให้บริการ)

### 4.3 Hairpin NAT และ split-horizon: เมื่อ NAT พบ DNS

ถ้าเว็บภายในบริษัทมีชื่อ `files.company.com` ที่ DNS สาธารณะชี้ไป public IP ของเราเตอร์ (ที่ทำ port forward) พนักงานที่นั่งในออฟฟิศ *ข้างในเครือข่าย* เปิดชื่อนี้ ก็ได้ public IP เดียวกัน แล้วแพ็กเก็ตต้องออกไปที่เราเตอร์แล้ว *วกกลับ* เข้า LAN (เรียก **hairpin / NAT loopback**) ซึ่งเราเตอร์บางรุ่นทำไม่ได้ ผลคือในออฟฟิศเปิดไม่ได้แต่จากบ้านเปิดได้

ทางแก้แบบองค์กรคือ **split-horizon DNS** (ตอบต่างกันตามผู้ถาม) ให้ DNS ภายในตอบ `files.company.com → 192.168.1.20` แต่ DNS สาธารณะตอบ public IP ข้อควรระวัง: ชุดข้อมูลภายในไม่ควรหลุดไปสู่ DNS สาธารณะ เพราะเผยโครงสร้างเครือข่าย

## 7. มุมมองด้าน Security

ทั้งสามบริการ *ออกแบบในยุคที่ทุกคนในเครือข่ายเชื่อใจกัน* จึงไม่ตรวจตัวตนผู้แจก/ผู้ตอบโดยปริยาย

| การโจมตี | กลไกที่ถูกใช้ | การป้องกัน |
|---|---|---|
| **Rogue DHCP server** | ผู้โจมตีเสียบเซิร์ฟเวอร์ DHCP เถื่อน ตอบ OFFER เร็วกว่า แจก **gateway และ DNS เป็นของตัวเอง** (ลูกข่ายเชื่อ OFFER แรกที่มา) ทำ MITM ได้ทั้งหมด | **DHCP snooping** บนสวิตช์: ยอมให้ตอบ OFFER/ACK เฉพาะพอร์ตที่เชื่อถือ |
| **DHCP starvation** | ส่ง DISCOVER ด้วย MAC ปลอมต่อเนื่องจน pool หมด (ตามโจทย์ร้านกาแฟ) แล้วตั้ง rogue server ตามหลัง | port security จำกัดจำนวน MAC ต่อพอร์ต, DHCP snooping rate limit |
| **DNS cache poisoning** | ผู้โจมตีส่งคำตอบปลอมให้ resolver ก่อนคำตอบจริง ต้องเดาให้ตรง ID 16 บิตและพอร์ตต้นทาง (Kaminsky, 2008) | **สุ่มพอร์ตต้นทาง** (รวมกับ ID ได้ราว 2³² ≈ 4.3 พันล้านความเป็นไปได้ แทน 65,536) และ **DNSSEC** ที่ลงลายเซ็นข้อมูล |
| **DNS hijack ที่เราเตอร์** | เจาะเราเตอร์แก้ DNS server ให้ชี้ไปของผู้โจมตี คนทั้งบ้านเปิดเว็บปลอม | เปลี่ยนรหัสผ่านเราเตอร์ อัปเดตเฟิร์มแวร์ ตรวจ DNS ที่ตั้งไว้ |
| **DNS tunneling** | ซ่อนข้อมูลในชื่อโดเมนยาวๆ (`data.evil.com`) ผ่าน DNS ที่ไฟร์วอลล์มักอนุญาต ใช้ลักลอบข้อมูล | เฝ้าดูชื่อยาวหรือปริมาณ TXT/ query ผิดปกติ |
| **DNS amplification (DDoS)** | ส่งคำถามเล็กโดยปลอมต้นทางเป็นของเหยื่อ ให้ resolver เปิดตอบคำตอบใหญ่ท่วมเหยื่อ | ปิด open resolver จำกัดให้ตอบเฉพาะเครือข่ายตัวเอง, response rate limiting, กรองการปลอมต้นทาง |
| **Typosquatting / domain ปลอม** | ลงทะเบียนชื่อที่พิมพ์ผิดง่าย (`examp1e.com`) | ใช้ bookmark, ตรวจ URL, DNS filtering |
| **ถือว่า NAT = ไฟร์วอลล์** | NAT ทิ้งแพ็กเก็ตที่ไม่มีแถวใน conntrack เป็นผลข้างเคียง แต่ไม่ตรวจเนื้อหา และ UPnP/มัลแวร์เปิดรูขาออกได้ | ใช้ไฟร์วอลล์จริง ปิด UPnP ที่ไม่ต้องใช้ |
| **ข้อมูลภายในหลุดผ่าน split-horizon** | zone ภายในถูกส่งให้ DNS สาธารณะหรือ zone transfer เปิดให้ทุกคน | จำกัด AXFR เฉพาะ secondary แยกข้อมูลภายใน/ภายนอก |

**หลักคิด:** ถ้าผู้โจมตีควบคุม **DHCP** ได้ เขาควบคุม **gateway และ DNS** ของเหยื่อ ซึ่งคือเส้นทางและการแปลงชื่อทั้งหมด การป้องกันจึงควรเริ่มที่ชั้น 2 (สวิตช์) ไม่ใช่รอให้ปลายทางตรวจทีหลัง และ **DNSSEC** พิสูจน์เฉพาะ *ความถูกต้องของข้อมูล* (ข้อมูลไม่ถูกแก้) ไม่ได้เข้ารหัสและไม่ได้ป้องกันการดักดูคำถาม

|---|---|---|
| IP เป็น `169.254.x.x` | DISCOVER ไม่มีใครตอบ | ตรวจสาย/พอร์ต/VLAN, DHCP server ทำงานไหม, pool เต็มไหม, relay ของ VLAN นี้ตั้งไว้ไหม (ถ้าสายเสีย จะไม่มีข้อความเลย) |
| ได้ IP แต่ผิดซับเน็ต เช่น `192.168.0.x` ที่บ้านไม่ใช่ | **rogue DHCP** (เช่น เราเตอร์ที่เพื่อนต่อพ่วง) ตอบเร็วกว่า | `ipconfig /all` ดู DHCP Server ว่าเป็นของใคร ถอดอุปกรณ์เถื่อนหรือเปิด DHCP snooping |
| ping `8.8.8.8` ได้ แต่เปิดเว็บด้วยชื่อไม่ได้ | เส้นทางปกติ มีเฉพาะการแปลงชื่อที่พัง | `nslookup example.com` ถ้าไม่ตอบ ลองเปลี่ยน DNS ชั่วคราวเป็นตัวอื่น (เช่น `nslookup example.com 1.1.1.1`) ถ้าได้แปลว่า DNS ที่ DHCP แจกเสีย ไม่ใช่เครือข่าย |
| เปิดชื่อไม่ได้ แต่ IP ตรงได้ และ nslookup ได้ผล | ปัญหาที่ชั้นแอป/แคช/ไฟล์ hosts/ proxy ไม่ใช่ DNS ของระบบ | ล้างแคชเบราว์เซอร์/ระบบ ตรวจไฟล์ hosts, ตั้งค่า DoH ของเบราว์เซอร์ |
| เปลี่ยน IP เซิร์ฟเวอร์แล้ว บางคนเข้าเครื่องเก่า | แคชที่ resolver ยังไม่หมด TTL | รอ TTL หมด ล้างแคชเครื่อง ใช้ `dig ชื่อ @ns-ของ-zone` ถาม authoritative โดยตรงเทียบ |
| ได้ NXDOMAIN ทั้งที่เพิ่งสร้าง record | negative cache ยังไม่หมดตามค่า SOA | รอ หรือถามจาก resolver อื่น |
| ใช้งานได้ปกติทั้งวัน แล้ว IP หลุดตอนสายๆ ของทุกวัน | lease หมดและเซิร์ฟเวอร์ต่ออายุไม่ได้ (เครือข่ายหายช่วงสั้นๆ) | ตรวจ log DHCP, ดูเวลา lease ใน `ipconfig /all`, ตั้ง lease ให้ยาวขึ้น |
| IP ซ้ำ (`IP address conflict`) | static IP อยู่ใน pool หรือ reservation ซ้ำกัน | ย้าย static ออกนอก range, ตรวจตาราง lease, `arp -a` หา MAC ที่ถือ IP นั้น |
| ในออฟฟิศเปิดเว็บบริษัทด้วยชื่อไม่ได้ แต่จากบ้านเปิดได้ | NAT hairpin ไม่รองรับ | ทำ split-horizon DNS ภายใน |
| SSH ค้างหลังปล่อยไว้นาน | ตาราง NAT/conntrack หมดอายุแถวที่เงียบ | ตั้ง `ServerAliveInterval` / keepalive ส่งทราฟฟิกเป็นระยะ |
| เปิดหลายแท็บแล้วบางแท็บโหลดไม่ขึ้น เฉพาะที่ ISP ใช้ CGNAT | พอร์ตต่อลูกค้าหมด หรือ conntrack เต็ม | ลองใช้ IPv6 ถ้ามี หรือขอ IP แบบ public |

## 10. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: ทำไม DHCPDISCOVER ใช้ต้นทาง 0.0.0.0 และปลายทาง 255.255.255.255 ทำไมไม่ใช้ TCP"}
เครื่องยังไม่มี IP จึงไม่มีที่อยู่ต้นทางที่ใช้ได้ (ใช้ 0.0.0.0) และไม่รู้ที่อยู่ของเซิร์ฟเวอร์จึงต้อง broadcast ใช้ UDP เพราะ TCP ต้อง handshake ด้วย IP ที่ใช้งานได้ทั้งสองฝั่งก่อน และการสื่อสารแบบถามตอบสั้นๆ ไม่ต้องการ connection
::

::reveal{question="ข้อ 2 (ท้ายบท): ถ้ามี DHCP server สองตัวในวงเดียวกันเสนอค่าต่างกัน เกิดอะไรขึ้น"}
ทั้งสองส่ง OFFER ลูกข่ายมักเลือกข้อเสนอที่มาถึงก่อน แล้วส่ง REQUEST แบบ broadcast ที่ระบุ server-id ของตัวที่เลือก อีกตัวเห็นว่าไม่ใช่ตน จึงถอนข้อเสนอ ผลคือลูกข่ายได้ค่าจากตัวที่ตอบเร็วกว่า ซึ่งอาจเป็น *ตัวที่ตั้งผิดหรือเป็น rogue* ถ้าสองตัวมี pool ซ้อนกันโดยไม่ประสานกัน อาจแจก IP เดียวกันให้สองเครื่อง (IP conflict) ทางแก้คือใช้ failover ของ DHCP ที่แบ่ง pool/ซิงก์สถานะ และเปิด DHCP snooping
::

::reveal{question="ข้อ 3: lease 7 วัน T1 และ T2 อยู่ที่เวลาใด และถ้า server ล่มหลัง T1 เครื่องต้องทิ้ง IP เมื่อไหร่"}
T1 = 7 × 0.5 = **3.5 วัน**, T2 = 7 × 0.875 = **6.125 วัน** (6 วัน 3 ชั่วโมง) เครื่องยังใช้ IP ได้จนถึง **7 วันเต็ม** ระหว่างนั้นลอง unicast ที่ T1 แล้ว broadcast ที่ T2 ถ้าไม่มีใครตอบเลยจึงทิ้ง IP ที่วันที่ 7 (คำนวณจริง)
::

::reveal{question="ข้อ 4: ทำไมต้องกำหนดอายุ lease ทั้งที่แจก IP ถาวรก็ง่ายกว่า"}
เพื่อให้ pool คืนที่อยู่ของเครื่องที่หายไปโดยอัตโนมัติ (มือถือที่เดินจากไปไม่ได้แจ้งลา) ถ้าถาวร pool จะรั่วไหลจนเต็ม ดูโจทย์ร้านกาแฟ: lease 8 ชั่วโมงกันที่อยู่ ≈ 320 ที่ แต่ pool มี 100
::

::reveal{question="ข้อ 5: ลูกข่ายอยู่ VLAN 20 แต่ DHCP server อยู่ VLAN 99 ลูกข่ายได้ 169.254.x.x เสมอ ตรวจอะไรเป็นอย่างแรก"}
ตรวจว่า **เราเตอร์/สวิตช์ L3 ของ VLAN 20 ตั้ง DHCP relay (IP helper) ชี้ไป server หรือไม่** เพราะ broadcast ของ DISCOVER ข้ามเราเตอร์ไม่ได้ ถ้าไม่มี relay เซิร์ฟเวอร์ไม่ได้ยินเลย รองลงมาคือตรวจว่า server มี scope (pool) สำหรับซับเน็ตของ giaddr นั้นด้วย ไม่เช่นนั้นจะไม่ตอบ
::

::reveal{question="ข้อ 6: ทำไม DNS จึงไม่ถาม root server ทุกครั้งที่เปิดเว็บ"}
เพราะ **แคช**: resolver จำทั้งคำตอบสุดท้ายและ NS ของ TLD/โดเมนที่ได้ระหว่างทางไว้ตาม TTL (NS ของ TLD มักมี TTL ระดับวัน) จึงเริ่มที่ขั้นกลางหรือตอบทันที ถ้าถาม root ทุกครั้ง root จะรับภาระมหาศาลและทุกคำขอจะช้า
::

::reveal{question="ข้อ 7 (ท้ายบท): ทำไม CNAME จึงอาจทำให้ช้ากว่า A record โดยตรง และไม่ช้าเสมอไปเพราะอะไร"}
CNAME ชี้ไป *ชื่ออื่น* ซึ่งต้องแปลงต่ออีกชั้น ถ้าชื่อปลายทางอยู่ใน zone/ผู้ให้บริการอื่นและไม่อยู่ในแคช resolver ต้องถามเพิ่ม (เพิ่ม RTT และมีหลาย TTL) แต่ถ้า authoritative ถือทั้งสองชื่อมักตอบรวมในข้อความเดียว และเมื่ออยู่ในแคชก็ไม่ช้า ผลกระทบจึงขึ้นกับเส้นทาง ไม่ใช่ทุกกรณีที่ช้าเด่นชัด
::

::reveal{question="ข้อ 8: ตั้ง CNAME ที่ example.com (apex) ได้ไหม เพราะอะไร"}
**ไม่ได้ตามมาตรฐาน** เพราะ CNAME ห้ามอยู่ร่วมกับ record อื่นที่ชื่อเดียวกัน แต่ apex ต้องมี SOA และ NS เสมอ (และมักมี MX/TXT ด้วย) ถ้าต้องการชี้ apex ไปผู้ให้บริการ ใช้ A/AAAA ที่ได้จากผู้ให้บริการ หรือฟีเจอร์ ALIAS/ANAME ของผู้ให้บริการ DNS บางราย
::

::reveal{question="ข้อ 9: ping 8.8.8.8 ได้ แต่ ping google.com ว่า could not find host อาการนี้แยกอะไรออกได้"}
แยกได้ว่า **เส้นทาง IP และ gateway ปกติ** (ถึง 8.8.8.8 ได้) ปัญหาอยู่ที่ **การแปลงชื่อ** เท่านั้น: DNS server ที่ได้จาก DHCP ใช้ไม่ได้ หรือเข้าถึง UDP/53 ไม่ได้ ตรวจด้วย `nslookup google.com` เทียบกับระบุ server อื่น
::

::reveal{question="ข้อ 10: เหตุใดการสุ่มพอร์ตต้นทางของ resolver จึงช่วยกัน DNS poisoning"}
ผู้โจมตีต้องส่งคำตอบปลอมที่ตรงทั้ง **ID (16 บิต = 65,536 ค่า)** และ **พอร์ตต้นทาง** ที่ resolver ใช้ถาม ถ้าพอร์ตคงที่ เดาแค่ ID ก็พอ แต่ถ้าสุ่มพอร์ตราว 64,000 ค่า ความเป็นไปได้เพิ่มเป็น ≈ 65,536 × 64,000 ≈ **4.2 พันล้าน** (ราว 2³²) ทำให้เดาในเวลาจำกัดยากขึ้นมาก (คำนวณจริง ค่าประมาณของจำนวนพอร์ตที่ใช้ได้)
::

::reveal{question="ข้อ 11 (กลางบท): เครื่อง 10.0.0.5 พอร์ต 49820 ถูก NAT เป็น 198.51.100.1:32005 เซิร์ฟเวอร์ตอบมาที่ 198.51.100.1:32005 เราเตอร์ทำอย่างไร"}
ค้นตาราง conntrack ด้วยพอร์ต/ที่อยู่ที่แปลงแล้ว พบแถว จึง **เขียนปลายทางกลับเป็น 10.0.0.5:49820 แล้วส่งเข้า LAN** ไม่ใช่ทิ้ง ไม่ broadcast เพราะแถวนั้นบอกชัดว่าเป็นของเครื่องใด
::

::reveal{question="ข้อ 12 (ท้ายบท): PAT ป้องกันเครื่องสองเครื่องใช้พอร์ตต้นทางเดียวกันชนกันภายนอกได้อย่างไร"}
เราเตอร์ **เปลี่ยนพอร์ตต้นทาง (remap)** ของอย่างน้อยหนึ่งเครื่อง เช่น ทั้งคู่ใช้ 51001 แต่ถูกแปลงเป็น 60001 และ 60002 ภายนอกจึงเห็นการเชื่อมต่อสองสายที่ต่างกันด้วยพอร์ต ตารางจดคู่ก่อน-หลังไว้เพื่อแปลงกลับ
::

::reveal{question="ข้อ 13 (ท้ายบท): ทำไมเครื่องภายนอกเริ่มเชื่อมต่อเข้ามาที่ IP ส่วนตัวหลัง NAT เองไม่ได้ถ้าไม่มี port forwarding"}
เพราะ (1) IP ส่วนตัวไม่ถูกส่งต่อบนอินเทอร์เน็ต ผู้อื่นเห็นแค่ public IP ของเราเตอร์ และ (2) แพ็กเก็ตขาเข้าที่ *ไม่ตรงแถวใน conntrack* (ไม่มีใครข้างในเริ่มคุยก่อน) เราเตอร์ไม่รู้ว่าจะส่งให้เครื่องไหนจึงทิ้ง port forwarding คือการสร้างกฎ DNAT ถาวรเพื่อบอกว่าพอร์ตนี้ให้ส่งไปเครื่องนั้น
::

::reveal{question="โจทย์: เพิ่ม hit rate ของแคช DNS จาก 95% เป็น 99% (hit ≈ 2 ms, miss ≈ 94 ms) เวลาเฉลี่ยเปลี่ยนเท่าไร"}
95%: 0.95×2 + 0.05×94 = 1.9 + 4.7 = **6.6 ms** · 99%: 0.99×2 + 0.01×94 = 1.98 + 0.94 = **2.92 ms** ลดลงราว **56%** (คำนวณจริง; ค่า ms เป็นค่าสมมติเพื่อเปรียบเทียบ)
::

## 11. แบบฝึกหัด (ลงมือทำจริง)

ทุกคำสั่งอ่านอย่างเดียว ไม่เปลี่ยนการตั้งค่า (ยกเว้นข้อ 5 ที่ล้างแคช ซึ่งไม่เป็นอันตราย)

1. **ดู lease ของเครื่องคุณ:** Windows `ipconfig /all` Linux `ip -4 addr show` และ `nmcli device show` (หา `DHCP4`) จด IP, gateway, DNS, DHCP server และเวลาเช่า แล้วคำนวณ T1/T2
2. **เทียบกับตารางเส้นทาง:** ค่า gateway ที่ DHCP แจกต้องตรงกับแถว `default` (`ip route` / `route print -4`) จากบทที่แล้ว
3. **หาว่าใครแจก DNS:** เทียบ DNS server ใน `ipconfig /all` กับที่คุณเคยตั้งเอง (ถ้ามี) หรือกับค่าของเราเตอร์
4. **ถามด้วยตา: แคชทำงาน:** รัน `nslookup example.com` (หรือ `dig example.com`) สองครั้งติดกัน เทียบเวลา (Linux) หรือ TTL ที่ลดลง
5. **ถาม server ต่างกัน:** `nslookup example.com 1.1.1.1` เทียบกับ resolver ปกติ ได้ IP เดียวกันไหม ถ้าไม่ เหตุผลอาจเป็นภูมิภาคหรือ CDN
6. **ดูเส้นทางชื่อ:** `dig +trace example.com` (ถ้ามี dig) ไล่ดู root → TLD → authoritative เทียบกับสื่อด้านบน
7. **ดู reverse DNS:** `nslookup 1.1.1.1` ได้ชื่ออะไรกลับมา
8. **ดู public IP เทียบ IP ในเครื่อง:** เปิดเว็บแสดง IP ของคุณ เทียบกับ IP ในเครื่อง (ถ้าต่างกัน แสดงว่าอยู่หลัง NAT) และถ้า IP ฝั่ง WAN ที่หน้าเราเตอร์แสดงอยู่ในช่วง `100.64.0.0/10` แสดงว่าอยู่หลัง CGNAT ของ ISP

::reveal{question="แนวคำตอบ"}
(1) lease ทั่วไปของเราเตอร์บ้านคือ 24 ชั่วโมง T1 = 12 ชั่วโมง T2 = 21 ชั่วโมง แต่บางรุ่นตั้งเป็นนาทีถึงชั่วโมง · (2) gateway ใน ipconfig ต้องตรงกับ `0.0.0.0/0 via ...` · (3) ที่บ้านมักเป็น IP ของเราเตอร์ (เช่น 192.168.1.1) ซึ่งทำ forwarder ต่อไป ISP · (4) ครั้งที่สองเร็วกว่ามากหรือ TTL ลดลง · (5) IP อาจต่างเมื่อบริการใช้ CDN ตอบตามที่ตั้งผู้ถาม ซึ่งไม่ผิดปกติ · (6) เห็น NS ของ root, ของ .com, และของโดเมน ตามลำดับ · (7) ชื่อ PTR เช่น `one.one.one.one` · (8) ถ้า IP สาธารณะต่างจาก IP ในเครื่อง = อยู่หลัง NAT ตามปกติ
::

## 12. สรุป

- **DHCP** แก้ปัญหาไก่กับไข่ด้วย broadcast (0.0.0.0 → 255.255.255.255, UDP 68→67) ผ่าน **DORA** และได้ IP แบบ *เช่า* พร้อม mask, gateway, DNS และ lease
- REQUEST เป็น broadcast พร้อม server-id เพื่อให้ทุกเซิร์ฟเวอร์รู้ว่าเลือกใคร · **T1 = 50%** (unicast) และ **T2 = 87.5%** (broadcast) ทำให้ทนเซิร์ฟเวอร์ล่มชั่วคราว
- ข้ามซับเน็ตต้องมี **relay agent** (giaddr) · static IP ต้องอยู่นอก pool · `169.254.x.x` = DHCP ไม่สำเร็จ
- **DNS** เป็นต้นไม้ที่มอบหมายอำนาจ (zone, NS, glue) resolver ถาม root → TLD → authoritative แบบ iterative ให้เรา · **แคชและ TTL** คือเหตุผลที่ระบบเร็วและเหตุผลที่การเปลี่ยนค่าใช้เวลา รวมถึง negative caching
- CNAME ชี้ชื่อ ไม่ใช่ IP และห้ามที่ apex · DNS ดั้งเดิมไม่เข้ารหัส (DoT/DoH ช่วยแต่ resolver ยังเห็น)
- **NAT** แบบมีสถานะใช้ **conntrack** สองทิศ · SNAT/MASQUERADE แปลงต้นทาง, DNAT แปลงปลายทาง · ระวังแถวหมดอายุ ตารางเต็ม hairpin และ NAT ไม่ใช่ไฟร์วอลล์
- Security: rogue DHCP (แจก gateway/DNS ปลอม) ป้องกันที่ DHCP snooping, DNS poisoning ป้องกันด้วยสุ่มพอร์ต + DNSSEC
- บทถัดไป: Routing, Switching, VLAN และ DMZ ซึ่งใช้ตัวเลือกที่เรียนมาแบ่งและป้องกันเครือข่าย
