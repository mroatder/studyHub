## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. ถาม 4 คำถามหลักของการแก้ปัญหา Linux ได้: บริการรันอยู่ไหม ทรัพยากรพอไหม ล็อกบอกอะไร เครือข่ายคุยได้ไหม
2. ใช้ `systemctl status/start/enable` และอ่านผลว่าบริการ `active`, `inactive` หรือ `failed`
3. ใช้ `ps aux | grep` หา PID และเลือก `kill` (SIGTERM) ก่อน `kill -9` (SIGKILL) อย่างรู้เหตุผล
4. อ่านผล `free -h` โดยแยก `free` กับ `available` และอ่าน load average จาก `top` เทียบกับจำนวนแกน CPU
5. อธิบายได้ว่าทำไมพื้นที่ว่างเหลือแต่ขึ้น "No space left on device" (inode หมด) และใช้ `df -h`, `df -i`, `du -sh` ตรวจ
6. อ่านล็อกด้วย `journalctl`, ไฟล์ใน `/var/log`, `tail -f`, `dmesg`
7. ตรวจ IP และพอร์ตที่เปิดฟังด้วย `ip addr show` และ `ss -tulpn`
8. ไล่วิเคราะห์บริการที่พังตามลำดับ status → logs → port และบันทึกลง ticket

## สรุปสั้น (TL;DR)

อย่าเดา ให้ **ถามระบบด้วยคำสั่ง** แล้วตอบ 4 คำถามตามลำดับ

| คำถาม | คำสั่งหลัก |
|---|---|
| บริการ/โปรเซสรันอยู่ไหม | `systemctl status`, `ps aux`, `kill` |
| ทรัพยากรพอไหม | `free -h`, `top`, `df -h`, `df -i`, `du -sh` |
| ล็อกบอกอะไร | `journalctl -u`, `tail -f /var/log/...`, `dmesg` |
| เครือข่ายใช้ได้ไหม | `ip addr show`, `ss -tulpn` |

กฎเหล็ก: **ดูก่อน แก้ทีหลัง** อ่านล็อกก่อนรีสตาร์ต และ `kill -9` เป็นทางเลือกสุดท้าย

## เปรียบเทียบกับชีวิตจริง

นึกถึง **แพทย์ที่ตรวจคนไข้ตามขั้นตอน** ก่อนสั่งยา

| แพทย์ | คำสั่ง Linux |
|---|---|
| ดูว่าหัวใจเต้นอยู่ไหม | `systemctl status` (บริการยังทำงานไหม) |
| วัดชีพจรและความดัน | `top`, `free`, `df` (ทรัพยากรตึงตรงไหน) |
| เปิดดูประวัติการรักษาและบันทึกพยาบาล | `journalctl`, `/var/log` (เหตุการณ์ที่ผ่านมา) |
| ตรวจว่าหูได้ยินและพูดได้ไหม | `ip`, `ss` (เครือข่ายและพอร์ต) |
| ยาแรง (ผลข้างเคียงสูง) ใช้เมื่อวิธีเบาไม่ได้ผล | `kill -9` |

## ภาพรวม

เมื่อเว็บเซิร์ฟเวอร์ไม่ตอบ ผู้ใช้เขียนไฟล์ในโฮมไม่ได้ หรืองานเบื้องหลังทำให้เทอร์มินัลค้าง การเดาไม่ช่วย ต้นฉบับจัดคำสั่งตาม 4 คำถามข้างบน บทนี้ไล่ตามนั้น เติมกลไกเบื้องหลัง และปิดด้วยกรณีบริการที่พังจริงทั้งสามขั้น คำสั่งส่วนใหญ่ในบทนี้ที่ **อ่านอย่างเดียว** ปลอดภัยที่จะลองกับเครื่อง Linux ของตัวเอง ส่วนที่แก้ไขสถานะ (`start`, `kill`) จะระบุไว้

> **ก่อนเริ่ม:** คำสั่งที่เปลี่ยนสถานะระบบหรืออ่านล็อกของระบบมักต้องขึ้นต้นด้วย `sudo` (ทำเป็นผู้ดูแล) ส่วนการดูข้อมูลทั่วไปเช่น `free`, `df` ใช้ผู้ใช้ธรรมดาได้

## 1. ตรวจบริการและโปรเซส

### 1.1 systemctl: คุมบริการของ systemd

ลีนุกซ์ส่วนใหญ่ปัจจุบันใช้ **systemd** เป็น init system คือโปรเซสแรก (PID 1) ที่เปิดบริการอื่นทั้งหมดตอนบูตและคอยเฝ้าดู `systemctl` คือเครื่องมือสั่งงานและดูสถานะบริการ (service) เช่น `nginx` เว็บเซิร์ฟเวอร์

```bash
systemctl status nginx
```

ผลลัพธ์ตัวอย่างเมื่อบริการหยุดอยู่ (ค่าเป็นตัวอย่าง)

```text
○ nginx.service - A high performance web server and a reverse proxy server
     Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
     Active: inactive (dead) since Wed 2026-03-25 14:10:02 UTC; 2m 15s ago
   Main PID: 1205 (code=exited, status=0/SUCCESS)
```

อ่านทีละบรรทัด

| ส่วน | ความหมาย |
|---|---|
| **Loaded** | systemd เจอไฟล์ตั้งค่าบริการ (unit file) ไหม และ `enabled` = จะเปิดเองตอนบูต, `disabled` = ไม่เปิดเอง |
| **Active** | สถานะตอนนี้: `active (running)` ทำงานอยู่, `inactive (dead)` หยุดตามปกติ, `failed` พังหรือออกด้วยรหัสผิดพลาด |
| **Main PID** | หมายเลขโปรเซสหลักของบริการ และรหัสออก (`status=0/SUCCESS` = จบปกติ, ค่าอื่น = ผิดพลาด) |

จุดที่หลายคนสับสน: **start กับ enable ไม่เหมือนกัน** `start` เปิดตอนนี้ (หายหลังรีบูต ถ้าไม่ได้ `enable`) ส่วน `enable` ตั้งให้เปิดอัตโนมัติตอนบูตครั้งต่อไป (แต่ไม่ได้เปิดตอนนี้)

::compare-cards{:items='[{"title":"systemctl start nginx","subtitle":"ตอนนี้","points":["สั่งให้บริการเริ่มทำงานทันที","ถ้ารีบูต แล้วไม่เคย enable บริการจะไม่กลับมาเอง","ใช้หลังพบว่าบริการหยุดอยู่"]},{"title":"systemctl enable nginx","subtitle":"ครั้งหน้า (ตอนบูต)","points":["ตั้งให้ systemd เปิดบริการเองทุกครั้งที่บูต","ไม่ได้ทำให้บริการเริ่มทำงานตอนนี้","ใช้เพื่อไม่ให้ปัญหาเดิมเกิดซ้ำหลังรีบูต"]}]'}
::

```bash
sudo systemctl start nginx
sudo systemctl enable nginx
```

> **เสริมจากผู้เขียน:** `sudo systemctl restart nginx` = หยุดแล้วเริ่มใหม่, `reload` = ให้บริการอ่านค่าตั้งใหม่โดยไม่ตัดการเชื่อมต่อ (ถ้าบริการรองรับ) และ `systemctl --failed` ลิสต์บริการทั้งหมดที่พังอยู่ ใช้ตอนเปิดเครื่องที่ไม่คุ้นเคยเป็นขั้นแรก

### 1.2 ps: ดูโปรเซสที่รันอยู่

**โปรเซส (process)** คือโปรแกรมที่กำลังทำงาน เคอร์เนลให้หมายเลข **PID** ประจำตัว `ps aux` แสดงโปรเซสของทุกผู้ใช้ (`a` ทุกผู้ใช้, `u` แสดงรูปแบบมีเจ้าของและ %CPU/%MEM, `x` รวมโปรเซสที่ไม่มีเทอร์มินัล) เนื่องจากผลลัพธ์ยาว เราใช้ท่อ (`|`) ส่งให้ `grep` กรอง

```bash
ps aux | grep nginx
```

บรรทัดของ `grep` เองก็จะโผล่ในผลลัพธ์ด้วย (เพราะคำสั่งมีคำว่า nginx) ให้เมินบรรทัดนั้น หรือใช้ `pgrep nginx` ที่ให้เฉพาะ PID

### 1.3 kill: ส่งสัญญาณถึงโปรเซส

ชื่อ `kill` ทำให้เข้าใจผิด จริงๆ มันคือการ **ส่งสัญญาณ (signal)** ไปบอกโปรเซส ว่าจะทำอะไรขึ้นกับสัญญาณที่ส่ง

```bash
kill 1841        # ส่ง SIGTERM (15)  = ขอให้ปิดตัวอย่างเรียบร้อย
kill -9 1841     # ส่ง SIGKILL (9)   = เคอร์เนลยุติทันที
```

- **SIGTERM (15)** เป็นค่าเริ่มต้น โปรแกรมรับสัญญาณได้ จึงเขียน buffer ลงดิสก์ ปิดไฟล์ ปิดการเชื่อมต่อฐานข้อมูล แล้วออกเอง
- **SIGKILL (9)** โปรแกรม **รับ/ดักไม่ได้** เคอร์เนลเก็บโปรเซสทิ้งทันที ข้อมูลที่ยังอยู่ใน RAM ไม่ถูกเขียนลงดิสก์

ลองส่งสัญญาณทั้งสองแบบกับโปรเซสสมมติที่เก็บข้อมูลไว้ใน buffer และลองติ๊กให้โปรเซส "ค้าง" เพื่อดูว่าทำไมบางครั้งจึงจำเป็นต้องใช้ -9

::signal-lab
::

> **กับดัก:** `kill -9` ทำให้ข้อมูลที่ยังไม่ลงดิสก์หายและอาจทำให้ไฟล์ฐานข้อมูลเสียหาย (ต้นฉบับย้ำจุดนี้) ลำดับที่ถูกต้อง: `kill` → รอสักครู่ → ตรวจด้วย `ps` ว่าออกไหม → ถ้ายังอยู่และยืนยันว่าโปรเซสค้างจริง ค่อย `kill -9`

## 2. ตรวจทรัพยากร: หน่วยความจำ โหลด และดิสก์

เครื่องช้าหรือบริการล้มบ่อย มักเกิดจากทรัพยากรหมดใน 3 จุด คือ **หน่วยความจำ (RAM)**, **ตัวประมวลผล (CPU)** และ **ดิสก์**

### 2.1 free: อ่านหน่วยความจำให้ถูก

```bash
free -h
```

```text
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       5.2Gi       310Mi       128Mi       2.2Gi       2.1Gi
Swap:          2.0Gi       1.8Gi       200Mi
```

คนใหม่มักตกใจที่ `free` เหลือแค่ 310 MB แต่ตัวที่ต้องดูคือ **`available`** เหตุผลคือลีนุกซ์ไม่ปล่อย RAM ว่างทิ้ง แต่เอาไปทำ **แคชไฟล์ (buff/cache)** เก็บข้อมูลดิสก์ที่เพิ่งอ่านไว้ให้เปิดซ้ำเร็วขึ้น เมื่อแอปต้องการ RAM เคอร์เนล **ทิ้งแคชส่วนนี้คืนให้ทันที** ดังนั้น available ≈ free + แคชที่คืนได้ จึงบอก "RAM ที่แอปใหม่ใช้ได้จริงโดยไม่ต้องใช้ swap"

**Swap** คือพื้นที่ดิสก์ที่ใช้พักข้อมูลของ RAM เมื่อ RAM ไม่พอ (ช้ากว่า RAM มาก ตามบทฮาร์ดแวร์) ถ้า Swap ใช้ไปเกือบเต็มแบบตัวอย่างนี้ (1.8 จาก 2.0 Gi) คือเครื่องกำลังเครียด

เลื่อนแถบจำลองว่าแอปขอ RAM เพิ่ม เคอร์เนลหาให้จากไหนตามลำดับ

::

### 2.2 top: เฝ้าดูโปรเซสและโหลดแบบสด

```bash
top
```

`top` รีเฟรชทุกไม่กี่วินาที แถวบนมี **load average** 3 ค่า คือค่าเฉลี่ยใน 1, 5, 15 นาที ซึ่งนับ "จำนวนโปรเซสที่กำลังใช้หรือรอใช้ CPU" (บนลีนุกซ์รวมโปรเซสที่รอดิสก์ด้วย) เกณฑ์ตัดสินคือเทียบกับ **จำนวนแกน CPU** เช่น เครื่อง 4 แกน load 4.0 = ใช้เต็ม 100% ถ้าเกินนั้น มีโปรเซสต้องรอคิว เครื่องจะรู้สึกช้า ส่วนการเปรียบเทียบ 3 ค่าบอกแนวโน้ม

::load-gauge
::

ด้านล่างเป็นรายการโปรเซสเรียงตามการใช้ CPU คอลัมน์ `%CPU`, `%MEM` ชี้ตัวการ กด `q` เพื่อออก (`top` เป็นโปรแกรมที่รันต่อเนื่อง ไม่ออกเอง) ข้อสังเกตที่เสริม: `htop` เป็นเวอร์ชันอ่านง่ายกว่า แต่ไม่ได้ติดตั้งมาเสมอ

### 2.3 df และ du: ดิสก์เต็มเพราะอะไร

```bash
df -h            # พื้นที่ของแต่ละระบบไฟล์ (human-readable)
df -i            # จำนวน inode
du -sh /var/log/*   # ขนาดรวมของแต่ละโฟลเดอร์/ไฟล์ใน /var/log
```

`df` (disk free) ดูภาพรวมต่อพาร์ทิชัน ส่วน `du` (disk usage) ดูว่า **โฟลเดอร์ไหนกินที่** (`-s` สรุปรวม, `-h` อ่านง่าย) ลำดับปกติ: `df -h` หาพาร์ทิชันที่เต็ม แล้ว `du -sh` ไล่ลงไปหาโฟลเดอร์ต้นเหตุ

**กรณีลึกลับ: พื้นที่ว่างตั้ง 45 GB แต่ "No space left on device"** ระบบไฟล์ของลีนุกซ์ (เช่น ext4) เก็บข้อมูลไฟล์ 2 ส่วนแยกกัน คือเนื้อหาในบล็อกดิสก์ และ **inode** ซึ่งเป็นโครงสร้างเมทาดาทา (เจ้าของ สิทธิ์ เวลา ตำแหน่งบล็อก) **ทุกไฟล์และทุกโฟลเดอร์กิน 1 inode** และจำนวน inode ถูกกำหนดตายตัวตอนฟอร์แมต เมื่อมีไฟล์เล็กๆ เป็นล้าน (เช่น ไฟล์ session ของเว็บที่ไม่เคยล้าง) inode หมดก่อนที่พื้นที่จะเต็ม สร้างไฟล์ใหม่ไม่ได้ แม้ `df -h` จะเห็นว่าว่างมาก

ลองเอง: เพิ่มไฟล์เล็กๆ จำนวนมาก แล้วเปรียบเทียบ `df -h` กับ `df -i` จากนั้นสั่ง `touch`

## 3. อ่านล็อก: ระบบเล่าว่าเกิดอะไรขึ้น

บริการที่พังแทบทุกกรณี **บันทึกเหตุผลไว้ในล็อก** การรีสตาร์ตโดยไม่อ่านล็อก คือการทิ้งหลักฐาน

### 3.1 journalctl: บันทึกของ systemd

บนลีนุกซ์ที่ใช้ systemd ล็อกจากเคอร์เนลและบริการต่างๆ ไปรวมที่ **journal** (เก็บแบบไบนารี) อ่านผ่าน `journalctl`

```bash
journalctl -u nginx.service -n 20 --no-pager   # 20 บรรทัดล่าสุดของบริการ nginx
journalctl -u nginx.service -f                 # ติดตามแบบสด (กด Ctrl+C เพื่อออก)
journalctl -p err..warning -n 10               # เฉพาะระดับ warning ถึง error
```

| ตัวเลือก | ความหมาย |
|---|---|
| `-u <unit>` | เฉพาะบริการนั้น |
| `-n 20` | แสดง 20 บรรทัดสุดท้าย |
| `--no-pager` | พิมพ์ออกหน้าจอตรงๆ ไม่เปิดโปรแกรมแบ่งหน้า (เหมาะกับการคัดลอกลง ticket) |
| `-f` | follow ติดตามบรรทัดใหม่แบบเรียลไทม์ |
| `-p err..warning` | กรองตามระดับความรุนแรง (priority) |

> **เสริมจากผู้เขียน:** `journalctl -b` = เฉพาะการบูตรอบปัจจุบัน และ `journalctl -b -1` = รอบก่อนหน้า มีประโยชน์เมื่อเครื่องรีบูตเองแล้วอยากรู้ว่าก่อนหน้านั้นเกิดอะไร

### 3.2 ไฟล์ล็อกแบบข้อความใน /var/log

โปรแกรมและตัวระบบจำนวนมากยังเขียนล็อกเป็นไฟล์ข้อความ ชื่อไฟล์ต่างกันตามตระกูลของระบบ (Debian/Ubuntu เทียบ RHEL/CentOS)

| พาธ | เนื้อหา |
|---|---|
| `/var/log/syslog` หรือ `/var/log/messages` | เหตุการณ์ทั่วไปของระบบและบริการ |
| `/var/log/auth.log` หรือ `/var/log/secure` | การพิสูจน์ตัวตน การใช้ `sudo` การล็อกอิน SSH |
| `/var/log/dmesg` | ข้อความของเคอร์เนลช่วงบูตและเหตุการณ์ฮาร์ดแวร์ |

```bash
sudo tail -f /var/log/auth.log           # ดูบรรทัดใหม่ทันทีที่เขียน (Ctrl+C ออก)
sudo dmesg -T | grep -i error            # ข้อความเคอร์เนลที่มีคำว่า error พร้อมเวลาอ่านง่าย (-T)
```

`tail -f` เลื่อนไปท้ายไฟล์แล้ว "ตามดู" ไม่ปิด มีประโยชน์มากเมื่อให้ผู้ใช้ลองทำซ้ำอาการ แล้วดูว่าล็อกเกิดบรรทัดอะไรขึ้นพอดีขณะนั้น ส่วน `dmesg` ใช้ตรวจปัญหาฮาร์ดแวร์/ไดรเวอร์ เช่น ดิสก์ I/O error หรือ USB ไม่รู้จัก

## 4. ตรวจเครือข่ายและพอร์ต

### 4.1 ip addr show: การ์ดเครือข่ายพร้อมไหม

```bash
ip addr show
```

มองหา 2 อย่างในแต่ละอินเทอร์เฟซ (เช่น `eth0`, `ens33`, `wlan0`)

- แฟล็ก `<...UP,LOWER_UP>` และ `state UP` = การ์ดเปิดและมีลิงก์ทางกายภาพ (`LOWER_UP`) ถ้าไม่มี `LOWER_UP` มักเป็นสายหลุด/สวิตช์ดับ
- บรรทัด `inet` มี IPv4 ที่ถูกต้อง เช่น `192.168.1.45/24` (ตัวเลขหลัง `/` คือขนาด subnet) ถ้าขึ้นต้น `169.254` แปลว่าไม่ได้ IP จาก DHCP เช่นเดียวกับ APIPA ฝั่ง Windows ในบทก่อน

### 4.2 ss: พอร์ตไหนเปิดฟังอยู่ ใครเปิด

บริการที่ "รันอยู่" แต่ติดต่อไม่ได้ มักเกิดจากไม่ได้เปิดพอร์ตฟัง หรือมีโปรแกรมอื่นแย่งพอร์ตไปแล้ว `ss` (socket statistics) แสดง socket ของเครื่อง

```bash
sudo ss -tulpn
```

| ตัวเลือก | ความหมาย |
|---|---|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | เฉพาะที่กำลัง **listening** (รอรับการเชื่อมต่อ) |
| `-p` | แสดงโปรเซสเจ้าของ socket (ต้อง `sudo` จึงเห็นของผู้ใช้อื่น) |
| `-n` | แสดงตัวเลข ไม่แปลงเป็นชื่อ (เร็วกว่าและไม่ติด DNS) |

จำง่ายๆ ว่า **t-u-l-p-n** ใช้เป็นชุดเดียวกันเสมอ

## มุมมองด้าน Security

- **ล็อกคือหลักฐานและเป้าหมายของผู้โจมตี:** `auth.log`/`secure` มีรายการล็อกอินล้มเหลวซ้ำๆ (brute force) และการใช้ `sudo` ผู้โจมตีที่ได้สิทธิ์สูงมักลบหรือแก้ล็อก จึงควรส่งล็อกไปเก็บที่เซิร์ฟเวอร์กลางและรักษาสิทธิ์ของ `/var/log`
- **`ss -tulpn` คือการสำรวจพื้นที่โจมตี (attack surface):** พอร์ตที่ฟังที่ `0.0.0.0` คือเปิดให้เครือข่ายเข้าถึง ถ้าเห็นพอร์ตและโปรเซสที่ไม่รู้จัก (เช่น shell ฟังพอร์ตแปลกๆ) ถือเป็นสัญญาณอันตราย ให้ escalate และเก็บหลักฐานก่อนปิดทันที
- **อย่า `kill -9` โปรเซสที่น่าสงสัยทันที:** ถ้าสงสัยเป็นมัลแวร์ ให้บันทึก PID พาธไฟล์ (`ls -l /proc/<PID>/exe`) และเวลา แล้วแจ้งทีม Security ตามขั้นตอน เพราะการฆ่าทิ้งอาจทำลายหลักฐานในหน่วยความจำ
- **`sudo` เท่าที่จำเป็น:** คำสั่งอ่านอย่าง `free`, `df`, `ps` ไม่ต้องใช้ `sudo` ลดความเสี่ยงจากการพิมพ์ผิด และการใช้ `sudo` ทุกครั้งถูกบันทึกลงล็อก
- **ผลลัพธ์ที่คัดลอกลง ticket/แชต:** ผลของ `ip addr`, `ss`, และล็อกอาจมี IP ภายใน ชื่อผู้ใช้ และชื่อบริการ ปิดข้อมูลที่ไม่จำเป็นก่อนส่งต่อ
- **ดิสก์/inode เต็มอาจเป็นการโจมตี:** ไฟล์ล็อกที่โตผิดปกติหรือไฟล์ขยะนับแสนในเวลาสั้นๆ อาจเป็นการโจมตีแบบทำให้ล่ม (DoS) ควรดูต้นเหตุ ไม่ใช่แค่ลบไฟล์

| "เว็บเข้าไม่ได้" | `systemctl status nginx` | `inactive/failed` → อ่านล็อกด้วย `journalctl -u nginx` ก่อนสั่ง `start` ถ้าเป็นแค่หยุด `start` แล้ว `enable` ถ้าไม่ตั้งให้เปิดตอนบูต |

| โปรแกรมค้าง ปิดไม่ลง | `pgrep <ชื่อ>` หรือ `ps aux` เพื่อหา PID | `kill <PID>` ก่อน รอแล้วตรวจ ถ้ายังไม่ออกจริงจึง `kill -9` และแจ้งผู้ใช้เรื่องข้อมูลที่ยังไม่เซฟ |
| เขียนไฟล์ไม่ได้ "No space left on device" แต่ `df -h` ยังว่าง | `df -i` | `IUse%` ใกล้ 100% = inode หมด หาโฟลเดอร์ที่มีไฟล์จำนวนมาก (เช่น session/cache/spool) และล้างไฟล์เก่า |
| `df -h` เต็ม 100% | `du -sh /var/*` ไล่ลงลึกทีละชั้น | มักเป็นล็อกที่โตไม่หยุด ตั้งการหมุนล็อก (log rotation) และล้างไฟล์เก่าอย่างระวัง |
| ตรวจสอบการล็อกอินแปลกๆ ผ่าน SSH | `sudo tail -f /var/log/auth.log` | ดู IP ที่ล้มเหลวซ้ำๆ แล้ว escalate ให้ Security ดูเรื่องบล็อก IP หรือปิดรหัสผ่านแล้วใช้คีย์ |
| บริการรันอยู่ แต่ลูกค้าติดต่อไม่ได้ | `sudo ss -tulpn` | ดูว่าพอร์ตฟังอยู่ที่อินเทอร์เฟซใด (`127.0.0.1` คือรับเฉพาะในเครื่อง) และมีกำแพงไฟร์วอลล์ขวางหรือไม่ |
| เครือข่ายไม่ติดเลย | `ip addr show` | ไม่มี `LOWER_UP` = สายหรือสวิตช์ ขึ้น `169.254` = DHCP ไม่ตอบ |

| Signal | ซิกนัล / สัญญาณ | ข้อความสั้นที่เคอร์เนลหรือผู้ใช้ส่งถึงโปรเซส |
| SIGTERM (15) | ซิกเทิร์ม | ขอให้ปิดตัว โปรแกรมดักและเก็บกวาดได้ |
| SIGKILL (9) | ซิกคิล | เคอร์เนลยุติทันที ดักไม่ได้ |
| Buffer / Page cache | บัฟเฟอร์ / แคชหน้า | หน่วยความจำที่เก็บข้อมูลดิสก์/ที่รอเขียนลงดิสก์ |
| Swap | สว็อป / พื้นที่สลับ | พื้นที่ดิสก์ที่ใช้พักข้อมูลของ RAM เมื่อไม่พอ |
| Load average | โหลดเอเวอเรจ | ค่าเฉลี่ยจำนวนโปรเซสที่ใช้หรือรอ CPU (1/5/15 นาที) |
| Inode | ไอโหนด | โครงสร้างเมทาดาทาของไฟล์ 1 ไฟล์ในระบบไฟล์ |
| Journal / journalctl | เจอร์นัล / เจอร์นัลซีทีแอล | ที่เก็บล็อกของ systemd / คำสั่งอ่านล็อก |
| dmesg | ดีเมสก์ | ข้อความจากเคอร์เนล (ฮาร์ดแวร์/ไดรเวอร์) |
| Listening port | ลิสเซนนิงพอร์ต / พอร์ตที่เปิดฟัง | พอร์ตที่โปรแกรมรอรับการเชื่อมต่อ |
| ss | เอสเอส | คำสั่งดู socket และพอร์ต (ทดแทน netstat) |

## ตรวจความเข้าใจ

::reveal{question="free -h แสดง free = 310Mi แต่ available = 2.1Gi ผู้ใช้ตกใจว่า RAM เกือบหมด คุณจะอธิบายอย่างไร"}
ลีนุกซ์ใช้ RAM ที่เหลือไปทำแคชไฟล์ (buff/cache) เพื่อให้เข้าถึงข้อมูลดิสก์เร็วขึ้น และพร้อมคืนให้แอปทันทีเมื่อต้องการ ตัวเลขที่บอกว่ามี RAM ให้แอปใหม่ใช้ได้จริงคือ available (2.1 GB) ไม่ใช่ free จึงยังไม่ใช่วิกฤต แต่ควรดู swap ด้วย ถ้า swap ใกล้เต็มแสดงว่าเครื่องเริ่มเครียด
::

::reveal{question="df -h แสดงพาร์ทิชันรากว่าง 45 GB แต่ touch test.txt ขึ้น No space left on device สาเหตุที่น่าจะเป็นที่สุดคืออะไร และตรวจอย่างไร"}
inode หมด ทุกไฟล์ต้องใช้ 1 inode และจำนวน inode ถูกกำหนดตอนฟอร์แมต ไฟล์เล็กๆ จำนวนมากทำให้ inode หมดก่อนพื้นที่ ตรวจด้วย `df -i` (ดู IUse%) แล้วใช้ `du` หาโฟลเดอร์ที่มีไฟล์เยอะ ตัวเลือก "RAM เต็ม" ไม่ตรงเพราะข้อความเป็นเรื่องอุปกรณ์/ระบบไฟล์ ส่วน "read-only" หรือ "สิทธิ์" จะให้ข้อความอื่น (`Read-only file system` หรือ `Permission denied`)
::

::reveal{question="เครื่อง 4 แกน CPU มี load average 6.2, 4.1, 2.0 หมายความว่าอย่างไร"}
load 1 นาทีคือ 6.2 มากกว่า 4 แกน แปลว่ามีโปรเซสรอคิวใช้ CPU เฉลี่ยราว 2 ตัว เครื่องกำลังโอเวอร์โหลดและรู้สึกช้า และเพราะ 1 นาที > 5 นาที > 15 นาที แนวโน้มกำลังเพิ่มขึ้น ปัญหาเพิ่งเกิดและกำลังแย่ลง ควรเปิด `top` หาโปรเซสที่กิน CPU
::

::reveal{question="ทำไมควรลอง kill (SIGTERM) ก่อน kill -9 (SIGKILL)"}
SIGTERM โปรแกรมรับสัญญาณได้ จึงเขียนข้อมูลใน buffer ลงดิสก์ ปิดไฟล์และการเชื่อมต่อฐานข้อมูล แล้วออกอย่างเรียบร้อย SIGKILL เคอร์เนลยุติทันที โปรแกรมไม่มีโอกาสเก็บกวาด ข้อมูลที่ยังไม่ลงดิสก์หายและอาจทำให้ไฟล์เสียหาย จึงใช้เป็นทางเลือกสุดท้ายเมื่อโปรเซสไม่ตอบสนองจริงๆ
::

::reveal{question="systemctl start nginx กับ systemctl enable nginx ต่างกันอย่างไร ถ้าต้องการให้เว็บทำงานทั้งตอนนี้และหลังรีบูต ต้องทำอย่างไร"}
`start` เริ่มบริการตอนนี้ แต่ไม่ได้ตั้งให้เริ่มตอนบูต ส่วน `enable` ตั้งให้เริ่มอัตโนมัติตอนบูตครั้งต่อไป แต่ไม่ได้เริ่มตอนนี้ ต้องการทั้งสองอย่างให้สั่งทั้ง `sudo systemctl start nginx` และ `sudo systemctl enable nginx` (หรือ `systemctl enable --now nginx` ที่รวมสองขั้นในคำสั่งเดียว)
::

::reveal{question="PostgreSQL ขึ้น failed ล็อกบอก Address already in use พอร์ต 5432 คุณจะหาว่าอะไรถือพอร์ตนั้นอยู่อย่างไร"}
`sudo ss -tulpn | grep 5432` คอลัมน์ Process จะบอกชื่อโปรแกรมและ PID ที่ถือพอร์ต เช่น docker-proxy (คอนเทนเนอร์) แล้วจึงตัดสินใจ หยุดคอนเทนเนอร์หรือย้ายพอร์ต โดยตรวจก่อนว่าเป็นของใครและใช้ทำอะไร แทนการ kill -9 ไปทั่ว
::

::reveal{question="เปรียบเทียบ journalctl -u nginx -f กับ sudo tail -f /var/log/auth.log ต่างกันอย่างไร และใช้เมื่อใด"}
ทั้งสองติดตามบรรทัดใหม่แบบสด (`-f`) `journalctl -u nginx -f` อ่านจาก journal ของ systemd กรองเฉพาะบริการ nginx ส่วน `tail -f /var/log/auth.log` ตามไฟล์ข้อความล็อกการพิสูจน์ตัวตน (ล็อกอิน SSH, sudo) ใช้ journalctl กับบริการที่ล็อกเข้า journal และใช้ tail กับไฟล์ใต้ `/var/log` ที่แอปเขียนเอง ทั้งคู่กด Ctrl+C เพื่อออก
::

## แบบฝึกหัด

ใช้เครื่อง Linux ของตัวเอง (หรือ VM / WSL) คำสั่งที่เลือกเป็นโหมดอ่านอย่างเดียว ปลอดภัย

1. **บริการ:** รัน `systemctl status ssh` (หรือ `sshd`) อ่านค่า Loaded กับ Active แล้วลิสต์ `systemctl --failed`
2. **ทรัพยากร:** รัน `free -h` ระบุตัวเลข `available` แล้วเปิด `top` ดู load average เทียบกับจำนวนแกนที่ได้จาก `nproc`
3. **ดิสก์:** รัน `df -h` และ `df -i` ดูพาร์ทิชันราก แล้ว `du -sh /var/log/* | sort -h | tail` หาไฟล์ล็อกที่ใหญ่สุด
4. **ล็อก:** รัน `journalctl -p err -b -n 20 --no-pager` เลือกข้อความผิดพลาดหนึ่งบรรทัดแล้วอธิบายความหมาย
5. **เครือข่าย:** รัน `ip addr show` และ `sudo ss -tulpn` แล้วระบุพอร์ตที่ฟังอยู่ที่ `0.0.0.0` ว่ามีกี่พอร์ต และโปรแกรมอะไร
6. **ticket:** สมมติ nginx ไม่ขึ้นเพราะไฟล์ตั้งค่าผิด เขียน ticket 4 ส่วน (อาการ สาเหตุที่ตรวจพบ ขั้นแก้ ผลลัพธ์) โดยระบุคำสั่งที่ใช้เป็นหลักฐาน

::reveal{question="แนวคำตอบข้อ 5 (พอร์ตที่ฟังอยู่ที่ 0.0.0.0)"}
ดูคอลัมน์ Local Address ของผล `ss -tulpn` บรรทัดที่เป็น `0.0.0.0:<พอร์ต>` หรือ `[::]:<พอร์ต>` (IPv6) คือเปิดรับจากเครือข่ายภายนอก ส่วน `127.0.0.1:<พอร์ต>` รับเฉพาะในเครื่อง ตัวอย่างที่พบบ่อยคือ sshd ที่พอร์ต 22 ควรตรวจว่าทุกพอร์ตที่เปิดมีเหตุผลทางธุรกิจ พอร์ตที่ไม่จำเป็นควรปิดหรือจำกัดด้วยไฟร์วอลล์
::

## สรุป

- ถามระบบให้ครบ 4 ข้อ: บริการรันไหม ทรัพยากรพอไหม ล็อกบอกอะไร เครือข่ายคุยได้ไหม
- `systemctl status` ดูบริการ (Loaded/Active) `start` เริ่มตอนนี้ `enable` เริ่มตอนบูต ใช้ `ps aux | grep` หา PID แล้ว `kill` (SIGTERM) ก่อน `kill -9` (SIGKILL) เป็นทางเลือกสุดท้าย
- `free -h` ดู `available` ไม่ใช่ `free` เพราะ buff/cache คืนให้แอปได้ ดู swap ว่าเครียดไหม `top` ดู load เทียบจำนวนแกน
- `df -h` ดูพื้นที่ `df -i` ดู inode `du -sh` หาโฟลเดอร์ต้นเหตุ ไฟล์เล็กจำนวนมากทำให้ inode หมดก่อนพื้นที่
- `journalctl -u`, `/var/log` (`syslog`, `auth.log`), `tail -f`, `dmesg` คือที่อ่านเหตุผลที่บริการพัง
- `ip addr show` ตรวจ UP/LOWER_UP/inet และ `ss -tulpn` ตรวจพอร์ตที่ฟังและโปรเซสเจ้าของ
- ไล่ status → logs → port ก่อนแก้ แล้วบันทึกลง ticket และระวังเรื่องหลักฐาน/ข้อมูลที่เปิดเผย
