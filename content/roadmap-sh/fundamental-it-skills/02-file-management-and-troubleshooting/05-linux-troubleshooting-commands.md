## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่าเครื่องมืออย่าง `ps`, `top`, `free` ล้วน **อ่านสถานะจากเคอร์เนล** (ผ่าน `/proc`) จึงเชื่อถือได้ว่าตรงกับที่เคอร์เนลรู้
2. อธิบายกลไกของ systemd: `start` เทียบ `enable`, สถานะ `inactive/failed`, รหัสออก, และเหตุที่บริการวนรีสตาร์ตแล้วถูกหยุด (start limit)
3. แยกสัญญาณ SIGTERM / SIGKILL ในระดับเคอร์เนล รู้ว่า `kill -9` ล้มเหลวได้เมื่อไร (สถานะ D, zombie) และอ่านรหัสออก 143 / 137
4. อ่าน `free -h` ให้ถูก อธิบาย page cache, swap, OOM killer และคำนวณจาก load average (ค่าเฉลี่ยถ่วงน้ำหนักแบบเอ็กซ์โปเนนเชียล) เทียบจำนวนแกน CPU
5. อธิบายว่าทำไมดิสก์ "ว่าง" แต่เขียนไม่ได้ (inode หมด) พร้อมคำนวณจำนวน inode และแยกจากกรณีไฟล์ถูกลบแต่ยังเปิดค้าง
6. เลือกอ่านล็อกให้ถูกที่ (`journalctl`, `/var/log`, `dmesg`) และรู้ลำดับความรุนแรง
7. อ่าน `ip addr`, `ss -tulpn` และแยก **connection refused / timeout / bind error** ด้วยกลไกของ TCP และการ bind
8. ไล่วิเคราะห์บริการพัง (status → logs → port) และแมปคำสั่งกับเทคนิคที่ผู้โจมตีใช้

## เปรียบเทียบกับชีวิตจริง

นึกถึง **แพทย์ที่ตรวจคนไข้ตามขั้นตอน** ก่อนสั่งยา

| แพทย์ | คำสั่ง Linux |
|---|---|
| ดูว่าหัวใจเต้นอยู่ไหม | `systemctl status` (บริการยังทำงานไหม) |
| วัดชีพจรและความดัน | `top`, `free`, `df` (ทรัพยากรตึงตรงไหน) |
| เปิดดูประวัติการรักษาและบันทึกพยาบาล | `journalctl`, `/var/log` (เหตุการณ์ที่ผ่านมา) |
| ตรวจว่าหูได้ยินและพูดได้ไหม | `ip`, `ss` (เครือข่ายและพอร์ต) |
| ยาแรง (ผลข้างเคียงสูง) ใช้เมื่อวิธีเบาไม่ได้ผล | `kill -9` |

## ภาพรวม

เมื่อเว็บเซิร์ฟเวอร์ไม่ตอบ ผู้ใช้เขียนไฟล์ในโฮมไม่ได้ หรืองานเบื้องหลังทำให้เทอร์มินัลค้าง การเดาไม่ช่วย ต้นฉบับจัดคำสั่งตาม 4 คำถามข้างบน บทนี้ไล่ตามนั้น แต่เพิ่ม **กลไกเบื้องหลัง** ว่าทำไมคำสั่งแต่ละตัวให้ผลอย่างที่เห็น และเมื่อใดมันหลอกเรา ปิดด้วยกรณีบริการที่พังจริง คำสั่งส่วนใหญ่ **อ่านอย่างเดียว** ปลอดภัยที่จะลองกับเครื่อง Linux ของตัวเอง ส่วนที่แก้ไขสถานะ (`start`, `kill`) จะระบุไว้

> **ก่อนเริ่ม:** คำสั่งที่เปลี่ยนสถานะระบบหรืออ่านล็อกของระบบมักต้องขึ้นต้นด้วย `sudo` (ทำเป็นผู้ดูแล) ส่วนการดูข้อมูลทั่วไปเช่น `free`, `df` ใช้ผู้ใช้ธรรมดาได้

## 0. หลักคิด: เคอร์เนลเก็บสถานะ คำสั่งเป็นแค่ตัวอ่าน

ปัญหาของการแก้ปัญหาบนเซิร์ฟเวอร์คือ **เราไม่เห็นข้างในเครื่อง** เคอร์เนล Linux แก้ด้วยการเปิดสถานะภายในให้เป็น "ไฟล์เสมือน" ใต้ `/proc` (โปรเซสและระบบ) และ `/sys` (อุปกรณ์) ไฟล์เหล่านี้ไม่ได้อยู่บนดิสก์ ทุกครั้งที่อ่าน เคอร์เนลสร้างข้อความขึ้นสดๆ จากโครงสร้างข้อมูลจริง

| คำสั่ง | อ่านจาก |
|---|---|
| `ps`, `top` | `/proc/<PID>/stat`, `/proc/<PID>/status` ของทุกโปรเซส |
| `free` | `/proc/meminfo` |
| `uptime`, load ใน `top` | `/proc/loadavg` |
| `ss` | ตาราง socket ของเคอร์เนล (ผ่าน netlink) |

สองข้อสรุปที่มีประโยชน์

1. **ถ้าคำสั่งทั้งหมดอ่านจากแหล่งเดียวกัน ผลต้องสอดคล้องกัน** ถ้า `ps` กับ `top` เห็นไม่ตรงกัน มักเป็นเพราะเวลาที่อ่านต่างกัน ไม่ใช่เครื่องมือผิด
2. **เครื่องมือเชื่อถือเคอร์เนล แต่เคอร์เนลที่ถูกยึด (rootkit) โกหกได้** ถ้าสงสัยว่าเครื่องถูกบุกรุก อย่าเชื่อ `ps` ของเครื่องนั้นเพียงอย่างเดียว

**ข้อจำกัดของแบบจำลองนี้:** ค่าเหล่านี้คือ "ภาพถ่าย ณ ขณะอ่าน" และบางค่าเป็นค่าประมาณที่เคอร์เนลคำนวณ (เช่น `available` ใน `free`, load average) ไม่ใช่การวัดตรงๆ ปัญหาเป็นๆ หายๆ ต้องเฝ้าดูซ้ำ (เช่น `top` แบบสด, `journalctl -f`) ไม่ใช่รันครั้งเดียว

## 1. ตรวจบริการและโปรเซส

### 1.1 systemctl: คุมบริการของ systemd

ปัญหา: บริการ (เว็บเซิร์ฟเวอร์ ฐานข้อมูล) ต้องเปิดตามลำดับที่ถูกต้องตอนบูต ต้องถูกเฝ้า และต้องเปิดใหม่เมื่อล้ม ลีนุกซ์ส่วนใหญ่ปัจจุบันให้ **systemd** ทำหน้าที่นี้ มันคือ init system คือ **โปรเซสแรก (PID 1)** ที่เคอร์เนลเรียก และเปิดบริการอื่นทั้งหมดเป็นลูก `systemctl` คือเครื่องมือส่งคำสั่งไปคุยกับ systemd

systemd อ่าน **unit file** (เช่น `/lib/systemd/system/nginx.service`) ซึ่งบอกว่า `ExecStart=` คืออะไร ต้องเริ่มหลังบริการใด และจะ `Restart=` เมื่อใด

กดดูลำดับ `systemctl start nginx` ทีละขั้น และสิ่งที่เกิดเมื่อล้ม

```bash
systemctl status nginx
```

ผลลัพธ์ตัวอย่างเมื่อบริการหยุดอยู่ (ค่าเป็นตัวอย่าง)

```text
○ nginx.service - A high performance web server and a reverse proxy server
     Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
     Active: inactive (dead) since Wed 2026-03-25 14:10:02 UTC; 2m 15s ago
   Main PID: 1205 (code=exited, status=0/SUCCESS)
```

อ่านทีละบรรทัด

| ส่วน | ความหมาย |
|---|---|
| **Loaded** | systemd เจอ unit file ไหม และ `enabled` = จะเปิดเองตอนบูต, `disabled` = ไม่เปิดเอง |
| **Active** | `active (running)` ทำงานอยู่, `inactive (dead)` หยุดและไม่ใช่ความผิดพลาด, `failed` ออกด้วยรหัสผิดพลาด/ถูกสัญญาณฆ่า/เริ่มไม่สำเร็จ |
| **Main PID / code** | PID ของโปรเซสหลัก และ `status=0/SUCCESS` จบปกติ ส่วน `status=1/FAILURE` หรือ `code=killed, signal=KILL` แปลว่าผิดพลาดหรือถูกฆ่า |

**ความต่างที่ช่วยวินิจฉัย:** `inactive (dead)` + `status=0` = ถูกหยุดโดยเจตนา (หรือจบงานเอง) ไม่ต้องหาบั๊ก ส่วน `failed` = มีสาเหตุที่ต้องอ่านล็อก และ `code=killed, signal=KILL` มักชี้ไปที่ OOM killer (หัวข้อ 2.1)

**start กับ enable ไม่เหมือนกัน** `start` เปิดตอนนี้ (หายหลังรีบูต ถ้าไม่ได้ `enable`) ส่วน `enable` ตั้งให้เปิดอัตโนมัติตอนบูตครั้งต่อไป (แต่ไม่ได้เปิดตอนนี้) ภายใน `enable` ทำแค่ **สร้างลิงก์สัญลักษณ์ (symlink)** ไปยัง unit file ในโฟลเดอร์ `.wants` ของ target ที่ใช้ตอนบูต (เช่น `/etc/systemd/system/multi-user.target.wants/`) ตอนบูต systemd เริ่ม target นั้นและเปิดทุกบริการที่ลิงก์อยู่ ไม่มีโปรแกรมใดทำงานเพิ่ม จึงเข้าใจได้ว่าทำไม `enable` ไม่เริ่มบริการเอง

::compare-cards{:items='[{"title":"systemctl start nginx","subtitle":"ตอนนี้","points":["สั่งให้บริการเริ่มทำงานทันที","ถ้ารีบูต แล้วไม่เคย enable บริการจะไม่กลับมาเอง","ใช้หลังพบว่าบริการหยุดอยู่"]},{"title":"systemctl enable nginx","subtitle":"ครั้งหน้า (ตอนบูต)","points":["สร้าง symlink ให้ systemd เปิดบริการเองทุกครั้งที่บูต","ไม่ได้ทำให้บริการเริ่มทำงานตอนนี้","ใช้เพื่อไม่ให้ปัญหาเดิมเกิดซ้ำหลังรีบูต"]}]'}
::

```bash
sudo systemctl start nginx
sudo systemctl enable nginx
```

> **เสริมจากผู้เขียน:** `sudo systemctl enable --now nginx` ทำสองอย่างในคำสั่งเดียว, `restart` = หยุดแล้วเริ่มใหม่, `reload` = ให้บริการอ่านค่าตั้งใหม่โดยไม่ตัดการเชื่อมต่อ (ถ้าบริการรองรับ), `systemctl is-active` / `is-enabled` ให้คำตอบสั้นสำหรับสคริปต์ และ `systemctl --failed` ลิสต์บริการที่พังทั้งหมด ใช้เป็นขั้นแรกเมื่อเปิดเครื่องที่ไม่คุ้นเคย

### 1.2 ps: โปรเซสและสถานะของมัน

**โปรเซส (process)** คือโปรแกรมที่กำลังทำงาน เคอร์เนลให้หมายเลข **PID** `ps aux` แสดงโปรเซสของทุกผู้ใช้ (`a` ทุกผู้ใช้, `u` รูปแบบมีเจ้าของและ %CPU/%MEM, `x` รวมโปรเซสที่ไม่มีเทอร์มินัล) ผลลัพธ์ยาว จึงส่งต่อด้วยท่อ (`|`) ให้ `grep` กรอง

```bash
ps aux | grep nginx
```

บรรทัดของ `grep` เองโผล่ในผลลัพธ์ด้วย ให้เมินบรรทัดนั้น หรือใช้ `pgrep nginx` ที่ให้เฉพาะ PID

คอลัมน์ **STAT** บอกสถานะของโปรเซส และเป็นเบาะแสวินิจฉัยที่สำคัญ

| STAT | ความหมาย | วินิจฉัย |
|---|---|---|
| `R` | กำลังรัน/รอคิว CPU | กิน CPU จริง นับใน load average |
| `S` | หลับรอเหตุการณ์ (ขัดจังหวะได้) | ปกติของโปรเซสที่ว่างงาน |
| `D` | หลับรอ I/O ที่ **ขัดจังหวะไม่ได้** (ดิสก์/NFS) | ติดอยู่กับอุปกรณ์ ตัวนี้ `kill -9` ไม่ได้ผลจนกว่า I/O จะกลับมา และ **นับใน load average** |
| `Z` | zombie: จบแล้วแต่พ่อแม่ยังไม่อ่านรหัสออก (wait) | ไม่กินทรัพยากรนอกจากช่องในตาราง PID `kill` ไม่ช่วย ต้องแก้ที่พ่อแม่ |
| `T` | ถูกหยุดชั่วคราว (เช่น Ctrl+Z) | สั่ง `kill -CONT` หรือ `fg` เพื่อไปต่อ |

ดูแต่ละโปรเซสลึกลงไปได้ที่ `/proc/<PID>/` เช่น `ls -l /proc/<PID>/exe` ชี้ไปยังไฟล์โปรแกรมจริงที่ถูกรัน (ใช้ตรวจโปรเซสที่น่าสงสัย)

### 1.3 kill: ส่งสัญญาณถึงโปรเซส

ชื่อ `kill` ทำให้เข้าใจผิด มันคือการ **ขอให้เคอร์เนลส่งสัญญาณ (signal)** ไปยังโปรเซส สัญญาณคือหมายเลขสั้นๆ ที่เคอร์เนลวางไว้ในโปรเซสเป้าหมาย พอโปรเซสถูกจัดตารางครั้งถัดไป เคอร์เนลจะทำตามการตั้งค่าของโปรเซสสำหรับสัญญาณนั้น

```bash
kill 1841        # ส่ง SIGTERM (15)  = ขอให้ปิดตัวอย่างเรียบร้อย
kill -9 1841     # ส่ง SIGKILL (9)   = เคอร์เนลยุติทันที
```

| สัญญาณ | เลข | ดักได้ไหม | ใช้เมื่อ |
|---|---|---|---|
| SIGINT | 2 | ได้ | Ctrl+C |
| SIGTERM | 15 | ได้ | ขอให้ปิดตัว (ค่าเริ่มต้นของ `kill`) |
| SIGHUP | 1 | ได้ | สั่งให้อ่านค่าตั้งใหม่ (หลายบริการใช้) |
| SIGKILL | 9 | **ไม่ได้ ไม่ถูกเพิกเฉยได้** | ตัดจบ เป็นทางเลือกสุดท้าย |

- **SIGTERM (15)** โปรแกรมลงทะเบียน handler ได้ จึงเขียน buffer ลงดิสก์ ปิดไฟล์ ปิดการเชื่อมต่อฐานข้อมูล แล้วออกเอง ถ้าไม่ลงทะเบียน การกระทำเริ่มต้นคือยุติโปรเซส
- **SIGKILL (9)** เคอร์เนลยุติโปรเซสเอง โปรแกรมไม่ได้รันโค้ดใดๆ ข้อมูลที่ยังอยู่ใน RAM ไม่ถูกเขียนลงดิสก์

**รหัสออกเปิดเผยว่าตายอย่างไร:** เมื่อโปรเซสถูกสัญญาณฆ่า เชลล์รายงานรหัสออก = 128 + หมายเลขสัญญาณ ดังนั้น `143` (128+15) = ถูก SIGTERM และ `137` (128+9) = ถูก SIGKILL เจอ `137` ในล็อกคอนเทนเนอร์หรือบริการ ให้นึกถึง OOM killer ก่อน

## 2. ตรวจทรัพยากร: หน่วยความจำ โหลด และดิสก์

เครื่องช้าหรือบริการล้มบ่อย มักเกิดจากทรัพยากรหมดใน 3 จุด คือ **หน่วยความจำ (RAM)**, **ตัวประมวลผล (CPU)** และ **ดิสก์**

### 2.1 free: อ่านหน่วยความจำให้ถูก

```bash
free -h
```

```text
               total        used        free      shared  buff/cache   available
Mem:           7.7Gi       5.2Gi       310Mi       128Mi       2.2Gi       2.1Gi
Swap:          2.0Gi       1.8Gi       200Mi
```

คนใหม่มักตกใจที่ `free` เหลือแค่ 310 MB แต่ตัวที่ต้องดูคือ **`available`** เหตุผลคือ RAM ที่ว่างเปล่าคือ RAM ที่เสียเปล่า ลีนุกซ์จึงเอาส่วนที่เหลือไปทำ **page cache** เก็บข้อมูลดิสก์ที่เพิ่งอ่านไว้ให้เปิดซ้ำเร็วขึ้น เมื่อแอปต้องการ RAM เคอร์เนล **ทิ้งแคชส่วนที่ไม่ได้แก้ไขคืนให้ทันที** (ไม่ต้องเขียนอะไรลงดิสก์) available จึงประมาณ free + แคชที่คืนได้ ไม่ใช่ผลบวกตรงๆ (ในตัวอย่าง 310Mi + 2.2Gi ≈ 2.4Gi แต่ available = 2.1Gi เพราะแคชบางส่วนคืนไม่ได้ เช่น ส่วนที่ใช้ร่วม ตัวเลขเป็นค่าประมาณจากเคอร์เนล)

**ลำดับเมื่อ RAM ตึง** (เรียงจากถูกไปแพง)

1. ทิ้ง page cache ที่สะอาด (เร็ว ไม่มีต้นทุน)
2. เขียน page ที่สกปรก (dirty) ลงดิสก์ก่อนแล้วทิ้ง (ใช้ I/O)
3. ย้ายหน้าความจำของโปรแกรมที่ไม่ค่อยใช้ไป **swap** บนดิสก์ (ช้ามาก)
4. ถ้ายังไม่พอ **OOM killer** เลือกโปรเซสที่มีคะแนนสูงสุด (`oom_score`) แล้วส่ง **SIGKILL**

**Swap** ช้ากว่า RAM ราว 1,000 เท่า ถ้าเทียบหน่วงเวลา RAM ราว 100 ns กับ SSD ราว 100 µs (ค่าประมาณตามบทฮาร์ดแวร์) เครื่องที่ต้อง swap หนักจะ "ช้าจนแทบค้าง" เรียกว่า **thrashing** ในตัวอย่าง swap ใช้ 1.8 จาก 2.0 Gi = **90%** เป็นสัญญาณว่าเครื่องกำลังเครียด

### 2.2 top และ load average

```bash
top
```

`top` รีเฟรชทุกไม่กี่วินาที แถวบนมี **load average** 3 ค่า คือค่าเฉลี่ยใน 1, 5, 15 นาที ซึ่งนับ "จำนวนโปรเซสเฉลี่ยที่กำลังใช้ CPU หรือพร้อมรัน (R) และบน Linux รวมโปรเซสที่รอ I/O แบบ D ด้วย" เกณฑ์ตัดสินคือเทียบกับ **จำนวนแกน CPU** (`nproc`) เช่น เครื่อง 4 แกน load 4.0 = เต็ม ถ้าเกินนั้น มีโปรเซสต้องรอคิว

**กลไกคำนวณ (เข้าใจง่าย):** ทุก 5 วินาที เคอร์เนลนับจำนวนงานที่รัน/รอ แล้วอัปเดตค่าเฉลี่ยแบบ **เอ็กซ์โปเนนเชียล** ค่าเก่าถูกคูณตัวถ่วง e^(−5/60) สำหรับ 1 นาที (e^(−5/300) สำหรับ 5 นาที และ e^(−5/900) สำหรับ 15 นาที) แล้วบวกค่าใหม่ เป็นผลให้ตัวเลข 1 นาทีไวต่อการเปลี่ยน ตัว 15 นาทีเฉื่อย

::load-gauge
::

#### โจทย์คำนวณ: อ่านแนวโน้มจาก 3 ค่า

สมมติเครื่อง 4 แกนว่างอยู่นาน แล้วมีงาน CPU-bound 4 งานเริ่มพร้อมกัน หลังผ่านไป 60 วินาที ค่า load จะไต่ตามสูตร 4 × (1 − e^(−t/τ)) (คำนวณด้วย node)

| ค่าเฉลี่ย | τ (วินาที) | หลัง 60 วินาที | สัดส่วนที่ไปถึง |
|---|---|---|---|
| 1 นาที | 60 | 2.53 | 63.2% |
| 5 นาที | 300 | 0.72 | 18.1% |
| 15 นาที | 900 | 0.26 | 6.4% |

กลับกัน ถ้างานหยุดทันทีที่ load = 4.0 หลัง 60 วินาที ค่าจะลดเป็น 1.47 / 3.27 / 3.74 ตามลำดับ

::reveal{question="เครื่อง 4 แกน CPU มี load average 6.2, 4.1, 2.0 หมายความว่าอย่างไร และต่างจากกรณี 2.0, 4.1, 6.2 อย่างไร"}
load 1 นาทีคือ 6.2 มากกว่า 4 แกน (6.2 ÷ 4 = 1.55 เท่า) แปลว่ามีโปรเซสรอคิว CPU เฉลี่ยราว 2.2 ตัว เครื่องกำลังโอเวอร์โหลดและรู้สึกช้า และเพราะ 1 นาที > 5 นาที > 15 นาที ค่าล่าสุดสูงกว่าค่าเก่า ปัญหาเพิ่งเกิดและกำลังแย่ลง ส่วน 2.0, 4.1, 6.2 คือตรงข้าม ช่วงที่แล้วหนัก แต่ตอนนี้กำลังคลายตัวแล้ว ควรเปิด `top` ดูโปรเซสกิน CPU ตอนนี้ ไม่ใช่ตามข้อมูลเก่า
::

**load สูงไม่ได้แปลว่า CPU เต็ม:** เพราะโปรเซสสถานะ `D` (รอดิสก์/NFS) ก็ถูกนับ ถ้า `top` แสดง load สูงแต่ `%us`+`%sy` ต่ำและ `%wa` (iowait) สูง ปัญหาคือ **I/O ไม่ใช่ CPU** ให้ไปตรวจดิสก์/เครือข่ายดิสก์ ไม่ใช่ฆ่าโปรเซส

### 2.3 df และ du: ดิสก์เต็มเพราะอะไร

```bash
df -h            # พื้นที่ของแต่ละระบบไฟล์ (human-readable)
df -i            # จำนวน inode
du -sh /var/log/*   # ขนาดรวมของแต่ละโฟลเดอร์/ไฟล์ใน /var/log
```

`df` (disk free) ดูภาพรวมต่อระบบไฟล์ ส่วน `du` (disk usage) ดูว่า **โฟลเดอร์ไหนกินที่** (`-s` สรุปรวม, `-h` อ่านง่าย) ลำดับปกติ: `df -h` หาระบบไฟล์ที่เต็ม แล้ว `du -sh` ไล่ลงไปหาโฟลเดอร์ต้นเหตุ

**กรณีลึกลับ: พื้นที่ว่างตั้ง 45 GB แต่ "No space left on device"** ระบบไฟล์ของลีนุกซ์ (เช่น ext4) เก็บข้อมูลไฟล์ 2 ส่วนแยกกัน คือเนื้อหาในบล็อกดิสก์ และ **inode** ซึ่งเป็นโครงสร้างเมทาดาทา (เจ้าของ สิทธิ์ เวลา ตำแหน่งบล็อก) **ทุกไฟล์และทุกโฟลเดอร์กิน 1 inode** และจำนวน inode ถูกกำหนดตายตัว **ตอนฟอร์แมต** เมื่อมีไฟล์เล็กๆ เป็นล้าน (เช่น ไฟล์ session ของเว็บที่ไม่เคยล้าง) inode หมดก่อนที่พื้นที่จะเต็ม สร้างไฟล์ใหม่ไม่ได้ แม้ `df -h` จะเห็นว่าว่างมาก

#### โจทย์คำนวณ: ทำไมต้องพันล้านไบต์ก็ inode หมด

ext4 ค่าเริ่มต้นทั่วไปตั้งอัตราส่วน 1 inode ต่อ 16 KiB ของพื้นที่ (ค่าตามไฟล์ตั้งค่า `mke2fs.conf` ต่างกันตามดิสโทรและขนาด) สำหรับระบบไฟล์ 100 GiB

- จำนวน inode = 100 GiB ÷ 16 KiB = 100 × 2³⁰ ÷ 16,384 = **6,553,600** (ตรงกับตัวอย่าง `df -i` ด้านล่าง)
- inode ขนาด 256 ไบต์ ตารางทั้งหมดกิน 6,553,600 × 256 = **1.5625 GiB** ที่กันไว้ตั้งแต่ฟอร์แมต
- ถ้าไฟล์เล็กทุกไฟล์ (ขนาดจริง 1 KB) ยังกินอย่างน้อย **1 บล็อก = 4 KiB** (ขนาดบล็อกทั่วไป) ไฟล์ 6,553,600 ไฟล์จึงกิน 6,553,600 × 4 KiB = **25 GiB** ของพื้นที่ 100 GiB และ inode หมด ในขณะที่พื้นที่ว่างยังมากกว่า 70%

บทเรียน: ขนาดไฟล์เฉลี่ยที่ **เล็กกว่า 16 KiB** ในปริมาณมาก ทำให้ inode หมดก่อนพื้นที่เสมอ วิธีป้องกันคือจำกัด/ล้างโฟลเดอร์ที่ขยะสะสม หรือฟอร์แมตด้วยอัตราส่วน inode ที่เหมาะกับงาน (XFS และ Btrfs ปรับจำนวน inode แบบไดนามิก ปัญหานี้แทบไม่เกิด)

ลองเอง: เพิ่มไฟล์เล็กๆ จำนวนมาก แล้วเปรียบเทียบ `df -h` กับ `df -i` จากนั้นสั่ง `touch`

**อาการเหมือนกัน สาเหตุคนละอย่าง:** ข้อความ "No space left on device" (ENOSPC) เกิดได้จาก **บล็อกเต็ม** หรือ **inode หมด** ส่วน `Read-only file system` (EROFS) คือระบบไฟล์ถูก mount เป็นอ่านอย่างเดียว (มักเพราะเจอ error แล้วตัวเองสลับโหมด) และ `Permission denied` (EACCES) คือเรื่องสิทธิ์ ให้ดูข้อความตรงตัวเสมอ

**ส่วนที่ df กับ du ไม่ตรงกัน:** ถ้า `df -h` บอกเต็ม 100% แต่ `du` รวมแล้วน้อยกว่ามาก สาเหตุที่พบบ่อยคือ **ไฟล์ถูกลบแล้วแต่ยังมีโปรเซสเปิดค้าง** (เช่น ล็อกขนาดใหญ่ที่ถูก `rm` โดยที่บริการยังเขียนอยู่) บล็อกจะคืนก็ต่อเมื่อโปรเซสปิดไฟล์ ตรวจด้วย `sudo lsof +L1` (ไฟล์ที่ link count น้อยกว่า 1) แล้วรีสตาร์ตบริการนั้น และอย่าลืมว่า ext4 สำรองพื้นที่ราว 5% ไว้ให้ root โดยปริยาย (ค่าเริ่มต้นทั่วไป) ทำให้ผู้ใช้ทั่วไปเห็นเต็มก่อน `df` จะแสดง 100% ของผลรวม

## 3. อ่านล็อก: ระบบเล่าว่าเกิดอะไรขึ้น

บริการที่พังแทบทุกกรณี **บันทึกเหตุผลไว้ในล็อก** การรีสตาร์ตโดยไม่อ่านล็อก คือการทิ้งหลักฐาน (และบางบริการล้างสถานะตอนเริ่มใหม่)

### 3.1 journalctl: บันทึกของ systemd

บนลีนุกซ์ที่ใช้ systemd ล็อกจากเคอร์เนลและบริการต่างๆ ไปรวมที่ **journal** (journald เก็บแบบไบนารี ค้นด้วย field ได้) อ่านผ่าน `journalctl`

```bash
journalctl -u nginx.service -n 20 --no-pager   # 20 บรรทัดล่าสุดของบริการ nginx
journalctl -u nginx.service -f                 # ติดตามแบบสด (กด Ctrl+C เพื่อออก)
journalctl -p err..warning -n 10               # เฉพาะระดับ warning ถึง error
```

| ตัวเลือก | ความหมาย |
|---|---|
| `-u <unit>` | เฉพาะบริการนั้น |
| `-n 20` | แสดง 20 บรรทัดสุดท้าย |
| `--no-pager` | พิมพ์ออกหน้าจอตรงๆ ไม่เปิดโปรแกรมแบ่งหน้า (เหมาะกับการคัดลอกลง ticket) |
| `-f` | follow ติดตามบรรทัดใหม่แบบเรียลไทม์ |
| `-p err..warning` | กรองตามระดับความรุนแรง (priority) |

**ระดับความรุนแรง (syslog priority):** 0 emerg, 1 alert, 2 crit, 3 err, 4 warning, 5 notice, 6 info, 7 debug การกรอง `-p err` แสดงตั้งแต่ระดับ err **และรุนแรงกว่า** (0–3) ส่วน `-p err..warning` แสดงเฉพาะช่วง 3–4

> **เสริมจากผู้เขียน:** `journalctl -b` = เฉพาะการบูตรอบปัจจุบัน และ `journalctl -b -1` = รอบก่อนหน้า มีประโยชน์เมื่อเครื่องรีบูตเองแล้วอยากรู้ว่าก่อนหน้านั้นเกิดอะไร **ข้อควรระวัง:** บางระบบเก็บ journal ไว้ใน RAM เท่านั้น (ไม่มีโฟลเดอร์ `/var/log/journal`) ล็อกก่อนรีบูตจึงหายไป ตรวจด้วย `journalctl --list-boots` และดูขนาดด้วย `journalctl --disk-usage`

### 3.2 ไฟล์ล็อกแบบข้อความใน /var/log

โปรแกรมและตัวระบบจำนวนมากยังเขียนล็อกเป็นไฟล์ข้อความ ชื่อไฟล์ต่างกันตามตระกูลของระบบ (Debian/Ubuntu เทียบ RHEL/CentOS)

| พาธ | เนื้อหา |
|---|---|
| `/var/log/syslog` หรือ `/var/log/messages` | เหตุการณ์ทั่วไปของระบบและบริการ |
| `/var/log/auth.log` หรือ `/var/log/secure` | การพิสูจน์ตัวตน การใช้ `sudo` การล็อกอิน SSH |
| `/var/log/dmesg` | ข้อความของเคอร์เนลช่วงบูตและเหตุการณ์ฮาร์ดแวร์ |

```bash
sudo tail -f /var/log/auth.log           # ดูบรรทัดใหม่ทันทีที่เขียน (Ctrl+C ออก)
sudo dmesg -T | grep -i error            # ข้อความเคอร์เนลที่มีคำว่า error พร้อมเวลาอ่านง่าย (-T)
```

`tail -f` เลื่อนไปท้ายไฟล์แล้ว "ตามดู" มีประโยชน์มากเมื่อให้ผู้ใช้ลองทำซ้ำอาการ แล้วดูว่าล็อกเกิดบรรทัดอะไรขึ้นพอดีขณะนั้น **กับดัก:** ล็อกถูกหมุนไฟล์ (logrotate) เป็นระยะ `tail -f` ติดตาม "ไฟล์เดิม" ที่ถูกเปลี่ยนชื่อไป จึงเงียบไปหลังหมุน ใช้ `tail -F` (ตัว F ใหญ่) เพื่อติดตามตามชื่อไฟล์ ส่วน `dmesg` อ่านจาก **ring buffer** ของเคอร์เนล (วนทับเมื่อเต็ม) ใช้ตรวจฮาร์ดแวร์/ไดรเวอร์ เช่น ดิสก์ I/O error, USB ไม่รู้จัก และข้อความ OOM killer

## 4. ตรวจเครือข่ายและพอร์ต

### 4.1 ip addr show: การ์ดเครือข่ายพร้อมไหม

```bash
ip addr show
```

มองหา 2 อย่างในแต่ละอินเทอร์เฟซ (เช่น `eth0`, `ens33`, `wlan0`)

- แฟล็ก `<...UP,LOWER_UP>` และ `state UP` = การ์ดเปิดและมีลิงก์ทางกายภาพ (`LOWER_UP`) ถ้ามี `UP` แต่ไม่มี `LOWER_UP` มักเป็นสายหลุด/สวิตช์ดับ (ผู้ดูแลเปิดการ์ดแล้วแต่ไม่เจอสัญญาณ)
- บรรทัด `inet` มี IPv4 ที่ถูกต้อง เช่น `192.168.1.45/24` (ตัวเลขหลัง `/` คือขนาด subnet) ถ้าขึ้นต้น `169.254` แปลว่าไม่ได้ IP จาก DHCP เช่นเดียวกับ APIPA ฝั่ง Windows ในบทก่อน

### 4.2 ss: พอร์ตไหนเปิดฟังอยู่ ใครเปิด

บริการที่ "รันอยู่" แต่ติดต่อไม่ได้ มักเกิดจากไม่ได้เปิดพอร์ตฟัง หรือมีโปรแกรมอื่นแย่งพอร์ตไปแล้ว `ss` (socket statistics) แสดง socket ของเครื่องจากตารางของเคอร์เนล

```bash
sudo ss -tulpn
```

| ตัวเลือก | ความหมาย |
|---|---|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | เฉพาะที่กำลัง **listening** (รอรับการเชื่อมต่อ) |
| `-p` | แสดงโปรเซสเจ้าของ socket (ต้อง `sudo` จึงเห็นของผู้ใช้อื่น) |
| `-n` | แสดงตัวเลข ไม่แปลงเป็นชื่อ (เร็วกว่าและไม่ติด DNS) |

จำง่ายๆ ว่า **t-u-l-p-n** ใช้เป็นชุดเดียวกันเสมอ

**กลไก bind ที่ต้องรู้:** โปรแกรมที่จะรับการเชื่อมต่อต้องเรียก `bind()` ผูก socket กับ **(ที่อยู่, พอร์ต)** แล้ว `listen()` ที่อยู่ที่ผูกกำหนดว่าใครเข้าถึงได้

| Local Address | ความหมาย |
|---|---|
| `0.0.0.0:80` | ฟังทุกอินเทอร์เฟซ IPv4 (เครือข่ายภายนอกเข้าถึงได้ถ้าไฟร์วอลล์ไม่กัน) |
| `[::]:80` | ฟังทุกอินเทอร์เฟซ IPv6 (หลายระบบรับ IPv4 ด้วย) |
| `127.0.0.1:5432` | ฟังเฉพาะในเครื่อง (loopback) เครื่องอื่นต่อไม่ได้ |
| `192.168.1.45:80` | ฟังเฉพาะบนที่อยู่นั้น |

และข้อผิดพลาดตอน bind มี 2 แบบที่แยกกัน: **EADDRINUSE** ("Address already in use") มีคนถือ (ที่อยู่, พอร์ต) นั้นอยู่แล้ว และ **EACCES** ("Permission denied") ผู้ใช้ธรรมดา bind พอร์ตต่ำกว่า 1024 ไม่ได้ (ต้อง root หรือมีสิทธิ์ `CAP_NET_BIND_SERVICE`) บริการที่ล้มตอนเริ่มจึงต้องอ่านข้อความให้ตรง

**refused กับ timeout ต่างกันที่ไหน** ส่วนฝั่งไคลเอนต์ สองอาการนี้ต่างกันเชิงกลไก และบอกว่าต้องไปดูที่ไหน

#### โจทย์คำนวณ: ไคลเอนต์เปิดการเชื่อมต่อไปปลายทางเดียวได้กี่ตัว

การเชื่อมต่อ TCP ถูกระบุด้วยสี่ค่า (IP ต้นทาง, พอร์ตต้นทาง, IP ปลายทาง, พอร์ตปลายทาง) เมื่อไคลเอนต์เชื่อมไปที่ปลายทางเดียวกัน (IP:พอร์ตเดียว) สามค่าคงที่ ต่างได้แค่ **พอร์ตต้นทาง** ซึ่งระบบเลือกจากช่วง ephemeral: ค่าเริ่มต้นของ Linux คือ 32768–60999 = **28,232 พอร์ต** (Windows ปัจจุบันใช้ 49152–65535 = 16,384 พอร์ต) เมื่อหมดช่วง การเชื่อมต่อใหม่ไปปลายทางนั้นล้มด้วย "Cannot assign requested address" นี่คือเหตุที่เซิร์ฟเวอร์ที่เชื่อมต่อออกไปหาฐานข้อมูลหรือ API เดียวกันถี่มากอาจชนเพดาน โดยเฉพาะเมื่อ socket ค้างสถานะ TIME_WAIT (ค่าเริ่มต้นราว 60 วินาที ตัวเลขทั้งหมดเป็นค่าเริ่มต้นทั่วไปที่ปรับได้)

::reveal{question="แอปเปิดการเชื่อมต่อใหม่ไปยัง API ภายนอก IP เดียว ด้วยอัตรา 600 ครั้ง/วินาที โดยปิดแล้ว socket ค้าง TIME_WAIT นาน 60 วินาที พอร์ต ephemeral ของ Linux ค่าเริ่มต้นจะหมดไหม และควรแก้อย่างไร"}
ต้องการพอร์ตพร้อมกัน = 600 × 60 = 36,000 พอร์ต มากกว่า 28,232 ที่ช่วงเริ่มต้นมี จึงหมดและเริ่มเจอข้อผิดพลาด ดูจำนวน TIME_WAIT ได้จาก `ss -s` ทางแก้ที่ตรงสาเหตุ: ใช้ connection pool/keep-alive ให้ใช้การเชื่อมต่อซ้ำ (ลดอัตราเปิดใหม่) หรือกระจายไปหลาย IP ปลายทาง ส่วนการขยายช่วงพอร์ต (`net.ipv4.ip_local_port_range`) ได้เพดานเพิ่มแต่เป็นแค่บรรเทา ค่าเป็นตัวอย่างเชิงตัวเลข
::

## 6. วินิจฉัยเชิงกลไก: อาการคล้ายกัน แต่ต้นเหตุต่างกัน

| สิ่งที่เห็น | แปลว่า | การทดสอบที่แยกสาเหตุ |
|---|---|---|
| บริการ `inactive (dead)`, `status=0/SUCCESS` | ถูกหยุดโดยเจตนา/จบงานเอง | อ่านล็อก `journalctl -u` หา `Stopping`/ผู้สั่ง (sudo) ถ้ามีคนหยุด ไม่ใช่บั๊ก |
| บริการ `failed`, `status=1/FAILURE` | โปรแกรมออกด้วยข้อผิดพลาดของตัวเอง | อ่านล็อก: พอร์ตซ้ำ (EADDRINUSE) ค่าตั้งผิด สิทธิ์ไฟล์ |
| `failed`, `code=killed, signal=KILL` (รหัสออก 137) | ถูกฆ่า ไม่ได้ล้มเอง มักเป็น OOM killer | `dmesg -T` หา `Out of memory`; ดู `free -h` และ swap |
| load สูง `%us` สูง | CPU-bound: มีโปรเซสกิน CPU | `top` เรียงตาม %CPU แล้วตรวจก่อน kill |
| load สูง แต่ CPU ว่าง `%wa` สูง | I/O-bound: โปรเซสสถานะ D รอดิสก์/NFS | `ps` หา STAT D; `dmesg` หา I/O error; ตรวจดิสก์/เครือข่ายดิสก์ |
| `ENOSPC` แต่ `df -h` ว่างเยอะ | inode หมด | `df -i`; `du --inodes` หาโฟลเดอร์ไฟล์เยอะ |
| `df -h` เต็ม แต่ `du` รวมน้อยกว่ามาก | ไฟล์ถูกลบแต่โปรเซสเปิดค้าง | `sudo lsof +L1`; รีสตาร์ตบริการเจ้าของไฟล์ |
| ไคลเอนต์ได้ `Connection refused` | ถึงเครื่องแล้วแต่ไม่มีบริการฟังที่ (ที่อยู่, พอร์ต) นั้น | `ss -tulpn` บนเซิร์ฟเวอร์: ไม่มีพอร์ต หรือฟังแค่ `127.0.0.1` |
| ไคลเอนต์ได้ `Connection timed out` | แพ็กเก็ตหายระหว่างทาง ไม่มีใครตอบ | ไฟร์วอลล์ (DROP), เส้นทาง, เซิร์ฟเวอร์ดับ ไม่ใช่เรื่องของ `ss` |
| บริการล้มวน แล้วหยุดลองเอง (`start-limit-hit`) | ล้มซ้ำเกินกำหนด systemd ตัดวงจร | อ่านล็อกหาสาเหตุ แก้ก่อน แล้ว `systemctl reset-failed` ค่อย start |

## มุมมองด้าน Security

เครื่องมือชุดนี้คือชุดเดียวกับที่ผู้โจมตีใช้ ตารางอ้างอิงเทคนิคใน MITRE ATT&CK เพื่อให้ค้นต่อได้

| เหตุการณ์/คำสั่ง | มุมผู้โจมตี | เทคนิค (ATT&CK) | การป้องกัน/ตรวจจับ |
|---|---|---|---|
| `ss -tulpn`, `ps aux` | สำรวจพอร์ต โปรเซส และบริการเพื่อหาเป้า | T1049 System Network Connections Discovery, T1057 Process Discovery | ลดสิทธิ์ผู้ใช้; `hidepid` บน `/proc`; ตรวจลำดับคำสั่งสำรวจรัวๆ |
| `auth.log` ล็อกอินล้มเหลวซ้ำ | เดารหัสผ่าน SSH | T1110 Brute Force | ใช้คีย์แทนรหัสผ่าน; fail2ban/จำกัดอัตรา; ส่งล็อกไปเครื่องกลาง |
| ผู้โจมตีสร้างบริการแล้ว `systemctl enable` | ฝังตัวให้กลับมาหลังรีบูต | T1543.002 Systemd Service | ตรวจ unit ใหม่ใน `/etc/systemd/system`; เฝ้าลิงก์ใต้ `*.wants` |
| ลบ/แก้ล็อก, `systemctl stop auditd` | ลบร่องรอย หรือปิดการเฝ้าดู | T1070.002 Clear Linux System Logs, T1562.001 Disable or Modify Tools | ส่งล็อกออกนอกเครื่องแบบเรียลไทม์; สิทธิ์ `/var/log`; แจ้งเตือนเมื่อบริการ audit หยุด |
| ไฟล์/inode เต็มโดยตั้งใจ | ทำให้บริการล่ม | T1499 Endpoint Denial of Service | โควตา/แยกพาร์ทิชัน `/var`; แจ้งเตือน `df -h`/`df -i` เกินเกณฑ์ |
| โปรเซสรันจากไฟล์ที่ถูกลบ | มัลแวร์ลบตัวเองหลังเริ่ม | (เทคนิคหลบเลี่ยงการตรวจจับ) | `ls -l /proc/<PID>/exe` ขึ้น `(deleted)` คือสัญญาณ ให้เก็บสำเนาก่อนฆ่า: `cp /proc/<PID>/exe` ไปเก็บหลักฐาน |

ข้อปฏิบัติ

- **ล็อกคือหลักฐานและเป้าหมาย:** ผู้โจมตีที่ได้สิทธิ์สูงมักลบหรือแก้ล็อก ส่งล็อกไปเก็บที่เซิร์ฟเวอร์กลาง รักษาสิทธิ์ของ `/var/log`
- **`ss -tulpn` คือการสำรวจพื้นที่โจมตี:** พอร์ตที่ฟังที่ `0.0.0.0` คือเปิดให้เครือข่ายเข้าถึง ถ้าเห็นพอร์ตและโปรเซสที่ไม่รู้จัก ให้ escalate และเก็บหลักฐานก่อนปิด
- **อย่า `kill -9` โปรเซสที่น่าสงสัยทันที:** บันทึก PID พาธไฟล์ (`ls -l /proc/<PID>/exe`) เวลา และแจ้งทีม Security เพราะการฆ่าทิ้งทำลายหลักฐานในหน่วยความจำ (ตามบทที่แล้วเรื่อง order of volatility)
- **`sudo` เท่าที่จำเป็น:** คำสั่งอ่านอย่าง `free`, `df`, `ps` ไม่ต้องใช้ `sudo` และการใช้ `sudo` ทุกครั้งถูกบันทึกลงล็อก
- **ผลลัพธ์ที่คัดลอกลง ticket/แชต:** ผลของ `ip addr`, `ss` และล็อกมี IP ภายใน ชื่อผู้ใช้ ปิดข้อมูลที่ไม่จำเป็น
- **ดิสก์/inode เต็มอาจเป็นการโจมตี:** ไฟล์ล็อกที่โตผิดปกติหรือไฟล์ขยะนับแสนในเวลาสั้นๆ ดูต้นเหตุ ไม่ใช่แค่ลบไฟล์

| อาการที่ผู้ใช้แจ้ง | คำสั่งแรกที่ควรใช้ | การตีความและขั้นต่อไป |
|---|---|---|
| "เว็บเข้าไม่ได้" | `systemctl status nginx` | `inactive/failed` → อ่านล็อกด้วย `journalctl -u nginx` ก่อนสั่ง `start` ถ้าเป็นแค่หยุด `start` แล้ว `enable` ถ้าไม่ตั้งให้เปิดตอนบูต ถ้า active แต่เข้าไม่ได้ ไปดู `ss` และไฟร์วอลล์ |
| บริการ failed ตอนเริ่ม | `journalctl -u <บริการ> -n 20 --no-pager` | อ่านสาเหตุ เช่น พอร์ตซ้ำ ค่าตั้งผิด สิทธิ์ไฟล์ แล้วจึงแก้ที่ต้นเหตุ |
| บริการหายไปเองไม่มีข้อความ error | `sudo dmesg -T` หา `Killed process` | OOM killer ฆ่า (รหัสออก 137) ดู `free -h`, จำกัดหน่วยความจำของบริการ หรือเพิ่ม RAM |
| "เซิร์ฟเวอร์ช้า" | `top` และ `free -h` | ดู load เทียบจำนวนแกน แยก `%us` กับ `%wa` และดู `available` กับการใช้ swap ถ้าโปรเซสเดียวกิน CPU/RAM ตรวจก่อน `kill` แจ้งเจ้าของงาน |
| โปรแกรมค้าง ปิดไม่ลง | `pgrep <ชื่อ>` หรือ `ps aux` เพื่อหา PID และ STAT | `kill <PID>` ก่อน รอแล้วตรวจ ถ้ายังไม่ออกและ STAT ไม่ใช่ D จึง `kill -9` แจ้งผู้ใช้เรื่องข้อมูลที่ยังไม่เซฟ ถ้า D ให้ดูอุปกรณ์ I/O |
| เขียนไฟล์ไม่ได้ "No space left on device" แต่ `df -h` ยังว่าง | `df -i` | `IUse%` ใกล้ 100% = inode หมด หาโฟลเดอร์ที่มีไฟล์จำนวนมาก (เช่น session/cache/spool) และล้างไฟล์เก่า |
| `df -h` เต็ม 100% | `du -sh /var/*` ไล่ลงลึกทีละชั้น | มักเป็นล็อกที่โตไม่หยุด ตั้งการหมุนล็อก (log rotation) ถ้า `du` รวมน้อยกว่า `df` มาก ลอง `lsof +L1` |
| ตรวจสอบการล็อกอินแปลกๆ ผ่าน SSH | `sudo tail -F /var/log/auth.log` | ดู IP ที่ล้มเหลวซ้ำๆ แล้ว escalate ให้ Security ดูเรื่องบล็อก IP หรือปิดรหัสผ่านแล้วใช้คีย์ |
| บริการรันอยู่ แต่ลูกค้าติดต่อไม่ได้ | `sudo ss -tulpn` | ดูว่าพอร์ตฟังอยู่ที่ใด (`127.0.0.1` คือรับเฉพาะในเครื่อง) ถ้าฟังถูกแล้วแต่ลูกค้าเจอ timeout ไปดูไฟร์วอลล์ ถ้าเจอ refused แปลว่าไม่มีใครฟัง |
| เครือข่ายไม่ติดเลย | `ip addr show` | ไม่มี `LOWER_UP` = สายหรือสวิตช์ ขึ้น `169.254` = DHCP ไม่ตอบ |

## ลงมือทำจริง (อ่านอย่างเดียว ปลอดภัย)

ใช้เครื่อง Linux ของตัวเอง (หรือ VM / WSL ที่ใช้ systemd ได้)

1. **ตรวจว่าเครื่องมืออ่านจาก /proc:** รัน `cat /proc/loadavg` แล้วเทียบกับ `uptime` และ `nproc` คำนวณ load ต่อแกน
2. **บริการ:** รัน `systemctl status ssh` (หรือ `sshd`) อ่านค่า Loaded กับ Active แล้วลิสต์ `systemctl --failed` และรัน `systemctl is-enabled ssh`
3. **ทรัพยากร:** รัน `free -h` ระบุตัวเลข `available` แล้วหา `MemAvailable` ใน `grep -E MemTotal|MemAvailable /proc/meminfo` เทียบกัน และคำนวณเปอร์เซ็นต์ที่ใช้ได้
4. **ดิสก์:** รัน `df -h` และ `df -i` ดูระบบไฟล์ราก แล้ว `du -sh /var/log/* | sort -h | tail` หาไฟล์ล็อกที่ใหญ่สุด และคำนวณ inode ต่อ GiB ของระบบไฟล์ของคุณ
5. **ล็อก:** รัน `journalctl -p err -b -n 20 --no-pager` เลือกข้อความผิดพลาดหนึ่งบรรทัดแล้วอธิบาย และ `journalctl --disk-usage`
6. **เครือข่าย:** รัน `ip addr show` และ `sudo ss -tulpn` แล้วระบุพอร์ตที่ฟังอยู่ที่ `0.0.0.0` ว่ามีกี่พอร์ต และโปรแกรมอะไร พร้อมแยกว่าตัวใดฟังเฉพาะ `127.0.0.1`
7. **สถานะโปรเซส:** รัน `ps -eo pid,stat,cmd | head -20` และนับว่ามีสถานะใดบ้าง ตรวจ `ls -l /proc/$$/exe`
8. **ticket:** สมมติ nginx ไม่ขึ้นเพราะไฟล์ตั้งค่าผิด เขียน ticket 4 ส่วน (อาการ สาเหตุที่ตรวจพบ ขั้นแก้ ผลลัพธ์) โดยระบุคำสั่งที่ใช้เป็นหลักฐาน

::reveal{question="แนวคำตอบข้อ 6 (พอร์ตที่ฟังอยู่ที่ 0.0.0.0)"}
ดูคอลัมน์ Local Address ของผล `ss -tulpn` บรรทัดที่เป็น `0.0.0.0:<พอร์ต>` หรือ `[::]:<พอร์ต>` (IPv6) คือเปิดรับจากเครือข่ายภายนอก ส่วน `127.0.0.1:<พอร์ต>` รับเฉพาะในเครื่อง ตัวอย่างที่พบบ่อยคือ sshd ที่พอร์ต 22 ควรตรวจว่าทุกพอร์ตที่เปิดมีเหตุผลทางธุรกิจ พอร์ตที่ไม่จำเป็นควรปิดหรือจำกัดด้วยไฟร์วอลล์
::

## ศัพท์สำคัญ

| English | คำอ่าน / คำไทย | ความหมาย |
|---|---|---|
| /proc | โปรค | ระบบไฟล์เสมือนที่เคอร์เนลสร้างสดเพื่อเปิดเผยสถานะโปรเซสและระบบ |
| systemd | ซิสเต็มดี | init system และตัวจัดการบริการของลีนุกซ์ส่วนใหญ่ (PID 1) |
| systemctl | ซิสเต็มซีทีแอล | คำสั่งควบคุมและตรวจบริการของ systemd |
| Unit / Service | ยูนิต / เซอร์วิส | หน่วยที่ systemd จัดการ บริการเป็นชนิดหนึ่ง เช่น `nginx.service` |
| Process / PID | โพรเซส / พีไอดี | โปรแกรมที่กำลังทำงาน / หมายเลขประจำตัว |
| Zombie / D state | ซอมบี้ / ดีสเตต | จบแล้วรอพ่อแม่รับรหัสออก / หลับรอ I/O ขัดจังหวะไม่ได้ |
| Signal | ซิกนัล / สัญญาณ | ข้อความสั้นที่เคอร์เนลหรือผู้ใช้ส่งถึงโปรเซส |
| SIGTERM (15) | ซิกเทิร์ม | ขอให้ปิดตัว โปรแกรมดักและเก็บกวาดได้ (รหัสออก 143 ถ้าไม่ดัก) |
| SIGKILL (9) | ซิกคิล | เคอร์เนลยุติทันที ดักไม่ได้ (รหัสออก 137) |
| Page cache / Buffer | เพจแคช / บัฟเฟอร์ | หน่วยความจำที่เก็บข้อมูลดิสก์/ที่รอเขียนลงดิสก์ คืนได้เมื่อต้องการ |
| Swap / Thrashing | สว็อป / แทรชชิง | พื้นที่ดิสก์พักข้อมูล RAM / อาการช้าจากสลับหน้าถี่เกินไป |
| OOM killer | โออูมคิลเลอร์ | กลไกเคอร์เนลที่ฆ่าโปรเซสเมื่อหน่วยความจำหมดสนิท |
| Load average | โหลดเอเวอเรจ | ค่าเฉลี่ยเอ็กซ์โปเนนเชียลของจำนวนงานที่รัน/รอ (1/5/15 นาที) |
| Inode | ไอโหนด | โครงสร้างเมทาดาทาของไฟล์ 1 ไฟล์ในระบบไฟล์ จำนวนจำกัดตั้งแต่ฟอร์แมต |
| Journal / journalctl | เจอร์นัล / เจอร์นัลซีทีแอล | ที่เก็บล็อกของ systemd / คำสั่งอ่านล็อก |
| dmesg | ดีเมสก์ | ข้อความจาก ring buffer ของเคอร์เนล (ฮาร์ดแวร์/ไดรเวอร์/OOM) |
| bind / listen | ไบนด์ / ลิสเซน | ผูก socket กับที่อยู่และพอร์ต / เริ่มรอรับการเชื่อมต่อ |
| EADDRINUSE | อีแอดเดรสอินยูส | ข้อผิดพลาด bind: ที่อยู่และพอร์ตนี้มีเจ้าของแล้ว |
| Connection refused / timeout | คอนเนกชันรีฟิวส์ / ไทม์เอาต์ | ถูกปฏิเสธด้วย RST (ไม่มีใครฟัง) / ไม่มีการตอบกลับเลย (ถูกทิ้งหรือไม่ถึง) |
| Ephemeral port | เอเฟเมอรัลพอร์ต | พอร์ตต้นทางชั่วคราวที่ระบบเลือกให้การเชื่อมต่อขาออก |
| ss | เอสเอส | คำสั่งดู socket และพอร์ต (ทดแทน netstat) |

## ตรวจความเข้าใจ

::reveal{question="free -h แสดง free = 310Mi แต่ available = 2.1Gi ผู้ใช้ตกใจว่า RAM เกือบหมด คุณจะอธิบายอย่างไร และต้องดูอะไรเพิ่ม"}
ลีนุกซ์ใช้ RAM ที่เหลือไปทำ page cache (buff/cache) เพื่อให้เข้าถึงข้อมูลดิสก์เร็วขึ้น และพร้อมทิ้งคืนให้แอปทันทีเมื่อต้องการ ตัวเลขที่บอกว่ามี RAM ให้แอปใหม่ใช้ได้จริงคือ available (2.1 GB) ไม่ใช่ free จึงยังไม่ใช่วิกฤต แต่ควรดู swap ด้วย ถ้า swap ใกล้เต็ม (ในตัวอย่าง 90%) แสดงว่าเครื่องเริ่มเครียด และดู `dmesg` ว่ามี OOM killer หรือยัง
::

::reveal{question="df -h แสดงระบบไฟล์รากว่าง 45 GB แต่ touch test.txt ขึ้น No space left on device สาเหตุที่น่าจะเป็นที่สุดคืออะไร และตรวจอย่างไร"}
inode หมด ทุกไฟล์ต้องใช้ 1 inode และจำนวน inode ถูกกำหนดตอนฟอร์แมต (ตัวอย่าง 100 GiB ได้ 6,553,600 inode) ไฟล์เล็กๆ จำนวนมากทำให้ inode หมดก่อนพื้นที่ ตรวจด้วย `df -i` (ดู IUse%) แล้วใช้ `du --inodes` หาโฟลเดอร์ที่มีไฟล์เยอะ ตัวเลือก "RAM เต็ม" ไม่ตรงเพราะข้อความเป็นเรื่องอุปกรณ์/ระบบไฟล์ ส่วน "read-only" หรือ "สิทธิ์" จะให้ข้อความอื่น (`Read-only file system` หรือ `Permission denied`)
::

::reveal{question="ระบบไฟล์ 200 GiB ใช้อัตราส่วน 1 inode ต่อ 16 KiB และไฟล์แต่ละไฟล์ขนาดจริง 2 KiB (กินบล็อก 4 KiB) มี inode กี่ตัว ไฟล์จะเต็ม inode เมื่อใช้พื้นที่จริงกี่ GiB"}
inode = 200 GiB ÷ 16 KiB = 200 × 2³⁰ ÷ 16,384 = 13,107,200 ตัว เมื่อสร้างไฟล์ครบจำนวนนั้น กินพื้นที่ 13,107,200 × 4 KiB = 50 GiB (25% ของระบบไฟล์) แล้วสร้างไฟล์ใหม่ไม่ได้ ทั้งที่ว่างอีก 150 GiB ตัวเลขนี้คำนวณด้วย node และถือค่าเริ่มต้นของ ext4 เป็นสมมติฐาน (ค่าประมาณ ของจริงต่างตามการตั้งค่าตอนฟอร์แมต)
::

::reveal{question="เครื่อง 4 แกนว่างอยู่ แล้วมีงานที่ใช้ CPU เต็ม 4 งานเริ่มพร้อมกัน หลัง 60 วินาที load 1 นาทีกับ 15 นาทีจะประมาณเท่าไร และทำไมสองค่านี้ต่างกันมาก"}
load 1 นาที ≈ 4 × (1 − e^(−60/60)) = 4 × 0.632 = 2.53 ส่วน load 15 นาที ≈ 4 × (1 − e^(−60/900)) = 4 × 0.0645 = 0.26 ต่างกันเพราะเป็นค่าเฉลี่ยเอ็กซ์โปเนนเชียลที่มีความจำยาวต่างกัน ค่า 1 นาทีไวต่อการเปลี่ยนแปลงเร็ว ค่า 15 นาทียังเฉื่อยอยู่ จึงใช้เทียบทั้งสามเพื่ออ่านแนวโน้ม (ขึ้นหรือลง) ได้ ตามที่ได้ในตารางด้านบน
::

::reveal{question="top แสดง load average 9.0 บนเครื่อง 4 แกน แต่ CPU us+sy รวมแค่ 5% และ wa 70% ควรทำอะไร และ kill -9 โปรเซสที่ใช้ CPU มากที่สุดช่วยไหม"}
ไม่ช่วย เพราะปัญหาไม่ใช่ CPU load สูงเพราะมีโปรเซสสถานะ D (รอ I/O) จำนวนมากที่ถูกนับรวม และ `wa` สูงยืนยันว่าเครื่องรอดิสก์หรือดิสก์เครือข่าย (NFS) ควรดู `ps` หา STAT D และคอลัมน์ wchan, ตรวจ `dmesg` หา I/O error/timeout, ตรวจสุขภาพดิสก์หรือการเชื่อมต่อ NFS การ `kill -9` ไม่สำเร็จกับโปรเซสสถานะ D จนกว่า I/O จะกลับมา
::

::reveal{question="ทำไมควรลอง kill (SIGTERM) ก่อน kill -9 (SIGKILL) และถ้าบริการใน systemd ตายด้วย code=killed, signal=KILL โดยไม่มีใครสั่ง สงสัยอะไร"}
SIGTERM โปรแกรมรับสัญญาณได้ จึงเขียนข้อมูลใน buffer ลงดิสก์ ปิดไฟล์และการเชื่อมต่อฐานข้อมูล แล้วออกอย่างเรียบร้อย SIGKILL เคอร์เนลยุติทันที โปรแกรมไม่มีโอกาสเก็บกวาด ข้อมูลที่ยังไม่ลงดิสก์หายและอาจทำให้ไฟล์เสียหาย ส่วนบริการที่ตายด้วย SIGKILL โดยไม่มีผู้สั่ง (รหัสออก 137) ให้สงสัย OOM killer ก่อน ตรวจ `dmesg -T | grep -i killed` และ `free -h` เพราะ SIGKILL คือวิธีที่ OOM killer ใช้
::

::reveal{question="systemctl start nginx กับ systemctl enable nginx ต่างกันอย่างไร อธิบายว่า enable ทำอะไรภายใน และถ้าต้องการให้เว็บทำงานทั้งตอนนี้และหลังรีบูต ต้องทำอย่างไร"}
`start` เริ่มบริการตอนนี้ แต่ไม่ได้ตั้งให้เริ่มตอนบูต ส่วน `enable` สร้าง symlink ไปยัง unit file ใต้โฟลเดอร์ `*.wants` ของ target ที่ใช้ตอนบูต ตอนบูต systemd เปิดทุกบริการที่ลิงก์อยู่ แต่ไม่ได้เริ่มบริการตอนนี้ ต้องการทั้งสองอย่างให้สั่งทั้ง `sudo systemctl start nginx` และ `sudo systemctl enable nginx` หรือ `systemctl enable --now nginx` ที่รวมสองขั้นในคำสั่งเดียว
::

::reveal{question="ลูกค้าเรียกเว็บเซิร์ฟเวอร์ได้ Connection refused ในเวลาไม่ถึงวินาที แต่อีกเครื่องที่อยู่หลังไฟร์วอลล์เจอ timeout หลายสิบวินาที ทั้งสองอาการชี้ไปที่ตรงไหนต่างกัน"}
refused (ได้ RST กลับมาทันที) แปลว่าแพ็กเก็ตถึงเครื่องเซิร์ฟเวอร์แล้ว แต่เคอร์เนลไม่เจอ socket ที่ฟังพอร์ตนั้น (บริการไม่ได้รัน หรือฟังแค่ 127.0.0.1) ให้ตรวจ `ss -tulpn` บนเซิร์ฟเวอร์ ส่วน timeout แปลว่าไม่มีใครตอบ แพ็กเก็ตถูกทิ้งระหว่างทาง (ไฟร์วอลล์ DROP, เส้นทางผิด) หรือเซิร์ฟเวอร์ปลายทางไม่อยู่ ให้ตรวจกฎไฟร์วอลล์และเส้นทาง การรีสตาร์ตบริการจึงไม่ช่วยกรณี timeout
::

::reveal{question="PostgreSQL ขึ้น failed ล็อกบอก Address already in use พอร์ต 5432 คุณจะหาว่าอะไรถือพอร์ตนั้นอยู่อย่างไร และข้อความ Permission denied ตอน bind ต่างกันอย่างไร"}
`sudo ss -tulpn | grep 5432` คอลัมน์ Process จะบอกชื่อโปรแกรมและ PID ที่ถือพอร์ต เช่น docker-proxy (คอนเทนเนอร์) แล้วจึงตัดสินใจ หยุดคอนเทนเนอร์หรือย้ายพอร์ต โดยตรวจก่อนว่าเป็นของใครและใช้ทำอะไร แทนการ kill -9 ไปทั่ว ส่วน Address already in use (EADDRINUSE) คือมีเจ้าของพอร์ตแล้ว ขณะที่ Permission denied (EACCES) ตอน bind มักเกิดเมื่อผู้ใช้ธรรมดาพยายาม bind พอร์ตต่ำกว่า 1024 โดยไม่มีสิทธิ์
::

::reveal{question="เปรียบเทียบ journalctl -u nginx -f กับ sudo tail -F /var/log/auth.log ต่างกันอย่างไร และทำไม tail -f ธรรมดาอาจเงียบไปกลางทาง"}
ทั้งสองติดตามบรรทัดใหม่แบบสด `journalctl -u nginx -f` อ่านจาก journal ของ systemd กรองเฉพาะบริการ nginx ส่วน `tail -F /var/log/auth.log` ตามไฟล์ข้อความล็อกการพิสูจน์ตัวตน (ล็อกอิน SSH, sudo) ใช้ journalctl กับบริการที่ล็อกเข้า journal และใช้ tail กับไฟล์ใต้ `/var/log` ที่แอปเขียนเอง `tail -f` ติดตามไฟล์เดิมตามตัวไฟล์ เมื่อ logrotate เปลี่ยนชื่อและสร้างไฟล์ใหม่ มันจะยังตามไฟล์เก่าที่ไม่มีข้อมูลใหม่ ใช้ `-F` เพื่อติดตามตามชื่อและเปิดไฟล์ใหม่ให้ ทั้งคู่กด Ctrl+C เพื่อออก
::

::reveal{question="ผู้ดูแลเห็นว่า df -h แสดง / เต็ม 100% แต่ du -sh /* รวมแล้วเหลือ 12 GB จากดิสก์ 50 GB สาเหตุที่พบบ่อยคืออะไร แก้อย่างไร"}
ไฟล์ขนาดใหญ่ถูกลบ (เช่น `rm` ไฟล์ล็อก) แต่โปรเซสยังเปิดค้างอยู่ จึงยังไม่คืนบล็อก `du` เดินจากรายการไฟล์ที่ยังอยู่ จึงไม่เห็นส่วนนี้ ตรวจด้วย `sudo lsof +L1` เพื่อหาไฟล์ที่ link count เป็น 0 แล้วรีสตาร์ต (หรือ reload ให้ปิดไฟล์) บริการเจ้าของ ทางป้องกันคือใช้ logrotate ให้ส่งสัญญาณให้บริการเปิดไฟล์ใหม่ แทนการลบด้วยมือ
::

## สรุป

- เครื่องมือ `ps`, `top`, `free`, `ss` อ่านสถานะจากเคอร์เนล (`/proc`) ผลสอดคล้องกัน แต่บางค่าเป็นค่าประมาณ และเคอร์เนลที่ถูกยึดโกหกได้
- systemd (PID 1) ถือชีวิตบริการ `start` เริ่มตอนนี้ `enable` สร้าง symlink ให้เริ่มตอนบูต `inactive (dead)` ต่างจาก `failed` และ `code=killed, signal=KILL` ชี้ OOM killer
- `kill` คือการส่งสัญญาณ SIGTERM (15, ดักได้, รหัสออก 143) ก่อน SIGKILL (9, ดักไม่ได้, รหัสออก 137) โปรเซสสถานะ D ฆ่าไม่ได้ zombie แก้ที่พ่อแม่
- `free -h` ดู `available` (page cache คืนได้) swap ตึงคือเครียด จนถึง OOM killer load average เป็นค่าเฉลี่ยเอ็กซ์โปเนนเชียลเทียบจำนวนแกน และ load สูงจาก D state ไม่ใช่ CPU
- `df -h` ดูบล็อก `df -i` ดู inode (100 GiB ได้ 6,553,600 inode ตามค่าเริ่มต้น ext4) `du` หาต้นเหตุ ถ้า df กับ du ไม่ตรงให้สงสัยไฟล์ถูกลบแต่เปิดค้าง
- `journalctl -u`, `/var/log`, `tail -F`, `dmesg` คือที่อ่านเหตุผลที่บริการพัง ระดับความรุนแรง 0–7
- `ip addr show` ตรวจ UP/LOWER_UP/inet และ `ss -tulpn` ตรวจพอร์ตที่ฟังและเจ้าของ refused (ถึงเครื่องแต่ไม่มีใครฟัง) ต่างจาก timeout (ไม่มีใครตอบ) EADDRINUSE ต่างจาก EACCES
- ไล่ status → logs → port ก่อนแก้ บันทึกลง ticket และระวังเรื่องหลักฐาน ผู้โจมตีใช้เครื่องมือเดียวกันสำรวจ ฝังตัว และลบล็อก (T1049, T1057, T1543.002, T1070.002, T1499)
