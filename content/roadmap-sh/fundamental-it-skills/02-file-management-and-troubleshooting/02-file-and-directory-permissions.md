## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่าทำไมต้องมีสิทธิ์ และบอกความต่างของโมเดล Linux (3 กลุ่ม × 3 สิทธิ์) กับ Windows NTFS (ACL ที่มีหลายรายการ)
2. อ่านผล `ls -l` และแปลง `rwxr-xr--` เป็นเลขฐานแปด (754) และกลับกันได้
3. บอกได้ว่า r / w / x ต่างกันอย่างไรบน **ไฟล์** กับบน **โฟลเดอร์** และอธิบายกฎ "ต้องมี x ทุกโฟลเดอร์ตลอดทาง"
4. ใช้ `chmod`, `chown` ได้ถูก และอธิบาย `umask` ว่าส่งผลต่อไฟล์ใหม่อย่างไร
5. อธิบาย special bits (setuid, setgid, sticky) และเหตุที่ setuid เกี่ยวกับความปลอดภัย
6. อ่านผล `icacls` ออก (`(I)`, `(OI)`, `(CI)`, `(F)`, `(M)`, `(R)`) และเข้าใจ inheritance
7. ทำนายผลเมื่อมีทั้ง Allow และ Deny, explicit และ inherited ตามลำดับที่ Windows ตรวจ
8. ไล่แก้ปัญหา "Permission denied / Access is denied" อย่างเป็นขั้นตอนบนทั้งสองระบบ
9. อธิบายจาก first principles ว่า "สิทธิ์" คือการตอบคำถามเดียว (ใคร ทำอะไร กับอะไร) และ Linux กับ Windows เลือกเก็บคำตอบต่างกัน (เก็บที่วัตถุ เทียบเก็บที่ตัวผู้ใช้) เพราะอะไร
10. ไล่ขั้นตอนที่ kernel ทำจริงเมื่อเรียก `open()` และเข้าใจเหตุที่ credential (uid, กลุ่ม) ถูก "ถ่ายสำเนา" ตอนล็อกอิน
11. คำนวณ umask ด้วยการ AND-NOT (ไม่ใช่ลบ), ถอดรหัส special bits (`s`/`S`/`t`/`T`) และอ่าน access mask ของ Windows ในระดับบิตได้
12. ระบุข้อจำกัดของโมเดลสิทธิ์พื้นฐาน (root, ACL, MAC, mount option, สิทธิ์ที่ตรวจตอน open เท่านั้น) และแมปการโจมตีที่เกิดจากสิทธิ์ผิดพลาดกับกลไกที่เรียนไป

## เปรียบเทียบกับชีวิตจริง

นึกถึง **ตึกสำนักงานที่มีคีย์การ์ด**

| ตึกสำนักงาน | คอมพิวเตอร์ | ข้อสังเกต |
|---|---|---|
| เจ้าของห้อง / ผู้เช่าชั้นเดียวกัน / บุคคลภายนอก | user / group / others | ตรวจว่าคุณเป็นกลุ่มไหนก่อน แล้วใช้สิทธิ์ของกลุ่มนั้น |
| ประตูห้องกับตู้เอกสารในห้อง | สิทธิ์ของโฟลเดอร์กับไฟล์ | เข้าถึงตู้ได้ต่อเมื่อผ่านประตูทุกบานตามทางก่อน |
| บัตรเข้าได้หรือไม่ได้ | x บนโฟลเดอร์ | ไม่มีบัตรผ่านประตู เห็นป้ายบนประตูได้ แต่เข้าไปไม่ได้ |
| รายชื่อติดหน้าห้อง | r บนโฟลเดอร์ | ดูได้ว่าข้างในมีอะไรบ้าง แต่เปิดดูไม่ได้ถ้าไม่มีบัตร |
| ห้ามเด็ดขาด (บัญชีดำ) | Deny ใน NTFS | บัญชีดำชนะรายชื่ออนุญาตในระดับเดียวกัน |
| ผู้บริหารถืออภิสิทธิ์ผ่านได้ทุกประตู | root / Administrator | มีอำนาจสูงสุด จึงต้องใช้น้อยที่สุด |

## ทำไมต้องมีสิทธิ์: จากหลักการสู่กลไก

ก่อนจำ `rwx` ลองถามให้ลึกกว่านั้นก่อนว่า **ระบบปฏิบัติการต้องตอบคำถามอะไร** ในทุกครั้งที่โปรแกรมแตะไฟล์ คำตอบคือคำถามเดียว

> **ผู้กระทำ (subject)** คนนี้ มีสิทธิ์ทำ **การกระทำ (operation)** นี้ กับ **วัตถุ (object)** นี้ หรือไม่?

เครื่องที่มีผู้ใช้หลายคน (หรือผู้ใช้คนเดียวที่รันโปรแกรมหลายตัวที่ไว้ใจไม่เท่ากัน เช่น เบราว์เซอร์กับตัวติดตั้ง) ต้องมีตัวกลางที่คอยตอบคำถามนี้ ตัวกลางนั้นคือ **kernel** เพราะเป็นส่วนเดียวที่โปรแกรมทั่วไปข้ามไม่ได้ (เรียกว่า *reference monitor*: ทุกการเข้าถึงต้องผ่านมัน, มันต้องแก้ไม่ได้, และต้องเล็กพอให้ตรวจสอบได้)

### เก็บคำตอบอย่างไร: ตารางควบคุมการเข้าถึง (access control matrix)

วิธีคิดตรงที่สุดคือตารางใหญ่ แถว = ผู้กระทำ คอลัมน์ = วัตถุ ช่อง = สิทธิ์ที่มี แต่ตารางเต็มใหญ่เกินไป ลองประมาณขนาด (สมมติฐานเพื่อให้เห็นภาพ ไม่ใช่ตัวเลขจากระบบจริง)

- ผู้ใช้ 1,000 คน × ไฟล์ 1,000,000 ไฟล์ = **10⁹ ช่อง**
- เก็บแค่ 3 สิทธิ์ (r, w, x) ช่องละ 1 บิต = 3 × 10⁹ บิต ≈ **375 MB** ของข้อมูลสิทธิ์อย่างเดียว และต้องแก้ทุกครั้งที่มีผู้ใช้หรือไฟล์ใหม่
- ถ้า Linux เก็บ "โหมด" ของแต่ละไฟล์ไว้ใน inode ใช้ราว 2 ไบต์ต่อไฟล์ → 10⁶ × 2 ≈ **2 MB** เท่านั้น

ระบบจริงจึง "ตัดตาราง" เป็นสองแนวทาง

| แนวทาง | เก็บอะไร | ข้อดี | ข้อเสีย | ใครใช้ |
|---|---|---|---|---|
| **ACL** (ตัดตามคอลัมน์) | แนบรายการ "ใครทำอะไรได้" ไว้ที่วัตถุแต่ละชิ้น | ตอบ "ใครเข้าไฟล์นี้ได้บ้าง" ได้ทันที เพิกถอนง่าย | ตอบ "ผู้ใช้คนนี้เข้าอะไรได้บ้าง" ต้องสแกนทั้งดิสก์ | NTFS, POSIX ACL |
| **Capability** (ตัดตามแถว) | ให้ผู้กระทำถือ "กุญแจ" ไปยังวัตถุ | ส่งต่อสิทธิ์ง่าย ตัดสินใจเร็ว | เพิกถอนกุญแจที่แจกไปแล้วยาก | file descriptor, token |
| **ย่อด้วยกลุ่ม** (บีบพิกัด) | แทนผู้ใช้ด้วย 3 ชนชั้น: เจ้าของ / กลุ่ม / คนอื่น | เล็กมาก เร็วมาก | ละเอียดได้แค่ 3 ชั้น | โหมดพื้นฐานของ Unix |

ดังนั้น **9 บิตของ Unix** คือการ "บีบ" ตารางให้เหลือเล็กสุดที่ยังใช้งานได้ ส่วน **ACL ของ NTFS** คือการยอมเสียที่เก็บเพิ่มแลกกับความละเอียด ทั้งสองไม่ได้ "ดีกว่า" กัน แต่ตอบเงื่อนไขของยุคที่ออกแบบต่างกัน และทั้งสองใช้หลักข้อเดียวกันคือ **สิทธิ์น้อยที่สุด (least privilege)** ของ Saltzer และ Schroeder (1975) ที่ว่าทุกโปรแกรมและทุกผู้ใช้ควรทำงานด้วยสิทธิ์น้อยที่สุดเท่าที่งานต้องการ

### ที่เก็บสิทธิ์: ในไดเรกทอรี หรือในไฟล์?

คำตอบของ Linux คือ **สิทธิ์อยู่ใน inode (ตัวไฟล์) ไม่ใช่ในชื่อ** ไดเรกทอรีคือไฟล์พิเศษที่เก็บแค่คู่ "ชื่อ → หมายเลข inode" ผลที่ตามมามีสามข้อ

1. ไฟล์เดียวที่มี hard link สองชื่อ **ใช้สิทธิ์ชุดเดียวกัน** เพราะเป็น inode เดียวกัน
2. การ **ลบ** ไฟล์คือการแก้ไดเรกทอรี (ตัดคู่ชื่อ→inode ออก) จึงต้องมี `w` + `x` บนไดเรกทอรี ไม่เกี่ยวกับ `w` ของไฟล์ ตรงกับที่จะเห็นในคำถามท้ายบท
3. การเปลี่ยนสิทธิ์ (`chmod`) ไม่แตะไดเรกทอรีเลย แก้แค่ฟิลด์ mode ใน inode

โมเดลมองเป็นภาพได้ดังนี้ ฟิลด์ **mode** ใน inode กว้าง 16 บิต (บน ext4 และระบบส่วนใหญ่)

| บิต (จากซ้าย) | 15–12 | 11 | 10 | 9 | 8–6 | 5–3 | 2–0 |
|---|---|---|---|---|---|---|---|
| ความหมาย | ชนิดไฟล์ (`-`, `d`, `l`, …) | setuid | setgid | sticky | สิทธิ์ user (rwx) | สิทธิ์ group (rwx) | สิทธิ์ others (rwx) |

ตัวเลขฐานแปดที่เราเขียน เช่น `4755` จึงคือการอ่านบิต 11–0 ทีละ 3 บิต: `4` = setuid, `7` = user rwx, `5` = group r-x, `5` = others r-x (4 หลักนี้ครอบ 12 บิต = **4,096** ค่าที่เป็นไปได้ โดยเฉพาะ 9 บิต rwx อย่างเดียว = 2⁹ = **512** โหมด)

## 1. โมเดลสิทธิ์ของ Linux

### 1.1 เจ้าของ กลุ่ม และคนอื่น

Linux ผูกทุกไฟล์และโฟลเดอร์เข้ากับ **เจ้าของ (owner)** หนึ่งบัญชี และ **กลุ่ม (group)** หนึ่งกลุ่ม เมื่อโปรแกรมของคุณขอเปิดไฟล์ kernel จะตรวจตามลำดับนี้ **แล้วหยุดที่ข้อแรกที่ตรง**

1. คุณเป็นเจ้าของไฟล์ → ใช้สิทธิ์ของ **user (u)**
2. ไม่ใช่เจ้าของ แต่อยู่ในกลุ่มของไฟล์ → ใช้สิทธิ์ของ **group (g)**
3. นอกจากนั้นทั้งหมด → ใช้สิทธิ์ของ **others (o)**

จุดที่คนมักพลาด: ถ้าคุณเป็นเจ้าของ จะถูกตรวจที่สิทธิ์ของเจ้าของเท่านั้น **ไม่สนใจว่ากลุ่มจะมีสิทธิ์มากกว่าหรือไม่** ไฟล์โหมด `060` (เจ้าของไม่มีสิทธิ์ กลุ่มอ่านเขียนได้) จึงทำให้เจ้าของเองเปิดไม่ได้ ข้อยกเว้นเดียวคือ **root** ซึ่งผ่านการตรวจสิทธิ์พื้นฐานเกือบทั้งหมด

### 1.2 สิทธิ์ r, w, x บนไฟล์และบนโฟลเดอร์

แต่ละกลุ่มมีสิทธิ์ย่อยสามอย่าง ความหมายต่างกันตามชนิดของสิ่งที่ถูกตรวจ

| สิทธิ์ | สัญลักษณ์ | บนไฟล์ | บนโฟลเดอร์ |
|---|---|---|---|
| อ่าน (Read) | r | ดูเนื้อหาไฟล์ | แสดงรายชื่อรายการข้างใน |
| เขียน (Write) | w | แก้ไขหรือล้างเนื้อหา | เพิ่ม เปลี่ยนชื่อ หรือลบรายการข้างใน |
| รัน (Execute) | x | สั่งรันเป็นโปรแกรมหรือสคริปต์ | เข้าโฟลเดอร์ (`cd`) และเข้าถึงรายการข้างใน |

สิ่งที่ต้นฉบับพูดสั้นแต่สำคัญมากในงานจริง

- **บนโฟลเดอร์ `x` สำคัญกว่าที่คิด:** ถ้าไม่มี `x` คุณเข้าถึงอะไรข้างในไม่ได้เลย แม้จะรู้ชื่อไฟล์และไฟล์ข้างในเปิดกว้าง `w` บนโฟลเดอร์ก็ใช้ไม่ได้ถ้าไม่มี `x` ควบคู่
- **โฟลเดอร์ที่มี r แต่ไม่มี x:** เห็นแค่ชื่อรายการ (และ `ls -l` จะฟ้อง error เพราะอ่านรายละเอียดไม่ได้) ส่วนโฟลเดอร์ที่มี x แต่ไม่มี r: เข้าถึงรายการได้ ถ้ารู้ชื่อเป๊ะ แต่ `ls` ไม่แสดงอะไร
- **สคริปต์ต้องมี r ด้วย:** ไฟล์สคริปต์ (เช่น `.sh`) ต้องมีทั้ง `r` และ `x` เพราะตัวแปลสคริปต์ต้องอ่านเนื้อหา ส่วนโปรแกรมที่คอมไพล์แล้วต้องการแค่ `x`

### 1.3 อ่านผลของ `ls -l`

```text
-rwxr-xr-- 1 alex devteam 4096 Apr 12 10:00 deploy.sh
```

| ส่วน | ตัวอย่าง | ความหมาย |
|---|---|---|
| ตัวที่ 1 | `-` | ชนิด: `-` ไฟล์ปกติ, `d` โฟลเดอร์, `l` ลิงก์สัญลักษณ์ |
| ตัวที่ 2-4 | `rwx` | สิทธิ์ของเจ้าของ (alex): อ่าน เขียน รัน |
| ตัวที่ 5-7 | `r-x` | สิทธิ์ของกลุ่ม (devteam): อ่านและรัน แก้ไม่ได้ |
| ตัวที่ 8-10 | `r--` | สิทธิ์ของคนอื่น: อ่านอย่างเดียว |
| ถัดมา | `alex devteam` | เจ้าของ และ กลุ่ม |

ใช้ `ls -ld ชื่อโฟลเดอร์` ถ้าอยากดูสิทธิ์ของตัวโฟลเดอร์เอง (ไม่ใช่ของข้างใน)

### 1.4 เลขฐานแปด

แต่ละสิทธิ์มีค่าประจำตัว r = 4, w = 2, x = 1 และ "ไม่มี" = 0 ของแต่ละกลุ่มให้ **บวกกัน** ได้เลขหนึ่งหลัก

| สตริง | คำนวณ | เลข |
|---|---|---|
| `rwx` | 4 + 2 + 1 | 7 |
| `rw-` | 4 + 2 + 0 | 6 |
| `r-x` | 4 + 0 + 1 | 5 |
| `r--` | 4 + 0 + 0 | 4 |
| `---` | 0 + 0 + 0 | 0 |

สามหลักเรียงเป็น เจ้าของ / กลุ่ม / คนอื่น ตัวอย่าง `754` = เจ้าของ 7 (`rwx`), กลุ่ม 5 (`r-x`), คนอื่น 4 (`r--`) ลองเปิดปิดสิทธิ์ในตัวคำนวณนี้ ดูตัวเลข สตริง และคำสั่ง `chmod` เปลี่ยนตาม และสลับดูความหมายบนไฟล์กับโฟลเดอร์

::

ค่าที่พบบ่อยในงานจริง (จากความรู้ทั่วไปของผู้เขียน)

| โหมด | ความหมาย | ใช้กับ |
|---|---|---|
| 644 | เจ้าของอ่าน/เขียน คนอื่นอ่านอย่างเดียว | ไฟล์ทั่วไป ไฟล์เว็บ |
| 600 | เฉพาะเจ้าของ | ไฟล์ลับ เช่น กุญแจ SSH |
| 755 | เจ้าของทำได้ทุกอย่าง คนอื่นอ่านและรัน | โปรแกรม สคริปต์ โฟลเดอร์ทั่วไป |
| 700 | เฉพาะเจ้าของ | โฟลเดอร์ส่วนตัว เช่น `~/.ssh` |
| 750 / 640 | กลุ่มอ่าน (และรัน) ได้ คนอื่นไม่ได้เลย | งานร่วมกันในทีม |
| 777 | ทุกคนทำได้ทุกอย่าง | **หลีกเลี่ยง** |

### 1.5 `chmod` และ `chown`

คำสั่ง **`chmod`** เปลี่ยนสิทธิ์ รับได้สองแบบ แบบเลขฐานแปด หรือแบบสัญลักษณ์

```bash
chmod 750 deploy.sh      # ตั้งใหม่ทั้งหมด: เจ้าของ rwx, กลุ่ม r-x, คนอื่นไม่มีสิทธิ์
chmod u+x deploy.sh      # เพิ่ม x ให้เจ้าของ (u = user)
chmod go-w deploy.sh     # ถอน w ออกจากกลุ่มและคนอื่น (g = group, o = others)
chmod a+r notes.txt      # เพิ่ม r ให้ทุกคน (a = all)
```

คำสั่ง **`chown`** เปลี่ยนเจ้าของและกลุ่ม

```bash
sudo chown alex:devteam deploy.sh     # เจ้าของ alex กลุ่ม devteam
```

กฎสำคัญที่ต้นฉบับพูดถึง: การเปลี่ยน **เจ้าของ** ทำได้เฉพาะ root (ผ่าน `sudo`) ส่วนเพิ่มเติมที่ควรรู้: **เจ้าของไฟล์** เปลี่ยนสิทธิ์ (`chmod`) ของไฟล์ตัวเองได้ และเปลี่ยนกลุ่ม (`chgrp`) ไปเป็นกลุ่มที่ตัวเองสังกัดอยู่ได้ แต่ถ้าไม่ใช่เจ้าของจะรัน `chmod` ไม่ได้ ลองรันในเทอร์มินัลจำลอง

### 1.7 กลไกภายใน: kernel ตัดสินอย่างไรเมื่อเรียก `open()`

โปรแกรมที่อยากอ่านไฟล์ไม่ได้ "อ่านสิทธิ์เอง" แต่ขอ kernel ผ่าน system call `open(path, flags)` kernel ถือ **credential** ของโปรเซสอยู่แล้ว ได้แก่ uid ที่มีผล (euid), gid ที่มีผล (egid) และรายการกลุ่มเสริม (supplementary groups) แล้วทำขั้นตอนต่อไปนี้ (อธิบายแบบย่อ ตัดรายละเอียดของ LSM/capability ออก)

```text
สำหรับแต่ละโฟลเดอร์ D ในพาธ (จากราก ไปทีละชื่อ):
    ต้องผ่านการตรวจ "x" บน D                  ← ไม่งั้น EACCES (Permission denied)
สำหรับไฟล์ปลายทาง F ที่ขอสิทธิ์ want (r / w / x):
    ถ้า euid == 0            → ผ่าน (ยกเว้น want มี x: ต้องมีบิต x อย่างน้อยหนึ่งบิตในไฟล์)
    ถ้า euid == เจ้าของ F     → ใช้บิต user   แล้ว "ตัดสินตรงนี้" (ผ่านหรือไม่ผ่านก็จบ)
    ถ้า egid หรือกลุ่มเสริมตรง กลุ่มของ F → ใช้บิต group แล้วตัดสินตรงนี้
    ไม่งั้น                     → ใช้บิต others
ผ่านแล้ว → สร้าง file descriptor คืนให้โปรเซส
```

จุดที่ต้องสังเกตสามข้อ

1. **ตัดสินที่ชั้นแรกที่ตรง ไม่ "รวมสิทธิ์"** เจ้าของไฟล์โหมด `060` จึงถูกปฏิเสธ ทั้งที่กลุ่มของตัวเองมี `rw`
2. **ตรวจตอน `open()` เท่านั้น** เมื่อได้ file descriptor แล้ว `read()`/`write()` รอบหลังไม่ตรวจสิทธิ์ซ้ำ (ตรวจแค่ว่าเปิดแบบอ่าน/เขียนไว้หรือไม่) ดังนั้น `chmod 000` ไฟล์ที่เปิดค้างอยู่แล้ว **ไม่ตัดโปรเซสที่ถือ fd อยู่** ต้องฆ่าโปรเซสหรือปิดไฟล์
3. **root ไม่ได้ "ข้ามทุกอย่าง"** (ดูหัวข้อข้อจำกัดด้านล่าง) แต่ผ่านการตรวจ DAC เกือบทั้งหมด

## 2. เรื่องที่ควรรู้เพิ่ม: umask และ special bits

### 2.1 umask: ทำไมไฟล์ใหม่ได้สิทธิ์ 644

เมื่อสร้างไฟล์ใหม่ โปรแกรมขอสิทธิ์เริ่มต้น 666 (ไฟล์) หรือ 777 (โฟลเดอร์) แล้วระบบ **ปิดบิตที่ `umask` ระบุ** ค่า `umask 022` ปิด w ของกลุ่มและคนอื่น จึงได้ไฟล์ 644 และโฟลเดอร์ 755 ไฟล์ไม่ได้ x ตั้งแต่เกิด จึงต้อง `chmod +x` เองเสมอ ลองเปลี่ยนค่า umask

::umask-lab
::

**สูตร:** `โหมดจริง = โหมดที่ขอ AND (NOT umask)` เป็นการ **ปิดบิต** ไม่ใช่ "เอาไปลบ" ในหลายกรณีผลเท่ากันจึงทำให้เข้าใจผิดว่าลบ แต่เมื่อ umask มีบิตที่โหมดที่ขอปิดอยู่แล้ว ผลจะต่างกัน ตรวจด้วยการคำนวณจริง (node) ดังนี้

| umask | ไฟล์ (666 AND NOT umask) | โฟลเดอร์ (777 AND NOT umask) | ถ้า "ลบ" ผิดวิธี (666 − umask) |
|---|---|---|---|
| 022 | 644 | 755 | 644 (บังเอิญตรง) |
| 002 | 664 | 775 | 664 (บังเอิญตรง) |
| 027 | 640 | 750 | **637** (ผิด) |
| 077 | 600 | 700 | **567** (ผิด) |
| 033 | 644 | 744 | **633** (ผิด) |

ตัวอย่างวิธีคิดแบบบิตของ `umask 033` กับไฟล์ที่ขอ 666: หลัก 6 = `110`, ค่า 3 = `011`, NOT = `100`, `110 AND 100` = `100` = 4 จึงได้ 644 (ไม่ใช่ 633 ซึ่งหมายถึงให้ x แก่กลุ่มและคนอื่น ทั้งที่ไม่เคยขอ)

ใช้คำสั่ง `umask` เฉยๆ เพื่อดูค่าปัจจุบัน ค่าเริ่มต้นขึ้นกับระบบ (มักเป็น 022 หรือ 002) บริการบนเซิร์ฟเวอร์ที่เก็บข้อมูลอ่อนไหวมักตั้ง umask เข้มขึ้น เช่น 027 หรือ 077 เพื่อให้ไฟล์ที่ถูกสร้างไม่เปิดกว้างโดยไม่ตั้งใจ

### 2.2 บิตพิเศษ 3 ตัว

นอกจาก rwx ยังมีบิตพิเศษ 3 ตัว (ข้อมูลส่วนนี้มาจากความรู้ทั่วไปของผู้เขียน ไม่ได้มาจากต้นฉบับ)

| บิต | เลข | แสดงใน ls -l | ทำอะไร |
|---|---|---|---|
| setuid | 4000 | `s` ที่ตำแหน่ง x ของเจ้าของ | โปรแกรมรันด้วยสิทธิ์ของ **เจ้าของไฟล์** ไม่ใช่ของผู้รัน เช่น `passwd` (`-rwsr-xr-x root`) ให้ผู้ใช้ธรรมดาเปลี่ยนรหัสผ่านที่เก็บในไฟล์ของ root ได้ |

## 3. สิทธิ์บน Windows (NTFS)

### 3.1 ACL และ ACE

Windows ที่ใช้ระบบไฟล์ **NTFS** ไม่เก็บสิทธิ์เป็นบิต 9 ตัว แต่ใช้ **Access Control List (ACL)** แนบกับไฟล์หรือโฟลเดอร์ ภายในมีรายการหลายรายการเรียกว่า **Access Control Entry (ACE)** แต่ละ ACE บอกสามอย่าง

1. **ผู้ที่ถูกกำหนด (security principal):** บัญชีผู้ใช้หรือกลุ่ม
2. **สิทธิ์:** เช่น Read, Write, Modify
3. **ชนิดกฎ:** Allow (อนุญาต) หรือ Deny (ห้าม)

ข้อได้เปรียบคือกำหนดละเอียดได้ เช่น ให้ทีม A แก้ได้ ทีม B อ่านได้ และห้ามกลุ่มผู้รับเหมาเขียน ในโฟลเดอร์เดียวกัน ซึ่งโมเดล Linux พื้นฐาน (เจ้าของ+กลุ่มเดียว) ทำไม่ได้โดยไม่ใช้ ACL เสริม

### 3.2 สิทธิ์มาตรฐาน (Standard permissions)

| สิทธิ์ | ทำอะไรได้ |
|---|---|
| Read | ดูเนื้อหา ดูคุณสมบัติ และดูรายการในโฟลเดอร์ |
| Write | เขียนทับ เขียนข้อมูล และสร้างไฟล์ใหม่ในโฟลเดอร์ |
| Read & Execute | อ่านและรันโปรแกรม/สคริปต์ |
| Modify | อ่าน เขียน รัน และลบไฟล์/โฟลเดอร์ |
| Full Control | ทำได้ทุกอย่าง และ **เปลี่ยนสิทธิ์ได้ กับยึดความเป็นเจ้าของ (take ownership) ได้** |

ความต่างสำคัญระหว่าง Modify กับ Full Control คือเรื่อง **การจัดการสิทธิ์เอง** ผู้ที่มีแค่ Modify แก้ไฟล์ได้ แต่เปลี่ยน ACL ไม่ได้ ใต้สิทธิ์มาตรฐานยังมี **สิทธิ์ละเอียด (special permissions)** อีกมาก เช่น Traverse folder, Delete subfolders and files ซึ่งเป็นองค์ประกอบของสิทธิ์มาตรฐานอีกที

### 3.3 การสืบทอดสิทธิ์ (Inheritance)

ไฟล์และโฟลเดอร์ย่อยที่สร้างใต้โฟลเดอร์แม่ **สืบทอดสิทธิ์จากแม่โดยอัตโนมัติ** ผู้ดูแลระบบตัดการสืบทอดได้เมื่อต้องการแยกโฟลเดอร์ที่ละเอียดอ่อน โดยเลือกได้สองทาง

- **แปลงสิทธิ์ที่สืบมาเป็น explicit** คงรายการเดิมไว้บนวัตถุนี้ (ใช้ `icacls ... /inheritance:d`)
- **ลบสิทธิ์ที่สืบมาทั้งหมด** แล้วเริ่ม ACL ว่างเปล่า (`/inheritance:r`) ระวัง: ถ้าไม่ได้เพิ่มรายการใหม่ จะไม่มีใครเข้าได้เลย

### 3.4 ลำดับที่ Windows ประเมินสิทธิ์

เมื่อมีหลาย ACE ที่เกี่ยวข้องกับคุณ Windows ตรวจตามลำดับ

1. **Explicit Deny** (สูงสุด)
2. **Explicit Allow**
3. **Inherited Deny**
4. **Inherited Allow** (ต่ำสุด)

> **จุดที่ต้นฉบับย่อไว้ และมักเข้าใจผิด:** "Deny ชนะ Allow เสมอ" จริงเมื่อทั้งสองอยู่ระดับเดียวกัน (explicit ทั้งคู่ หรือ inherited ทั้งคู่) แต่ **explicit Allow ชนะ inherited Deny** เพราะถูกตรวจก่อน (ข้อมูลนี้ผู้เขียนสรุปจากกฎมาตรฐานของ ACL ควรทดสอบในเครื่องจริงกับกรณีของคุณ) ตัวอย่างในต้นฉบับ: ผู้ใช้อยู่กลุ่ม Developers (Allow Modify) และ Contractors (Deny Modify) ถ้าสองรายการนี้เป็น explicit ทั้งคู่ ผลคือถูกปฏิเสธ

ลองสลับกลุ่มและสลับ explicit/inherited ดูว่าผู้ตัดสินเปลี่ยนไปอย่างไร

#### กลไกภายใน: ไล่ ACE ใน DACL อย่างไร

ลำดับ "explicit Deny → explicit Allow → inherited Deny → inherited Allow" ไม่ใช่ตรรกะแยกต่างหาก มันคือ **ลำดับที่เก็บ ACE ใน DACL** (เรียกว่า canonical order) ส่วนตัวตัดสินคืออัลกอริทึมง่ายๆ ที่ Security Reference Monitor ของ Windows ทำ (ย่อ)

```text
want = ชุดสิทธิ์ที่ขอ (เช่น READ_DATA)        granted = ว่าง
สำหรับ ACE แต่ละรายการ "ตามลำดับที่เก็บ":
    ถ้า SID ใน ACE ตรงกับ SID ใดๆ ใน token ของผู้ขอ:
        ถ้าเป็น Deny  และ มีบิตที่ทับกับ want ที่ยังไม่ได้ granted → ปฏิเสธทันที
        ถ้าเป็น Allow → granted = granted + บิตของ ACE (เฉพาะส่วนที่อยู่ใน want)
        ถ้า granted ครอบ want ครบแล้ว → อนุญาตทันที (หยุด ไม่ดู ACE ถัดไป)
จบรายการแล้ว granted ยังไม่ครบ → ปฏิเสธ (ไม่มี ACE ให้ = ไม่ได้)
```

ผลที่ตามมา

- **ไม่มี ACE ที่ตรง = ปฏิเสธโดยปริยาย** (default deny) ต่างจากกรณี "DACL ว่าง" ที่ไม่มี ACE เลยซึ่งไม่มีใครเข้าได้ กับ "ไม่มี DACL (NULL)" ที่ทุกคนเข้าได้ ซึ่งเป็นความผิดพลาดด้านความปลอดภัยที่พบได้ในโปรแกรมที่ตั้งสิทธิ์เอง
- **Deny ทับเฉพาะบิตที่ขอ:** Deny Write ไม่ได้ห้ามการ Read ถ้าอ่านอย่างเดียว อ่านผ่าน ก็ผ่านได้
- **token ถูกสร้างตอน logon:** รายการ SID ของผู้ใช้และกลุ่มทั้งหมดถูกบรรจุใน access token ตอนล็อกอิน เหมือนกับ credential ของ Linux เพิ่มกลุ่มแล้วต้อง log off/on

#### Access mask: สิทธิ์มาตรฐานก็คือกลุ่มบิตใน 32 บิต

ในกลไกจริง ทุกสิทธิ์คือบิตใน **access mask** ขนาด 32 บิต "Read", "Modify" ฯลฯ ที่เห็นใน GUI เป็นชื่อเรียกของกลุ่มบิตสำเร็จรูป ค่าต่อไปนี้มาจากนิยามใน Windows API (ตรวจกับเครื่องจริงด้วย `Get-Acl` ได้)

| สิทธิ์มาตรฐาน | access mask | ที่มาของบิต |
|---|---|---|
| Read & Execute | `0x1200A9` | READ_DATA (0x1) + READ_EA (0x8) + EXECUTE (0x20) + READ_ATTRIBUTES (0x80) + READ_CONTROL (0x20000) + SYNCHRONIZE (0x100000) |
| Modify | `0x1301BF` | ทุกบิตของ Read & Execute + WRITE_DATA (0x2) + APPEND_DATA (0x4) + WRITE_EA (0x10) + WRITE_ATTRIBUTES (0x100) + **DELETE (0x10000)** |
| Full Control | `0x1F01FF` | ทุกบิตของ Modify + **DELETE_CHILD (0x40)** + **WRITE_DAC (0x40000)** + **WRITE_OWNER (0x80000)** |

อ่านตารางนี้แล้วเห็นเชิงกลไกว่า **Modify ต่างจาก Full Control เพียง 3 บิต**: ลบรายการลูกโดยไม่ต้องมี DELETE ของลูกเอง (DELETE_CHILD), แก้ ACL (WRITE_DAC) และยึดความเป็นเจ้าของ (WRITE_OWNER) ตรวจเลขได้ว่า `0x1F01FF − 0x1301BF = 0xC0040` ซึ่งตรงกับ 0x40000 + 0x80000 + 0x40 และ Read & Execute เป็นเซตย่อยของ Modify จริง (บิตของ Modify ที่ไม่อยู่ใน Read & Execute มีแค่ `0x10116` คือ DELETE และบิตเขียน)

**ต่างจาก Linux ตรงที่สำคัญ: Windows ไม่บังคับ "x ทุกโฟลเดอร์ตลอดพาธ"** โดยปริยาย ผู้ใช้ทุกคนมีสิทธิ์ระบบ *Bypass traverse checking* (SeChangeNotifyPrivilege) ซึ่งทำให้ข้ามการตรวจ Traverse Folder ของโฟลเดอร์ระหว่างทางได้ ถ้าเข้าไฟล์ปลายทางได้ด้วย ACL ของมันเองก็เปิดได้ แม้โฟลเดอร์แม่จะมองไม่เห็นรายการ (ค่าเริ่มต้นของ Windows ที่ผู้ดูแลปรับได้ ควรทดสอบก่อนอาศัยพฤติกรรมนี้เป็นมาตรการป้องกัน)

### 3.5 ตรวจและแก้สิทธิ์ด้วย `icacls`

**`icacls`** ใช้ดูและแก้ ACL ได้จาก Command Prompt หรือ PowerShell

```powershell
icacls C:\Projects
```

ตัวอย่างผลลัพธ์ และความหมายของวงเล็บ

```text
C:\Projects NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
            BUILTIN\Administrators:(I)(OI)(CI)(F)
            CORP\Domain Users:(I)(OI)(CI)(M)
            CORP\Auditors:(I)(OI)(CI)(R)
```

| โค้ด | ความหมาย |
|---|---|
| `(I)` | สืบมาจากโฟลเดอร์แม่ (Inherited) |
| `(OI)` | Object Inherit: ใช้กับไฟล์ข้างใน |
| `(CI)` | Container Inherit: ใช้กับโฟลเดอร์ย่อยข้างใน |
| `(F)` | Full Control |
| `(M)` | Modify |
| `(RX)` | Read & Execute |
| `(R)` | Read |
| `(W)` | Write |

คำสั่งที่ใช้บ่อย

| ต้องการ | คำสั่ง |
|---|---|
| เพิ่มสิทธิ์ให้ Taylor โดยไม่แตะรายการอื่น | `icacls C:\Projects /grant Taylor:(W)` |
| ตั้งสิทธิ์ใหม่แทนของเดิมของ Taylor | `icacls C:\Projects /grant:r Taylor:(M)` |
| ห้ามกลุ่มหนึ่ง | `icacls C:\Projects /deny Contractors:(W)` |
| ลบรายการของ Taylor | `icacls C:\Projects /remove Taylor` |
| ตัดการสืบทอด คงสิทธิ์ที่สืบมาเป็น explicit | `icacls C:\Projects /inheritance:d` |
| ทำซ้ำลงทุกไฟล์ข้างใน | เติม `/T` ท้ายคำสั่ง |

> **หมายเหตุสำหรับ PowerShell:** วงเล็บของสิทธิ์มีความหมายพิเศษใน PowerShell ต้องครอบด้วยเครื่องหมายคำพูด เช่น `icacls C:\Projects /grant "Taylor:(W)"` ส่วน Command Prompt ใช้แบบไม่ครอบได้ (ผู้เขียนสรุปจากความรู้ทั่วไป ควรลองกับโฟลเดอร์ทดสอบ)

### 3.6 เรื่องที่ควรรู้เพิ่มบน Windows

- **สิทธิ์ของโฟลเดอร์แชร์ (share) กับ NTFS:** เมื่อเข้าถึงผ่านเครือข่าย Windows ใช้ผลที่ **เข้มกว่า** ระหว่างสองชั้น อาการ "เปิดในเครื่องได้ แต่ผ่านเครือข่ายไม่ได้" มักเป็นสิทธิ์ share
- **ผู้ดูแลระบบไม่ได้ผ่านเสมอ:** แม้เป็น Administrator ก็อาจโดน "Access is denied" เมื่อไม่ได้รันแบบ elevated (UAC) หรือเมื่อ ACL ไม่มีรายการของกลุ่มนั้น วิธีกู้: ยึดความเป็นเจ้าของด้วย `takeown /f พาธ /r` แล้วแก้ ACL ด้วย `icacls`
- **ดูผลรวมจริง:** แท็บ Properties > Security > Advanced > Effective Access บอกสิทธิ์สุทธิของผู้ใช้ที่เลือก ส่วน PowerShell ใช้ `Get-Acl พาธ | Format-List`
- **ย้ายหรือคัดลอกแล้วสิทธิ์เปลี่ยน:** ย้ายไฟล์ในไดรฟ์เดียวกันมักคง ACL เดิม ส่วนคัดลอก หรือย้ายข้ามไดรฟ์ จะรับสิทธิ์สืบจากโฟลเดอร์ปลายทาง (ผู้เขียนสรุปจากความรู้ทั่วไป ควรทดสอบ)
- **ให้สิทธิ์ผ่านกลุ่ม ไม่ให้ทีละคน:** ดูแลง่ายกว่า และตรวจสอบย้อนหลังได้ชัดกว่า

## 4. เปรียบเทียบ Linux กับ Windows

| หัวข้อ | Linux (POSIX) | Windows (NTFS) |
|---|---|---|
| กลไกหลัก | 3 ขอบเขต (user, group, others) | ACL ที่มีรายการได้หลายรายการ |
| การห้ามโดยตรง | ไม่มี (ใช้การไม่ให้สิทธิ์) | มี explicit Allow และ Deny |
| การลบไฟล์ | ขึ้นกับสิทธิ์ w+x ของ **โฟลเดอร์แม่** | ให้หรือห้ามได้ที่ตัวไฟล์ได้โดยตรง |
| การสืบทอดสิทธิ์ | ไฟล์ใหม่ไม่สืบจากโฟลเดอร์แม่ ใช้ `umask` กำหนดตอนสร้าง (มี setgid ช่วยเรื่องกลุ่ม) | สืบจากโฟลเดอร์แม่อัตโนมัติ |
| สิทธิ์รัน | บิต x ชัดเจน | ขึ้นกับนามสกุล (.exe .bat .ps1) และสิทธิ์ Read & Execute |
| เครื่องมือ | `ls -l`, `chmod`, `chown`, `getfacl` | `icacls`, `Get-Acl`, แท็บ Security |

> **ควรรู้:** Linux ยุคใหม่รองรับ POSIX ACL (`getfacl`, `setfacl`) ให้ระบุผู้ใช้เพิ่มเติมนอกเหนือเจ้าของและกลุ่มเดียวได้ ทำให้ความต่างกับ Windows แคบลง

## ข้อจำกัดของโมเดลที่เรียนมา (อย่าอ้างเกินจริง)

`rwx` และ ACL เป็น **DAC (Discretionary Access Control)** คือ "เจ้าของวัตถุเป็นผู้ตัดสินใจเองว่าจะให้ใคร" ซึ่งเรียบง่ายแต่ไม่ครบทุกกรณี ควรรู้ว่าอะไรอยู่นอกขอบเขตของมัน

| ข้อจำกัด | อธิบาย | ใช้อะไรเสริม |
|---|---|---|
| **root / Administrator** ผ่าน DAC เกือบทั้งหมด | ใครได้ root ก็ข้ามบิต `rwx` ได้ (Linux ใช้ capability เช่น CAP_DAC_OVERRIDE) | แยก capability, `sudo` เฉพาะคำสั่ง, MAC |
| เจ้าของแจกสิทธิ์ได้ตามใจ | ผู้ใช้ที่ถูกหลอกให้ `chmod 777` ไฟล์ตัวเอง ระบบไม่ขวาง | MAC (SELinux, AppArmor) บังคับนโยบายที่เจ้าของแก้ไม่ได้ |
| ตรวจเฉพาะตอน `open()` | fd ที่เปิดค้างอยู่ไม่ถูกเพิกถอนเมื่อ `chmod` ภายหลัง | ปิดโปรเซสที่ถือ fd, จัดวงจรชีวิตของ credential |
| ระดับเจ้าของ-กลุ่ม-คนอื่นหยาบ | ให้ผู้ใช้ที่ 2 เข้าถึงโดยไม่สร้างกลุ่มใหม่ไม่ได้ | POSIX ACL (`setfacl`) ซึ่งเพิ่ม **mask** ที่ทำให้ `chmod g` ไปเปลี่ยนสิทธิ์สูงสุดของรายการ ACL ทุกรายการด้วย |
| สิทธิ์ไฟล์ไม่ครอบทั้งการกระทำ | ไฟล์ที่ `rw-` ก็ยังถูกป้องกันด้วยตัวเลือกอื่นได้ เช่นไฟล์ที่ตั้ง `chattr +i` (immutable) แก้ไม่ได้แม้เป็น root จนกว่าจะปลดแฟลก | `chattr`, mount option `ro` / `noexec` / `nosuid` |
| เครือข่ายเปลี่ยนความหมายของ uid | บน NFS ที่ไม่ใช้ Kerberos เซิร์ฟเวอร์เชื่อ uid ที่ลูกข่ายส่งมา, `root_squash` จึงแปลง root ของลูกข่ายเป็นผู้ใช้ไม่มีสิทธิ์ | Kerberos, `root_squash` |
| สิทธิ์ NTFS ≠ ความลับทางกายภาพ | คนที่บูตเครื่องด้วยระบบอื่นอ่านดิสก์ได้โดยไม่ผ่านการตรวจ ACL | เข้ารหัสดิสก์ (BitLocker, LUKS) |

หลักคิดสรุป: สิทธิ์ไฟล์ปกป้องจาก **โปรเซสและผู้ใช้ที่ทำงานอยู่ภายใต้ OS ที่ไว้ใจได้** เท่านั้น ถ้าผู้โจมตีได้ root, ได้ kernel หรือได้ตัวดิสก์ สิทธิ์ไฟล์ไม่ช่วยอะไร ต้องมีมาตรการชั้นอื่นประกอบ (defense in depth)

## มุมมองด้าน Security

### แมปการโจมตีที่เกิดจากสิทธิ์ผิดพลาด กับกลไกที่เพิ่งเรียน

ตารางนี้เชื่อมความเสี่ยงจริงกลับไปยังกลไกในบท (เพื่อการป้องกันและตรวจสอบระบบของตัวเอง)

| สถานการณ์ผิดพลาด | ทำไมจึงอันตราย (กลไก) | ป้องกัน / ตรวจ |
|---|---|---|
| ไบนารี setuid-root ที่มีช่องโหว่ หรือไฟล์ setuid ที่ผู้ใช้ทั่วไปแก้ได้ | euid = 0 ตลอดโปรเซส ถ้าโค้ดถูกควบคุมก็ได้ root (หัวข้อ 2.2) | ลด setuid ให้น้อยที่สุด, `find / -perm -4000 -type f`, mount `nosuid` |
| โฟลเดอร์ที่ทุกคนเขียนได้แต่ไม่มี sticky bit | ลบหรือเปลี่ยนชื่อไฟล์ของคนอื่นได้ เพราะการลบคือการแก้ไดเรกทอรี และเปิดทางให้โจมตีด้วย symlink race ในไฟล์ชั่วคราว | ตั้ง `chmod +t`, เปิด `fs.protected_symlinks` (หลายดิสโทรเปิดเป็นค่าเริ่มต้น) |
| สคริปต์ที่ root รัน (เช่น cron) แต่ผู้ใช้ทั่วไปเขียนไฟล์หรือ **โฟลเดอร์ระหว่างทาง** ได้ | ใครแก้สคริปต์ได้ = สั่งรันคำสั่งด้วยสิทธิ์ root ผู้เขียนไฟล์เท่ากับมีสิทธิ์ของผู้รัน | `namei -l` ตรวจ **ทุกชั้น** ของพาธ, ให้เจ้าของเป็น root และไม่มี `w` ของ group/others |
| กุญแจ SSH, `.env`, ไฟล์สำรองที่ 644 | ทุกบัญชีบนเครื่อง (รวมโปรเซสของบริการที่ถูกเจาะ) อ่านความลับได้ | 600 / 640, `umask 077` สำหรับบริการ, ตรวจด้วย `find -perm -004` |
| (Windows) โฟลเดอร์ของบริการหรือโปรแกรมที่รันเป็น SYSTEM ให้ Users มี Modify/Write | ผู้ใช้ทั่วไปแทนที่ไฟล์ปฏิบัติการหรือ DLL ที่บริการจะโหลด แล้วโค้ดนั้นรันด้วยสิทธิ์สูง | `icacls` ตรวจว่า Users มีแค่ `(RX)`, หลีกเลี่ยง `Everyone:(F)` |
| (Windows) Deny ซ้อนกันหลายชั้น หรือเปลี่ยนลำดับ ACE เอง | ลำดับไม่ canonical ทำให้ผลต่างจากที่คาด ไล่ยาก ผู้ดูแลเผลอเปิดช่อง | ใช้ Allow ผ่านกลุ่ม, เครื่องมือมาตรฐานเรียง ACE ให้ถูกต้องเอง |
| permission creep: ย้ายแผนกแต่สิทธิ์เก่าไม่ถูกถอน | สะสมสิทธิ์เกินจำเป็น ผู้โจมตีที่ยึดบัญชีได้ได้ประโยชน์เต็มที่ | ทบทวนสมาชิกกลุ่มเป็นรอบ ใช้รูปแบบ role-based group |

### หลักปฏิบัติ

- **หลักสิทธิ์น้อยที่สุด (least privilege):** ให้เท่าที่ต้องใช้ ไม่ใช้ `chmod 777` หรือ Everyone: Full Control เป็นทางลัดแก้ปัญหา มันแก้อาการแต่เปิดช่องโหว่ เมื่อเจอ Permission denied ให้หาสาเหตุ (หัวข้อ 2.3) แทนการเปิดกว้าง
- **ไฟล์ลับต้องปิดแน่น:** กุญแจ SSH ส่วนตัว 600 และ `~/.ssh` 700 ไฟล์ตั้งค่าที่มีรหัสผ่าน (เช่น `.env`) ไม่ควรให้คนอื่นอ่านได้ ไฟล์รหัสผ่านระบบ `/etc/shadow` ปิดจากผู้ใช้ทั่วไป
- **ตรวจ setuid และไฟล์ที่ใครก็เขียนได้:** `find / -perm -4000` และ `find / -perm -0002 -type f` (ผลที่ไม่คาดคิดคือสัญญาณเตือน) การใช้ umask เข้มสำหรับบริการช่วยกันของใหม่เปิดกว้างโดยไม่ตั้งใจ
- **ให้สิทธิ์ผ่านกลุ่ม และทบทวนเป็นระยะ:** เมื่อพนักงานย้ายแผนก สิทธิ์เก่าที่ค้างอยู่ (permission creep) คือความเสี่ยง
- **Deny ใช้อย่างระมัดระวัง:** กฎ Deny ที่ซับซ้อนทำให้ไล่ปัญหายาก ควรใช้ Allow ให้ชัดและเรียบง่าย
- **อย่าทำงานประจำด้วยบัญชีสิทธิ์สูง:** พิมพ์ผิดคำสั่งเดียวภายใต้ root หรือ Administrator ไม่มีอะไรหยุด
- **ระวัง `chmod -R` และ `icacls /T`:** คำสั่งแบบ recursive แก้ทั้งต้นไม้ในครั้งเดียว ผิดพลาดแล้วกู้ยาก (ไฟล์ปกติก็จะได้ x ไปด้วย) ควรสำรอง ACL ก่อน เช่น `getfacl -R` หรือ `icacls พาธ /save acl.txt /T`

| `./script.sh` แล้ว Permission denied | ไฟล์ไม่มี x | `ls -l` ดู แล้ว `chmod u+x script.sh` (หรือรัน `bash script.sh` ซึ่งต้องการแค่ r) |
| SSH ขึ้นว่ากุญแจ ถูกเปิดกว้างเกินไป (too open) แล้วไม่ยอมใช้ | กุญแจส่วนตัวสิทธิ์ 644 ที่คนอื่นอ่านได้ | `chmod 600 key.pem` และ `chmod 700 ~/.ssh` |
| เว็บขึ้น 403 Forbidden | ผู้ใช้เว็บเซิร์ฟเวอร์ (เช่น www-data) ไม่มี x ในบางโฟลเดอร์ของพาธ หรือไม่มี r ที่ไฟล์ | `namei -l พาธ` ดูทุกชั้น ปรับให้พอดี ไม่ใช้ 777 |
| เพิ่มผู้ใช้เข้ากลุ่มแล้วยังเข้าไฟล์ไม่ได้ | เซสชันเดิมยังไม่รับสมาชิกกลุ่มใหม่ | ออกจากระบบแล้วเข้าใหม่ (หรือ `newgrp`) ตรวจด้วย `id` |
| เป็นเจ้าของไฟล์แต่ลบไม่ได้ | ไม่มี w+x บนโฟลเดอร์แม่ หรือโฟลเดอร์มี sticky bit และเจ้าของไฟล์คนละคน | `ls -ld โฟลเดอร์แม่` |
| `sudo echo x > ไฟล์` แล้ว Permission denied | redirect ถูกเปิดโดยเชลล์ผู้ใช้ปกติ ไม่ใช่ sudo | `echo x \| sudo tee ไฟล์` (บทที่แล้ว) |
| Windows ขึ้น Access is denied ทั้งที่เป็น Administrator | ไม่ได้รันแบบ elevated หรือไม่มี ACE ของตัวเอง | เปิดแบบ Run as administrator, `takeown` แล้วแก้ด้วย `icacls` |
| เปิดโฟลเดอร์แชร์ในเครื่องเซิร์ฟเวอร์ได้ แต่ผ่านเครือข่ายไม่ได้ | สิทธิ์ share เข้มกว่า NTFS | ตรวจแท็บ Sharing ควบคู่กับ Security |
| ผู้ใช้อยู่กลุ่มที่ Allow แต่เข้าไม่ได้ | อยู่อีกกลุ่มที่มี Deny (explicit) | Effective Access หรือ `whoami /groups` ดูกลุ่มทั้งหมด |
| ย้ายไฟล์ไปโฟลเดอร์ใหม่แล้วสิทธิ์ไม่ตรงที่คาด | ย้ายคงสิทธิ์เดิม แต่คัดลอกรับสิทธิ์ใหม่ | ตรวจ ACL หลังย้าย/คัดลอก และตั้งสิทธิ์ใหม่ถ้าต้องการ |
| ใช้ `chmod -R 777` แล้ว SSH หรือบริการบางตัวปฏิเสธทำงาน | บริการตรวจสิทธิ์เข้ม (เช่น SSH ไม่ยอมรับกุญแจที่เปิดกว้าง) | คืนสิทธิ์ให้เหมาะสม กู้จากการสำรอง |

**แยกข้อความ error ที่หน้าตาคล้ายกันออกจากกัน** ข้อความต่างกันเพราะ kernel คืนรหัสผิดพลาด (errno) ต่างกัน ซึ่งบอกชั้นที่ล้มเหลว

| ข้อความ | errno | ความหมายเชิงกลไก | ตรวจอะไรต่อ |
|---|---|---|---|
| `Permission denied` | EACCES | การตรวจ DAC ไม่ผ่าน (บิต rwx / ACL / x ของโฟลเดอร์) | `id`, `namei -l` |
| `Operation not permitted` | EPERM | การกระทำนั้นต้องการ "ความเป็นเจ้าของ" หรือ capability ไม่ใช่แค่บิต เช่น `chmod` ไฟล์คนอื่น, `chown`, ไฟล์ immutable | `ls -l` ดูเจ้าของ, `lsattr` |
| `Read-only file system` | EROFS | ระบบไฟล์ถูก mount แบบอ่านอย่างเดียว (หรือถูกบังคับเพราะดิสก์มีปัญหา) สิทธิ์ไฟล์ไม่เกี่ยวเลย root ก็เขียนไม่ได้ | `mount`, `findmnt` |
| `No such file or directory` | ENOENT | ไม่มีชื่อนั้นในพาธ (หรือ symlink ชี้ว่าง) ไม่ใช่เรื่องสิทธิ์ | `ls`, `readlink -f` |
| `Text file busy` | ETXTBSY | พยายามเขียนทับไฟล์โปรแกรมที่กำลังรันอยู่ | ปิดโปรเซสก่อน |
| Windows `Access is denied` (ข้อผิดพลาด 5) | ERROR_ACCESS_DENIED | ไล่ ACE แล้ว granted ไม่ครบ หรือเจอ Deny | Effective Access, `whoami /groups` |
| Windows `The process cannot access the file because it is being used by another process` (32) | ERROR_SHARING_VIOLATION | มีโปรเซสอื่นเปิดไฟล์แบบไม่แชร์ ไม่ใช่เรื่อง ACL | Resource Monitor / `handle` |

## ตรวจความเข้าใจ

::reveal{question="โฟลเดอร์ /data มีสิทธิ์ r--r--r-- (444) ผู้ใช้ทั่วไปรัน ls /data แล้วพยายามเปิด /data/notes.txt จะเกิดอะไรขึ้น"}
เห็นรายชื่อไฟล์ได้เพราะมี r แต่เปิดไฟล์ข้างในไม่ได้ เพราะโฟลเดอร์ไม่มี x จึงเข้าถึงรายการข้างในไม่ได้เลย แม้ตัวไฟล์จะเปิดสิทธิ์อ่านไว้ (และ `ls -l` จะฟ้อง error เพราะอ่านรายละเอียดไม่ได้เช่นกัน)
::

::reveal{question="ผู้ใช้ Linux มี x บนโฟลเดอร์แต่ไม่มี r จะเกิดอะไรขึ้น"}
เข้าโฟลเดอร์ได้ และเปิดไฟล์ข้างในได้ถ้ารู้ชื่อเป๊ะและตัวไฟล์อนุญาต แต่ `ls` แสดงรายชื่อไม่ได้ เหมือนห้องที่มีประตูเปิดแต่ไม่มีรายชื่อติดหน้าห้อง
::

::reveal{question="ทำไมกฎ Deny แบบ explicit ถึงถูกตรวจก่อน Allow ใน NTFS"}
เพราะ Deny มีไว้ทำเป็นข้อยกเว้นเด็ดขาด ถ้าถูกตรวจทีหลัง Allow กฎห้ามจะไม่มีความหมาย ลำดับมาตรฐานคือ explicit Deny, explicit Allow, inherited Deny, inherited Allow จึงรับประกันว่ากฎที่ตั้งตรงที่วัตถุเอาชนะกฎที่สืบมา และ Deny ชนะ Allow ในระดับเดียวกัน (ข้อควรระวัง: explicit Allow จึงชนะ inherited Deny)
::

::reveal{question="umask ส่งผลต่อสิทธิ์เริ่มต้นของไฟล์ที่สร้างใหม่อย่างไร"}
umask คือชุดบิตที่ถูกปิดทิ้งจากสิทธิ์เริ่มต้น (ไฟล์ 666 โฟลเดอร์ 777) เช่น umask 022 ปิด w ของกลุ่มและคนอื่น ได้ไฟล์ 644 และโฟลเดอร์ 755 ไฟล์ใหม่ไม่ได้ x อัตโนมัติ
::

::reveal{question="Modify กับ Full Control ใน NTFS ต่างกันอย่างไร"}
Modify อ่าน เขียน รัน และลบไฟล์/โฟลเดอร์ได้ แต่ **เปลี่ยนสิทธิ์ (ACL) หรือยึดความเป็นเจ้าของไม่ได้** ส่วน Full Control ทำทุกอย่างได้ รวมถึงเปลี่ยนสิทธิ์และ take ownership
::

::reveal{question="โจทย์ 1: หาเลขฐานแปดของ -rwxr-x--- และสตริงของโหมด 640"}
`rwx` = 4+2+1 = 7, `r-x` = 4+0+1 = 5, `---` = 0 จึงเป็น **750** ส่วนโหมด 640 คือ 6 (`rw-`), 4 (`r--`), 0 (`---`) = `-rw-r-----`
::

::reveal{question="โจทย์ 2: ผู้ใช้อยู่กลุ่ม staff ไฟล์ /shared/budget.csv เป็น -rw-rw---- (root:staff) แต่โฟลเดอร์ /shared เป็น drwx------ (root:root) อ่านไฟล์ได้ไหม"}
**อ่านไม่ได้** เพราะการอ่านไฟล์ต้องผ่านทุกโฟลเดอร์ในพาธด้วยสิทธิ์ x โฟลเดอร์ /shared เป็นของ root:root และมีสิทธิ์เฉพาะเจ้าของ ผู้ใช้ทั่วไปไม่มี x จึงเข้าไม่ได้ ไฟล์ข้างในเปิดสิทธิ์ให้กลุ่มไว้ก็ไม่ช่วย ทางแก้ที่เหมาะสมคือเปลี่ยนกลุ่มของโฟลเดอร์เป็น staff แล้วตั้ง 750 (ไม่ใช่ 777)
::

::reveal{question="โจทย์ 3: Jordan อยู่กลุ่ม Engineering กับ Contractors โฟลเดอร์มี explicit Allow Read ให้ Engineering และ explicit Deny Read ให้ Contractors Jordan อ่านได้ไหม"}
**อ่านไม่ได้** เพราะทั้งสองเป็น explicit และ explicit Deny ถูกตรวจก่อน explicit Allow จึงตัดสินที่ Deny
::

::reveal{question="ทำไมการลบไฟล์บน Linux ไม่ต้องมีสิทธิ์ w ที่ตัวไฟล์"}
เพราะการลบคือการเอารายการชื่อออกจากไดเรกทอรี ซึ่งเป็นการแก้ตัวโฟลเดอร์ จึงต้องมี w และ x บนโฟลเดอร์แม่ (สิทธิ์ของไฟล์เองมีผลกับการอ่าน/เขียนเนื้อหาเท่านั้น) และถ้าโฟลเดอร์มี sticky bit ต้องเป็นเจ้าของไฟล์หรือเจ้าของโฟลเดอร์ด้วย
::

::reveal{question="โจทย์ 4 (คำนวณ): umask 027 ให้สิทธิ์ไฟล์ใหม่และโฟลเดอร์ใหม่เท่าไร และทำไม umask 033 ไม่ได้ 633"}
027 → ไฟล์ 666 AND NOT 027 = **640** โฟลเดอร์ 777 AND NOT 027 = **750** ส่วน 033 กับไฟล์: หลัก 6 = 110 และ NOT 3 = 100 ผล 100 = 4 จึงได้ **644** การเอา 666 − 033 = 633 ผิด เพราะ umask เป็นการปิดบิตด้วย AND ไม่ใช่การลบเลข และไฟล์ที่ไม่เคยขอ x (666 ไม่มี x) ก็ไม่มีทางได้ x
::

::reveal{question="โจทย์ 5 (คำนวณ): จาก 754 สั่ง chmod g+w,o-r จะได้โหมดอะไร และจาก 640 สั่ง chmod g=rx,o= จะได้อะไร"}
754 = rwx r-x r-- → `g+w` เปลี่ยนกลุ่มเป็น rwx (7) → `o-r` เอา r ของคนอื่นออก เหลือ `---` (0) ได้ **770** ส่วน 640 = rw- r-- --- → `g=rx` ตั้งกลุ่มเป็น r-x (5), `o=` ล้างสิทธิ์คนอื่น (0) ได้ **650** สังเกตว่า `=` แทนที่ทั้งชุด ส่วน `+`/`-` แก้เฉพาะบิตที่ระบุ
::

::reveal{question="โจทย์ 6 (ถอดรหัส): ls -l แสดง -rwSr--r-- และ drwxrwxrwt แต่ละอันบอกอะไร"}
`-rwSr--r--` คือ setuid ตั้งอยู่ (4644) แต่เจ้าของไม่มี x (`S` ตัวใหญ่) บิต setuid จึงไม่มีผล เพราะรันไม่ได้ เป็นสัญญาณว่าตั้งผิด `drwxrwxrwt` คือโฟลเดอร์ 1777 มี sticky bit (`t` ตัวเล็ก = others มี x ด้วย) ทุกคนสร้างไฟล์ได้ แต่ลบหรือเปลี่ยนชื่อได้เฉพาะไฟล์ของตัวเอง (เช่น `/tmp`)
::

::reveal{question="โจทย์ 7 (เชิงปริมาณ): ผู้ใช้ 1,000 คน ไฟล์ 1,000,000 ไฟล์ เก็บสิทธิ์ r/w/x เป็นตารางเต็ม กับเก็บโหมด 2 ไบต์ต่อไฟล์ ใช้ที่ต่างกันเท่าไร และสะท้อนอะไร"}
ตารางเต็ม = 1,000 × 1,000,000 × 3 บิต = 3 × 10⁹ บิต ≈ **375 MB** ส่วนโหมด 2 ไบต์/ไฟล์ = **2 MB** ต่างกันราว 187 เท่า (ตัวเลขจากสมมติฐานของโจทย์ ไม่ใช่การวัดจริง) สะท้อนว่า Unix ยอมแลกความละเอียดเพื่อบีบข้อมูลสิทธิ์ให้เล็กและตรวจเร็ว ด้วยการแทนผู้ใช้ทั้งหมดด้วย 3 ชนชั้น
::

::reveal{question="โจทย์ 8 (Windows): Modify กับ Full Control ต่างกันกี่บิตใน access mask และคือบิตอะไร"}
Full Control = 0x1F01FF, Modify = 0x1301BF ต่างกัน 0xC0040 ซึ่งแยกเป็น 3 บิต: **DELETE_CHILD (0x40)**, **WRITE_DAC (0x40000)** และ **WRITE_OWNER (0x80000)** คือลบรายการลูกโดยไม่ต้องมีสิทธิ์ลบของลูกเอง แก้ ACL และยึดความเป็นเจ้าของ ผู้ที่มีแค่ Modify จึงจัดการสิทธิ์เองไม่ได้
::

::reveal{question="โจทย์ 9 (วินิจฉัย): ผู้ดูแลเพิ่ม alex เข้ากลุ่ม staff แล้วแจ้งว่าใช้งานได้ แต่ alex ยังเปิดไฟล์ของกลุ่มไม่ได้ในเทอร์มินัลที่เปิดค้างไว้ ทำไม และมีวิธีแก้เร็วที่สุดอะไรบ้าง"}
credential ของเชลล์ถูกประกอบตอนล็อกอินและสืบทอดต่อโปรเซสลูก จึงไม่เห็นกลุ่มใหม่ ตรวจด้วย `id` (จะไม่เห็น staff) แก้โดยออกจากระบบแล้วเข้าใหม่ หรือเปิดเชลล์ที่ได้กลุ่มใหม่ด้วย `newgrp staff` (หรือ `su - alex`) บน Windows หลักการเดียวกันคือ access token สร้างตอน logon ต้อง log off/on
::

::reveal{question="โจทย์ 10 (กลไก): chmod 000 ไฟล์ที่โปรเซสหนึ่งเปิดไว้แล้ว โปรเซสนั้นยังอ่านต่อได้ไหม ทำไม"}
**ยังอ่านต่อได้** เพราะ kernel ตรวจสิทธิ์ตอน `open()` แล้วเก็บผลไว้ใน file descriptor ที่เปิดแบบอ่าน การ `read()` ต่อมาไม่ตรวจโหมดใหม่ ถ้าอยากตัดการเข้าถึงจริง ต้องปิดโปรเซสหรือให้มันปิดไฟล์ นี่คือข้อจำกัดของสิทธิ์แบบ DAC ที่ตรวจเฉพาะตอนเปิด
::

::reveal{question="โจทย์ 11 (วินิจฉัยเชิงกลไก): echo hi > /etc/motd ได้ Permission denied แต่ echo hi > /mnt/usb/a.txt ได้ Read-only file system ต่างกันอย่างไร"}
ข้อแรกเป็น **EACCES**: ผ่านการ mount ได้ แต่การตรวจ DAC ไม่ผ่าน (ผู้ใช้ปกติไม่มี w ที่ไฟล์) แก้ที่สิทธิ์หรือใช้ `sudo tee` ข้อสองเป็น **EROFS**: ระบบไฟล์ถูก mount แบบอ่านอย่างเดียว ไม่เกี่ยวกับบิตสิทธิ์ แม้เป็น root ก็เขียนไม่ได้ ต้อง remount หรือหาสาเหตุที่ระบบไฟล์ถูกบังคับอ่านอย่างเดียว
::

## แบบฝึกหัด

ทำในเครื่องทดลองหรือเครื่องเสมือน (VM) ไม่ใช่เครื่องใช้งานจริง และห้ามใช้ `chmod -R` กับพาธระบบ

1. **คำนวณ:** แปลง `-rwxr-xr-x`, `-rw-------`, `-rw-r-----` เป็นเลขฐานแปด และ 664, 711 เป็นสตริง
2. **ฝึกบน Linux:** สร้างโฟลเดอร์ `lab` และไฟล์ `lab/note.txt` แล้ว (ก) ดู `ls -l`, `stat -c %a` (ข) `chmod 600` แล้วลองอ่านด้วยบัญชีอื่นหรือ `sudo -u` บัญชีอื่น (ค) `chmod 000 lab` แล้วลอง `ls lab` กับ `cat lab/note.txt` ดูข้อความ error จากนั้นคืนค่าด้วย `chmod 755 lab`
3. **ทดลอง umask:** รัน `umask` แล้วสร้างไฟล์และโฟลเดอร์ใหม่ เทียบกับค่าที่ตัวคำนวณในบทนี้ให้ จากนั้นลอง `umask 077` ในเชลล์นั้นแล้วสร้างใหม่อีกครั้ง
4. **ฝึกบน Windows:** สร้างโฟลเดอร์ `C:\Lab` แล้วรัน `icacls C:\Lab` อ่านผลตามตารางในหัวข้อ 3.5 จากนั้นทดลอง `/inheritance:d` (บนโฟลเดอร์ทดลองเท่านั้น)
5. **โจทย์ความคิด:** เซิร์ฟเวอร์เว็บคืน 403 ทั้งที่ไฟล์ `/var/www/site/index.html` เป็น 644 คุณจะตรวจอะไรเป็นข้อแรก และด้วยคำสั่งใด

### ปฏิบัติการตรวจสิทธิ์บนเครื่องจริง (คำสั่งอ่านอย่างเดียว ปลอดภัย)

คำสั่งชุดนี้ **ไม่แก้อะไรเลย** รันบนเครื่องของคุณได้ (Linux/WSL) แล้วเทียบกับแนวคำตอบ

```bash
id                                         # ฉันคือใคร กลุ่มอะไร
namei -l "$HOME"                           # สิทธิ์ทุกชั้นของพาธบ้านฉัน
ls -ld /tmp /etc/passwd /etc/shadow        # ดูสิทธิ์ของสามเป้าหมาย
stat -c '%A %a %U:%G %n' /usr/bin/passwd   # setuid จริงหน้าตาอย่างไร
find /usr/bin -perm -4000 -type f 2>/dev/null | head   # รายการ setuid บางส่วน
getfacl "$HOME" 2>/dev/null | head         # มี ACL เพิ่มไหม
```

```powershell
whoami /groups                             # กลุ่มทั้งหมดใน token ของฉัน
icacls $env:USERPROFILE                    # ACL ของโฟลเดอร์ผู้ใช้
(Get-Acl C:\Windows).Access | Select-Object IdentityReference, FileSystemRights, AccessControlType, IsInherited -First 8
```

**แนวคำตอบ (ผลจริงขึ้นกับดิสโทรและเวอร์ชัน)**

- `ls -ld /tmp` ควรได้ `drwxrwxrwt` (1777) ให้ระบุว่า `t` คืออะไรและช่วยกันอะไร
- `/etc/passwd` มักเป็น 644 ใครก็อ่านได้ (ไม่มีรหัสผ่านจริงอยู่ในนั้นแล้ว) ส่วน `/etc/shadow` มักเป็น 640 `root:shadow` (Debian/Ubuntu) หรือ 000 (RHEL) ให้อธิบายว่าทำไม `passwd` ที่เป็น setuid จึงแก้ไฟล์นี้ได้ทั้งที่ผู้ใช้ทั่วไปอ่านไม่ได้ (กลไกหัวข้อ 2.2)
- `namei -l "$HOME"` ดูว่าชั้นไหนมี `x` ของ others บ้าง ถ้าบ้านเป็น `drwx------` ให้ทำนายว่า web server ที่รันเป็นผู้ใช้อื่นจะอ่านไฟล์ใต้บ้านได้ไหม (ไม่ได้ เพราะไม่มี x)
- Windows: ใน `IsInherited` ให้นับว่า ACE ที่ `True` มีกี่รายการ และบอกว่ารายการ `AccessControlType = Deny` (ถ้ามี) อยู่ตำแหน่งไหนของลำดับ canonical
- ท้าทาย: เขียนสรุป 3 บรรทัดว่า "ถ้าฉันเป็นผู้โจมตีที่ได้แค่บัญชีผู้ใช้ปกติ ไฟล์ไหนจากผลข้างบนที่ฉันอยากแก้ที่สุด และสิทธิ์ใดทำให้แก้ไม่ได้" (ฝึกมองจากมุมผู้ป้องกัน)

## สรุป

- สิทธิ์คือกฎว่าบัญชีไหนทำอะไรกับไฟล์ได้ Linux ใช้ owner/group/others × r/w/x (เลขฐานแปด 4/2/1) Windows ใช้ ACL ของ ACE ที่มี Allow/Deny
- kernel เลือกกลุ่มแรกที่ตรง (owner → group → others) แล้วหยุด และบนโฟลเดอร์ต้องมี `x` ตลอดพาธ
- `chmod` เปลี่ยนสิทธิ์ (เจ้าของหรือ root) `chown` เปลี่ยนเจ้าของ (root เท่านั้น) `umask` กำหนดสิทธิ์ของไฟล์ใหม่ special bits (setuid, setgid, sticky) ทำหน้าที่เฉพาะ และ setuid เกี่ยวกับความปลอดภัย
- NTFS มีสิทธิ์มาตรฐาน (Read, Write, Read & Execute, Modify, Full Control) และ inheritance ลำดับตรวจคือ explicit Deny, explicit Allow, inherited Deny, inherited Allow
- `icacls` ใช้ดูและแก้ ACL ส่วน `namei -l` และ `id` ช่วยไล่ปัญหาบน Linux
- ให้สิทธิ์น้อยที่สุดผ่านกลุ่ม และหลีกเลี่ยง `chmod 777`
- **หลักการ:** สิทธิ์ตอบคำถามเดียว (ใคร ทำอะไร กับอะไร) ตารางเต็มใหญ่เกิน Unix จึงบีบเป็น 9 บิตใน inode ส่วน NTFS เก็บ ACL ที่ละเอียดกว่าที่วัตถุ
- **กลไก:** kernel เดินพาธทีละชั้น (ต้อง `x`) แล้วเลือกชั้นแรกที่ตรง (owner → group → others) ตรวจตอน `open()` เท่านั้น credential เป็นสำเนา ณ ตอนล็อกอิน (เพิ่มกลุ่มแล้วต้องล็อกอินใหม่) Windows ไล่ ACE ตามลำดับ canonical จน granted ครบหรือเจอ Deny ที่ทับบิตที่ขอ
- **คำนวณ:** umask คือ AND-NOT (ไม่ใช่ลบ), `S`/`T` ตัวใหญ่ = บิตพิเศษที่ไม่มี x รองรับ, Modify ต่าง Full Control 3 บิต (DELETE_CHILD, WRITE_DAC, WRITE_OWNER)
- **ข้อจำกัด:** DAC ถูก root ข้ามได้ ตรวจแค่ตอนเปิด และไม่ป้องกันผู้ที่ได้ดิสก์ ต้องมี MAC, mount option, การเข้ารหัสดิสก์เสริม
- **วินิจฉัย:** แยก EACCES / EPERM / EROFS / ENOENT ออกจากกันก่อนแก้ เพราะแต่ละอย่างชี้ชั้นที่ล้มเหลวคนละชั้น
