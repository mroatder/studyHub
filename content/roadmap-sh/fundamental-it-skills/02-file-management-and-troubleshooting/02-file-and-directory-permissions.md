## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่าทำไมต้องมีสิทธิ์ และบอกความต่างของโมเดล Linux (3 กลุ่ม × 3 สิทธิ์) กับ Windows NTFS (ACL ที่มีหลายรายการ)
2. อ่านผล `ls -l` และแปลง `rwxr-xr--` เป็นเลขฐานแปด (754) และกลับกันได้
3. บอกได้ว่า r / w / x ต่างกันอย่างไรบน **ไฟล์** กับบน **โฟลเดอร์** และอธิบายกฎ "ต้องมี x ทุกโฟลเดอร์ตลอดทาง"
4. ใช้ `chmod`, `chown` ได้ถูก และอธิบาย `umask` ว่าส่งผลต่อไฟล์ใหม่อย่างไร
5. อธิบาย special bits (setuid, setgid, sticky) และเหตุที่ setuid เกี่ยวกับความปลอดภัย
6. อ่านผล `icacls` ออก (`(I)`, `(OI)`, `(CI)`, `(F)`, `(M)`, `(R)`) และเข้าใจ inheritance
7. ทำนายผลเมื่อมีทั้ง Allow และ Deny, explicit และ inherited ตามลำดับที่ Windows ตรวจ
8. ไล่แก้ปัญหา "Permission denied / Access is denied" อย่างเป็นขั้นตอนบนทั้งสองระบบ

## สรุปสั้น (TL;DR)

**สิทธิ์** คือกฎที่บอกว่าบัญชีไหนทำอะไรกับไฟล์ได้ **Linux** ให้ทุกไฟล์มีเจ้าของ (user), กลุ่ม (group) และ "คนอื่น" (others) แต่ละกลุ่มมีสิทธิ์อ่าน (r), เขียน (w), รัน (x) แทนด้วยเลข 4, 2, 1 จึงเขียนเป็น 754 ได้ kernel เลือกกลุ่มที่ตรงกับคุณ **ก่อนอันเดียว** แล้วหยุด **Windows NTFS** ใช้ **ACL** (รายการ ACE หลายรายการ ทั้ง Allow และ Deny) และมีการสืบทอดสิทธิ์จากโฟลเดอร์แม่ ลำดับตรวจคือ explicit Deny → explicit Allow → inherited Deny → inherited Allow เมื่อเจอ Permission denied ให้ถามสามข้อ: **ฉันคือใคร (กลุ่มอะไร)**, **สิทธิ์ของไฟล์เป็นอย่างไร**, **สิทธิ์ของทุกโฟลเดอร์ตามทางเป็นอย่างไร**

## เปรียบเทียบกับชีวิตจริง

นึกถึง **ตึกสำนักงานที่มีคีย์การ์ด**

| ตึกสำนักงาน | คอมพิวเตอร์ | ข้อสังเกต |
|---|---|---|
| เจ้าของห้อง / ผู้เช่าชั้นเดียวกัน / บุคคลภายนอก | user / group / others | ตรวจว่าคุณเป็นกลุ่มไหนก่อน แล้วใช้สิทธิ์ของกลุ่มนั้น |
| ประตูห้องกับตู้เอกสารในห้อง | สิทธิ์ของโฟลเดอร์กับไฟล์ | เข้าถึงตู้ได้ต่อเมื่อผ่านประตูทุกบานตามทางก่อน |
| บัตรเข้าได้หรือไม่ได้ | x บนโฟลเดอร์ | ไม่มีบัตรผ่านประตู เห็นป้ายบนประตูได้ แต่เข้าไปไม่ได้ |
| รายชื่อติดหน้าห้อง | r บนโฟลเดอร์ | ดูได้ว่าข้างในมีอะไรบ้าง แต่เปิดดูไม่ได้ถ้าไม่มีบัตร |
| ห้ามเด็ดขาด (บัญชีดำ) | Deny ใน NTFS | บัญชีดำชนะรายชื่ออนุญาตในระดับเดียวกัน |
| ผู้บริหารถืออภิสิทธิ์ผ่านได้ทุกประตู | root / Administrator | มีอำนาจสูงสุด จึงต้องใช้น้อยที่สุด |

## 1. โมเดลสิทธิ์ของ Linux

### 1.1 เจ้าของ กลุ่ม และคนอื่น

Linux ผูกทุกไฟล์และโฟลเดอร์เข้ากับ **เจ้าของ (owner)** หนึ่งบัญชี และ **กลุ่ม (group)** หนึ่งกลุ่ม เมื่อโปรแกรมของคุณขอเปิดไฟล์ kernel จะตรวจตามลำดับนี้ **แล้วหยุดที่ข้อแรกที่ตรง**

1. คุณเป็นเจ้าของไฟล์ → ใช้สิทธิ์ของ **user (u)**
2. ไม่ใช่เจ้าของ แต่อยู่ในกลุ่มของไฟล์ → ใช้สิทธิ์ของ **group (g)**
3. นอกจากนั้นทั้งหมด → ใช้สิทธิ์ของ **others (o)**

จุดที่คนมักพลาด: ถ้าคุณเป็นเจ้าของ จะถูกตรวจที่สิทธิ์ของเจ้าของเท่านั้น **ไม่สนใจว่ากลุ่มจะมีสิทธิ์มากกว่าหรือไม่** ไฟล์โหมด `060` (เจ้าของไม่มีสิทธิ์ กลุ่มอ่านเขียนได้) จึงทำให้เจ้าของเองเปิดไม่ได้ ข้อยกเว้นเดียวคือ **root** ซึ่งผ่านการตรวจสิทธิ์พื้นฐานเกือบทั้งหมด

### 1.2 สิทธิ์ r, w, x บนไฟล์และบนโฟลเดอร์

แต่ละกลุ่มมีสิทธิ์ย่อยสามอย่าง ความหมายต่างกันตามชนิดของสิ่งที่ถูกตรวจ

| สิทธิ์ | สัญลักษณ์ | บนไฟล์ | บนโฟลเดอร์ |
|---|---|---|---|
| อ่าน (Read) | r | ดูเนื้อหาไฟล์ | แสดงรายชื่อรายการข้างใน |
| เขียน (Write) | w | แก้ไขหรือล้างเนื้อหา | เพิ่ม เปลี่ยนชื่อ หรือลบรายการข้างใน |
| รัน (Execute) | x | สั่งรันเป็นโปรแกรมหรือสคริปต์ | เข้าโฟลเดอร์ (`cd`) และเข้าถึงรายการข้างใน |

สิ่งที่ต้นฉบับพูดสั้นแต่สำคัญมากในงานจริง

- **บนโฟลเดอร์ `x` สำคัญกว่าที่คิด:** ถ้าไม่มี `x` คุณเข้าถึงอะไรข้างในไม่ได้เลย แม้จะรู้ชื่อไฟล์และไฟล์ข้างในเปิดกว้าง `w` บนโฟลเดอร์ก็ใช้ไม่ได้ถ้าไม่มี `x` ควบคู่
- **โฟลเดอร์ที่มี r แต่ไม่มี x:** เห็นแค่ชื่อรายการ (และ `ls -l` จะฟ้อง error เพราะอ่านรายละเอียดไม่ได้) ส่วนโฟลเดอร์ที่มี x แต่ไม่มี r: เข้าถึงรายการได้ ถ้ารู้ชื่อเป๊ะ แต่ `ls` ไม่แสดงอะไร
- **สคริปต์ต้องมี r ด้วย:** ไฟล์สคริปต์ (เช่น `.sh`) ต้องมีทั้ง `r` และ `x` เพราะตัวแปลสคริปต์ต้องอ่านเนื้อหา ส่วนโปรแกรมที่คอมไพล์แล้วต้องการแค่ `x`

### 1.3 อ่านผลของ `ls -l`

```text
-rwxr-xr-- 1 alex devteam 4096 Apr 12 10:00 deploy.sh
```

| ส่วน | ตัวอย่าง | ความหมาย |
|---|---|---|
| ตัวที่ 1 | `-` | ชนิด: `-` ไฟล์ปกติ, `d` โฟลเดอร์, `l` ลิงก์สัญลักษณ์ |
| ตัวที่ 2-4 | `rwx` | สิทธิ์ของเจ้าของ (alex): อ่าน เขียน รัน |
| ตัวที่ 5-7 | `r-x` | สิทธิ์ของกลุ่ม (devteam): อ่านและรัน แก้ไม่ได้ |
| ตัวที่ 8-10 | `r--` | สิทธิ์ของคนอื่น: อ่านอย่างเดียว |
| ถัดมา | `alex devteam` | เจ้าของ และ กลุ่ม |

ใช้ `ls -ld ชื่อโฟลเดอร์` ถ้าอยากดูสิทธิ์ของตัวโฟลเดอร์เอง (ไม่ใช่ของข้างใน)

### 1.4 เลขฐานแปด

แต่ละสิทธิ์มีค่าประจำตัว r = 4, w = 2, x = 1 และ "ไม่มี" = 0 ของแต่ละกลุ่มให้ **บวกกัน** ได้เลขหนึ่งหลัก

| สตริง | คำนวณ | เลข |
|---|---|---|
| `rwx` | 4 + 2 + 1 | 7 |
| `rw-` | 4 + 2 + 0 | 6 |
| `r-x` | 4 + 0 + 1 | 5 |
| `r--` | 4 + 0 + 0 | 4 |
| `---` | 0 + 0 + 0 | 0 |

สามหลักเรียงเป็น เจ้าของ / กลุ่ม / คนอื่น ตัวอย่าง `754` = เจ้าของ 7 (`rwx`), กลุ่ม 5 (`r-x`), คนอื่น 4 (`r--`) ลองเปิดปิดสิทธิ์ในตัวคำนวณนี้ ดูตัวเลข สตริง และคำสั่ง `chmod` เปลี่ยนตาม และสลับดูความหมายบนไฟล์กับโฟลเดอร์

| 600 | เฉพาะเจ้าของ | ไฟล์ลับ เช่น กุญแจ SSH |
| 755 | เจ้าของทำได้ทุกอย่าง คนอื่นอ่านและรัน | โปรแกรม สคริปต์ โฟลเดอร์ทั่วไป |
| 700 | เฉพาะเจ้าของ | โฟลเดอร์ส่วนตัว เช่น `~/.ssh` |
| 750 / 640 | กลุ่มอ่าน (และรัน) ได้ คนอื่นไม่ได้เลย | งานร่วมกันในทีม |
| 777 | ทุกคนทำได้ทุกอย่าง | **หลีกเลี่ยง** |

### 1.5 `chmod` และ `chown`

คำสั่ง **`chmod`** เปลี่ยนสิทธิ์ รับได้สองแบบ แบบเลขฐานแปด หรือแบบสัญลักษณ์

```bash
chmod 750 deploy.sh      # ตั้งใหม่ทั้งหมด: เจ้าของ rwx, กลุ่ม r-x, คนอื่นไม่มีสิทธิ์
chmod u+x deploy.sh      # เพิ่ม x ให้เจ้าของ (u = user)
chmod go-w deploy.sh     # ถอน w ออกจากกลุ่มและคนอื่น (g = group, o = others)
chmod a+r notes.txt      # เพิ่ม r ให้ทุกคน (a = all)
```

คำสั่ง **`chown`** เปลี่ยนเจ้าของและกลุ่ม

```bash
sudo chown alex:devteam deploy.sh     # เจ้าของ alex กลุ่ม devteam
```

กฎสำคัญที่ต้นฉบับพูดถึง: การเปลี่ยน **เจ้าของ** ทำได้เฉพาะ root (ผ่าน `sudo`) ส่วนเพิ่มเติมที่ควรรู้: **เจ้าของไฟล์** เปลี่ยนสิทธิ์ (`chmod`) ของไฟล์ตัวเองได้ และเปลี่ยนกลุ่ม (`chgrp`) ไปเป็นกลุ่มที่ตัวเองสังกัดอยู่ได้ แต่ถ้าไม่ใช่เจ้าของจะรัน `chmod` ไม่ได้ ลองรันในเทอร์มินัลจำลอง

### 1.6 ลำดับการตรวจ และกฎ "ต้องผ่านทุกโฟลเดอร์ตลอดทาง"

## 2. เรื่องที่ควรรู้เพิ่ม: umask และ special bits

### 2.1 umask: ทำไมไฟล์ใหม่ได้สิทธิ์ 644

เมื่อสร้างไฟล์ใหม่ โปรแกรมขอสิทธิ์เริ่มต้น 666 (ไฟล์) หรือ 777 (โฟลเดอร์) แล้วระบบ **ปิดบิตที่ `umask` ระบุ** ค่า `umask 022` ปิด w ของกลุ่มและคนอื่น จึงได้ไฟล์ 644 และโฟลเดอร์ 755 ไฟล์ไม่ได้ x ตั้งแต่เกิด จึงต้อง `chmod +x` เองเสมอ ลองเปลี่ยนค่า umask

::umask-lab
::

ใช้คำสั่ง `umask` เฉยๆ เพื่อดูค่าปัจจุบัน ค่าเริ่มต้นขึ้นกับระบบ (มักเป็น 022 หรือ 002) บริการบนเซิร์ฟเวอร์ที่เก็บข้อมูลอ่อนไหวมักตั้ง umask เข้มขึ้น เช่น 027 หรือ 077 เพื่อให้ไฟล์ที่ถูกสร้างไม่เปิดกว้างโดยไม่ตั้งใจ

### 2.2 บิตพิเศษ 3 ตัว

นอกจาก rwx ยังมีบิตพิเศษ 3 ตัว (ข้อมูลส่วนนี้มาจากความรู้ทั่วไปของผู้เขียน ไม่ได้มาจากต้นฉบับ)

| บิต | เลข | แสดงใน ls -l | ทำอะไร |
|---|---|---|---|
| setuid | 4000 | `s` ที่ตำแหน่ง x ของเจ้าของ | โปรแกรมรันด้วยสิทธิ์ของ **เจ้าของไฟล์** ไม่ใช่ของผู้รัน เช่น `passwd` (`-rwsr-xr-x root`) ให้ผู้ใช้ธรรมดาเปลี่ยนรหัสผ่านที่เก็บในไฟล์ของ root ได้ |
| setgid | 2000 | `s` ที่ตำแหน่ง x ของกลุ่ม | บนโฟลเดอร์: ไฟล์ใหม่ข้างในได้กลุ่มเดียวกับโฟลเดอร์ (ช่วยงานทีม) |
| sticky | 1000 | `t` ที่ตำแหน่ง x ของคนอื่น | บนโฟลเดอร์: ลบหรือเปลี่ยนชื่อไฟล์ได้เฉพาะเจ้าของไฟล์ เจ้าของโฟลเดอร์ หรือ root เช่น `/tmp` (`drwxrwxrwt`) |

**ประเด็น Security:** ไฟล์ setuid ที่เจ้าของเป็น root ถ้ามีช่องโหว่ จะกลายเป็นทางยกระดับสิทธิ์ ผู้ดูแลระบบจึงตรวจรายการเป็นระยะ ด้วย `find / -perm -4000 -type f 2>/dev/null` (ดูว่ามีรายการแปลกที่ไม่ควรมีไหม)

## 3. สิทธิ์บน Windows (NTFS)

### 3.1 ACL และ ACE

Windows ที่ใช้ระบบไฟล์ **NTFS** ไม่เก็บสิทธิ์เป็นบิต 9 ตัว แต่ใช้ **Access Control List (ACL)** แนบกับไฟล์หรือโฟลเดอร์ ภายในมีรายการหลายรายการเรียกว่า **Access Control Entry (ACE)** แต่ละ ACE บอกสามอย่าง

1. **ผู้ที่ถูกกำหนด (security principal):** บัญชีผู้ใช้หรือกลุ่ม
2. **สิทธิ์:** เช่น Read, Write, Modify
3. **ชนิดกฎ:** Allow (อนุญาต) หรือ Deny (ห้าม)

ข้อได้เปรียบคือกำหนดละเอียดได้ เช่น ให้ทีม A แก้ได้ ทีม B อ่านได้ และห้ามกลุ่มผู้รับเหมาเขียน ในโฟลเดอร์เดียวกัน ซึ่งโมเดล Linux พื้นฐาน (เจ้าของ+กลุ่มเดียว) ทำไม่ได้โดยไม่ใช้ ACL เสริม

### 3.2 สิทธิ์มาตรฐาน (Standard permissions)

| สิทธิ์ | ทำอะไรได้ |
|---|---|
| Read | ดูเนื้อหา ดูคุณสมบัติ และดูรายการในโฟลเดอร์ |
| Write | เขียนทับ เขียนข้อมูล และสร้างไฟล์ใหม่ในโฟลเดอร์ |
| Read & Execute | อ่านและรันโปรแกรม/สคริปต์ |
| Modify | อ่าน เขียน รัน และลบไฟล์/โฟลเดอร์ |
| Full Control | ทำได้ทุกอย่าง และ **เปลี่ยนสิทธิ์ได้ กับยึดความเป็นเจ้าของ (take ownership) ได้** |

ความต่างสำคัญระหว่าง Modify กับ Full Control คือเรื่อง **การจัดการสิทธิ์เอง** ผู้ที่มีแค่ Modify แก้ไฟล์ได้ แต่เปลี่ยน ACL ไม่ได้ ใต้สิทธิ์มาตรฐานยังมี **สิทธิ์ละเอียด (special permissions)** อีกมาก เช่น Traverse folder, Delete subfolders and files ซึ่งเป็นองค์ประกอบของสิทธิ์มาตรฐานอีกที

### 3.3 การสืบทอดสิทธิ์ (Inheritance)

ไฟล์และโฟลเดอร์ย่อยที่สร้างใต้โฟลเดอร์แม่ **สืบทอดสิทธิ์จากแม่โดยอัตโนมัติ** ผู้ดูแลระบบตัดการสืบทอดได้เมื่อต้องการแยกโฟลเดอร์ที่ละเอียดอ่อน โดยเลือกได้สองทาง

- **แปลงสิทธิ์ที่สืบมาเป็น explicit** คงรายการเดิมไว้บนวัตถุนี้ (ใช้ `icacls ... /inheritance:d`)
- **ลบสิทธิ์ที่สืบมาทั้งหมด** แล้วเริ่ม ACL ว่างเปล่า (`/inheritance:r`) ระวัง: ถ้าไม่ได้เพิ่มรายการใหม่ จะไม่มีใครเข้าได้เลย

### 3.4 ลำดับที่ Windows ประเมินสิทธิ์

เมื่อมีหลาย ACE ที่เกี่ยวข้องกับคุณ Windows ตรวจตามลำดับ

1. **Explicit Deny** (สูงสุด)
2. **Explicit Allow**
3. **Inherited Deny**
4. **Inherited Allow** (ต่ำสุด)

> **จุดที่ต้นฉบับย่อไว้ และมักเข้าใจผิด:** "Deny ชนะ Allow เสมอ" จริงเมื่อทั้งสองอยู่ระดับเดียวกัน (explicit ทั้งคู่ หรือ inherited ทั้งคู่) แต่ **explicit Allow ชนะ inherited Deny** เพราะถูกตรวจก่อน (ข้อมูลนี้ผู้เขียนสรุปจากกฎมาตรฐานของ ACL ควรทดสอบในเครื่องจริงกับกรณีของคุณ) ตัวอย่างในต้นฉบับ: ผู้ใช้อยู่กลุ่ม Developers (Allow Modify) และ Contractors (Deny Modify) ถ้าสองรายการนี้เป็น explicit ทั้งคู่ ผลคือถูกปฏิเสธ

ลองสลับกลุ่มและสลับ explicit/inherited ดูว่าผู้ตัดสินเปลี่ยนไปอย่างไร

::acl-eval
::

### 3.5 ตรวจและแก้สิทธิ์ด้วย `icacls`

**`icacls`** ใช้ดูและแก้ ACL ได้จาก Command Prompt หรือ PowerShell

```powershell
icacls C:\Projects
```

ตัวอย่างผลลัพธ์ และความหมายของวงเล็บ

```text
C:\Projects NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
            BUILTIN\Administrators:(I)(OI)(CI)(F)
            CORP\Domain Users:(I)(OI)(CI)(M)
            CORP\Auditors:(I)(OI)(CI)(R)
```

| โค้ด | ความหมาย |
|---|---|
| `(I)` | สืบมาจากโฟลเดอร์แม่ (Inherited) |
| `(OI)` | Object Inherit: ใช้กับไฟล์ข้างใน |
| `(CI)` | Container Inherit: ใช้กับโฟลเดอร์ย่อยข้างใน |
| `(F)` | Full Control |
| `(M)` | Modify |
| `(RX)` | Read & Execute |
| `(R)` | Read |
| `(W)` | Write |

คำสั่งที่ใช้บ่อย

| ต้องการ | คำสั่ง |
|---|---|
| เพิ่มสิทธิ์ให้ Taylor โดยไม่แตะรายการอื่น | `icacls C:\Projects /grant Taylor:(W)` |
| ตั้งสิทธิ์ใหม่แทนของเดิมของ Taylor | `icacls C:\Projects /grant:r Taylor:(M)` |
| ห้ามกลุ่มหนึ่ง | `icacls C:\Projects /deny Contractors:(W)` |
| ลบรายการของ Taylor | `icacls C:\Projects /remove Taylor` |
| ตัดการสืบทอด คงสิทธิ์ที่สืบมาเป็น explicit | `icacls C:\Projects /inheritance:d` |
| ทำซ้ำลงทุกไฟล์ข้างใน | เติม `/T` ท้ายคำสั่ง |

> **หมายเหตุสำหรับ PowerShell:** วงเล็บของสิทธิ์มีความหมายพิเศษใน PowerShell ต้องครอบด้วยเครื่องหมายคำพูด เช่น `icacls C:\Projects /grant "Taylor:(W)"` ส่วน Command Prompt ใช้แบบไม่ครอบได้ (ผู้เขียนสรุปจากความรู้ทั่วไป ควรลองกับโฟลเดอร์ทดสอบ)

### 3.6 เรื่องที่ควรรู้เพิ่มบน Windows

- **สิทธิ์ของโฟลเดอร์แชร์ (share) กับ NTFS:** เมื่อเข้าถึงผ่านเครือข่าย Windows ใช้ผลที่ **เข้มกว่า** ระหว่างสองชั้น อาการ "เปิดในเครื่องได้ แต่ผ่านเครือข่ายไม่ได้" มักเป็นสิทธิ์ share
- **ผู้ดูแลระบบไม่ได้ผ่านเสมอ:** แม้เป็น Administrator ก็อาจโดน "Access is denied" เมื่อไม่ได้รันแบบ elevated (UAC) หรือเมื่อ ACL ไม่มีรายการของกลุ่มนั้น วิธีกู้: ยึดความเป็นเจ้าของด้วย `takeown /f พาธ /r` แล้วแก้ ACL ด้วย `icacls`
- **ดูผลรวมจริง:** แท็บ Properties > Security > Advanced > Effective Access บอกสิทธิ์สุทธิของผู้ใช้ที่เลือก ส่วน PowerShell ใช้ `Get-Acl พาธ | Format-List`
- **ย้ายหรือคัดลอกแล้วสิทธิ์เปลี่ยน:** ย้ายไฟล์ในไดรฟ์เดียวกันมักคง ACL เดิม ส่วนคัดลอก หรือย้ายข้ามไดรฟ์ จะรับสิทธิ์สืบจากโฟลเดอร์ปลายทาง (ผู้เขียนสรุปจากความรู้ทั่วไป ควรทดสอบ)
- **ให้สิทธิ์ผ่านกลุ่ม ไม่ให้ทีละคน:** ดูแลง่ายกว่า และตรวจสอบย้อนหลังได้ชัดกว่า

## 4. เปรียบเทียบ Linux กับ Windows

| หัวข้อ | Linux (POSIX) | Windows (NTFS) |
|---|---|---|
| กลไกหลัก | 3 ขอบเขต (user, group, others) | ACL ที่มีรายการได้หลายรายการ |
| การห้ามโดยตรง | ไม่มี (ใช้การไม่ให้สิทธิ์) | มี explicit Allow และ Deny |
| การลบไฟล์ | ขึ้นกับสิทธิ์ w+x ของ **โฟลเดอร์แม่** | ให้หรือห้ามได้ที่ตัวไฟล์ได้โดยตรง |
| การสืบทอดสิทธิ์ | ไฟล์ใหม่ไม่สืบจากโฟลเดอร์แม่ ใช้ `umask` กำหนดตอนสร้าง (มี setgid ช่วยเรื่องกลุ่ม) | สืบจากโฟลเดอร์แม่อัตโนมัติ |
| สิทธิ์รัน | บิต x ชัดเจน | ขึ้นกับนามสกุล (.exe .bat .ps1) และสิทธิ์ Read & Execute |
| เครื่องมือ | `ls -l`, `chmod`, `chown`, `getfacl` | `icacls`, `Get-Acl`, แท็บ Security |

> **ควรรู้:** Linux ยุคใหม่รองรับ POSIX ACL (`getfacl`, `setfacl`) ให้ระบุผู้ใช้เพิ่มเติมนอกเหนือเจ้าของและกลุ่มเดียวได้ ทำให้ความต่างกับ Windows แคบลง

## มุมมองด้าน Security

- **หลักสิทธิ์น้อยที่สุด (least privilege):** ให้เท่าที่ต้องใช้ ไม่ใช้ `chmod 777` หรือ Everyone: Full Control เป็นทางลัดแก้ปัญหา มันแก้อาการแต่เปิดช่องโหว่ เมื่อเจอ Permission denied ให้หาสาเหตุ (หัวข้อ 2.3) แทนการเปิดกว้าง
- **ไฟล์ลับต้องปิดแน่น:** กุญแจ SSH ส่วนตัว 600 และ `~/.ssh` 700 ไฟล์ตั้งค่าที่มีรหัสผ่าน (เช่น `.env`) ไม่ควรให้คนอื่นอ่านได้ ไฟล์รหัสผ่านระบบ `/etc/shadow` ปิดจากผู้ใช้ทั่วไป
- **ตรวจ setuid และไฟล์ที่ใครก็เขียนได้:** `find / -perm -4000` และ `find / -perm -0002 -type f` (ผลที่ไม่คาดคิดคือสัญญาณเตือน) การใช้ umask เข้มสำหรับบริการช่วยกันของใหม่เปิดกว้างโดยไม่ตั้งใจ
- **ให้สิทธิ์ผ่านกลุ่ม และทบทวนเป็นระยะ:** เมื่อพนักงานย้ายแผนก สิทธิ์เก่าที่ค้างอยู่ (permission creep) คือความเสี่ยง
- **Deny ใช้อย่างระมัดระวัง:** กฎ Deny ที่ซับซ้อนทำให้ไล่ปัญหายาก ควรใช้ Allow ให้ชัดและเรียบง่าย
- **อย่าทำงานประจำด้วยบัญชีสิทธิ์สูง:** พิมพ์ผิดคำสั่งเดียวภายใต้ root หรือ Administrator ไม่มีอะไรหยุด
- **ระวัง `chmod -R` และ `icacls /T`:** คำสั่งแบบ recursive แก้ทั้งต้นไม้ในครั้งเดียว ผิดพลาดแล้วกู้ยาก (ไฟล์ปกติก็จะได้ x ไปด้วย) ควรสำรอง ACL ก่อน เช่น `getfacl -R` หรือ `icacls พาธ /save acl.txt /T`

## ตรวจความเข้าใจ

::reveal{question="โฟลเดอร์ /data มีสิทธิ์ r--r--r-- (444) ผู้ใช้ทั่วไปรัน ls /data แล้วพยายามเปิด /data/notes.txt จะเกิดอะไรขึ้น"}
เห็นรายชื่อไฟล์ได้เพราะมี r แต่เปิดไฟล์ข้างในไม่ได้ เพราะโฟลเดอร์ไม่มี x จึงเข้าถึงรายการข้างในไม่ได้เลย แม้ตัวไฟล์จะเปิดสิทธิ์อ่านไว้ (และ `ls -l` จะฟ้อง error เพราะอ่านรายละเอียดไม่ได้เช่นกัน)
::

::reveal{question="ผู้ใช้ Linux มี x บนโฟลเดอร์แต่ไม่มี r จะเกิดอะไรขึ้น"}
เข้าโฟลเดอร์ได้ และเปิดไฟล์ข้างในได้ถ้ารู้ชื่อเป๊ะและตัวไฟล์อนุญาต แต่ `ls` แสดงรายชื่อไม่ได้ เหมือนห้องที่มีประตูเปิดแต่ไม่มีรายชื่อติดหน้าห้อง
::

::reveal{question="ทำไมกฎ Deny แบบ explicit ถึงถูกตรวจก่อน Allow ใน NTFS"}
เพราะ Deny มีไว้ทำเป็นข้อยกเว้นเด็ดขาด ถ้าถูกตรวจทีหลัง Allow กฎห้ามจะไม่มีความหมาย ลำดับมาตรฐานคือ explicit Deny, explicit Allow, inherited Deny, inherited Allow จึงรับประกันว่ากฎที่ตั้งตรงที่วัตถุเอาชนะกฎที่สืบมา และ Deny ชนะ Allow ในระดับเดียวกัน (ข้อควรระวัง: explicit Allow จึงชนะ inherited Deny)
::

::reveal{question="umask ส่งผลต่อสิทธิ์เริ่มต้นของไฟล์ที่สร้างใหม่อย่างไร"}
umask คือชุดบิตที่ถูกปิดทิ้งจากสิทธิ์เริ่มต้น (ไฟล์ 666 โฟลเดอร์ 777) เช่น umask 022 ปิด w ของกลุ่มและคนอื่น ได้ไฟล์ 644 และโฟลเดอร์ 755 ไฟล์ใหม่ไม่ได้ x อัตโนมัติ
::

::reveal{question="Modify กับ Full Control ใน NTFS ต่างกันอย่างไร"}
Modify อ่าน เขียน รัน และลบไฟล์/โฟลเดอร์ได้ แต่ **เปลี่ยนสิทธิ์ (ACL) หรือยึดความเป็นเจ้าของไม่ได้** ส่วน Full Control ทำทุกอย่างได้ รวมถึงเปลี่ยนสิทธิ์และ take ownership
::

::reveal{question="โจทย์ 1: หาเลขฐานแปดของ -rwxr-x--- และสตริงของโหมด 640"}
`rwx` = 4+2+1 = 7, `r-x` = 4+0+1 = 5, `---` = 0 จึงเป็น **750** ส่วนโหมด 640 คือ 6 (`rw-`), 4 (`r--`), 0 (`---`) = `-rw-r-----`
::

::reveal{question="โจทย์ 2: ผู้ใช้อยู่กลุ่ม staff ไฟล์ /shared/budget.csv เป็น -rw-rw---- (root:staff) แต่โฟลเดอร์ /shared เป็น drwx------ (root:root) อ่านไฟล์ได้ไหม"}
**อ่านไม่ได้** เพราะการอ่านไฟล์ต้องผ่านทุกโฟลเดอร์ในพาธด้วยสิทธิ์ x โฟลเดอร์ /shared เป็นของ root:root และมีสิทธิ์เฉพาะเจ้าของ ผู้ใช้ทั่วไปไม่มี x จึงเข้าไม่ได้ ไฟล์ข้างในเปิดสิทธิ์ให้กลุ่มไว้ก็ไม่ช่วย ทางแก้ที่เหมาะสมคือเปลี่ยนกลุ่มของโฟลเดอร์เป็น staff แล้วตั้ง 750 (ไม่ใช่ 777)
::

::reveal{question="โจทย์ 3: Jordan อยู่กลุ่ม Engineering กับ Contractors โฟลเดอร์มี explicit Allow Read ให้ Engineering และ explicit Deny Read ให้ Contractors Jordan อ่านได้ไหม"}
**อ่านไม่ได้** เพราะทั้งสองเป็น explicit และ explicit Deny ถูกตรวจก่อน explicit Allow จึงตัดสินที่ Deny
::

::reveal{question="ทำไมการลบไฟล์บน Linux ไม่ต้องมีสิทธิ์ w ที่ตัวไฟล์"}
เพราะการลบคือการเอารายการชื่อออกจากไดเรกทอรี ซึ่งเป็นการแก้ตัวโฟลเดอร์ จึงต้องมี w และ x บนโฟลเดอร์แม่ (สิทธิ์ของไฟล์เองมีผลกับการอ่าน/เขียนเนื้อหาเท่านั้น) และถ้าโฟลเดอร์มี sticky bit ต้องเป็นเจ้าของไฟล์หรือเจ้าของโฟลเดอร์ด้วย
::

## แบบฝึกหัด

ทำในเครื่องทดลองหรือเครื่องเสมือน (VM) ไม่ใช่เครื่องใช้งานจริง และห้ามใช้ `chmod -R` กับพาธระบบ

1. **คำนวณ:** แปลง `-rwxr-xr-x`, `-rw-------`, `-rw-r-----` เป็นเลขฐานแปด และ 664, 711 เป็นสตริง
2. **ฝึกบน Linux:** สร้างโฟลเดอร์ `lab` และไฟล์ `lab/note.txt` แล้ว (ก) ดู `ls -l`, `stat -c %a` (ข) `chmod 600` แล้วลองอ่านด้วยบัญชีอื่นหรือ `sudo -u` บัญชีอื่น (ค) `chmod 000 lab` แล้วลอง `ls lab` กับ `cat lab/note.txt` ดูข้อความ error จากนั้นคืนค่าด้วย `chmod 755 lab`
3. **ทดลอง umask:** รัน `umask` แล้วสร้างไฟล์และโฟลเดอร์ใหม่ เทียบกับค่าที่ตัวคำนวณในบทนี้ให้ จากนั้นลอง `umask 077` ในเชลล์นั้นแล้วสร้างใหม่อีกครั้ง
4. **ฝึกบน Windows:** สร้างโฟลเดอร์ `C:\Lab` แล้วรัน `icacls C:\Lab` อ่านผลตามตารางในหัวข้อ 3.5 จากนั้นทดลอง `/inheritance:d` (บนโฟลเดอร์ทดลองเท่านั้น)
5. **โจทย์ความคิด:** เซิร์ฟเวอร์เว็บคืน 403 ทั้งที่ไฟล์ `/var/www/site/index.html` เป็น 644 คุณจะตรวจอะไรเป็นข้อแรก และด้วยคำสั่งใด

## สรุป

- สิทธิ์คือกฎว่าบัญชีไหนทำอะไรกับไฟล์ได้ Linux ใช้ owner/group/others × r/w/x (เลขฐานแปด 4/2/1) Windows ใช้ ACL ของ ACE ที่มี Allow/Deny
- kernel เลือกกลุ่มแรกที่ตรง (owner → group → others) แล้วหยุด และบนโฟลเดอร์ต้องมี `x` ตลอดพาธ
- `chmod` เปลี่ยนสิทธิ์ (เจ้าของหรือ root) `chown` เปลี่ยนเจ้าของ (root เท่านั้น) `umask` กำหนดสิทธิ์ของไฟล์ใหม่ special bits (setuid, setgid, sticky) ทำหน้าที่เฉพาะ และ setuid เกี่ยวกับความปลอดภัย
- NTFS มีสิทธิ์มาตรฐาน (Read, Write, Read & Execute, Modify, Full Control) และ inheritance ลำดับตรวจคือ explicit Deny, explicit Allow, inherited Deny, inherited Allow
- `icacls` ใช้ดูและแก้ ACL ส่วน `namei -l` และ `id` ช่วยไล่ปัญหาบน Linux
- ให้สิทธิ์น้อยที่สุดผ่านกลุ่ม และหลีกเลี่ยง `chmod 777`
