## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **ไฟล์ประกอบด้วย 3 ส่วนที่เก็บแยกกัน** (ชื่อในไดเรกทอรี, inode/MFT, บล็อกข้อมูล) และ **hard link / link count** คืออะไร
2. ทำนายได้ว่าคำสั่ง create / read / update / delete แต่ละตัว **แตะส่วนไหนของดิสก์** และทำไมบางตัวเสร็จทันที บางตัวช้า
3. อธิบายว่า **ทำไม `sort data.txt > data.txt` ทำให้ไฟล์ว่าง** (เชลล์ตัดไฟล์ก่อนโปรแกรมจะรัน) และเลือกใช้ `>`, `>>`, `tee`, ไฟล์ชั่วคราว + `mv` ให้ถูก
4. อธิบายว่า **rename เป็นปฏิบัติการ atomic** ในดิสก์เดียวกัน และเหตุผลที่ย้ายข้ามดิสก์ต้อง "คัดลอกแล้วลบ"
5. อธิบายได้ว่า **การลบ = ลบชื่อ (unlink)** พื้นที่ถูกคืนเมื่อ link count เป็น 0 **และไม่มีโปรเซสเปิดอยู่** แล้ววินิจฉัยอาการ "ลบแล้วดิสก์ยังเต็ม"
6. คำนวณเวลา/พื้นที่ของการย้าย คัดลอก และอ่านไฟล์ใหญ่ได้ (พร้อมระบุว่าเป็นค่าประมาณ)
7. ใช้ชุดเครื่องมือ **ซ้อมก่อนลบ** (`ls` pattern เดียวกัน, `-WhatIf`, `rm -i`, `find` ก่อน `-delete`) และอ่านข้อความ error ทั่วไปออก
8. อธิบายความเสี่ยง Security ที่เกิดกับ CRUD: **การลบ/ตัด log, ไฟล์ชั่วคราวที่เดาชื่อได้ (symlink attack), ransomware, การลบที่ไม่ลบจริง**

## สรุปสั้น (TL;DR)

**CRUD = Create, Read, Update, Delete** แต่คำสั่งเดียวกันทำงานต่างกันมากเมื่อมองลงไปที่ดิสก์

- **ไฟล์ = ชื่อ + inode (metadata) + บล็อกข้อมูล:** ชื่ออยู่ในไดเรกทอรี ชี้ไปหา inode และ inode ชี้ไปหาบล็อก
- **เปลี่ยนชื่อ/ย้ายในดิสก์เดียวกัน = แก้รายการชื่อ** เสร็จทันที atomic ไม่ว่าไฟล์ใหญ่แค่ไหน
- **`>` ถูกเชลล์ทำก่อนโปรแกรมรัน:** ไฟล์ถูกตัดว่างตั้งแต่ยังไม่เริ่มอ่าน (ต้นเหตุของ `cmd f > f`)
- **ลบ = ลบชื่อ** บล็อกเดิมไม่ถูกล้าง พื้นที่คืนเมื่อไม่มีชื่อและไม่มีโปรเซสเปิดอยู่ ใน CLI ไม่มีถังขยะ
- **ซ้อมก่อนทำลาย:** ดูขอบเขตด้วย pattern เดียวกันก่อนเสมอ และมีสำรองข้อมูล

## เปรียบเทียบกับชีวิตจริง

นึกถึง **ห้องสมุดที่มีบัตรรายการ**

| ห้องสมุด | ไฟล์ในคอมพิวเตอร์ | ข้อสังเกต |
|---|---|---|
| บัตรรายการ (ชื่อหนังสือ → เลขชั้น) | ไดเรกทอรี (ชื่อ → inode) | หนังสือเล่มเดียวมีบัตรได้หลายใบ = hard link |
| ใบประวัติเล่ม (ผู้แต่ง ขนาด วันที่ลงทะเบียน ตำแหน่งบนชั้น) | inode / ระเบียน MFT | ประวัติไม่ได้บอกชื่อ ชื่อมาจากบัตรรายการ |
| เนื้อหาหนังสือบนชั้น | บล็อกข้อมูล | |
| เปลี่ยนป้ายบนบัตร หรือย้ายบัตรไปตู้อื่น | rename / mv | หนังสือไม่ถูกแตะ |
| ถ่ายเอกสารทั้งเล่ม | cp | ได้เล่มอิสระใหม่ ใช้พื้นที่เพิ่ม |
| ฉีกบัตรทิ้ง | rm (unlink) | หนังสือยังอยู่บนชั้นจนกว่าจะไม่มีบัตรเหลือ และไม่มีใครถืออ่านอยู่ |
| คนยังถือหนังสืออ่านอยู่ตอนฉีกบัตร | ไฟล์ถูกลบแต่โปรเซสยังเปิดอยู่ | ห้องสมุดเอาชั้นไปใช้ไม่ได้จนกว่าเขาจะคืน |

## ภาพรวม

บทนี้เริ่มจาก "ไฟล์คืออะไรจริงๆ" แล้วเดินตามตัวอักษรของ CRUD โดยทุกขั้นถามว่า **คำสั่งนี้แตะอะไรบนดิสก์ และถ้าพลาดจะเสียหายแค่ไหน** จบด้วยการซ้อมก่อนลบและมุมมอง Security

## 1. ไฟล์คืออะไรกันแน่

### 1.1 สามส่วนที่เก็บแยกกัน

| ส่วน | เก็บอะไร | ที่อยู่ (Linux ext4 / Windows NTFS) |
|---|---|---|
| **ชื่อ** | ข้อความชื่อไฟล์ | รายการในไดเรกทอรี (ไดเรกทอรีก็คือไฟล์พิเศษที่เป็นตาราง "ชื่อ → inode") |
| **Metadata** | ขนาด เจ้าของ สิทธิ์ เวลา และตำแหน่งของบล็อก | **inode** / ระเบียนใน **MFT** (ดูบทที่ 3-4) |
| **ข้อมูล** | เนื้อหาจริง | **บล็อก** บนดิสก์ (กรณีไฟล์เล็กมากบน NTFS อาจอยู่ในระเบียน MFT เลย) |

ผลที่ตามมาจากการแยกกัน (สำคัญมากสำหรับทั้งบท):

- ชื่ออยู่ **นอก** inode จึง **เปลี่ยนชื่อ/ย้ายได้โดยไม่แตะข้อมูล**
- inode หนึ่งตัวมี **หลายชื่อ** ได้ เรียกว่า **hard link** inode เก็บ **link count** (จำนวนชื่อที่ชี้มา)
- ไฟล์จะถูก "ลบจริง" (คืนบล็อก) เมื่อ **link count = 0 และไม่มีโปรเซสเปิดอยู่ (open count = 0)** เท่านั้น

สิ่งที่ควรสังเกตจากแบบจำลอง: เปลี่ยนชื่อ/ย้ายในดิสก์เดียวกัน **บล็อกไม่ขยับ** ย้ายข้ามดิสก์ต้องคัดลอกก่อนแล้วลบ ส่วนการลบคือเอารายการออกและบอกว่าบล็อกว่าง (เส้นประ) ข้อมูลเดิมไม่ถูกล้าง

> **ข้อจำกัด:** hard link ใช้ข้ามระบบไฟล์ไม่ได้ (เพราะเลข inode มีความหมายแค่ในระบบไฟล์เดียว) และปกติสร้างกับไดเรกทอรีไม่ได้ ส่วน **symbolic link (symlink)** เป็นไฟล์พิเศษที่เก็บ "พาธ" ชี้ไปอีกที่ ข้ามระบบไฟล์ได้ แต่จะ "ชำรุด" ถ้าปลายทางหาย NTFS มีทั้งสองแบบ (`New-Item -ItemType HardLink` / `SymbolicLink`)

## 2. Create: สร้างไฟล์และโฟลเดอร์

### 2.1 ทำไมการสร้างไฟล์จึงเร็วและไม่เท่ากับการเขียนข้อมูล

การสร้างไฟล์ใหม่ทำ 2 อย่าง: (1) จองหนึ่ง **inode** (2) เพิ่มรายการ **ชื่อ → inode** ในไดเรกทอรี ไฟล์ว่างจึงใช้บล็อกข้อมูล **0 บล็อก** มีแต่ metadata ข้อมูลถูกจองภายหลังเมื่อมีการเขียนจริง (system call ที่เกี่ยวคือ `open()` พร้อมแฟลกสร้าง)

### 2.2 บน Windows (PowerShell)

```powershell
New-Item -ItemType Directory -Path "C:\logs"
New-Item -ItemType File -Path "C:\logs\app.log"
"Application started" > "C:\logs\app.log"        # สร้างพร้อมข้อความ (ทับถ้ามี)
```

### 2.3 บน Linux (Bash)

```bash
mkdir /var/log/app                        # โฟลเดอร์
touch /var/log/app/app.log                # ไฟล์ว่าง (ถ้ามีอยู่แล้ว แค่อัปเดตเวลา)
echo "Application started" > /var/log/app/app.log
mkdir -p /tmp/a/b/c                       # สร้างโฟลเดอร์แม่ที่ยังไม่มีให้ด้วย
```

### 2.4 กับดักและรายละเอียดที่ควรรู้

- **`touch` ไม่ทำลายเนื้อหา** เปลี่ยนแค่เวลา ส่วน **`New-Item -ItemType File -Force` กับไฟล์ที่มีอยู่จะสร้างทับจนว่าง** (ควรทดสอบกับไฟล์ทดลองก่อน) ถ้าไม่ใส่ `-Force` จะ error แทน ซึ่งปลอดภัยกว่า
- **`echo "" > file` ไม่ใช่ไฟล์ว่างจริง** มี 1 ไบต์ (ตัวขึ้นบรรทัดใหม่) ถ้าต้องการว่างจริงใช้ `: > file` หรือ `touch`
- **สร้างแบบไม่ทับ:** Bash ตั้ง `set -o noclobber` ให้ `>` ปฏิเสธไฟล์ที่มีอยู่ (บังคับทับด้วย `>|`) การสร้างแบบ "ต้องเป็นไฟล์ใหม่เท่านั้น" ในระดับระบบเรียกว่า `O_EXCL`
- **สิทธิ์เริ่มต้น** ของไฟล์ใหม่มาจาก `umask` (บทที่ 7)
- **Encoding ของ PowerShell:** `>` ใน **Windows PowerShell 5.1 เขียนเป็น UTF-16** ส่วน PowerShell 7 เขียนเป็น UTF-8 ไฟล์ที่ส่งไปให้เครื่องมืออื่นอาจอ่านเพี้ยน ใช้ `Out-File -Encoding utf8` หรือ `Set-Content -Encoding utf8`
- **ไฟล์ชั่วคราวต้องใช้ `mktemp`** ไม่ใช่ชื่อที่เดาได้ (เหตุผลดูหัวข้อ 7.2)

## 3. Read: อ่านไฟล์

### 3.1 หลักการ: การอ่านไม่แก้ไฟล์ แต่ "ราคา" ต่างกัน

การอ่านเปิดไฟล์แล้วดึงไบต์ตามตำแหน่งอ่านปัจจุบัน (file offset) **ไม่แก้เนื้อหา** (จึงปลอดภัยที่สุดใน CRUD ควรทำก่อนทุกครั้งที่ต้องตรวจสอบ) แต่เครื่องมือต่างกันที่ **อ่านมากแค่ไหน**

| เครื่องมือ | อ่านอะไรจากดิสก์ | เหมาะกับ |
|---|---|---|
| `cat` / `Get-Content` | ทั้งไฟล์ ตั้งแต่ต้นจนจบ | ไฟล์สั้น (ไฟล์ยาวท่วมหน้าจอ) |
| `head -n N` / `-TotalCount N` | แค่ช่วงต้น แล้วหยุด | ดูหัวตาราง/ไฟล์ |
| `tail -n N` / `-Tail N` | กระโดดไปท้ายไฟล์ (seek) แล้วอ่านถอยหลังเท่าที่ต้อง | เหตุการณ์ล่าสุดใน log |
| `less` | เปิดแล้วอ่านทีละหน้าตามที่เลื่อนดู ไม่ต้องโหลดทั้งไฟล์ | อ่านเอกสารยาว ค้นหาด้วย `/` |

**ตัวอย่างเชิงปริมาณ (ค่าประมาณ):** log ขนาด 10 GiB บน SSD อ่านต่อเนื่องที่ราว 500 MiB/s การ `cat` ทั้งไฟล์ต้องใช้เวลา ≈ 10 × 1024 ÷ 500 ≈ **20 วินาที** (และท่วมหน้าจอ) ส่วน `tail -n 20` กระโดดไปท้ายไฟล์อ่านเพียงไม่กี่ KiB เสร็จในเสี้ยววินาทีไม่ว่าไฟล์จะใหญ่แค่ไหน

### 3.2 คำสั่ง

```powershell
Get-Content -Path "C:\logs\app.log"                  # ทั้งไฟล์
Get-Content -Path "C:\logs\app.log" -TotalCount 10   # 10 บรรทัดแรก
Get-Content -Path "C:\logs\app.log" -Tail 10         # 10 บรรทัดท้าย
Get-Content -Path "C:\logs\app.log" -Tail 10 -Wait   # ตามดูแบบสด
```

```bash
cat file ; less file ; head -n 20 file ; tail -n 20 file ; tail -f file
```

### 3.3 `tail -f` กับ log rotation และไฟล์ที่ถูกลบ

`tail -f` ตามดู **ไฟล์ที่เปิดไว้ (file descriptor)** ไม่ใช่ **ชื่อ** ระบบมักหมุนเวียน log: เปลี่ยนชื่อ `app.log` เป็น `app.log.1` แล้วสร้าง `app.log` ใหม่ ผลคือ `tail -f` ยังตามไฟล์เก่า (ชื่อใหม่ `app.log.1`) จึงเงียบไปทั้งที่ระบบกำลังเขียนไฟล์ใหม่ ใช้ **`tail -F`** (F ใหญ่) ที่ติดตาม **ชื่อ** และเปิดใหม่เมื่อชื่อชี้ไฟล์อื่น ความต่างนี้จะอธิบายเรื่อง "ลบแล้วพื้นที่ไม่คืน" ในหัวข้อ 5 ด้วย

**ข้อควรรู้เรื่องหน่วยความจำ:** `cat` ไม่โหลดไฟล์เข้า RAM ทั้งก้อน (ส่งออกเป็นชิ้นๆ) แต่ใน PowerShell ถ้าเก็บผลลง **ตัวแปร** (`$x = Get-Content ไฟล์ใหญ่`) จะโหลดทุกบรรทัดเข้า RAM จึงนิยมใช้ `-Tail` / `-TotalCount` หรือส่งต่อผ่านท่อ

## 4. Update: แก้ไข ย้าย และคัดลอก

### 4.1 `>` กับ `>>` และ "ใครเป็นคนเปิดไฟล์"

- **`>`** เปิดไฟล์พร้อม **ตัดให้ว่าง (truncate)** แล้วค่อยเขียน
- **`>>`** เปิดไฟล์แบบ **ต่อท้าย (append)** เนื้อหาเดิมอยู่ครบ

::redirect-lab
::

หลักจำ: **เก็บสะสมใช้ `>>` เริ่มใหม่ใช้ `>`** ความผิดพลาดตัวอักษรเดียวนี้ทำให้ log หลายวันหายได้

**ทำไม `>>` ปลอดภัยกว่าในกรณีหลายโปรแกรมเขียนพร้อมกัน:** การเขียนแบบ append ให้ระบบวางตำแหน่ง "ต่อท้ายไฟล์" เป็นขั้นเดียวกับการเขียน (บนระบบไฟล์ในเครื่อง) หลายโปรเซสจึงเขียนต่อท้ายไฟล์เดียวกันได้โดยไม่ทับกัน ต่างจากการเขียนทับ ที่แต่ละคนอาจเขียนที่ตำแหน่งเดียวกัน

### 4.2 กับดักสำคัญ: เชลล์ตัดไฟล์ก่อนโปรแกรมจะรัน

จากบทที่ 5 เราเห็นว่าเชลล์ทำงาน **ก่อน** โปรแกรม การ redirect ก็เช่นกัน: เชลล์เปิด (และตัดให้ว่าง) ไฟล์ปลายทาง **ก่อน** เรียกโปรแกรม นำไปสู่ความผิดพลาดคลาสสิก `sort data.txt > data.txt`

::seq-diagram{:actors='[{"label":"คุณ","icon":"👤"},{"label":"เชลล์","icon":"🐚"},{"label":"sort","icon":"📄"},{"label":"data.txt","icon":"💾"}]' :messages='[{"from":0,"to":1,"label":"พิมพ์ sort data.txt > data.txt","note":"เจตนา: เรียงบรรทัดในไฟล์แล้วเก็บกลับที่เดิม"},{"from":1,"to":3,"label":"เปิด data.txt สำหรับเขียน พร้อมตัดให้ว่าง","note":"เชลล์จัดการ stdout ก่อน fork ไฟล์ปลายทางถูกตัดเหลือ 0 ไบต์ทันที ข้อมูลเดิมในไฟล์ถูกทิ้ง (บล็อกถูกปล่อย)"},{"from":1,"to":2,"label":"fork/exec sort โดยให้ stdout = data.txt","note":"sort เพิ่งเริ่มทำงาน"},{"from":2,"to":3,"label":"sort เปิด data.txt เพื่ออ่าน","note":"ไฟล์ว่างแล้ว sort จึงอ่านได้ 0 บรรทัด"},{"from":3,"to":2,"label":"ส่งข้อมูล 0 ไบต์","note":"","dashed":true},{"from":2,"to":3,"label":"เขียนผลเรียง (ว่างเปล่า)","note":"ไม่มีอะไรจะเขียน"},{"from":3,"to":0,"label":"ผลลัพธ์: data.txt ว่าง ข้อมูลหาย","note":"ไม่มี error ใดๆ เพราะทุกขั้นถูกต้องตามกติกา","dashed":true}]' caption="redirect ทำก่อนคำสั่งทำงาน จึงอ่านและเขียนไฟล์เดียวกันด้วย > ไม่ได้"}
::

**ทางที่ถูก (เรียงจากทั่วไปไปเฉพาะทาง):**

1. เขียนผลลงไฟล์ชั่วคราวในโฟลเดอร์เดียวกัน แล้ว `mv` ทับ: `sort data.txt > data.tmp && mv data.tmp data.txt`
2. ใช้ตัวเลือกที่แก้ในที่เดิมอย่างปลอดภัย เช่น `sort -o data.txt data.txt` (sort อ่านครบก่อนเขียน) หรือ `sed -i`
3. ใช้ `sponge` (จากชุด moreutils) ถ้ามีติดตั้ง

#### ทำไม "ไฟล์ชั่วคราว + `mv`" จึงเป็นรูปแบบมาตรฐานของการแก้ไฟล์อย่างปลอดภัย

เพราะ `rename()` ในระบบไฟล์เดียวกันเป็น **ปฏิบัติการ atomic**: ผู้ที่เปิดชื่อเป้าหมายจะเห็น "ไฟล์เก่าทั้งไฟล์" หรือ "ไฟล์ใหม่ทั้งไฟล์" ไม่เคยเห็นสถานะครึ่งๆ กลางๆ และถ้าไฟดับระหว่างเขียนไฟล์ชั่วคราว ไฟล์เดิมยังสมบูรณ์ ตัวแก้ไขข้อความและโปรแกรมที่ดีทำแบบนี้ (โดยบังคับเขียนลงดิสก์ด้วย `fsync` ก่อน rename เพื่อกันข้อมูลค้างในแคช) ต่างจากการเขียนทับตรงๆ ที่ไฟดับกลางคันทิ้งไฟล์ที่ครึ่งใหม่ครึ่งเก่าไว้

### 4.3 stdout, stderr และกับดัก `sudo`

โปรแกรมมีช่องออกสองช่อง: **stdout** (ผลปกติ, fd 1) กับ **stderr** (ข้อผิดพลาด, fd 2) `>` ส่งเฉพาะ stdout

| ต้องการ | Bash | PowerShell |
|---|---|---|
| เก็บ stdout | `cmd > out.txt` | `cmd > out.txt` |
| เก็บ stderr | `cmd 2> err.txt` | `cmd 2> err.txt` |
| รวมสองช่อง | `cmd > all.txt 2>&1` | `cmd *> all.txt` |
| ทิ้ง error | `cmd 2> /dev/null` | `cmd 2> $null` |

**กับดัก `sudo` + redirect:** `sudo echo x > /etc/hosts` **ล้มเหลว** (Permission denied) เพราะ `>` ถูกเปิดโดย **เชลล์ของคุณ** (สิทธิ์ผู้ใช้ปกติ) ก่อน sudo ทำงาน sudo ครอบเฉพาะ `echo` วิธีแก้คือให้โปรแกรมที่รันด้วย sudo เป็นคนเปิดไฟล์: `echo x | sudo tee -a /etc/hosts` (`-a` คือต่อท้าย ถ้าไม่ใส่จะทับ)

**ตัวขึ้นบรรทัดใหม่:** Windows ใช้ CRLF (2 ตัวอักษร) Linux ใช้ LF (1 ตัวอักษร) สคริปต์ที่เขียนบน Windows แล้วรันบน Linux อาจ error `bad interpreter: /bin/bash^M` แก้ด้วย `dos2unix` หรือ `sed -i 's/\r$//' script.sh`

### 4.4 ย้ายและเปลี่ยนชื่อ

เพราะชื่ออยู่ในไดเรกทอรี "เปลี่ยนชื่อ" = แก้ชื่อในรายการ "ย้ายในดิสก์เดียวกัน" = เอารายการไปไว้ในไดเรกทอรีอื่น (system call เดียวคือ `rename()`) บล็อกข้อมูลไม่ขยับ

```powershell
Move-Item "C:\logs\app.log" "C:\logs\app-old.log"      # เปลี่ยนชื่อ
Move-Item "C:\logs\app-old.log" "C:\archive\"          # ย้าย
Rename-Item app.log app-old.log                        # เปลี่ยนชื่ออย่างเดียว
```

```bash
mv app.log app-old.log ; mv app-old.log /var/archive/
```

**ย้ายข้ามระบบไฟล์ (คนละดิสก์/พาร์ทิชัน):** `rename()` ทำไม่ได้ (เลข inode ไม่ข้ามระบบไฟล์) ระบบคืนข้อผิดพลาด `EXDEV` ("Invalid cross-device link") และ `mv` สลับไปใช้ **คัดลอกทั้งไฟล์ แล้วลบต้นฉบับ** แทน ผลคือ

| | ในระบบไฟล์เดียวกัน | ข้ามระบบไฟล์ |
|---|---|---|
| เวลา | เกือบทันที ไม่ขึ้นกับขนาด | ตามขนาด ÷ ความเร็วเขียน |
| พื้นที่ว่างที่ต้องมี | ไม่ต้อง | ต้องมีที่ปลายทางเท่าขนาดไฟล์ |
| ถ้าพลาดกลางคัน | ไม่เสียหาย (atomic) | ต้นฉบับยังอยู่จนกว่าคัดลอกจะเสร็จ (ปลายทางอาจเหลือไฟล์ที่ไม่ครบ) |

**ตัวอย่างคำนวณ (ค่าประมาณ):** ย้ายไฟล์ 50 GiB ไปดิสก์อื่นที่เขียนได้ 150 MiB/s ใช้เวลา ≈ 50 × 1024 ÷ 150 ≈ **341 วินาที (ราว 5.7 นาที)** และระหว่างนั้นมีข้อมูลสองชุดพร้อมกัน ส่วนการเปลี่ยนชื่อไฟล์ขนาดเท่ากันในดิสก์เดียวกันใช้เวลาไม่ถึงมิลลิวินาที

### 4.5 คัดลอก

คัดลอก = อ่านต้นฉบับแล้ว **เขียนข้อมูลใหม่ในบล็อกใหม่** ได้ไฟล์อิสระ (ต่างจาก hard link) ใช้พื้นที่เพิ่มเท่าเดิม (ระบบไฟล์บางแบบมี reflink ที่แชร์บล็อกจนกว่าจะมีการแก้ แต่เป็นรายละเอียดขั้นสูง)

```powershell
Copy-Item "C:\logs\app.log" "C:\backup\app.log"
Copy-Item "C:\logs\" "C:\backup\logs\" -Recurse
```

```bash
cp app.log backup.log
cp -r logs backup          # ทั้งโฟลเดอร์ (ถ้าไม่ใส่ -r: omitting directory)
cp -a data data.bak        # รักษาสิทธิ์ เจ้าของ เวลา (เหมาะกับสำรอง)
```

- **ทับโดยไม่ถาม:** `cp`, `mv`, `Copy-Item`, `Move-Item` ทับไฟล์ปลายทางชื่อซ้ำ ใช้ `-i` (ถามก่อน) หรือ `-n` (ไม่ทับ)
- **ปลายทางเป็นโฟลเดอร์ที่มีอยู่แล้ว:** `cp -r logs backup` จะได้ `backup/logs` ซ้อนอีกชั้น แทนที่จะรวมเนื้อหา ตรวจด้วย `ls` ทุกครั้ง ถ้าต้องการรวมเนื้อหา ใช้ `cp -r logs/. backup/`
- **สำเนาไม่ใช่สำรองจริงถ้าอยู่ดิสก์เดียวกัน:** ดิสก์เสียก็เสียทั้งคู่

## 5. Delete: ลบ

### 5.1 ลบ = unlink: ลบ "ชื่อ" ไม่ใช่ข้อมูล

คำสั่งลบเรียก `unlink()` ซึ่ง **ลบรายการชื่อในไดเรกทอรี และลด link count ลง 1** จากนั้นระบบตรวจ: ถ้า **link count = 0 และไม่มีโปรเซสเปิดไฟล์อยู่** จึงคืน inode กับบล็อกให้ว่าง (เนื้อหายังอยู่บนดิสก์จนกว่าจะถูกเขียนทับ) ถ้ายังมีโปรเซสเปิดอยู่ พื้นที่ยัง **ไม่คืน** จนกว่าโปรเซสนั้นจะปิดไฟล์

บน Windows ส่วนใหญ่ไฟล์ที่โปรแกรมเปิดอยู่จะ **ลบไม่ได้** (error "in use") จึงไม่เจออาการนี้บ่อยเท่า Linux

### 5.2 คำสั่งลบ

```powershell
Remove-Item "C:\logs\app.log"
Remove-Item "C:\logs\" -Recurse -Force        # โฟลเดอร์ทั้งก้อน
```

```bash
rm app.log
rmdir logs               # ลบเฉพาะโฟลเดอร์ว่าง
rm -rf logs              # โฟลเดอร์พร้อมทุกอย่าง
```

- `Remove-Item` กับโฟลเดอร์ไม่ว่าง **ถามยืนยัน** ถ้าไม่ใส่ `-Recurse` ; `-Force` ข้ามไฟล์ซ่อน/อ่านอย่างเดียว
- `-r` ลงทุกชั้น ; `-f` ไม่ถามและข้ามข้อผิดพลาด **ชุด `-rf` อันตรายที่สุด**
- **ไม่ผ่านถังขยะ:** ถังขยะเป็นฟีเจอร์ของ GUI (File Explorer ย้ายไฟล์ไป Recycle Bin) คำสั่ง `Remove-Item`/`rm` เรียก unlink ตรง
- **ต้องมีสิทธิ์เขียนที่ "โฟลเดอร์แม่"** ไม่ใช่ที่ตัวไฟล์ เพราะการลบคือการแก้รายการในไดเรกทอรี (บทที่ 7)
- `rm -rf /` ถูกกันไว้ใน GNU rm รุ่นใหม่ (`--preserve-root`) แต่ `rm -rf /*` ซึ่งเชลล์ขยายเป็นทุกโฟลเดอร์ใต้ราก **ไม่ถูกกัน**

**ต้นทุนของการลบ:** `rm -rf` ต้องเดินต้นไม้ แล้วเรียก unlink ทีละไฟล์ ลบไฟล์เล็ก 1 ล้านไฟล์ = 1 ล้านครั้งของการแก้ไดเรกทอรีและ inode ใช้เวลาหลายสิบวินาทีถึงนาที (ค่าประมาณ ขึ้นกับดิสก์และระบบไฟล์) ในขณะที่ลบไฟล์ใหญ่ไฟล์เดียวขนาดเท่ากันใช้เวลาน้อยกว่ามาก เพราะเป็นการคืนบล็อกครั้งเดียว

### 5.5 ชุดเครื่องมือซ้อมก่อนลบ

หลักการเดียว: **ใช้ pattern เดียวกันเป๊ะ ดูขอบเขตก่อน แล้วค่อยเปลี่ยนคำสั่งเป็นลบ**

| เครื่องมือ | ทำอะไร | ตัวอย่าง |
|---|---|---|
| `echo` / `ls` นำหน้า | เห็นว่า glob ขยายเป็นอะไรบ้าง | `ls /tmp/*.log` แล้วกดลูกศรขึ้น แก้ `ls` เป็น `rm` |
| `-WhatIf` | แสดงว่าจะทำอะไรโดยไม่ทำจริง | `Remove-Item C:\logs\* -Recurse -WhatIf` |
| `-Confirm` | ถามทีละรายการ | `Remove-Item C:\logs\* -Confirm` |
| `rm -i` / `rm -I` | ถามทีละไฟล์ / ถามครั้งเดียวถ้าลบมาก | `rm -ri old_logs` |
| `find` ก่อน `-delete` | ดูรายการตามเงื่อนไข | `find /tmp/logs -name '*.old' -type f` แล้วต่อ `-delete` |
| สำรองก่อน | กันพลาด | `cp -a data data.bak` |

**ลบแล้วกู้ได้ไหม:** ไม่มีถังขยะ ทางที่เชื่อถือได้คือสำรอง โปรแกรมกู้ข้อมูลทำงานได้เพราะเนื้อหายังไม่ถูกทับ จึงควรหยุดเขียนดิสก์ทันที แต่บน **SSD ที่ใช้ TRIM** ข้อมูลมักถูกล้างเร็วจนกู้ยากกว่า HDD มาก และ **ลบแล้วไม่ใช่ลบจริง:** ข้อมูลลับเมื่อทิ้งดิสก์ต้องเขียนทับหรือเข้ารหัสดิสก์ตั้งแต่ต้น

## 7. มุมมองด้าน Security

### 7.1 แผนที่ภัยคุกคาม ↔ กลไกที่เรียน

| ภัย | ทำไมเกิดได้ (กลไก) | ป้องกันด้วย | ข้อจำกัด |
|---|---|---|---|
| ผู้บุกรุกลบ/ตัด log ลบหลักฐาน | `> /var/log/auth.log` ตัดไฟล์ให้ว่างทันที ผู้ที่มีสิทธิ์เขียนทำได้เสมอ | ส่ง log ไปเก็บเครื่องอื่นแบบต่อท้ายอย่างเดียว, สิทธิ์ไฟล์ log จำกัด | ผู้ที่ได้ root ในเครื่องเดียวกันแก้ได้ทุกอย่าง จึงต้องเก็บนอกเครื่อง |
| สคริปต์ใช้ `>` ผิด ข้อมูลหาย | เชลล์ตัดไฟล์ก่อนโปรแกรมรัน (หัวข้อ 4.2) | ทดสอบสคริปต์บนข้อมูลจำลอง ใช้ไฟล์ชั่วคราว + `mv` | |
| ตัวแปรไม่ครอบคำพูดแล้วลบผิดชิ้น | แยกคำซ้ำ (บทที่ 5) `rm $f` กับ `f="My Old Files"` ลบ 3 ชื่อ | `rm "$f"`, `set -u`, ซ้อมด้วย `echo` | |
| **Symlink attack บนไฟล์ชั่วคราว** | ผู้โจมตีสร้าง symlink ชื่อ `/tmp/report.tmp` ชี้ไป `/etc/passwd` ล่วงหน้า แล้วสคริปต์ที่สิทธิ์สูงเขียนไฟล์ชื่อนั้น จะเขียนทับไฟล์ปลายทางจริง (เพราะเดาชื่อได้และตรวจก่อน-ใช้ทีหลังมีช่วงเวลาให้แทรก: ช่องโหว่แบบ TOCTOU) | สร้างไฟล์ชั่วคราวด้วย `mktemp` (ชื่อสุ่มและสร้างแบบ O_EXCL), ไม่ใช้ชื่อที่เดาได้ใน `/tmp` | |
| **Ransomware** | อ่านไฟล์ → เขียนเวอร์ชันเข้ารหัส → ลบ/ทับต้นฉบับ ใช้ CRUD ธรรมดาทั้งหมด | สำรองข้อมูลที่ตัดขาดจากเครื่อง (offline/immutable) สิทธิ์น้อยที่สุด | การลบธรรมดาไม่ช่วยกู้ ต้องมีสำรองก่อนเกิดเหตุ |
| ข้อมูลลับยังอยู่หลัง "ลบ" | unlink ไม่ล้างบล็อก | เข้ารหัสดิสก์ตั้งแต่ต้น (BitLocker/LUKS) หรือเขียนทับก่อนทิ้ง | เขียนทับบน SSD อาจไม่การันตีเพราะการกระจายการสึกหรอ จึงพึ่งการเข้ารหัสมากกว่า |
| ใช้ root/Administrator ทำงานประจำ | ระบบไม่ปฏิเสธการลบผิดที่ | ผู้ใช้ปกติ + `sudo` เฉพาะคำสั่งที่จำเป็น | `sudo` ไม่ครอบ redirect (หัวข้อ 4.3) |

## 8. ตัวอย่างการวิเคราะห์ปัญหาในงาน IT Support

หลักคิด: ถามว่า **คำสั่งนั้นแตะส่วนไหน (ชื่อ / inode / บล็อก)** และ **เชลล์ทำอะไรก่อน** แล้วอาการจะอธิบายได้

| อาการ | สาเหตุเชิงกลไก (ทำไมถึงเกิด) | วิธีตรวจ/แก้ |
|---|---|---|
| log ที่สะสมหลายวัน เหลือบรรทัดเดียว | สคริปต์ใช้ `>` ตัดไฟล์ทุกครั้ง | แก้เป็น `>>` กู้จากสำรอง |
| `sort f > f` ได้ไฟล์ว่าง | เชลล์ตัดไฟล์ก่อน sort อ่าน | `sort f > f.tmp && mv f.tmp f` หรือ `sort -o f f` |
| `sudo echo x > /etc/y` Permission denied | redirect เปิดโดยเชลล์สิทธิ์ผู้ใช้ปกติ | `echo x \| sudo tee /etc/y` |
| ลบ log ใหญ่แล้ว `df` ยังเต็ม | โปรเซสยังถือ inode (open count > 0) | `lsof +L1` แล้ว restart บริการ หรือใช้ `: > file` แทนลบ |
| `tail -f` เงียบ ทั้งที่ระบบยังทำงาน | log ถูก rotate `-f` ตามไฟล์เดิมที่เปลี่ยนชื่อ | ใช้ `tail -F` |
| `mv` ไฟล์ใหญ่ช้ามาก | ปลายทางคนละระบบไฟล์ จึงเป็นคัดลอก+ลบ | ตรวจด้วย `df` ว่าอยู่ดิสก์เดียวกันไหม ใช้ `rsync` ถ้าต้องการ resume |
| `mv` ข้ามดิสก์ error "No space left" | ต้องมีที่ว่างปลายทางเท่าขนาดไฟล์ | เคลียร์ที่ว่างหรือเปลี่ยนปลายทาง |
| `rm folder` → `Is a directory` | `rm` ไม่ลบโฟลเดอร์ | ว่าง → `rmdir` ไม่ว่าง → `rm -r` (ซ้อมก่อน) |
| `rmdir` → `Directory not empty` | มีรายการข้างใน (ตั้งใจกันพลาด) | `ls -A` ดู แล้วค่อยตัดสิน |
| ลบไฟล์ได้ทั้งที่ไฟล์อ่านอย่างเดียว | สิทธิ์ลบอยู่ที่โฟลเดอร์แม่ ไม่ใช่ตัวไฟล์ | ตรวจสิทธิ์โฟลเดอร์แม่ (บทที่ 7) |
| คัดลอกโฟลเดอร์แล้วได้ `backup/logs` ซ้อน | ปลายทางเป็นโฟลเดอร์ที่มีอยู่แล้ว | ตรวจด้วย `ls` ; ใช้ `cp -r logs/. backup/` |
| ไฟล์จาก PowerShell เปิดบน Linux เพี้ยน | `>` ของ 5.1 เขียน UTF-16 | `-Encoding utf8` |
| สคริปต์ `bad interpreter ^M` | ตัวขึ้นบรรทัดแบบ CRLF | `dos2unix` |
| `rm -rf` ใน PowerShell error | `rm` เป็น alias ของ `Remove-Item` แฟลกคนละชุด | `Remove-Item -Recurse -Force` |

### 9.3 แบบฝึกหัดบนเครื่องของคุณ (ในโฟลเดอร์ทดลองเท่านั้น: Windows `$env:TEMP`, Linux `/tmp`)

1. สร้างโฟลเดอร์ `lab_test` เข้าไปสร้าง `notes.txt` ด้วย `>` แล้วต่อบรรทัดด้วย `>>` อ่านด้วย `Get-Content` / `cat`
2. (Linux) `ln notes.txt hard.txt` แล้วรัน `ls -li` เทียบเลข inode และ link count จากนั้น `rm notes.txt` ตรวจว่า `hard.txt` ยังอ่านได้
3. (Linux) ทดลอง `sort` ตามหัวข้อ 4.2 กับไฟล์ **สำเนา**: `sort copy.txt > copy.txt` ดูผล แล้วกู้ด้วยสำเนาที่เหลือ ก่อนทำให้สร้างสำเนาสำรองไว้ก่อน
4. `Rename-Item` / `mv` เปลี่ยนชื่อ แล้วเทียบ inode ก่อน-หลังใน Linux (`ls -li`) ควรเป็นเลขเดิม
5. ซ้อมลบด้วย `Remove-Item lab_test -Recurse -WhatIf` หรือ `ls lab_test` แล้วลบจริง
6. (ท้าทาย, Linux) `tail -f` ไฟล์หนึ่งในหน้าต่างที่หนึ่ง อีกหน้าต่างเขียน `echo x >> file`, `mv file file.1`, `echo y > file` ดูว่า `tail -f` และ `tail -F` ต่างกันอย่างไร

::reveal{question="แนวคำตอบข้อ 2, 3 และ 6"}
**ข้อ 2:** หลัง `ln` ทั้งสองชื่อมีเลข inode เดียวกันและ link count = 2 หลัง `rm notes.txt` link count เหลือ 1 และ `hard.txt` ยังอ่านเนื้อหาได้ครบ แสดงว่า rm ลบชื่อ ไม่ใช่ข้อมูล
**ข้อ 3:** ได้ไฟล์ว่าง (0 ไบต์) เพราะเชลล์ตัดไฟล์ก่อน sort อ่าน ไม่มี error ใดๆ
**ข้อ 6:** `tail -f` ยังตามไฟล์เดิมที่ถูกเปลี่ยนชื่อเป็น file.1 จึงไม่เห็น `y` ส่วน `tail -F` ติดตามชื่อ `file` เมื่อไฟล์ใหม่ถูกสร้างจะเปิดใหม่และแสดง `y`
::

## 10. โจทย์คำนวณและตรวจความเข้าใจ

::reveal{question="โจทย์ 1: ไฟล์มี hard link 3 ชื่อ และมี 1 โปรเซสเปิดอยู่ ต้องลบชื่ออย่างน้อยกี่ชื่อและต้องทำอะไรอีกบ้าง พื้นที่จึงจะคืน"}
ต้องลบครบทั้ง 3 ชื่อ (link count เป็น 0) และโปรเซสที่เปิดอยู่ต้องปิดไฟล์ (open count เป็น 0) พื้นที่จึงถูกคืน ถ้าลบแค่ 2 ชื่อ ไฟล์ยังอยู่ผ่านชื่อที่เหลือ ถ้าลบครบ 3 ชื่อแต่โปรเซสยังเปิด พื้นที่ยังไม่คืน
::

::reveal{question="โจทย์ 2: ย้ายไฟล์ 200 GiB ข้ามดิสก์ที่เขียนได้ 250 MiB/s ใช้เวลาเท่าใดโดยประมาณ และปลายทางต้องว่างอย่างน้อยเท่าใด ถ้าย้ายในดิสก์เดียวกันล่ะ"}
ข้ามดิสก์: 200 × 1024 ÷ 250 = 819.2 วินาที ≈ 13.7 นาที (ค่าประมาณ ความเร็วจริงอาจต่ำกว่า) ปลายทางต้องว่าง ≥ 200 GiB ระหว่างนั้นมีข้อมูลสองชุด ถ้าในดิสก์เดียวกันเป็น rename ใช้เวลาไม่ถึงมิลลิวินาที ไม่ใช้พื้นที่เพิ่ม
::

::reveal{question="โจทย์ 3: ทำไม tail -n 20 ไฟล์ log ขนาด 100 GiB จึงเสร็จเร็ว แต่ cat ไฟล์เดียวกันช้า"}
tail กระโดด (seek) ไปท้ายไฟล์แล้วอ่านถอยหลังเท่าที่พอกับ 20 บรรทัด อ่านเพียงไม่กี่ KiB ไม่ขึ้นกับขนาดไฟล์ ส่วน cat อ่านตั้งแต่ต้นจนจบ 100 GiB ที่ 500 MiB/s ใช้ราว 100 × 1024 ÷ 500 ≈ 205 วินาที (ค่าประมาณ) และท่วมหน้าจอ
::

::reveal{question="โจทย์ 4: ทำไม awk PROGRAM data.txt > data.txt ทำให้ไฟล์ว่าง และ awk PROGRAM data.txt > tmp && mv tmp data.txt ปลอดภัยกว่าอย่างไร"}
เชลล์เปิดและตัด data.txt ให้ว่างก่อน awk เริ่ม awk จึงอ่านไฟล์ว่าง ส่วนแบบใช้ tmp เขียนผลลงไฟล์ใหม่ก่อน ถ้าคำสั่ง awk ล้มเหลว (&& จะไม่รัน mv) ไฟล์เดิมยังครบ และ mv เป็น rename ที่ atomic ผู้ใช้จึงเห็นไฟล์เก่าทั้งไฟล์หรือไฟล์ใหม่ทั้งไฟล์ ไม่เห็นสถานะครึ่งๆ
::

::reveal{question="โจทย์ 5: ลบไฟล์ log ใหญ่แล้ว df ยังเต็ม วินิจฉัยและแก้อย่างไร และจะป้องกันครั้งหน้าอย่างไร"}
น่าจะมีโปรเซสถือไฟล์ที่ลบแล้ว (link count 0 แต่ open count > 0) ตรวจด้วย lsof +L1 แล้ว restart หรือสั่งให้บริการเปิด log ใหม่ (เช่น reload) พื้นที่จะคืน ครั้งหน้าตัดไฟล์ด้วย : > file หรือตั้ง logrotate ให้หมุนเวียนและบีบอัด
::

::reveal{question="โจทย์ 6: ทำไมผู้ใช้ลบไฟล์ที่ตนเองอ่านอย่างเดียวได้ ในขณะที่ลบไฟล์ของคนอื่นในโฟลเดอร์ของตัวเองไม่ได้ถ้าไฟล์นั้นตั้ง sticky bit"}
สิทธิ์ลบอยู่ที่โฟลเดอร์แม่ (การลบคือแก้รายการในไดเรกทอรี) ไม่ใช่ที่ตัวไฟล์ จึงลบไฟล์อ่านอย่างเดียวได้ถ้าเขียนโฟลเดอร์แม่ได้ ส่วนโฟลเดอร์แบบ /tmp ตั้ง sticky bit ไว้ ผู้ใช้ลบได้เฉพาะไฟล์ที่ตนเป็นเจ้าของ แม้โฟลเดอร์จะเขียนได้ทุกคน (รายละเอียดในบทที่ 7)
::

::reveal{question="โจทย์ 7: ทำไมใช้ชื่อ /tmp/report.tmp ในสคริปต์ที่รันด้วยสิทธิ์สูงจึงเป็นช่องโหว่ และควรทำอย่างไร"}
ผู้ใช้อื่นเดาชื่อได้และสร้าง symlink ชื่อนั้นชี้ไปไฟล์สำคัญไว้ก่อน สคริปต์เขียนผ่าน symlink ไปทับไฟล์เป้าหมายด้วยสิทธิ์สูง และช่วงตรวจ-แล้วใช้ (TOCTOU) ยังมีโอกาสแทรก ควรใช้ mktemp ซึ่งสร้างชื่อสุ่มและเปิดแบบ O_EXCL (ล้มเหลวถ้าชื่อมีอยู่แล้ว) พร้อมสิทธิ์ที่เจ้าของคนเดียว
::

::

::reveal{question="ทำไมการเปลี่ยนชื่อกับการย้ายไฟล์ในดิสก์เดียวกันใช้คำสั่งเดียวกัน และเร็วเสมอ"}
เพราะชื่ออยู่ในรายการของไดเรกทอรี ไม่ได้อยู่ในตัวไฟล์ การเปลี่ยนชื่อและการย้ายคือแก้รายการ ชื่อ → inode (ผ่าน rename) บล็อกข้อมูลไม่ขยับ จึงเสร็จทันทีไม่ขึ้นกับขนาด และเป็น atomic
::

::reveal{question="เพราะเหตุใด sudo echo x > /etc/hosts จึงล้มเหลวและแก้อย่างไร"}
การเปิดไฟล์ปลายทางของ > ทำโดยเชลล์ของผู้ใช้ปกติก่อน sudo ทำงาน sudo ครอบเฉพาะ echo แก้ด้วยให้ tee ที่รันด้วย sudo เป็นผู้เขียน: echo x | sudo tee -a /etc/hosts
::

::reveal{question="rm ลบอะไรจริงๆ และทำไมกู้ไฟล์ที่ลบจึงมีโอกาส (แต่ไม่แน่นอน)"}
rm เรียก unlink ลบชื่อออกจากไดเรกทอรีและลด link count เมื่อเป็น 0 และไม่มีใครเปิดอยู่ บล็อกถูกบอกว่าว่าง แต่เนื้อหาไม่ถูกล้าง จึงกู้ได้ถ้ายังไม่ถูกเขียนทับ แต่บน SSD ที่มี TRIM ข้อมูลมักถูกล้างเร็ว ทางเดียวที่เชื่อถือได้คือมีสำรอง
::

::reveal{question="ทำไมการลบในเทอร์มินัลอันตรายกว่า GUI และมีวิธีลดความเสี่ยงอย่างไร"}
GUI ย้ายไปถังขยะก่อนและเห็นรายการที่เลือก ส่วน Remove-Item/rm เรียก unlink ตรง ไม่มี undo และ glob หรือ -r ทำให้ขอบเขตกว้างจากพิมพ์ผิดตัวเดียว ลดความเสี่ยงด้วยการซ้อม (ls pattern เดียวกัน, -WhatIf, rm -i, find ก่อน -delete) ตรวจ pwd และมีสำรอง
::

::reveal{question="head กับ tail ต่างกันอย่างไรเมื่อดู log"}
head แสดงต้นไฟล์ (เหมาะดูหัวตาราง) tail แสดงท้ายไฟล์ซึ่งใน log คือเหตุการณ์ล่าสุด และ tail กระโดดไปท้ายไฟล์ จึงเร็วแม้ไฟล์ใหญ่ ส่วน tail -f ตามดูบรรทัดใหม่ และ -F ตามชื่อเมื่อ log ถูกหมุนเวียน
::

## สรุป

- **ไฟล์ = ชื่อ (ในไดเรกทอรี) + inode/MFT (metadata) + บล็อกข้อมูล** hard link คือหลายชื่อต่อ inode เดียว มี link count
- **Create:** จอง inode + เพิ่มชื่อ ; ระวัง `New-Item -Force`, `>` ที่ทับ, encoding UTF-16 ของ PowerShell 5.1
- **Read:** เลือกเครื่องมือตามต้นทุน (`tail` seek ท้ายไฟล์, `cat` อ่านทั้งไฟล์) ; `tail -F` สำหรับ log ที่หมุนเวียน
- **Update:** `>` ตัดไฟล์ **ก่อน** โปรแกรมรัน (`sort f > f` = ไฟล์ว่าง) ; แก้ปลอดภัยด้วยไฟล์ชั่วคราว + `mv` (rename แบบ atomic) ; `sudo` ไม่ครอบ redirect ; ย้ายข้ามดิสก์ = คัดลอก + ลบ
- **Delete:** unlink ลบชื่อ พื้นที่คืนเมื่อ link count = 0 และ open count = 0 ; ไม่มีถังขยะ ; ซ้อมก่อนลบด้วย pattern เดียวกัน
- **Security:** log tampering, symlink/temp file (ใช้ `mktemp`), ransomware, ข้อมูลที่ "ลบแล้วไม่จริง" ; ป้องกันด้วยสำรอง สิทธิ์น้อยที่สุด และการเข้ารหัสดิสก์
- บทถัดไป: สิทธิ์ไฟล์และไดเรกทอรี (ใครทำ CRUD กับอะไรได้)
