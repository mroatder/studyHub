## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า `ipconfig` **อ่านอะไรจากไหน** และทำไมค่าที่เห็นจึงบอกว่าปัญหาอยู่ชั้นไหน (สาย → DHCP → เกตเวย์ → DNS)
2. เล่ากระบวนการ DHCP 4 ขั้น (DORA), เวลา T1/T2 ของ lease และเหตุที่เครื่องตกไปที่ **APIPA (169.254.x.x)** พร้อมคำนวณเวลาและโอกาสชนกันของที่อยู่
3. อธิบายความต่างเชิงกลไกของ `taskkill` แบบสุภาพ (ส่งข้อความปิดหน้าต่าง) กับ `/F` (ให้เคอร์เนลตัดจบ) และเหตุที่ `/T` จำเป็น
4. อธิบายว่า `sfc` กับ `DISM` ซ่อม **คนละชั้น** (ไฟล์ที่ใช้งาน เทียบกับคลังอะไหล่) และเลือกลำดับได้อย่างมีเหตุผล
5. อธิบายว่า NTFS ป้องกันความเสียหายอย่างไร (journal, dirty bit) จึงรู้ว่า `chkdsk` จำเป็นเมื่อไร และประมาณเวลาของ `/r` ได้
6. อ่าน `tasklist`, `systeminfo` แล้วคำนวณเปอร์เซ็นต์การใช้หน่วยความจำ
7. แยกอาการที่คล้ายกัน (เช่น ไม่มี IP กับมี IP แต่ไม่มีเกตเวย์กับมีเกตเวย์แต่ชื่อไม่แปลง) ด้วยการทดสอบที่ตัดสาเหตุได้
8. แมปคำสั่งแต่ละตัวกับการใช้ของผู้โจมตี (discovery, impair defenses) และการป้องกัน

## เปรียบเทียบกับชีวิตจริง

นึกถึง **ช่างที่ตรวจรถด้วยเครื่องมือเฉพาะทาง** แทนการเดาจากเสียง

| ช่างรถ | คำสั่ง Windows |
|---|---|
| ดูป้ายทะเบียนและที่อยู่ ว่ารถวิ่งในเส้นทางไหน | `ipconfig` (เครื่องมีที่อยู่และทางออกหรือเปล่า) |
| ตรวจว่ามีงานอะไรกินเครื่องอยู่ แล้วสั่งดับงานที่ค้าง | `tasklist` / `taskkill` |
| สแกนชิ้นส่วนเครื่องยนต์เทียบกับอะไหล่แท้ แล้วเปลี่ยนชิ้นที่เสีย | `sfc /scannow` |
| ถ้าคลังอะไหล่เสียหาย ต้องซ่อมคลังก่อนจึงเปลี่ยนชิ้นได้ | `DISM` แล้วค่อย `sfc` |
| ตรวจสภาพถังและท่อน้ำมัน | `chkdsk` |
| อ่านสมุดรายการรถ (รุ่น ปีผลิต หมายเลขตัวถัง) | `systeminfo` |

## ภาพรวม

ต้นฉบับไล่คำสั่งเป็นกลุ่ม: เครือข่าย โปรเซส ไฟล์ระบบ ดิสก์ และข้อมูลระบบ บทนี้เดินตามลำดับเดิม แต่ **ถามก่อนว่า "ทำไมคำสั่งนี้ถึงแก้ได้"** เพราะคนที่รู้กลไกจะแยกได้ว่าเมื่อใดคำสั่งไม่ช่วย และจะไม่กดคำสั่งอันตรายโดยไม่รู้ผล แต่ละส่วนมีแอนิเมชันให้กดดูทีละขั้น

> **ก่อนเริ่ม:** เปิด Command Prompt แบบปกติสำหรับ `ipconfig`, `tasklist`, `systeminfo` ส่วน `sfc`, `DISM`, `chkdsk` ต้องเปิดแบบ **Run as administrator** (ค้นหา "cmd" แล้วคลิกขวา) ถ้าไม่ใช่จะขึ้นข้อความว่าต้องใช้สิทธิ์ผู้ดูแล

## 0. หลักคิด: คำสั่งทุกตัวคือหน้าต่างมองเข้าไปในสถานะของระบบ

ระบบปฏิบัติการคือโปรแกรมที่ถือ **ตารางสถานะ** ไว้หลายตาราง ปัญหาที่ผู้ใช้เห็น (เว็บไม่ขึ้น เครื่องช้า) คือผลจากตารางใดตารางหนึ่งผิดเพี้ยน

| ตารางสถานะ | ใครเป็นเจ้าของ | คำสั่งที่เปิดดู/แก้ |
|---|---|---|
| การตั้งค่า IP ของการ์ด + สัญญาเช่า DHCP | ชุดโปรโตคอลเครือข่าย (TCP/IP stack) | `ipconfig` |
| แคชชื่อ → IP | บริการ DNS Client | `ipconfig /displaydns`, `/flushdns` |
| รายการโปรเซสและเธรด | เคอร์เนล (Object Manager) | `tasklist`, `taskkill` |
| ไฟล์ระบบที่ป้องกัน + คลังต้นฉบับ | Windows Resource Protection, component store | `sfc`, `DISM` |
| โครงสร้างไฟล์บนดิสก์ (MFT, ดัชนี, บิตมลทิน) | ระบบไฟล์ NTFS | `chkdsk`, `fsutil` |
| ข้อมูลฮาร์ดแวร์/OS รวม | WMI และเคอร์เนล | `systeminfo` |

วิธีคิดนี้ช่วยเลือกคำสั่ง: **อาการระบุตารางที่น่าจะเสีย แล้วเลือกคำสั่งที่เปิดตารางนั้น** ไม่ใช่ลองทุกคำสั่งตามลำดับ (เทียบกับบทระเบียบวิธีแก้ปัญหา ที่ให้ตั้งสมมุติฐานแล้วทดสอบตัวที่ถูกที่สุดก่อน)

**ข้อจำกัดของแบบจำลองนี้:** คำสั่งเหล่านี้แสดง "สถานะที่ระบบเชื่อ" ไม่ใช่ความจริงทางกายภาพเสมอไป เช่น `ipconfig` บอกว่าการ์ดมี IP แต่สายอาจหลุดไปแล้วเมื่อสองวินาทีก่อน (Windows อาจแสดงค่าเก่าอยู่ช่วงสั้นๆ) และ `chkdsk` ที่ไม่พบปัญหาไม่ได้แปลว่าฮาร์ดแวร์ดิสก์สุขภาพดี มันตรวจ **โครงสร้างข้อมูล** ไม่ได้วัดสภาพชิป

## 1. ตรวจเครือข่ายด้วย ipconfig

### 1.1 ไล่ลำดับสิ่งที่ต้องเกิดก่อนเว็บจะขึ้น

จะเปิดเว็บได้ เครื่องต้องผ่านลำดับ "ห่วงโซ่" ต่อไปนี้ ขาดข้อใดข้อหนึ่งอาการจะต่างกัน

1. การ์ดมีลิงก์ทางกายภาพ (สาย/Wi-Fi เชื่อมจริง)
2. ได้ **IP + subnet mask + default gateway** (ด้วย DHCP หรือตั้งเอง)
3. ส่งแพ็กเก็ตถึงเกตเวย์ได้
4. แปลงชื่อเว็บเป็น IP ได้ (DNS)
5. ปลายทางตอบ

`ipconfig` (Internet Protocol Configuration) อ่านสถานะ **ข้อ 2 และข้อ 4 บางส่วน** จากการ์ดเครือข่าย (network adapter) เท่านั้น ถ้าข้อ 2 ผิด ไม่ต้องไปดู DNS เลย นี่คือเหตุผลที่ต้องรัน `ipconfig` เป็นลำดับแรกเมื่อ "เน็ตไม่ขึ้น"

พิมพ์เฉยๆ จะได้สรุปของแต่ละอะแดปเตอร์ ค่าที่ต้องดูมี 3 ตัว

| ค่า | ความหมาย | ถ้าผิดปกติ |
|---|---|---|
| **IPv4 Address** | ที่อยู่ของเครื่องในเครือข่าย | ขึ้นต้น `169.254` = APIPA ไม่ได้ IP จริง |
| **Subnet Mask** | ขอบเขตของเครือข่ายเดียวกัน (เครื่องใช้ตัดสินว่าปลายทาง "อยู่วงเดียวกัน" ไหม) | ไม่ตรงกับเครือข่ายจริง = ตั้งค่าผิด |
| **Default Gateway** | ประตูออกสู่เครือข่ายอื่น (ปกติคือเราเตอร์) | ว่าง = ปลายทางนอกวงเดียวกันส่งไปไหนไม่ได้ |

**ทำไม subnet mask สำคัญ:** เมื่อเครื่องจะส่งไปที่ IP ใด มันนำ IP ปลายทางมา AND กับ mask ของตัวเอง ถ้าได้เครือข่ายเดียวกัน ส่งตรงในวง (ผ่าน ARP) ถ้าไม่ใช่ ส่งให้เกตเวย์ เช่น เครื่อง `192.168.1.45/24` ส่งถึง `192.168.1.200` ตรงๆ แต่ถึง `8.8.8.8` ต้องผ่าน `192.168.1.1` (รายละเอียดอยู่ในบทเครือข่ายที่ตามมา)

### 1.2 DHCP: IP คือสัญญาเช่า ไม่ใช่ของถาวร

ปัญหา: ถ้าต้องตั้ง IP ทุกเครื่องด้วยมือ จะชนกันง่ายและแก้ยากเมื่อมีหลายร้อยเครื่อง **DHCP (Dynamic Host Configuration Protocol)** จึงให้เซิร์ฟเวอร์แจกที่อยู่แบบ **เช่า (lease)** มีเวลาหมดอายุ กดดูแอนิเมชันว่าเครื่องขอ IP อย่างไร และเกิดอะไรเมื่อไม่มีใครตอบ

**ตัวเลขที่ควรจำ (จากข้อกำหนด DHCP):** ต่ออายุที่ T1 = 50% ของเวลาเช่า และ rebind ที่ T2 = 87.5% เช่น lease 24 ชั่วโมง ต่ออายุที่ชั่วโมงที่ 12 และเปลี่ยนเป็น broadcast ที่ชั่วโมงที่ 21 ดังนั้นถ้าเซิร์ฟเวอร์ดับ เครื่องที่เช่ามา 24 ชั่วโมงมี "เวลาซื้อ" อีกอย่างน้อยราว 12 ชั่วโมงก่อน IP หายจริง นี่คือเหตุที่บางครั้ง DHCP ล่มแล้วผู้ใช้ไม่รู้สึกทันที

**APIPA (Automatic Private IP Addressing)** คือกลไกสำรองของ Windows: เมื่อหา DHCP ไม่เจอ จะสุ่มหมายเลขในช่วง `169.254.0.0/16` ให้ตัวเอง (ช่วงนี้ถูกสงวนไว้เป็น link-local) แล้ว **ส่ง ARP ถามก่อนว่ามีใครใช้อยู่ไหม** ถ้าไม่มีจึงยึดใช้ สิ่งที่ได้คือคุยกับเครื่องบนสายเดียวกันที่ได้ช่วงเดียวกันได้ แต่ **ไม่มีเกตเวย์ จึงออกนอกวงไม่ได้** Windows จะพยายามขอ DHCP ใหม่เป็นระยะ (ราว 5 นาที ตามพฤติกรรมทั่วไป ค่าประมาณ) ถ้าเราเตอร์กลับมา เครื่องจะได้ IP จริงเอง

#### โจทย์คำนวณ: APIPA จะสุ่มชนกันบ่อยแค่ไหน

ช่วงใช้งานได้จริงตามข้อกำหนดคือ `169.254.1.0` ถึง `169.254.254.255` = 254 × 256 = **65,024** ที่อยู่ ถ้ามี n เครื่องสุ่มพร้อมกันบนสายเดียว โอกาสที่อย่างน้อยสองเครื่องสุ่มได้เลขซ้ำคือ (ปัญหาวันเกิด) 1 − ∏(1 − i/65,024)

::reveal{question="ออฟฟิศเล็กปิดไฟทั้งชั้น แล้วเปิดพร้อมกัน 100 เครื่อง เราเตอร์ยังไม่ขึ้น โอกาสที่มีอย่างน้อยหนึ่งคู่สุ่ม APIPA ซ้ำกันคือเท่าไร และเกิดอะไรต่อ"}
คำนวณด้วย node: n=100 ได้ราว **7.3%** (n=50 ได้ 1.9%, n=300 ได้ราว 49.9%) ตัวเลขนี้เป็นการประมาณแบบสุ่มสม่ำเสมอ ในความจริงเครื่องจะ **ส่ง ARP probe ตรวจก่อนใช้** ถ้าซ้ำ เครื่องที่พบจะสุ่มใหม่ ผลคือชนกันจริงแทบไม่เกิดปัญหา แต่ตัวเลขช่วยให้เห็นว่า "ช่วงเล็กแค่ 65 พันที่อยู่" ทำไมจึงต้องมีกลไกตรวจก่อนใช้ และเหตุใด APIPA เหมาะแค่เครือข่ายวงเล็ก
::

### 1.3 /release, /renew และ /flushdns ทำอะไรกับตารางสถานะ

| คำสั่ง | สิ่งที่เปลี่ยนจริง | ใช้เมื่อ | ข้อจำกัด |
|---|---|---|---|
| `ipconfig /release` | ส่ง DHCPRELEASE คืน IP แล้วลบค่า IP ของการ์ด | ได้ IP ผิด/ซ้ำ ต้องการเริ่มขอใหม่ | ใช้ไม่ได้ผลกับอะแดปเตอร์ที่ตั้ง static และตัดการเชื่อมต่อทันที |
| `ipconfig /renew` | เริ่ม DORA (หรือต่ออายุ) เพื่อขอค่าใหม่ | ต่อจาก `/release` หรือเพิ่งเสียบสาย | ถ้าไม่มี DHCP ตอบ จะรอแล้วล้มเหลวหรือตกไป APIPA |
| `ipconfig /flushdns` | ล้างแคชที่ DNS Client เก็บ (ผล lookup ที่ยังไม่หมด TTL) | เข้าเว็บ/ระบบภายในไม่ได้ทั้งที่คนอื่นเข้าได้ | ไม่แก้ปัญหาที่ DNS server ปลายทางตอบผิด |

**ทำไมแคช DNS ถึงทำให้เจอปัญหา:** ผลแปลงชื่อถูกเก็บไว้ตามค่า **TTL (Time To Live)** ที่เซิร์ฟเวอร์กำหนด เช่น TTL 3600 วินาที (1 ชั่วโมง) ถ้าเซิร์ฟเวอร์ปลายทางย้าย IP เครื่องที่เพิ่งถามจะยังใช้ IP เก่าได้สูงสุดราว 1 ชั่วโมงจนหมด TTL หรือจนสั่ง `/flushdns` Windows ยังเก็บ **negative cache** (จำว่า "หาชื่อนี้ไม่เจอ") ไว้ด้วย ทำให้ชื่อที่เพิ่งสร้างใหม่ยังหาไม่เจออยู่พักหนึ่ง ดูแคชปัจจุบันได้ด้วย `ipconfig /displaydns` (อ่านอย่างเดียว) และอย่าลืมว่า **ไฟล์ hosts** (`C:\Windows\System32\drivers\etc\hosts`) ถูกตรวจก่อน DNS เสมอ

> **ข้อควรระวัง (ส่วนเสริมจากผู้เขียน):** อย่าสั่ง `/release` ผ่านรีโมต (RDP/SSH) บนเครื่องที่คุณต่อเข้าไป เพราะ IP หายแล้วการเชื่อมต่อของคุณขาดทันที และพิมพ์ `/renew` ต่อไม่ได้ ถ้าจำเป็นให้สั่งรวมบรรทัดเดียว เช่น `ipconfig /release & ipconfig /renew` เพื่อให้คำสั่งถัดไปทำงานต่อโดยไม่ต้องมีคนพิมพ์

## 2. จัดการโปรเซสด้วย tasklist และ taskkill

### 2.1 โปรเซสในมุมเคอร์เนล

**โปรเซส (process)** คือโปรแกรมที่กำลังรัน ประกอบด้วยพื้นที่หน่วยความจำของตัวเอง ตารางตัวจัดการ (handle) ไปยังไฟล์/อุปกรณ์ และอย่างน้อยหนึ่งเธรด เคอร์เนลให้ **PID** (Process ID) เป็นเลขประจำตัวขณะรัน เลขนี้ถูกนำกลับมาใช้ใหม่ได้เมื่อโปรเซสเดิมจบ ดังนั้นการจด PID ไว้นานแล้วค่อยสั่ง `taskkill /PID` อาจไปโดนโปรเซสใหม่ที่ได้เลขเดิม **ตรวจ `tasklist` ซ้ำทันทีก่อนสั่ง**

`tasklist` แสดงรายการโปรเซสจากบรรทัดคำสั่ง เมื่อ Task Manager ค้าง

::terminal-sim{title="หาโปรเซสที่กินหน่วยความจำ" prompt="C:⧵>" :commands='[{"cmd":"tasklist","out":"Image Name                     PID Session Name        Session#    Mem Usage⏎========================= ======== ================ =========== ============⏎System Idle Process              0 Services                   0          8 K⏎System                           4 Services                   0        140 K⏎explorer.exe                  3812 Console                    1    112,430 K⏎report_generator.exe          7104 Console                    1  1,845,120 K⏎cmd.exe                       5408 Console                    1      4,112 K","note":"report_generator.exe ใช้หน่วยความจำราว 1.8 GB สูงกว่าตัวอื่นมาก (เลขเป็นตัวอย่าง) จดค่า PID 7104 ไว้ใช้ต่อ"},{"cmd":"tasklist | findstr report","out":"report_generator.exe          7104 Console                    1  1,845,120 K","note":"กรองเฉพาะบรรทัดที่มีคำว่า report ด้วย findstr เหมาะกับรายการยาว (เครื่องจริงมีหลายร้อยบรรทัด)"}]'}

คอลัมน์ที่ใช้ตัดสิน

| คอลัมน์ | ความหมาย |
|---|---|
| **Image Name** | ชื่อไฟล์โปรแกรมที่รัน |
| **PID** | หมายเลขโปรเซสที่เคอร์เนลกำหนดให้ ไม่ซ้ำกันขณะรัน และนำกลับมาใช้ใหม่ได้ |
| **Session Name / Session#** | `Services`/0 = งานเบื้องหลังของระบบ, `Console`/1 = ของผู้ใช้ที่ล็อกอินหน้าเครื่อง (แยกเซสชันตั้งแต่ Windows Vista เพื่อกันบริการกับผู้ใช้ปะปนกัน) |
| **Mem Usage** | หน่วยความจำจริง (working set) ที่โปรเซสถืออยู่ตอนนี้ ไม่ได้รวมส่วนที่ถูกสลับลงดิสก์ |

> **เสริม:** `tasklist /FI "IMAGENAME eq notepad.exe"` กรองด้วยเงื่อนไขในตัวคำสั่ง และ `tasklist /SVC` แสดงว่าโปรเซสไหนรันบริการ (service) อะไร มีประโยชน์เมื่อชื่อโปรเซสอย่าง `svchost.exe` ไม่บอกอะไร (ตัวเดียวโฮสต์หลายบริการ)

### 2.2 taskkill: สุภาพ เทียบกับ ตัดจบ

ปิดโปรเซสด้วย `/PID` (เลขโปรเซส) หรือ `/IM` (image name = ชื่อไฟล์)

| ตัวเลือก | ความหมาย |
|---|---|
| `/PID 7104` | ระบุด้วยหมายเลขโปรเซส ตรงตัวที่สุด ไม่พลาดตัวอื่น |
| `/IM name.exe` | ระบุด้วยชื่อ ปิด **ทุกโปรเซสที่ชื่อนี้** ซึ่งอาจมีหลายตัว |
| `/F` | บังคับยุติทันที (force) |
| `/T` | ปิดโปรเซสนั้นพร้อมโปรเซสลูกทั้งหมด (tree) |

**ความต่างที่ระดับระบบปฏิบัติการ:** (1) แบบไม่มี `/F` `taskkill` **ส่งข้อความปิดหน้าต่าง (WM_CLOSE)** ไปยังหน้าต่างของโปรเซส โปรแกรมที่ดีจะรับข้อความ ถามเซฟงาน ปิดไฟล์ แล้วออกเอง แต่โปรแกรมที่ค้างจนไม่อ่านคิวข้อความ หรือโปรเซสไม่มีหน้าต่าง (เช่น โปรแกรมคอนโซล) จะไม่ตอบ จึงได้ข้อความ "can only be terminated forcefully" (2) ด้วย `/F` เรียกกลไกที่ให้ **เคอร์เนลทำลายโปรเซสโดยตรง (TerminateProcess)** โปรแกรมไม่มีโอกาสรันโค้ดปิดตัว เคอร์เนลเก็บคืนหน่วยความจำและปิด handle ทั้งหมดให้ แต่ข้อมูลที่โปรแกรมยังไม่ได้เขียนลงดิสก์หายไปเลย

(ข้อสังเกตเทียบกับ Linux: ที่นั่นมีสัญญาณหลายชนิด ให้โปรแกรมดักได้ ดูบทถัดไป ส่วน Windows ใช้ข้อความหน้าต่างสำหรับ "ขอปิด" และ TerminateProcess สำหรับ "ตัดจบ")

**ทำไมต้อง /T:** บน Windows โปรเซสลูกไม่ตายตามพ่อแม่โดยอัตโนมัติ (เคอร์เนลเก็บแค่ว่าใครสร้าง ไม่ได้ผูกชีวิต) ถ้าปิดโปรเซสหลักตัวเดียว ลูกอาจกลายเป็นโปรเซสกำพร้าที่ยังกินทรัพยากรต่อ ลองประกอบคำสั่งและดูว่าโปรเซสใดถูกปิด

## 3. ซ่อมไฟล์ระบบด้วย sfc และ DISM

### 3.1 ปัญหา: ไฟล์ระบบเสียเพราะอะไร และตรวจอย่างไร

ไฟล์สำคัญของ Windows (DLL, ไดรเวอร์ ฯลฯ) เสียหายเมื่อเครื่องดับกลางคัน อัปเดตไม่สมบูรณ์ ดิสก์ผิดพลาด หรือมัลแวร์แก้ไข อาการคือแอปและเมนูตั้งค่าค้าง หรือ error ที่ชี้ไปยัง DLL

ปัญหาเชิงตรรกะ: จะรู้ได้อย่างไรว่าไฟล์ "เสีย" ต้องมี **ค่าอ้างอิงที่ถูกต้อง** มาเทียบ Windows เก็บสองสิ่งไว้ (อธิบายแบบสรุป)

- **ค่าอ้างอิงของไฟล์ที่ได้รับการป้องกัน** (ลายเซ็นดิจิทัลและแฮชในแคตตาล็อก)
- **สำเนาต้นฉบับ** ในคลังส่วนประกอบ **component store** (โฟลเดอร์ `C:\Windows\WinSxS`) ซึ่งไฟล์ในระบบหลายไฟล์เป็น hard link ชี้มาที่นี่

**System File Checker (`sfc`)** ใช้ค่าอ้างอิงตรวจไฟล์ที่ป้องกันไว้ ตัวไหนเสียหรือหายก็คัดลอกตัวสะอาดจาก component store มาแทน

```cmd
sfc /scannow
```

ปัญหาคือ ถ้า **component store เองเสียหาย** `sfc` ก็ไม่มีของดีไปเปลี่ยน จึงรายงานว่าพบไฟล์เสียแต่ซ่อมไม่ได้ ตรงนี้ใช้ **DISM (Deployment Image Servicing and Management)** ซ่อม "คลังอะไหล่" ก่อน โดยดึงไฟล์ดีจาก Windows Update (ต้องต่ออินเทอร์เน็ต หรือชี้แหล่งอื่นด้วย `/Source`) แล้วค่อยรัน `sfc` ซ้ำ

## 4. ตรวจดิสก์และระบบไฟล์ด้วย chkdsk

### 4.1 ทำไมระบบไฟล์ถึงเสียได้ และ NTFS ป้องกันอย่างไร

การสร้างหรือลบไฟล์เดียวต้องแก้ข้อมูลหลายจุดบนดิสก์ (ตารางไฟล์ MFT, ดัชนีโฟลเดอร์, bitmap ของพื้นที่ว่าง) ถ้าไฟดับกลางคัน อาจสำเร็จแค่บางจุด เกิดโครงสร้างขัดแย้ง (เช่น ดัชนีบอกมีไฟล์ แต่ตารางไฟล์ไม่มี)

NTFS แก้ด้วย **การทำ journal (`$LogFile`)**: เขียนบันทึก "กำลังจะทำอะไร" ก่อน ถ้าดับกลางคัน ตอนเปิดเครื่อง ระบบ **เล่นบันทึกซ้ำ/ย้อนกลับ** ให้ metadata กลับมาสอดคล้อง โดยปกติจึงไม่ต้องรัน `chkdsk` เองหลังไฟดับ แต่ journal ป้องกันเฉพาะ **metadata** ไม่รับประกันเนื้อหาไฟล์ที่เขียนค้าง และไม่ช่วยเมื่อเสียหายจากฮาร์ดแวร์ ระบบจึงมี **dirty bit** ติดไว้ที่วอลลุ่มเมื่อสงสัยว่าไม่สะอาด ตอนบูต `autochk` ตรวจบิตนี้และรัน chkdsk ให้อัตโนมัติ ดูบิตด้วยคำสั่งอ่านอย่างเดียว

```cmd
fsutil dirty query C:
```

`chkdsk` (Check Disk) มีสองระดับของปัญหา ระดับ **ตรรกะ** (โครงสร้างข้อมูลผิดเพี้ยน) และระดับ **กายภาพ** (เซกเตอร์เสีย) ที่ทำงานเป็นขั้นๆ

| ขั้นของ chkdsk (NTFS) | ตรวจอะไร | เมื่อไร |
|---|---|---|
| Stage 1 | โครงสร้างพื้นฐานของไฟล์ (MFT) | ทุกครั้ง |
| Stage 2 | การเชื่อมชื่อไฟล์ (ดัชนีโฟลเดอร์) | ทุกครั้ง |
| Stage 3 | security descriptor (สิทธิ์ของไฟล์) | ทุกครั้ง |
| Stage 4 | อ่านข้อมูลของทุกไฟล์ทีละคลัสเตอร์ | เฉพาะ `/r` |
| Stage 5 | ตรวจพื้นที่ว่างทั้งหมด | เฉพาะ `/r` |

| คำสั่ง | ทำอะไร | ผลข้างเคียง |
|---|---|---|
| `chkdsk C:` | อ่านอย่างเดียว รายงานปัญหา ไม่แก้ | ปลอดภัย |
| `chkdsk C: /scan` | สแกนออนไลน์ขณะใช้งาน (NTFS) ไม่ต้องปลดไดรฟ์ | ปลอดภัย, ไม่แก้ในตัวเอง |
| `chkdsk C: /f` | แก้ข้อผิดพลาดของโครงสร้างระบบไฟล์ | ต้องล็อกวอลลุ่มระหว่างทำ |
| `chkdsk C: /r` | ทำ `/f` และ **อ่านทุกเซกเตอร์** หาจุดเสีย ทำเครื่องหมายคลัสเตอร์เสีย | ช้ามาก (ไล่ทั้งดิสก์) |

ต่างกันสั้นๆ: `/f` แก้ "สมุดสารบัญ" ที่ผิด ส่วน `/r` ไล่ตรวจ "ทุกหน้ากระดาษ" ด้วย (และรวม `/f` ไว้แล้ว)

::compare-cards{:items='[{"title":"chkdsk C: /f","subtitle":"แก้ตรรกะ","points":["แก้โครงสร้างระบบไฟล์ เช่น ตารางไฟล์ ดัชนีโฟลเดอร์ (Stage 1–3)","เร็วกว่ามาก","เหมาะเมื่อมีสัญญาณว่าไฟล์ระบบผิดเพี้ยน เช่น หลังเครื่องดับกลางคัน","ไม่อ่านผิวดิสก์ทั้งหมด"]},{"title":"chkdsk C: /r","subtitle":"แก้ตรรกะ + สแกนกายภาพ","points":["รวมการทำงานของ /f","อ่านทุกเซกเตอร์ (Stage 4–5) ทำเครื่องหมายจุดเสียและกู้ข้อมูลที่อ่านได้","ใช้เวลานานมาก โดยเฉพาะดิสก์ใหญ่หรือ HDD ช้า","เหมาะเมื่อสงสัยดิสก์เสียทางกายภาพ"]}]'}
::

#### โจทย์คำนวณ: /r ใช้เวลานานแค่ไหน

ขั้นที่ใช้เวลามากที่สุดคือการอ่านข้อมูลทั้งดิสก์ ประมาณเวลาขั้นต่ำ = ขนาดข้อมูล ÷ ความเร็วอ่านต่อเนื่อง (ตัวเลขความเร็วเป็นค่าประมาณทั่วไป ของจริงช้ากว่านี้เพราะการหมุนหาตำแหน่งและการลองอ่านซ้ำตอนเจอเซกเตอร์เสีย)

::reveal{question="ดิสก์ HDD ขนาด 1 TB (10⁶ MB) อ่านต่อเนื่องราว 120 MB/s เทียบกับ SATA SSD 1 TB ราว 500 MB/s chkdsk /r ใช้เวลาอย่างน้อยกี่ชั่วโมง และถ้าเป็น HDD 4 TB"}
คำนวณด้วย node: HDD 1 TB = 10⁶ ÷ 120 = 8,333 วินาที ≈ **2.31 ชั่วโมง** SSD = 10⁶ ÷ 500 = 2,000 วินาที ≈ **0.56 ชั่วโมง (ราว 33 นาที)** HDD 4 TB ≈ **9.26 ชั่วโมง** ทั้งหมดเป็นเวลาขั้นต่ำตามทฤษฎี (ค่าประมาณ) จึงต้องนัดนอกเวลางาน และเหตุที่ `/r` ไม่ค่อยเหมาะกับ SSD คือ SSD จัดการเซกเตอร์เสียเองในเฟิร์มแวร์ ผลการสแกนผิวไม่สะท้อนสุขภาพชิปเท่าค่า SMART
::

## 5. ดูข้อมูลเครื่องด้วย systeminfo

`systeminfo` รวบรวมข้อมูลเครื่องไว้ที่เดียว: ชื่อและเวอร์ชัน OS, วันที่ติดตั้ง, เวลาบูตล่าสุด, รุ่นเมนบอร์ดและเวอร์ชัน BIOS, หน่วยความจำ, แพตช์ (hotfix) ที่ติดตั้ง และการ์ดเครือข่าย ใช้ตอนเปิด ticket เพื่อรู้ว่าเครื่องนี้คืออะไร หรือตอบคำถามเช่น "ติดตั้งแพตช์ล่าสุดแล้วหรือยัง" โดยไม่ต้องคลิกหาในหลายเมนู

เนื่องจากผลลัพธ์ยาว ให้ใช้ท่อ (`|`) ส่งต่อให้ `findstr` ซึ่งกรองบรรทัดที่ตรงกับข้อความ ตัวเลือก `/B` = ตรงต้นบรรทัด และ `/C:` = ใช้ข้อความทั้งก้อนรวมช่องว่าง

```cmd
systeminfo | findstr /B /C:"Total Physical Memory" /C:"Available Physical Memory"
Total Physical Memory:     16,142 MB
Available Physical Memory: 9,410 MB
```

**ท่อ (pipe) ทำงานอย่างไร:** `|` เชื่อมเอาต์พุตมาตรฐาน (stdout) ของคำสั่งซ้ายเข้าอินพุตมาตรฐาน (stdin) ของคำสั่งขวา เปิดสองโปรเซสพร้อมกัน ข้อมูลไหลผ่านบัฟเฟอร์ของเคอร์เนล ไม่ได้เขียนไฟล์ชั่วคราว

#### โจทย์คำนวณ: ใช้ RAM ไปกี่เปอร์เซ็นต์

จากตัวอย่างข้างบน ใช้ไป = รวม − ว่าง = 16,142 − 9,410 = 6,732 MB คิดเป็น 6,732 ÷ 16,142 = **41.7%** (ตรวจด้วย node) ถ้า Available ต่ำกว่าราว 10% ของ RAM รวมและเครื่องช้า ให้ไปดู `tasklist` ว่าโปรเซสใดกินหน่วยความจำ ซึ่งเชื่อมกลับไปหัวข้อ 2 ตัวเลข 10% เป็นเกณฑ์หยาบเชิงปฏิบัติ (ค่าประมาณ) ไม่ใช่มาตรฐาน

## 6. วินิจฉัยเชิงกลไก: อาการคล้ายกัน แต่สาเหตุต่างชั้น

ข้อได้เปรียบของคนที่รู้กลไกคือแยกอาการที่ผู้ใช้เล่ามาเหมือนกันได้ด้วยการทดสอบเดียว

| สิ่งที่เห็น | แปลว่า (ชั้นที่เสีย) | การทดสอบที่ตัดสาเหตุ |
|---|---|---|
| IPv4 ขึ้นต้น `169.254` | ขั้นขอ IP ล้ม: ไม่มี DHCP ตอบ (สาย/Wi-Fi/เซิร์ฟเวอร์ DHCP) | `ipconfig /renew`; ถ้าเครื่องอื่นบนสายเดียวกันได้ IP ปกติ ปัญหาอยู่ที่เครื่องนี้หรือสายของมัน |
| มี IP ถูกช่วง แต่เกตเวย์ว่าง | ตั้งค่า static ไม่ครบ หรือ DHCP ส่งตัวเลือกเกตเวย์ไม่ครบ | ดู `ipconfig /all` ว่า DHCP Enabled เป็น Yes/No; ถ้า No แก้ค่า static |
| มี IP และเกตเวย์ แต่ ping เกตเวย์ไม่ตอบ | ชั้นเชื่อมต่อในวง (สายหรือสวิตช์ หรือเกตเวย์ปิดการตอบ ICMP) | ลอง ping เครื่องอื่นในวง และดูว่าไฟร์วอลล์ปิด ICMP ไหม (ไม่ตอบ ping ≠ ล่มเสมอไป) |
| ping เกตเวย์ได้ ping `8.8.8.8` ได้ แต่เข้าเว็บด้วยชื่อไม่ได้ | DNS (เซิร์ฟเวอร์ DNS ผิดหรือแคชผิด) | `nslookup ชื่อ`; ถ้าแปลงชื่อได้ที่ DNS อื่น ปัญหาอยู่ที่ DNS ที่ตั้งไว้; ลอง `/flushdns` และตรวจ hosts |
| เฉพาะเครื่องนี้เข้าระบบภายในไม่ได้ ที่อื่นได้ | แคช DNS หรือไฟล์ hosts ของเครื่องนี้ชี้ IP เก่า | `ipconfig /displaydns` เทียบกับ `nslookup`; ถ้าต่างกัน แคช/hosts ผิด |
| เครื่องช้าตลอด เมื่อเปิดโปรแกรมหนึ่ง | โปรเซสเดียวกินหน่วยความจำจนระบบต้อง swap | `tasklist` เรียงดู Mem Usage; เทียบกับ Available ใน `systeminfo` |
| แอปค้างหลังไฟดับ และ `sfc` ล้ม | ไฟล์ระบบเสียและคลังเสีย | `DISM` ซ่อมคลังแล้ว `sfc` ซ้ำ; ถ้ากลับมาเสียบ่อยให้สงสัยดิสก์/มัลแวร์ |
| ไฟล์เปิดไม่ได้เป็นระยะ ชื่อไฟล์เพี้ยน | โครงสร้าง NTFS ผิด หรือเซกเตอร์เสีย | `fsutil dirty query` แล้ว `chkdsk C:` อ่านอย่างเดียว; พบเซกเตอร์เสียซ้ำ สำรองข้อมูลก่อน |

## มุมมองด้าน Security

เครื่องมือซ่อมคือสิ่งเดียวกับที่ผู้โจมตีใช้สำรวจ เรียกว่า **living off the land** (ใช้เครื่องมือที่มากับระบบเพื่อไม่ให้ตรวจพบ) ตารางเลขรหัสด้านล่างอ้างอิงเทคนิคใน MITRE ATT&CK เพื่อให้ค้นต่อได้

| คำสั่ง | ผู้โจมตีใช้ทำอะไร | เทคนิค (ATT&CK) | การป้องกัน/ตรวจจับ |
|---|---|---|---|
| `ipconfig /all` | รู้โครงสร้างเครือข่าย โดเมน DNS | T1016 System Network Configuration Discovery | บันทึก command line (Event ID 4688 พร้อม command line auditing / Sysmon); แปลก ถ้าเกิดจากบัญชีที่ไม่เคยรัน |
| `tasklist`, `systeminfo` | หา EDR/แอนตี้ไวรัสที่รัน, เวอร์ชัน OS และแพตช์เพื่อเลือกช่องโหว่ | T1057 Process Discovery, T1082 System Information Discovery | ลดสิทธิ์ผู้ใช้, ตรวจลำดับคำสั่งรัวๆ หลายตัวที่ไม่ใช่งานปกติ |
| `taskkill /F` | ปิดโปรแกรมป้องกันก่อนลงมือ | T1562.001 Impair Defenses: Disable or Modify Tools | เปิด Tamper Protection ของ Defender; แจ้งเตือนเมื่อ process ป้องกันถูกยุติ |
| DHCP ปลอม | เซิร์ฟเวอร์ DHCP ที่ไม่ใช่ของจริงแจกเกตเวย์/DNS ของผู้โจมตี | T1557.003 DHCP Spoofing | DHCP snooping บนสวิตช์ (อนุญาตเฉพาะพอร์ตที่ต่อเซิร์ฟเวอร์จริง); `ipconfig /all` ดู DHCP Server ว่าตรงที่รู้จักไหม |
| แก้ `hosts` หรือแคช DNS | เปลี่ยนชื่อธนาคารให้ชี้เว็บปลอม | (ใกล้เคียง) การเปลี่ยนไฟล์ระบบ | ตรวจ hosts เมื่อชื่อชี้ผิดโดยไม่มีเหตุ; จำกัดสิทธิ์เขียน; `/flushdns` ช่วยเมื่อแคชถูกวางข้อมูลปลอม |
| ไฟล์ระบบถูกแก้ (rootkit) | ฝังตัวผ่านไฟล์ระบบ | (เทคนิคฝังตัวหลายแบบ) | `sfc /verifyonly` พบไฟล์เปลี่ยนโดยไม่มีสาเหตุ (ไม่ได้ไฟดับ/อัปเดตค้าง) ให้สงสัยและ escalate; ข้อจำกัด: มัลแวร์ระดับเคอร์เนลอาจหลอกให้ sfc ไม่เห็น |

ข้อปฏิบัติ

- **ปิดข้อมูลก่อนส่งต่อ:** ผลของ `ipconfig`, `systeminfo` มี IP ภายใน ชื่อเครื่อง ระดับแพตช์ ปิดส่วนที่ไม่จำเป็นก่อนแปะลง ticket/แชตสาธารณะ
- **สอบสวนก่อนปิด:** โปรเซสแปลก (เช่น `svch0st.exe`) ให้จด PID พาธไฟล์ เวลา แล้ว escalate และรักษาหลักฐาน แทนการ `taskkill` แล้วลบทิ้ง (ตามบทระเบียบวิธีเรื่องลำดับความผันผวนของหลักฐาน)
- **ปิดผิดโปรเซสเสียหายจริง:** `taskkill /F /IM` กับชื่อซ้ำหลายตัว หรือโปรเซสระบบ ตรวจ PID ก่อนทุกครั้ง
- **sfc/DISM/chkdsk ต้องใช้สิทธิ์ผู้ดูแล:** รันเฉพาะเมื่อจำเป็น ปิดหน้าต่างเมื่อเสร็จ
- **chkdsk /r กับดิสก์ที่กำลังจะพัง:** สำรองข้อมูลก่อนเสมอ
- **`systeminfo` เปิดเผยระดับแพตช์:** ผู้โจมตีใช้เทียบกับช่องโหว่ที่รู้จัก ผู้ดูแลใช้ตรวจว่าแพตช์ครบ

## ลงมือทำจริง (อ่านอย่างเดียว ปลอดภัย)

ใช้เครื่อง Windows ของตัวเอง

1. **ตาราง lease:** รัน `ipconfig /all` จด `Lease Obtained` และ `Lease Expires` คำนวณเวลาเช่าทั้งหมด แล้วหา T1 (50%) และ T2 (87.5%) ว่าเป็นเวลาอะไร
2. **แคช DNS:** รัน `ipconfig /displaydns | more` เปิดเว็บใหม่หนึ่งเว็บ แล้วดูว่ามีรายการใหม่เพิ่มเข้ามาไหม ดูค่า `Time To Live` ของรายการ แล้วอ่านไฟล์ hosts ด้วย `type C:\Windows\System32\drivers\etc\hosts`
3. **โปรเซส:** เปิด Notepad รัน `tasklist | findstr notepad` หา PID แล้วรัน `tasklist /SVC /FI "IMAGENAME eq svchost.exe"` นับว่า `svchost.exe` ตัวเดียวโฮสต์กี่บริการ
4. **ตรวจไฟล์ระบบแบบไม่แก้:** เปิดแบบผู้ดูแลแล้วรัน `sfc /verifyonly` และ `fsutil dirty query C:`
5. **เวลาบูตและ RAM:** `systeminfo | findstr /B /C:"System Boot Time" /C:"Total Physical Memory" /C:"Available Physical Memory"` แล้วคำนวณเปอร์เซ็นต์ RAM ที่ใช้
6. **เขียน ticket:** สมมติเครื่องได้ IP 169.254.x.x เขียน ticket 4 ส่วน (อาการ สาเหตุที่ตรวจพบ ขั้นแก้ ผลลัพธ์) โดยระบุคำสั่งที่ใช้เป็นหลักฐาน

::reveal{question="แนวคำตอบข้อ 1 (คำนวณ T1 และ T2 จาก lease)"}
สมมติ Lease Obtained = 08:00 และ Lease Expires = 08:00 ของวันถัดไป เวลาเช่า = 24 ชั่วโมง T1 = 08:00 + 12 ชม. = 20:00 (ต่ออายุกับเซิร์ฟเวอร์เดิมแบบ unicast) T2 = 08:00 + 21 ชม. = 05:00 วันถัดไป (ถ้ายังไม่ได้ต่อ เปลี่ยนเป็น broadcast หาเซิร์ฟเวอร์ใดก็ได้) บางเครือข่ายตั้ง lease สั้นเป็นชั่วโมง เช่น 8 ชม. จะได้ T1 = 4 ชม. และ T2 = 7 ชม.
::

::reveal{question="แนวคำตอบข้อ 3 (svchost.exe โฮสต์กี่บริการ)"}
ผลของ `tasklist /SVC` จะแสดงชื่อบริการหลายตัวต่อท้ายแต่ละ `svchost.exe` (จำนวนขึ้นกับเครื่อง) เหตุที่ Windows รวมบริการไว้ในโปรเซสเดียวคือประหยัดหน่วยความจำและเวลาสร้างโปรเซส แต่ข้อเสียคือถ้าโปรเซสหนึ่งล้ม บริการที่อยู่ร่วมกันล้มตามกัน และชื่อโปรเซสเดียวไม่บอกว่าบริการไหนกินทรัพยากร ต้องใช้ `/SVC` ช่วยแยก
::

| Component store (WinSxS) | คอมโพเนนต์สโตร์ | คลังสำเนาต้นฉบับของส่วนประกอบ Windows |

| chkdsk | เช็กดิสก์ | เครื่องมือตรวจระบบไฟล์และเซกเตอร์เสียของดิสก์ |
| Journal ($LogFile) | เจอร์นัล | บันทึกการเปลี่ยนแปลง metadata ของ NTFS ใช้กู้เมื่อดับกลางคัน |
| Dirty bit | เดอร์ตีบิต | ธงบนวอลลุ่มที่บอกว่าอาจไม่สะอาด ทำให้ autochk ตรวจตอนบูต |
| Bad sector | แบดเซกเตอร์ / เซกเตอร์เสีย | ส่วนของดิสก์ที่อ่านหรือเขียนไม่ได้ |
| Volume | วอลลุ่ม | พาร์ทิชัน/ไดรฟ์ที่ฟอร์แมตแล้ว เช่น C: |
| Elevated | อีลิเวเต็ด / สิทธิ์ยกระดับ | รันแบบผู้ดูแล (Run as administrator) |
| Pipe / findstr | ไปป์ / ไฟนด์สตริง | ตัวเชื่อมเอาต์พุตของคำสั่งหนึ่งเข้าอีกคำสั่ง / คำสั่งกรองบรรทัดที่ตรงกับข้อความ |

## ตรวจความเข้าใจ

::reveal{question="เครื่องขึ้นสถานะต่อ Wi-Fi แล้ว แต่ ipconfig แสดง IPv4 Address เป็น 169.254.37.201 และ Default Gateway ว่าง หมายความว่าอย่างไร ควรทำอะไรต่อ"}
เครื่องขอ IP จากเซิร์ฟเวอร์ DHCP แล้วไม่มีใครตอบ Windows จึงตั้ง IP ชั่วคราวช่วง APIPA (169.254.x.x) ให้เอง ซึ่งไม่มีเกตเวย์จึงออกอินเทอร์เน็ตไม่ได้ ปัญหาอยู่ที่ขั้นขอ IP ไม่ใช่เว็บหรือ DNS ลอง `ipconfig /renew` ตรวจว่าเชื่อม Wi-Fi/สายจริง และดูว่าเราเตอร์/DHCP ทำงานอยู่ไหม เช่น เครื่องอื่นได้ IP ปกติหรือไม่ ถ้าหลายเครื่องเป็นพร้อมกัน แสดงว่าจุดร่วมเสีย (เซิร์ฟเวอร์ DHCP/สวิตช์)
::

::reveal{question="lease 12 ชั่วโมง เครื่องเริ่มเช่าเวลา 09:00 จะต่ออายุกับเซิร์ฟเวอร์เดิมเมื่อไร และจะเปลี่ยนเป็น broadcast หา server อื่นเมื่อไร ถ้าเซิร์ฟเวอร์ดับตั้งแต่ 10:00 เครื่องนี้จะเสียเครือข่ายเมื่อไรที่เร็วที่สุด"}
T1 = 50% = 6 ชม. ต่อมาเวลา 15:00 (unicast ไปที่เซิร์ฟเวอร์เดิม) T2 = 87.5% = 10.5 ชม. คือ 19:30 (เปลี่ยนเป็น broadcast) หมดสัญญาที่ 21:00 ถ้าเซิร์ฟเวอร์ดับตั้งแต่ 10:00 และไม่มีเซิร์ฟเวอร์ตัวอื่น เครื่องนี้ยังใช้ IP เดิมได้ถึง 21:00 จึงตกไป APIPA ผลคือผู้ใช้ไม่รู้สึกทันที แต่เครื่องที่เปิดใหม่หลัง 10:00 จะไม่ได้ IP เลย
::

::reveal{question="ผู้ใช้เปิดเมนู Settings แล้วแอปค้างหลังไฟดับกลางคัน สงสัยไฟล์ระบบเสีย ควรรันคำสั่งใดก่อน และต้องเปิด Command Prompt แบบไหน"}
`sfc /scannow` (หรือ `sfc /verifyonly` ถ้าอยากสำรวจก่อน) ใน Command Prompt แบบผู้ดูแล (Run as administrator) เพราะ sfc ตรวจและแก้ไฟล์ระบบที่ได้รับการป้องกัน ไม่ใช่ `ipconfig` (เรื่องเครือข่าย) หรือ `taskkill` (ปิดโปรเซสไม่ได้ซ่อมไฟล์) ถ้ารายงานว่าพบแต่ซ่อมไม่ได้ ให้ใช้ `DISM /Online /Cleanup-Image /RestoreHealth` แล้วรัน sfc ซ้ำ
::

::reveal{question="ทำไมต้องรัน DISM ก่อน sfc ซ้ำ เมื่อ sfc ซ่อมไม่สำเร็จ ลำดับ sfc ก่อน DISM กับ DISM ก่อน sfc ต่างกันอย่างไร"}
เพราะ sfc ซ่อมโดยคัดลอกไฟล์สะอาดจาก component store ถ้าคลังเองเสียหาย ก็ไม่มีไฟล์ดีให้เอาไปแทน DISM ซ่อมคลังนั้น เมื่อคลังสมบูรณ์แล้ว sfc จึงซ่อมไฟล์ที่ใช้งานอยู่ได้ ถ้าเริ่มด้วย DISM ก่อนจะเสียเวลาน้อยลงกรณีที่ sfc ต้องล้มเหลวอยู่แล้ว แต่ถ้าไฟล์เสียเพียงไม่กี่ไฟล์และคลังดี sfc อย่างเดียวก็พอ ทั้งสองลำดับให้ผลสุดท้ายเดียวกัน ต่างที่เวลาที่เสีย
::

::reveal{question="chkdsk C: /f ต่างจาก chkdsk C: /r อย่างไร และทำไมกับไดรฟ์ C: จึงมีคำถามให้รีสตาร์ต"}
`/f` แก้ข้อผิดพลาดของโครงสร้างระบบไฟล์ (ระดับตรรกะ, Stage 1–3) ส่วน `/r` ทำ `/f` และสแกนทุกเซกเตอร์ (Stage 4–5) เพื่อหาจุดเสียทางกายภาพ ใช้เวลานานกว่ามาก ไดรฟ์ C: ถูกระบบและโปรแกรมใช้อยู่จึงล็อกวอลลุ่มไม่ได้ Windows ถามว่าจะนัดตรวจตอนเปิดเครื่องครั้งหน้า (autochk) ไหม
::

::reveal{question="ทำไม taskkill บางกรณีต้องใช้ /F และทำไมต้องระวัง อธิบายด้วยสิ่งที่เกิดขึ้นในระบบ"}
แบบปกติ taskkill ส่งข้อความปิดหน้าต่าง (WM_CLOSE) ให้โปรแกรมจัดการเอง โปรแกรมที่ค้างไม่อ่านคิวข้อความหรือไม่มีหน้าต่างจึงไม่ตอบ `/F` ให้เคอร์เนลยุติโปรเซสทันที (TerminateProcess) โดยโปรแกรมไม่ได้รันโค้ดปิดตัว ข้อมูลที่ยังไม่บันทึกหาย ไฟล์ชั่วคราวไม่ถูกล้าง และไม่ควรใช้กับโปรเซสระบบ ควรลองแบบไม่ใส่ /F ก่อนและแจ้งผู้ใช้ก่อนบังคับปิด
::

::reveal{question="ต้องการปิดโปรแกรมที่มีโปรเซสหลักและโปรเซสลูกหลายตัวพร้อมกัน ควรใช้ตัวเลือกใด และมีข้อควรระวังอะไรเมื่อระบุด้วยชื่อ (/IM)"}
ใช้ `/T` ปิดโปรเซสนั้นพร้อมลูกทั้งหมด เพราะ Windows ไม่ปิดลูกตามพ่อแม่ให้โดยอัตโนมัติ ถ้าไม่ใส่ โปรเซสลูกอาจค้างกินทรัพยากรต่อ เมื่อระบุด้วย `/IM` จะปิดทุกโปรเซสที่ชื่อเดียวกัน ซึ่งอาจรวมของผู้ใช้อื่นหรือหลาย instance ที่ไม่ได้ตั้งใจ ถ้าต้องการตรงตัวให้ใช้ `/PID` หลังตรวจด้วย `tasklist` ซ้ำ เพราะ PID ถูกนำกลับมาใช้ได้
::

::reveal{question="ทำไมหลังไฟดับ Windows ส่วนใหญ่บูตขึ้นได้ปกติโดยไม่ต้องรัน chkdsk เอง แต่บางครั้งก็ยังเจอไฟล์เสียหาย"}
NTFS ทำ journaling ของ metadata ($LogFile) ตอนบูตจึงเล่นบันทึกซ้ำหรือย้อนกลับให้โครงสร้างสอดคล้อง และถ้าสงสัยว่ายังไม่สะอาดจะติด dirty bit ให้ autochk ตรวจ แต่ journal ป้องกันเฉพาะ metadata ไม่ได้รับประกันเนื้อหาไฟล์ที่เขียนค้าง ไฟล์ที่กำลังถูกบันทึกขณะไฟดับจึงอาจเสียหรือสั้นกว่าเดิมได้ และ journal ช่วยอะไรไม่ได้เมื่อความเสียหายมาจากฮาร์ดแวร์
::

::reveal{question="ต้องการดูเฉพาะ RAM รวมและ RAM ที่ว่างของเครื่องด้วยคำสั่งเดียว ทำอย่างไร และคำนวณเปอร์เซ็นต์ที่ใช้ถ้าได้ 8,192 MB และ 2,048 MB"}
`systeminfo | findstr /B /C:"Total Physical Memory" /C:"Available Physical Memory"` (`/B` ตรงต้นบรรทัด, `/C:` ใช้ข้อความรวมช่องว่าง) ใช้ไป = 8,192 − 2,048 = 6,144 MB คิดเป็น 75% ว่างเหลือ 25% ยังไม่ต่ำกว่าเกณฑ์หยาบ 10% แต่ควรดูโปรเซสที่กินมากด้วย `tasklist`
::

::reveal{question="ผู้ใช้เจอโปรเซสชื่อ svch0st.exe (เลขศูนย์แทนตัว o) กินหน่วยความจำสูง ควรปิดทันทีด้วย taskkill /F หรือไม่ เพราะอะไร"}
ไม่ควรปิดแล้วจบ ชื่อที่สะกดเลียนแบบ svchost.exe เป็นสัญญาณมัลแวร์ที่ปลอมตัวเป็นไฟล์ระบบ ให้บันทึกข้อมูล (PID, ตำแหน่งไฟล์, เวลา) แล้ว escalate ให้ทีม Security เพราะการปิดหรือลบทิ้งอาจทำลายหลักฐาน และมัลแวร์อาจกลับมาหรือมีส่วนอื่นซ่อนอยู่ ควรแยกเครื่องออกจากเครือข่ายตามขั้นตอนขององค์กร
::

::reveal{question="ผู้ใช้ทั้งชั้นได้ 169.254.x.x พร้อมกันตอนเช้า ช่างคนหนึ่งเสนอให้เดินสั่ง ipconfig /renew ทีละเครื่อง อีกคนเสนอให้ตรวจที่เซิร์ฟเวอร์ DHCP ก่อน ใครถูก เพราะอะไร"}
คนที่สองถูก เพราะอาการเกิดพร้อมกันหลายเครื่อง แปลว่าสาเหตุอยู่ที่จุดร่วม (เซิร์ฟเวอร์ DHCP, สวิตช์ หรือ VLAN ที่ใช้ร่วมกัน) ไม่ใช่เครื่องแต่ละเครื่อง การ renew ทีละเครื่องจะล้มเหมือนกันและเสียเวลา ควรทดสอบที่ต้นทางก่อน เช่น เซิร์ฟเวอร์ DHCP ทำงานอยู่ไหม pool ที่อยู่หมดหรือยัง แล้วค่อยให้ทุกเครื่อง renew หลังแก้ ซึ่งสอดคล้องกับหลัก "แบ่งครึ่ง/หาจุดร่วม" ในบทระเบียบวิธี
::

## สรุป

- คำสั่งทุกตัวคือหน้าต่างมองตารางสถานะของระบบ เลือกคำสั่งจาก "ตารางที่น่าจะเสียตามอาการ" แล้วใช้โหมดอ่านอย่างเดียวก่อน
- `ipconfig` อ่าน IP, mask, gateway และสัญญาเช่า DHCP (DORA, T1=50%, T2=87.5%) ถ้าได้ 169.254.x.x คือ APIPA = ขั้นขอ IP ล้ม `/renew` ขอใหม่ `/flushdns` ล้างแคช DNS ที่เก็บตาม TTL (hosts ถูกตรวจก่อน DNS)
- `tasklist` หา PID (ใช้ซ้ำได้ ตรวจก่อนสั่ง) `taskkill` แบบปกติส่ง WM_CLOSE ให้โปรแกรมจัดการเอง `/F` ให้เคอร์เนลตัดจบ (ข้อมูลที่ไม่เซฟหาย) `/T` ปิดลูกพร้อมกัน
- `sfc /scannow` ซ่อมไฟล์ที่ใช้งานจาก component store ถ้าคลังเสีย ใช้ `DISM /RestoreHealth` ซ่อมคลังแล้ว `sfc` ซ้ำ (ลำดับ DISM ก่อนก็ใช้ได้)
- NTFS มี journal ป้องกัน metadata และ dirty bit ให้ autochk ตรวจตอนบูต `chkdsk` อ่านอย่างเดียวโดยปกติ `/f` แก้ตรรกะ `/r` อ่านทุกเซกเตอร์ (HDD 1 TB อย่างน้อยราว 2.3 ชม. ค่าประมาณ) ไดรฟ์ระบบต้องรอรีสตาร์ต สำรองข้อมูลก่อนเสมอ
- `systeminfo` + `findstr` ดึงข้อมูลเครื่อง คำนวณ RAM ที่ใช้ได้ (6,732 ÷ 16,142 ≈ 41.7% ในตัวอย่าง)
- ผู้โจมตีใช้คำสั่งเดียวกันสำรวจและปิดการป้องกัน (T1016, T1057, T1082, T1562.001) บันทึก command line, เปิด Tamper Protection, ใช้ DHCP snooping, รักษาหลักฐานก่อนปิดโปรเซสที่น่าสงสัย
