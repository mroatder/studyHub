## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **ทำไม** ค่าเริ่มต้นของระบบจึงเน้นความสะดวกมากกว่าความปลอดภัย และนิยาม **พื้นผิวโจมตี (attack surface)** ได้
2. ตรวจว่าเครื่องเปิดอะไรรอรับการเชื่อมต่ออยู่ (`ss -tulpn`) และอ่านความต่างของ `0.0.0.0` กับ `127.0.0.1` ได้
3. อธิบาย **least privilege**, sudo, และข้อดีของกุญแจ SSH เหนือรหัสผ่าน พร้อมคำนวณเวลาเดารหัสผ่านได้
4. ตั้งไฟร์วอลล์แบบ **default deny** โดยเรียงลำดับไม่ให้ล็อกตัวเองออก
5. อธิบายว่าสิทธิ์ไฟล์ และ **full-disk encryption** ป้องกันภัยอะไรและไม่ป้องกันอะไร
6. อธิบาย **ช่วงเวลาเปิดช่องโหว่** ของการแพตช์ และอ่าน log ล็อกอินล้มเหลวของ Linux/Windows ได้
7. แมปมาตรการ hardening กับการโจมตีจริง และบอกข้อจำกัดของ hardening ได้

## สรุปสั้น (TL;DR)

- ระบบที่เพิ่งติดตั้งตั้งค่าไว้ให้ **ใช้งานง่ายสำหรับทุกบทบาท** จึงมีบริการ พอร์ต บัญชีเกินที่เครื่องหนึ่งๆ ต้องใช้ ทุกอย่างที่เกินคือทางเข้าของผู้โจมตี
- **Hardening = ลดพื้นผิวโจมตี**: ถอด/ปิดสิ่งที่ไม่ต้องใช้, ให้สิทธิ์น้อยที่สุด, ปิดทางเข้าเครือข่ายที่ไม่จำเป็น, แพตช์, เข้ารหัสข้อมูลที่พัก, และบันทึกเหตุการณ์ไว้ตรวจ
- ลำดับคิด: **บทบาทของเครื่องคืออะไร → อะไรจำเป็นต่อบทบาทนั้น → ที่เหลือปิด**
- **ไฟร์วอลล์:** default deny + อนุญาตเฉพาะที่จำเป็น และ *อนุญาตช่องทางดูแลก่อนเปิดใช้* ไม่งั้นล็อกตัวเองออก
- **กุญแจ SSH ปิดช่องเดารหัสผ่าน** โดยหลักการ ส่วนรหัสผ่านสุ่มยาวก็ยังไม่ปลอดภัยพอหากถูกใช้ซ้ำหรือรั่ว
- **เข้ารหัสดิสก์ป้องกันตอนเครื่องปิด/ถูกขโมย** ไม่ช่วยตอนระบบเปิดและถูกโจมตีผ่านเครือข่าย
- hardening **ไม่ใช่จุดสิ้นสุด** เป็นการลดโอกาสและความเสียหาย ไม่ได้ทำให้ปลอดภัย 100% และต้องแลกกับความสะดวก/ความพร้อมใช้งาน

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | สิ่งที่เทียบได้ |
|---|---|
| บ้านใหม่ที่ผู้รับเหมาทำประตูหน้าต่างทุกบานแบบเปิดง่ายและเก็บกุญแจสำรองไว้ใต้กระถาง | ค่าเริ่มต้นของระบบหลังติดตั้ง |
| ปิดหน้าต่างและประตูที่ไม่ได้ใช้ ถอดกุญแจสำรองทิ้ง | ปิดบริการ/พอร์ต/บัญชีที่ไม่จำเป็น |
| ให้ช่างได้กุญแจเฉพาะห้องที่ต้องซ่อม ไม่ใช่กุญแจทั้งบ้าน | least privilege |
| ยามหน้าประตูให้เข้าเฉพาะคนที่อยู่ในรายชื่อ | ไฟร์วอลล์ default deny |
| ตู้เซฟยึดกับพื้น: ขโมยยกบ้านไปก็เปิดไม่ได้ แต่ถ้าเจ้าของเปิดตู้ค้างไว้ก็ไม่ช่วย | เข้ารหัสดิสก์ |
| กล้องวงจรปิดที่ส่งภาพออกไปเก็บนอกบ้าน | log ส่งไปเครื่องกลาง |

## 1. ทำไมต้อง hardening: หลักการพื้นฐาน

### 1.1 ค่าเริ่มต้นถูกออกแบบให้ "ใช้ได้กับทุกคน"

ผู้ผลิตระบบปฏิบัติการไม่รู้ว่าเครื่องคุณจะเป็นเว็บเซิร์ฟเวอร์ คอมพิวเตอร์พนักงาน หรือเครื่องฐานข้อมูล จึงเปิดไว้ก่อนให้ครอบคลุม: บริการพิมพ์ บริการแชร์ไฟล์ เครื่องมือวินิจฉัย บัญชีเริ่มต้น เพราะ "เปิดแล้วใช้ได้เลย" ลดเรื่องร้องเรียนจากผู้ใช้ แต่ **ทุกอย่างที่เปิดมีโค้ดที่อาจมีบั๊ก มีสิทธิ์ที่อาจถูกยึด และมีช่องเครือข่ายที่ผู้โจมตีเข้าถึงได้**

### 1.2 พื้นผิวโจมตี (attack surface)

**พื้นผิวโจมตี** คือผลรวมของทุกจุดที่ผู้ไม่หวังดีโต้ตอบกับระบบได้: พอร์ตที่ฟังอยู่ บริการที่รัน บัญชีที่ล็อกอินได้ ไฟล์ที่เขียนได้ ซอฟต์แวร์ที่ติดตั้ง หลักคิดตรงไปตรงมา:

> ความเสี่ยงรวม ≈ Σ (โอกาสที่แต่ละจุดมีช่องโหว่ × ความเสียหายถ้าจุดนั้นถูกยึด × ความเข้าถึงได้ของผู้โจมตี)

เราลดได้สามทาง: **ลดจำนวนจุด** (ถอดของที่ไม่ใช้), **ลดความเข้าถึง** (จำกัดว่าใครเรียกใช้ได้ เช่น ฟังเฉพาะ localhost หรือบล็อกที่ไฟร์วอลล์), **ลดความเสียหาย** (ให้สิทธิ์น้อย แยกเครื่อง) หลักการที่อยู่เบื้องหลัง:

- **Minimal TCB / ลดโค้ดที่ต้องไว้ใจ:** โค้ดที่ไม่มีอยู่ ไม่มีบั๊ก
- **Least privilege:** ถ้าโปรเซสถูกยึด ผู้โจมตีได้เท่าสิทธิ์ของโปรเซสนั้นเท่านั้น
- **Defense in depth:** ไม่พึ่งชั้นเดียว ไฟร์วอลล์พลาด สิทธิ์และการเข้ารหัสยังช่วยได้
- **Fail-safe default:** ค่าเริ่มต้นต้องเป็น "ปฏิเสธ" แล้วค่อยอนุญาตเป็นรายกรณี (บท 13, 22 เห็นหลักนี้แล้ว)

## 2. ลดพื้นผิวโจมตี: บริการและพอร์ต

### 2.1 พอร์ตที่ฟังอยู่คืออะไร (ทบทวนบท 13)

บริการที่รอรับการเชื่อมต่อสร้าง **listening socket** ผูกกับที่อยู่ IP และพอร์ต เคอร์เนลส่งแพ็กเก็ตที่ตรงเข้าโปรเซสนั้น ที่อยู่ที่ผูกสำคัญมาก

| Local Address | ความหมาย | ใครเข้าถึงได้ |
|---|---|---|
| `127.0.0.1:3306` | loopback (บท 14) | เฉพาะโปรแกรมบนเครื่องเดียวกัน |
| `192.168.1.10:3306` | ผูกกับการ์ดเครือข่ายเดียว | เครื่องที่ถึงที่อยู่นั้นได้ |
| `0.0.0.0:631` | ทุกอินเทอร์เฟซ IPv4 | ทุกคนที่ส่งแพ็กเก็ตมาถึง (ถ้าไม่มีไฟร์วอลล์กั้น) |
| `[::]:631` | ทุกอินเทอร์เฟซ IPv6 | เช่นเดียวกัน อย่าลืมตรวจ IPv6 ด้วย |

**ตัวอย่างจริงว่าทำไมเรื่องเล็กนี้สำคัญ:** บริการพิมพ์เคยมีช่องโหว่ร้ายแรงทั้งบน Windows (PrintNightmare, CVE-2021-34527, ใช้ยกระดับสิทธิ์และรันโค้ดผ่านบริการ Print Spooler) และบน Linux (ชุดช่องโหว่ใน CUPS/cups-browsed ที่เปิดเผยปี 2024) เครื่องที่ไม่เคยพิมพ์เอกสารไม่ควรต้องรับความเสี่ยงนี้ ตามหลัก Microsoft ควรปิด Print Spooler บน domain controller และเซิร์ฟเวอร์ที่ไม่ได้ทำหน้าที่พิมพ์

**ฝั่ง Windows** ใช้ PowerShell ตรวจและปิด:

```powershell
Get-Service Spooler | Select Status, StartType
Stop-Service Spooler -PassThru | Set-Service -StartupType Disabled
Get-NetTCPConnection -State Listen | Sort LocalPort | Select LocalAddress, LocalPort, OwningProcess
```

บน Windows Server ถอด role/feature ที่ไม่ใช้ผ่าน Server Manager หรือ `Uninstall-WindowsFeature` ด้วย

> **ข้อควรระวัง:** ก่อนปิดอะไรให้ถามว่า "มีอะไรพึ่งมันอยู่ไหม" ปิดผิดตัวทำให้ระบบล่ม (ผลกระทบด้าน Availability ในบท 23) จึงควรทดลองบนเครื่องทดสอบหรือปิดทีละข้อพร้อมบันทึก เพื่อย้อนกลับได้

## 3. บัญชีและ least privilege

### 3.1 หลักการ

ทุกบัญชี/โปรเซสควรได้สิทธิ์ **เท่าที่ต้องใช้พอดี** เพราะเมื่อมันถูกยึด ผู้โจมตีได้สิทธิ์เดียวกัน บัญชีผู้ดูแลที่ใช้ทำงานประจำวัน (อ่านเมล เปิดเว็บ) คือเป้าหมายที่คุ้มที่สุด

| แนวทาง | ทำไมดี |
|---|---|
| บัญชีส่วนตัวต่อผู้ดูแลหนึ่งคน + `sudo` | log รู้ว่า *ใคร* ยกระดับสิทธิ์เมื่อไร ถ้าแชร์รหัส root จะตามไม่ได้ (accountability, บท 21) |
| `sudo` เฉพาะคำสั่งที่จำเป็น (`/etc/sudoers.d/`) | ไม่ต้องให้สิทธิ์เต็มถ้างานต้องการแค่รีสตาร์ตบริการหนึ่งตัว |
| บัญชีบริการ (service account) ไม่มี shell ล็อกอิน | โปรเซสเว็บที่ถูกยึดอยู่ในบัญชีที่ทำอะไรได้น้อย |
| ลบ/ล็อกบัญชีที่ไม่ใช้ | บัญชีที่ไม่มีใครดูแลคือประตูที่ไม่มีใครสังเกต |
| ปิดบัญชี Guest, บังคับ UAC บน Windows | กันโปรเซสได้สิทธิ์สูงโดยผู้ใช้ไม่รู้ตัว |

**หมายเหตุความแม่นยำ:** ต้นฉบับกล่าวถึง "root ที่เปิดอยู่เป็นค่าเริ่มต้น" ซึ่งไม่ใช่ทุกดิสทริบิวชัน เช่น Ubuntu ล็อกรหัสผ่านของ root ไว้ตั้งแต่ต้น ให้ใช้ sudo อยู่แล้ว สิ่งที่ต้องตรวจจริงคือการตั้งค่า SSH ของเครื่องนั้น

### 3.2 SSH: รหัสผ่านเทียบกุญแจ

ทำไมกุญแจดีกว่า? เพราะรหัสผ่าน *เป็นความลับที่ผู้โจมตีเดาได้ซ้ำๆ จากระยะไกล* ส่วนกุญแจใช้ **การพิสูจน์ว่ามีกุญแจส่วนตัว** โดยที่กุญแจส่วนตัวไม่เคยออกจากเครื่องผู้ใช้ (เชื่อมกับ DH/ลายเซ็นในบท 24)

**คำนวณ: เวลาเดารหัสผ่านออนไลน์** ถ้าผู้โจมตีทดลองได้ r ครั้ง/วินาที ต้องลองเฉลี่ยครึ่งหนึ่งของพื้นที่ค้นหา (ตรวจด้วย node)

| รหัสผ่านสุ่ม | จำนวนความเป็นไปได้ | เวลาเฉลี่ยที่ 10 ครั้ง/วินาที (ค่าประมาณ) |
|---|---|---|
| ตัวเลข 6 หลัก | 10⁶ | ราว 14 ชั่วโมง |
| ตัวพิมพ์เล็ก 8 ตัว | 2.1×10¹¹ | ราว 330 ปี |
| อักษรผสม 8 ตัว (62 แบบ) | 2.2×10¹⁴ | ราว 3.5×10⁵ ปี |
| อักษรผสม 12 ตัว | 3.2×10²¹ | ราว 5×10¹² ปี |
| กุญแจ Ed25519 | ความปลอดภัยราว 2¹²⁸ | ที่ 10¹² ครั้ง/วินาที ราว 5×10¹⁸ ปี |

ตัวเลขนี้ชวนให้คิดว่ารหัสผ่านสุ่มยาวก็พอ **แต่ในความจริงมนุษย์ไม่เลือกรหัสแบบสุ่ม** ผู้โจมตีจึงไม่เดาทุกความเป็นไปได้ แต่ลอง *รหัสที่คนใช้บ่อย* (พันอันดับแรก) หรือรหัสที่รั่วจากเว็บอื่น (credential stuffing): 1,000 รหัส ที่ 10 ครั้ง/วินาที ใช้เวลาแค่ ~100 วินาที (ไม่รวมการหน่วง/การล็อกบัญชี) ข้อสรุป: **ปัญหาไม่ใช่ความยาวของพื้นที่ แต่คือรหัสผ่านที่คนตั้ง** กุญแจตัดทั้งการเดาและการใช้ซ้ำออกไป

ตั้งค่าใน `/etc/ssh/sshd_config`:

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
```

ลำดับที่ปลอดภัย: (1) ใส่กุญแจสาธารณะของผู้ดูแลก่อน (`ssh-copy-id`) (2) *เปิดเซสชันที่สองค้างไว้* (3) ตรวจไวยากรณ์ `sudo sshd -t` (4) รีโหลดบริการ (5) ทดสอบล็อกอินใหม่จากเครื่องอื่นก่อนปิดเซสชันเดิม เสริมด้วยเครื่องมือจำกัดการลองซ้ำเช่น fail2ban และการยืนยันตัวตนหลายปัจจัยตามบท 22

### 3.3 บน Windows

- ใช้ Local Security Policy / Group Policy กำหนดนโยบายรหัสผ่านและ **account lockout** (ล็อกชั่วคราวหลังพลาดหลายครั้ง) ปิด Guest
- เปิด UAC ให้ถามก่อนยกระดับสิทธิ์ และใช้บัญชีมาตรฐานทำงานประจำวัน
- การเปลี่ยนชื่อบัญชี Administrator (`Rename-LocalUser`) เป็น *ข้อเสริมที่ค่าไม่มาก* ผู้โจมตีค้นชื่อจริงได้ด้วยวิธีอื่น (บัญชีนี้มี SID ลงท้าย -500 เสมอ) หลักที่ได้ผลจริงกว่าคือปิดใช้ บัญชี Administrator ในตัวและใช้บัญชีที่ตรวจสอบย้อนหลังได้ รวมถึงเครื่องมือจัดการรหัสผ่านผู้ดูแลท้องถิ่นของแต่ละเครื่อง (เช่น LAPS) เพื่อไม่ให้ทุกเครื่องใช้รหัสเดียวกัน

## 4. ไฟร์วอลล์บนเครื่อง (host firewall)

### 4.1 ทำไมต้องมีบนเครื่องด้วย

ไฟร์วอลล์ที่ขอบเครือข่ายไม่เห็นทราฟฟิกระหว่างเครื่องในซับเน็ตเดียวกัน (บท 15–16 เห็นแล้วว่าเฟรมภายใน LAN ไม่ผ่านเกตเวย์) ถ้าเครื่องหนึ่งถูกยึด มันสแกนเครื่องข้างเคียงได้ทันที ไฟร์วอลล์บนเครื่องคือชั้นสุดท้ายที่ทำให้ **พอร์ตที่เผลอเปิดไม่ถึงผู้โจมตี** และเป็นหลัก defense in depth

### 4.2 กลไก: กฎเรียงลำดับ + นโยบายค่าเริ่มต้น

เคอร์เนลตรวจแต่ละแพ็กเก็ตกับกฎ *จากบนลงล่าง* ตรงกฎแรกก็จบ ไม่ตรงอะไรเลยใช้ **นโยบายเริ่มต้น (default policy)** ถ้าตั้ง `default deny incoming` สิ่งที่ไม่ได้ระบุว่าอนุญาตจะถูกทิ้งหมด การเชื่อมต่อขาออกที่เครื่องเป็นผู้เริ่ม ตารางสถานะ (connection tracking) จะจำไว้และปล่อยแพ็กเก็ตตอบกลับเข้ามาให้เอง

```bash
sudo ufw allow 22/tcp                 # 1) อนุญาตช่องทางดูแลก่อน
sudo ufw allow 443/tcp                # ตามบทบาทของเครื่อง
sudo ufw default deny incoming        # 2) ค่าเริ่มต้นปฏิเสธ
sudo ufw default allow outgoing
sudo ufw enable                       # 3) เปิดใช้เป็นขั้นสุดท้าย
sudo ufw status verbose
```

::ufw-lockout
::

**กับดัก:** ถ้าเปิด default deny *ก่อน* อนุญาต 22/tcp เซสชันเดิมอาจยังอยู่ชั่วคราวเพราะตารางสถานะ แต่เมื่อหลุดหรือเปิดเซสชันใหม่ จะเข้าไม่ได้ (ufw จะเตือนว่าอาจกระทบ SSH เดิม) วิธีป้องกัน: จัดลำดับ allow ก่อน deny, จำกัดต้นทางถ้าได้ (`sudo ufw allow from 10.0.5.0/24 to any port 22 proto tcp`), และมีทางเข้าสำรอง เช่น คอนโซลของผู้ให้บริการ

บน Windows ไฟร์วอลล์เปิดอยู่และ block ขาเข้าเป็นค่าเริ่มต้นของโปรไฟล์ส่วนใหญ่ แต่ติดตั้งโปรแกรมมักเพิ่มกฎอนุญาตเองจึงควรตรวจรายการ:

```powershell
Get-NetFirewallProfile | Select Name, Enabled, DefaultInboundAction
Get-NetFirewallRule -Direction Inbound -Action Allow -Enabled True | Select DisplayName, Profile
New-NetFirewallRule -DisplayName "Allow WinRM HTTPS" -Direction Inbound -Protocol TCP -LocalPort 5986 -Action Allow
```

> **ข้อจำกัด:** ไฟร์วอลล์กรองตามพอร์ต/ที่อยู่ ไม่รู้ว่าข้อมูลในพอร์ตที่อนุญาตเป็นการโจมตีหรือไม่ ถ้าเว็บแอปบน 443 มีช่องโหว่ ไฟร์วอลล์ปล่อยผ่านเพราะพอร์ตถูกอนุญาต

## 5. ปกป้องไฟล์และข้อมูลที่พัก

### 5.1 สิทธิ์ไฟล์และไฟล์พิเศษ

ทบทวนบท 7: สิทธิ์ `600` = เจ้าของอ่านเขียน คนอื่นไม่ได้ ใช้กับไฟล์ความลับ (กุญแจส่วนตัว, ไฟล์ `.env` ของแอป) ข้อควรระวังเรื่องความแม่นยำ: ต้นฉบับยกตัวอย่าง `chmod 600 /etc/shadow` แต่บน Debian/Ubuntu ค่าเริ่มต้นคือ `640 root:shadow` (กลุ่ม shadow เป็นกลุ่มของเครื่องมือระบบอย่างตัวตรวจรหัสผ่านที่ต้องอ่านไฟล์) อย่าสั่งเปลี่ยนตามตัวอย่างโดยไม่ตรวจก่อน ให้ **เทียบกับค่าเริ่มต้นของดิสทริบิวชัน** และใช้เครื่องมือตรวจ

ไฟล์ **SUID** (บิตตั้ง uid) รันด้วยสิทธิ์ของ *เจ้าของไฟล์* ไม่ใช่ผู้เรียก ถ้าเป็น root และมีบั๊ก ผู้ใช้ทั่วไปยกระดับเป็น root ได้ ตรวจรายการแล้วเทียบว่าแต่ละตัวจำเป็นไหม:

```bash
find / -xdev -perm -4000 -type f 2>/dev/null
find / -xdev -type f -perm -0002 2>/dev/null   # ไฟล์ที่ทุกคนเขียนได้
```

**ข้อจำกัดที่ต้องรู้ (ไม่อ้างเกินจริง):**

- ป้องกัน **ข้อมูลที่พัก (data at rest)** เมื่อเครื่องปิด/ถูกขโมย ไม่ป้องกันผู้โจมตีผ่านเครือข่ายขณะระบบเปิด เพราะตอนนั้นวอลุ่มถูกปลดล็อกและระบบถอดรหัสให้โปรเซสทุกตัวที่มีสิทธิ์
- กุญแจอยู่ใน RAM ขณะเครื่องทำงาน จึงมีการโจมตีแบบ cold boot และ DMA (บท 1) โดยเฉพาะเครื่อง *พักการทำงาน (sleep)*; เครื่องพกพาควรใช้ hibernate/ปิดเครื่อง และตั้ง PIN
- กุญแจกู้คืนต้องเก็บแยกที่ปลอดภัย (ไม่ใช่ในเครื่องเดียวกัน) หายแล้วข้อมูลหายถาวร
- มีผลต่อประสิทธิภาพเล็กน้อย (ซีพียูสมัยใหม่มีชุดคำสั่ง AES-NI ทำให้ส่วนใหญ่ไม่เด่นชัด ค่าประมาณ)

## 6. แพตช์: ช่วงเวลาเปิดช่องโหว่

ซอฟต์แวร์มีบั๊กเสมอ เมื่อช่องโหว่ถูกประกาศ (พร้อมแพตช์) ผู้โจมตีไล่ดูว่าแพตช์แก้อะไร แล้วเขียนโค้ดโจมตีกับเครื่องที่ **ยังไม่แพตช์** ซึ่งทำได้เร็ว (ระดับวันถึงสัปดาห์ ค่าประมาณ ขึ้นกับช่องโหว่) จึงมีแนวคิด **window of exposure**:

> ช่วงเปิดช่องโหว่ = เวลาที่ผู้โจมตีรู้ช่องโหว่ → เวลาที่เครื่องคุณแพตช์เสร็จ

::step-diagram{:steps='[{"title":"1. พบช่องโหว่และผู้ผลิตออกแพตช์","text":"อาจมีผู้โจมตีรู้มาก่อนแล้ว (zero-day: ยังไม่มีแพตช์) หลังประกาศ ทุกคนรู้ รวมผู้โจมตี"},{"title":"2. ผู้โจมตีสร้างโค้ดโจมตีและสแกนหาเป้าหมาย","text":"เครื่องมืออัตโนมัติสแกนทั้งอินเทอร์เน็ตหาเวอร์ชันที่มีช่องโหว่ เครื่องที่เปิดพอร์ตนั้นออกสู่ภายนอกถูกพบก่อน"},{"title":"3. ผู้ดูแลประเมินและทดสอบแพตช์","text":"ตรวจว่าใช้กับระบบเราไหม ทดสอบบนเครื่องจำลองว่าไม่ทำของพัง ขั้นนี้ยิ่งช้า ช่วงเปิดช่องโหว่ยิ่งยาว แต่ข้ามไปเลยเสี่ยงให้ระบบล่ม"},{"title":"4. ติดตั้งในช่วงซ่อมบำรุงและรีสตาร์ตบริการ","text":"ช่องโหว่ระดับร้ายแรงและเข้าถึงได้จากอินเทอร์เน็ตควรเร่ง ที่เหลือตามรอบ บางแพตช์ (เคอร์เนล) ต้องรีบูตจึงมีผล ถ้าไม่รีบูตก็ยังเปิดช่องอยู่"},{"title":"5. ตรวจว่าแพตช์มีผลจริง","text":"เทียบเวอร์ชันหลังแพตช์ สแกนซ้ำ และสำหรับช่องโหว่ที่มีผู้ใช้โจมตีแล้ว ตรวจ log ย้อนหลังด้วยว่าถูกเจาะก่อนแพตช์หรือไม่ เพราะแพตช์ไม่ลบสิ่งที่ผู้โจมตีทิ้งไว้"}]'}
::

```bash
sudo apt update && sudo apt upgrade        # แพตช์ด้วยมือ
sudo apt install unattended-upgrades       # ติดตั้งอัปเดตความปลอดภัยอัตโนมัติ
sudo dpkg-reconfigure -plow unattended-upgrades
[ -f /var/run/reboot-required ] && echo "ต้องรีบูต"
```

ค่าเริ่มต้นของ unattended-upgrades ติดตั้งเฉพาะแพตช์ความปลอดภัย ไม่ใช่อัปเกรดทุกอย่าง ซึ่งเป็นการแลกที่สมเหตุสมผล บน Windows ใช้ Windows Update / WSUS / Intune กำหนดกลุ่มทดสอบก่อนปล่อยทั้งองค์กร (หมายเหตุ: `Get-WindowsUpdate` มาจากโมดูลเสริม PSWindowsUpdate ไม่ได้มากับระบบ)

> **ข้อควรระวัง:** แพตช์ซอฟต์แวร์ที่ผู้ผลิตเลิกสนับสนุนแล้ว (end of life) ไม่มีให้ ทางเลือกคือเปลี่ยนระบบ หรือกั้นเครื่องนั้นให้แน่นหนาที่สุด

## 7. บันทึกเหตุการณ์ (logging) และการตรวจสอบ

## 9. จาก "ทำมือ" สู่ baseline ที่ตรวจซ้ำได้

ทำมือทีละเครื่องจะพลาดและ drift ได้ องค์กรจึงใช้:

- **Baseline มาตรฐาน:** CIS Benchmarks, DISA STIG, Microsoft Security Baselines เป็นรายการค่าตั้งที่ผ่านการทบทวนจากชุมชน มีระดับ (เช่น Level 1 ใช้ได้ทั่วไป, Level 2 เข้มงวดกว่าและอาจกระทบการใช้งาน)
- **เครื่องมือตรวจ:** `lynis audit system`, OpenSCAP บน Linux; Security Compliance Toolkit บน Windows ให้คะแนนและรายการที่ต้องแก้
- **ระบุเป็นโค้ด:** Ansible, Group Policy, Intune ใช้นโยบายเดียวกันกับทุกเครื่องและตรวจ drift ได้
- **Golden image:** เตรียมอิมเมจที่เสริมความแข็งแรงแล้วใช้ติดตั้งทุกเครื่อง

**การแลกเปลี่ยน (trade-off):** ทุกมาตรการลดความสะดวกหรือความพร้อมใช้งาน บริการที่ถูกปิดอาจมีคนใช้ ไฟร์วอลล์เข้มอาจบล็อกแอปที่ชอบ การเข้ารหัสทำให้กู้ข้อมูลยากขึ้นเมื่อลืมกุญแจ จึงต้องมี **การทดสอบก่อน, แผนย้อนกลับ, และบันทึกเหตุผลของข้อยกเว้น** อย่า hardening ตามรายการสำเร็จรูปแบบปิดตา

**ข้อจำกัดของ hardening:** ลดความเสี่ยงที่รู้ ไม่ครอบคลุม zero-day, ช่องโหว่ในแอปที่คุณเขียนเอง, ผู้ใช้ที่ถูกหลอก (phishing), หรือผู้ไม่หวังดีภายใน จึงเป็น *หนึ่งในหลายชั้น* ร่วมกับการสำรองข้อมูล (backup), การเฝ้าระวัง และแผนรับมือเหตุการณ์

## 10. มุมมอง Security: แมปการโจมตีกับมาตรการ

| การโจมตี/ปัญหา | กลไกที่ถูกโจมตี | มาตรการที่ตรงจุด |
|---|---|---|
| สแกนพอร์ตแล้วเจาะบริการที่ไม่ใช้ (เช่น spooler, FTP) | พื้นผิวโจมตีเกินบทบาท | ถอด/ปิดบริการ, ไฟร์วอลล์ default deny |
| brute force / credential stuffing บน SSH, RDP | รหัสผ่านที่เดาหรือใช้ซ้ำ | กุญแจ SSH, MFA, account lockout, fail2ban, ไม่เปิด RDP ออกอินเทอร์เน็ต |
| โจมตีช่องโหว่ที่ประกาศแล้ว (เช่นแรนซัมแวร์ที่ใช้ SMB) | แพตช์ไม่ครบ | แพตช์อัตโนมัติ, สแกนเวอร์ชัน, ปิด SMBv1 และปิดพอร์ต 445 ขาเข้าจากภายนอก |
| ยกระดับสิทธิ์ (local privilege escalation) | SUID/บริการสิทธิ์สูง/สิทธิ์ไฟล์หละหลวม | ตรวจ SUID, least privilege, บัญชีบริการสิทธิ์ต่ำ |
| ขโมยเครื่อง/ดิสก์ | ข้อมูลที่พักไม่เข้ารหัส | LUKS/BitLocker + TPM + PIN |
| ลามไปเครื่องอื่น (lateral movement) | เครื่องในซับเน็ตเดียวกันเชื่อใจกัน | ไฟร์วอลล์บนเครื่อง, VLAN/DMZ (บท 16), รหัสผู้ดูแลไม่ซ้ำกันทุกเครื่อง |
| ผู้โจมตีลบร่องรอย | log อยู่ในเครื่องที่ถูกยึด | ส่ง log ออกนอกเครื่อง, แจ้งเตือน event 1102 |

## 11. ตัวอย่างวิเคราะห์ปัญหา IT Support

| อาการ | สาเหตุที่เป็นไปได้ (กลไก) | ตรวจ/แก้ |
|---|---|---|
| เปิดไฟร์วอลล์แล้ว SSH/RDP เข้าไม่ได้ | เปิด default deny โดยไม่มีกฎอนุญาตพอร์ตดูแล (ขั้นตอนผิดลำดับ) | เข้าทางคอนโซล `ufw allow 22/tcp` ก่อน แล้วค่อยเปิดใช้ |
| ปิดล็อกอินด้วยรหัสผ่านแล้วผู้ดูแลเข้าไม่ได้ | ยังไม่ได้ใส่กุญแจสาธารณะใน `authorized_keys` หรือสิทธิ์โฟลเดอร์ `~/.ssh` กว้างเกิน (sshd ปฏิเสธ) | ตรวจ `~/.ssh` เป็น 700, `authorized_keys` 600, ดู log `journalctl -u ssh` |
| แอปบนอีกเครื่องต่อฐานข้อมูลไม่ได้หลัง bind localhost | MySQL ฟังเฉพาะ 127.0.0.1 จึงไม่รับจากเครือข่าย | ผูกกับที่อยู่ภายในที่ถูกต้อง + จำกัดด้วยไฟร์วอลล์ให้เฉพาะเครื่องแอป หรือใช้อุโมงค์ SSH |
| ปิดบริการแล้วระบบ/โปรแกรมอื่นผิดปกติ | มีบริการอื่นพึ่งพา (dependency) | `systemctl list-dependencies --reverse <unit>` ก่อนปิดเสมอ |
| ล็อกอินเครื่องหนึ่ง *บ่อยครั้ง* ล้มเหลวหลายร้อยครั้งต่อวันจาก IP ต่างประเทศ | การสแกน/เดารหัสอัตโนมัติ ปกติสำหรับเครื่องที่เปิดสู่อินเทอร์เน็ต | ปิดรหัสผ่าน, จำกัดต้นทางด้วยไฟร์วอลล์/VPN, fail2ban; ถ้ามี "ล้มเหลวแล้วสำเร็จ" ให้สอบสวนเป็นเหตุการณ์ |
| บูตเครื่องแล้วขอ BitLocker recovery key | ค่าวัดการบูตเปลี่ยน (อัปเดตเฟิร์มแวร์, เปลี่ยนฮาร์ดแวร์/Secure Boot) TPM จึงไม่ปล่อยกุญแจ | กรอกกุญแจกู้คืน (เก็บใน AD/บัญชีองค์กร) ตรวจว่าการเปลี่ยนแปลงมีที่มา |
| แพตช์แล้วบริการล่ม | ความเข้ากันได้ของเวอร์ชันใหม่ | ย้อนแพตช์/สแนปช็อต ตั้งกลุ่มทดสอบก่อนปล่อยทั้งหมด |
| สแกนแล้วพบพอร์ตเปิดที่ `ss` ไม่เห็น | ฟังบนอินเทอร์เฟซ/IPv6 ที่ไม่ได้ดู, หรือเป็นอุปกรณ์อื่น (NAT/port forward) | ดูทั้ง IPv4/IPv6, ตรวจ port forward ที่เราเตอร์ (บท 15) |

| TPM (Trusted Platform Module) | ทีพีเอ็ม | ชิปเก็บกุญแจและวัดสถานะการบูต |
| Patch / Window of exposure | แพตช์ / ช่วงเปิดช่องโหว่ | การแก้ช่องโหว่ / เวลาที่ช่องโหว่ยังเปิดอยู่ |
| End of life (EOL) | อีโอแอล | ซอฟต์แวร์ที่เลิกให้แพตช์ความปลอดภัยแล้ว |
| Drift | ดริฟต์ | ค่าตั้งเบี่ยงจาก baseline ตามเวลา |
| Baseline (CIS Benchmark) | เบสไลน์ / ซีไอเอส | ชุดค่าตั้งปลอดภัยมาตรฐานที่ใช้เทียบ |
| Event ID 4625 | อีเวนต์ไอดี 4625 | เหตุการณ์ Windows: ล็อกอินล้มเหลว |

## 13. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: ไฟร์วอลล์ของเครือข่ายกับไฟร์วอลล์บนเครื่อง (host-based) ต่างกันอย่างไร (ตรงกับคำถามท้ายบท 1)"}
ไฟร์วอลล์เครือข่ายอยู่ที่ขอบระหว่างโซน กรองทราฟฟิกที่ผ่านขอบนั้น ไม่เห็นทราฟฟิกระหว่างเครื่องในซับเน็ตเดียวกัน · ไฟร์วอลล์บนเครื่องอยู่ในเคอร์เนลของเครื่องนั้น กรองทุกแพ็กเก็ตที่เข้าถึงเครื่องไม่ว่ามาจากไหน รวมเครื่องข้างเคียง จึงกัน lateral movement ได้ และเป็นชั้นสำรองถ้าไฟร์วอลล์ขอบพลาด · ใช้ร่วมกัน (defense in depth) ไม่ใช่เลือกอย่างเดียว
::

::reveal{question="ข้อ 2: ทำไมควรปิดล็อกอิน root ผ่าน SSH (ตรงกับคำถามท้ายบท 2)"}
(1) root เป็นชื่อบัญชีที่ผู้โจมตีรู้อยู่แล้ว เหลือแค่รหัสผ่าน (2) root มีสิทธิ์สูงสุด ถ้าเดาถูกคือจบทันที (3) แชร์บัญชี root ทำให้ตามไม่ได้ว่าใครทำอะไร ให้ใช้บัญชีส่วนตัว + sudo ที่มี log รายคน · ปิดรหัสผ่านและใช้กุญแจจึงตัดทั้งการเดา · แต่ต้องมีกุญแจและบัญชี sudo ที่ใช้ได้จริงก่อนปิด ไม่งั้นล็อกตัวเองออก
::

::reveal{question="ข้อ 3: ถ้ารหัสผ่านระบบถูกข้าม การเข้ารหัสทั้งดิสก์ยังช่วยได้อย่างไร (ตรงกับคำถามท้ายบท 3)"}
รหัสผ่านระบบเป็นการควบคุมที่ *เคอร์เนลของระบบนั้น* บังคับใช้ ถ้าผู้โจมตีบูตระบบอื่นหรือถอดดิสก์ เขาไม่ผ่านด่านนั้นเลย · FDE ทำให้ข้อมูลบนดิสก์เป็น ciphertext กุญแจถอดรหัสต้องมาจากวลีผ่านหรือ TPM ที่ตรวจสถานะบูต จึงอ่านไม่ได้ · ไม่ช่วยถ้าระบบเปิดและวอลุ่มปลดล็อกอยู่ แล้วผู้โจมตีเจาะผ่านเครือข่าย หรือถ้ากุญแจอยู่ใน RAM ของเครื่องที่ถูกยึดขณะ sleep
::

::reveal{question="ข้อ 4: Event ID 4625 ใช้ทำอะไร (ตรงกับคำถามท้ายบท 4)"}
บันทึกการล็อกอินล้มเหลว ใช้ตรวจหาการเดารหัสผ่าน (หลายครั้งในเวลาสั้น ต้นทางเดียว หลายบัญชี) ตรวจว่าการล็อกบัญชีทำงานไหม และแยกประเภทด้วย LogonType (3 เครือข่าย, 10 RDP) · สัญญาณอันตรายจริงคือ 4625 หลายครั้ง *ตามด้วย 4624 สำเร็จ* จากต้นทางเดียวกัน · อย่าตีความ 4625 ครั้งเดียวว่าเป็นการโจมตี ผู้ใช้พิมพ์ผิดก็เกิดได้
::

::reveal{question="ข้อ 5: เซิร์ฟเวอร์เว็บสาธารณะมี FTP ฟังพอร์ต 21 แต่ทีมใช้ SFTP ทางที่ดีที่สุดคืออะไร และทำไมข้ออื่นไม่พอ"}
หยุดและปิด (หรือถอนแพ็กเกจ) เพราะกำจัดโค้ดที่เป็นพื้นผิวโจมตีและพอร์ต · แค่บล็อกที่ไฟร์วอลล์ยังปล่อยโค้ดที่มีบั๊กไว้ ถ้าไฟร์วอลล์ถูกตั้งผิดหรือผู้โจมตีอยู่ในเครื่องข้างเคียงก็ถึงบริการได้ · เปลี่ยนพอร์ตเป็นความคลุมเครือ สแกนทุกพอร์ตเจอได้ · เปลี่ยนผู้ใช้ที่รันบริการลดความเสียหายแต่ไม่ลดความเสี่ยงที่บริการถูกยึด · ข้อสุดท้ายเสริมได้ แต่ข้อ "ปิด/ถอน" ลดทั้งโอกาสและความเสียหาย
::

::reveal{question="ข้อ 6: คำนวณ: รหัสผ่านตัวพิมพ์เล็ก 8 ตัวสุ่ม เดาที่ 10 ครั้ง/วินาที ใช้เวลาเฉลี่ยเท่าไร และทำไมก็ยังไม่ควรเชื่อว่าปลอดภัย"}
26⁸ ≈ 2.09×10¹¹ ค่าเฉลี่ยครึ่งหนึ่ง ÷ 10 ≈ 1.04×10¹⁰ วินาที ≈ 330 ปี (ตรวจด้วย node ค่าประมาณ) · แต่ผู้ใช้ไม่ได้ตั้งแบบสุ่ม ลองรหัสยอดนิยมหรือที่รั่ว (credential stuffing) ใช้เวลาไม่กี่นาที · ถ้ารั่วแบบแฮชที่เดาออฟไลน์ได้ ความเร็วเดาสูงกว่าออนไลน์หลายระดับ ขึ้นกับอัลกอริทึมแฮช · จึงใช้กุญแจ/MFA แทนการพึ่งความยาว
::

::reveal{question="ข้อ 7: ทำไมเปลี่ยนชื่อบัญชี Administrator จึงเป็นมาตรการที่อ่อน และอะไรได้ผลกว่า"}
เป็นความคลุมเครือ (security through obscurity) ผู้โจมตีค้นชื่อจริงได้ เช่น จาก SID ที่ลงท้าย -500 หรือจากข้อมูลโดเมน · ได้ผลกว่า: ปิดใช้บัญชี Administrator ในตัว, ใช้บัญชีส่วนตัวที่มีสิทธิ์ผู้ดูแลและมี MFA, ใช้ LAPS ให้รหัสผู้ดูแลท้องถิ่นไม่ซ้ำกันทุกเครื่อง, ตั้ง lockout และเฝ้าดู 4625/4740 · เปลี่ยนชื่อยังพอมีประโยชน์ลดเสียงรบกวนจากสคริปต์ที่เดาชื่อตายตัว แต่ไม่ควรนับเป็นการป้องกันหลัก
::

::reveal{question="ข้อ 8: ก่อนปิดบริการหนึ่งบนเซิร์ฟเวอร์ที่ใช้งานจริง ควรตรวจอะไร"}
(1) บทบาทของเครื่องจริงๆ ว่าบริการนั้นจำเป็นไหม (2) ใครหรืออะไรใช้อยู่ ดูการเชื่อมต่อปัจจุบันและ log (3) บริการอื่นพึ่งพาไหม (`systemctl list-dependencies --reverse`) (4) แผนย้อนกลับและช่วงเวลาที่รับผลกระทบได้ (5) ทดลองบนเครื่องทดสอบ · ปิดผิดตัวคือความเสียหายด้าน Availability ที่เกิดจากมาตรการความปลอดภัยเอง
::

::reveal{question="ข้อ 9: ข้อจำกัดของบทนี้ที่ควรรู้"}
(1) ตัวเลขเวลาเดารหัสผ่านเป็นแบบจำลอง (อัตราการลองคงที่ ไม่รวมการล็อกบัญชีหรือการหน่วง) (2) น้ำหนักความเสี่ยงในห้องทดลองเป็นค่าสมมติ ไม่ใช่ CVSS (3) คำสั่งและตำแหน่งไฟล์ต่างกันตามดิสทริบิวชัน/เวอร์ชัน (ตรวจเอกสารของระบบที่ใช้) (4) ไม่ได้ลงลึก SELinux/AppArmor, auditd, kernel hardening (sysctl), Secure Boot, container hardening และ Windows Defender Application Control ซึ่งเป็นชั้นป้องกันเพิ่มเติม
::

## 14. แบบฝึกหัด (ลงมือทำจริง)

ทำบนเครื่องของคุณเอง ใช้คำสั่งอ่านอย่างเดียวก่อน ห้ามแก้ค่าบนระบบที่คุณไม่ได้เป็นเจ้าของ

1. **สำรวจพอร์ต:** Linux: `sudo ss -tulpn` · Windows: `Get-NetTCPConnection -State Listen | Sort LocalPort` จดทุกพอร์ต ระบุโปรเซส และตัดสินว่าจำเป็นต่อบทบาทไหม
2. **ดูบริการที่เริ่มเอง:** `systemctl list-unit-files --state=enabled` หรือ `Get-Service | Where StartType -eq Automatic` เลือก 3 ตัวที่ไม่รู้จัก ค้นว่าคืออะไร
3. **ตรวจ SUID:** `find / -xdev -perm -4000 -type f 2>/dev/null` นับจำนวนและดูตัวที่ไม่คุ้น
4. **ตรวจไฟร์วอลล์:** `sudo ufw status verbose` หรือ `Get-NetFirewallProfile` จดนโยบายเริ่มต้นขาเข้า
5. **ตรวจการเข้ารหัสดิสก์:** Windows: `manage-bde -status` (ต้องสิทธิ์ผู้ดูแล) · Linux: `lsblk -f` ดูคอลัมน์ `crypto_LUKS`
6. **ตรวจการแพตช์:** `apt list --upgradable` หรือ Windows Update ประวัติ จดว่าค้างอัปเดตกี่รายการ
7. **ลองสื่อ:** ใน `hardening-lab` ทำจนความเสี่ยงเหลือน้อยที่สุด แล้วลองเรียงผิดลำดับของไฟร์วอลล์ จดว่ามาตรการใดมีข้อควรระวังด้านความพร้อมใช้งาน
8. **ทดสอบจริงอย่างปลอดภัย:** ใช้เครื่องเสมือน (VM) ของคุณเอง ลองตั้ง `ufw` ตามลำดับที่ถูกและผิด โดยเปิดคอนโซลของ VM ไว้เป็นทางเข้าสำรอง

::reveal{question="แนวคำตอบ"}
(1) เครื่องทั่วไปมักมีบริการพิมพ์/ค้นหาอุปกรณ์ (mDNS), SSH, อาจมี RPC/SMB บน Windows; ที่ตรงบทบาทเท่านั้นควรเหลือ · (3) ปกติมีหลักสิบตัว เช่น passwd, sudo, mount, ping ฯลฯ ตัวที่ไม่ใช่ของแพ็กเกจระบบน่าสงสัย · (4) Windows ส่วนมาก Inbound = Block · Ubuntu ที่ยังไม่เปิดใช้ ufw จะ inactive · (5) ไม่มี `crypto_LUKS` แปลว่าดิสก์ไม่ได้เข้ารหัสระดับวอลุ่ม ตรวจว่ามีการเข้ารหัสแบบอื่นหรือไม่ · (7) ข้อมูลสำคัญ: ปิด root/รหัสผ่านและแพตช์มีน้ำหนักมาก; ข้อที่มี "breaks" คือ bind localhost, แพตช์ (ต้องรีสตาร์ต), เข้ารหัสดิสก์ (กุญแจหาย = ข้อมูลหาย)
::

## 15. สรุป

- **Hardening = ลดพื้นผิวโจมตี** เริ่มจากรู้บทบาทของเครื่อง สำรวจของที่เปิดอยู่จริง แล้วตัดของที่เกิน ถอนแพ็กเกจดีกว่าแค่หยุด
- **Least privilege:** บัญชีส่วนตัว + sudo, ปิดบัญชีที่ไม่ใช้, กุญแจ SSH แทนรหัสผ่าน (ปัญหาจริงคือรหัสผ่านที่คนตั้งและใช้ซ้ำ ไม่ใช่พื้นที่ค้นหา)
- **ไฟร์วอลล์ default deny** ต้องอนุญาตช่องทางดูแลก่อนเปิดใช้ และมีทางเข้าสำรอง
- **สิทธิ์ไฟล์ + ตรวจ SUID** ลดความเสียหายเมื่อโปรเซสถูกยึด · **FDE** ป้องกันดิสก์ที่ถูกขโมยตอนเครื่องปิด ไม่ป้องกันระบบที่เปิดและถูกเจาะ
- **แพตช์** ลดช่วงเปิดช่องโหว่ ต้องทดสอบ/รีบูตให้มีผลจริง · **log** ต้องเปิด ส่งออกนอกเครื่อง และดูรูปแบบ (ล้มเหลวแล้วสำเร็จ) ไม่ใช่นับอย่างเดียว
- ใช้ **baseline ที่ตรวจซ้ำได้** (CIS) แต่เข้าใจ trade-off: ปิดผิดตัวหรือลืมกุญแจก็ทำให้ระบบล่มเอง
- hardening ไม่ใช่ความปลอดภัย 100% ยังต้องมี backup, การเฝ้าระวัง, และการอบรมผู้ใช้
- ตัวเลขที่ไม่ได้มาจากต้นฉบับ (เวลาเดารหัสผ่าน, จำนวน log ต่อวัน, น้ำหนักความเสี่ยง) เป็นแบบจำลองหรือค่าประมาณ
- นี่เป็นบทสุดท้ายของคอร์ส Fundamental IT Skills (25 บท)
