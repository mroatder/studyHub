## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **ทำไม** ปัจจัยเดียวเป็นจุดล้มเหลวเดียว และทำไมปัจจัยที่สองต้อง *ต่างประเภทและเป็นอิสระ* จากปัจจัยแรก
2. เล่ากลไก TOTP ได้ทีละขั้น (secret ร่วม → ตัวนับเวลา → HMAC → ตัดช่วง → 6 หลัก) และอธิบายว่าทำไมมือถือไม่ต้องต่ออินเทอร์เน็ต
3. เทียบ SMS, TOTP, push, push + number matching และ FIDO2 ว่า **ผู้โจมตีแบบไหนผ่านได้ แบบไหนไม่ได้ เพราะกลไกอะไร**
4. อธิบายบทบาท IdP กับ SP และเล่าลำดับ OIDC ทีละคำขอ รวมถึงโครงสร้างและการตรวจ JWT
5. เทียบ SAML กับ OIDC และแยก OAuth 2.0 (การให้สิทธิ์) ออกจาก OIDC (การพิสูจน์ตัวตน)
6. ชี้ได้ว่า SSO ช่วยอะไร (ถอนสิทธิ์ที่เดียว บังคับนโยบายที่เดียว) และเพิ่มความเสี่ยงอะไร (จุดรวมศูนย์) รวมถึงข้อจำกัดว่า "ปิดบัญชีที่ IdP แล้วเข้าไม่ได้ทันที" ไม่จริงเสมอไป
7. วินิจฉัยอาการที่พบบ่อย เช่น รหัส 6 หลักถูกแต่ถูกปฏิเสธ, ล็อกอิน SSO วนลูป, เปลี่ยนเครื่องแล้วเสียตัวสร้างรหัส

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | สิ่งที่เทียบได้ |
|---|---|
| ตู้เซฟต้องใช้ทั้งกุญแจและรหัสกด คนขโมยกุญแจอย่างเดียวเปิดไม่ได้ | MFA: ต่างประเภท ขโมยอันเดียวไม่พอ |
| ตู้เซฟที่ต้องใช้รหัสกด 2 ชุด แต่ทั้งสองชุดจดไว้ในสมุดเล่มเดียวกัน | ปัจจัยไม่อิสระ: ผู้โจมตีได้ทั้งคู่ในคราวเดียว |
| นาฬิกาสองเรือนที่ตั้งเวลาตรงกัน ตกลงกันไว้ล่วงหน้าว่า "ทุกครึ่งนาที ให้ใช้คำลับตามตารางเดียวกัน" โดยไม่ต้องโทรบอกกัน | TOTP: คำนวณเองพร้อมกัน |
| คนแปลกหน้าโทรมาบอกว่า "บอกรหัสที่เพิ่งได้รับหน่อย" แล้วเราบอกไป | หลอกถามรหัส (phishing / vishing) |
| บัตรประชาชนใบเดียวใช้ได้กับทุกหน่วยงานของรัฐ หน่วยงานไม่ต้องออกบัตรเอง แต่ละแห่งแค่ตรวจว่าเป็นของจริง | SSO: IdP ออกบัตร SP แค่ตรวจ |
| ถ้าบัตรประชาชนถูกปลอมได้ ทุกหน่วยงานโดนพร้อมกัน | จุดรวมศูนย์ของ SSO |

## 1. ปัญหาตั้งต้น: ทำไมปัจจัยเดียวถึงไม่พอ

จากบทที่ 21 รหัสผ่านคือหลักฐานประเภท "รู้" และมีธรรมชาติที่ **เอาไปใช้ซ้ำได้** ใครรู้ก็ล็อกอินได้โดยไม่ต้องอยู่ที่เดียวกับเจ้าของ รหัสผ่านรั่วได้หลายทาง

- ฐานข้อมูลของเว็บอื่นรั่ว แล้วผู้ใช้ใช้รหัสซ้ำ (credential stuffing)
- ถูกหลอกให้กรอกในหน้าเว็บปลอม (phishing)
- มัลแวร์ดักแป้นพิมพ์ หรือคนแอบดู
- เดาได้ง่าย

ถ้าความปลอดภัยของบัญชีขึ้นกับสิ่งเดียวที่ *คัดลอกได้และถูกขโมยจากระยะไกลได้* สิ่งนั้นก็เป็น **จุดล้มเหลวเดียว (single point of failure)** MFA แก้ด้วยหลักการเดียวกับเครื่องบินที่มีสองเครื่องยนต์: เพิ่มด่านที่ **ล้มเหลวด้วยสาเหตุคนละแบบ** เพื่อให้ผู้โจมตีต้องชนะสองเรื่องที่ไม่เกี่ยวกัน

### 1.1 สามประเภท และเงื่อนไข "ต้องอิสระ"

| ประเภท | ตัวอย่าง | ผู้โจมตีขโมยได้อย่างไร |
|---|---|---|
| **รู้** (knowledge) | รหัสผ่าน, PIN, คำถามลับ | ดักพิมพ์, หลอก, เดา, ฐานข้อมูลรั่ว |
| **มี** (possession) | โทรศัพท์, กุญแจ FIDO2, สมาร์ตการ์ด | ต้องเอาอุปกรณ์ไปจริง หรือยึด SIM/แอปจากระยะไกลได้ |
| **เป็น** (inherence) | ลายนิ้วมือ, ใบหน้า, ม่านตา | เลียนแบบยาก แต่ *เปลี่ยนไม่ได้* ถ้ารั่ว และมักใช้ปลดล็อกอุปกรณ์ในเครื่อง |

เงื่อนไขสำคัญคือ "ต่างประเภท" เพราะประเภทเดียวกันมักถูกขโมยด้วยวิธีเดียวกัน รหัสผ่าน + PIN + คำถามลับ ล้วนเป็น "รู้" และ keylogger ตัวเดียวเก็บได้ทั้งสามอย่าง นี่เรียกว่า *การยืนยันสองขั้น (two-step verification)* ไม่ใช่ MFA

> **ความแม่นยำ:** "ต่างประเภท" ยังไม่รับประกันว่า "อิสระ" เสมอไป ตัวอย่างคือโทรศัพท์เครื่องเดียวที่ทั้งเปิดเว็บล็อกอิน (รู้) *และ* รับรหัส SMS/แอป TOTP (มี) ถ้ามัลแวร์ยึดโทรศัพท์ได้ ก็ได้ทั้งสองประเภทพร้อมกัน ในทางปฏิบัติ "ความอิสระ" เป็นสเปกตรัม ไม่ใช่ใช่/ไม่ใช่

> **ข้อควรระวัง (เรื่อง "เป็น"):** ลายนิ้วมือบนโทรศัพท์ส่วนใหญ่ **ไม่ได้ถูกส่งไปเซิร์ฟเวอร์** มันแค่ปลดล็อกกุญแจในเครื่อง (ดู FIDO2 หัวข้อ 4.4) จึงนับเป็นการยืนยันผู้ใช้ในเครื่อง ไม่ใช่เซิร์ฟเวอร์ตรวจลายนิ้วมือคุณ

## 2. ลองดู: ตัวอย่างสถานการณ์ที่ *ไม่ใช่* MFA

| สถานการณ์ | ประเภทที่ใช้ | เป็น MFA ไหม |
|---|---|---|
| รหัสผ่าน + คำถามลับ ("ชื่อสัตว์เลี้ยง") | รู้ + รู้ | ไม่ (two-step) |
| รหัสผ่าน + รหัส 6 หลักจากแอป | รู้ + มี | ใช่ |
| ลายนิ้วมือ + รหัส SMS | เป็น + มี | ใช่ (แต่ SMS อ่อน ดูหัวข้อ 4) |
| กุญแจ FIDO2 + PIN ของกุญแจ | มี + รู้ | ใช่ |
| ล็อกอินด้วย passkey ที่ปลดล็อกด้วยลายนิ้วมือบนมือถือ | มี + เป็น (ในเครื่อง) | ใช่ในตัวเดียว (ไม่ต้องมีรหัสผ่าน) |
| รหัสผ่านสองชุดจากสองระบบต่างกัน | รู้ + รู้ | ไม่ |

## 3. TOTP: รหัส 6 หลักที่ไม่มีใครส่งให้ใคร

### 3.1 ปัญหาที่ TOTP แก้

SMS ต้องส่งรหัสผ่านเครือข่ายมือถือ (ดักได้ ซิมถูกย้ายได้) TOTP ถามคำถามใหม่ว่า: **ถ้ามือถือกับเซิร์ฟเวอร์รู้ความลับเดียวกัน และมีนาฬิกาที่ตรงกัน ทำไมไม่คำนวณรหัสเองทั้งสองฝั่งเลย?** ความลับที่ต้องส่งมีแค่ครั้งเดียวตอนสมัคร (สแกน QR) หลังจากนั้นไม่มีอะไรวิ่งบนเครือข่ายนอกจากรหัส 6 หลักที่ผู้ใช้พิมพ์เอง

### 3.2 กลไกทีละขั้น (ลองเล่นจริงด้านล่าง)

ตัวคำนวณนี้ทำ HMAC-SHA1 จริงในเบราว์เซอร์ ตามมาตรฐาน RFC 4226 (HOTP) และ RFC 6238 (TOTP) ขั้นตอนคือ

1. **ตัวนับเวลา:** T = ⌊เวลา Unix ÷ 30⌋ เปลี่ยนค่าทุก 30 วินาที (เวลา Unix = วินาทีนับจาก 1 ม.ค. 1970 UTC จึงไม่ขึ้นกับเขตเวลา)
2. **HMAC:** คำนวณ HMAC-SHA1 โดยใช้ secret เป็นกุญแจ และ T (เขียนเป็น 8 ไบต์ big-endian) เป็นข้อความ ได้ผล 20 ไบต์
3. **ตัดช่วงแบบไดนามิก:** เอาครึ่งไบต์ท้ายของไบต์สุดท้ายเป็น *offset* (0–15) แล้วหยิบ 4 ไบต์เริ่มที่ offset
4. **ล้างบิตเครื่องหมาย:** AND กับ `0x7fffffff` เพื่อให้เป็นจำนวนเต็มบวก 31 บิต
5. **ลดเหลือ 6 หลัก:** หารเอาเศษด้วย 10⁶ (mod 1,000,000) เติมศูนย์ด้านหน้าให้ครบ 6 หลัก

::totp-lab
::

**ตัวอย่างคำนวณมือ** (ตรวจด้วย node แล้ว): ใช้กุญแจ ASCII `12345678901234567890` ซึ่งเป็นตัวอย่างทดสอบในมาตรฐาน ที่เวลา t = 59 วินาที จะได้ T = ⌊59÷30⌋ = 1

- HMAC-SHA1 = `75a48a19 d4cbe100 644e8ac1 397eea74 7a2d33ab`
- ไบต์สุดท้ายคือ `ab` ครึ่งท้ายคือ `b` = 11 → offset = 11
- 4 ไบต์ที่ offset 11 = `c1 39 7e ea` = 0xc1397eea
- AND `0x7fffffff` = 0x41397eea = 1,094,287,082
- mod 10⁶ = **287082** (ตรงกับค่าอ้างอิงของมาตรฐาน)

> **เกร็ดความแม่นยำ:** SHA-1 ถูกทำลายในแง่ *การหาชนกัน (collision)* แต่ **HMAC-SHA1 ยังไม่ถูกทำลาย** เพราะความปลอดภัยของ HMAC ไม่พึ่งการต้านการชนกัน TOTP ที่ใช้ SHA-1 จึงยังปลอดภัยในทางปฏิบัติ และแอปส่วนใหญ่ใช้ SHA-1 เป็นค่าตั้งต้น เพราะความเข้ากันได้ (บางระบบรองรับ SHA-256/512 ด้วย)

### 3.3 โจทย์เชิงปริมาณ

**(ก) ผู้โจมตีเดา 6 หลักได้โอกาสเท่าไร** รหัสมี 10⁶ แบบ (≈ 19.9 บิต) ถ้าเซิร์ฟเวอร์ยอมรับ 3 ช่วง มี 3 รหัสที่ถูกพร้อมกัน โอกาสต่อครั้ง = 3 ÷ 10⁶ = 0.0003% ถ้าอนุญาตเดา 5 ครั้งก่อนล็อก ≈ 1.5 × 10⁻⁵ (0.0015%) แต่ถ้าไม่มีการจำกัดอัตรา และเดาได้ 10 ครั้งต่อวินาที (ตัวเลขสมมติ) โอกาสถึง 50% ต้องเดา ≈ ln 2 ÷ (3 × 10⁻⁶) ≈ 231,000 ครั้ง ≈ **6.4 ชั่วโมง** นี่คือเหตุผลที่ต้องมี **การจำกัดอัตรา/ล็อก** คู่กับ TOTP เสมอ

**(ข) secret 160 บิตเดาไม่ได้จริงไหม** 2¹⁶⁰ ≈ 1.5 × 10⁴⁸ แบบ จึงเดา secret ไม่ได้ ผู้โจมตีต้อง *ขโมย* secret (จากฐานข้อมูลเซิร์ฟเวอร์ ภาพ QR หรือเครื่องมือถือ) ไม่ใช่เดา

**(ค) รหัสหนึ่งตัวมีอายุจริงเท่าไร** แม้รหัสบนจอเปลี่ยนทุก 30 วินาที แต่ถ้าเซิร์ฟเวอร์ยอมรับ T−1 ถึง T+1 รหัสหนึ่งตัวใช้ได้ในเวลาเซิร์ฟเวอร์ ≈ **90 วินาที** (ตัวเลขนี้ขึ้นกับการตั้งค่า) ผู้โจมตีแบบ relay จึงมีเวลาเหลือเฟือ

**(ง) นาฬิกาเพี้ยนได้เท่าไร** ถ้ายอมรับ ±1 ช่วง: เพี้ยนไม่เกิน 30 วินาทีผ่านเสมอ, 30–60 วินาที *ผ่านบ้างไม่ผ่านบ้าง* ขึ้นกับว่าตอนนั้นอยู่ตำแหน่งไหนของช่วง, เกิน 60 วินาทีไม่ผ่านแน่ ลองลาก drift ในสื่อด้านบนไปที่ +45 และ +120 ดู (เหตุผลที่ต้องตั้งเวลาอัตโนมัติด้วย NTP)

## 4. วิธีเป็นปัจจัยที่สอง: ไม่ได้เท่ากันทั้งหมด

### 4.1 SMS

ส่งรหัสไปที่เบอร์โทร ใช้ง่าย ไม่ต้องลงแอป แต่เชื่อถือเครือข่ายมือถือ ซึ่งมีจุดอ่อนที่ *ไม่ได้อยู่ที่คุณ* การย้ายซิม (SIM swap) ที่ผู้โจมตีหลอกผู้ให้บริการให้โอนเบอร์, ช่องโหว่โปรโตคอลสัญญาณ SS7, การดักด้วยมัลแวร์บนมือถือ แนวปฏิบัติของ NIST (SP 800-63B) จัดการส่งรหัสผ่านเครือข่ายโทรศัพท์เป็นตัวตรวจสอบที่ "จำกัด" (restricted) ยังใช้ได้ แต่ควรหลีกเลี่ยงถ้ามีทางเลือกที่ดีกว่า

### 4.2 Push กดอนุมัติ และ MFA fatigue

ส่งข้อความเข้าแอป ผู้ใช้กด "อนุมัติ" สะดวกที่สุด แต่กลไกคือ "ใครที่มีรหัสผ่านก็สั่งให้โทรศัพท์เหยื่อสั่นได้" ผู้โจมตีใช้ช่องนี้ยิง push ซ้ำๆ จนเหยื่อกดอนุมัติเพื่อให้หยุด (เหตุการณ์ที่มีรายงานกันกว้างขวางคือกรณี Uber ปี 2022 ซึ่งผู้โจมตียิง push แล้วติดต่อเหยื่อผ่านแชตแอบอ้างเป็นฝ่าย IT)

### 4.3 Number matching

แก้ที่ต้นเหตุ: หน้าล็อกอินแสดงเลข 2 หลัก ผู้ใช้ต้อง *พิมพ์เลขนั้นในแอป* ผู้โจมตีที่ยิง push มั่วๆ เป็นคนเห็นเลข ส่วนเหยื่อไม่เห็น จึงกดผ่านไม่ได้ **แต่ไม่ช่วยทุกกรณี:** ถ้าผู้โจมตีโทรไปหลอกให้อ่านเลข, หรือใช้หน้าเว็บปลอมแบบกลาง (AiTM) ที่ส่งต่อเลขไปให้เหยื่อเห็น ก็ยังผ่านได้

### 4.4 FIDO2 / WebAuthn / passkey

หลักการต่างจากทั้งหมดข้างต้น: **ไม่มีความลับร่วมที่ผู้ใช้พิมพ์หรือกดอนุมัติ** แต่ใช้กุญแจสาธารณะ

- ตอนลงทะเบียน อุปกรณ์ (authenticator) สร้างคู่กุญแจ **เฉพาะเว็บไซต์นั้น** กุญแจส่วนตัวอยู่ในอุปกรณ์ ส่วนกุญแจสาธารณะส่งให้เซิร์ฟเวอร์เก็บ
- ตอนล็อกอิน เซิร์ฟเวอร์ส่ง **challenge สุ่ม** อุปกรณ์เซ็นพร้อมข้อมูลที่รวม **โดเมน (origin) ที่เบราว์เซอร์เห็นจริง** ตัวเบราว์เซอร์เป็นผู้ใส่โดเมน ไม่ใช่หน้าเว็บ
- การแตะ/PIN/สแกนนิ้วเกิดภายในอุปกรณ์เท่านั้น (ยืนยันตัวผู้ใช้ต่ออุปกรณ์) ไม่ส่งไปเซิร์ฟเวอร์

**Passkey** คือ FIDO credential ที่ผู้ใช้เห็นเป็นประสบการณ์ไร้รหัสผ่าน และมักซิงก์ข้ามอุปกรณ์ผ่านบัญชีผู้ให้บริการ (ข้อดี: ไม่เสียถ้าเครื่องหาย / ข้อแลก: ความปลอดภัยพึ่งบัญชีที่ซิงก์ด้วย) ส่วนกุญแจฮาร์ดแวร์ (เช่น YubiKey) ผูกกับอุปกรณ์จริงตัวเดียว

### 4.6 การกู้คืนบัญชี: ด่านที่อ่อนที่สุดกำหนดความแข็งแรงทั้งหมด

ถ้าผู้ใช้ทำโทรศัพท์หายแล้วกู้บัญชีด้วยอีเมลหรือ SMS ผู้โจมตีก็ข้าม MFA ผ่านทางนั้นได้ สิ่งที่ควรมี: **รหัสสำรอง (backup codes)** ที่ใช้ครั้งเดียวและเก็บแยก, ลงทะเบียนอุปกรณ์สำรองอย่างน้อย 2 ตัว, ขั้นตอนยืนยันตัวตนของฝ่าย IT ก่อนรีเซ็ต MFA (ห้ามรีเซ็ตตามคำขอทางโทรศัพท์เฉยๆ)

## 5. Single Sign-On (SSO)

### 5.1 ปัญหาตั้งต้น

บริษัท 200 คน ใช้ 20 แอป ถ้าทุกแอปมีบัญชีและรหัสผ่านของตัวเอง จะมี 200 × 20 = **4,000 ชุดรหัสผ่าน** ให้ดูแล ผลคือคนใช้รหัสซ้ำ จดไว้ และเวลาพนักงานออก IT ต้องไล่ปิด 20 ที่ (ลืมที่ไหนก็เป็นช่องโหว่) SSO ย้ายความรับผิดชอบการพิสูจน์ตัวตนทั้งหมดไปอยู่ที่ **ที่เดียว** (ตัวเลขนี้สมมติ)

- **IdP (Identity Provider):** ระบบกลางที่ถือตัวตนและตรวจรหัสผ่าน/MFA เช่น Microsoft Entra ID, Okta, Google Workspace, Keycloak
- **SP / RP (Service Provider / Relying Party):** แอปที่ไม่ตรวจรหัสผ่านเอง แต่ "เชื่อ" IdP เช่น Slack, Salesforce (ในภาษา OIDC เรียก *Relying Party*)

ความไว้วางใจนี้ตั้งอยู่บน **การเซ็นลายเซ็น** IdP ถือกุญแจส่วนตัว (private key) และเผยแพร่กุญแจสาธารณะ SP ใช้กุญแจสาธารณะตรวจว่า token ออกโดย IdP จริง และไม่ถูกแก้ไขระหว่างทาง ขั้นตอนนี้ใช้หลักการเดียวกับลายเซ็นดิจิทัลที่คุณจะเจอต่อในบท SSL/TLS

### 5.3 JWT: บัตรที่เซ็นลายเซ็นแล้ว

`id_token` เป็น JWT 3 ส่วนคั่นด้วยจุด `header.payload.signature` แต่ละส่วนเข้ารหัสแบบ base64url (**ไม่ใช่การเข้ารหัสลับ** ใครก็ถอดอ่านได้ ลายเซ็นกัน *แก้ไข* ไม่ได้กัน *อ่าน*)

```
header   : {"alg":"RS256","kid":"2026-10-key1"}
payload  : {"iss":"https://idp.company.com","sub":"u-4821","aud":"app-slack",
            "iat":1792496400,"exp":1792500000,"nonce":"n-0S6_WzA2Mj",
            "email":"alice@company.com","amr":["pwd","otp"]}
signature: RSA-SHA256(base64url(header)+"."+base64url(payload), IdP private key)
```

| ฟิลด์ | ความหมาย | ถ้า SP ไม่ตรวจจะเกิดอะไร |
|---|---|---|
| **sig** (ลายเซ็น) | พิสูจน์ว่า IdP ออกจริงและไม่ถูกแก้ | ใครก็ปลอม token ได้ (ช่องโหว่คลาสสิก: ยอมรับ `alg: none`) |
| **iss** | ผู้ออก token | ยอมรับ token จาก IdP ของคนอื่น |
| **aud** | ผู้รับที่ตั้งใจ (แอปนี้) | token ที่ออกให้แอป A ถูกเอามาใช้กับแอป B |
| **exp / iat** | อายุของ token | token เก่าที่รั่วใช้ได้ตลอดไป |
| **nonce** | ค่าสุ่มที่แอปส่งไปตอนเริ่ม | เล่น token ซ้ำ (replay) ได้ |
| **amr** | วิธีพิสูจน์ที่ใช้ (pwd, otp, hwk ฯลฯ) | แอปที่ละเอียดอ่อนไม่รู้ว่า ผู้ใช้ผ่าน MFA แค่ไหน |

ที่อายุ `exp − iat` = 1792500000 − 1792496400 = 3,600 วินาที = 1 ชั่วโมง (ค่าในตัวอย่าง) token สั้นเท่าไรยิ่งลดความเสียหายเมื่อรั่ว

### 5.4 SAML เทียบ OIDC

::compare-cards{:items='[{"title":"SAML 2.0","subtitle":"รุ่นเก่า ยังใช้มากในองค์กร","points":["ส่ง Assertion เป็น XML ที่เซ็นด้วย XML Signature","แอปองค์กรเก่า, ระบบ B2B, SaaS สำหรับองค์กรจำนวนมาก","เบราว์เซอร์เป็นผู้ส่ง (POST) ไปที่ ACS URL ของ SP","จุดอ่อนที่รู้จัก: XML signature wrapping ถ้า SP ตรวจไม่ดี","ไม่เหมาะกับแอปมือถือ/SPA"]},{"title":"OpenID Connect (OIDC)","subtitle":"รุ่นใหม่ บน OAuth 2.0","points":["ส่ง id_token เป็น JWT (JSON)","เว็บและมือถือสมัยใหม่","แลก code ทางหลังบ้าน (+ PKCE)","มาพร้อม discovery (/.well-known/openid-configuration) และ JWKS","เบากว่า SAML และตรวจง่ายกว่า"]}]'}
::

**OAuth 2.0 กับ OIDC ไม่ใช่เรื่องเดียวกัน** (ตัวอย่างของความแม่นยำที่เชื่อมกับบทที่ 21) OAuth 2.0 เป็นกรอบ **การให้สิทธิ์ (AuthZ)** แบบมอบหมาย: "อนุญาตให้แอปนี้อ่านปฏิทินของฉัน" ผลคือ *access token* ซึ่งไม่ได้บอกว่าผู้ใช้คือใคร OIDC เพิ่มชั้น **การพิสูจน์ตัวตน (AuthN)** ขึ้นมา คือ `id_token` และ scope `openid` แอปที่ใช้ OAuth ล้วนๆ เพื่อ "ล็อกอิน" มีช่องโหว่หลายแบบ จึงมี OIDC ขึ้นมา

| ระบบ | ใช้ที่ไหนโดยทั่วไป | หมายเหตุ |
|---|---|---|
| **SAML / OIDC** | SSO ของเว็บแอป/SaaS ข้ามองค์กร | บทนี้ |
| **Kerberos** | SSO ภายในโดเมน Windows (Active Directory) ด้วย ticket | ไม่ผ่านเบราว์เซอร์ redirect เหมาะภายในเครือข่ายองค์กร |
| **LDAP** | ไดเรกทอรี ใช้ค้นหา/ตรวจรหัสผ่าน (bind) | เป็นโปรโตคอลไดเรกทอรี ไม่ใช่ SSO ในตัว |
| **RADIUS** | การเข้าเครือข่าย Wi-Fi (802.1X)/VPN | ศูนย์กลางการพิสูจน์ตัวตนระดับเครือข่าย |

### 5.5 ประโยชน์ และสิ่งที่ SSO *ไม่ได้* ทำให้

**ประโยชน์**
- **รหัสผ่านที่ต้องจัดการลดลง:** จาก 4,000 เหลือ 200 (ในตัวอย่าง) และผู้ใช้พิมพ์รหัสที่โดเมนเดียวที่คุ้น จึงสังเกตหน้าปลอมได้ง่ายขึ้น
- **นโยบายที่เดียว:** บังคับ MFA แบบ FIDO2 หรือกฎ "ห้ามล็อกอินจากต่างประเทศ" (conditional access) ที่ IdP ครั้งเดียว มีผลกับทุกแอป
- **บันทึกกลาง (audit):** เห็นการล็อกอินทุกแอปที่เดียว จับความผิดปกติได้ เช่น ล็อกอินสองประเทศในหนึ่งชั่วโมง
- **ถอนสิทธิ์ที่เดียว** (แต่อ่านข้อจำกัดด้านล่าง)

**ข้อจำกัดที่ต้องรู้ ซึ่งเอกสารเบื้องต้นมักข้าม**
- **การถอนสิทธิ์ไม่ได้ทันทีเสมอไป:** เมื่อปิดบัญชีที่ IdP แอปที่ผู้ใช้ล็อกอินค้างไว้มักยังมี session ของตัวเอง (หัวข้อ 5.2 ขั้นสุดท้าย) ซึ่งอยู่ต่อจนหมดอายุ จึงควรมี session สั้น, back-channel logout, และการ **provisioning อัตโนมัติ (SCIM)** ที่ลบ/ปิดบัญชีในแอป
- **จุดรวมศูนย์:** IdP ล่ม = ไม่มีใครล็อกอินได้ IdP ถูกยึด = เสียทุกแอป ต้องมีบัญชีฉุกเฉิน (break-glass) ที่เก็บแยกพร้อมกุญแจฮาร์ดแวร์
- **ไม่ได้แก้ phishing เอง:** ถ้าด่าน MFA ที่ IdP เป็น TOTP/push AiTM ยังขโมย session ได้ ต้องใช้ FIDO2
- **แอปที่ไม่รองรับ SSO** ยังต้องมีรหัสผ่านแยก (มักต้องใช้ตัวจัดการรหัสผ่าน)

## 6. มุมมอง Security: แมปการโจมตีกับกลไก

| การโจมตี | กลไกที่ถูกใช้ | การป้องกัน |
|---|---|---|
| **MFA fatigue / bombing** | push ที่อนุมัติได้ด้วยปุ่มเดียว ใครมีรหัสผ่านก็สั่งยิงได้ | number matching, จำกัดจำนวน push, แจ้งเตือนฝ่าย IT เมื่อผู้ใช้ปฏิเสธซ้ำ, ย้ายไป FIDO2 |
| **AiTM phishing** | พร็อกซีกลางส่งต่อรหัสและขโมยคุกกี้ session | FIDO2 (ผูกโดเมน), ผูก session กับอุปกรณ์, ตรวจโดเมนที่เข้า |
| **SIM swap** | ย้ายเบอร์ไปซิมผู้โจมตี | เลิกใช้ SMS เป็นปัจจัยหลัก, PIN ที่ผู้ให้บริการ, อย่าใช้ SMS กู้บัญชี |
| **ขโมย secret TOTP** | ฐานข้อมูลเซิร์ฟเวอร์รั่ว (เก็บแบบอ่านได้) หรือภาพ QR | เข้ารหัส secret ที่พักข้อมูลด้วยกุญแจแยก, ไม่เก็บภาพ QR, สมัครใหม่เมื่อสงสัย |
| **เดารหัส 6 หลัก** | วนส่งรหัสโดยไม่จำกัด | จำกัดอัตรา/ล็อกบัญชีชั่วคราว (หัวข้อ 3.3) |
| **ปลอม token SSO** | SP ไม่ตรวจลายเซ็น/`alg` | ใช้ไลบรารีมาตรฐาน กำหนด alg ที่ยอมรับ ตรวจ iss/aud/exp/nonce |
| **ขโมย session หลังล็อกอิน** | มัลแวร์อ่านคุกกี้ | session สั้น, ผูกกับอุปกรณ์, ตรวจพฤติกรรม, เพิกถอนเมื่อเปลี่ยนรหัส |
| **IdP ถูกยึดบัญชีผู้ดูแล** | จุดรวมศูนย์ | FIDO2 บังคับกับผู้ดูแล, แยกบัญชีผู้ดูแลจากบัญชีใช้งานประจำ, บันทึกกลาง+แจ้งเตือน |
| **Open redirect ใน redirect_uri** | ผู้โจมตีให้ IdP ส่ง code ไปยังเว็บตัวเอง | ลงทะเบียน redirect_uri แบบตรงตัว (exact match) |
| **MFA bypass ผ่านกู้บัญชี** | ช่องทางกู้ที่อ่อนกว่า | ตรวจยืนยันตัวตนก่อนรีเซ็ต MFA, backup codes |

> **ข้อควรจำ:** MFA ลดความเสี่ยงจาก *รหัสผ่านรั่ว* ได้มาก แต่ไม่ได้ทำให้บัญชีปลอดภัย 100% ผู้โจมตีย้ายไปโจมตีจุดที่เหลือ: คนใช้ (วิศวกรรมสังคม), การกู้คืน, และ session

## 7. ตัวอย่างวิเคราะห์ปัญหา IT Support

| อาการ | สาเหตุที่เป็นไปได้ (กลไก) | ตรวจ/แก้ |
|---|---|---|
| ใส่รหัส 6 หลักถูกต้องแต่ถูกปฏิเสธซ้ำๆ | **นาฬิกาเพี้ยน** เกินหน้าต่าง ±1 ช่วง (หัวข้อ 3.3 ง) ทำให้ T ไม่ตรงกัน | ตั้งเวลามือถือเป็นอัตโนมัติ (ใน Google Authenticator มีเมนู "Time correction for codes") และตรวจ NTP ของเซิร์ฟเวอร์ (`timedatectl`, `w32tm /query /status`) |
| รหัสถูกแต่ถูกปฏิเสธเฉพาะบางครั้ง | อยู่ในช่วง 30–60 วินาทีของ drift ผ่านบ้างไม่ผ่านบ้าง | เหมือนข้อบน สังเกตว่า "บางครั้ง" เป็นลายนิ้วมือของ drift |
| ผู้ใช้เปลี่ยนมือถือแล้วเข้าไม่ได้ | secret อยู่ในแอปเครื่องเก่า ไม่ติดมาด้วย | ใช้ backup code / อุปกรณ์สำรอง ถ้าไม่มี ให้ฝ่าย IT ยืนยันตัวตนแล้วรีเซ็ต MFA และสมัครใหม่ (ได้ secret ใหม่) |
| ผู้ใช้รายงานว่าได้ push อนุมัติมาตอนตีสาม ทั้งที่ไม่ได้ล็อกอิน | รหัสผ่านของผู้ใช้รั่ว ผู้โจมตีกำลังพยายามล็อกอิน (อาจเป็น MFA fatigue) | ให้ปฏิเสธ แล้วรีเซ็ตรหัสผ่านทันที ตรวจ log ล็อกอิน ถือเป็นเหตุการณ์ความปลอดภัย |
| ล็อกอิน SSO วนกลับมาหน้าล็อกอินซ้ำ (redirect loop) | คุกกี้ของแอปถูกบล็อก/ไม่ถูกตั้ง (SameSite, third-party cookie) หรือ `redirect_uri` ไม่ตรงที่ลงทะเบียน หรือเวลาเครื่องเพี้ยนทำให้ `exp` ดูหมดอายุ | เปิด DevTools → Network ดูลำดับ 302 และ Set-Cookie ตรวจเวลาเครื่อง |
| `invalid_redirect_uri` / `AADSTS50011` | URL ที่แอปส่งไปไม่ตรงกับที่ลงทะเบียนไว้ที่ IdP (ตรงตัวอักษร รวมถึง http/https, ท้าย /) | แก้ที่ IdP หรือที่การตั้งค่าแอปให้ตรงกัน |
| ล็อกอินที่แอป A ได้แต่แอป B ถามรหัสอีก | แอป B ไม่ได้ผูก SSO (ยังใช้บัญชีท้องถิ่น) หรือมีนโยบายบังคับยืนยันซ้ำ (step-up) | ตรวจการตั้งค่า SSO ของแอป B และ conditional access |
| พนักงานลาออก ปิดบัญชีที่ IdP แล้ว แต่ยังเข้า Slack ได้อีกครึ่งวัน | session ของ Slack ยังไม่หมดอายุ ไม่มีการเพิกถอนฝั่ง SP | เพิกถอน session ที่แอป, ใช้ SCIM / ปิด session ผ่าน API, ลดอายุ session |
| ใช้งาน IdP ไม่ได้ทั้งบริษัท | IdP ล่ม (จุดรวมศูนย์) | ใช้บัญชี break-glass ที่เก็บแยก ตรวจหน้าสถานะผู้ให้บริการ |
| ผู้ใช้ปฏิเสธแอป Authenticator เพราะไม่อยากลงในมือถือส่วนตัว | นโยบายองค์กรขัดความสะดวก | เสนอกุญแจฮาร์ดแวร์ FIDO2 ให้ (ไม่ต้องพึ่งมือถือส่วนตัว) |

## 9. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: ทำไมรหัสผ่านกับคำถามลับ (เช่น ชื่อสัตว์เลี้ยง) จึงไม่นับเป็น MFA"}
ทั้งสองเป็นประเภท "สิ่งที่คุณรู้" ผู้โจมตีที่ดักพิมพ์ (keylogger) หรือหลอกถามผ่านหน้าเว็บปลอมได้ทั้งสองอย่างในคราวเดียวด้วยวิธีเดียวกัน จึงไม่มีความอิสระของสาเหตุล้มเหลว ถือเป็นการยืนยันสองขั้น (two-step) ไม่ใช่ MFA ที่ต่างประเภท · และคำตอบของคำถามลับมักหาได้จากโซเชียลมีเดียด้วย
::

::reveal{question="ข้อ 2: แอปสร้างรหัส TOTP ได้อย่างไรทั้งที่มือถืออยู่ในโหมดเครื่องบิน"}
เพราะทั้งสองฝั่งคำนวณเอง: แอปมี secret ที่เก็บไว้ตั้งแต่สแกน QR และมีนาฬิกาของเครื่อง จึงคำนวณ HMAC-SHA1(secret, ⌊เวลา÷30⌋) แล้วตัดเป็น 6 หลักได้โดยไม่ใช้เครือข่าย เซิร์ฟเวอร์ทำคำนวณเดียวกันด้วยนาฬิกาตัวเอง สิ่งเดียวที่ต้องตรงกันคือเวลา (ผิดกันไม่เกินหน้าต่างที่ยอมรับ)
::

::reveal{question="ข้อ 3: ทำไมเซิร์ฟเวอร์เก็บ secret TOTP เป็น hash แบบรหัสผ่านไม่ได้ และมีผลอะไรต่อความปลอดภัย"}
เพราะเซิร์ฟเวอร์ต้องนำ secret มาคำนวณ HMAC ใหม่ทุกครั้งที่ตรวจ ต้องรู้ค่าจริง (hash ย้อนกลับไม่ได้ จึงคำนวณต่อไม่ได้) ผลคือถ้าฐานข้อมูลรั่วพร้อมกุญแจเข้ารหัส ผู้โจมตีได้ secret แล้วสร้างรหัสได้ทุกบัญชี ต่างจากรหัสผ่านที่รั่วแค่ hash จึงต้องเข้ารหัส secret ที่พักข้อมูลด้วยกุญแจแยกและจำกัดการเข้าถึง · FIDO2 เก็บแค่กุญแจสาธารณะจึงไม่มีปัญหานี้
::

::reveal{question="ข้อ 4: คำนวณ ผู้โจมตีเดารหัส TOTP 6 หลักสำเร็จในครั้งเดียวด้วยโอกาสเท่าใด ถ้าเซิร์ฟเวอร์ยอมรับ 3 ช่วง และจำกัดไว้ 5 ครั้ง"}
รหัสที่ถูกมี 3 ค่าจาก 10⁶ → 3 ÷ 1,000,000 = 3 × 10⁻⁶ ต่อครั้ง · 5 ครั้ง ≈ 1 − (1 − 3×10⁻⁶)⁵ ≈ 1.5 × 10⁻⁵ หรือราว 0.0015% · ถ้าไม่จำกัดและเดา 10 ครั้ง/วินาที (สมมติ) ถึง 50% ใน ≈ 231,000 ครั้ง ≈ 6.4 ชั่วโมง จึงต้องจำกัดอัตราเสมอ
::

::reveal{question="ข้อ 5: นาฬิกามือถือเดินเร็วกว่าเซิร์ฟเวอร์ 45 วินาที ถ้าเซิร์ฟเวอร์ยอมรับ ±1 ช่วง จะผ่านไหม"}
ขึ้นกับตำแหน่งในช่วง: ตัวนับของมือถือคือ ⌊(t+45)÷30⌋ เทียบกับของเซิร์ฟเวอร์ ⌊t÷30⌋ ต่างกัน 1 หรือ 2 ช่วง ขึ้นกับว่า t mod 30 เท่าไร ถ้า t mod 30 < 15 ต่างกัน 1 ช่วง → ผ่าน ถ้า ≥ 15 ต่างกัน 2 ช่วง → ไม่ผ่าน (ลองในสื่อโต้ตอบ แล้วกดหยุดเวลา/ขยับ 30 วินาที) ดังนั้นอาการ ผ่านบ้างไม่ผ่านบ้าง คือสัญญาณของ drift
::

::reveal{question="ข้อ 6: พนักงานล็อกอินด้วยลายนิ้วมือ แล้วรับรหัส SMS ใช่ MFA ไหม ประเภทอะไร และแข็งแรงแค่ไหน"}
ใช่ ประเภท "เป็น" + "มี" (โทรศัพท์) · แต่ SMS เป็นปัจจัยที่อ่อน (SIM swap, SS7, การถูก relay) และลายนิ้วมือที่สแกนเครื่องผู้ใช้ปกติปลดล็อกอุปกรณ์ ไม่ได้ส่งให้เซิร์ฟเวอร์ตรวจ ในระบบที่เซิร์ฟเวอร์ตรวจชีวมิติเอง การรั่วไหลแก้ไขไม่ได้ (เปลี่ยนนิ้วไม่ได้) นับเป็นความเสี่ยงอีกแบบ
::

::reveal{question="ข้อ 7: ทำไม number matching กัน MFA fatigue ได้ แต่ไม่กัน AiTM"}
fatigue: ผู้โจมตีเป็นคนเห็นเลขบนหน้าล็อกอินที่ตนเองสั่ง เหยื่อไม่เห็น จึงกดมั่วให้ผ่านไม่ได้ · AiTM: ผู้โจมตีส่งต่อหน้าล็อกอินจริงมายังเหยื่อ เหยื่อเห็นเลขนั้นจริงและพิมพ์ถูกต้องในแอป ผู้โจมตีจึงได้คุกกี้ session เพราะ number matching ไม่ได้ผูกกับโดเมน
::

::reveal{question="ข้อ 8: ทำไม FIDO2 กัน phishing ได้ ทั้งที่ผู้ใช้ถูกหลอกให้เข้าเว็บปลอม"}
เพราะลายเซ็นถูกสร้างโดยรวมค่า origin ที่ *เบราว์เซอร์* เห็น (ไม่ใช่หน้าเว็บบอก) และกุญแจแต่ละตัวผูกกับ rpId ของเว็บที่ลงทะเบียน เว็บปลอมที่โดเมนต่างกัน จึงไม่มีกุญแจให้ใช้ หรือได้ลายเซ็นที่เว็บจริงปฏิเสธเพราะ origin ไม่ตรง ผู้ใช้ไม่ต้องตัดสินใจเรื่องโดเมนเอง · ข้อจำกัด: ถ้าผู้โจมตีควบคุมเบราว์เซอร์/เครื่องของเหยื่อ หรือผู้ใช้ถูกหลอกให้ลงทะเบียนกุญแจกับเว็บปลอมตั้งแต่ต้น การป้องกันนี้ก็ไม่ช่วย
::

::reveal{question="ข้อ 9: ในลำดับ OIDC ทำไมแอปจึงรับ code ผ่านเบราว์เซอร์แล้วค่อยแลก token ทางหลังบ้าน แทนที่จะรับ token ตรงๆ"}
URL ที่ผ่านเบราว์เซอร์เก็บในประวัติ/บันทึก proxy และอ่านได้ด้วยสคริปต์ จึงไม่ควรมี token อยู่ที่นั่น code อายุสั้นใช้ครั้งเดียวและแลกได้เฉพาะแอปที่พิสูจน์ตัวเองกับ IdP (และมี PKCE code_verifier) ผู้ดัก code ได้ก็ใช้ไม่ได้
::

::reveal{question="ข้อ 10: SAML ต่างจาก OpenID Connect อย่างไร"}
ต่างกันที่รูปแบบและยุคสมัย: SAML ใช้ XML Assertion เซ็นด้วย XML Signature เหมาะกับแอปองค์กรเดิม ส่วน OIDC อยู่บน OAuth 2.0 ใช้ JWT (JSON) เหมาะกับเว็บ/มือถือสมัยใหม่ ตรวจง่ายกว่า มี discovery · ทั้งสองมีบทบาท IdP/SP เหมือนกันและพึ่งลายเซ็นเหมือนกัน
::

::reveal{question="ข้อ 11: ปิดบัญชีผู้ใช้ที่ IdP แล้ว session ในแอปที่ล็อกอินค้างอยู่จะเกิดอะไร"}
ไม่แน่ ขึ้นกับแต่ละแอป ส่วนใหญ่ session ของแอปเป็นอิสระหลังล็อกอินสำเร็จ จึงอยู่ต่อจนหมดอายุหรือแอปเช็กกับ IdP (คำตอบจากเอกสารต้นฉบับที่ว่า เสียสิทธิ์ทันทีทุกแอป เป็นภาพที่ง่ายเกินจริง) วิธีลดช่องว่าง: อายุ session สั้น, refresh token ที่ IdP เพิกถอนได้, back-channel logout, SCIM ลบบัญชีในแอป, เพิกถอน session ด้วยมือสำหรับเหตุร้ายแรง
::

::reveal{question="ข้อ 12: บริษัท 200 คน 20 แอป เปลี่ยนมาใช้ SSO จำนวนชุดรหัสผ่านที่ต้องดูแลลดจากเท่าไรเป็นเท่าไร และความเสี่ยงอะไรเพิ่มขึ้น"}
จาก 200 × 20 = 4,000 ชุด เหลือ 200 ชุด (ที่ IdP) · ความเสี่ยงที่เพิ่มคือจุดรวมศูนย์: บัญชีที่ IdP ถูกยึดเปิดทุกแอปพร้อมกัน และ IdP ล่มทำให้ทั้งบริษัททำงานไม่ได้ จึงต้องมี MFA ที่แข็งที่สุด บัญชีฉุกเฉิน และการเฝ้าระวังเป็นพิเศษที่ IdP
::

::reveal{question="ข้อ 13: ข้อจำกัดของบทนี้ที่ควรรู้"}
ตัวเลข (6.4 ชั่วโมง, 90 วินาที, 4,000 ชุดรหัส) เป็นค่าประมาณหรือสมมติ · หน้าต่างการยอมรับ TOTP และอายุ session ต่างกันตามผลิตภัณฑ์ · เมทริกซ์การโจมตีเป็นการประเมินเชิงกลไกแบบกว้าง ผลจริงขึ้นกับการตั้งค่า · บทนี้ไม่ลงลึก SAML XML signature, OAuth scope/consent หรือ Zero Trust/conditional access ที่เชื่อมกับหัวข้อถัดๆ ไป
::

## 10. แบบฝึกหัด (ลงมือทำจริง)

ทำบนเครื่องของคุณเอง เป็นคำสั่งอ่านอย่างเดียว (ห้ามใช้ secret ของบัญชีจริง)

1. **ตรวจ MFA ของบัญชีตัวเอง:** เปิดการตั้งค่าความปลอดภัยของบัญชี Google/GitHub/Microsoft ที่คุณใช้ จดว่าเปิด MFA แบบใดไว้บ้าง และมี backup codes หรืออุปกรณ์สำรองหรือยัง แล้วเรียงตามความแข็งแรงจากหัวข้อ 4
2. **คำนวณ TOTP ด้วยมือ:** รัน `node -e "const c=require('crypto');const b=Buffer.alloc(8);b.writeBigUInt64BE(1n);const h=c.createHmac('sha1','12345678901234567890').update(b).digest();const o=h[19]&15;console.log(((h.readUInt32BE(o)&0x7fffffff)%1e6+'').padStart(6,'0'))"` ควรได้ `287082` แล้วเปลี่ยน `1n` เป็น `2n` (จะได้ค่าอีกตัว) นี่คือกลไกเดียวกับหัวข้อ 3.2
3. **ทดสอบ drift:** ในสื่อ `totp-lab` ลาก drift ไปที่ 0, 25, 45, 120 กดหยุดเวลาแล้วขยับทีละ 30 วินาที จดว่าที่ +45 ผ่านเมื่อไร
4. **ดูตัวนับเวลาบนเครื่อง:** `date +%s` แล้วใช้ `echo $(( $(date +%s) / 30 ))` (Linux/macOS) หรือ `[int](([DateTimeOffset]::UtcNow.ToUnixTimeSeconds())/30)` (PowerShell) ดูว่าตัวเลขเพิ่มทีละ 1 ทุก 30 วินาที
5. **ตรวจนาฬิกา:** `timedatectl` (Linux) หรือ `w32tm /query /status` (Windows) ดูว่าซิงก์เวลาอยู่ไหม
6. **อ่าน OIDC จริง:** เปิด `https://accounts.google.com/.well-known/openid-configuration` ในเบราว์เซอร์ (ข้อมูลสาธารณะ) หา `authorization_endpoint`, `token_endpoint` และ `jwks_uri` แล้วเปิด `jwks_uri` ดูกุญแจสาธารณะที่ใช้ตรวจลายเซ็น `id_token`
7. **ถอด JWT:** นำ JWT ตัวอย่างจากเว็บ jwt.io หรือสร้างเองด้วยข้อความสมมติ (อย่านำ token จริงของบัญชีคุณไปวางในเว็บภายนอก) ดูว่า payload อ่านได้โดยไม่ต้องมีกุญแจ

::reveal{question="แนวคำตอบ"}
(1) อันดับโดยทั่วไป: ไม่มี MFA < SMS < TOTP < push + number matching < FIDO2/passkey · (2) 287082 สำหรับ 1n ส่วน 2n ได้ 359152 · (3) ที่ +45 วินาที ผ่านเมื่อ t mod 30 < 15 และไม่ผ่านเมื่อ ≥ 15 (ถ้าเซิร์ฟเวอร์ยอมรับ ±1) · (4) ตัวเลขเพิ่ม 1 ทุก 30 วินาที · (5) ควรเห็น synchronized: yes · (6) จะเห็น URL ของ authorization/token/jwks และกุญแจสาธารณะ (ชุด JWK ที่หมุนเวียนเป็นระยะ) · (7) payload เป็นเพียง base64url ของ JSON อ่านได้ทั้งหมด สิ่งที่กุญแจปกป้องคือไม่ให้ถูกแก้ไข ไม่ใช่ไม่ให้ถูกอ่าน
::

## 11. สรุป

- **MFA** ต้องใช้หลักฐานต่างประเภทและเป็นอิสระต่อกัน รหัสผ่าน + PIN ไม่ใช่ MFA
- **TOTP** คำนวณพร้อมกันสองฝั่งจาก secret + ⌊เวลา÷30⌋ ด้วย HMAC-SHA1 → offset → mod 10⁶ ทำงานโดยไม่ต้องใช้เครือข่าย แต่เซิร์ฟเวอร์ต้องเก็บ secret จริง รหัสหนึ่งตัวมีอายุจริง ≈ 90 วินาที และต้องจำกัดอัตราการเดา
- ปัจจัยที่สองไม่เท่ากัน: SMS (ซิม/relay) < TOTP (relay) < push + number matching (กัน fatigue ไม่กัน AiTM) < **FIDO2** (ผูกโดเมน กัน phishing)
- **SSO**: IdP พิสูจน์ตัวตนครั้งเดียว แล้วออก token ที่เซ็นลายเซ็นให้ SP ตรวจ (OIDC: code → id_token JWT → ตรวจ sig/iss/aud/exp/nonce) SP ไม่เคยเห็นรหัสผ่าน
- SAML (XML, องค์กรเดิม) vs OIDC (JSON/JWT, สมัยใหม่) · OAuth 2.0 = การให้สิทธิ์ OIDC = การพิสูจน์ตัวตนบน OAuth
- SSO ช่วยรวมนโยบายและถอนสิทธิ์ แต่เป็นจุดรวมศูนย์ และการปิดบัญชีที่ IdP ไม่ได้ตัด session เดิมของ SP ทันทีเสมอ
- ข้อจำกัด: ตัวเลขเป็นค่าประมาณ/สมมติ การตั้งค่าจริงแตกต่างกันตามผลิตภัณฑ์
- บทถัดไป: CIA Triad (ความลับ ความถูกต้อง ความพร้อมใช้) กรอบที่อธิบายว่ามาตรการทั้งหมดนี้ปกป้องอะไร
