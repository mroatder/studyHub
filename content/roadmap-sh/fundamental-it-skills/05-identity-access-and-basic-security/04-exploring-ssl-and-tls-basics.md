## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **ทำไม** การเข้ารหัสอย่างเดียวไม่พอบนเครือข่ายเปิด และ TLS ตอบ *สามโจทย์* อะไร (ความลับ, ความถูกต้อง, ตัวตนของเซิร์ฟเวอร์)
2. อธิบายปัญหา **การแลกกุญแจ** และวิธีที่ Diffie-Hellman ให้สองฝ่ายได้ความลับร่วมโดยไม่ส่งมันผ่านสาย พร้อมคำนวณตัวเลขจริงได้
3. อธิบายได้ว่าทำไมต้อง **ผสมสองแบบ** (อสมมาตรเพื่อตกลงกุญแจ, สมมาตรเพื่อเข้ารหัสข้อมูลจริง) และ AEAD ให้ทั้งความลับและความถูกต้องอย่างไร
4. ไล่ **การตรวจใบรับรอง X.509** ทีละข้อ (ชื่อโฮสต์, วันที่, ลายเซ็น, สายถึง root, การเพิกถอน) และวินิจฉัยได้ว่าทำไมเบราว์เซอร์เตือน
5. เล่า **handshake ของ TLS 1.2 เทียบ TLS 1.3** และคำนวณเวลารอ (RTT) ได้
6. อธิบาย **forward secrecy** และอ่านชื่อ cipher suite / ผล `openssl s_client` เป็น
7. บอกว่า TLS *ป้องกันอะไรและไม่ป้องกันอะไร* (ข้อมูลที่พักบนดิสก์, เครื่องปลายทางที่ถูกยึด, ข้อมูลเมตา) และแมปการโจมตีสำคัญกับกลไก

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | สิ่งที่เทียบได้ |
|---|---|
| จดหมายโปสการ์ดผ่านไปรษณีย์ ใครจับถือก็อ่านได้ | HTTP ธรรมดา (ไม่เข้ารหัส) |
| สองคนที่ไม่เคยเจอกันตกลงรหัสลับกลางห้องที่มีคนฟังอยู่ได้ (เปรียบเทียบด้วยการผสมสี: แต่ละคนผสมสีลับของตนกับสีกลางแล้วแลกกัน ผสมสีลับตัวเองซ้ำ จะได้สีเดียวกัน แต่คนฟังแยกสีลับออกมาไม่ได้) | Diffie-Hellman |
| บัตรประชาชนที่ออกโดยหน่วยงานรัฐ มีลายน้ำปลอมยาก คนรับตรวจได้โดยไม่ต้องโทรถามรัฐ | ใบรับรอง X.509 ที่ CA เซ็น |
| ตรวจบัตร: ชื่อตรงคนไหม, หมดอายุหรือยัง, ลายน้ำจริงไหม, อยู่ในบัญชีบัตรที่ถูกยกเลิกหรือเปล่า | ขั้นตรวจใบรับรองของเบราว์เซอร์ |
| คนไปรับของ ต้องโชว์บัตรก่อน แล้วค่อยคุยเรื่องส่งของด้วยรหัสที่ตกลงกัน | handshake ก่อน แล้วค่อยส่งข้อมูลด้วยกุญแจสมมาตร |
| ล็อกเกอร์ที่ใช้กุญแจดอกเดียวตลอดชีวิต ถ้ากุญแจถูกลอกทีหลัง ของเก่าทุกชิ้นเสี่ยง vs ใช้รหัสใหม่ทุกครั้ง | ไม่มี vs มี forward secrecy |

## 1. ปัญหาตั้งต้น: ทำไมต้องมี TLS

> **นึกภาพว่า:** ส่งโปสการ์ดผ่านคนกลางหลายมือ ทุกคนอ่านได้ แก้ได้ และใครก็อ้างว่าเป็นธนาคารได้ TLS ทำสามอย่างพร้อมกัน: ใส่ซองปิดผนึก (ความลับ) ตราประทับกันแก้ (ความถูกต้อง) และบัตรประจำตัวของปลายทาง (ตัวตน)

ข้อมูลที่คุณส่งไปเว็บธนาคารเดินทางผ่านเราเตอร์ที่บ้าน, ISP, เราเตอร์กลางทางอีกหลายตัว โดยที่ไม่มีใครรับประกันว่าทุกตัวซื่อสัตย์ (บท 15 และ 20 เห็นแล้วว่า Wireshark อ่านข้อมูลแบบไม่เข้ารหัสได้ทั้งหมด) เมื่อจะคุยกับเซิร์ฟเวอร์อย่างปลอดภัย มีโจทย์ที่ต้องแก้ **สามข้อ** และแต่ละข้อมีเทคนิคของตัวเอง

| โจทย์ | ถ้าไม่แก้จะเกิดอะไร | เทคนิคที่ TLS ใช้ | ตรงกับ CIA |
|---|---|---|---|
| ผู้ดักฟังอ่านไม่ได้ | รหัสผ่านและข้อมูลรั่ว | เข้ารหัสสมมาตร ด้วยกุญแจที่ตกลงกันเฉพาะการเชื่อมต่อนั้น | C |
| ผู้อยู่กลางทางแก้ไม่ได้โดยไม่ถูกจับ | ผู้ร้ายแก้ยอดโอน/แทรกสคริปต์ | MAC/AEAD tag ติดทุกเรคคอร์ด | I |
| คุยกับ *ตัวจริง* ไม่ใช่คนปลอมตัว | MITM เข้ารหัสกับผู้ร้ายแทนธนาคาร | ใบรับรอง + ลายเซ็นของเซิร์ฟเวอร์ | ตัวตน (authenticity) |

สังเกตว่าข้อสามเป็นสิ่งที่ CIA เปล่าๆ ไม่ครอบคลุม (บท 23 หัวข้อ 6.2) ซึ่ง TLS เติมให้ และเป็นข้อที่คนมักลืม: **การเข้ารหัสที่ไม่ยืนยันตัวตนปลายทาง ก็แค่เข้ารหัสไปหาผู้ร้าย**

> **ความแม่นยำ:** ต้นฉบับบางส่วนกล่าวว่า TLS ให้ "non-repudiation" (ปฏิเสธไม่ได้) ซึ่งไม่ตรงนัก TLS ใช้ MAC แบบสมมาตรกับข้อมูลในเซสชัน ทั้งสองฝ่ายสร้าง tag ได้ จึง *พิสูจน์ต่อบุคคลที่สามไม่ได้* ว่าใครส่ง (ต่างจากลายเซ็นดิจิทัลบนเอกสาร) TLS ให้การยืนยันตัวตน *ต่อคู่สนทนา* ในเวลานั้น เท่านั้น

## 2. SSL กับ TLS: ประวัติและสถานะ

> **นึกภาพว่า:** ชื่อเดิมกับชื่อใหม่ของสินค้าเดียวกัน SSL เป็นรุ่นเก่าที่ถูกเลิกใช้เพราะมีช่องโหว่ TLS คือรุ่นต่อมา ปัจจุบันควรใช้ TLS 1.2 และ 1.3 เท่านั้น คนยังพูดว่า "SSL" ตามความเคยชิน

SSL เริ่มที่ Netscape ในทศวรรษ 1990 ช่องโหว่ในรุ่นเก่า (เช่น POODLE กับ SSL 3.0) ทำให้ IETF ออกแบบใหม่และเปลี่ยนชื่อเป็น TLS คำว่า "SSL certificate" ที่ได้ยินทุกวันนี้เป็นแค่คำเรียกติดปาก ของจริงคือใบรับรองที่ใช้กับ TLS

| รุ่น | ปีที่ออก | สถานะ (ณ ปัจจุบัน) |
|---|---|---|
| SSL 2.0 | 1995 | ห้ามใช้ |
| SSL 3.0 | 1996 | ห้ามใช้ |
| TLS 1.0 | 1999 | เลิกใช้ (deprecated) |
| TLS 1.1 | 2006 | เลิกใช้ (deprecated) |
| TLS 1.2 | 2008 | ยังใช้กว้าง ถ้าตั้งค่าดี |
| TLS 1.3 | 2018 | แนะนำ |

ใน OSI (บท 9) TLS อยู่ **เหนือ TCP และใต้โปรโตคอลแอป** (HTTP, SMTP, IMAP …) ไม่ได้ตรงกับชั้นใดชั้นหนึ่งพอดี (เป็นตัวอย่างที่ OSI ไม่ตรงกับโลกจริงทุกกรณี) HTTP ธรรมดาใช้พอร์ต 80 พอห่อด้วย TLS เป็น HTTPS ใช้พอร์ต 443 ส่วน QUIC/HTTP/3 ฝัง TLS 1.3 ไว้บน UDP ต่างจากที่ว่ามาเล็กน้อย แต่หลักการเดียวกัน

## 3. แก้โจทย์การแลกกุญแจ: Diffie-Hellman

> **นึกภาพว่า:** อยากตกลงกุญแจลับกับคนแปลกหน้าท่ามกลางคนดักฟัง ต้องไม่ส่งกุญแจตรงๆ วิธีคือต่างฝ่ายผสมสีลับของตัวเองกับสีสาธารณะ แล้วแลกสีที่ผสมแล้ว ผสมสีลับตัวเองซ้ำอีกที ได้สีเดียวกัน แต่คนดักฟังแยกสีลับออกจากสีผสมไม่ได้

### 3.1 ทำไมต้องผสมสองแบบ

> **นึกภาพว่า:** กุญแจชุดเดียวที่ทั้งสองฝ่ายถือ (สมมาตร) เร็วมากแต่ส่งให้กันยาก ส่วนกุญแจคู่ (อสมมาตร) แลกกันปลอดภัยแต่ช้า จึงใช้แบบช้าตกลงกุญแจ แล้วใช้แบบเร็วส่งข้อมูลจริง

**สมมาตร** (AES) ใช้กุญแจเดียวเข้าและถอดรหัส เร็วมาก แต่ทั้งสองฝ่ายต้อง *รู้กุญแจเดียวกันล่วงหน้า* ถ้าส่งกุญแจผ่านสายที่ถูกดักฟัง ก็ไม่ต่างจากไม่ได้เข้ารหัส (โจทย์ "ไก่กับไข่")

**อสมมาตร** (คู่กุญแจสาธารณะ/ส่วนตัว) แก้ปัญหานี้ได้ เพราะไม่ต้องแชร์ความลับล่วงหน้า แต่คำนวณหนักกว่าสมมาตรมาก (ต้นฉบับว่าราว 1,000 เท่า ซึ่งเป็น *ค่าประมาณ* ขึ้นกับอัลกอริทึมและฮาร์ดแวร์) จึงไม่เหมาะเข้ารหัสข้อมูลก้อนใหญ่

ทางออกที่ TLS ใช้: **ใช้อสมมาตรเฉพาะตอนตกลงกุญแจและยืนยันตัวตน แล้วเปลี่ยนไปใช้สมมาตรกับข้อมูลทั้งหมดหลังจากนั้น** (เรียกว่า hybrid cryptosystem)

### 3.2 Diffie-Hellman ทำงานอย่างไร (ทดลองคำนวณจริง)

> **นึกภาพว่า:** ตัวเลขเล็กที่ตรวจด้วย node (ตัวอย่างสมมติ p=23, g=5)
>
> ```
> A เลือก a=6   ส่ง A = 5^6 mod 23  = 8
> B เลือก b=15  ส่ง B = 5^15 mod 23 = 19
> A คำนวณ 19^6  mod 23 = 2
> B คำนวณ  8^15 mod 23 = 2     <- ความลับร่วม
> ```
>
> คนดักฟังเห็น 23, 5, 8, 19 แต่หา a หรือ b ยาก เมื่อ p ใหญ่จริง

ทั้งสองฝ่ายตกลง *ค่าสาธารณะ* สองค่า: จำนวนเฉพาะ p และฐาน g แล้วต่างสุ่ม *ความลับ* ของตัวเอง (a และ b) ที่ไม่ส่งออกสาย

1. ไคลเอนต์ส่ง **A = gᵃ mod p** · เซิร์ฟเวอร์ส่ง **B = gᵇ mod p**
2. ไคลเอนต์คำนวณ **Bᵃ mod p** · เซิร์ฟเวอร์คำนวณ **Aᵇ mod p**
3. ทั้งสองได้ค่าเดียวกัน = **g^(ab) mod p** เพราะ (gᵇ)ᵃ = (gᵃ)ᵇ

ผู้ดักฟังเห็น p, g, A, B แต่จะได้ g^(ab) ต้องหา a หรือ b ซึ่งคือ **ปัญหาลอการิทึมไม่ต่อเนื่อง (discrete logarithm)** ที่ไม่มีวิธีเร็วเมื่อ p ใหญ่พอ ตัวอย่างเล็กที่ตรวจด้วย node: p=23, g=5, a=6, b=15 → A=8, B=19 ทั้งสองฝ่ายได้ความลับร่วม **2**

ลองเอง: เปลี่ยน p ให้ใหญ่ขึ้นแล้วดูว่าผู้ดักฟังต้อง *ลองกี่ครั้ง* ตอนท้ายสื่อมีสวิตช์จำลอง MITM และการเซ็นเพื่อป้องกัน

::

> **ความแม่นยำ:** ตัวอย่างใช้ p เล็กเพื่อให้เห็นตัวเลข เบราว์เซอร์จริงใช้ **ECDHE** บนเส้นโค้งวงรี (เช่น X25519 กุญแจราว 255 บิต) หรือ DH กลุ่มใหญ่ ≥ 2048 บิต ความปลอดภัยของ DH อาศัย *ความเชื่อ* ว่าลอการิทึมไม่ต่อเนื่องแก้ยาก (ยังไม่มีบทพิสูจน์ทางคณิตศาสตร์) และคอมพิวเตอร์ควอนตัมขนาดใหญ่จะทำลายได้ด้วยอัลกอริทึมของ Shor จึงมีการพัฒนา key exchange แบบทนควอนตัมที่ผสมกับ X25519 แล้วในซอฟต์แวร์ปัจจุบันบางตัว

### 3.3 Forward secrecy: ทำไมต้องใช้กุญแจ "ชั่วคราว"

> **นึกภาพว่า:** ใช้กุญแจใหม่ทุกการสนทนา แล้วทิ้งกุญแจนั้น วันหนึ่งโจรขโมยกุญแจหลักของเซิร์ฟเวอร์ได้ ก็ถอดบันทึกการสนทนาเก่าที่เก็บไว้ไม่ได้

ในรูปแบบเก่า (RSA key exchange) ไคลเอนต์สร้างความลับแล้วเข้ารหัสด้วย *กุญแจสาธารณะของเซิร์ฟเวอร์* ที่ใช้ซ้ำนานเป็นปี ถ้าผู้ร้าย **บันทึกทราฟฟิกเก็บไว้** แล้ววันหนึ่งได้กุญแจส่วนตัวของเซิร์ฟเวอร์ (เจาะเซิร์ฟเวอร์ หรือหมายศาล) ก็ถอดการสนทนาย้อนหลังได้ทั้งหมด

ใน **ECDHE** (E = ephemeral) a และ b ถูกสุ่มใหม่ทุกการเชื่อมต่อและทิ้งทันทีหลังคำนวณ กุญแจระยะยาวของเซิร์ฟเวอร์ใช้ *เซ็น* เท่านั้น ไม่ได้ใช้ห่อกุญแจเซสชัน ดังนั้นแม้กุญแจส่วนตัวรั่วทีหลัง ผู้ร้ายก็ได้แค่ปลอมตัวเป็นเซิร์ฟเวอร์ *จากนี้ไป* ถอดข้อมูลเก่าไม่ได้ นี่คือ **forward secrecy** (หรือ perfect forward secrecy) TLS 1.3 *บังคับ* ใช้ key exchange แบบชั่วคราวเสมอ

## 4. เข้ารหัสข้อมูลจริง: สมมาตรแบบ AEAD

> **นึกภาพว่า:** หลังตกลงกุญแจแล้ว ใช้ตู้ล็อกแบบมีตราประทับในตัว ใส่ของ -> ล็อก -> ได้ตราประทับ ถ้ามีใครแก้กล่องแม้นิดเดียว ตราประทับไม่ตรง เปิดไม่ได้เลย (AEAD เช่น AES-GCM)

เมื่อมีความลับร่วมแล้ว TLS ใช้มันเป็นวัตถุดิบ ผ่านฟังก์ชันสร้างกุญแจ (HKDF ใน TLS 1.3) แตกเป็นกุญแจหลายดอกแยกหน้าที่ (ฝั่งส่ง/ฝั่งรับ, handshake/ข้อมูลแอป) แล้วเข้ารหัสด้วยอัลกอริทึมแบบ **AEAD** (Authenticated Encryption with Associated Data) เช่น **AES-GCM** หรือ **ChaCha20-Poly1305**

AEAD คือ *เข้ารหัสและแปะ tag ตรวจความถูกต้องในขั้นตอนเดียว* ผู้รับถอดแล้วคำนวณ tag ใหม่ ถ้า tag ไม่ตรง (มีบิตถูกแก้แม้เพียงบิตเดียว) ก็ **ทิ้งทั้งเรคคอร์ด** โดยไม่ส่งข้อมูลที่เสียให้แอป นี่คือ Integrity ที่บท 23 บอกว่า "ต้องมีกุญแจ" (หลักเดียวกับ HMAC) ตัวอย่างการอ่านชื่อ cipher suite ของ TLS 1.3: `TLS_AES_256_GCM_SHA384`

- **AES_256_GCM** = อัลกอริทึม AEAD (กุญแจ 256 บิต, โหมด GCM)
- **SHA384** = ฟังก์ชันแฮชที่ใช้ใน HKDF และใน transcript ของ handshake

(TLS 1.2 ใช้ชื่อยาวกว่า เช่น `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` ที่บอกครบว่า key exchange = ECDHE, ลายเซ็น = RSA, เข้ารหัส = AES-128-GCM, แฮช = SHA-256 ส่วน TLS 1.3 แยก key exchange และลายเซ็นออกจากชื่อ suite เพราะเจรจาแยกกัน)

> **ข้อควรระวัง:** AES-GCM *ห้ามใช้ nonce ซ้ำ* กับกุญแจเดิม ถ้าซ้ำ ความปลอดภัยพังทั้งความลับและความถูกต้อง TLS จัดการนี้ให้โดยนับลำดับเรคคอร์ด จึงเป็นเหตุผลหนึ่งที่ *ไม่ควรเขียนโปรโตคอลเข้ารหัสเอง*

## 5. ใบรับรองดิจิทัลและความเชื่อถือ (PKI)

> **นึกภาพว่า:** บัตรประจำตัวที่ออกโดยหน่วยงานที่คุณไว้ใจ ใครอ้างเป็น bank.com ต้องแสดงบัตรที่มีตราของหน่วยงานนั้น เบราว์เซอร์ตรวจตราก่อนเชื่อ

### 5.1 ทำไมต้องมีใบรับรอง

> **นึกภาพว่า:** แลกกุญแจเฉยๆ ไม่รู้ว่ากำลังคุยกับใคร อาจเป็นคนกลางที่ปลอมตัว (MITM) ใบรับรองผูก "ชื่อ" เข้ากับ "กุญแจสาธารณะ" ด้วยลายเซ็นของผู้ออก

DH ตกลงกุญแจได้ แต่ **ไม่บอกว่ากำลังคุยกับใคร** ถ้ามี Mallory อยู่กลางทาง เธอทำ DH กับไคลเอนต์ทีหนึ่ง และทำ DH กับเซิร์ฟเวอร์อีกทีหนึ่ง เห็นข้อความทั้งหมด (ลองในสื่อ `dh-lab` ด้านบนโดยติ๊ก MITM) ไคลเอนต์ต้องมี *วิธีรู้* ว่า key share ที่ได้มาจากเจ้าของโดเมนจริง

ใบรับรอง **X.509** คือเอกสารที่ **Certificate Authority (CA)** เซ็นดิจิทัลเพื่อยืนยันว่า "กุญแจสาธารณะนี้เป็นของโดเมนนี้" ภายในมี: ชื่อเจ้าของ (Subject) และรายชื่อโดเมนที่ใช้ได้ (SAN, Subject Alternative Name), กุญแจสาธารณะ, ช่วงเวลาที่ใช้ได้ (Not Before/Not After), ผู้ออก (Issuer), หมายเลขซีเรียล และลายเซ็นของ CA

เซิร์ฟเวอร์พิสูจน์ว่า *เป็นเจ้าของกุญแจส่วนตัวที่ตรงกับใบรับรอง* โดยเซ็น transcript ของ handshake (ข้อความ `CertificateVerify`) ผู้โจมตีที่ *คัดลอกใบรับรอง* ของจริงไปก็เซ็นไม่ได้ เพราะไม่มีกุญแจส่วนตัว ใบรับรองจึง **ไม่เป็นความลับ** ใครก็ดูได้ ความลับคือกุญแจส่วนตัว

### 5.2 สายความเชื่อถือ (chain of trust)

> **นึกภาพว่า:** ลายเซ็นของผู้จัดการถูกรับรองโดยผู้อำนวยการ ซึ่งถูกรับรองโดยกระทรวง ที่เครื่องคุณมีรายชื่อกระทรวงที่ไว้ใจอยู่แล้ว (root CA)
>
> ```
> เว็บไซต์ -> CA กลาง (intermediate) -> CA ราก (root) <- ติดมากับเครื่องคุณ
> ```

ใบรับรองปลายทางถูกเซ็นโดย **CA กลาง (intermediate)** ซึ่งถูกเซ็นโดย **root CA** ใบ root เซ็นตัวเอง (self-signed) และ *ติดตั้งมาล่วงหน้า* ใน **root trust store** ของระบบปฏิบัติการ/เบราว์เซอร์ ที่เป็นรายการ CA ที่ผู้ผลิตตรวจสอบและยอมเชื่อ

ทำไมต้องมีใบกลาง: เก็บกุญแจ root ไว้ออฟไลน์ที่ปลอดภัยสุด และใช้ใบกลางเซ็นงานประจำ ถ้าใบกลางรั่วก็เพิกถอนเฉพาะใบกลางโดยไม่ต้องเปลี่ยนที่เก็บของทุกเครื่องในโลก

### 5.3 ทดลอง: เบราว์เซอร์ตรวจอะไรบ้าง

> **นึกภาพว่า:** ยามตรวจบัตรทีละข้อ: ลายเซ็นจริงไหม ชื่อตรงกับเว็บที่เปิดไหม หมดอายุหรือยัง ถูกเพิกถอนหรือไม่ สายความเชื่อถือไปถึงรากที่ไว้ใจไหม ข้อใดผิดข้อเดียว เบราว์เซอร์เตือน

เลือกสถานการณ์แล้วกด "ตรวจข้อถัดไป" ดูว่าข้อไหนไม่ผ่านก่อน และทำไมจึงเกิดอาการแบบนั้น

::cert-chain
::

สรุปสิ่งที่ต้องผ่านทั้งหมด (ขาดข้อเดียวคือไม่ผ่าน):

1. **ชื่อตรง:** ชื่อที่เปิดต้องอยู่ใน SAN (เบราว์เซอร์สมัยใหม่ไม่ดู CN แล้ว)
2. **ช่วงเวลา:** วันนี้อยู่ระหว่าง Not Before ถึง Not After
3. **ลายเซ็นถูกต้อง:** ถอดลายเซ็นของผู้ออกด้วยกุญแจสาธารณะของผู้ออก แล้วแฮชเนื้อหาต้องตรงกัน
4. **สายครบ:** ต่อใบปลายทาง → ใบกลาง → … ได้
5. **จบที่ root ที่เชื่อถือ**
6. **ไม่ถูกเพิกถอน** (CRL/OCSP, หรือ OCSP stapling ที่เซิร์ฟเวอร์แนบหลักฐานมาให้)

อายุใบรับรองสาธารณะสั้นลงเรื่อยๆ ตามนโยบายของอุตสาหกรรม (ปัจจุบันไม่เกินราว 398 วัน และกำลังมีกำหนดลดลงอีกเป็นขั้น; Let's Encrypt ออกใบอายุ 90 วัน — *ตัวเลขนโยบายเปลี่ยนได้ ควรตรวจกับแหล่งล่าสุด*) เหตุผลคือจำกัดความเสียหายจากกุญแจรั่วที่ไม่ถูกตรวจพบ และบังคับให้ใช้ระบบต่ออายุอัตโนมัติ (ACME)

> **ความแม่นยำ:** CA ยืนยันเพียงว่าผู้ขอ *ควบคุมโดเมนนั้น* (domain validation, DV) ไม่ได้ยืนยันว่าเว็บนั้นน่าเชื่อถือหรือไม่ใช่เว็บหลอกลวง เว็บฟิชชิงก็ขอใบรับรอง HTTPS ได้ กุญแจในแถบที่อยู่จึงแปลว่า *"ช่องทางถึงโดเมนนี้ปลอดภัย"* ไม่ใช่ *"เว็บนี้ปลอดภัย"* และระบบ PKI พึ่งพา CA ทุกเจ้าใน trust store ถ้า CA ใดออกใบผิดพลาด (เช่นกรณี DigiNotar ปี 2011 ที่ถูกเจาะแล้วออกใบปลอมให้ google.com) ผู้ร้ายก็ MITM ได้ จึงมี Certificate Transparency (บันทึกสาธารณะของใบที่ออก) ช่วยตรวจจับ

## 6. Handshake: ไล่ทีละขั้น

> **นึกภาพว่า:** การทักทายก่อนคุยจริง ตกลงภาษา (cipher) แลกกุญแจ แสดงบัตร แล้วจึงเริ่มคุยเรื่องจริงในซองปิดผนึก

หลัง TCP handshake (SYN, SYN-ACK, ACK) เสร็จ ไคลเอนต์กับเซิร์ฟเวอร์เริ่ม TLS handshake เพื่อตกลงอัลกอริทึม, ยืนยันเซิร์ฟเวอร์ และสร้างกุญแจเซสชัน

### 6.1 TLS 1.3 (1 RTT)

> **นึกภาพว่า:** ไคลเอนต์ส่งส่วนของกุญแจมาพร้อมคำทักทายเลย เซิร์ฟเวอร์ตอบพร้อมบัตรและส่วนกุญแจของตัวเอง จบใน 1 ไปกลับ แล้วเริ่มส่งข้อมูลได้เลย

ขั้นตอนเหล่านี้ทำให้เห็นสามเรื่องสำคัญ

1. **Finished คือ MAC ของทั้ง handshake** ถ้าผู้โจมตีกลางทางแก้ ClientHello (เช่น ลบ suite แข็งออกเพื่อบังคับให้ใช้ตัวอ่อน เรียก downgrade attack) ค่า Finished จะไม่ตรง การเชื่อมต่อล้ม
2. **ใบรับรองถูกเข้ารหัสแล้วใน TLS 1.3** ผู้ดักฟังเห็นใบรับรองไม่ได้ (ต่างจาก 1.2) แต่ยังเห็น **SNI** (ชื่อโฮสต์ใน ClientHello) ซึ่งเป็นข้อมูลเมตาที่รั่ว กำลังแก้ด้วย ECH (Encrypted Client Hello) ที่ยังไม่ใช้ทั่วทุกที่
3. **0-RTT (early data)** ใน 1.3 ใช้กับการเชื่อมต่อซ้ำ (session resumption) ส่งข้อมูลมากับ ClientHello ได้เลย แต่ **เสี่ยงโดนส่งซ้ำ (replay)** จึงควรใช้เฉพาะคำขอที่ซ้ำแล้วไม่เสียหาย (เช่น GET ที่ไม่เปลี่ยนสถานะ)

### 6.2 TLS 1.2 ต่างอย่างไร และคำนวณเวลารอ

> **นึกภาพว่า:** รุ่น 1.2 ต้องถามตอบเพิ่มหนึ่งรอบก่อนแลกกุญแจ
>
> ```
> TCP handshake 1 RTT + TLS 1.2 = 2 RTT  -> รวม 3 RTT ก่อนส่งข้อมูล
> TCP handshake 1 RTT + TLS 1.3 = 1 RTT  -> รวม 2 RTT
> ```

ใน TLS 1.2 ไคลเอนต์ *ยังไม่รู้* ว่าเซิร์ฟเวอร์จะเลือกอะไร จึงไม่ส่ง key share ตั้งแต่แรก ต้องรอ ServerHello (ที่มี key share ของเซิร์ฟเวอร์ และใบรับรองส่งเป็นข้อความเปิด) ก่อน แล้วค่อยตอบด้วย key share ของตัวเอง จึงต้องใช้ **2 RTT** ก่อนส่งข้อมูลแอปได้ (ถ้าไม่ใช้ session resumption)

โจทย์: เวลาจนถึงไบต์แรกของคำตอบ (ไม่นับเวลาประมวลผล) = TCP handshake (1 RTT) + TLS handshake + คำขอ/คำตอบ (1 RTT) TLS 1.2 = 1 + 2 + 1 = **4 RTT** · TLS 1.3 = 1 + 1 + 1 = **3 RTT** · TLS 1.3 แบบ 0-RTT ที่ต่อเชื่อมซ้ำ = 1 + 0 + 1 = **2 RTT**

| RTT ไปเซิร์ฟเวอร์ | TLS 1.2 | TLS 1.3 | TLS 1.3 (0-RTT) |
|---|---|---|---|
| 20 ms (ในประเทศ) | 80 ms | 60 ms | 40 ms |
| 100 ms (ข้ามทวีป) | 400 ms | 300 ms | 200 ms |
| 200 ms (มือถือสัญญาณแย่) | 800 ms | 600 ms | 400 ms |

(ตรวจด้วย node; เป็นแบบจำลองของแค่ RTT ไม่รวมเวลาประมวลผล, DNS, หรือการส่งซ้ำของ TCP) จะเห็นว่าบนเครือข่ายหน่วงสูง TLS 1.3 ประหยัดเวลาจริงจัง และนี่คือเหตุผลที่ QUIC ยังรวม TCP + TLS handshake เข้าด้วยกันอีก

เหตุผลอื่นที่ 1.3 ดีกว่า: ตัด RSA key exchange, ตัด cipher ที่มีปัญหา (CBC, RC4, SHA-1, การบีบอัด), เหลือ suite แบบ AEAD เท่านั้น ลดพื้นที่ที่จะตั้งค่าผิด

## 8. มุมมอง Security: แมปการโจมตีกับกลไก

> **นึกภาพว่า:** TLS ไม่ได้ป้องกันทุกอย่าง เว็บที่มีกุญแจเขียว (DV) บอกแค่ว่าติดต่อถูกเว็บ ไม่ได้บอกว่าเว็บนั้นน่าเชื่อถือ ตารางด้านล่างแมปแต่ละการโจมตีไปที่ข้อที่กันได้และข้อที่กันไม่ได้

| การโจมตี/ปัญหา | กลไกที่ถูกโจมตี | การป้องกัน |
|---|---|---|
| ดักฟังบน Wi-Fi สาธารณะ | ข้อมูลไม่เข้ารหัส (HTTP) | HTTPS ทั้งเว็บ, HSTS |
| **SSL stripping** | ผู้ร้ายกลางทางแปลงลิงก์ https เป็น http ก่อนไปถึงเหยื่อ | **HSTS** (เบราว์เซอร์จำว่าโดเมนนี้ต้อง https เท่านั้น) และ HSTS preload |
| **MITM ด้วยใบรับรองปลอม** | trust store / การตรวจสาย | ตรวจสายครบ, Certificate Transparency, อย่ากด "ดำเนินการต่อ" เมื่อมีคำเตือน |
| **Downgrade** (บังคับใช้รุ่น/suite อ่อน) | การเจรจา | Finished MAC, ปิด SSL/TLS รุ่นเก่า, TLS_FALLBACK_SCSV |
| **POODLE, BEAST** | ช่องโหว่ของ SSL 3.0 / CBC ใน TLS 1.0 | ปิดรุ่นเก่า ใช้ AEAD |
| **Heartbleed (2014)** | *บั๊กของโปรแกรม OpenSSL* (อ่านหน่วยความจำเกินขอบ) ไม่ใช่จุดอ่อนของโปรโตคอล TLS | อัปเดตไลบรารี + *เปลี่ยนกุญแจและใบรับรอง* เพราะกุญแจส่วนตัวอาจรั่วออกจากหน่วยความจำ |
| กุญแจส่วนตัวรั่ว | ผู้ร้ายปลอมเป็นเซิร์ฟเวอร์ได้ | เพิกถอนใบ + ออกกุญแจใหม่ + forward secrecy กันถอดของเก่า |
| ใบรับรองหมดอายุ | ไม่ใช่การโจมตี แต่ทำให้บริการล่ม (A) | ต่ออายุอัตโนมัติ (ACME) + เฝ้าระวังวันหมดอายุ |
| **TLS inspection / proxy องค์กร** | ติดตั้ง CA ขององค์กรลงเครื่อง ให้พร็อกซีถอดรหัสแล้วเข้ารหัสใหม่ (MITM โดยเจตนา) | ต้องรู้ว่ามีและมีนโยบายชัด มันได้ความสามารถตรวจมัลแวร์ แต่ก็เป็นจุดรวมความเสี่ยง |

**TLS ไม่ใช่ยาครอบจักรวาล:** ไม่ปกป้อง (1) ข้อมูลที่พักบนเซิร์ฟเวอร์ (2) เครื่องปลายทางที่ติดมัลแวร์ (3) เว็บที่ผู้ร้ายเป็นเจ้าของเอง (ที่มีใบรับรองถูกต้อง) (4) ข้อมูลเมตา เช่น IP ปลายทาง ขนาดและจังหวะของแพ็กเก็ต (และ SNI ถ้ายังไม่ใช้ ECH) และ (5) ความผิดพลาดของแอปเหนือ TLS (SQL injection ที่ส่งผ่าน HTTPS ก็ยังโดน)

## 9. ตัวอย่างวิเคราะห์ปัญหา IT Support

| อาการ | สาเหตุที่เป็นไปได้ (กลไก) | ตรวจ/แก้ |
|---|---|---|
| เบราว์เซอร์ขึ้น "Your connection is not private" `NET::ERR_CERT_DATE_INVALID` | ใบปลายทางหมดอายุ **หรือ** นาฬิกาเครื่องผิด (ตรวจช่วงวันที่เทียบเวลาเครื่อง) | ดูวันที่ในใบรับรอง และเวลาของเครื่อง ถ้าเครื่องเดียวที่เป็น เป็นที่เวลา ถ้าทุกเครื่อง เป็นที่ใบ ต่ออายุ |
| `ERR_CERT_COMMON_NAME_INVALID` | ชื่อที่เปิดไม่อยู่ใน SAN (เช่น เปิดด้วย IP แต่ใบออกให้ชื่อโดเมน, หรือย้ายโดเมนแต่ใบเดิม) | `openssl x509 -ext subjectAltName` เทียบกับ URL ออกใบใหม่ให้ครอบคลุมชื่อ |
| `ERR_CERT_AUTHORITY_INVALID` เฉพาะเว็บภายใน | ใช้ self-signed หรือ CA ภายในที่ยังไม่ได้ติดตั้งเป็น trusted root | แจก CA ภายในผ่านนโยบายองค์กร (GPO/MDM) ไม่ใช่ให้ผู้ใช้กด "ข้าม" |
| เปิดในเบราว์เซอร์ได้ แต่ `curl`/สคริปต์/แอปมือถือ error `unable to get local issuer certificate` | เซิร์ฟเวอร์ **ไม่ส่งใบกลาง** (เบราว์เซอร์ไปดึงเองได้ ไคลเอนต์อื่นไม่ได้) | ตั้งเซิร์ฟเวอร์ให้ส่ง fullchain (ใบปลายทาง + ใบกลาง) |
| เว็บใช้ได้ทุกเครื่อง ยกเว้นระบบเก่า (Windows 7 / Android เก่า) | ระบบเก่าไม่มี root ใหม่ใน trust store หรือไม่รองรับ TLS 1.2+ | อัปเดต trust store/ระบบ หรือยอมรับว่าเลิกรองรับ (ดีกว่าลดความปลอดภัยฝั่งเซิร์ฟเวอร์) |
| อยู่ในออฟฟิศแล้วเว็บขึ้นว่าผู้ออกคือ "บริษัทเรา" ทุกเว็บ | **TLS inspection** ของไฟร์วอลล์/พร็อกซีองค์กร (CA องค์กรอยู่ใน trust store) | ปกติ ถ้านโยบายประกาศไว้ แต่ถ้าที่บ้านก็เจอ → สงสัย MITM/มัลแวร์ที่ติดตั้ง root |
| `SSL_ERROR_RX_RECORD_TOO_LONG` / handshake failure ที่พอร์ต 443 | พอร์ตตอบด้วย HTTP ธรรมดา, หรือเซิร์ฟเวอร์กับไคลเอนต์ไม่มี suite/รุ่นที่ตรงกัน | `openssl s_client -connect host:443` ดูว่าตอบอะไร ตรวจ ssl_protocols/ciphers ของเซิร์ฟเวอร์ |
| API ล้มหลังต่ออายุใบรับรอง ทั้งที่เบราว์เซอร์ปกติ | แอปไคลเอนต์ทำ **certificate pinning** ไว้กับใบ/กุญแจเก่า | อัปเดต pin ก่อนสลับใบ ใช้ pin ที่กุญแจสาธารณะของ CA กลาง หรือหลีกเลี่ยง pinning ที่ยืดหยุ่นไม่ได้ |
| หน้าเว็บ https ขึ้นเตือน mixed content / ไอคอนไม่ปลอดภัย | หน้า https โหลดรูป/สคริปต์ผ่าน http (ส่วนที่ไม่เข้ารหัสถูกแก้ได้ จึงทำลายความน่าเชื่อถือทั้งหน้า) | แก้ลิงก์ให้เป็น https หรือ protocol-relative, ใช้ CSP `upgrade-insecure-requests` |

## 10. ศัพท์สำคัญ

| English | คำอ่าน / คำไทย | ความหมาย |
|---|---|---|
| TLS (Transport Layer Security) | ทีแอลเอส | โปรโตคอลเข้ารหัสและยืนยันตัวตนเหนือ TCP |
| SSL (Secure Sockets Layer) | เอสเอสแอล | รุ่นเก่าก่อน TLS (เลิกใช้แล้ว) คำนี้ยังถูกใช้เรียกแทน TLS ตามความเคยชิน |
| HTTPS | เอชทีทีพีเอส | HTTP ที่ห่อด้วย TLS ใช้พอร์ต 443 |
| Symmetric encryption | ซิมเมตริก / การเข้ารหัสแบบสมมาตร | ใช้กุญแจเดียวเข้าและถอดรหัส เร็ว (AES, ChaCha20) |
| Asymmetric encryption | แอสซิมเมตริก / แบบอสมมาตร | ใช้คู่กุญแจสาธารณะ-ส่วนตัว ช้ากว่า ใช้ตกลงกุญแจ/เซ็น |
| Diffie-Hellman (DH / ECDHE) | ดิฟฟี-เฮลล์แมน | วิธีให้สองฝ่ายสร้างความลับร่วมบนสายเปิด (ECDHE = ชนิดเส้นโค้งวงรี ชั่วคราว) |
| Forward secrecy | ฟอร์เวิร์ดซีเครซี / ความลับล่วงหน้า | กุญแจระยะยาวรั่วทีหลัง ก็ถอดเซสชันเก่าไม่ได้ |
| AEAD | เออีเอดี | การเข้ารหัสที่ให้ความถูกต้องในตัว (AES-GCM, ChaCha20-Poly1305) |
| Cipher suite | ไซเฟอร์สวีต | ชุดอัลกอริทึมที่ตกลงกัน เช่น TLS_AES_256_GCM_SHA384 |
| Handshake | แฮนด์เชก / การจับมือ | ขั้นตอนเริ่มต้นเพื่อตกลงพารามิเตอร์และสร้างกุญแจเซสชัน |
| RTT (Round-Trip Time) | อาร์ทีที / เวลาไปกลับ | เวลาที่ข้อความไปถึงปลายทางและตอบกลับ |
| Certificate (X.509) | ใบรับรอง | ไฟล์ที่ผูกชื่อโดเมนกับกุญแจสาธารณะ เซ็นโดย CA |
| Certificate Authority (CA) | ซีเอ / ผู้ออกใบรับรอง | องค์กรที่ยืนยันและเซ็นใบรับรอง |
| Root / Intermediate CA | รูท / ซีเอกลาง | ใบต้นสายที่เชื่อถือในเครื่อง / ใบที่ root มอบอำนาจเซ็นงานประจำ |
| Trust store | ทรัสต์สโตร์ | รายการ root CA ที่ระบบเชื่อถือ |
| SAN (Subject Alternative Name) | แซน | รายชื่อโดเมน/IP ที่ใบรับรองใช้ได้ |
| CRL / OCSP | ซีอาร์แอล / โอซีเอสพี | วิธีตรวจว่าใบถูกเพิกถอนแล้วหรือยัง |
| HSTS | เอชเอสทีเอส | หัว HTTP ที่สั่งให้เบราว์เซอร์ใช้ https เท่านั้น กัน SSL stripping |
| SNI (Server Name Indication) | เอสเอ็นไอ | ชื่อโฮสต์ที่ไคลเอนต์บอกใน ClientHello (ยังอ่านได้ถ้าไม่ใช้ ECH) |
| Certificate pinning | การปักหมุดใบรับรอง | แอปจำเพาะว่าจะเชื่อเฉพาะใบ/กุญแจนี้ |

## 11. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: ทำไมไม่ใช้การเข้ารหัสแบบอสมมาตรเข้ารหัสข้อมูลทั้งหมดไปเลย (ตรงกับคำถามท้ายบท 3)"}
(1) ช้ากว่าสมมาตรมากในการเข้ารหัสข้อมูลก้อนใหญ่ (ต้นฉบับว่าราว 1,000 เท่า ค่าประมาณ) (2) ขนาดข้อมูลที่เข้ารหัสได้ต่อครั้งจำกัดตามขนาดกุญแจ (3) ไม่ให้ forward secrecy ถ้าใช้กุญแจระยะยาวห่อข้อมูล · TLS จึงใช้อสมมาตรเฉพาะตกลงกุญแจ/เซ็น แล้วสลับไปสมมาตร (AEAD) ที่เร็วและให้ความถูกต้องในตัว
::

::reveal{question="ข้อ 2: ทำไม TLS 1.3 เร็วกว่า 1.2 ตอนเริ่มเชื่อมต่อ (ตรงกับคำถามท้ายบท 1)"}
ไคลเอนต์ส่ง key share (ECDHE) มาในข้อความแรกเลยโดยเดากลุ่มที่เซิร์ฟเวอร์จะเลือก เซิร์ฟเวอร์ตอบพร้อม key share ของตน จึงมีกุญแจครบหลัง 1 RTT ส่วน 1.2 ต้องรอ ServerHello ก่อนจึงส่ง key share ใช้ 2 RTT · เวลาถึงไบต์แรก: 1.2 = 4 RTT (TCP 1 + TLS 2 + คำขอ 1) vs 1.3 = 3 RTT เช่นที่ RTT 100 ms ได้ 400 vs 300 ms · ถ้าเดากลุ่มผิด ต้องมี HelloRetryRequest ทำให้ช้าลงอีกรอบ (ข้อจำกัดของ "1 RTT" คือกรณีปกติ)
::

::reveal{question="ข้อ 3: เซิร์ฟเวอร์ส่งใบรับรองที่ออกให้ admin.org ขณะผู้ใช้เปิด portal.org จะเกิดอะไร (ตรงกับคำถามท้ายบท 2)"}
เบราว์เซอร์เทียบชื่อที่เปิดกับ SAN แล้วไม่พบ จึงเตือน (เช่น ERR_CERT_COMMON_NAME_INVALID) แม้ลายเซ็นของ CA ถูกต้อง สายถึง root ผ่าน และใบยังไม่หมดอายุก็ตาม · เหตุผล: ถ้าไม่ตรวจชื่อ ผู้ร้ายที่มีใบรับรองถูกต้องของโดเมน *ตัวเอง* (ขอได้ง่าย) จะเอามาแสดงแทนโดเมนของคุณได้ · ใช้สื่อ `cert-chain` เลือก "ชื่อโฮสต์ไม่ตรง" ดูผลทีละข้อ
::

::reveal{question="ข้อ 4: ระบบปฏิบัติการตัดสินใจอย่างไรว่าจะเชื่อ CA ไหน (ตรงกับคำถามท้ายบท 4)"}
ผู้ผลิต OS/เบราว์เซอร์ (Microsoft, Apple, Mozilla, Google) ดูแลโปรแกรม root ของตัวเอง โดยกำหนดเกณฑ์การตรวจสอบ (การตรวจสอบระบบของ CA, การปฏิบัติตามข้อกำหนดของ CA/Browser Forum, Certificate Transparency ฯลฯ) แล้วรวมใบ root ของ CA ที่ผ่านเกณฑ์ไว้ใน trust store ที่มากับระบบ และถอดออกได้เมื่อ CA ทำผิด · องค์กรหรือผู้ใช้เพิ่ม root ของตัวเองได้ (เช่น CA ภายใน) ซึ่งหมายถึงให้สิทธิ์ CA นั้นออกใบสำหรับ *ทุกโดเมน* ได้ จึงเป็นสิทธิ์ที่ต้องระวัง
::

::reveal{question="ข้อ 5: ในสื่อ dh-lab ผู้ดักฟังเห็น p=23, g=5, A=8, B=19 หาความลับร่วมได้ไหม และทำไมของจริงทำไม่ได้"}
ได้ เพราะ p เล็ก ไล่ x = 1, 2, 3, … จนเจอ 5ˣ mod 23 = 8 (x = 6) แล้วคำนวณ 19⁶ mod 23 = 2 · ของจริง p ≥ 2048 บิต (หรือเส้นโค้ง ~255 บิต) วิธีที่ดีที่สุดที่รู้จักยังต้องใช้งานราว 2¹²⁷ ขั้นขึ้นไปแม้เป็นเส้นโค้ง 255 บิต หากลองด้วยความเร็ว 10¹² ครั้ง/วินาที ยังใช้เวลานานกว่าอายุจักรวาลหลายเท่า (ค่าประมาณ ตรวจด้วย node สำหรับ 2¹²⁸ ได้ราว 1.1×10¹⁹ ปี) · อัลกอริทึมที่ฉลาดกว่าไล่ตรงมีอยู่ แต่ขนาดกุญแจเลือกมาเผื่อไว้แล้ว
::

::reveal{question="ข้อ 6: ทำไม DH อย่างเดียวถึงกัน MITM ไม่ได้ และ TLS แก้อย่างไร"}
DH ให้ความลับร่วมแก่ *ใครก็ตามที่อีกฝั่งเป็น* ไม่ได้ยืนยันว่าอีกฝั่งคือใคร Mallory ทำ DH แยกกับสองฝ่ายและเป็นตัวกลางถอด-เข้ารหัสต่อได้ (ลองใน dh-lab) · TLS แก้โดยให้เซิร์ฟเวอร์เซ็น transcript ของ handshake (ซึ่งรวม key share) ด้วยกุญแจส่วนตัวที่ตรงกับใบรับรอง และไคลเอนต์ตรวจใบรับรองกับ trust store ผู้ร้ายไม่มีกุญแจส่วนตัวจึงเซ็นไม่ได้
::

::reveal{question="ข้อ 7: forward secrecy คืออะไร ปกป้องอะไรและไม่ปกป้องอะไร"}
ปกป้อง: ถ้ากุญแจส่วนตัวระยะยาวของเซิร์ฟเวอร์รั่ว *ภายหลัง* ทราฟฟิกที่ถูกบันทึกไว้ในอดีตยังถอดไม่ได้ เพราะกุญแจเซสชันมาจาก ECDHE ชั่วคราวที่ถูกทิ้งไปแล้ว · ไม่ปกป้อง: (1) ผู้ร้ายที่ได้กุญแจนั้น ปลอมเป็นเซิร์ฟเวอร์ได้นับจากนั้น (จึงต้องเพิกถอนใบ) (2) ถ้าเซิร์ฟเวอร์ถูกยึดขณะเซสชันยังเปิด กุญแจเซสชันในหน่วยความจำอ่านได้ (3) ถ้าเปิดใช้ session ticket ที่เซิร์ฟเวอร์ใช้กุญแจคงที่นานเกินไป ก็ลดคุณสมบัตินี้ได้
::

::reveal{question="ข้อ 8: ต้นฉบับบอกว่า TLS ให้ non-repudiation ถูกหรือไม่"}
ไม่ตรงนัก การเข้ารหัสข้อมูลแอปใช้ MAC แบบสมมาตร ทั้งสองฝั่งมีกุญแจและสร้าง tag ได้ จึงพิสูจน์ต่อบุคคลที่สามไม่ได้ว่าใครส่ง · มีเพียงส่วน CertificateVerify ที่เซ็นด้วยกุญแจส่วนตัวของเซิร์ฟเวอร์ ซึ่งยืนยันตัวตนในเซสชันนั้น แต่ก็ไม่ใช่ลายเซ็นบนข้อมูลแอปแบบ non-repudiation · ถ้าต้องการปฏิเสธไม่ได้ ต้องใช้ลายเซ็นดิจิทัลที่ระดับข้อความ/เอกสาร
::

::reveal{question="ข้อ 9: มือถือเปิดเว็บภายในบริษัทได้ แต่เปิดเว็บเดียวกันที่บ้านผ่าน VPN ไม่ได้ ขึ้นเตือนใบรับรอง ควรสงสัยอะไร"}
หลายเหตุผล ตรวจ: (1) ที่ออฟฟิศอาจมี TLS inspection หรือ DNS ภายในชี้ไปเซิร์ฟเวอร์ที่ใช้ใบรับรองภายใน ส่วนที่บ้านผ่านเส้นทางต่างกันจึงได้ใบอื่น (2) ชื่อที่เปิดต่างกัน (ชื่อสั้นภายใน vs ชื่อเต็ม) ไม่อยู่ใน SAN (3) ที่บ้านไม่มี CA ภายในใน trust store ของเครื่องนั้น · ใช้ `openssl s_client -connect` จากทั้งสองที่ แล้วเทียบ issuer และ SAN
::

::reveal{question="ข้อ 10: ข้อจำกัดของบทนี้ที่ควรรู้"}
(1) ตัวเลข RTT เป็นแบบจำลอง ไม่รวมเวลาประมวลผลและการเสียแพ็กเก็ต (2) ตัวอย่าง DH ขนาดเล็กเพื่อการสอน ไม่ใช่พารามิเตอร์ที่ใช้จริง (3) นโยบายอายุใบรับรองและรุ่น TLS ที่รองรับเปลี่ยนตามเวลา ควรตรวจแหล่งล่าสุด (4) บทไม่ได้ลงลึก key schedule, การต่อเซสชัน (PSK/tickets), mutual TLS (ไคลเอนต์แสดงใบรับรองด้วย) และ post-quantum ซึ่งมีรายละเอียดมากกว่านี้
::

## 12. แบบฝึกหัด (ลงมือทำจริง)

ทำบนเครื่องของคุณเอง ใช้เฉพาะคำสั่งอ่านอย่างเดียว กับเว็บไซต์สาธารณะ หรือระบบที่คุณมีสิทธิ์

1. **ดูใบรับรองในเบราว์เซอร์:** เปิดเว็บ https ที่คุณใช้ คลิกกุญแจ → ดูใบรับรอง จดผู้ออก ช่วงวันที่ และ SAN แล้วดูว่าสายมีกี่ใบ
2. **อ่านด้วยบรรทัดคำสั่ง:** `openssl s_client -connect <โดเมน>:443 -servername <โดเมน> </dev/null` แล้วหา TLS รุ่น, cipher และ `Verify return code` (Windows: ใช้ Git Bash หรือ WSL; ใน PowerShell เทียบเท่าคือเปิด `curl.exe -vI https://<โดเมน>` ดูบรรทัด `SSL connection using`)
3. **คำนวณ RTT:** `ping <โดเมน>` จดค่าเฉลี่ย แล้วคำนวณเวลาถึงไบต์แรกของ TLS 1.2 (4 × RTT) และ TLS 1.3 (3 × RTT) เทียบกับที่ `curl -w "%{time_connect} %{time_appconnect} %{time_starttransfer}\n" -o /dev/null -s https://<โดเมน>` วัดได้
4. **ตรวจวันหมดอายุ:** `openssl s_client -connect <โดเมน>:443 </dev/null | openssl x509 -noout -enddate` แล้วคำนวณว่าเหลือกี่วัน ถ้าต้องดูแลระบบ ตั้งการแจ้งเตือนล่วงหน้า 30 และ 7 วัน
5. **ทดลองสื่อ:** ใน `dh-lab` เปลี่ยน p จาก 23 ไปจนถึง 1299709 จดจำนวนครั้งที่ผู้ดักฟังต้องลอง แล้วติ๊ก MITM สองระดับ อธิบายด้วยคำของคุณว่า "ลายเซ็น" ช่วยอะไร · ใน `cert-chain` ไล่ทั้ง 7 สถานการณ์ จดว่าข้อไหนไม่ผ่านเป็นข้อแรกในแต่ละกรณี
6. **ดู root trust store ของเครื่อง:** Windows: `certmgr.msc` → Trusted Root Certification Authorities · macOS: Keychain Access · Linux: `ls /etc/ssl/certs | wc -l` นับจำนวน และดูว่ามี CA องค์กรที่คุณไม่รู้จักไหม

::reveal{question="แนวคำตอบ"}
(1) ใบปลายทาง → ใบกลาง → root (ปกติ 2–3 ใบ); ผู้ออกของเว็บใหญ่เช่น Let's Encrypt, DigiCert, Google Trust Services · (2) ปกติ TLSv1.3 + `TLS_AES_*_GCM` หรือ `TLS_CHACHA20_POLY1305`, `Verify return code: 0 (ok)` · (3) ค่า `time_appconnect − time_connect` ≈ เวลา TLS handshake (≈ 1 RTT สำหรับ 1.3, ≈ 2 RTT สำหรับ 1.2) ผลจริงมีเวลาประมวลผลบวกอยู่ · (4) ใบ Let's Encrypt มักอายุ 90 วัน ต่ออัตโนมัติ · (5) p=1299709 (~21 บิต) ยังเดาได้ภายในหลักล้านครั้ง; ลายเซ็นทำให้ Mallory ผ่านการตรวจไม่ได้ เพราะไม่มีกุญแจส่วนตัวของเซิร์ฟเวอร์ · cert-chain: ปกติผ่านทั้งหมด, หมดอายุ → ข้อ 2, ชื่อไม่ตรง → ข้อ 1, self-signed → ข้อ 5, ลืมใบกลาง → ข้อ 4, ถูกเพิกถอน → ข้อ 6, ลายเซ็นปลอม → ข้อ 3 · (6) จำนวนหลักร้อย (ราว 130–150 ใบ ค่าประมาณ ขึ้นกับระบบ) ถ้าพบ CA แปลกที่ไม่มีที่มา ให้ตรวจว่ามาจากนโยบายองค์กรหรือมัลแวร์
::

## 13. สรุป

- **TLS = ความลับ + ความถูกต้อง + ยืนยันตัวตนเซิร์ฟเวอร์** บน TCP (HTTPS = HTTP + TLS, พอร์ต 443) SSL เลิกใช้แล้ว ใช้ TLS 1.2 (ตั้งค่าดี) และ 1.3 (แนะนำ)
- **ผสมสองแบบ:** ECDHE ตกลงกุญแจ (ช้าแต่แก้ปัญหาส่งกุญแจ ให้ forward secrecy), AEAD (AES-GCM/ChaCha20-Poly1305) เข้ารหัสข้อมูลจริง (เร็ว และ tag ตรวจการแก้ไข)
- **DH เปล่าๆ ไม่กัน MITM:** ต้องมีใบรับรองและลายเซ็น (CertificateVerify) ผูก key share กับตัวตน
- **ใบรับรองผ่านเมื่อ:** ชื่อตรง SAN, อยู่ในช่วงวันที่, ลายเซ็นถูก, สายครบ, จบที่ root ที่เชื่อถือ, ไม่ถูกเพิกถอน · ใบรับรองไม่เป็นความลับ ความลับคือกุญแจส่วนตัว
- **TLS 1.3 = 1 RTT** (1.2 = 2 RTT) ถึงไบต์แรก 3 vs 4 RTT รวม TCP และคำขอ · 0-RTT เร็วกว่าแต่เสี่ยง replay
- **ข้อจำกัด:** ไม่ปกป้องข้อมูลที่พัก, เครื่องที่ถูกยึด, เว็บที่ผู้ร้ายเป็นเจ้าของ, ข้อมูลเมตา · กุญแจในแถบที่อยู่ไม่ได้แปลว่าเว็บปลอดภัย
- อาการที่พบบ่อยแยกด้วย *ข้อที่ไม่ผ่านก่อน*: วันที่/ชื่อ/ผู้ออก/สายไม่ครบ/เพิกถอน
- ตัวเลขที่ไม่ได้มาจากต้นฉบับ (RTT, เวลาเดา, จำนวน root) เป็นค่าประมาณหรือแบบจำลอง
- บทถัดไป: **การทำ hardening ระบบปฏิบัติการ** (ลดพื้นผิวโจมตีที่ปลายทาง ซึ่ง TLS ไม่ครอบคลุม)
