## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **ทำไมดิสก์เปล่าใช้งานไม่ได้ทันที** และต้องมีตารางพาร์ทิชันกับระบบไฟล์ก่อน
2. อธิบายโครงสร้างภายในของ **MBR และ GPT** และ **คำนวณขีดจำกัดขนาดดิสก์** จากจำนวนบิตของที่อยู่ได้เอง
3. เล่า **ลำดับบูตทีละขั้น** ตั้งแต่กดปุ่มเปิดเครื่อง → UEFI → พาร์ทิชัน ESP → Boot Manager → WinPE → ตัวติดตั้ง
4. อธิบายกลไกของ **NTFS** (MFT, journaling) กับ **FAT32** (ตาราง FAT, ขีดจำกัด 4 GB) และคำนวณพื้นที่สูญเปล่าจากขนาดคลัสเตอร์
5. อธิบายว่าตัวติดตั้ง **แตกอิมเมจ (WIM)** ลงดิสก์ สร้างไฟล์บูต และเข้าสู่ **OOBE** อย่างไร และ SID ถูกสร้างตอนไหน
6. วางลำดับงานหลังติดตั้งและอธิบายว่า **ทำไมไดรเวอร์จึงเป็นความเสี่ยง** (รันใน Kernel Mode)
7. อธิบาย **Secure Boot, TPM และ BitLocker** ว่าต่อกันเป็นห่วงโซ่ความเชื่อถือ (chain of trust) อย่างไร พร้อมข้อจำกัด
8. วินิจฉัยปัญหาติดตั้งที่พบบ่อยจาก **สาเหตุเชิงกลไก** ไม่ใช่การท่องวิธีแก้

## สรุปสั้น (TL;DR)

การติดตั้ง Windows คือการเปลี่ยนดิสก์เปล่าให้เป็นระบบที่เปิดแล้วบูตเองได้ ผ่าน 4 ด่านต่อเนื่อง

1. **เฟิร์มแวร์ (UEFI)** หาตัวบูตจากพาร์ทิชันพิเศษ (ESP) แล้วตรวจลายเซ็นก่อนรัน (Secure Boot)
2. **WinPE** คือ Windows ย่อส่วนที่โหลดขึ้น RAM เพื่อทำงานกับดิสก์ (แบ่งพาร์ทิชัน ฟอร์แมต แตกอิมเมจ)
3. **อิมเมจ install.wim** ถูกแตกลงพาร์ทิชัน Windows แล้วเขียนไฟล์บูตลง ESP
4. **รีบูต → OOBE** สร้างบัญชี ตั้งค่า แล้วจึงติดไดรเวอร์ อัปเดต และเปิดการป้องกัน

เหตุผลที่ต้องรู้กลไกเหล่านี้: **ปัญหาติดตั้งเกือบทั้งหมด** (มองไม่เห็นดิสก์ ติดตั้งไม่ได้ วนกลับมาตัวติดตั้ง เห็นดิสก์ 2 TB จาก 4 TB) อธิบายได้จาก 4 ด่านนี้

## เปรียบเทียบกับชีวิตจริง

นึกถึง **การสร้างบ้านบนที่ดินเปล่า**

| การสร้างบ้าน | การติดตั้ง Windows | ข้อสังเกต |
|---|---|---|
| ที่ดินเปล่า | ดิสก์ใหม่ (พื้นที่ดิบเป็นเซกเตอร์ต่อกัน) | ยังไม่รู้ว่าตรงไหนเป็นอะไร |
| โฉนดและแนวเขตที่ดิน | ตารางพาร์ทิชัน (MBR/GPT) | บอกว่าที่ดินแบ่งเป็นกี่แปลง แปลงไหนเริ่มและจบที่ใด |
| ระบบทะเบียนบ้านเลขที่และผังห้อง | ระบบไฟล์ (NTFS) | บอกว่าของแต่ละชิ้นอยู่ตรงไหนในแปลงนั้น |
| ทีมงานก่อสร้างชั่วคราวที่ขนวัสดุมาเอง | WinPE (ระบบเล็กๆ บน RAM) | มีไว้ทำงานก่อสร้าง ไม่ได้อยู่อาศัย |
| บ้านสำเร็จรูปที่ยกมาวางทั้งหลัง | อิมเมจ install.wim | ไม่ได้ก่ออิฐทีละก้อน แต่ "กางแม่แบบ" ลงพื้นที่ |
| ตรวจรับบ้านแล้วรับกุญแจ | OOBE | ตั้งเจ้าของบ้านและกฎการเข้าออกครั้งแรก |
| ยามตรวจบัตรทุกคนที่เข้าโครงการ | Secure Boot | ไม่มีลายเซ็นที่เชื่อถือได้ ไม่ให้เข้าก่อสร้าง |

## ภาพรวม

บทนี้เดินตาม "เส้นทางของข้อมูล" จากแรกสุดไปสุดท้าย: **ก่อนติดตั้ง → บูตเข้าตัวติดตั้ง → โครงสร้างดิสก์ → ระบบไฟล์ → แตกอิมเมจและ OOBE → หลังติดตั้ง → ความปลอดภัย** ทุกหัวข้อเริ่มจากคำถามว่า "ทำไมต้องมี" ก่อนถึงรายละเอียด

## 1. ก่อนติดตั้ง: เลือกวิธีและตรวจเงื่อนไข

### 1.1 สามกลยุทธ์ และทำไมแต่ละแบบจึงมีอยู่

สิ่งที่ต้องตัดสินใจมีเรื่องเดียว คือ **จะเก็บอะไรจากระบบเดิมไว้บ้าง** ยิ่งเก็บมาก ยิ่งสะดวก แต่ยิ่งพกปัญหาเดิมมาด้วย

- **Clean installation:** ล้างดิสก์แล้วเริ่มใหม่ ไม่เหลือมัลแวร์ ไฟล์ระบบเสีย หรือการตั้งค่าเก่า แต่ต้องลงโปรแกรมและย้ายข้อมูลเอง
- **In-place upgrade:** อัปเกรดทับ เก็บโปรไฟล์ ไฟล์ และโปรแกรมไว้ ลดงาน แต่พกค่า Registry และไดรเวอร์เก่าติดมาด้วย
- **Imaging / Automated deployment:** ทำเครื่องต้นแบบหนึ่งเครื่อง (หรือใช้ไฟล์ตอบอัตโนมัติ `unattend.xml`) แล้วปล่อยให้เครื่องอื่นผ่านเครือข่าย (PXE) เครื่องมือเช่น MDT, WDS เหมาะกับหลายสิบเครื่องที่เหมือนกัน เพราะ **คนทำซ้ำย่อมพลาด แต่ไฟล์ตอบทำซ้ำได้เหมือนเดิมทุกครั้ง**

> **ข้อจำกัด:** ไม่มีวิธีที่ดีที่สุดเสมอ In-place upgrade สะดวกกับเครื่องเดี่ยวที่ระบบยังดี ส่วน clean install คือคำตอบเมื่อสงสัยว่าระบบเสียหรือติดมัลแวร์ เพราะ "ล้างแล้วเริ่มใหม่" เป็นวิธีเดียวที่ยืนยันได้ว่าไม่เหลืออะไรตกค้าง

### 1.2 เงื่อนไขขั้นต่ำของ Windows 11 และทำไมต้องมี

| รายการ | เงื่อนไข (ตามที่ Microsoft ประกาศ) | ทำไมถึงกำหนด |
|---|---|---|
| โปรเซสเซอร์ | 64-bit, 1 GHz ขึ้นไป, 2 คอร์ขึ้นไป | ระบบปฏิบัติการนี้เป็น 64-bit ล้วน |
| หน่วยความจำ (RAM) | 4 GB | น้อยกว่านี้ใช้งานไม่ไหว ต้องสลับไปดิสก์บ่อย |
| พื้นที่เก็บข้อมูล | 64 GB | ระบบ + อัปเดตสะสม + ไฟล์ชั่วคราวระหว่างอัปเดต |
| เฟิร์มแวร์ | UEFI ที่รองรับ Secure Boot | ใช้ตรวจตัวบูตก่อนรัน (หัวข้อ 7) |
| ชิปความปลอดภัย | TPM 2.0 | เก็บกุญแจและค่าวัดสถานะการบูต (BitLocker, หัวข้อ 7) |

สังเกตว่าสองข้อท้าย **ไม่ใช่เรื่องความเร็ว แต่เป็นเรื่องความปลอดภัย** นี่คือเหตุผลที่เครื่องเร็วแต่เก่าบางเครื่องติดตั้งไม่ได้

## 2. บูตเข้าตัวติดตั้ง: ตั้งแต่กดปุ่มเปิดเครื่อง

คำถามแรกที่ต้องตอบคือ **ดิสก์ยังว่างเปล่า แล้วคอมพิวเตอร์รู้ได้อย่างไรว่าจะรันอะไร?** คำตอบคือโค้ดเล็กๆ ที่ฝังอยู่บนเมนบอร์ดเรียกว่า **เฟิร์มแวร์** ซึ่งมี 2 ยุค

| | BIOS (Legacy) | UEFI |
|---|---|---|
| หาตัวบูตจาก | เซกเตอร์แรกของดิสก์ (MBR) | ไฟล์ `.efi` ในพาร์ทิชันพิเศษ **ESP** |
| ใช้คู่กับ | ตารางพาร์ทิชัน MBR | GPT (ใช้กับ MBR ได้ในโหมดเข้ากันได้) |
| รันตัวบูต | รันโค้ด 446 ไบต์ตรงๆ ไม่ตรวจอะไร | ตรวจลายเซ็นได้ (Secure Boot) |

### 2.1 ลำดับบูตของ UEFI ทีละขั้น

ESP (EFI System Partition) คือพาร์ทิชันเล็กๆ ฟอร์แมตเป็น **FAT32** เสมอ เพราะมาตรฐาน UEFI กำหนดให้เฟิร์มแวร์ต้องอ่านระบบไฟล์ได้เพียงแบบนี้ (เฟิร์มแวร์ไม่มีความสามารถอ่าน NTFS ในตัว) จึงเป็นเหตุผลที่ไฟล์บูตอยู่บน FAT32

> **ทำไม WinPE ต้องรันบน RAM:** ถ้าตัวติดตั้งรันจากดิสก์เป้าหมาย การลบพาร์ทิชันหรือฟอร์แมตจะลบตัวมันเองไปด้วย การรันจาก RAM แยกตัวติดตั้งออกจากสิ่งที่มันกำลังแก้ไข

### 2.2 โหมด BIOS/UEFI ต้องตรงกับชนิดตารางพาร์ทิชัน

ถ้าเครื่องบูต USB ในโหมด UEFI ตัวติดตั้งจะยอมลงเฉพาะดิสก์ **GPT** ถ้าบูตในโหมด Legacy จะยอมลงเฉพาะ **MBR** นี่คือต้นเหตุของข้อความ "Windows cannot be installed to this disk" ที่พบบ่อย (ดูตารางวินิจฉัยหัวข้อ 8) เพราะตัวติดตั้งต้องเขียนไฟล์บูตให้เฟิร์มแวร์โหมดนั้นหาเจอ ถ้าไม่ตรงกัน เครื่องจะบูตไม่ขึ้น

## 3. โครงสร้างดิสก์: ตารางพาร์ทิชัน

### 3.1 ทำไมต้องแบ่งพาร์ทิชัน

ดิสก์ในสายตาของเฟิร์มแวร์คือ **ลำดับเซกเตอร์ยาวๆ** ที่ตั้งชื่อเป็นเลข (LBA = Logical Block Address) เซกเตอร์ละ 512 ไบต์ (หรือ 4,096 ไบต์ในดิสก์ยุคใหม่) ไม่มีแนวคิดว่า "ตรงไหนเป็นของใคร" ตารางพาร์ทิชันจึงเป็นแผนที่ที่บอกว่า **"เซกเตอร์ A ถึง B เป็นพื้นที่หนึ่งชนิดนี้"** ประโยชน์คือแยกระบบออกจากข้อมูล ใส่หลายระบบปฏิบัติการได้ และแยกพื้นที่บูตออกมาเฉพาะ

### 3.2 MBR: โครงสร้างปี 1983 ที่ยังเหลืออยู่

MBR ใช้ **เซกเตอร์แรก (LBA 0) ขนาด 512 ไบต์** เพียงเซกเตอร์เดียว แบ่งเป็น

| ส่วน | ขนาด | หน้าที่ |
|---|---|---|
| โค้ดบูต | 446 ไบต์ | โปรแกรมเล็กๆ ที่ BIOS รันเป็นอย่างแรก |
| ตารางพาร์ทิชัน | 4 รายการ × 16 ไบต์ = 64 ไบต์ | แต่ละรายการเก็บ **จุดเริ่ม** กับ **จำนวนเซกเตอร์** |
| ลายเซ็น | 2 ไบต์ (ค่า `0x55AA`) | ใช้ยืนยันว่าเป็น MBR ที่ใช้ได้ |

รวม 446 + 64 + 2 = 512 ไบต์พอดี **ขีดจำกัดทั้งหมดของ MBR มาจากตรงนี้:**

- มี 4 รายการ ได้ **4 พาร์ทิชันหลัก** (อยากได้มากกว่านี้ต้องใช้กลเม็ดพาร์ทิชันขยาย)
- จุดเริ่มและจำนวนเซกเตอร์เก็บเป็นเลข **32 บิต** ต่อรายการ จึงมีที่อยู่ได้ 2³² เซกเตอร์

**คำนวณขีดจำกัด:**

> 2³² เซกเตอร์ × 512 ไบต์ = 2,199,023,255,552 ไบต์ = **2 TiB** (≈ 2.2 TB)

(ถ้าดิสก์ใช้เซกเตอร์ 4,096 ไบต์ ขีดจำกัดจะเป็น 2³² × 4,096 = 16 TiB)

### 3.3 GPT: ออกแบบใหม่ให้พ้นขีดจำกัดเดิม

GPT (GUID Partition Table) แก้ปัญหาของ MBR ตรงจุด โดยใช้ที่อยู่ **64 บิต** และพื้นที่เก็บตารางที่ใหญ่ขึ้นมาก

| ตำแหน่ง | เนื้อหา |
|---|---|
| LBA 0 | **Protective MBR:** MBR ปลอมที่บอกว่า "ดิสก์นี้เต็มแล้ว" เพื่อให้เครื่องมือรุ่นเก่าที่ไม่รู้จัก GPT ไม่เผลอเขียนทับ |
| LBA 1 | **หัวตาราง (Primary GPT Header):** ตำแหน่งตาราง จำนวนรายการ และค่า **CRC32** ของตัวเอง |
| LBA 2–33 | **รายการพาร์ทิชัน:** 128 รายการ × 128 ไบต์ = 16,384 ไบต์ = 32 เซกเตอร์ |
| พื้นที่ใช้งาน | พาร์ทิชันจริงทั้งหมด |
| ท้ายดิสก์ | **ตารางสำรอง (Backup)** และหัวตารางสำรอง |

จุดเด่นที่ MBR ไม่มี:

- **ตรวจความเสียหายได้:** ใช้ CRC32 ตรวจหัวตารางและรายการ ถ้าตัวหลักเสียก็กู้จากตัวสำรองท้ายดิสก์
- **ที่อยู่ 64 บิต:** 2⁶⁴ × 512 ไบต์ = 2⁷³ ไบต์ = **8 ZiB** (ทางทฤษฎี) ในทางปฏิบัติขีดจำกัดจริงมาจากระบบไฟล์และ OS ไม่ใช่ GPT
- **ชนิดพาร์ทิชันระบุด้วย GUID** (เลข 128 บิตที่ไม่ซ้ำกัน) ทำให้ ESP ถูกระบุได้ชัดเจน

> **ข้อควรระวัง:** CRC32 ตรวจได้ว่า "ข้อมูลเสียหรือไม่" ไม่ได้ตรวจว่า "ถูกแก้โดยผู้ไม่ประสงค์ดี" เพราะใครก็คำนวณ CRC ใหม่ได้ ความปลอดภัยด้านนั้นเป็นหน้าที่ของ Secure Boot

## 4. ระบบไฟล์: จัดระเบียบพื้นที่ในพาร์ทิชัน

พาร์ทิชันยังเป็นแค่เซกเตอร์ดิบ **ระบบไฟล์ (file system)** คือโครงสร้างข้อมูลที่ทำให้เก็บ "ไฟล์ที่มีชื่อ" ได้ ตอบสามคำถาม: ไฟล์ชื่อนี้อยู่ที่บล็อกไหน, บล็อกไหนว่าง, และสิทธิ์เป็นอย่างไร

### 4.1 คลัสเตอร์ (Cluster) และพื้นที่ที่เสียไป

ระบบไฟล์ไม่จัดสรรพื้นที่ทีละเซกเตอร์ แต่จัดทีละ **คลัสเตอร์** (กลุ่มเซกเตอร์ ค่าตั้งต้นของ NTFS คือ 4 KB) เพื่อให้ตารางที่ต้องจดจำเล็กลง ผลข้างเคียงคือ **ไฟล์ใช้พื้นที่เป็นจำนวนเต็มของคลัสเตอร์** ส่วนที่เหลือท้ายไฟล์เสียเปล่า เรียกว่า slack space

**สูตร:** คลัสเตอร์ที่ใช้ = ⌈ขนาดไฟล์ ÷ ขนาดคลัสเตอร์⌉ , พื้นที่เสีย = คลัสเตอร์ที่ใช้ × ขนาดคลัสเตอร์ − ขนาดไฟล์

| ไฟล์ | คลัสเตอร์ 4 KB ที่ใช้ | พื้นที่เสีย |
|---|---|---|
| 5,000 ไบต์ | 2 (8,192 ไบต์) | 3,192 ไบต์ |
| 10 KB (10,240 ไบต์) | 3 (12,288 ไบต์) | 2,048 ไบต์ |

โดยเฉลี่ยจะเสียราว **ครึ่งคลัสเตอร์ต่อไฟล์** ไฟล์เล็กมากๆ จำนวนล้านไฟล์จึงเปลืองพื้นที่ได้ถึงระดับกิกะไบต์ ส่วนคลัสเตอร์ใหญ่ขึ้นทำให้ตารางเล็กและอ่านไฟล์ใหญ่เร็ว แต่เสียพื้นที่ต่อไฟล์เล็กมากขึ้น (ถือเป็นการแลกกัน)

### 4.2 FAT32: ระบบไฟล์ง่ายที่สุดที่ยังใช้อยู่

FAT (File Allocation Table) เก็บตารางหนึ่งตาราง **ให้แต่ละคลัสเตอร์ชี้ไปยังคลัสเตอร์ถัดไป** ของไฟล์เดียวกัน เป็นลิงก์ลิสต์ที่เก็บในตาราง ถ้าไฟล์เริ่มที่คลัสเตอร์ 5 ตารางจะบอกว่า 5 → 9 → 12 → จบ

ข้อจำกัดทั้งหมดมาจากขนาดฟิลด์:

- ขนาดไฟล์เก็บเป็นเลข **32 บิต** จึงใหญ่สุด 2³² − 1 = 4,294,967,295 ไบต์ = **4 GiB − 1 ไบต์**
- ไม่มีที่เก็บสิทธิ์ (ACL) ไม่มี journal จึงไม่มีการป้องกันไฟดับกลางคัน
- เครื่องมือฟอร์แมตในตัว Windows ปฏิเสธ FAT32 เกิน 32 GB (เป็นนโยบายของเครื่องมือ ไม่ใช่ขีดจำกัดของ FAT32 เอง)

ที่ยังใช้ FAT32 เพราะ **ทุกระบบอ่านได้** รวมถึงเฟิร์มแวร์ UEFI (ESP) กล้อง และทีวี ส่วน **exFAT** ขยายขนาดไฟล์และพาร์ทิชันให้ใหญ่มาก แต่ยังคงความเรียบง่ายไว้

### 4.3 NTFS: ระบบไฟล์ที่มีฐานข้อมูลอยู่ข้างใน

หัวใจของ NTFS คือ **MFT (Master File Table)** ตารางที่ทุกไฟล์และโฟลเดอร์มี "ระเบียน" (record) ละ 1 KB (ค่าตั้งต้น) เก็บชื่อ ขนาด เวลา สิทธิ์ และที่ตั้งของข้อมูล

- **ไฟล์เล็กมาก (ราวหลายร้อยไบต์ ค่าประมาณ) เก็บข้อมูลไว้ในระเบียน MFT เลย** ไม่ใช้คลัสเตอร์ จึงไม่มี slack
- ไฟล์ใหญ่เก็บเป็น **extent** คือ "เริ่มคลัสเตอร์ X ยาว N คลัสเตอร์" จึงบันทึกไฟล์ที่ติดกันเป็นก้อนได้ด้วยรายการเดียว
- ตัว MFT เองเป็นไฟล์ (`$MFT`) และระบบไฟล์เก็บ metadata อื่นเป็นไฟล์พิเศษด้วย เช่น `$Bitmap` (คลัสเตอร์ไหนว่าง) และ `$LogFile` (journal)

**Journaling:** การสร้างไฟล์ต้องแก้หลายที่ (MFT, bitmap, ไดเรกทอรี) ถ้าไฟดับระหว่างทาง โครงสร้างจะขัดแย้งกัน NTFS จึง **จดแผนลง `$LogFile` ก่อน (write-ahead log)** แล้วค่อยลงมือแก้จริง หลังไฟดับจะอ่าน log เพื่อทำต่อให้จบหรือย้อนกลับ

> **ข้อจำกัดที่ต้องเข้าใจให้ถูก:** NTFS journal ปกป้อง **ความสอดคล้องของโครงสร้างระบบไฟล์ (metadata)** เป็นหลัก ไม่ได้รับประกันว่าเนื้อหาที่แอปกำลังเขียนจะอยู่ครบ ไฟล์ที่กำลังบันทึกตอนไฟดับยังอาจได้ข้อมูลไม่สมบูรณ์

## 5. จากอิมเมจถึงระบบที่ใช้งานได้

### 5.1 WIM คืออะไร และทำไมไม่ใช่ไฟล์ ISO ธรรมดา

Windows ไม่ได้ถูกติดตั้งด้วยการรันโปรแกรมที่ก๊อบไฟล์ทีละไฟล์ แต่ **ไฟล์ `install.wim` (หรือ `install.esd`) คือคลังไฟล์ของ Windows ที่เตรียมไว้แล้วทั้งชุด** แล้วตัวติดตั้งแค่ "กางออก" ลงพาร์ทิชัน

- WIM เป็นรูปแบบอิมเมจ **ระดับไฟล์** (ไม่ใช่ระดับเซกเตอร์) จึงกางลงพาร์ทิชันขนาดใดก็ได้ ต่างจากอิมเมจดิสก์แบบก๊อปทีละเซกเตอร์
- ไฟล์ที่เนื้อหาเหมือนกันถูกเก็บครั้งเดียว (single-instance) และบีบอัด ทำให้ไฟล์ติดตั้งเล็กลง `.esd` บีบอัดหนักกว่า
- หนึ่งไฟล์เก็บได้หลาย **index** คือหลายรุ่น (Home, Pro ฯลฯ) ตัวติดตั้งแสดงเมนูเลือกรุ่นจากตรงนี้

### 5.3 OOBE และเรื่องของ "ตัวตน" (SID)

ระหว่าง OOBE คุณเลือกชนิดบัญชี ซึ่งส่งผลต่อโครงสร้างความปลอดภัยของเครื่องทั้งหมด

| ชนิดบัญชี | เก็บที่ไหน | จุดเด่น / ข้อสังเกต |
|---|---|---|
| Local account | ในเครื่องเท่านั้น | ไม่ผูกคลาวด์ กู้รหัสผ่านต้องจัดการเอง |
| Microsoft account | คลาวด์ + สำเนาในเครื่อง | ซิงค์การตั้งค่า กู้บัญชีได้ และ BitLocker อาจสำรอง recovery key ไว้บัญชีนี้ |
| Work/School (Entra ID) | ไดเรกทอรีองค์กรบนคลาวด์ | ผู้ดูแลระบบองค์กรคุมนโยบายและกุญแจได้ |

ทุกบัญชีมี **SID (Security Identifier)** ซึ่งระบบใช้ระบุตัวตนจริงๆ ในการตรวจสิทธิ์ (ไม่ใช่ชื่อ) หน้าตาเช่น `S-1-5-21-<ตัวเลขประจำเครื่อง>-1001` ส่วนท้ายสุดเรียกว่า RID: ผู้ใช้ที่สร้างเองเริ่มที่ 1000 ขึ้นไป และ 500 คือ Administrator ในตัว แนวคิดนี้เชื่อมกับบทสิทธิ์ไฟล์ที่ ACL ของ NTFS เทียบ SID ของผู้ใช้กับรายการสิทธิ์

> **เกร็ดสำหรับงานอิมเมจ:** ถ้าก๊อปเครื่องที่ติดตั้งแล้วไปลงเครื่องอื่นตรงๆ ทุกเครื่องจะมี SID เดียวกัน เครื่องมือ **Sysprep (generalize)** จึงมีไว้ล้างข้อมูลเฉพาะเครื่องก่อนเก็บเป็นอิมเมจ แล้วแต่ละเครื่องจะสร้างใหม่ตอน specialize

## 6. หลังติดตั้ง: ไดรเวอร์และลำดับงาน

### 6.1 ทำไมไดรเวอร์จึงสำคัญและอันตราย

ตอนติดตั้งเสร็จ Windows ใช้ไดรเวอร์ทั่วไป (generic) ที่ติดมากับอิมเมจ ทำให้จอขึ้นภาพและดิสก์ใช้ได้ แต่ฟีเจอร์เฉพาะของชิป (การ์ดจอ เครือข่าย ชิปเซ็ต) ต้องใช้ไดรเวอร์ของผู้ผลิต

สิ่งที่ต้องเข้าใจ: **ไดรเวอร์รันใน Kernel Mode (ระดับสิทธิ์สูงสุดของ CPU)** ไม่ได้รันแบบแอปทั่วไป ไดรเวอร์ที่บั๊กทำให้เครื่องค้างหรือจอฟ้า (BSOD) ได้ทั้งเครื่อง และไดรเวอร์ที่ถูกเจาะ เท่ากับผู้โจมตีได้สิทธิ์ระดับสูงสุดทันที ด้วยเหตุนี้ Windows บังคับให้ไดรเวอร์ 64-bit ต้องมีลายเซ็นดิจิทัล

> **ข้อจำกัด:** ลายเซ็นพิสูจน์ว่า "ใครเป็นผู้ออกไดรเวอร์" ไม่ได้รับประกันว่าไดรเวอร์ไม่มีช่องโหว่ ผู้โจมตีจึงมีเทคนิค **BYOVD (Bring Your Own Vulnerable Driver)** คือนำไดรเวอร์ที่มีลายเซ็นถูกต้องแต่มีช่องโหว่ติดตั้งเข้าไปเอง เพื่อยืมสิทธิ์ระดับเคอร์เนลไปใช้โจมตี

เหตุผลของลำดับ (คิดแบบ "ปิดความเสี่ยงที่ใหญ่ที่สุดก่อน"):

1. **ให้เครือข่ายใช้ได้ก่อน** (ไดรเวอร์ LAN/Wi-Fi) เพราะทุกขั้นถัดไปต้องดึงของจากอินเทอร์เน็ต
2. **Windows Update** ปิดช่องโหว่ที่รู้กันแล้ว เครื่องที่ยังไม่อัปเดตและออนไลน์คือเป้าหมายที่ง่ายที่สุด
3. **ไดรเวอร์เฉพาะ** (การ์ดจอ ชิปเซ็ต) หลังอัปเดต เพราะ Windows Update มักติดไดรเวอร์ที่ผ่านการทดสอบมาให้แล้ว
4. **ซอฟต์แวร์ป้องกัน นโยบาย บัญชี** เปิดไฟร์วอลล์ ใช้บัญชีผู้ใช้ปกติ (ไม่ใช่ Administrator) ในงานประจำ
5. **เปิด BitLocker แล้วสำรอง recovery key** ก่อนนำเครื่องไปใช้จริง

## 7. มุมมองด้าน Security: ห่วงโซ่ความเชื่อถือ

ทำไมต้องมี? เพราะ **โค้ดที่รันก่อน Windows (ตัวบูต) เป็นจุดที่ซอฟต์แวร์ป้องกันยังไม่ตื่น** มัลแวร์ที่ซ่อนตรงนั้น (bootkit) จะเริ่มทำงานก่อนแอนติไวรัสและมองไม่เห็นจากระบบ จึงต้องมีการตรวจสอบตั้งแต่ก่อนบูต

### 7.1 Secure Boot: ตรวจลายเซ็นทุกชั้น

เฟิร์มแวร์เก็บฐานข้อมูลกุญแจ 4 กลุ่ม: **PK** (กุญแจเจ้าของแพลตฟอร์ม) → **KEK** (กุญแจที่แก้ฐานข้อมูลได้) → **db** (ลายเซ็น/ใบรับรองที่อนุญาต) และ **dbx** (รายการที่เพิกถอนแล้ว) เฟิร์มแวร์จะรันเฉพาะไฟล์บูตที่ลายเซ็นอยู่ใน db และไม่อยู่ใน dbx จากนั้นตัวบูตก็ตรวจชั้นถัดไป (เคอร์เนล ไดรเวอร์เริ่มต้น) ต่อเป็นลูกโซ่

> **ข้อจำกัด:** Secure Boot ไม่ใช่เกราะป้องกันทุกอย่าง ถ้าตัวบูตที่ลงลายเซ็นถูกต้องมีช่องโหว่ ผู้โจมตีก็ใช้มันได้ (เคยมีกรณี bootkit ชื่อ BlackLotus ที่เจาะผ่านช่องโหว่ของตัวบูตที่มีลายเซ็นจริง) การเพิกถอนผ่าน dbx จึงต้องอัปเดตต่อเนื่อง

### 7.2 TPM และ BitLocker: กุญแจที่ผูกกับสถานะเครื่อง

**ปัญหา:** ถ้าถอดดิสก์ไปต่อเครื่องอื่นหรือบูตระบบอื่น ก็อ่านไฟล์ได้หมด ต่อให้ Windows ตั้งรหัสผ่านไว้ เพราะรหัสผ่านล็อกอินไม่ได้เข้ารหัสข้อมูลบนดิสก์ **BitLocker** แก้ด้วยการเข้ารหัสทั้งวอลลุม (ค่าตั้งต้นของ Windows รุ่นใหม่คือ XTS-AES 128 บิต)

กลไกกุญแจเป็นชั้นๆ

- **FVEK** (Full Volume Encryption Key) เข้ารหัส/ถอดรหัสข้อมูลบนดิสก์จริงๆ
- **VMK** (Volume Master Key) ห่อ (เข้ารหัส) FVEK ไว้
- VMK ถูกห่ออีกชั้นด้วย **protector** เช่น TPM, PIN, หรือ **recovery key 48 หลัก** (ตัวสำรองเมื่อ TPM ไม่ยอมปล่อยกุญแจ)

**TPM (Trusted Platform Module)** คือชิปที่เก็บกุญแจและมี **PCR** (Platform Configuration Register) เก็บ "ค่าวัดสถานะการบูต" ตัวบูตแต่ละชั้นคำนวณแฮชของชั้นถัดไปแล้วนำไป *extend* เข้า PCR (ผสมค่าเดิมกับค่าใหม่ ย้อนกลับไม่ได้) TPM จะปล่อย VMK ก็ต่อเมื่อ **ค่า PCR ตรงกับตอนที่ปิดผนึกกุญแจไว้** เท่านั้น

## 9. แบบฝึกหัดลงมือทำ (คำสั่งอ่านอย่างเดียว บนเครื่องของคุณ)

เปิด PowerShell แบบ Administrator (คำสั่งเหล่านี้ **ไม่เปลี่ยนแปลงอะไรในเครื่อง**)

1. `Get-Disk | Format-Table Number, FriendlyName, PartitionStyle, Size` ดิสก์ของคุณเป็น GPT หรือ MBR?
2. `Get-Partition -DiskNumber 0 | Format-Table PartitionNumber, Type, Size` มีพาร์ทิชัน ESP / Reserved (MSR) / Basic / Recovery ตามหัวข้อ 3.4 ครบไหม ขนาดต่างจากที่เรียนอย่างไร
3. `Confirm-SecureBootUEFI` และ `Get-Tpm` เครื่องคุณพร้อมสำหรับ Windows 11 หรือไม่
4. `fsutil fsinfo ntfsinfo C:` อ่านค่า Bytes Per Cluster แล้วคำนวณพื้นที่เสียของไฟล์ขนาด 7,000 ไบต์
5. `msinfo32` ดูช่อง "BIOS Mode" (UEFI หรือ Legacy) และ "Secure Boot State"

::reveal{question="แนวคำตอบแบบฝึกหัดข้อ 2 และ 4"}
**ข้อ 2:** เครื่อง UEFI ที่ติดตั้งมาตรฐานจะเห็นชนิด `System` (ESP ประมาณ 100–300 MB), `Reserved` (MSR 16 MB), `Basic` (ไดรฟ์ C:) และ `Recovery` ขนาดอาจต่างจากตัวเลขในบทเพราะต่างรุ่น และผู้ผลิตเครื่องบางรายเพิ่มพาร์ทิชันของตัวเอง
**ข้อ 4:** ถ้าคลัสเตอร์ 4,096 ไบต์ ไฟล์ 7,000 ไบต์ใช้ ⌈7000 ÷ 4096⌉ = 2 คลัสเตอร์ = 8,192 ไบต์ เสียพื้นที่ 8,192 − 7,000 = 1,192 ไบต์
::

## 10. โจทย์คำนวณ

::reveal{question="โจทย์ 1: ดิสก์ MBR ที่ใช้เซกเตอร์ 4,096 ไบต์ ใหญ่สุดกี่ TiB และเมื่อเทียบกับเซกเตอร์ 512 ไบต์ ต่างกันกี่เท่า"}
2³² × 4,096 = 2³² × 2¹² = 2⁴⁴ ไบต์ = 16 TiB ส่วนเซกเตอร์ 512 ไบต์ได้ 2 TiB จึงต่างกัน 4,096 ÷ 512 = 8 เท่า สรุปคือขีดจำกัดแปรตามขนาดเซกเตอร์โดยตรง
::

::reveal{question="โจทย์ 2: รายการพาร์ทิชัน GPT มาตรฐานมี 128 รายการ รายการละ 128 ไบต์ ต้องใช้กี่เซกเตอร์ (เซกเตอร์ 512 ไบต์) และรายการเหล่านี้อยู่ LBA ใดถึงใด"}
128 × 128 = 16,384 ไบต์ ÷ 512 = 32 เซกเตอร์ เนื่องจาก LBA 0 คือ Protective MBR และ LBA 1 คือหัวตาราง รายการจึงเริ่มที่ LBA 2 และจบที่ LBA 33
::

::reveal{question="โจทย์ 3: มีไฟล์เล็ก 100,000 ไฟล์ แต่ละไฟล์ 5,000 ไบต์ บนคลัสเตอร์ 4 KB ใช้พื้นที่จริงเท่าไร เสียไปเท่าไร และถ้าใช้คลัสเตอร์ 64 KB จะเป็นอย่างไร"}
คลัสเตอร์ 4 KB: ไฟล์ละ 2 คลัสเตอร์ = 8,192 ไบต์ รวม 819,200,000 ไบต์ ≈ 781 MiB เสียไฟล์ละ 3,192 ไบต์ รวม ≈ 319 MB (ข้อมูลจริง 500 MB)
คลัสเตอร์ 64 KB: ไฟล์ละ 1 คลัสเตอร์ = 65,536 ไบต์ รวม 6,553,600,000 ไบต์ ≈ 6.1 GiB เสียกว่า 6 GB ทั้งที่ข้อมูลจริงเท่าเดิม บทเรียนคือคลัสเตอร์ใหญ่เหมาะกับไฟล์ใหญ่ ไม่เหมาะกับไฟล์เล็กจำนวนมาก (ในทางปฏิบัติ NTFS ที่ไฟล์เล็กมากเก็บใน MFT จะเลี่ยงปัญหานี้ได้บางส่วน)
::

::reveal{question="โจทย์ 4: install.wim ขนาด 5 GiB จะใส่ลง USB ฟอร์แมต FAT32 ได้หรือไม่ เพราะอะไร และมีทางออกอะไรบ้าง"}
ไม่ได้ เพราะ FAT32 เก็บขนาดไฟล์เป็นเลข 32 บิต ใหญ่สุด 2³² − 1 ไบต์ ≈ 4 GiB และ 5 GiB เกินขีดจำกัด ทางออกคือ (1) แบ่ง WIM เป็นไฟล์ .swm หลายชิ้นเล็กกว่า 4 GiB ซึ่งตัวติดตั้งรู้จัก (2) ฟอร์แมต USB เป็น NTFS แล้วใช้ตัวบูตที่รองรับ (3) ใช้เครื่องมือสร้าง USB ที่จัดการให้ ทางเลือก (2) ต้องระวังว่าเฟิร์มแวร์ UEFI ปกติอ่านไม่ได้เพราะเป็น NTFS จึงต้องมีพาร์ทิชันบูตเล็กๆ แยกต่างหาก
::

## ตรวจความเข้าใจ

::reveal{question="ทำไมไฟล์บูตของ UEFI จึงอยู่ในพาร์ทิชันที่เป็น FAT32 ทั้งที่ Windows ใช้ NTFS เป็นหลัก"}
เพราะมาตรฐาน UEFI กำหนดให้เฟิร์มแวร์ต้องอ่านระบบไฟล์ FAT เท่านั้น เฟิร์มแวร์เป็นโค้ดเล็กๆ ที่ยังไม่มีไดรเวอร์ NTFS การให้ ESP เป็น FAT32 จึงรับประกันว่าเมนบอร์ดทุกยี่ห้อหาตัวบูตเจอ ผลข้างเคียงคือสื่อติดตั้งที่ต้องให้เฟิร์มแวร์อ่านก็ถูกจำกัดด้วยข้อจำกัดของ FAT32 (ไฟล์ละไม่เกิน 4 GiB) ด้วย
::

::reveal{question="WinPE ต้องรันบน RAM แทนที่จะรันจากดิสก์ที่กำลังจะติดตั้ง เพราะเหตุใด"}
เพราะตัวติดตั้งต้องลบ แบ่ง และฟอร์แมตดิสก์เป้าหมาย ถ้ารันจากดิสก์นั้นเอง ก็เท่ากับลบพื้นที่ที่ตัวเองใช้อยู่ การโหลดทั้งระบบลง RAMDisk ทำให้ตัวติดตั้งแยกขาดจากสิ่งที่มันแก้ไข
::

::reveal{question="อธิบายว่า GPT ป้องกันความเสียหายของตารางพาร์ทิชันได้ดีกว่า MBR อย่างไร และมีสิ่งใดที่ GPT ป้องกันไม่ได้"}
GPT เก็บตารางสำรองท้ายดิสก์และใช้ CRC32 ตรวจทั้งหัวตารางและรายการ ถ้าด้านหน้าเสีย สามารถตรวจพบและกู้จากสำเนาท้ายดิสก์ได้ ส่วน MBR มีสำเนาเดียวและไม่มีการตรวจ สิ่งที่ GPT ป้องกันไม่ได้คือการแก้ไขโดยเจตนา เพราะ CRC32 ใครก็คำนวณใหม่ได้ ต้องพึ่ง Secure Boot และการเข้ารหัสดิสก์
::

::reveal{question="NTFS journal ช่วยอะไรหลังไฟดับ และไม่ช่วยอะไร"}
ช่วยให้โครงสร้างระบบไฟล์ (MFT, bitmap, ไดเรกทอรี) กลับสู่สภาพสอดคล้องได้ โดยอ่าน log แล้วทำธุรกรรมที่ค้างให้จบหรือย้อนกลับ ไม่ช่วยรับประกันเนื้อหาไฟล์ที่แอปกำลังเขียน ไฟล์นั้นอาจเขียนไม่ครบได้ จึงต้องมีการสำรองข้อมูลและแอปที่เขียนอย่างปลอดภัย
::

::reveal{question="เครื่องติดตั้งเสร็จแล้วรีบูต แต่กลับเข้าตัวติดตั้งอีก ควรสงสัยอะไรก่อน และเทียบกับกรณีที่ขึ้นว่า Boot device not found ต่างกันอย่างไร"}
กรณีกลับเข้าตัวติดตั้ง เฟิร์มแวร์ยังเลือกบูตจาก USB ก่อน ถอด USB หรือปรับลำดับบูต ถือว่าติดตั้งสำเร็จแล้ว ส่วน Boot device not found หมายถึงเฟิร์มแวร์หาตัวบูตที่ใช้ได้ไม่เจอเลย สาเหตุที่พบบ่อยคือโหมดเฟิร์มแวร์ (UEFI/Legacy) ไม่ตรงกับชนิดตารางพาร์ทิชัน หรือไฟล์บูตใน ESP ไม่ถูกเขียนไว้ สองอาการนี้ต่างกันเพราะเกิดคนละด่านของลำดับบูต
::

::reveal{question="BitLocker ขอ recovery key ทั้งที่เจ้าของเครื่องไม่ได้ทำอะไร เป็นสัญญาณของการถูกโจมตีเสมอหรือไม่"}
ไม่เสมอไป สาเหตุที่พบบ่อยกว่าคือค่า PCR เปลี่ยนจากเหตุปกติ เช่น อัปเดตเฟิร์มแวร์ เปลี่ยนค่า Secure Boot หรือเปลี่ยนลำดับบูต TPM จึงไม่ยอมปลดผนึกกุญแจ แต่ก็อาจเกิดจากมีคนแก้ตัวบูตจริงได้ ทั้งสองกรณีดูภายนอกเหมือนกัน การขอ recovery key คือกลไกทำงานถูกต้องตามที่ออกแบบ ผู้ดูแลควรตรวจว่ามีการเปลี่ยนแปลงที่ตั้งใจหรือไม่ก่อนใส่คีย์
::

## สรุป

- **ก่อนติดตั้ง** เลือกวิธีตามสิ่งที่ต้องเก็บจากระบบเดิม ตรวจเงื่อนไข (TPM 2.0, Secure Boot) และตรวจค่าแฮชไฟล์ ISO
- **ลำดับบูต:** UEFI → อ่าน GPT → หา ESP (FAT32) → ตรวจลายเซ็น → Boot Manager → โหลด WinPE ลง RAM → setup
- **MBR เทียบ GPT:** ขีดจำกัดมาจากจำนวนบิตของที่อยู่ MBR 32 บิต = 2 TiB (เซกเตอร์ 512 ไบต์) GPT 64 บิต พร้อม CRC32 และตารางสำรอง
- **ระบบไฟล์:** คลัสเตอร์ทำให้มีพื้นที่เสียครึ่งคลัสเตอร์ต่อไฟล์โดยเฉลี่ย FAT32 จำกัดไฟล์ 4 GiB − 1 ไบต์ NTFS มี MFT กับ journal ที่รักษาความสอดคล้องของโครงสร้าง
- **การแตกอิมเมจ:** ตัวติดตั้งกาง install.wim ลงพาร์ทิชัน เขียนไฟล์บูตด้วย bcdboot รีบูตเข้า specialize (สร้าง SID) แล้ว OOBE
- **หลังติดตั้ง:** เครือข่าย → อัปเดต → ไดรเวอร์ → การป้องกัน ไดรเวอร์รันใน Kernel Mode จึงต้องระวังที่มา
- **Security:** Secure Boot ตรวจลายเซ็นตัวบูต TPM ผูกกุญแจ BitLocker กับสถานะการบูต แต่ทุกกลไกมีข้อจำกัดและต้องอัปเดตต่อเนื่อง
- บทถัดไป: ติดตั้ง Linux เปรียบเทียบกลไกเดียวกัน (GRUB แทน Boot Manager, ext4 แทน NTFS)
