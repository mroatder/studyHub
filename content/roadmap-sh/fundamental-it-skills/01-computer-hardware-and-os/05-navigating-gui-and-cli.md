## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **GUI และ CLI เป็น "โปรแกรม" ธรรมดา** ที่ขอบริการจาก kernel ผ่าน system call เหมือนกัน ไม่ใช่ระบบคนละอัน
2. เล่า **วงจรการทำงานของเชลล์** ตั้งแต่อ่านบรรทัด → แยกคำ → ขยาย → สร้างโปรเซส (fork/exec) → รอผล
3. อธิบายว่า **kernel แปล path อย่างไร** ทีละส่วน และคำนวณ relative path จากตำแหน่งสองจุดได้
4. ทำนายได้ว่าบรรทัดคำสั่งหนึ่ง **จะกลายเป็นอาร์กิวเมนต์ (argv) กี่ตัวและอะไรบ้าง** เมื่อมีช่องว่าง เครื่องหมายคำพูด ตัวแปร และ `*`
5. อธิบายได้ว่า **เชลล์หาโปรแกรมจาก PATH อย่างไร** และเหตุผลที่ลำดับใน PATH เกี่ยวกับความปลอดภัย
6. เปรียบเทียบ **pipeline แบบข้อความ (Bash) กับแบบออบเจ็กต์ (PowerShell)** และอ่าน **exit code** ได้
7. ใช้ Tab completion, history และการตรวจก่อนลบ (`echo`/`ls` ก่อน) เพื่อลดความผิดพลาดและความเสี่ยง
8. วินิจฉัยอาการยอดฮิต (ไม่พบไฟล์, `too many arguments`, ลบผิดชิ้น, `command not found`) จากกลไก ไม่ใช่การท่องจำ

## เปรียบเทียบกับชีวิตจริง

นึกถึง **การสั่งอาหารผ่านพนักงานเสิร์ฟ**

| ในร้านอาหาร | ในคอมพิวเตอร์ | ข้อสังเกต |
|---|---|---|
| ลูกค้าชี้เมนูมีรูปให้พนักงานดู | GUI | ง่ายเมื่อยังไม่รู้ว่าจะกินอะไร แต่สั่ง 100 โต๊ะซ้ำๆ ช้า |
| ลูกค้าเขียนออร์เดอร์เป็นข้อความ | CLI | แม่นและทำซ้ำได้ แต่ตัวสะกดผิดตัวเดียวก็ผิดเมนู |
| พนักงานเสิร์ฟแปลออร์เดอร์เป็นใบสั่งที่ครัวเข้าใจ | **เชลล์** | ครัวไม่เคยเห็นลายมือลูกค้า เห็นแต่ใบสั่งที่พนักงานเขียนใหม่ |
| ออร์เดอร์ "ข้าวผัด ไม่ผัก" ที่พนักงานเข้าใจเป็น 2 รายการ | ช่องว่างแยกคำผิด | ตัวอย่างว่าทำไมครอบเครื่องหมายคำพูดจึงสำคัญ |
| ครัวหลายสาขา พนักงานเดินหาตามลำดับจนเจอ | PATH | ลำดับการค้นหาตัดสินว่าได้ของจากสาขาไหน |

## ภาพรวม

บทนี้ตอบคำถามเดียวซ้ำๆ: **"ระหว่างสิ่งที่ฉันพิมพ์/คลิก กับสิ่งที่ระบบทำจริง มีอะไรเกิดขึ้นตรงกลาง"** เริ่มจากภาพใหญ่ (GUI/CLI/เชลล์/kernel) → path → การแยกคำ → การหาโปรแกรม → ท่อส่งข้อมูล → ความปลอดภัย

## 1. GUI และ CLI ต่างกันตรงไหนจริงๆ

### 1.1 ทั้งสองคือโปรแกรม ไม่ใช่ระบบปฏิบัติการ

> **นึกภาพว่า:** ธนาคารมีตู้ ATM (กดปุ่มตามเมนู) กับใบฝาก-ถอน (เขียนเอง) สองทางนี้ดูต่างกัน แต่ทั้งคู่ส่งเรื่องไปที่ **เคาน์เตอร์หลังบ้านเดียวกัน** ยอดเงินจึงตรงกันเสมอ
> - ตู้ ATM = GUI (เช่น File Explorer)
> - ใบฝาก-ถอนที่เขียนเอง = CLI (เช่น `dir`, `ls`)
> - เคาน์เตอร์หลังบ้าน = kernel ที่รับคำขอผ่าน system call
>
> ของที่สร้างด้วยเมาส์จึงเห็นใน CLI ทันที เพราะอยู่ในยอดเงินบัญชีเดียวกัน

**GUI (Graphical User Interface)** แสดงเครื่องเป็นหน้าต่าง ไอคอน และตัวชี้เมาส์ **CLI (Command-Line Interface)** รับข้อความแล้วตอบเป็นข้อความ คนมักคิดว่าสองอย่างนี้เป็น "โหมดของระบบ" แต่ความจริงคือ **ทั้งคู่เป็นโปรแกรมธรรมดา** (File Explorer, GNOME Files, PowerShell, Bash) ที่ขอบริการจาก kernel ผ่าน **system call** เช่น "เปิดไดเรกทอรีนี้" "อ่านรายการ" "สร้างโปรเซสใหม่" เมื่อคุณเปิดโฟลเดอร์ใน File Explorer กับพิมพ์ `dir` ภายในต่างก็ขอข้อมูลเดียวกันจาก kernel ต่างกันแค่หน้าตาของคนที่มาขอ นี่คือเหตุผลที่ของที่สร้างด้วยเมาส์เห็นใน CLI ทันที

### 1.2 เปรียบเทียบอย่างมีเหตุผล

> **นึกภาพว่า:** ย้ายบ้านแล้วต้องแปะป้ายชื่อใหม่บนกล่อง 500 ใบ จะแปะทีละใบด้วยมือ (GUI) หรือจ้างช่างพิมพ์ป้ายให้ด้วยคำสั่งเดียว (CLI) ก็ได้
>
> ```
> GUI : เลือก → เปลี่ยนชื่อ → ยืนยัน   × 500 กล่อง = ประมาณ 1,500 การกระทำ
> CLI : วนลูปบรรทัดเดียว             × รันครั้งเดียว
> ถ้ามีกล่องแค่ 1 ใบและไม่รู้ว่าอยู่ห้องไหน → เดินดูเอง (GUI) เร็วกว่า
> ```
>
> ยิ่งงานซ้ำมาก ช่างพิมพ์ป้าย (CLI) ยิ่งคุ้ม ตัวเลข 1,500 เป็นค่าประมาณ

**ตัวเลขประกอบการตัดสินใจ (ค่าประมาณ):** เปลี่ยนชื่อไฟล์ 500 ไฟล์ด้วย GUI ต้องคลิก/พิมพ์อย่างน้อย 500 × 3 ครั้ง (เลือก, เปลี่ยนชื่อ, ยืนยัน) ≈ 1,500 การกระทำ ส่วน CLI เขียนบรรทัดเดียว (วนลูปเปลี่ยนชื่อ) แล้วรันซ้ำเมื่อไรก็ได้ ยิ่งงานซ้ำมาก CLI ยิ่งได้เปรียบ แต่ถ้าทำครั้งเดียวและยังไม่รู้ว่าไฟล์อยู่ไหน GUI เร็วกว่า

### 1.3 เทอร์มินัล เชลล์ และคอนโซล ต่างกันอย่างไร

> **นึกภาพว่า:** โทรศัพท์บ้านสมัยก่อน มีตัวเครื่อง (จอ+แป้นกด) กับคนรับสายที่ฟังแล้วไปทำงานต่อ
> - ตัวเครื่องที่มีหน้าจอและแป้น = **terminal** (หน้าตา)
> - คนรับสายที่ตีความสิ่งที่เราพูด = **shell** (สมอง)
> - ตู้โทรศัพท์ที่ต่อตรงกับเครื่องเดียวกัน = **console**
>
> เปลี่ยนคนรับสายได้โดยไม่ต้องเปลี่ยนเครื่อง เหมือนเปิด Windows Terminal แล้วเลือก PowerShell หรือ Bash

| คำ | คืออะไร | ตัวอย่าง |
|---|---|---|
| **Terminal** | หน้าต่างที่แสดงข้อความและรับการกดแป้น (หน้าตา) | GNOME Terminal, Windows Terminal |
| **Shell** | โปรแกรมที่ตีความสิ่งที่พิมพ์และสั่งงาน (สมอง) | Bash, Zsh, PowerShell, cmd.exe |
| **Console** | จอ/แป้นพิมพ์ของเครื่องโดยตรง (ในอดีตคือตัวเครื่อง) | คอนโซลของ VM |

เปลี่ยนเชลล์ได้โดยไม่ต้องเปลี่ยนเทอร์มินัล เช่น เปิด Windows Terminal แล้วรัน PowerShell หรือ Bash (ผ่าน WSL) ในหน้าต่างเดียวกัน

## 2. เชลล์ทำงานอย่างไร: วงจรหนึ่งรอบ

### 2.1 ทำไมต้องเข้าใจ

> **นึกภาพว่า:** ลูกค้าพูดว่า "ข้าวผัด ไม่ผัก" พนักงานเสิร์ฟจดลงใบสั่งเป็น **2 รายการ** ("ข้าวผัด" กับ "ไม่ผัก") ครัวเห็นแต่ใบสั่ง ไม่เคยได้ยินลูกค้า
>
> ครัวคือโปรแกรม พนักงานเสิร์ฟคือเชลล์ ความผิดพลาดส่วนใหญ่เกิดที่ขั้น "จดใบสั่ง" ก่อนครัวเริ่มทำอาหารด้วยซ้ำ

เกือบทุกความผิดพลาดของ CLI (ลบผิดชิ้น, `too many arguments`, `command not found`) เกิดจาก **ความเข้าใจผิดว่าโปรแกรมเห็นสิ่งที่เราพิมพ์** ความจริงคือเชลล์ดัดแปลงบรรทัดก่อนเสมอ

### 2.2 วงจรของเชลล์ (read–parse–expand–execute)

> **นึกภาพว่า:** เลขาที่แปลงโน้ตของเจ้านายก่อนส่งต่อ: ตัดเป็นคำ แทนตัวย่อด้วยชื่อเต็ม แล้วหาแผนกที่ทำงานนั้นได้ จึงส่งงานไป ลองไล่บรรทัด `ls -l *.txt` (สมมติในโฟลเดอร์มี a.txt กับ b.txt)
>
> ```
> พิมพ์       : ls -l *.txt
> แยกคำ       : [ls] [-l] [*.txt]            → 3 คำ
> ขยาย *      : [ls] [-l] [a.txt] [b.txt]    → 4 คำ
> หา ls ใน PATH: /usr/bin/ls
> ส่งให้ ls   : argv = 4 ตัว (ls ไม่เคยเห็นเครื่องหมาย *)
> ```
>
> เลขาคือ shell ส่วน "รายการ 4 คำที่ส่งต่อ" คือ argv ขั้น fork/exec คือการจ้างพนักงานใหม่มาทำงานนั้น

ข้อสังเกตสำคัญ

- **คำสั่งในตัว (built-in)** เช่น `cd` ต้องทำงานในโปรเซสเชลล์เอง เพราะ **โฟลเดอร์ทำงานปัจจุบัน (cwd) เป็นคุณสมบัติของแต่ละโปรเซส** ถ้า `cd` เป็นโปรแกรมแยก มันจะเปลี่ยน cwd ของโปรเซสลูกแล้วจบไป เชลล์แม่ไม่เปลี่ยนตาม
- **stdin / stdout / stderr** คือไฟล์พิเศษ 3 ตัวที่ทุกโปรเซสได้มา (fd 0, 1, 2) การเปลี่ยนทิศทาง `>` หรือท่อ `|` คือการที่เชลล์ต่อ fd เหล่านี้ใหม่ก่อน exec (เรื่องนี้จะลงลึกในบทไฟล์)
- เชลล์ Windows (PowerShell) มีวงจรคล้ายกัน แต่สร้างโปรเซสด้วยกลไกของ Windows (ไม่ใช่ fork) ผลที่เห็นเหมือนกัน

## 3. Path: kernel เดินต้นไม้อย่างไร

### 3.1 ระบบไฟล์คือต้นไม้ และ path คือคำสั่งเดิน

> **นึกภาพว่า:** ที่อยู่ในคอนโดฯ: ตึก → ชั้น → ห้อง ถ้าเริ่มจากล็อบบี้ (ราก) ต้องไล่ทีละขั้นไม่มีทางลัด ทุกชั้นมีป้ายบอกว่า "ห้องชื่ออะไรอยู่ตรงไหน" (ตารางไดเรกทอรี)
>
> ```
> /home/alex/documents/report.txt
> /          → ค้น "home"      ในตารางของราก
> home       → ค้น "alex"      ในตารางของ home
> alex       → ค้น "documents" ในตารางของ alex
> documents  → ค้น "report.txt" ได้ไฟล์   (ค้น 4 ครั้ง)
> ```
>
> ปุ่ม "ขึ้นหนึ่งชั้น" คือ `..` และ "อยู่ที่เดิม" คือ `.` ทั้งสองเป็นรายการจริงในตารางของทุกไดเรกทอรี

ไดเรกทอรีคือไฟล์พิเศษที่เป็น **ตารางรายการ "ชื่อ → ตำแหน่ง"** (ใน Linux ชี้ไปหา inode) path อย่าง `/home/alex/documents/report.txt` จึงเป็นลำดับขั้นให้ kernel ทำทีละส่วน

1. เริ่มที่ราก `/` (ถ้าขึ้นต้นด้วย `/`) หรือที่ **โฟลเดอร์ทำงานปัจจุบัน** (ถ้าไม่ขึ้นต้น)
2. ค้นชื่อ `home` ในตารางของราก → ได้ไดเรกทอรีถัดไป
3. ค้น `alex` ในตารางของ `home` → ... ต่อไปจนถึง `report.txt`
4. ถ้าขั้นใดไม่พบชื่อ หรือไม่มีสิทธิ์เข้า (บท 7) การเดินหยุดและรายงานข้อผิดพลาด

**`.` และ `..` เป็นรายการจริงในตารางของทุกไดเรกทอรี** ไม่ใช่เวทมนตร์ของเชลล์ `.` ชี้ตัวเอง และ `..` ชี้ไดเรกทอรีแม่ (ที่รากชี้ตัวเอง) เหมือนเลื่อนขึ้นไปหนึ่งชั้น

### 3.2 ความต่างระหว่าง Windows และ Linux

> **นึกภาพว่า:** Windows เหมือนหลายตึกแยกชื่อ (C: D: E:) แต่ละตึกมีล็อบบี้ของตัวเอง ส่วน Linux เป็นตึกเดียว (`/`) ถ้าได้ดิสก์ใหม่ก็ต่อเติมเป็นชั้นของตึกเดิม (mount)
> - Linux แยกตัวพิมพ์ `Report.txt` ≠ `report.txt` เหมือนคนชื่อ Somchai กับ somchai เป็นคนละคน
> - Windows มองว่าเป็นคนเดียวกัน แต่จำการสะกดที่ตั้งไว้
>
> ตารางข้างล่างคือรายละเอียดที่ต่างกัน

| | Windows | Linux |
|---|---|---|
| ราก | ตัวอักษรไดรฟ์แต่ละตัว `C:⧵` `D:⧵` | รากเดียว `/` (ดิสก์อื่นถูก mount เข้ามา ดูบท 4) |
| ตัวคั่น | `⧵` (รับ `/` ได้ในหลายส่วน) | `/` |
| ตัวพิมพ์เล็ก/ใหญ่ | **ไม่แยก** โดยทั่วไป (แต่เก็บตัวพิมพ์ตามที่ตั้ง) | **แยก** `Report.txt` ≠ `report.txt` |
| ความยาว path | ข้อจำกัดเดิม 260 ตัวอักษร (MAX_PATH) ใน API เก่า ซึ่งขยายได้ในรุ่นใหม่ | ชื่อแต่ละส่วนยาวได้ 255 ไบต์ ทั้ง path 4,096 ไบต์ (ค่าตั้งต้นทั่วไป) |
| ตัวอักษรต้องห้ามในชื่อ | หลายตัว เช่น `< > : ? *` กับ `/` และ `⧵` และชื่อเฉพาะ เช่น `CON`, `NUL` | ห้ามเฉพาะ `/` และอักขระ NUL |

เหตุผลของตัวคั่น: ใน MS-DOS เครื่องหมาย `/` ถูกใช้นำหน้าตัวเลือกของคำสั่ง (เช่น `dir /w`) อยู่แล้ว จึงเลือก `⧵` เป็นตัวคั่นโฟลเดอร์ ขณะที่ Unix ใช้ `/` มาแต่แรก

### 3.3 Absolute กับ relative และการคำนวณ

> **นึกภาพว่า:** บอกทาง 2 แบบ: "พิกัด GPS" (absolute) ใช้ได้เหมือนกันทุกที่ กับ "จากที่คุณยืนอยู่ ถอยออกไป 2 ชั้นแล้วเลี้ยวไปห้องดนตรี" (relative) ซึ่งขึ้นกับว่ายืนอยู่ตรงไหน
>
> ```
> ยืนที่ A = /home/sam/projects/web     ปลายทาง B = /home/sam/music/rock
> บรรพบุรุษร่วม (LCA) = /home/sam
> ถอย: web → projects → sam              = 2 ชั้น  → ../..
> ลง : sam → music → rock                = music/rock
> relative = ../../music/rock
> ```
>
> cwd คือ "ที่ที่คุณยืน" LCA คือ "ทางแยกที่ใกล้ที่สุดของสองที่อยู่"

- **Absolute path:** ขึ้นต้นจากราก ใช้ผลเหมือนเดิมทุกที่
- **Relative path:** นับจากโฟลเดอร์ทำงานปัจจุบัน (cwd) ของโปรเซส จึงให้ผลต่างกันเมื่อ cwd ต่างกัน

**วิธีคำนวณ relative path จาก A ไป B:** หา "บรรพบุรุษร่วมที่ลึกที่สุด" (LCA) ของทั้งสอง แล้ว

> relative = (`..` ซ้ำ จำนวนชั้นจาก A ขึ้นไปถึง LCA) + (ส่วนที่เหลือของ B ลงมาจาก LCA)

ตัวอย่าง: A = `/home/sam/projects/web`, B = `/home/sam/music/rock`
LCA = `/home/sam` ; จาก A ขึ้นไป LCA ต้องถอย 2 ชั้น (`web` → `projects` → `sam`) ; จาก LCA ลงไป B คือ `music/rock`
ดังนั้น relative = `../../music/rock`

ลองกำหนดตำแหน่งปัจจุบันกับปลายทางเอง แล้วสังเกตว่า absolute ของปลายทางไม่เปลี่ยน ขณะที่ relative เปลี่ยนตามตำแหน่งที่ยืนอยู่

::path-navigator
::

> **ข้อควรระวัง:** `~` (โฮมของผู้ใช้) เป็น **สิ่งที่เชลล์ขยาย** ไม่ใช่ของ kernel ถ้าไปอยู่ในเครื่องหมายคำพูด (`"~/x"`) Bash จะไม่ขยายให้ ในขณะที่ `$HOME` ใช้ได้ในเครื่องหมายคำพูดคู่ รายละเอียดนี้ทำให้สคริปต์ของคนที่ไม่ระวังพังบ่อย

## 4. บรรทัดคำสั่งกลายเป็นอาร์กิวเมนต์อย่างไร (ส่วนที่คนพลาดบ่อยที่สุด)

### 4.1 หลักการ: โปรแกรมได้ "รายการ" ไม่ใช่ "บรรทัด"

> **นึกภาพว่า:** ส่งของให้ร้านค้าเป็น **ถุงที่แบ่งช่องแล้ว** ไม่ใช่ใบรายการยาวๆ ถ้าเขียนว่า "My Docs" เฉยๆ คนแพ็กจะแยกเป็นสองช่อง
>
> ```
> ls My Docs     → argv = [ls] [My] [Docs]      3 ตัว (หาโฟลเดอร์ 2 ชื่อ)
> ls "My Docs"   → argv = [ls] [My Docs]        2 ตัว (โฟลเดอร์ชื่อเดียว)
> ```
>
> ถุงคือ argv ส่วนเครื่องหมายคำพูดคือเทปที่มัดคำให้อยู่ช่องเดียวกัน

เชลล์แปลงบรรทัดเป็น **argv** (รายการข้อความ) แล้วส่งให้โปรแกรม โดยผ่านกฎตามลำดับต่อไปนี้ (แบบย่อของ Bash)

1. **แยกคำ:** ช่องว่าง (นอกเครื่องหมายคำพูด) คือตัวแบ่งคำ
2. **เครื่องหมายคำพูด:** `'...'` ทุกตัวอักษรเป็นตัวอักษรตรงๆ ; `"..."` ยังขยาย `$ตัวแปร` ให้ แต่ไม่แยกคำ ; `⧵` นำหน้าอักษรตัวถัดไปให้เป็นตัวอักษรตรงๆ
3. **ขยายตัวแปร** `$VAR` (ถ้าไม่ครอบเครื่องหมายคำพูด ผลลัพธ์จะถูก **แยกคำซ้ำ** ตามช่องว่างอีกครั้ง)
4. **ขยาย glob** `*` `?` เป็นรายชื่อไฟล์ที่ตรง (ถ้าไม่ตรงอะไรเลย Bash ส่งข้อความเดิมต่อไป) **เชลล์เป็นคนขยาย ไม่ใช่โปรแกรม**

ลองพิมพ์เองหรือกดตัวอย่าง แล้วดูว่าโปรแกรมจะได้อาร์กิวเมนต์กี่ตัว

::shell-parse
::

สรุปจากแล็บ

| บรรทัด | โปรแกรมได้อะไร | บทเรียน |
|---|---|---|
| `ls My Docs` | 2 ชื่อ: `My`, `Docs` | ช่องว่างแบ่งคำ |
| `ls "My Docs"` | 1 ชื่อ: `My Docs` | ครอบด้วยเครื่องหมายคำพูด |
| `echo *.txt` | `a.txt`, `b.txt` | `*` ถูกเชลล์ขยายก่อน echo ทำงาน |
| `rm $DIR` (DIR=`My Docs`) | 2 ชื่อ | ตัวแปรที่ไม่ครอบคำพูดถูกแยกคำซ้ำ **เป็นแหล่งของการลบผิดชิ้น** |
| `rm "$DIR"` | 1 ชื่อ | ครอบตัวแปรเสมอ |

### 4.2 เปรียบเทียบเชลล์ Windows

> **นึกภาพว่า:** Bash กับ PowerShell เหมือนสำนักงานที่มีเลขาแยกซองให้เสร็จก่อนส่ง ส่วน cmd.exe ส่ง **ซองทั้งซองที่ยังไม่แกะ** ให้โปรแกรมแกะเอง โปรแกรมแต่ละตัวแกะไม่เหมือนกัน
>
> PowerShell ไม่แยกคำซ้ำกับตัวแปรที่มีช่องว่าง (ปลอดภัยกว่า Bash จุดนี้) แต่ยังต้องครอบพาธที่มีช่องว่าง

PowerShell มีกฎต่างกันที่ควรรู้: **ตัวแปรที่มีช่องว่างไม่ถูกแยกคำซ้ำ** (ปลอดภัยกว่า Bash ในจุดนี้) แต่ชื่อพาธที่มีช่องว่างยังต้องครอบด้วยเครื่องหมายคำพูด และ `*` ถูกขยายโดย **cmdlet เอง** ในหลายกรณี ไม่ใช่เชลล์ ส่วน `cmd.exe` ส่งบรรทัดทั้งบรรทัดให้โปรแกรมไปแยกเอง จึงเกิดความไม่สม่ำเสมอระหว่างโปรแกรม

> **ข้อจำกัด:** กฎข้างต้นเป็นแบบย่อ Bash จริงมีรายละเอียดอีกมาก (`{a,b}`, `$(...)`, `~`, ลำดับการขยายหลายชนิด) แต่สี่ข้อนี้ครอบคลุมปัญหาในงานจริงส่วนใหญ่

## 5. เชลล์หาโปรแกรมเจอได้อย่างไร: PATH

> **นึกภาพว่า:** ห้องสมุดหลายอาคาร คุณถือรายการอาคารที่ต้องไล่หาตามลำดับ เจอหนังสือชื่อนั้นเล่มแรกที่ไหนก็หยิบที่นั่น
>
> ```
> PATH = /usr/local/bin : /usr/bin : /bin
> พิมพ์ ls → ค้น /usr/local/bin (ไม่เจอ) → /usr/bin (เจอ) → รัน /usr/bin/ls และหยุด
> ถ้ามี ls ที่ /usr/local/bin ด้วย จะชนะ เพราะอยู่ซ้ายกว่า
> ไล่ครบแล้วไม่เจอ → command not found
> ```
>
> รายการอาคารคือ PATH ลำดับในรายการตัดสินว่าใครชนะ ซึ่งเป็นเหตุที่คนร้ายแอบวางของปลอมไว้อาคารหน้าสุด

เมื่อพิมพ์ `ls` เชลล์ต้องรู้ว่าไฟล์โปรแกรมอยู่ที่ไหน จึงใช้ตัวแปรสภาพแวดล้อม **PATH** คือรายการโฟลเดอร์ (คั่นด้วย `:` บน Linux และ `;` บน Windows) เชลล์ไล่ **ตามลำดับ** ตัวแรกที่พบชื่อตรงกันถูกนำไปรัน ส่วนที่ไม่พบเลยจะได้ `command not found`

คำสั่งที่เป็นได้หลายแบบ ตรวจให้ชัดด้วย `type` (Bash) หรือ `Get-Command` (PowerShell) ซึ่งบอกว่ากำลังจะรันอะไร: alias, built-in, function หรือไฟล์ที่ไหน

**ทำไมลำดับใน PATH เกี่ยวกับความปลอดภัย:** ถ้ามีโฟลเดอร์ที่ผู้ใช้เขียนได้อยู่ **หน้า** `/usr/bin` ผู้โจมตีวางโปรแกรมชื่อ `ls` ไว้ที่นั่น แล้ว `ls` ของคุณจะกลายเป็นของเขา (PATH hijacking) การใส่ `.` (โฟลเดอร์ปัจจุบัน) ใน PATH ก็อันตรายด้วยเหตุเดียวกัน ส่วน `cmd.exe` ของ Windows ในอดีตค้นโฟลเดอร์ปัจจุบันก่อน PATH ซึ่งเป็นช่องโหว่คลาสสิก PowerShell ไม่ทำแบบนั้น (ต้องพิมพ์ `.⧵โปรแกรม` ชัดเจน)

## 6. CLI บน Windows: PowerShell และความต่างที่เป็นหลักการ

### 6.1 ท่อส่งออบเจ็กต์ ไม่ใช่ข้อความ

> **นึกภาพว่า:** สายพานในโรงงานสองแบบ แบบแรกส่ง **ใบกระดาษเขียนข้อความ** (Bash) คนรับต้องอ่านแล้วตัดคอลัมน์เอง แบบที่สองส่ง **กล่องที่ติดฉลากชื่อช่อง** (PowerShell) หยิบช่อง Length ได้ทันที
>
> ```
> Bash       : "notes.txt 1024"      → ต้องตัดคำที่ 2 เอง (พังเมื่อชื่อมีช่องว่าง)
> PowerShell : { Name: notes.txt, Length: 1024 }   → Where Length -gt 500
> ```
>
> ใบกระดาษคือข้อความ กล่องมีฉลากคือออบเจ็กต์ที่มี property

Bash/Unix ส่งผ่านท่อ (`|`) เป็น **ข้อความ** ทุกโปรแกรมต้องแยกข้อความเองด้วยเครื่องมืออย่าง `grep`, `awk` PowerShell ส่ง **ออบเจ็กต์** ที่มีคุณสมบัติ (property) พร้อมชนิดข้อมูล ทำให้กรองโดยอ้างชื่อคุณสมบัติได้เลย ไม่ต้องตัดข้อความ

| งาน | Bash (ข้อความ) | PowerShell (ออบเจ็กต์) |
|---|---|---|
| แสดงไฟล์ใหญ่กว่า 1 MB เรียงตามขนาด | `find . -type f -size +1M` | `Get-ChildItem -Recurse -File ⎮ Where-Object Length -gt 1MB ⎮ Sort-Object Length` |
| ข้อดี | เบา แพร่หลาย ใช้ได้ทุกที่ | อ่านง่ายกว่า กรองด้วยชื่อคุณสมบัติ ไม่ต้องกลัวรูปแบบข้อความเปลี่ยน |
| ข้อควรระวัง | พังเมื่อรูปแบบเอาต์พุตเปลี่ยนหรือมีช่องว่างในชื่อ | ต้องรู้ชื่อ property ของออบเจ็กต์ |

(ในตาราง ใช้เครื่องหมายท่อ `⎮` แทนเพื่อไม่ชนกับรูปแบบตาราง พิมพ์จริงใช้ `|` ปกติ)

### 6.2 คำสั่งพื้นฐานของสองโลก

> **นึกภาพว่า:** ภาษาเดียวกันคนละสำเนียง ศัพท์ `pwd` และ `cd` ใช้ได้ทั้งสองโลก แต่ `ls` ใน PowerShell เป็นแค่ชื่อเล่นของ `Get-ChildItem` ไม่ใช่โปรแกรม ls ของ Linux ตัวเลือกจึงใช้ไม่ตรงกัน
>
> ชื่อ cmdlet เป็น **กริยา-นาม** (Get-, Set-, New-, Remove-) เหมือนบอกว่า "ทำอะไรกับอะไร" เดาชื่อคำสั่งอื่นได้

| ทำอะไร | PowerShell (cmdlet เต็ม / alias) | Bash |
|---|---|---|
| ตำแหน่งปัจจุบัน | `Get-Location` / `pwd` | `pwd` |
| ดูรายการ | `Get-ChildItem` / `dir`, `ls` | `ls`, `ls -la` (รวมไฟล์ซ่อน) |
| เปลี่ยนโฟลเดอร์ | `Set-Location` / `cd` | `cd` |
| ดูเนื้อหาไฟล์ | `Get-Content` / `cat` | `cat`, `less` |
| ผลของคำสั่งก่อนหน้า | `$?` (สำเร็จ/ไม่) และ `$LASTEXITCODE` (โปรแกรมภายนอก) | `$?` (exit code) |

cmdlet ชื่อรูปแบบ **กริยา-นาม** (`Get-`, `Set-`, `New-`, `Remove-`) ทำให้เดาชื่อคำสั่งอื่นได้ ส่วน alias อย่าง `ls` ใน PowerShell เป็นเพียงชื่อทางลัดของ `Get-ChildItem` ไม่ใช่โปรแกรม `ls` ของ Linux (ตัวเลือกจึงใช้ไม่ตรงกัน)

## 8. เทคนิคใช้เชลล์ให้เร็วและผิดน้อย

### 8.1 Tab completion

> **นึกภาพว่า:** ช่องพิมพ์ค้นหาที่เสนอคำให้ขณะพิมพ์ สมมติในโฟลเดอร์มี `Documents` กับ `Downloads`
>
> ```
> พิมพ์ D  + Tab → เติมได้แค่ "Do" (ตรงกันทั้งคู่) กด Tab อีกครั้งเห็นสองชื่อ
> พิมพ์ Doc + Tab → เติมเป็น "Documents/" ทั้งชื่อ
> พิมพ์ Zzz + Tab → ไม่เติมอะไร = ไม่มีชื่อนั้น
> ```
>
> "Tab ไม่เติม" จึงเป็นสัญญาณตรวจว่าพิมพ์ผิดหรือยืนผิดโฟลเดอร์

พิมพ์ต้นชื่อแล้วกด **Tab** เชลล์ค้นรายการที่ขึ้นต้นตรงกันในโฟลเดอร์ให้ ถ้าเจอชื่อเดียวเติมจนจบ ถ้าเจอหลายชื่อ Bash เติมเท่าส่วนที่ตรงกัน กด Tab ซ้ำเพื่อดูรายการ ส่วน PowerShell กด Tab วนผ่านตัวเลือก

นอกจากพิมพ์น้อยลง ยังช่วย **ตรวจสอบ** ด้วย: ถ้า Tab ไม่เติม แปลว่าชื่อนั้นไม่มีอยู่ พิมพ์ผิด หรือยืนอยู่ผิดโฟลเดอร์ และ Tab ยัง **ใส่เครื่องหมายหนีช่องว่างให้อัตโนมัติ** (`My⧵ Docs`) จึงเป็นวิธีง่ายที่สุดกับชื่อที่มีช่องว่าง

### 8.2 ชื่อที่มีช่องว่าง (เชื่อมกับหัวข้อ 4)

> **นึกภาพว่า:** นึกถึงชื่อคน "สมชาย ใจดี" ถ้าไม่ผูกเป็นชื่อเดียว พนักงานจะเรียกเป็นสองคน คือ "สมชาย" กับ "ใจดี"
>
> ```
> cd My Documents     → argv = [cd] [My] [Documents]   → cd รับได้ 1 ตัว → too many arguments
> cd "My Documents"   → argv = [cd] [My Documents]     → สำเร็จ
> ```
>
> เครื่องหมายคำพูดหรือ `\ ` ผูกคำให้เป็นชื่อเดียว

ขณะนี้คุณรู้แล้วว่าทำไม `cd My Documents` จึงผิด: เชลล์ส่งอาร์กิวเมนต์ 2 ตัว (`My`, `Documents`) ให้ `cd` ซึ่งรับตัวเดียว

```bash
cd "My Documents"        # ครอบด้วยเครื่องหมายคำพูด
cd My\ Documents         # หรือหนีช่องว่างด้วย \
```

### 8.3 ประวัติคำสั่ง (history)

> **นึกภาพว่า:** สมุดจดทุกคำสั่งที่เคยสั่ง ลูกศรขึ้นคือเปิดย้อนทีละหน้า ส่วน Ctrl+R คือพิมพ์คำสำคัญแล้วให้สมุดหาหน้าที่ตรงกันให้
>
> แต่สมุดนี้ **ถูกเก็บลงไฟล์** ถ้าเคยพิมพ์รหัสผ่านในคำสั่ง ข้อความนั้นก็ค้างอยู่ในสมุดด้วย

กด **ลูกศรขึ้น/ลง** ย้อนคำสั่งเก่า ใน Bash กด **Ctrl+R** แล้วพิมพ์ส่วนหนึ่งของคำสั่งเก่าเพื่อค้นย้อนหลัง คำสั่ง `history` แสดงรายการ

**ด้านความปลอดภัย:** ประวัติถูกบันทึกลงไฟล์ (Bash: `~/.bash_history`, PowerShell: ไฟล์ `ConsoleHost_history.txt` ใต้โฟลเดอร์ PSReadLine ของผู้ใช้) หากพิมพ์รหัสผ่านหรือโทเค็นเป็นอาร์กิวเมนต์ ข้อมูลนั้นค้างในไฟล์ ผู้โจมตีที่เข้าเครื่องได้มักเปิดไฟล์นี้เป็นอย่างแรกๆ และอาร์กิวเมนต์ยังอาจปรากฏในรายการโปรเซส (`ps`) ให้ผู้ใช้อื่นเห็นชั่วขณะ จึงควรให้โปรแกรมถามรหัสแบบซ่อน หรืออ่านจากไฟล์/ตัวแปรสภาพแวดล้อม แทนการพิมพ์ในบรรทัดคำสั่ง

## 9. มุมมองด้าน Security

| ความเสี่ยง | กลไก (ทำไมเกิด) | ป้องกันด้วย |
|---|---|---|
| ลบผิดชิ้นจากตัวแปรไม่ครอบคำพูด | ตัวแปรถูกแยกคำซ้ำ (หัวข้อ 4) `rm $DIR` กลายเป็นหลายชื่อ แย่สุดคือตัวแปรว่างแล้ว `rm -rf $DIR/` กลายเป็น `rm -rf /` | ครอบตัวแปรด้วย `"..."` เสมอ ตรวจตัวแปรก่อนใช้ ลองด้วย `echo` นำหน้าเพื่อดู argv จริง |
| `rm` ไม่มีถังขยะ | `rm` ลบรายการในไดเรกทอรีทันที ไม่ผ่านถังขยะของ GUI | เช็ก `pwd` `ls` ก่อน ใช้ `rm -i` หรือ `echo rm …` ซ้อมก่อน |
| `*` ขยายเกินที่คิด | glob ถูกขยายโดยเชลล์เป็นทุกไฟล์ในโฟลเดอร์ปัจจุบัน | `echo *` ดูก่อนว่าจะได้ไฟล์ไหนบ้าง |
| PATH hijacking | โฟลเดอร์ที่เขียนได้อยู่หน้าใน PATH หรือมี `.` ใน PATH | ไม่ใส่ `.` ใน PATH ตรวจ `echo $PATH` และใช้ `type`/`command -v` |
| ลอกคำสั่งจากเว็บมาวาง | คำสั่งอาจซ่อนส่วนอันตราย และ `curl … ⎮ bash` รันโค้ดที่ยังไม่ได้อ่าน | อ่านทุกบรรทัดก่อนรัน ดาวน์โหลดเป็นไฟล์เปิดดูก่อน ตรวจ checksum |
| ประวัติคำสั่งเก็บความลับ | ไฟล์ history อ่านได้ภายหลัง | ไม่ใส่รหัสในอาร์กิวเมนต์ ตั้ง `HISTCONTROL=ignorespace` แล้วนำหน้าคำสั่งสำคัญด้วยช่องว่าง (ถ้าตั้งไว้) |
| Path traversal | โปรแกรมเอาชื่อไฟล์จากผู้ใช้ไปต่อ path โดยไม่กัน `..` เช่น `../../etc/passwd` เดินหลุดนอกโฟลเดอร์ที่อนุญาตตามกลไก 3.1 | ปรับ path ให้เป็นรูปมาตรฐานแล้วตรวจว่ายังอยู่ใต้โฟลเดอร์ที่อนุญาต ไม่รับ `..` จากผู้ใช้ |
| ทำงานเป็น root (`#`) | พิมพ์ผิดตัวเดียวมีสิทธิ์ทำลายทั้งระบบ | ใช้ผู้ใช้ปกติ + `sudo` เฉพาะคำสั่งที่จำเป็น |

| อาการ | สาเหตุเชิงกลไก (ทำไมถึงเกิด) | วิธีตรวจ/แก้ |
|---|---|---|
| `cd My Documents` ขึ้น `too many arguments` | ช่องว่างแบ่งคำ `cd` ได้ 2 อาร์กิวเมนต์ | ครอบด้วยเครื่องหมายคำพูดหรือใช้ Tab |
| Linux: `cd documents` ว่าไม่พบ ทั้งที่เห็น Documents | ระบบไฟล์แยกตัวพิมพ์เล็ก/ใหญ่ | `ls` ดูชื่อจริง ใช้ Tab เติม |
| cmd.exe: `cd D:` แล้วยังอยู่ไดรฟ์ C | cmd.exe เก็บโฟลเดอร์ปัจจุบันแยกต่อไดรฟ์ `cd` ไม่สลับไดรฟ์ | พิมพ์ `D:` หรือ `cd /d D:⧵` (PowerShell ใช้ `cd D:` ได้) |
| `ls` ไม่เห็น `.bashrc` | ไฟล์ขึ้นต้นด้วยจุดถูกข้าม | `ls -a` |
| รันสคริปต์ไม่ได้: `command not found` ทั้งที่ไฟล์อยู่ในโฟลเดอร์นี้ | โฟลเดอร์ปัจจุบันไม่อยู่ใน PATH (ตั้งใจเพื่อความปลอดภัย) | รันด้วย `./script.sh` ระบุพาธชัดเจน |
| `echo *.txt` แสดง `*.txt` ตรงๆ | ไม่มีไฟล์ตรงกัน Bash ส่งข้อความเดิมต่อ (หรืออยู่ผิดโฟลเดอร์) | `pwd` และ `ls` ตรวจ |
| คำสั่งทำงานคนละผลเมื่อรันคนละที่ | ใช้ relative path ซึ่งขึ้นกับ cwd | ใช้ absolute path ในสคริปต์ หรือ `cd` ก่อน |
| ใน GUI ไม่เห็นไฟล์ที่ซ่อน | ยังไม่เปิดแสดง hidden | Windows: View → Show → Hidden items ; Linux: Ctrl+H |
| SSH เข้าเซิร์ฟเวอร์แล้วไม่มีเดสก์ท็อป | เซิร์ฟเวอร์ไม่ติดตั้ง GUI (ตั้งใจเพื่อประหยัดทรัพยากรและลดพื้นผิวโจมตี) | ใช้ CLI ตามปกติ |
| ลบแล้วไม่เจอในถังขยะ | CLI ลบผ่านระบบไฟล์ตรงๆ ไม่ผ่านถังขยะที่เป็นฟีเจอร์ของ GUI | กู้จากสำรอง ต่อไปให้ซ้อมด้วย `echo`/`ls` ก่อน |

## 11. แบบฝึกหัดลงมือทำ (บนเครื่องของคุณ)

ใช้ PowerShell หรือ Bash ก็ได้ คำสั่งเหล่านี้อ่านอย่างเดียว

1. `pwd` แล้วเขียนทั้ง absolute path และ relative path ไปยังโฟลเดอร์ `Documents` (หรือโฟลเดอร์อื่นที่มี)
2. `ls -la` (Bash) หรือ `Get-ChildItem -Force` (PowerShell) แล้วหาไฟล์ซ่อน
3. `echo $PATH` (Bash) หรือ `$env:Path -split ';'` (PowerShell) นับว่ามีกี่โฟลเดอร์ และโฟลเดอร์แรกคืออะไร
4. `type ls` / `type cd` (Bash) หรือ `Get-Command ls, cd` (PowerShell) ดูว่าเป็น alias, built-in หรือไฟล์
5. `echo *` (Bash) หรือ `Get-ChildItem | Select-Object -ExpandProperty Name` เทียบกับสิ่งที่คาดไว้
6. สร้างโฟลเดอร์ทดสอบ `mkdir "my test"` แล้วลอง `cd my test` ก่อนและหลังใส่เครื่องหมายคำพูด สังเกตข้อความ
7. รันคำสั่งที่ผิด เช่น `ls /ไม่มีโฟลเดอร์นี้` แล้วดู exit code ด้วย `echo $?` (Bash) หรือ `$?` (PowerShell)

::reveal{question="แนวคำตอบข้อ 3 ข้อ 6 และ 7"}
**ข้อ 3:** แต่ละเครื่องต่างกัน หลักคือโฟลเดอร์แรกสุดมีสิทธิ์ถูกค้นก่อน ตรวจว่าไม่มีโฟลเดอร์ที่ผู้ใช้ทั่วไปเขียนได้อยู่หน้า `/usr/bin` (Linux) หรือหน้า `C:⧵Windows⧵System32` (Windows)
**ข้อ 6:** ก่อนครอบคำสั่ง Bash ขึ้น `too many arguments` ส่วน PowerShell จะรายงานว่าหา path ไม่พบ เพราะแยกอาร์กิวเมนต์ต่างกัน หลังใส่เครื่องหมายคำพูดเข้าโฟลเดอร์ได้
**ข้อ 7:** Bash คืนค่า exit code ไม่ใช่ 0 (มักเป็น 2 สำหรับ `ls` ที่ไม่พบพาธ) ส่วน PowerShell `$?` เป็น `False`
::

## 12. โจทย์ตรวจความเข้าใจและคำนวณ

::reveal{question="โจทย์ 1: ตอนนี้อยู่ที่ /var/log/nginx ในฐานะผู้ใช้ sam ต้องการเข้า Music ในโฮมของ sam ควรใช้ cd Music, cd ~/Music, cd /Music หรือ cd ../Music"}
คือ `cd ~/Music` เพราะ `~` ขยายเป็นโฮมของ sam (`/home/sam`) ตัวอื่น: `cd Music` ไปหา `/var/log/nginx/Music`, `cd /Music` ไปหาที่ราก, `cd ../Music` ไปหา `/var/log/Music` ทั้งสามไม่ใช่ที่ต้องการ
::

::reveal{question="โจทย์ 2: เขียน relative path จาก /home/sam/projects/web/src ไปยัง /home/sam/music/rock"}
LCA คือ /home/sam ; จาก src ถอยขึ้นไปถึง sam ต้อง 3 ชั้น (src → web → projects → sam) ; ลงไป music/rock ดังนั้น `../../../music/rock` ตรวจโดยเดินทีละ `..`: src → web → projects → sam แล้วลง music → rock ถูกต้อง
::

::reveal{question="โจทย์ 3: โฟลเดอร์มีไฟล์ a.txt b.txt notes.md และโฟลเดอร์ My Docs คำสั่ง rm * จะส่งอาร์กิวเมนต์กี่ตัวให้ rm และคำสั่ง rm My Docs ส่งกี่ตัว ต่างกันอย่างไร"}
rm * : เชลล์ขยาย * เป็นทุกชื่อที่ไม่ขึ้นต้นด้วยจุด จึงได้ 4 อาร์กิวเมนต์ (a.txt, b.txt, notes.md และ My Docs เป็นอาร์กิวเมนต์เดียวเพราะ glob ไม่ตัดแบ่งที่ช่องว่างในชื่อที่ได้มา) ส่วน rm My Docs ส่ง 2 ตัวคือ My กับ Docs ซึ่งผิดเจตนาเพราะชื่อจริงคือ My Docs หนึ่งชื่อ
::

::reveal{question="โจทย์ 4: ตัวแปร DIR ว่างเปล่า แล้วรัน rm -rf $DIR/ ใน Bash เกิดอะไรขึ้น และป้องกันอย่างไร"}
ตัวแปรที่ว่างและไม่ครอบเครื่องหมายคำพูดหายไปเลย เหลือ rm -rf / ซึ่งจะพยายามลบจากราก (ระบบ GNU rm รุ่นใหม่มีกลไกกันค่าเริ่มต้น แต่ไม่ควรพึ่ง) ป้องกันด้วยการตรวจว่าตัวแปรไม่ว่างก่อนใช้ (เช่น ${DIR:?} ให้หยุดทำงานถ้าว่าง) และครอบตัวแปรด้วย "..." รวมถึงซ้อมด้วย echo ก่อนเสมอ
::

::reveal{question="โจทย์ 5: ทำไมสร้างโปรแกรมชื่อ cd แยกเป็นไฟล์แล้วใช้เปลี่ยนโฟลเดอร์ของเชลล์ไม่ได้"}
เพราะ cwd เป็นคุณสมบัติของแต่ละโปรเซส เมื่อเชลล์ fork โปรเซสลูกมารัน cd การเปลี่ยน cwd เกิดกับลูกซึ่งจบทันที เชลล์แม่ไม่เปลี่ยน cd จึงต้องเป็นคำสั่งในตัว (built-in) ที่ทำงานในโปรเซสเชลล์เอง
::

::reveal{question="โจทย์ 6: ทำไม Linux ไม่ผิดที่มีทั้ง Report.txt และ report.txt ในโฟลเดอร์เดียว แต่ Windows ปกติสร้างไม่ได้"}
Linux ถือว่าชื่อเป็นลำดับไบต์ ตัวพิมพ์ต่างกันคือชื่อต่างกัน ส่วน Windows ปกติเปรียบเทียบชื่อโดยไม่แยกตัวพิมพ์ จึงมองเป็นชื่อเดียวกัน (มีข้อยกเว้น เช่น โฟลเดอร์ที่ตั้งให้แยกตัวพิมพ์ใน WSL) ผลคือโปรเจกต์ที่ย้ายจาก Linux ไป Windows อาจชนกันได้
::

::reveal{question="โจทย์ 7: เมื่อไรควรใช้ GUI และเมื่อไรควรใช้ CLI ยกตัวอย่างอย่างละสองงาน พร้อมเหตุผลเชิงกลไก"}
GUI: เลือกรูปไปแนบอีเมล (ต้องเห็นภาพ), หาไฟล์ที่ยังไม่รู้ว่าอยู่ไหน (ต้องการ discoverability) ; CLI: เปลี่ยนชื่อไฟล์ 500 ไฟล์ (ทำซ้ำได้ด้วยบรรทัดเดียว), ตรวจเซิร์ฟเวอร์ผ่าน SSH (ไม่มีหน้าจอกราฟิก และใช้แบนด์วิดท์ต่ำ) เหตุผลหลักคือ GUI ให้การค้นพบ CLI ให้ความแม่น ความเร็ว และความสามารถในการทำซ้ำเป็นสคริปต์
::

## สรุป

- **GUI และ CLI เป็นโปรแกรม** ที่ขอบริการจาก kernel เหมือนกัน จึงเห็นไฟล์ชุดเดียวกัน เลือกตามงาน: ค้นพบ→GUI, แม่น/ซ้ำ/ระยะไกล→CLI
- **เชลล์ = วงจร** อ่าน → แยกคำ → ขยาย → หาโปรแกรมใน PATH → fork/exec → exit code ; `cd` เป็นคำสั่งในตัวเพราะ cwd เป็นของแต่ละโปรเซส
- **kernel แปล path ทีละส่วน** จากรากหรือ cwd ; `.` และ `..` เป็นรายการจริงในไดเรกทอรี ; คำนวณ relative path ด้วย LCA
- **โปรแกรมเห็น argv ไม่ใช่บรรทัด:** ช่องว่างแบ่งคำ ครอบด้วยคำพูดเมื่อต้องการ 1 ชิ้น `*` ถูกเชลล์ขยาย ตัวแปรที่ไม่ครอบคำพูดถูกแยกคำซ้ำ (ต้นเหตุของการลบผิดชิ้น)
- **PATH เรียงลำดับ** และเป็นประเด็นความปลอดภัย ; **PowerShell ส่งออบเจ็กต์ Bash ส่งข้อความ**
- **ก่อนลบ/เปลี่ยน ให้ดูก่อน:** `pwd`, `ls`, `echo *` ; ไม่ใส่ความลับในอาร์กิวเมนต์ ; ไม่รันคำสั่งที่ยังไม่ได้อ่าน
- บทถัดไป (โมดูล 2): คำสั่งจัดการไฟล์ (CRUD) บนแนวคิดที่ได้ในบทนี้
