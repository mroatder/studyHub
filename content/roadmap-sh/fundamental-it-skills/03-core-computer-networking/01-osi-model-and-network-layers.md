## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายได้ว่า **ทำไม** ต้องแบ่งเครือข่ายเป็นชั้น (abstraction, modularity, interface/service/protocol) ไม่ใช่แค่ท่องชื่อ 7 ชั้น
2. อธิบายหน้าที่ของแต่ละชั้นและระบุ **PDU ที่อยู่ของมัน** (data, segment, packet, frame, bit) พร้อม header field สำคัญจริง
3. ไล่ **encapsulation / de-encapsulation** ทีละขั้น และ **คำนวณ overhead กับประสิทธิภาพ** บน Ethernet (เช่น 94.9%)
4. อธิบายได้ว่าเฟรมที่ข้าม router เปลี่ยนอะไรบ้าง (MAC เปลี่ยนทุกเฮป, IP คงเดิม, TTL ลดลง)
5. อธิบายการทำงานของ switch (MAC learning/flooding) และ router (routing table, longest-prefix match) ได้
6. อธิบาย CRC ว่าตรวจข้อผิดพลาดอย่างไร และทำไมเลเยอร์ 2 มี trailer
7. เทียบ OSI กับ TCP/IP และบอกได้ว่าทำไม OSI เป็น "ภาษากลาง" ทั้งที่อินเทอร์เน็ตรัน TCP/IP
8. แก้ปัญหาแบบ bottom-up โดยเลือกคำสั่งที่ตรวจแต่ละชั้นได้
9. จับคู่การโจมตีกับชั้นที่เกิด และเสนอการป้องกันแบบหลายชั้น (defense in depth)

## สรุปสั้น (TL;DR)

เครือข่ายซับซ้อนเกินกว่าจะออกแบบเป็นก้อนเดียว วิศวกรจึง **แบ่งเป็นชั้น** แต่ละชั้นให้บริการแก่ชั้นบน โดยใช้บริการของชั้นล่าง และคุยกับ "เพื่อนร่วมชั้น" ปลายทางผ่าน header ของตัวเอง

| ชั้น | ชื่อ | PDU | ตัวอย่าง | อุปกรณ์ |
|---|---|---|---|---|
| 7 | Application | data | HTTP, DNS, SMTP | – |
| 6 | Presentation | data | UTF-8, TLS, การบีบอัด | – |
| 5 | Session | data | การจัดการ session | – |
| 4 | Transport | segment / datagram | TCP, UDP (พอร์ต) | firewall แบบ stateful |
| 3 | Network | packet | IP (ที่อยู่ IP, TTL) | router |
| 2 | Data Link | frame | Ethernet (MAC, CRC) | switch |
| 1 | Physical | bit | สายทองแดง ไฟเบอร์ คลื่นวิทยุ | hub, สาย, NIC |

จำ: "All People Seem To Need Data Processing" (Application ลงไป Physical) และกฎการแก้ปัญหา: **ตรวจจากล่างขึ้นบน**

## เปรียบเทียบกับชีวิตจริง

การส่งจดหมายสำคัญระหว่างบริษัท

| ในไปรษณีย์ | ในเครือข่าย |
|---|---|
| ผู้บริหารเขียนเนื้อหาจดหมาย | ชั้น 7: ข้อมูลของแอป |
| เลขาจัดรูปแบบ แปลภาษา ปิดผนึกซองลับ | ชั้น 6: การเข้ารหัส/แปลงรูปแบบ |
| ใส่ซองใหญ่ ระบุเลขที่แฟ้ม แยกหลายซองถ้าเยอะ และตามว่าถึงครบ | ชั้น 4: segment, พอร์ต, ส่งซ้ำ |
| ติดที่อยู่ปลายทางสุดท้าย (บ้านเลขที่ ถนน จังหวัด) | ชั้น 3: IP address (ระดับ "ข้ามเมือง") |
| คนขับรถประจำเส้นทางส่งจากสาขานี้ไปสาขาถัดไป ติดป้ายสาขาต้นทาง/ปลายทางของ "เที่ยวรถ" | ชั้น 2: MAC address (ระดับ "เฮปเดียว") |
| ถนน ราง เครื่องบิน | ชั้น 1: สัญญาณจริง |

จุดที่อุปมาบอกได้ดี: **ที่อยู่ปลายทางสุดท้ายไม่เปลี่ยนตลอดทาง แต่ป้ายเที่ยวรถเปลี่ยนทุกสาขา** (IP คงเดิม MAC เปลี่ยนทุกเฮป) เราจะพิสูจน์ด้วยตัวเลขในหัวข้อ 5

## 1. ทำไมต้องแบ่งชั้น

### 1.1 ปัญหาที่ต้องแก้

ลองนึกว่าเบราว์เซอร์ต้องรู้ว่าการ์ดเครือข่ายยี่ห้อไหน สายเป็นทองแดงหรือ Wi-Fi ข้อมูลเดินผ่าน router กี่ตัว และจะส่งซ้ำอย่างไรถ้าแพ็กเก็ตหาย ทุกแอปต้องเขียนโค้ดนั้นเองและแก้ทุกครั้งที่ฮาร์ดแวร์เปลี่ยน ไม่มีทางทำได้ วิศวกรรมซอฟต์แวร์แก้ด้วยหลักเดียวกับทั้งสาขา: **นามธรรม (abstraction)** และ **การแยกส่วน (modularity)**

### 1.2 สามคำที่ต้องแยกให้ออก

- **Service (บริการ):** สิ่งที่ชั้น N *ให้* ชั้น N+1 (เช่น "ส่งข้อมูลถึงปลายทางตามลำดับและครบ")
- **Interface (ส่วนต่อประสาน):** วิธีที่ชั้น N+1 *เรียกใช้* บริการนั้น (ในทางปฏิบัติคือ socket API)
- **Protocol (โปรโตคอล):** กฎที่ชั้น N ของเครื่องหนึ่ง *คุยกับ* ชั้น N ของอีกเครื่อง (เช่น TCP ฝั่งส่งคุยกับ TCP ฝั่งรับ)

ผลที่ได้คือแต่ละชั้น **เปลี่ยนการทำงานภายในได้โดยไม่กระทบชั้นอื่น** ตราบที่ service/interface เหมือนเดิม เช่น เปลี่ยนจากสาย Ethernet เป็น Wi-Fi (ชั้น 1–2) เบราว์เซอร์ (ชั้น 7) ไม่ต้องแก้สักบรรทัด นี่คือเหตุผลที่อินเทอร์เน็ตโตจากไม่กี่เครื่องเป็นหลายพันล้านเครื่องได้

### 1.3 หลักการ end-to-end

บทความคลาสสิกของ Saltzer, Reed และ Clark (1984) เสนอว่า ฟังก์ชันที่ต้อง "ถูกต้องจริง" เช่น ข้อมูลครบและไม่เสียหาย ควรตรวจที่ **ปลายทางสองฝั่ง** (ชั้นบน) เพราะการตรวจกลางทางไม่พอและไม่สามารถรับประกันได้อยู่ดี ชั้นล่างทำแค่ "พยายามส่งให้ดีที่สุด" (best effort) อินเทอร์เน็ตจึงออกแบบให้ IP ไม่รับประกันอะไรเลย แล้วให้ TCP ที่ปลายทางสร้างความน่าเชื่อถือขึ้นมา แนวคิดนี้ทำให้เครือข่ายกลางทางเรียบง่ายและถูก เป็นเหตุผลที่อินเทอร์เน็ตขยายได้

### 1.4 ที่มา: OSI เทียบ TCP/IP

**OSI (Open Systems Interconnection)** เป็นมาตรฐานของ ISO (ISO 7498) เสนอ 7 ชั้นเป็นกรอบกลางเพื่อให้ระบบของผู้ผลิตต่างรายคุยกันได้ ส่วน **TCP/IP** เกิดจากโครงการวิจัยของสหรัฐ (ARPANET) และถูกนำไปใช้จริงก่อน เมื่ออินเทอร์เน็ตแพร่หลาย TCP/IP ชนะในทางปฏิบัติ แต่คำศัพท์ของ OSI (ชั้น 1–7) กลายเป็นภาษากลางที่วิศวกรใช้ทุกวัน เช่น "ปัญหาชั้น 1" หรือ "firewall ชั้น 7" ดังนั้นเราเรียนทั้งสอง: OSI เพื่อภาษาและกรอบวิเคราะห์ TCP/IP เพื่อสิ่งที่ทำงานจริง

## 2. เจ็ดชั้นของ OSI ในรายละเอียด

### 2.1 ชั้น 7 Application: ไม่ใช่ตัวแอป แต่คือโปรโตคอลของแอป

ชั้นนี้คือกฎการสนทนาระดับแอป เช่น HTTP กำหนดว่าคำขอเป็นข้อความ `GET /index.html HTTP/1.1` และตอบกลับด้วยรหัสสถานะ `200 OK` เบราว์เซอร์เป็นโปรแกรมที่ *ใช้* HTTP แต่ตัวมันเองไม่ใช่ชั้น 7 (คำถามสอบที่ผิดบ่อย) โปรโตคอลชั้นนี้ที่พบบ่อย: HTTP/HTTPS (เว็บ), DNS (แปลงชื่อเป็น IP), SMTP/IMAP (อีเมล), SSH, FTP

### 2.2 ชั้น 6 Presentation และชั้น 5 Session

ชั้น 6 แก้ปัญหา **syntax ต่างกัน**: เครื่องหนึ่งใช้ UTF-8 อีกเครื่องใช้ encoding อื่น หรือข้อมูลต้องบีบอัด/เข้ารหัสก่อนส่ง ชั้น 5 จัดการ **บทสนทนา**: เปิด รักษา ปิด และ checkpoint ระหว่างโอนไฟล์ใหญ่

ข้อสังเกตเชิงวิศวกรรม: ในโลกจริง สองชั้นนี้แทบไม่มีโปรโตคอลแยกต่างหาก ฟังก์ชันของมันถูกรวมในไลบรารีของแอปหรือในโปรโตคอลชั้น 7 เอง (เช่น TLS เข้ารหัสระหว่างชั้น 4 กับ 7 และไม่ตรงกับชั้นใดชั้นหนึ่งของ OSI พอดี) นี่คือเหตุผลที่ TCP/IP รวม 5–7 เป็นชั้นเดียว

### 2.3 ชั้น 4 Transport: ถึงโปรแกรมที่ถูกต้อง

IP ส่งถึง *เครื่อง* แต่เครื่องหนึ่งมีโปรแกรมที่ใช้เครือข่ายพร้อมกันหลายตัว (เบราว์เซอร์ อีเมล เพลงออนไลน์) ชั้น 4 ใช้ **หมายเลขพอร์ต (port, 16 บิต: 0–65535)** แยกว่าข้อมูลนี้ของโปรแกรมไหน (**multiplexing/demultiplexing**) การเชื่อมต่อหนึ่งๆ ระบุด้วย **5-tuple** คือ (IP ต้นทาง, พอร์ตต้นทาง, IP ปลายทาง, พอร์ตปลายทาง, โปรโตคอล)

สองโปรโตคอลหลักให้บริการต่างกัน

### 2.4 ชั้น 3 Network: ข้ามเครือข่าย

ชั้นนี้ให้ **ที่อยู่เชิงตรรกะ (IP)** ที่เปลี่ยนได้ตามตำแหน่งในเครือข่าย (ต่างจาก MAC ที่ผูกกับฮาร์ดแวร์) และ **การค้นหาเส้นทาง (routing)** ข้ามหลายเครือข่าย ข้อมูลที่ชั้น 3 เพิ่ม: IP ต้นทาง/ปลายทาง, **TTL (Time To Live)** ที่ router ลดลง 1 ทุกเฮปและทิ้งแพ็กเก็ตเมื่อเป็น 0 กันการวนลูปไม่รู้จบ, และจัดการเมื่อแพ็กเก็ตใหญ่กว่า **MTU** (ขนาดสูงสุดที่ลิงก์หนึ่งส่งได้ ปกติ Ethernet = 1500 ไบต์) ด้วยการแบ่งชิ้น (fragmentation)

### 2.5 ชั้น 2 Data Link: เฮปเดียว

ชั้น 2 รับผิดชอบการส่ง **เฟรม** ระหว่างอุปกรณ์สองตัวที่ *เชื่อมกันโดยตรง* ในเครือข่ายท้องถิ่นเดียวกัน ใช้ **MAC address** (48 บิต เขียนเป็น hex 6 ชุด เช่น `3C:22:FB:1A:09:7E`) ระบุการ์ดเครือข่ายแต่ละตัว (3 ไบต์แรกคือรหัสผู้ผลิต OUI) และเพิ่ม **trailer** ตรวจความผิดพลาด (ดูหัวข้อ 4)

เหตุผลที่ชั้น 2 ต้องแยกจากชั้น 3: ที่อยู่ IP บอก *ปลายทางสุดท้าย* ซึ่งอาจอยู่คนละทวีป แต่การส่งจริงต้องทำทีละเฮปบนลิงก์จริง แต่ละลิงก์ใช้เทคโนโลยีต่างกัน (Ethernet, Wi-Fi, DSL) ชั้น 2 จึงเป็นตัวกลางแปลง "ส่งแพ็กเก็ตนี้ไปเฮปถัดไป" เป็นรูปแบบเฉพาะของลิงก์นั้น

### 2.6 ชั้น 1 Physical: บิตกลายเป็นสัญญาณ

ชั้น 1 ไม่รู้จักความหมายของข้อมูล รู้แค่ส่งบิต กำหนดแรงดันไฟ (สายทองแดง), พัลส์แสง (ไฟเบอร์), หรือคลื่นพาหะ (ไร้สาย), ขั้วต่อ (RJ-45) และอัตราบิต ปัญหาที่พบ: สายขาด หลวม ยาวเกินมาตรฐาน (Ethernet ทองแดงสูงสุด 100 เมตร), สัญญาณรบกวน, ไฟเบอร์โค้งเกิน ผู้ที่ช่วยตรวจ: ไฟ LED ที่พอร์ต (link/activity)

## 3. Encapsulation: ห่อทีละชั้น

เมื่อข้อมูลลงมาแต่ละชั้น ชั้นนั้น **ห่อ** ข้อมูลของชั้นบนไว้เป็น payload แล้วเติม header (และบางชั้นเติม trailer) ของตัวเอง เหมือนใส่จดหมายในซองหลายชั้น หน่วยข้อมูลของแต่ละชั้นเรียก **PDU (Protocol Data Unit)**

| ชั้น | PDU | สิ่งที่ชั้นเติม |
|---|---|---|
| 7–5 | data | ข้อความของแอป (เช่น คำขอ HTTP) |
| 4 | segment (TCP) / datagram (UDP) | พอร์ตต้นทาง/ปลายทาง, หมายเลขลำดับและ ACK, flags, window, checksum |
| 3 | packet | IP ต้นทาง/ปลายทาง, TTL, protocol, header checksum |
| 2 | frame | MAC ปลายทาง/ต้นทาง, EtherType, **FCS** (trailer) |
| 1 | bits | สัญญาณไฟฟ้า/แสง/คลื่น |

ปลายทาง **de-encapsulation** ย้อนกลับ: ชั้น 1 รับบิตประกอบเป็นเฟรม → ชั้น 2 ตรวจ FCS และ MAC ปลายทาง แล้วลอก header/trailer ส่งขึ้น → ชั้น 3 ตรวจ IP ปลายทาง ลอก header → ชั้น 4 ดูพอร์ตปลายทางเพื่อส่งให้โปรแกรมที่ถูกต้อง

### 3.1 คำนวณ overhead: ทำไมส่งข้อมูลน้อยๆ เปลืองมาก

Header ขนาดคงที่ ไม่ขึ้นกับปริมาณข้อมูล (บน Ethernet + IPv4 + TCP แบบไม่มี options)

- Ethernet header 14 + FCS 4 = 18 ไบต์
- IP header = 20 ไบต์
- TCP header = 20 ไบต์ (UDP = 8)
- บนสายยังมี preamble 8 + ช่องว่างระหว่างเฟรม 12 = 20 ไบต์ (ไม่นับเป็นส่วนของเฟรมแต่ใช้เวลาบนสาย)

**MTU = 1500** หมายถึง IP packet (header + payload) ยาวสุด 1500 ไบต์ ดังนั้น ข้อมูลต่อ segment สูงสุดคือ **MSS = 1500 − 20 − 20 = 1460 ไบต์**

ประสิทธิภาพสูงสุดของ TCP ต่อเฟรม = 1460 ÷ (1460 + 20 + 20 + 14 + 4 + 20) = 1460 ÷ 1538 ≈ **94.9%** (นี่คือเหตุผลที่ลิงก์ 1 Gbps ถ่ายไฟล์ได้จริงราว 940 Mbps)

ข้อมูลเล็ก: Ethernet ต้องการเฟรมยาวอย่างน้อย 64 ไบต์ (รวม header และ FCS) ถ้าสั้นกว่าต้องเติม padding เช่น ผู้ใช้พิมพ์ 1 ตัวอักษรผ่าน Telnet: 14 + 20 + 20 + 1 + 4 = 59 ไบต์ → pad เป็น 64 + 20 บนสาย = 84 ไบต์เพื่อส่งข้อมูล 1 ไบต์ ประสิทธิภาพ ≈ 1.2%

ลองปรับขนาดข้อมูลและเลือก TCP/UDP ดูจำนวนเฟรม ไบต์บนสาย และประสิทธิภาพ สังเกตจุดที่ข้อมูลเกิน 1460

## 4. ชั้น 2 ลึกขึ้น: เฟรม, MAC และ CRC

### 4.1 โครงสร้างเฟรม Ethernet II

| ฟิลด์ | ขนาด | ความหมาย |
|---|---|---|
| MAC ปลายทาง | 6 ไบต์ | `FF:FF:FF:FF:FF:FF` = broadcast ถึงทุกเครื่องในเครือข่ายท้องถิ่น |
| MAC ต้นทาง | 6 ไบต์ | การ์ดเครือข่ายผู้ส่ง |
| EtherType | 2 ไบต์ | บอกว่า payload เป็นอะไร: `0x0800` IPv4, `0x86DD` IPv6, `0x0806` ARP |
| Payload | 46–1500 ไบต์ | ถ้าน้อยกว่า 46 ต้อง pad |
| FCS | 4 ไบต์ | CRC-32 ของทั้งเฟรม |

ฟิลด์ **EtherType** และฟิลด์ **protocol** ใน IP header (6 = TCP, 17 = UDP, 1 = ICMP) คือ "ตัวชี้" ที่บอกชั้นล่างว่าจะส่ง payload ขึ้นให้ใคร นี่คือกลไกที่ทำให้ชั้นต่างๆ ซ้อนกันได้โดยไม่ต้องรู้จักกันภายใน

### 4.2 ทำไมมี trailer: CRC

เฟรมอาจเสียระหว่างทางจากสัญญาณรบกวน การตรวจต้องทำ *หลัง* ได้เนื้อหาครบ ผู้ส่งจึงคำนวณค่าตรวจจากทั้งเฟรมแล้วต่อท้าย (trailer) ถ้าวางไว้ต้นเฟรมต้องรู้ก่อนว่าเนื้อหาคืออะไร สิ่งที่ใช้คือ **CRC (Cyclic Redundancy Check)** มองบิตเป็นพหุนามเหนือฟิลด์ 2 และหารด้วยพหุนามตัวสร้าง (generator) เศษที่ได้คือค่า CRC

ตัวอย่างขนาดเล็ก: ข้อมูล `1101` ตัวสร้าง `1011` (x³ + x + 1, ตัวสร้างยาว 4 บิต ได้ CRC 3 บิต)

1. ต่อศูนย์ 3 ตัวท้ายข้อมูล: `1101000`
2. หารแบบ XOR ไล่จากซ้าย (ทุกครั้งที่บิตหน้าเป็น 1 ให้ XOR กับ `1011`):
   - `1101000` → `0110000` → `0011100` → `0001010` → `0000001`
3. เศษ = `001` ส่งเฟรม `1101` + `001` = `1101001`
4. ผู้รับหาร `1101001` ด้วย `1011` ถ้าเศษเป็น `000` ถือว่าไม่พบข้อผิดพลาด

ถ้าบิตหนึ่งพลิกระหว่างทาง ผู้รับจะได้เศษไม่ใช่ศูนย์ เช่น `1100001` → เศษ `011`, `1101011` → เศษ `010` ตรวจพบ ใน Ethernet ใช้ CRC-32 (ตัวสร้าง 33 บิต) ซึ่งตรวจพบข้อผิดพลาดแบบบิตเดียว สองบิต (ในเฟรมขนาดปกติ) และ burst error ที่ยาวไม่เกิน 32 บิตได้ทั้งหมด ส่วนข้อผิดพลาดที่ยาวกว่านั้นพลาดได้ด้วยความน่าจะเป็นราว 1 ใน 2³²

ข้อจำกัดสำคัญที่ต้องรู้: **CRC ตรวจจับความผิดพลาดโดยบังเอิญ ไม่ใช่การโจมตี** ผู้โจมตีแก้ข้อมูลแล้วคำนวณ CRC ใหม่ได้ง่าย การป้องกันการแก้ไขโดยเจตนาต้องใช้ MAC/ลายเซ็นดิจิทัลที่มีคีย์ (บทความปลอดภัยในโมดูลหลัง) เมื่อ CRC ไม่ผ่าน เฟรมถูกทิ้งเงียบๆ ชั้น 2 ไม่ส่งซ้ำ การกู้คืนเป็นหน้าที่ของ TCP ชั้น 4 ตามหลัก end-to-end

## 5. อุปกรณ์กับชั้น: Switch และ Router

อุปกรณ์แต่ละตัวอ่านและตัดสินใจจาก header ของชั้นตัวเองเท่านั้น

| อุปกรณ์ | ชั้น | ดู header อะไร | ตัดสินใจอย่างไร |
|---|---|---|---|
| Hub / repeater | 1 | ไม่ดูอะไร | ขยายสัญญาณส่งออกทุกพอร์ต (ทุกคนได้ยินทุกอย่าง) |
| Switch | 2 | MAC ปลายทาง | ส่งออกเฉพาะพอร์ตที่ MAC นั้นอยู่ |
| Router | 3 | IP ปลายทาง | ค้นตาราง routing เลือก next hop |

### 5.1 Switch เรียนรู้ MAC อย่างไร

Switch มี **MAC address table** (ตารางว่า MAC ไหนอยู่ที่พอร์ตไหน) ที่สร้างเองโดยไม่ต้องตั้งค่า ด้วยกฎ 3 ข้อ

1. **เรียนรู้ (learn):** เมื่อเฟรมเข้ามาที่พอร์ต p จาก MAC ต้นทาง S จดว่า "S อยู่ที่พอร์ต p"
2. **ส่งต่อ (forward):** ถ้า MAC ปลายทางอยู่ในตาราง ส่งออกพอร์ตนั้นพอร์ตเดียว
3. **ท่วม (flood):** ถ้า MAC ปลายทางไม่รู้จัก หรือเป็น broadcast ส่งออก *ทุกพอร์ตยกเว้นพอร์ตที่เข้ามา*

ตัวอย่าง: สี่เครื่อง A, B, C, D ต่อพอร์ต 1–4 ตารางว่างเปล่า A ส่งหา C → switch เรียนรู้ "A = พอร์ต 1", ไม่รู้จัก C จึง flood ไปพอร์ต 2, 3, 4 → C ตอบกลับ A → switch เรียนรู้ "C = พอร์ต 3" และรู้ว่า A อยู่พอร์ต 1 จึงส่งตรงพอร์ต 1 พอร์ตเดียว ต่อจากนี้ A↔C ไม่รบกวน B กับ D ตารางมีอายุจำกัด (ปกติหลักนาที) เพื่อลืมเครื่องที่ย้ายหรือดับ

### 5.2 Router: IP คงเดิม MAC เปลี่ยนทุกเฮป

Router รับเฟรมที่ส่งมาถึง MAC ของตัวเอง ลอกชั้น 2 ออก อ่าน IP ปลายทาง ค้นตาราง routing หา route ที่ตรงที่สุด (**longest-prefix match**: คำนำหน้าเครือข่ายที่ยาวที่สุดที่ตรงชนะ เช่น `10.1.2.0/24` ชนะ `10.1.0.0/16`) ลด TTL ลง 1 คำนวณ IP checksum ใหม่ แล้ว **ห่อเฟรมใหม่** ด้วย MAC ต้นทางของตนและ MAC ปลายทางของ next hop

ตัวอย่างคอมพิวเตอร์ A (192.168.1.10) ส่งถึงเซิร์ฟเวอร์ 203.0.113.5 ผ่าน gateway (R1) และ router R2 แล้วถึงเซิร์ฟเวอร์

| ลิงก์ | MAC ต้นทาง → ปลายทาง | IP ต้นทาง → ปลายทาง | TTL |
|---|---|---|---|
| A → R1 | A → R1 | 192.168.1.10 → 203.0.113.5 | 64 |
| R1 → R2 | R1 → R2 | 192.168.1.10 → 203.0.113.5 | 63 |
| R2 → เซิร์ฟเวอร์ | R2 → เซิร์ฟเวอร์ | 192.168.1.10 → 203.0.113.5 | 62 |

สังเกต: ฝั่ง MAC เปลี่ยนทุกบรรทัด ส่วน IP ไม่เปลี่ยนเลย (นอกกรณีมี NAT ซึ่งบทถัดๆ ไปจะเรียน) และ TTL ลดลงทีละ 1 เหตุที่ A รู้ MAC ของ R1: ใช้โปรโตคอล **ARP** ถามในเครือข่ายท้องถิ่นว่า "ใครคือ 192.168.1.1" (เรียนในบทถัดๆ ไป) A *ไม่ต้อง* รู้ MAC ของเซิร์ฟเวอร์เลย

คำสั่ง `traceroute` (Windows: `tracert`) ใช้ TTL นี้เอง ส่งแพ็กเก็ตที่ TTL = 1, 2, 3... router แต่ละตัวที่ลด TTL เป็น 0 จะตอบ ICMP "Time Exceeded" กลับมา ทำให้เห็น router ทีละเฮป

## 6. OSI เทียบ TCP/IP

อินเทอร์เน็ตจริงรัน TCP/IP 4 ชั้น

| TCP/IP | OSI ที่ตรงกัน | ตัวอย่าง |
|---|---|---|
| Application | 7, 6, 5 | HTTP, DNS, SSH, TLS |
| Transport | 4 | TCP, UDP |
| Internet | 3 | IP, ICMP |
| Network Access (Link) | 2, 1 | Ethernet, Wi-Fi, ไดรเวอร์ NIC |

(บางตำราแบ่ง TCP/IP เป็น 5 ชั้นโดยแยก Link กับ Physical)

OSI ยังสำคัญเพราะเป็น **ภาษากลางในการสื่อสารและวินิจฉัย** ควรรู้ด้วยว่า โลกจริง "ไม่สะอาด" แบบตำรา: TLS อยู่กลางชั้น 4–7, **NAT** แก้ทั้ง IP (ชั้น 3) และพอร์ต (ชั้น 4), **VPN/tunnel** ห่อแพ็กเก็ตทั้งก้อนเป็น payload ของแพ็กเก็ตอื่น (encapsulation ซ้อนกันหลายรอบ), **MPLS** อยู่ "ระหว่าง" ชั้น 2 กับ 3, firewall ชั้น 7 ตรวจเนื้อหา HTTP ได้ ดังนั้นให้ใช้โมเดลเป็นเครื่องมือคิด ไม่ใช่กฎที่ต้องตรงทุกกรณี

## 7. แก้ปัญหาด้วย OSI: ล่างขึ้นบน

บทที่ 8 เรียนวงจรแก้ปัญหา 6 ขั้นและ 3 กลยุทธ์ (top-down, bottom-up, divide and conquer) OSI ให้ "แผนที่" ที่ทำให้กลยุทธ์เหล่านี้เป็นรูปธรรม แต่ละชั้นมีคำถามและคำสั่งตรวจของตัวเอง ไล่จากล่างขึ้นบน เพราะชั้นบนพึ่งชั้นล่าง ถ้าชั้น 1 เสีย การไล่ตรวจ DNS เสียเวลาเปล่า

| ชั้น | คำถาม | ตรวจด้วย (Windows / Linux) |
|---|---|---|
| 1 | สาย/Wi-Fi ต่ออยู่ไหม ไฟ LED ติดไหม | ดู LED, `Get-NetAdapter` / `ip link` (ดู `state UP`, `LOWER_UP`) |

## 8. มุมมองด้าน Security

ชั้นต่างๆ ไม่เพียงเป็นแผนที่ของฟังก์ชัน แต่เป็นแผนที่ของ **พื้นผิวการโจมตี** ผู้โจมตีเลือกชั้นที่การป้องกันอ่อน และผู้ป้องกันที่ดีวางมาตรการ **หลายชั้น (defense in depth)** เพราะการป้องกันชั้นเดียวไม่พอ

| ชั้น | ตัวอย่างการโจมตี | หลักการ | การป้องกัน |
|---|---|---|---|
| 1 | ดักสัญญาณ (tap สาย/ไฟเบอร์), ขโมยหรือตัดสาย, jamming คลื่นวิทยุ | เข้าถึงทางกายภาพ | ควบคุมการเข้าถึงห้อง/ตู้ rack, ปิดพอร์ตที่ไม่ใช้, ไฟเบอร์/การเข้ารหัสลิงก์ |
| 2 | MAC flooding, ARP spoofing, VLAN hopping, rogue access point | switch และ ARP เชื่อใจข้อมูลที่ได้รับโดยไม่ตรวจสอบ | port security, DHCP snooping + Dynamic ARP Inspection, 802.1X, ตั้งค่า VLAN อย่างถูกต้อง |
| 3 | IP spoofing, ICMP flood/smurf, route hijacking | IP ไม่ตรวจสอบต้นทาง | ACL, ตัดแพ็กเก็ตที่ต้นทางปลอม (ingress/egress filtering), IPsec, ตรวจสอบ routing |
| 4 | SYN flood, port scanning, session hijacking | TCP handshake กินทรัพยากรผู้รับ | SYN cookies, firewall แบบ stateful, rate limit, ปิดพอร์ตที่ไม่ใช้ |
| 5–7 | SQL injection, XSS, DNS poisoning, phishing, brute force | แอปเชื่อ input หรือผู้ใช้ | ตรวจสอบ input, WAF, TLS, MFA, อัปเดตแพตช์ |

หลักที่ควรเก็บ

- **ชั้นล่างเสีย ชั้นบนไม่ช่วย:** ถ้าผู้โจมตีทำ ARP spoofing (ชั้น 2) ได้ ดักอ่านทราฟฟิกที่ไม่ได้เข้ารหัสได้ทั้งหมด แม้แอปจะ "ปลอดภัย" การเข้ารหัสชั้นบน (TLS) จึงสำคัญเพราะไม่ต้องเชื่อใจเครือข่ายข้างล่าง
- **CRC ≠ ความปลอดภัย:** ตรวจเฉพาะความผิดพลาดโดยบังเอิญ
- **การดักจับแพ็กเก็ต (packet capture) เปิดโปงทุกชั้น:** เครื่องมืออย่าง Wireshark แสดง header ทุกชั้นของเฟรมเดียวกัน ถูกใช้ทั้งแก้ปัญหาและตรวจจับการโจมตี ใช้เฉพาะเครือข่ายที่คุณได้รับอนุญาต
- **ไฟร์วอลล์ต่างชั้น ตรวจต่างกัน:** แบบกรองแพ็กเก็ต (ชั้น 3–4: IP/พอร์ต) เร็วแต่ไม่เห็นเนื้อหา แบบ stateful จำสถานะการเชื่อมต่อ แบบ application/WAF (ชั้น 7) เห็นเนื้อหาแต่แพงกว่าและตรวจ TLS ไม่ได้ถ้าไม่ถอดรหัส

## 11. ตรวจความเข้าใจ

::reveal{question="อธิบายด้วยคำของตัวเองว่า service, interface และ protocol ต่างกันอย่างไร และทำไมการแยกสามอย่างนี้ทำให้เปลี่ยนจาก Ethernet เป็น Wi-Fi ได้โดยไม่แก้เบราว์เซอร์"}
service คือสิ่งที่ชั้นล่างให้ชั้นบน (เช่น ส่งข้อมูลถึงอีกเครื่อง) interface คือวิธีที่ชั้นบนเรียกบริการนั้น (เช่น socket API) protocol คือกฎที่ชั้นเดียวกันของสองเครื่องใช้คุยกัน เมื่อเปลี่ยน Ethernet เป็น Wi-Fi สิ่งที่เปลี่ยนคือ protocol และการทำงานภายในของชั้น 1–2 แต่ service และ interface ที่ชั้น 3 ได้รับยังเหมือนเดิม เบราว์เซอร์จึงไม่รู้และไม่ต้องแก้
::

::reveal{question="คอมพิวเตอร์รับเฟรมที่ MAC ปลายทางถูกต้อง IP ปลายทางถูกต้อง แต่ไม่มีโปรแกรมฟังพอร์ตปลายทาง การ de-encapsulation ผ่านถึงชั้นไหน และเกิดอะไรขึ้น"}
ผ่านชั้น 1, 2, 3 สำเร็จ (บิตครบ FCS ผ่าน MAC และ IP ตรงกัน) ไปติดที่ชั้น 4 เพราะไม่มีปลายทางให้ส่ง payload ขึ้นไป TCP จะตอบกลับด้วย RST (ผู้ส่งเห็นเป็น Connection refused) ส่วน UDP มักตอบ ICMP Port Unreachable สวิตช์ไม่เกี่ยวข้องเพราะ switch ดูแค่ MAC
::

::reveal{question="ข้อมูลจากแอป 3,000 ไบต์ส่งผ่าน TCP บน Ethernet (MTU 1500) แบ่งเป็นกี่ segment แต่ละเฟรมยาวเท่าไร รวมไบต์บนสายเท่าไร และประสิทธิภาพกี่เปอร์เซ็นต์"}
MSS = 1460 → 3,000 = 1,460 + 1,460 + 80 จึงเป็น 3 segment เฟรม 1 และ 2: 14 + 20 + 20 + 1,460 + 4 = 1,518 ไบต์ (บนสาย +20 = 1,538) เฟรม 3: 14 + 20 + 20 + 80 + 4 = 138 ไบต์ (บนสาย +20 = 158) รวมบนสาย 1,538 × 2 + 158 = 3,234 ไบต์ ประสิทธิภาพ = 3,000 ÷ 3,234 ≈ 92.8%
::

::reveal{question="ทำไมผู้ใช้พิมพ์ 1 ตัวอักษรผ่าน TCP ใช้ประสิทธิภาพต่ำมาก คำนวณให้ดู"}
ข้อมูล 1 ไบต์ + TCP 20 + IP 20 + Ethernet 14 + FCS 4 = 59 ไบต์ ต่ำกว่าขั้นต่ำ 64 จึงเติม pad 5 ไบต์ รวมบนสาย 64 + 20 (preamble และช่องว่าง) = 84 ไบต์ ประสิทธิภาพ = 1 ÷ 84 ≈ 1.2% header และช่องว่างมีขนาดคงที่ จึงควรรวมข้อมูลเล็กๆ ไว้ส่งทีเดียว (เช่น อัลกอริทึม Nagle ของ TCP)
::

::reveal{question="Switch ที่ตารางว่างเปล่าได้รับเฟรมจาก A (พอร์ต 1) ไปหา C ที่ยังไม่เคยคุย switch ทำอะไรบ้าง และเมื่อ C ตอบกลับต่างไปอย่างไร"}
จดว่า A อยู่ที่พอร์ต 1 (learn) เนื่องจากไม่รู้จัก C จึง flood ส่งออกทุกพอร์ตยกเว้นพอร์ต 1 เมื่อ C ตอบกลับ switch จดว่า C อยู่ที่พอร์ตของ C และเนื่องจากรู้แล้วว่า A อยู่พอร์ต 1 จึงส่งตรงพอร์ต 1 พอร์ตเดียว (forward) ไม่ flood อีก
::

::reveal{question="เฟรมจาก 192.168.1.10 ถึง 203.0.113.5 ผ่าน router 2 ตัว ฟิลด์ใดเปลี่ยนและฟิลด์ใดคงเดิมเมื่อเทียบก่อนและหลังข้าม router ตัวแรก"}
เปลี่ยน: MAC ต้นทาง (กลายเป็นของ router) MAC ปลายทาง (กลายเป็นของ next hop) TTL (ลดลง 1) และ checksum ของ IP header (คำนวณใหม่) และ FCS ของเฟรม คงเดิม: IP ต้นทาง IP ปลายทาง พอร์ต และข้อมูลทั้งหมด (ยกเว้นกรณีมี NAT) เพราะ router เปิดชั้น 2 ทิ้ง ตัดสินใจที่ชั้น 3 แล้วสร้างชั้น 2 ใหม่
::

::reveal{question="ใช้ตัวสร้าง 1011 หา CRC ของข้อมูล 1101 (ดูหัวข้อ 4.2) ผู้รับได้รับ 1100001 จะรู้ได้อย่างไรว่าผิด"}
ต่อศูนย์ 3 ตัวได้ 1101000 หารแบบ XOR ได้เศษ 001 ส่ง 1101001 ผู้รับหาร 1101001 ได้เศษ 000 ปกติ แต่ 1100001 (บิตที่ 4 พลิก) หารแล้วได้เศษ 011 ซึ่งไม่ใช่ศูนย์ ผู้รับจึงรู้ว่าเฟรมเสียและทิ้ง CRC ไม่ช่วยแก้ข้อมูลและไม่ป้องกันผู้โจมตีที่คำนวณ CRC ใหม่หลังแก้ข้อมูล
::

::reveal{question="ping gateway ได้ ping 8.8.8.8 ไม่ได้ และ ping 8.8.8.8 ได้แต่เปิดเว็บด้วยชื่อไม่ได้ สองกรณีนี้ชี้ไปที่ชั้นไหนต่างกันอย่างไร"}
กรณีแรก ชั้น 1–3 ในวงท้องถิ่นปกติ ปัญหาอยู่เกิน gateway (ชั้น 3: การ route ออก ISP หรือไฟร์วอลล์ขาออก) ใช้ tracert หาเฮปที่หยุด กรณีที่สอง ชั้น 1–4 ปกติ (ส่งข้อมูลด้วย IP ได้) ปัญหาอยู่ที่ชั้น 7 คือ DNS แปลงชื่อเป็น IP ไม่ได้ ตรวจ DNS server ที่ตั้ง
::

::reveal{question="Connection refused กับ Connection timed out ต่างกันอย่างไรในแง่การวินิจฉัย"}
refused: แพ็กเก็ตไปถึงเครื่องปลายทาง และปลายทางตอบปฏิเสธ (RST) แปลว่าเส้นทางเครือข่ายปกติ แต่ไม่มีโปรแกรมฟังพอร์ตนั้น (ปัญหาชั้น 4/บริการ) timed out: ไม่มีคำตอบ เป็นไปได้ว่าไฟร์วอลล์ทิ้งแพ็กเก็ตเงียบๆ เส้นทางเสีย หรือเครื่องปลายทางดับ ต้องตรวจต่อด้วย traceroute และกฎไฟร์วอลล์
::

::reveal{question="ผู้โจมตีทำ ARP spoofing ในออฟฟิศ ชั้นไหนถูกโจมตี ทำไมแอปที่ใช้ HTTP ธรรมดาจึงเสี่ยง และ HTTPS ช่วยได้แค่ไหน"}
ชั้น 2 เพราะ ARP ผูก IP กับ MAC โดยไม่ตรวจสอบ ผู้โจมตีทำให้เหยื่อส่งเฟรมมาที่เครื่องตนแทน gateway แล้วดักอ่านหรือแก้ HTTP ธรรมดาไม่เข้ารหัส จึงเห็นทุกอย่าง HTTPS (TLS) ทำให้ผู้ดักอ่านเนื้อหาไม่ได้ และตรวจจับการปลอมแปลงได้ด้วยใบรับรอง แต่ผู้โจมตียังเห็นข้อมูลเมทาดาทา เช่น ปลายทางและปริมาณ และยังทำให้ล่มได้ การป้องกันที่ต้นเหตุคือ Dynamic ARP Inspection / DHCP snooping บน switch
::

## 12. แบบฝึกหัด

ใช้เครื่องของตัวเอง คำสั่งอ่านอย่างเดียวหรือผลกระทบน้อย

1. **ดู 3 ชั้นของเครื่องคุณ:** จด MAC (Windows: `ipconfig /all` ช่อง Physical Address, Linux: `ip link`) IP, subnet mask และ default gateway แล้วรัน `arp -a` หา MAC ของ gateway ระบุว่าข้อมูลแต่ละอย่างอยู่ชั้นไหน
2. **หา MTU ของเส้นทาง:** ส่ง ping แบบห้ามแบ่งชิ้น Windows: `ping 8.8.8.8 -f -l 1472` Linux: `ping -M do -s 1472 8.8.8.8` ถ้าสำเร็จ ลองเพิ่มทีละน้อยจนล้มเหลว จด ขนาดสูงสุด + 28 (IP 20 + ICMP 8) = MTU ของเส้นทาง (ปกติ 1500) อธิบายว่าทำไมต้อง +28
3. **ดู TTL ลดลง:** รัน `tracert 8.8.8.8` (Linux: `traceroute 8.8.8.8`) นับจำนวนเฮป อธิบายว่า tracert ใช้ TTL อย่างไรให้เห็นแต่ละเฮป
4. **ดู encapsulation ด้วยตา (ถ้ามี Wireshark):** จับแพ็กเก็ตขณะ `ping` เฉพาะเครือข่ายของคุณ เลือกหนึ่งเฟรมแล้วขยายแต่ละชั้นใน packet details (Frame, Ethernet II, IPv4, ICMP) จดค่า EtherType, protocol, TTL, ขนาด header
5. **ไล่ล่างขึ้นบน:** ใช้ตาราง 7 หัวข้อด้านบน ตรวจเครื่องของคุณทีละชั้น (ชั้น 1–3 แล้วลอง `Test-NetConnection google.com -Port 443` หรือ `nc -zv google.com 443`) บันทึกผลทุกชั้น
6. **เขียน ticket:** สมมติ "เข้าเว็บภายในบริษัทไม่ได้ ทั้งที่ ping เซิร์ฟเวอร์ได้" เขียน ticket 4 ส่วน (อาการ ชั้นที่สงสัย การตรวจ ขั้นแก้) โดยระบุว่า ping ได้บอกอะไรและไม่บอกอะไร

::reveal{question="แนวคำตอบข้อ 2 (หา MTU)"}
ping -l / -s กำหนดขนาด payload ของ ICMP ซึ่งถูกห่อด้วย ICMP header 8 ไบต์และ IP header 20 ไบต์ จึงรวมเป็น payload + 28 ไบต์ ถ้า 1472 + 28 = 1500 ผ่านโดยไม่แบ่งชิ้น แปลว่า MTU อย่างน้อย 1500 ถ้า 1473 ล้มเหลวด้วยข้อความต้องแบ่งชิ้นแต่ห้ามแบ่ง (Packet needs to be fragmented but DF set) แปลว่า MTU = 1500 พอดี ถ้าเส้นทางมี VPN/PPPoE ค่าอาจเป็น 1492 หรือต่ำกว่า ใช้เป็นหลักฐานเวลาเว็บบางหน้าค้าง
::

## 13. สรุป

- เครือข่ายถูกแบ่งเป็นชั้นเพื่อ **abstraction และ modularity**: แต่ละชั้นให้ **service** แก่ชั้นบน ผ่าน **interface** และคุยกับชั้นเดียวกันของปลายทางด้วย **protocol** ตามหลัก end-to-end ชั้นล่างทำแค่ส่งอย่างดีที่สุด ความถูกต้องรับประกันที่ปลายทาง
- OSI 7 ชั้น (Application, Presentation, Session, Transport, Network, Data Link, Physical) เป็นภาษากลาง ส่วนอินเทอร์เน็ตจริงรัน TCP/IP 4 ชั้น
- **Encapsulation** เติม header (ชั้น 2 เติม trailer FCS ด้วย) เป็น segment → packet → frame → bit และ de-encapsulation ย้อนกลับ header ขนาดคงที่ทำให้ส่งข้อมูลเล็กเปลืองมาก (TCP เต็มเฟรม 94.9%, 1 ไบต์ ~1.2%)
- **ชั้น 2** ทำงานเฮปเดียวด้วย MAC และ CRC ตรวจความผิดพลาดโดยบังเอิญ (ไม่ใช่การโจมตี) switch เรียนรู้ MAC และ flood เมื่อไม่รู้ปลายทาง
- **ชั้น 3** ทำงานข้ามเครือข่ายด้วย IP: router ลอกชั้น 2 ค้น routing table (longest-prefix) ลด TTL และห่อชั้น 2 ใหม่ ดังนั้น **IP คงเดิม MAC เปลี่ยนทุกเฮป**
- **ชั้น 4** ใช้พอร์ตส่งถึงโปรแกรมที่ถูกต้อง TCP เชื่อถือได้ UDP เร็วแต่ไม่รับประกัน
- แก้ปัญหาแบบ **ล่างขึ้นบน**: ตรวจชั้น 1 → 7 แยก refused กับ timeout ได้จะลดสมมติฐานเร็ว
- Security: ทุกชั้นมีการโจมตีเฉพาะ (ARP spoofing ชั้น 2, IP spoofing ชั้น 3, SYN flood ชั้น 4, injection ชั้น 7) ต้องป้องกันหลายชั้น และใช้การเข้ารหัสที่ชั้นบนเพราะเชื่อใจเครือข่ายข้างล่างไม่ได้
