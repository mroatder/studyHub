## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. นิยาม **โปรโตคอล** ด้วย 3 องค์ประกอบ (รูปแบบข้อความ ความหมาย ลำดับเวลา) และบอกได้ว่าโปรโตคอลแต่ละตัวอยู่ชั้นไหน
2. อธิบาย TCP ในเชิงกลไก: three-way handshake, sequence/ack เป็นหมายเลข **ไบต์**, การส่งซ้ำ, flow control, congestion control, การปิดการเชื่อมต่อ
3. **คำนวณ** ผลของ window และ RTT ต่อความเร็ว (bandwidth-delay product) และจำนวน RTT ก่อนได้ข้อมูลแรกของหน้าเว็บ
4. เลือก TCP หรือ UDP ได้ด้วยเหตุผลเชิงระบบ รวมถึงเข้าใจว่าทำไม HTTP/3 (QUIC) ใช้ UDP
5. อธิบายโครงสร้างข้อความ HTTP, ความหมายรหัสสถานะ และการทำงานของ TLS (ยืนยันตัวตน เข้ารหัส ตรวจความสมบูรณ์)
6. เปรียบเทียบคู่ปลอดภัย/ไม่ปลอดภัย (HTTP/HTTPS, Telnet/SSH, FTP/SFTP) และโปรโตคอลอีเมล (SMTP, IMAP, POP3) พร้อมบทบาท SPF/DKIM/DMARC
7. ไล่กระบวนการของ DNS (recursive และ iterative), DHCP (DORA), ARP, ICMP ทีละข้อความ
8. จับคู่การโจมตีกับโปรโตคอล (SYN flood, DNS poisoning, ARP spoofing, rogue DHCP) พร้อมมาตรการป้องกัน
9. วินิจฉัยอาการ IT Support โดยระบุโปรโตคอลที่เกี่ยวข้องและคำสั่งที่ตรวจได้

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | โปรโตคอล |
|---|---|
| โทรหาคนก่อนส่งของ ให้เขาพร้อมรับ ส่งของแล้วขอใบเซ็นรับ ถ้าไม่มีใบเซ็นก็ส่งใหม่ | **TCP** (handshake, ACK, ส่งซ้ำ) |
| ตะโกนข่าวผ่านโทรโข่ง ใครได้ยินก็ได้ยิน ไม่รอยืนยัน | **UDP** |
| ถามเบอร์โทรจากสมุดโทรศัพท์ (หาในสมุดหน้าเหลือง → หมวด → ร้าน) | **DNS** |
| ไปเคาน์เตอร์ขอบัตรเข้าห้องพักชั่วคราว ได้ห้องและกฎ เมื่อครบเวลาต้องมาต่อ | **DHCP** (lease) |
| ตะโกนถามในห้องว่า ใครชื่อสมชาย เจ้าตัวตอบ ‘ผมอยู่โต๊ะนี้’ | **ARP** |
| ส่งจดหมายใส่ซองปิดผนึก มีตราประทับยืนยันผู้ส่ง | **HTTPS/TLS** |
| ส่งโปสการ์ด ใครผ่านมาก็อ่านได้ | **HTTP/Telnet/FTP** แบบไม่เข้ารหัส |

## 0. โปรโตคอลคืออะไรในเชิงวิศวกรรม

โปรโตคอลกำหนด 3 อย่าง (ตามตำราเครือข่ายมาตรฐาน)

- **Syntax:** รูปแบบ เช่น ข้อความ HTTP เป็นข้อความที่มี request line, header, บรรทัดว่าง, body หรือ header ของ TCP มีฟิลด์ใดกี่บิต
- **Semantics:** ความหมาย เช่น flag SYN แปลว่า ‘ขอเริ่มการเชื่อมต่อ’ รหัส 404 แปลว่า ‘ไม่พบทรัพยากร’
- **Timing/Sequencing:** ลำดับและเวลา เช่น ต้องส่ง SYN ก่อน ถ้าไม่มี ACK ภายในเวลาที่กำหนดต้องส่งซ้ำ

โปรโตคอลที่ใช้กับอินเทอร์เน็ตกำหนดเป็นเอกสารเปิดสาธารณะชื่อ **RFC (Request for Comments)** ดูแลโดย IETF ทำให้ผู้ผลิตต่างรายทำเครื่องที่คุยกันได้ เช่น TCP = RFC 9293, HTTP = RFC 9110 ถ้าแอปบนมือถือกับเซิร์ฟเวอร์คุยกันได้ ก็เพราะทั้งคู่ทำตามเอกสารเดียวกัน

อ่านร่วมกับบทที่แล้ว: protocol คือ ‘กฎคุยระหว่างเพื่อนร่วมชั้น’ และแต่ละตัวอยู่ในชั้นของตน เช่น TCP/UDP ชั้น 4, DNS/HTTP/SMTP ชั้น 7, ARP ใกล้ชั้น 2–3, ICMP ชั้น 3

## 1. ชั้นขนส่ง: UDP และ TCP

IP (ชั้น 3) ส่งแพ็กเก็ตถึง *เครื่อง* แบบ best-effort ไม่รับประกันว่าถึง ไม่ซ้ำ หรือเรียงลำดับ ชั้นขนส่งเติมสองสิ่ง: **พอร์ต** เพื่อแยกโปรแกรม และ (ถ้าเลือก TCP) **ความน่าเชื่อถือ** ซึ่งเป็นไปตามหลัก end-to-end ที่เรียนแล้ว

### 1.1 UDP: บางที่สุดเท่าที่เป็นไปได้

header ของ UDP มีเพียง **8 ไบต์** (ฟิลด์ละ 16 บิต): พอร์ตต้นทาง, พอร์ตปลายทาง, ความยาว, checksum ไม่มีหมายเลขลำดับ ไม่มี ACK ไม่มีสถานะการเชื่อมต่อ ผู้ส่งยิงดาตาแกรมออกไปแล้วจบ

ข้อดี: ไม่มีค่าใช้จ่ายในการตั้งการเชื่อมต่อ (ไม่เสีย RTT) header เล็ก ไม่มีการรอส่งซ้ำที่ทำให้ล่าช้า และส่งแบบ broadcast/multicast ได้ ข้อเสีย: แอปต้องจัดการเอง ถ้าต้องการความน่าเชื่อถือ ใช้กับ DNS (คำถามสั้น ส่งซ้ำเองได้), DHCP, เสียง/วิดีโอสด (ข้อมูลเก่าไม่มีประโยชน์แล้ว), เกมออนไลน์, และ **QUIC** (ฐานของ HTTP/3) ที่สร้างความน่าเชื่อถือเองบน UDP

### 1.2 TCP: สร้างท่อที่เชื่อถือได้บนเครือข่ายที่เชื่อถือไม่ได้

TCP ให้แอปเห็น **สายไบต์ที่เชื่อถือได้ ครบ ตามลำดับ ไม่ซ้ำ** ทั้งที่ข้างล่างอาจสูญหาย ซ้ำ หรือสลับลำดับ เพื่อให้ทำได้ header ขนาดอย่างน้อย 20 ไบต์ มีฟิลด์สำคัญ

| ฟิลด์ | ขนาด | หน้าที่ |
|---|---|---|
| Source / Destination port | 16 + 16 บิต | ระบุปลายทางของการเชื่อมต่อ |
| Sequence number | 32 บิต | **หมายเลขของไบต์แรก** ใน segment นี้ในสายไบต์ |
| Acknowledgment number | 32 บิต | หมายเลขไบต์ **ถัดไป** ที่ผู้ส่ง ACK ต้องการ (ยืนยันทุกไบต์ก่อนหน้านั้น) |
| Flags | SYN, ACK, FIN, RST, PSH ฯลฯ | ควบคุมสถานะการเชื่อมต่อ |
| Window | 16 บิต | พื้นที่บัฟเฟอร์ว่างของผู้รับ (flow control) |
| Checksum | 16 บิต | ตรวจความผิดพลาด |

จุดที่หลายคนเข้าใจผิด: sequence/ack นับเป็น **ไบต์ ไม่ใช่นับ segment** เช่น ส่งข้อมูล 500 ไบต์ที่ seq = 1001 ผู้รับตอบ ack = 1501 ('ได้ถึงไบต์ 1500 ครบแล้ว ต้องการ 1501 ต่อ') และ ack เป็นแบบ **สะสม (cumulative)** ยืนยันทุกอย่างก่อนหน้า

#### Three-way handshake

ก่อนส่งข้อมูล สองฝั่งต้องตกลง **หมายเลขลำดับเริ่มต้น (ISN)** ของตนและยืนยันว่าอีกฝั่งอยู่จริงและรับได้ ใช้ข้อความ 3 ชุด: **SYN**, **SYN-ACK**, **ACK** กดดูทีละขั้น สังเกตเลข seq/ack ที่เพิ่มทีละ 1 (SYN นับเป็น 1 หมายเลข) และจุดที่ข้อมูลจริงเริ่มส่ง

เหตุที่ต้อง *สามทาง* ไม่ใช่สองทาง: ต้องให้ ‘ทั้งสองฝั่ง’ พิสูจน์ว่ารับสัญญาณของอีกฝั่งได้ และยืนยัน ISN ของตัวเองกับอีกฝั่ง ไม่ให้ SYN เก่าที่ค้างในเครือข่ายสร้างการเชื่อมต่อผีขึ้นมา

#### ความน่าเชื่อถือ: ACK การส่งซ้ำ และหน้าต่างเลื่อน

ผู้ส่งไม่หยุดรอ ACK ทุก segment เพราะจะช้ามาก (1 segment ต่อ 1 RTT) แต่ปล่อยได้หลาย segment ก่อน ACK กลับ จำนวนข้อมูลที่ส่งได้โดยยังไม่ถูก ACK เรียก **window** (หน้าต่างเลื่อน sliding window) เมื่อได้ ACK หน้าต่างเลื่อนไปข้างหน้า ถ้า segment หาย ผู้รับจะตอบ ACK ซ้ำเลขเดิม ('ยังรอไบต์นี้') เมื่อผู้ส่งเห็น **duplicate ACK 3 ครั้ง** (fast retransmit) หรือหมดเวลา **RTO (retransmission timeout)** ก็ส่งชิ้นที่หายซ้ำ

ลองเล่น เลือก TCP/UDP และ segment ที่หาย แล้วเทียบ สังเกตว่า TCP ใช้เวลาเพิ่มเพื่อให้ข้อมูลครบ ส่วน UDP จบเร็วกว่าแต่ข้อมูลขาด

> **RTO ปรับตามเครือข่าย (RFC 6298):** TCP วัด RTT แล้วคำนวณค่าเฉลี่ยเรียบ SRTT และความแปรปรวน RTTVAR แล้วตั้ง **RTO = SRTT + 4 × RTTVAR** (ขั้นต่ำเป็นไปตามมาตรฐาน 1 วินาที ส่วนระบบจริงอย่าง Linux ใช้ค่าต่ำสุด 200 ms) ตัวอย่าง SRTT = 100 ms, RTTVAR = 20 ms → RTO ≈ 180 ms ก่อนปรับขั้นต่ำ ตั้งสั้นไปจะส่งซ้ำโดยไม่จำเป็น ตั้งยาวไปจะช้าเมื่อมีการสูญหายจริง

#### Flow control และ congestion control

TCP ควบคุมความเร็วสองแบบที่ต่างกัน

- **Flow control** ป้องกัน *ผู้รับ* ล้น: ผู้รับบอกพื้นที่ว่างผ่านฟิลด์ window (rwnd) ผู้ส่งต้องไม่ส่งเกิน
- **Congestion control** ป้องกัน *เครือข่ายกลางทาง* ล้น: ผู้ส่งตั้งหน้าต่างความแออัด **cwnd** ของตนเอง ใช้ `min(rwnd, cwnd)` เป็นขีดจำกัดจริง วิธีคลาสสิก:
  1. **Slow start:** เริ่ม cwnd = 1 MSS แล้วเพิ่มเท่าตัวทุก RTT (1, 2, 4, 8, ...) จนถึงเกณฑ์ ssthresh หรือเกิดการสูญหาย
  2. **Congestion avoidance:** เพิ่มช้าลงเป็น +1 MSS ต่อ RTT
  3. เมื่อพบการสูญหาย (ตีความว่าเครือข่ายแออัด) ลด cwnd ลงครึ่งหนึ่ง (หรือเริ่มใหม่เมื่อ timeout) แล้วค่อยๆ เพิ่มอีก

   ผลคือทราฟฟิกของหลายการเชื่อมต่อแบ่งลิงก์กันอย่างเป็นธรรมโดยประมาณ โดยไม่มีใครสั่งการจากส่วนกลาง (ตัวอัลกอริทึมจริงปัจจุบัน เช่น CUBIC และ BBR ซับซ้อนกว่านี้ แต่หลักการนี้เป็นฐาน)

#### คำนวณ: ทำไมเส้นทางไกลถึงช้า (Bandwidth-Delay Product)

ปริมาณข้อมูลที่ ‘อยู่บนสาย’ พร้อมกันได้เต็มท่อ = **bandwidth × RTT** (BDP) ถ้า window เล็กกว่า BDP ผู้ส่งจะต้องหยุดรอ ACK ท่อไม่เต็ม

ตัวอย่าง: ลิงก์ 100 Mbps, RTT 50 ms

- BDP = (100 × 10⁶ ÷ 8 ไบต์/วินาที) × 0.05 วินาที = **625,000 ไบต์ ≈ 625 KB**
- ถ้า window สูงสุดแค่ 64 KB (65,535 ไบต์ ซึ่งเป็นขีดจำกัดของฟิลด์ window 16 บิต หากไม่ใช้ window scaling): throughput สูงสุด = window ÷ RTT = 65,535 ÷ 0.05 ≈ 1.31 MB/s ≈ **10.5 Mbps** ใช้ท่อ 100 Mbps แค่ราว 10%

นี่คือเหตุผลที่มีตัวเลือก **window scaling** (RFC 7323) ที่ขยาย window หลาย GB และที่ ‘ดาวน์โหลดไฟล์จากต่างประเทศช้า ทั้งที่เน็ตเร็ว’

#### การปิดการเชื่อมต่อ

แต่ละทิศทางปิดแยกกันด้วย **FIN** (จึงมักเห็น 4 ข้อความ) ฝั่งที่ปิดก่อนเข้าสถานะ **TIME_WAIT** นาน 2 × MSL (บน Linux ปกติ 60 วินาที) เพื่อให้แน่ใจว่าแพ็กเก็ตเก่าที่หลงอยู่ในเครือข่ายหมดอายุก่อนใช้คู่ที่อยู่/พอร์ตเดิมอีก ส่วน **RST** คือ ‘ตัดทันที’ ใช้เมื่อเกิดความผิดพลาดหรือไม่มีใครฟังพอร์ตนั้น

**ทำไม VoIP ใช้ UDP:** เสียงที่มาช้ากว่าเวลาเล่นแล้วไม่มีประโยชน์ ถ้า TCP หยุดรอส่งซ้ำแพ็กเก็ตเสียงที่หาย ทุกแพ็กเก็ตหลังจากนั้นจะถูกกักไว้ ผู้ฟังจะได้ยินสะดุดและหน่วงสะสม การทิ้งช่วงเสียง 20 ms ที่หายยังดีกว่า

**HTTP/3 และ QUIC:** เว็บยุคใหม่ใช้ QUIC ซึ่งสร้างความน่าเชื่อถือและการเข้ารหัสไว้บน UDP เอง เหตุผลสำคัญ: หลายสตรีมในการเชื่อมต่อเดียวไม่บล็อกกันเมื่อชิ้นหนึ่งหาย (แก้ head-of-line blocking) และรวม handshake ของการขนส่งกับการเข้ารหัสไว้ด้วยกัน ลดจำนวน RTT ก่อนส่งข้อมูล

## 2. โปรโตคอลชั้นแอปพลิเคชัน

### 2.1 HTTP: ภาษาของเว็บ

HTTP เป็นโปรโตคอลแบบ **คำขอ–คำตอบ (request–response)** ที่ ‘ไม่มีสถานะ’ (stateless) แต่ละคำขออิสระต่อกัน การจำผู้ใช้ทำด้วยคุกกี้ที่เซิร์ฟเวอร์ตั้งและไคลเอนต์ส่งกลับ ข้อความ HTTP/1.1 เป็นข้อความธรรมดาที่อ่านได้

```text
GET /index.html HTTP/1.1          <- request line: method, path, version
Host: www.example.com             <- header (บังคับใน HTTP/1.1)
Accept: text/html
                                  <- บรรทัดว่าง = จบ header
```

```text
HTTP/1.1 200 OK                   <- status line
Content-Type: text/html
Content-Length: 1256
                                  <- บรรทัดว่าง
<html> ... </html>                <- body
```

**Method:** GET (ขอข้อมูล ไม่ควรแก้อะไร), POST (ส่งข้อมูลไปประมวลผล), PUT/PATCH (แก้ไข), DELETE (ลบ) **รหัสสถานะ** แบ่งเป็นหมวดตามหลักแรก

| หมวด | ความหมาย | ตัวอย่างที่ควรรู้ |
|---|---|---|
| 1xx | ข้อมูลเพิ่มเติม | 101 Switching Protocols |
| 2xx | สำเร็จ | 200 OK, 201 Created, 204 No Content |
| 3xx | ย้ายไปที่อื่น | 301 Moved Permanently, 302 Found, 304 Not Modified (ใช้ของในแคช) |
| 4xx | **ความผิดพลาดฝั่งไคลเอนต์** | 400 Bad Request, 401 Unauthorized (ยังไม่ยืนยันตัวตน), 403 Forbidden (ยืนยันแล้วแต่ไม่มีสิทธิ์), 404 Not Found, 429 Too Many Requests |
| 5xx | **ความผิดพลาดฝั่งเซิร์ฟเวอร์** | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

ใช้แยกปัญหาได้เร็ว: 4xx ตรวจคำขอ/สิทธิ์ของผู้ใช้, 5xx ตรวจเซิร์ฟเวอร์และ backend (502/504 มักแปลว่า reverse proxy ต่อ backend ไม่ได้หรือรอนานเกินไป)

### 2.2 HTTPS = HTTP + TLS

HTTPS ไม่ใช่โปรโตคอลใหม่ แต่คือ HTTP ที่ส่งภายใน **TLS (Transport Layer Security)** ซึ่งให้ 3 อย่างพร้อมกัน

1. **Confidentiality (การรักษาความลับ):** เข้ารหัสด้วยกุญแจสมมาตร (เช่น AES-GCM) ผู้ดักฟังอ่านไม่ได้
2. **Integrity (ความสมบูรณ์):** ตรวจพบการแก้ไขข้อมูลระหว่างทาง
3. **Authentication (การยืนยันตัวตน):** พิสูจน์ว่าเซิร์ฟเวอร์เป็นเจ้าของชื่อเว็บนั้นจริง ผ่าน **ใบรับรองดิจิทัล (certificate)** ที่ออกโดย **CA (Certificate Authority)** ที่เบราว์เซอร์เชื่อถือ

หัวใจคือ *handshake* ที่ทำให้สองฝั่งได้กุญแจลับร่วมกันโดยไม่ต้องส่งกุญแจผ่านสาย ใน TLS 1.3 ใช้การแลกเปลี่ยนกุญแจแบบ **ECDHE** (Elliptic-Curve Diffie-Hellman แบบชั่วคราว) ทำให้ได้ **forward secrecy**: ต่อให้กุญแจส่วนตัวของเซิร์ฟเวอร์รั่วในอนาคต ก็ถอดรหัสการสนทนาเก่าที่ดักเก็บไว้ไม่ได้ ดูทีละขั้น

### 2.3 Telnet เทียบ SSH

**Telnet** (พอร์ต 23) ส่งทุกอย่างเป็นข้อความธรรมดา รวมถึงรหัสผ่าน **SSH** (พอร์ต 22) สร้างช่องทางเข้ารหัสก่อนใครล็อกอิน มีหลักการสำคัญ 2 ข้อ

- **ยืนยันเซิร์ฟเวอร์ด้วย host key:** ครั้งแรกที่เชื่อมต่อ ไคลเอนต์แสดงลายนิ้วมือ (fingerprint) ของกุญแจเซิร์ฟเวอร์และถามว่าเชื่อถือไหม (**TOFU: trust on first use**) แล้วจดไว้ใน `known_hosts` ครั้งต่อไปถ้ากุญแจ *เปลี่ยน* จะขึ้นคำเตือนใหญ่ `REMOTE HOST IDENTIFICATION HAS CHANGED` อาจเป็นเพราะติดตั้งเซิร์ฟเวอร์ใหม่ หรือมีผู้โจมตีสวมรอย (MITM) ห้ามลบคำเตือนทิ้งโดยไม่ตรวจ
- **ยืนยันผู้ใช้ด้วยกุญแจ:** ใช้คู่กุญแจสาธารณะ/ส่วนตัวแทนรหัสผ่านได้ ปลอดภัยกว่าและป้องกัน brute force

นอกจากเชลล์ SSH ยังห่อโปรโตคอลอื่นได้ (port forwarding, SFTP, scp)

### 2.4 FTP เทียบ SFTP

**FTP** (พอร์ต 21 ควบคุม และพอร์ตข้อมูลอีกช่อง) ใช้ *สองการเชื่อมต่อ*: ช่องควบคุมส่งคำสั่งและรหัสผ่าน ช่องข้อมูลส่งไฟล์ ทุกอย่างไม่เข้ารหัส และการมีหลายพอร์ตทำให้ผ่านไฟร์วอลล์/NAT ยาก **SFTP** คือโปรโตคอลถ่ายโอนไฟล์ที่ทำงาน *บน SSH* (พอร์ต 22 ช่องเดียว) เข้ารหัสทั้งหมด ระวังชื่อคล้าย: **FTPS** คือ FTP ที่ห่อด้วย TLS ซึ่งเป็นคนละโปรโตคอลกับ SFTP

เปรียบเทียบสามคู่โดยสลับสวิตช์ ดูว่าผู้ที่ดักจับแพ็กเก็ตบนเครือข่ายเห็นอะไร (ข้อมูลสมมติ)

::sniff-view

ข้อควรจำ: HTTPS ไม่ได้ซ่อน *ทั้งหมด* ผู้ดักฟังยังเห็น IP ปลายทาง ขนาด จังหวะเวลา และมักเห็นชื่อเว็บ (SNI) พฤติกรรมการใช้งานจึงยังพอเดาได้ และ HTTPS ปกป้องช่องทาง ไม่ได้รับประกันว่าเว็บนั้นน่าเชื่อถือ (เว็บฟิชชิงก็ใช้ HTTPS ได้)

### 2.6 อีเมล: SMTP, IMAP, POP3

อีเมลแบ่งงานเป็นสองส่วน คือ *ส่ง* กับ *รับ/อ่าน*

- **SMTP (Simple Mail Transfer Protocol):** ‘ผลัก’ (push) จดหมายจากผู้ส่งไปเซิร์ฟเวอร์ และระหว่างเซิร์ฟเวอร์กับเซิร์ฟเวอร์ ใช้พอร์ต 25 (ระหว่างเซิร์ฟเวอร์) 587 (ส่งจากแอป พร้อม STARTTLS) หรือ 465 (TLS ตั้งแต่ต้น)
- **IMAP:** ‘ดึง’ จดหมายแต่เก็บ *สำเนาหลักไว้บนเซิร์ฟเวอร์* ซิงก์สถานะ (อ่านแล้ว โฟลเดอร์) ข้ามหลายอุปกรณ์ พอร์ต 143 / 993 (TLS)
- **POP3:** ดึงจดหมายลงเครื่องเดียวแล้ว *ลบจากเซิร์ฟเวอร์เป็นค่าเริ่มต้น* เหมาะกับกล่องเมลที่มีพื้นที่น้อยและใช้เครื่องเดียว พอร์ต 110 / 995 (TLS)

ผู้ส่งไม่รู้ที่อยู่เซิร์ฟเวอร์ของผู้รับ จึงใช้ **DNS ระเบียน MX** ค้นหาเซิร์ฟเวอร์รับเมลของโดเมนปลายทาง

## 3. โปรโตคอลโครงสร้างพื้นฐาน

### 3.1 DNS: สมุดโทรศัพท์ของอินเทอร์เน็ต

คอมพิวเตอร์ส่งแพ็กเก็ตด้วย IP ไม่ใช่ชื่อ **DNS (Domain Name System)** คือฐานข้อมูลกระจายศูนย์ที่แปลงชื่อเป็น IP ออกแบบเป็น **ลำดับชั้น (hierarchy)** เพื่อไม่ให้มีเครื่องเดียวต้องรู้ทุกชื่อ: `www.example.com.` อ่านจากขวา: root (`.`) → TLD (`com`) → โดเมน (`example`) → เครื่อง (`www`) แต่ละระดับมีเซิร์ฟเวอร์ที่รู้ว่า ‘ใครดูแลระดับถัดไป’ ส่วน **authoritative server** ของโดเมนคือผู้ที่รู้คำตอบจริง

ขั้นตอน: แอปถาม **stub resolver** ในระบบปฏิบัติการ → ถ้าไม่มีในแคชท้องถิ่น ส่งต่อ **recursive resolver** (ที่ ISP, 8.8.8.8, 1.1.1.1 หรือในองค์กร) ซึ่งทำงานหนักแทน โดยถามไล่ระดับ (iterative) และ **เก็บผลในแคชตาม TTL** ที่เจ้าของโดเมนกำหนด เพื่อให้คำถามต่อไปตอบทันที

::seq-diagram{:actors='[{"label":"เครื่องเรา","icon":"💻"},{"label":"Recursive resolver","icon":"🔁"},{"label":"Root","icon":"🌐"},{"label":"TLD .com","icon":"🏷️"},{"label":"Authoritative","icon":"📒"}]' :messages='[{"from":0,"to":1,"label":"www.example.com ?","note":"เครื่องเราถาม resolver ที่ตั้งไว้ (เรียก recursive query: ขอให้หาคำตอบให้ครบ)"},{"from":1,"to":1,"label":"ตรวจแคช","note":"ถ้าเคยมีคำตอบที่ TTL ยังไม่หมด ตอบทันที (กรณีนี้ไม่พบ)"},{"from":1,"to":2,"label":"www.example.com ?","note":"resolver เริ่มจาก root server ซึ่ง IP ฝังอยู่ในซอฟต์แวร์ล่วงหน้า"},{"from":2,"to":1,"label":"ไปถามเซิร์ฟเวอร์ของ .com","note":"root ไม่รู้คำตอบ แต่ชี้ทาง (NS referral) ไปที่เซิร์ฟเวอร์ TLD ของ .com"},{"from":1,"to":3,"label":"www.example.com ?","note":"ถามเซิร์ฟเวอร์ .com"},{"from":3,"to":1,"label":"ไปถาม ns1.example.com","note":"TLD ชี้ไปยัง authoritative ของ example.com"},{"from":1,"to":4,"label":"www.example.com ?","note":"ถามผู้ที่รู้คำตอบจริง"},{"from":4,"to":1,"label":"A 203.0.113.10 TTL 300","note":"ได้ระเบียน A (IPv4) พร้อม TTL 300 วินาที"},{"from":1,"to":0,"label":"203.0.113.10","note":"resolver ตอบเครื่องเราและเก็บแคชไว้ 300 วินาที คนอื่นที่ถามชื่อเดียวกันในช่วงนี้ได้คำตอบทันที"}]' caption="แคช (TTL) คือเหตุผลที่ DNS ทนต่อโหลดมหาศาล และเหตุผลที่แก้ไขระเบียนแล้ว ‘ยังไม่เห็นผลทันที’"}
::

**ชนิดระเบียนที่ต้องรู้:** A (ชื่อ → IPv4), AAAA (ชื่อ → IPv6), CNAME (ชื่อแทน), MX (เซิร์ฟเวอร์อีเมลและลำดับความสำคัญ), NS (ผู้ดูแลโซน), TXT (ข้อความ ใช้กับ SPF/DKIM/DMARC และการพิสูจน์ความเป็นเจ้าของโดเมน), PTR (IP → ชื่อ)

DNS ปกติใช้ **UDP พอร์ต 53** เพราะคำถาม/คำตอบเล็ก (ประหยัด handshake) และใช้ **TCP พอร์ต 53** เมื่อคำตอบใหญ่เกิน หรือในการคัดลอกโซน (zone transfer)

### 3.2 DHCP: ขอ IP อัตโนมัติ (DORA)

### 3.3 ARP: หา MAC จาก IP ในวงเดียวกัน

ตามที่เรียนในบทที่แล้ว ชั้น 2 ส่งเฟรมด้วย MAC แต่แอปรู้แค่ IP **ARP (Address Resolution Protocol)** แปลง IP เป็น MAC *เฉพาะภายในเครือข่ายท้องถิ่น* ถ้าปลายทางอยู่นอกวง เครื่องจะ ARP หา MAC ของ **default gateway** แทน เครื่องจดผลไว้ใน **ARP cache** ชั่วคราว (ดูด้วย `arp -a`)

### 3.4 ICMP: รายงานสภาพเครือข่าย

**ICMP (Internet Control Message Protocol)** เป็นโปรโตคอลชั้น 3 ที่ห่อใน IP (protocol number 1) ไม่ใช่ TCP/UDP และไม่มีพอร์ต ใช้ *รายงานความผิดปกติและสื่อสารสถานะ* ชนิดข้อความสำคัญ

| Type | ความหมาย | ใช้ที่ไหน |
|---|---|---|
| 8 / 0 | Echo Request / Reply | `ping` |
| 3 | Destination Unreachable (มี code ย่อย เช่น port unreachable, fragmentation needed) | รายงานว่าส่งไม่ได้; ใช้ใน Path MTU Discovery |
| 11 | Time Exceeded (TTL หมด) | `traceroute` |

`traceroute` ใช้ TTL อย่างชาญฉลาด ส่งแพ็กเก็ต TTL = 1, 2, 3... router ที่ลด TTL เป็นศูนย์ตอบ Time Exceeded ทำให้รู้ที่อยู่ของแต่ละเฮป

## 4. มุมมองด้าน Security

หลักใหญ่: **โปรโตคอลรุ่นแรกๆ ออกแบบโดยเชื่อใจเครือข่าย** จึงไม่เข้ารหัสและไม่ตรวจสอบผู้ส่ง ผู้ป้องกันต้องรู้ทั้งช่องโหว่ของการออกแบบและตัวทดแทน

| โปรโตคอล (ไม่ปลอดภัย) | ปัญหา | ใช้แทนด้วย |
|---|---|---|
| HTTP | อ่านและแก้ไขได้ระหว่างทาง | HTTPS (TLS) + HSTS บังคับ HTTPS |
| Telnet | รหัสผ่านและคำสั่งเป็นข้อความธรรมดา | SSH (ปิด Telnet) |
| FTP | รหัสผ่านและไฟล์เป็นข้อความธรรมดา | SFTP หรือ FTPS |
| SMTP/IMAP/POP3 ไม่เข้ารหัส | จดหมายและรหัสผ่านถูกดัก | พอร์ตที่ใช้ TLS (587/465, 993, 995) |
| DNS ธรรมดา | ถูกดัก ปลอมคำตอบ (cache poisoning) | DNSSEC (ตรวจลายเซ็นของคำตอบ), DoT/DoH (เข้ารหัสช่องถามตอบ) |

ภัยเฉพาะโปรโตคอลที่เพิ่งเรียน

- **SYN flood (TCP):** ผู้โจมตีส่ง SYN จำนวนมากด้วย IP ปลอมแล้วไม่ตอบ ACK ที่สามเลย เซิร์ฟเวอร์ต้องเก็บสถานะ half-open (SYN-RECV) ไว้ รอจนตารางเต็มแล้วรับผู้ใช้จริงไม่ได้ ป้องกัน: **SYN cookies** (เข้ารหัสสถานะไว้ในเลข sequence ของ SYN-ACK จึงไม่ต้องเก็บสถานะ), จำกัดอัตรา, ไฟร์วอลล์/CDN
- **การเดา sequence number:** ถ้า ISN เดาได้ ผู้โจมตีแทรกแพ็กเก็ตปลอมเข้าการเชื่อมต่อเดิมได้ (session hijacking) จึงต้องสุ่ม ISN
- **UDP amplification (DDoS):** UDP ไม่ตรวจต้นทาง ผู้โจมตีส่งคำถามเล็กด้วย IP ต้นทางปลอมเป็นของเหยื่อ ไปยังบริการ UDP ที่ตอบกลับตัวใหญ่ (DNS, NTP แบบตั้งค่าไม่ดี) เหยื่อได้รับคำตอบขนาดใหญ่ท่วม ป้องกัน: ปิด open resolver, ตรวจกรอง IP ต้นทางปลอม (BCP 38)
- **DNS cache poisoning:** ยัดคำตอบปลอมเข้าแคชของ resolver ทำให้ชื่อเว็บชี้ไปเซิร์ฟเวอร์ของผู้โจมตี ป้องกัน: DNSSEC, สุ่มพอร์ตและ ID ของคำถาม ใช้ HTTPS ที่ตรวจใบรับรอง (แม้ DNS ถูกหลอก ผู้โจมตีก็ปลอมใบรับรองไม่ได้) อีกภัยที่เกี่ยวข้อง: **DNS tunneling** ลักข้อมูลออกโดยซ่อนใน query ชื่อโดเมนยาวๆ ตรวจจับได้จาก query ปริมาณมากไปโดเมนเดียวที่ผิดปกติ
- **ARP spoofing:** ผู้โจมตีตอบ ARP ปลอมว่า ‘IP ของ gateway อยู่ที่ MAC ของฉัน’ ทำให้ทราฟฟิกวิ่งผ่านเครื่องตน (man-in-the-middle) ป้องกัน: Dynamic ARP Inspection บน switch, ใช้ TLS/SSH ทุกที่ เพื่อให้แม้ถูกดักก็อ่านไม่ได้
- **Rogue DHCP:** เครื่องปลอมตอบ DHCP ก่อนตัวจริง แจก gateway หรือ DNS ของตนเอง ป้องกัน: **DHCP snooping** บน switch ให้ตอบได้เฉพาะพอร์ตที่เชื่อถือ
- **การปลอมอีเมล:** SMTP ดั้งเดิมไม่ตรวจว่าผู้ส่งเป็นเจ้าของ From จริง จึงมี 3 ชั้นประกอบกัน: **SPF** (โดเมนประกาศว่าเซิร์ฟเวอร์ IP ใดส่งแทนได้), **DKIM** (ลายเซ็นดิจิทัลของจดหมาย), **DMARC** (นโยบายว่าถ้า SPF/DKIM ไม่ผ่านให้ทำอย่างไร และรายงานกลับ) ทั้งหมดประกาศผ่านระเบียน TXT ของ DNS
- **ใบรับรองและ SSH host key:** คำเตือนห้ามกดข้าม ‘ไม่ปลอดภัยแต่ไปต่อ’ โดยไม่ตรวจ เพราะอาจเป็น MITM จริง

## 7. โจทย์คำนวณและวิเคราะห์

::reveal{question="โจทย์ 1 (sequence/ack): ไคลเอนต์ส่งข้อมูล 1,200 ไบต์เป็น 2 segment ๆ ละ 600 ไบต์ segment แรก seq=2001 ถามว่า segment ที่สอง seq เท่าไร และผู้รับตอบ ack เท่าไรหลังได้ครบทั้งสอง"}
segment แรกคือไบต์ 2001–2600 segment ที่สองเริ่มที่ไบต์ 2601 จึง seq = **2601** (ไบต์ 2601–3200) เมื่อได้ครบ ผู้รับตอบ ack = **3201** ('ได้ถึง 3200 ครบ ต้องการ 3201 ต่อ') ถ้า segment แรกหาย ผู้รับจะตอบ ack = 2001 ซ้ำ (duplicate ACK) แม้ segment ที่สองมาถึงแล้ว เพราะ ack เป็นแบบสะสมและยังรอไบต์ 2001
::

::reveal{question="โจทย์ 2 (BDP): ลิงก์ 1 Gbps, RTT 20 ms จะต้องใช้ window อย่างน้อยเท่าไรจึงเต็มท่อ และถ้า window สูงสุดคือ 64 KB (65,535 ไบต์) ความเร็วที่ได้เท่าไร"}
BDP = (1 × 10⁹ ÷ 8) × 0.02 = 125,000,000 × 0.02 = **2,500,000 ไบต์ ≈ 2.5 MB** ถ้า window = 65,535 ไบต์ ความเร็ว = 65,535 ÷ 0.02 ≈ 3.28 MB/s ≈ **26 Mbps** ใช้ลิงก์ 1 Gbps แค่ราว 2.6% ต้องใช้ window scaling
::

::reveal{question="โจทย์ 3 (slow start): MSS = 1,460 ไบต์ cwnd เริ่ม 1 MSS เพิ่มเท่าตัวทุก RTT ใช้กี่ RTT จึงส่งได้ครั้งละ ≥ 64 KB และตอนนั้นส่งไปแล้วรวมกี่ segment (นับจนครบ RTT นั้น)"}
64 KB ≈ 65,535 ÷ 1,460 ≈ 45 segment cwnd ต่อรอบ: 1, 2, 4, 8, 16, 32, 64 segment ต้องถึงรอบที่ cwnd = 64 (≥ 45) คือรอบที่ 7 หรือผ่านการเพิ่มเท่าตัว 6 ครั้ง ผลรวมที่ส่งไปแล้วถึงรอบที่ 7 = 1+2+4+8+16+32+64 = 127 segment ≈ 185 KB บทเรียน: การเชื่อมต่อสั้นๆ (ไฟล์เล็ก) ไม่เคยไปถึงความเร็วเต็ม ใช้เวลาส่วนใหญ่ใน slow start นี่คือเหตุผลของ connection reuse และ initial cwnd ที่ปัจจุบันตั้งไว้ 10 segment
::

::reveal{question="โจทย์ 4 (นับ RTT): RTT ไปเซิร์ฟเวอร์ = 80 ms ทุกอย่าง ไม่มีแคช เปิดหน้า https ครั้งแรก ใช้ TLS 1.3 ได้ข้อมูลไบต์แรกที่เวลาประมาณเท่าไร และถ้าเรียกซ้ำทันทีบนการเชื่อมต่อเดิม (keep-alive) ได้ที่เวลาเท่าไร"}
รอบที่ 1 DNS, รอบที่ 2 TCP handshake, รอบที่ 3 TLS 1.3 handshake, รอบที่ 4 คำขอ HTTP รวม **4 × 80 = 320 ms** (ยังไม่รวมเวลาประมวลผลของเซิร์ฟเวอร์) ถ้าเรียกซ้ำบนการเชื่อมต่อเดิมและ DNS มีแคช เหลือแค่ 1 RTT = **80 ms** (ถ้า TLS 1.2 จะบวกอีก 1 RTT) ใช้ตัวเลขนี้อธิบายประโยชน์ของ CDN, keep-alive และ HTTP/3
::

::reveal{question="โจทย์ 5 (DHCP): lease = 8 ชั่วโมง ไคลเอนต์เริ่มพยายามต่ออายุเมื่อไร (T1) และเมื่อไรจะเปลี่ยนไปกระจายเสียงหาเซิร์ฟเวอร์ใดก็ได้ (T2) ตามค่าทั่วไป"}
T1 = 50% ของ lease = **4 ชั่วโมง** (ขอต่อกับเซิร์ฟเวอร์เดิมแบบ unicast) T2 = 87.5% = **7 ชั่วโมง** (ถ้ายังไม่ได้ต่อ ส่ง broadcast หาเซิร์ฟเวอร์ใดก็ได้) หมดที่ 8 ชั่วโมงถ้ายังไม่ได้ต่อ ต้องเลิกใช้ IP และเริ่ม DISCOVER ใหม่
::

::reveal{question="โจทย์ 6 (DNS TTL): เจ้าของโดเมนเปลี่ยน IP ของเว็บ ระเบียน A เดิมมี TTL = 3,600 วินาที ผู้ใช้บางคนยังเข้าไปเซิร์ฟเวอร์เก่าได้นานที่สุดประมาณกี่นาที และควรทำอะไรล่วงหน้าเพื่อลดผลกระทบ"}
แคชของ resolver ที่เพิ่งถามก่อนการเปลี่ยนแปลงเก็บคำตอบเก่าได้ถึง 3,600 วินาที = **60 นาที** (ยังไม่นับแคชในเบราว์เซอร์/ระบบปฏิบัติการ) แนวปฏิบัติ: ลด TTL ลงเหลือสั้นๆ (เช่น 300 วินาที) ล่วงหน้าอย่างน้อยหนึ่งช่วง TTL เดิมก่อนย้าย ย้ายเสร็จแล้วค่อยเพิ่ม TTL กลับ และให้เซิร์ฟเวอร์เก่ายังใช้งานได้ช่วงเปลี่ยนผ่าน
::

## 8. ตรวจความเข้าใจ

::reveal{question="ทำไม TCP handshake ต้องมีสามข้อความ ทำไมสองไม่พอ"}
เพื่อให้ ‘ทั้งสองฝั่ง’ ยืนยันว่าอีกฝั่งรับและส่งได้ และตกลง ISN ของทั้งสองทิศทาง SYN จากไคลเอนต์ยืนยัน ISN ของไคลเอนต์ SYN-ACK ยืนยัน ISN ของเซิร์ฟเวอร์พร้อมรับ ISN ไคลเอนต์ และ ACK สุดท้ายยืนยัน ISN ของเซิร์ฟเวอร์ ถ้ามีแค่สองข้อความ เซิร์ฟเวอร์ไม่รู้ว่าไคลเอนต์ได้รับตอบรับหรือไม่ และ SYN เก่าที่ค้างในเครือข่ายอาจสร้างการเชื่อมต่อผีขึ้นมาได้
::

::reveal{question="ack = 1501 หมายความว่าอย่างไร และต่างจากการ ack ‘segment ที่ 3’ อย่างไร"}
หมายถึง ‘ได้รับไบต์ทุกตัวถึงหมายเลข 1500 ครบแล้ว และต้องการไบต์ที่ 1501 ต่อ’ TCP นับเป็น *ไบต์* ไม่ใช่นับ segment และเป็น ack แบบสะสม จึงยืนยันทุกอย่างก่อนหน้านั้นในครั้งเดียว ทำให้ ACK ที่หายบางตัวไม่เป็นปัญหาถ้า ACK ตัวถัดไปมาถึง
::

::reveal{question="ทำไมเมื่อใช้ TCP แล้ว ข้อมูลช้าลงอย่างเห็นได้ชัดเมื่อมีแพ็กเก็ตหายเพียงชิ้นเดียว ทั้งที่ชิ้นอื่นมาถึงหมดแล้ว"}
เพราะ TCP ส่งมอบข้อมูลให้แอปตามลำดับเท่านั้น (head-of-line blocking) segment ที่มาถึงก่อนลำดับถูกพักในบัฟเฟอร์จนกว่าชิ้นที่หายจะถูกส่งซ้ำและมาถึง (อย่างน้อยอีกประมาณ 1 RTT หรือรอ RTO) และ TCP ยังลด cwnd ลงเพราะตีความว่าเครือข่ายแออัด จึงช้าลงทั้งสายข้อมูล
::

::reveal{question="ถ้า window = 64 KB และ RTT = 100 ms ความเร็วสูงสุดของ TCP คือเท่าไร ไม่ว่าลิงก์จะเร็วแค่ไหน"}
throughput ≤ window ÷ RTT = 65,535 ÷ 0.1 ≈ 655 KB/s ≈ 5.2 Mbps ผู้ส่งส่งครบ window แล้วต้องหยุดรอ ACK ที่กลับมาหลัง 1 RTT ต่อให้ลิงก์เป็น 1 Gbps ก็ไม่เร็วกว่านี้ แก้ด้วย window scaling ซึ่งเพิ่ม window ให้เกิน 64 KB
::

::reveal{question="ทำไมการสตรีมวิดีโอสด/เสียงมักใช้ UDP ทั้งที่มีโอกาสข้อมูลหาย และ HTTP/3 ใช้ UDP ด้วยเหตุผลต่างกันอย่างไร"}
วิดีโอ/เสียงสด ข้อมูลที่ช้าเกินเวลาเล่นไม่มีประโยชน์ การรอส่งซ้ำของ TCP ทำให้ล่าช้าสะสม ส่วนการสูญเสียเล็กน้อยรับได้ (ข้ามเฟรม) HTTP/3 (QUIC) ใช้ UDP ไม่ใช่เพราะยอมให้ข้อมูลหาย แต่เพราะต้องการสร้างความน่าเชื่อถือเองในระดับสตรีมแยกกัน (ชิ้นหนึ่งหายไม่บล็อกสตรีมอื่น) รวม handshake ขนส่งกับ TLS เข้าด้วยกัน และพัฒนาได้เร็วกว่า TCP ซึ่งฝังอยู่ในเคอร์เนลของระบบปฏิบัติการและอุปกรณ์กลางทาง
::

::reveal{question="HTTPS ให้อะไรสามอย่าง และ forward secrecy คืออะไร"}
การรักษาความลับ (เข้ารหัส), ความสมบูรณ์ (ตรวจพบการแก้ไข) และการยืนยันตัวตนเซิร์ฟเวอร์ (ใบรับรองจาก CA) Forward secrecy คือคุณสมบัติที่กุญแจเข้ารหัสของแต่ละเซสชันได้จากการแลกเปลี่ยนกุญแจแบบชั่วคราว (ECDHE) ดังนั้นแม้กุญแจส่วนตัวของเซิร์ฟเวอร์รั่วในอนาคต ผู้ที่ดักเก็บทราฟฟิกเก่าไว้ก็ถอดรหัสไม่ได้
::

::reveal{question="SSH ขึ้นเตือนว่า host key เปลี่ยน ควรทำอย่างไร และอะไรคือความเสี่ยงของการลบบรรทัดใน known_hosts ทันที"}
อย่าลบทันที ตรวจกับผู้ดูแลเซิร์ฟเวอร์ผ่านช่องทางอื่นว่ามีการติดตั้งใหม่/เปลี่ยนกุญแจหรือไม่ และเปรียบเทียบ fingerprint ใหม่กับค่าที่เชื่อถือได้ ถ้าลบแล้วยอมรับกุญแจใหม่โดยไม่ตรวจ ในกรณีที่เกิดจาก MITM คุณจะเชื่อมต่อกับผู้โจมตีและเปิดเผยรหัสผ่านหรือข้อมูลให้เขา
::

::reveal{question="IMAP กับ POP3 ต่างกันอย่างไรในแง่ผู้ใช้ที่มีมือถือกับคอมพิวเตอร์หลายเครื่อง"}
IMAP เก็บจดหมายไว้บนเซิร์ฟเวอร์และซิงก์สถานะ (อ่านแล้ว โฟลเดอร์ ลบ) ให้ทุกอุปกรณ์เห็นตรงกัน POP3 ดาวน์โหลดไปเครื่องเดียวและมักลบจากเซิร์ฟเวอร์ อีกเครื่องจะไม่เห็นจดหมายเหล่านั้น จึงไม่เหมาะกับการใช้หลายอุปกรณ์
::

::reveal{question="อธิบายว่า DNS recursive resolver ทำอะไรบ้างเมื่อถูกถามชื่อที่ยังไม่มีในแคช และ TTL มีบทบาทอย่างไร"}
resolver ถามไล่ระดับ (iterative): ถาม root ได้ที่อยู่ของ TLD ถาม TLD ได้ที่อยู่ authoritative ถาม authoritative ได้คำตอบจริง แล้วส่งคำตอบกลับให้เครื่องเรา และเก็บแคชตามค่า TTL ที่ระบุในระเบียน ภายใน TTL คำถามซ้ำตอบจากแคชทันที ไม่ต้องไล่ใหม่ จึงลดภาระของเซิร์ฟเวอร์ระดับบน แต่ทำให้การเปลี่ยนระเบียนมีผลช้าตาม TTL
::

::reveal{question="ทำไม ARP จึงปลอมแปลงได้ง่าย และ DHCP กับ ARP ในวงเดียวกันเกี่ยวข้องกันอย่างไรเมื่อเกิด rogue DHCP"}
ARP ไม่มีการยืนยันผู้ตอบ เครื่องจะเชื่อคำตอบแรกหรือล่าสุดที่ได้และจดลงแคช ผู้โจมตีจึงส่ง ARP reply ปลอมได้ ส่วน rogue DHCP แจก gateway/DNS ของผู้โจมตีให้เครื่องเหยื่อ ทำให้เหยื่อส่งทราฟฟิกไปหาผู้โจมตีตั้งแต่ต้น (ด้วย ARP หา MAC ของ gateway ปลอมนั้น) ทั้งสองแก้ได้ที่ switch ด้วย DHCP snooping และ Dynamic ARP Inspection และลดความเสียหายด้วยการใช้ TLS/SSH ทุกที่
::

## 9. แบบฝึกหัด (ลงมือทำจริง)

คำสั่งอ่านอย่างเดียวหรือผลกระทบน้อย ใช้กับเครื่อง/เครือข่ายของคุณเอง

1. **ดู handshake จริง:** เปิด Wireshark (ถ้ามี) ตั้ง filter `tcp.flags.syn == 1` แล้วเปิดเว็บหนึ่งหน้า จดค่า seq/ack ของแพ็กเก็ต SYN, SYN-ACK, ACK เทียบกับแอนิเมชัน ดูต่อว่ามี TLS ClientHello อยู่ถัดจาก ACK หรือไม่
2. **ดูสถานะการเชื่อมต่อ:** `netstat -an` (Windows) หรือ `ss -tan` (Linux) นับจำนวน ESTABLISHED, LISTEN, TIME_WAIT
3. **DNS:** `nslookup example.com` แล้ว `nslookup example.com 8.8.8.8` เทียบคำตอบ ดูระเบียน MX และ TXT ของโดเมนที่คุณมี (`nslookup -type=MX โดเมน`) ถ้ามี SPF ให้อ่านความหมาย
4. **TTL ของ DNS:** รัน `dig example.com` สองครั้งติดกันแล้วดูตัวเลข TTL ลดลงหรือไม่ (ถ้ามาจากแคช) อธิบายสาเหตุ
5. **ARP:** `arp -a` ดูตาราง ลอง ping เครื่องในวงที่ไม่เคยคุยแล้วดูว่ามีรายการใหม่เพิ่มหรือไม่
6. **HTTP:** `curl -I https://example.com` แล้ว `curl -v https://example.com` อ่านสถานะ ชื่อ TLS เวอร์ชัน และ header
7. **ตรวจ DHCP lease:** Windows `ipconfig /all` ดู Lease Obtained / Lease Expires และ DHCP Server คำนวณ T1 และ T2 ของ lease นั้น
8. **เขียน ticket:** ‘เปิดเว็บภายนอกไม่ได้ แต่ ping ไป 8.8.8.8 ได้’ ระบุโปรโตคอลที่สงสัยและคำสั่งที่ใช้ยืนยันอย่างน้อย 2 คำสั่ง

::reveal{question="แนวคำตอบข้อ 4 (TTL ลดลง)"}
เมื่อถามผ่าน resolver ที่มีแคช ครั้งแรกจะเห็น TTL เต็ม (เช่น 300) ครั้งที่สองใน 2–3 วินาทีถัดมา TTL ลดลง (เช่น 297) เพราะ resolver ตอบจากแคชโดยลดค่า TTL ตามเวลาที่ผ่านไป แปลว่าคำตอบไม่ได้ถูกไล่ถามใหม่จากต้นทาง เมื่อ TTL ถึง 0 แคชหมดอายุ และ resolver จะไปถามผู้ดูแลโดเมนใหม่ ซึ่งทำให้เห็นค่ากลับไปเต็มอีกครั้ง
::

## 10. สรุป

- **โปรโตคอล** = รูปแบบ + ความหมาย + ลำดับ/เวลา ที่ตกลงกัน กำหนดเป็น RFC ทำให้ระบบต่างผู้ผลิตคุยกันได้
- **UDP** header 8 ไบต์ ไม่รับประกัน เร็ว เหมาะกับ DNS, VoIP, เกม, QUIC **TCP** สร้างสายไบต์ที่เชื่อถือได้ด้วย handshake สามทาง, sequence/ack (นับไบต์ สะสม), การส่งซ้ำ (dup ACK/RTO), window, flow และ congestion control
- ความเร็วของ TCP ถูกจำกัดด้วย **window ÷ RTT** และ BDP; การเชื่อมต่อสั้นอยู่ใน slow start; ก่อนได้ข้อมูลหน้าเว็บแรกต้องใช้ราว 4 RTT (DNS + TCP + TLS + HTTP)
- **HTTP** คือคำขอ–คำตอบแบบไม่มีสถานะ รหัสสถานะ 4xx/5xx แยกฝั่งปัญหา **HTTPS = HTTP + TLS** ให้การเข้ารหัส ความสมบูรณ์ และยืนยันตัวตนผ่านใบรับรอง พร้อม forward secrecy
- **SSH** ยืนยันเซิร์ฟเวอร์ด้วย host key (TOFU) และแทน Telnet; **SFTP** ทำงานบน SSH แทน FTP; อีเมล: SMTP ส่ง IMAP ซิงก์ POP3 ดาวน์โหลด และใช้ SPF/DKIM/DMARC กันปลอม
- **DNS** แปลงชื่อเป็น IP แบบลำดับชั้น (root → TLD → authoritative) มีแคชตาม TTL; **DHCP** แจก IP ด้วย DORA และ lease; **ARP** หา MAC ในวงเดียวกัน; **ICMP** รายงานสถานะ (ping, traceroute, PMTUD) อย่าบล็อกทั้งหมด
- Security: โปรโตคอลรุ่นเก่าเชื่อใจเครือข่าย (ไม่เข้ารหัส ไม่ตรวจต้นทาง) จึงมี SYN flood, UDP amplification, DNS poisoning, ARP spoofing, rogue DHCP ซึ่งแก้ด้วยการเข้ารหัสทุกที่ ตรวจต้นทาง และควบคุมที่ switch/ไฟร์วอลล์
