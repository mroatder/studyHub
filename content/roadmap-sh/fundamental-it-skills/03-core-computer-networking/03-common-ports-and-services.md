## วัตถุประสงค์การเรียนรู้

เมื่อจบบทนี้ คุณควรจะ

1. อธิบายว่าทำไมต้องมี **พอร์ต** นอกเหนือจาก IP และเคอร์เนลใช้พอร์ตส่งแพ็กเก็ตไปยังโปรแกรมที่ถูกต้องอย่างไร
2. ระบุ **socket** และ **4-tuple** และอธิบายว่าทำไมเว็บเซิร์ฟเวอร์ที่ฟังพอร์ต 443 พอร์ตเดียวรับผู้ใช้หลายหมื่นคนได้
3. จำแนกช่วงพอร์ตของ IANA (well-known, registered, dynamic) และอธิบาย **ephemeral port** ฝั่งไคลเอนต์
4. จับคู่พอร์ตมาตรฐานกับบริการ พร้อมระบุว่าใช้ TCP หรือ UDP เพราะเหตุใด และเวอร์ชันที่เข้ารหัสคือพอร์ตไหน
5. แยกผลของการติดต่อพอร์ต 3 แบบ **open / closed / filtered** ด้วยพฤติกรรมของแพ็กเก็ต (SYN-ACK, RST, เงียบ) และวินิจฉัย "refused" เทียบ "timeout"
6. ใช้ `ss`, `netstat`, `tasklist`, `lsof` ตรวจว่าพอร์ตไหนเปิดและโปรเซสใดถืออยู่
7. คำนวณจำนวนพอร์ตและเวลาที่ใช้สแกนเชิงตัวเลข และอธิบายหลัก **ลดพื้นผิวการโจมตี (attack surface)**

## สรุปสั้น (TL;DR)

**IP address** พาแพ็กเก็ตไปถึง *เครื่อง* ส่วน **พอร์ต (port)** เลข 16 บิต (0–65535) พาแพ็กเก็ตต่อไปถึง *โปรแกรม* ที่รออยู่ในเครื่องนั้น พอร์ตไม่ใช่ของจริงที่เสียบได้ แต่เป็นเลขใน header ของ TCP/UDP ที่เคอร์เนลใช้เลือกโปรแกรม

| ชุดพอร์ต | ช่วง | ใช้ทำอะไร |
|---|---|---|
| Well-known | 0–1023 | บริการมาตรฐาน (80, 443, 22, 53 ...) ต้องมีสิทธิ์ผู้ดูแลจึงจะ bind บน Linux |
| Registered | 1024–49151 | แอปเฉพาะ (3389 RDP, 3306 MySQL, 8080 ...) |
| Dynamic / ephemeral | 49152–65535 (มาตรฐาน IANA) | ระบบเลือกให้ฝั่งไคลเอนต์ชั่วคราวเมื่อเปิดการเชื่อมต่อออก |

กฎจำให้ขึ้นใจ: **ทุกพอร์ตที่ "ฟัง" อยู่คือประตูที่ผู้อื่นลองเปิดได้** ยิ่งเปิดน้อยยิ่งปลอดภัย และแยกให้ออกว่า *ปิด (RST ตอบกลับทันที)* ต่างจาก *ถูกไฟร์วอลล์ทิ้ง (เงียบ แล้ว timeout)*

## เปรียบเทียบกับชีวิตจริง

| สถานการณ์จริง | พอร์ต |
|---|---|
| ที่อยู่อาคาร = IP, เลขห้อง = พอร์ต | ไปถึงอาคารแล้วยังต้องรู้ห้องที่ต้องการ |
| ห้องมาตรฐานของอาคาร: ห้อง 1 = นิติบุคคล ห้อง 2 = ไปรษณีย์ | พอร์ตมาตรฐานที่ทุกคนรู้ (443 = เว็บ) จึงไม่ต้องถามก่อนไป |
| ห้องที่ไม่มีคนเช่า ประตูมีป้าย "ไม่มีผู้พักอาศัย" ทันที | พอร์ตปิด: เคอร์เนลตอบ RST ทันที |
| ห้องที่ รปภ. ชั้นล่างไม่ยอมให้ขึ้นและไม่ตอบอะไรเลย | พอร์ตถูกไฟร์วอลล์ DROP: เงียบ ผู้มาเคาะรอจนเหนื่อย |
| ผู้มาเยือนขอเบอร์ห้องกลับสำหรับให้ตอบ (เลขโทรศัพท์ชั่วคราวเฉพาะสายนั้น) | พอร์ตต้นทางชั่วคราว (ephemeral) ของฝั่งไคลเอนต์ |

## 1. ทำไมต้องมีพอร์ต

เครื่องหนึ่งรันหลายโปรแกรมที่ต้องใช้เครือข่ายพร้อมกัน เบราว์เซอร์ โปรแกรมอีเมล เกม ตัวอัปเดต ถ้ามี IP แค่ตัวเดียวและแพ็กเก็ตมีแค่ที่อยู่ปลายทาง ชั้นล่างจะไม่รู้ว่าต้องส่งข้อมูลให้โปรแกรมไหน จึงต้อง **มัลติเพล็กซ์ (multiplexing)** ข้อมูลของหลายโปรแกรมลงสายเส้นเดียว และ **ดีมัลติเพล็กซ์ (demultiplexing)** แยกกลับที่ปลายทาง

ชั้นขนส่ง (ชั้น 4 ตามบทที่ 11) ทำหน้าที่นี้: ทั้ง TCP และ UDP มี header ที่ขึ้นต้นด้วย **พอร์ตต้นทาง (source port) 16 บิต** และ **พอร์ตปลายทาง (destination port) 16 บิต** รวมสองฟิลด์นี้ 4 ไบต์แรกของทั้งสองโปรโตคอล

| ฟิลด์ใน header | ขนาด | ตำแหน่ง |
|---|---|---|
| Source Port | 16 บิต (0–65535) | ไบต์ 0–1 |
| Destination Port | 16 บิต (0–65535) | ไบต์ 2–3 |

จำนวนพอร์ตทั้งหมด = 2¹⁶ = **65,536** (0–65535) พอร์ต 0 สงวนไว้ ไม่ใช้รับส่งข้อมูลปกติ

**ข้อควรจำ:** พอร์ต TCP 443 กับ UDP 443 เป็นคนละพอร์ต (คนละ "เนมสเปซ") โปรแกรมหนึ่งถือ TCP 53 ได้โดยไม่ขวางอีกโปรแกรมที่ถือ UDP 53 (เหตุที่ DNS ใช้ได้ทั้งสองอย่างบนเลข 53)

## 2. Socket และ 4-tuple: พอร์ตเดียวรับคนได้หลายหมื่น

โปรแกรมเรียก API ของระบบปฏิบัติการเพื่อทำสิ่งที่เรียกว่า **socket** แล้วมีขั้นตอนฝั่งเซิร์ฟเวอร์ดังนี้ (ชื่อฟังก์ชันตามมาตรฐาน POSIX/Winsock)

| ขั้น | ฟังก์ชัน | ความหมาย |
|---|---|---|
| 1 | `socket()` | ขอ "ท่อ" ใหม่จากเคอร์เนล (ระบุ TCP หรือ UDP) |
| 2 | `bind()` | ผูกท่อกับ IP:พอร์ต ถ้ามีใครถืออยู่แล้วจะได้ error `EADDRINUSE` |
| 3 | `listen()` | (TCP) ประกาศว่าพร้อมรับการเชื่อมต่อ เคอร์เนลเริ่มตอบ SYN แทนโปรแกรม |
| 4 | `accept()` | หยิบการเชื่อมต่อที่ผ่าน handshake แล้ว ได้ socket *ตัวใหม่* ต่อผู้เชื่อมต่อแต่ละคน |

สังเกตขั้นที่ 4: socket ที่ฟัง (listening socket) ไม่ได้ส่งข้อมูลจริง มันเป็นเพียง "ประตูต้อนรับ" ส่วนการสนทนาจริงของผู้ใช้แต่ละคนเกิดบน socket ลูกที่ `accept()` คืนมา

เคอร์เนลแยกการเชื่อมต่อ TCP แต่ละเส้นด้วย **4-tuple** คือ

> (IP ต้นทาง, พอร์ตต้นทาง, IP ปลายทาง, พอร์ตปลายทาง)

เมื่อแพ็กเก็ต TCP เข้ามา เคอร์เนลเอา 4-tuple ไปค้นในตารางการเชื่อมต่อ (ตารางแฮช) ถ้าเจอก็ส่งเข้า socket ของการเชื่อมต่อนั้น ถ้าไม่เจอและเป็น SYN จึงดูว่ามี listening socket ที่พอร์ตนั้นหรือไม่ เพราะ 4-tuple ของผู้ใช้สองคนต่างกันที่ IP ต้นทางอย่างน้อย ทั้งที่ปลายทางเป็น `:443` เหมือนกัน จึงเป็น "คนละการเชื่อมต่อ" เสมอ

ลองทดลองด้วยสื่อด้านล่าง ลองส่ง SYN จากหลายไคลเอนต์ไปพอร์ตเดียว แล้วสลับไปพอร์ตที่ไม่มีคนฟัง หรือเปิดไฟร์วอลล์ แล้วเทียบข้อความผลลัพธ์

**คำนวณ: การเชื่อมต่อพร้อมกันจากไคลเอนต์ IP เดียวไปยังเซิร์ฟเวอร์เดียว** ในการเชื่อมต่อหนึ่ง ค่าที่ไคลเอนต์เลือกได้อิสระมีแค่พอร์ตต้นทาง ส่วน IP ต้นทาง IP ปลายทาง และพอร์ตปลายทางตายตัว ดังนั้นจำนวนการเชื่อมต่อพร้อมกันสูงสุดไปยัง `เซิร์ฟเวอร์:443` จาก IP นั้น ≤ จำนวน ephemeral port ที่มี ค่าเริ่มต้นของ Linux ปกติคือ 32768–60999 (ดูที่ `/proc/sys/net/ipv4/ip_local_port_range`) = 60999 − 32768 + 1 = **28,232** ค่านี้ตรวจได้จากเครื่องจริงของคุณ ส่วนช่วงมาตรฐาน IANA 49152–65535 มี 16,384 พอร์ต (Windows ใช้ช่วงนี้เป็นค่าเริ่มต้นตั้งแต่ Vista)

เมื่อเซิร์ฟเวอร์ถูกคั่นกลางด้วย NAT (บทถัดไป) ผู้ใช้จำนวนมากที่อยู่หลัง IP สาธารณะเดียวจะแย่งพอร์ตชุดเดียวกันนี้ เป็นสาเหตุของอาการ "port exhaustion" ในระบบองค์กรขนาดใหญ่

## 3. พอร์ตฝั่งไคลเอนต์: ephemeral port

เมื่อเบราว์เซอร์ต่อไปยัง `server:443` ไคลเอนต์ไม่ได้เลือกเลขเอง แต่ระบบปฏิบัติการเลือก **พอร์ตชั่วคราว (ephemeral port)** ให้จากช่วงที่กำหนด (เช่น 51234) ใช้เป็นพอร์ตต้นทาง เพื่อให้เซิร์ฟเวอร์ตอบกลับมาถูกการเชื่อมต่อ เมื่อปิดการเชื่อมต่อ พอร์ตนั้นก็คืนกลับ ดูลำดับด้านล่าง ผู้ใช้เปิดสองแท็บไปเว็บเดียวกัน ได้ 4-tuple สองชุดที่ต่างกันเฉพาะพอร์ตต้นทาง

พอร์ตต้นทางที่เดายากยังเป็นมาตรการความปลอดภัยด้วย (**source port randomization**) ผู้โจมตีที่ไม่เห็นการจราจรและพยายามปลอมแพ็กเก็ตตอบ ต้องเดาเลขลำดับ TCP (ตามบทที่ 12) และพอร์ตต้นทางให้ถูกทั้งคู่ เช่นเดียวกับการโจมตี DNS cache poisoning ของ Kaminsky ที่เป็นเหตุให้ DNS ต้องสุ่มพอร์ตต้นทางด้วย

## 4. พอร์ตมาตรฐาน: IANA และไฟล์ services

**IANA (Internet Assigned Numbers Authority)** เป็นผู้ดูแลทะเบียนพอร์ตว่าเลขไหนเป็นของบริการใด เพื่อให้ไคลเอนต์รู้ล่วงหน้าว่าจะไปเคาะที่ห้องไหน พอร์ตมาตรฐานเป็น *ข้อตกลง* ไม่ใช่กฎบังคับทางเทคนิค เว็บเซิร์ฟเวอร์ตั้งให้ฟังพอร์ต 8443 ก็ได้ เพียงแต่ผู้ใช้ต้องพิมพ์พอร์ตเอง ค่าเริ่มต้นช่วยให้ไฟร์วอลล์ ระบบเฝ้าระวัง และผู้ดูแลระบบเดาบริการจากเลขพอร์ตได้ แต่เดาผิดได้เสมอ (มัลแวร์อาจใช้พอร์ต 443 สื่อสารโดยไม่ใช่ HTTPS จริง) จึงต้องตรวจโปรโตคอลจริงด้วยไม่ใช่ดูเลขอย่างเดียว

### 4.1 เหตุผลที่เลือก TCP หรือ UDP ของแต่ละบริการ

| บริการ | ขนส่ง | เหตุผลเชิงออกแบบ |
|---|---|---|
| HTTP/HTTPS, SSH, SMTP, IMAP, POP3, FTP | TCP | ต้องครบทุกไบต์ ถูกลำดับ (ไฟล์หรือจดหมายขาดไม่ได้) |
| DNS | UDP เป็นหลัก | คำถาม/คำตอบเล็ก (ปกติไม่เกิน 512 ไบต์ในอดีต ปัจจุบันขยายด้วย EDNS) ส่ง 1 คำถาม รับ 1 คำตอบ ไม่ต้องเสีย 1 RTT ให้ handshake ถ้าตกหล่นแอปถามใหม่เอง สลับไป TCP เมื่อคำตอบถูกตัดทอน (flag TC) หรือโอนโซน (AXFR) |
| DHCP | UDP | ลูกข่ายยังไม่มี IP เลยตั้งการเชื่อมต่อ TCP ไม่ได้ ใช้ broadcast (ข้อมูลเดิมจากบทที่ 12) |
| NTP, SNMP | UDP | ข้อความเล็ก ทนต่อการสูญหาย ไม่ต้องมีสถานะ |
| RDP | TCP และ UDP | TCP พื้นฐาน เสริม UDP เพื่อภาพ/เสียงที่ต้องสดและทนสูญหาย |
| QUIC (HTTP/3) | UDP 443 | สร้างความน่าเชื่อถือและเข้ารหัสไว้บน UDP เอง ลด head-of-line blocking |

### 4.2 FTP: ทำไมต้องสองพอร์ต

FTP แยก **ช่องควบคุม (control, พอร์ต 21)** สำหรับคำสั่ง (`USER`, `LIST`, `RETR`) ออกจาก **ช่องข้อมูล (data)** สำหรับไฟล์จริง เพราะการโอนไฟล์ยาวนานไม่ควรบล็อกการส่งคำสั่ง ในโหมด *active* เซิร์ฟเวอร์เป็นฝ่ายเปิดช่องข้อมูลกลับมาหาไคลเอนต์จากพอร์ต 20 ซึ่งมีปัญหากับไฟร์วอลล์/NAT ฝั่งไคลเอนต์ที่ไม่ยอมรับการเชื่อมต่อขาเข้า จึงมีโหมด *passive* ที่ไคลเอนต์เป็นฝ่ายเปิดช่องข้อมูลเอง ไปยังพอร์ตสูงที่เซิร์ฟเวอร์แจ้ง

### 4.3 อีเมล: ทำไมมีหลายพอร์ต

- **25 (SMTP)**: ส่งต่อจดหมายระหว่างเซิร์ฟเวอร์ ผู้ให้บริการอินเทอร์เน็ตบ้านมักบล็อกขาออกเพื่อกันสแปมจากเครื่องที่ติดมัลแวร์
- **587 (Submission)**: ผู้ใช้ส่งจดหมายผ่านเซิร์ฟเวอร์ของผู้ให้บริการ ต้องล็อกอินและมักใช้ STARTTLS
- **110 / 143** ดาวน์โหลดหรือซิงก์ข้อความแบบไม่เข้ารหัส และ **995 / 993** เป็นรุ่นที่เข้ารหัสด้วย TLS (POP3S / IMAPS)

กลไก "ครอบด้วย TLS" มี 2 แบบ **implicit TLS** (เช่น 993, 995, 465) เริ่ม TLS ตั้งแต่ต่อทันที ส่วน **STARTTLS** (เช่น 143, 587) เริ่มแบบธรรมดาแล้วสั่งอัปเกรดเป็น TLS กลางทาง ซึ่งผู้โจมตีที่อยู่กลางทางตัดคำสั่ง STARTTLS ทิ้ง (downgrade) ได้ถ้าไคลเอนต์ไม่บังคับ TLS จึงควรตั้งให้ "ต้องใช้ TLS เสมอ"

## 5. ติดต่อพอร์ตแล้วเกิดอะไรขึ้น: open, closed, filtered

เมื่อมีแพ็กเก็ตไปถึงเครื่อง ผลขึ้นกับสิ่งที่ตั้งอยู่ระหว่างทางและที่ปลายทาง มี 3 สถานะ (ตามนิยามของเครื่องมือสแกนพอร์ตอย่าง Nmap)

| สถานะ | สิ่งที่เกิดกับ TCP SYN | สิ่งที่ผู้เรียกเห็น |
|---|---|---|
| **open** | มีโปรแกรม listen ตอบ **SYN-ACK** | เชื่อมต่อสำเร็จ |
| **closed** | เครื่องปลายทางไม่มีโปรแกรมฟัง เคอร์เนลตอบ **RST** | `Connection refused` ทันที (มักเสี้ยววินาที) |
| **filtered** | ไฟร์วอลล์ **DROP** ไม่ตอบอะไร (หรือบางชนิดตอบ ICMP unreachable) | ค้างจน **timeout** (หลายสิบวินาที) |

**ทำไมไฟร์วอลล์นิยม DROP แทน REJECT:** DROP ทำให้ผู้สแกนต้องรอ timeout ต่อพอร์ต ช้าลงมาก และไม่เปิดเผยว่าเครื่องมีอยู่ ส่วน REJECT ตอบเร็วกว่า ผู้ใช้ในเครือข่ายภายในจึงเห็นปัญหาไวและไม่ต้องรอ บางองค์กรใช้ REJECT ภายในและ DROP ต่อภายนอก

**UDP ต่างออกไป:** UDP ไม่มี handshake จึงไม่มี "SYN-ACK เป็นสัญญาณเปิด" พอร์ตปิดเรียกคืนด้วย ICMP Port Unreachable (Type 3, Code 3) พอร์ตเปิดอาจเงียบก็ได้หากโปรแกรมไม่ตอบข้อความที่ไม่ถูกรูปแบบ การสแกน UDP จึงช้าและไม่แน่นอนกว่า TCP ที่ผู้สแกนแยก "เปิดเงียบ" ออกจาก "ถูกกรอง" ไม่ได้ชัดเจน (Nmap จึงใช้สถานะ `open|filtered`)

| `127.0.0.1:5432` (หรือ `::1`) | loopback เท่านั้น | เฉพาะโปรแกรมในเครื่องเดียวกัน |
| `192.168.1.10:5432` | ผูกกับ IP ของเครือข่ายหนึ่ง | เครื่องในเครือข่ายนั้น |
| `0.0.0.0:5432` หรือ `[::]:5432` | ทุกอินเทอร์เฟซ | ทุกคนที่ส่งแพ็กเก็ตถึงเครื่องได้ (ถ้าไฟร์วอลล์ไม่กัน) |

ฐานข้อมูลที่ตั้งผูก `0.0.0.0` แล้วลืมใส่รหัสผ่านหรือไฟร์วอลล์ เป็นสาเหตุของการรั่วไหลข้อมูลขนาดใหญ่จำนวนมากที่เกิดจากการตั้งค่า ไม่ใช่ช่องโหว่ของซอฟต์แวร์

## 7. มุมมองด้าน Security

**พื้นผิวการโจมตี (attack surface)** ของเครื่องหนึ่งคือผลรวมของทุกพอร์ตที่ฟังและเข้าถึงได้ ผู้โจมตีเริ่มต้นด้วย **การสแกนพอร์ต (port scanning)** เพื่อทำแผนที่ว่าอะไรเปิดอยู่ จากนั้นดู *banner* หรือพฤติกรรมเพื่อเดาซอฟต์แวร์และเวอร์ชัน (service fingerprinting) แล้วหาช่องโหว่ของเวอร์ชันนั้น

| ประเด็น | กลไก | การป้องกัน |
|---|---|---|
| พอร์ตจัดการเปิดสู่อินเทอร์เน็ต (SSH 22, RDP 3389, SMB 445, ฐานข้อมูล) | ถูกสแกนและโจมตีเดารหัสผ่าน (brute force) หรือใช้ช่องโหว่ตลอดเวลา เซิร์ฟเวอร์ที่เปิดสู่สาธารณะมักเห็นความพยายามล็อกอินภายในไม่กี่นาที | ปิดไม่ให้เข้าจากภายนอก ใช้ VPN หรือ bastion host จำกัด IP ที่เข้าได้ เปิด MFA และใช้กุญแจ SSH แทนรหัสผ่าน |
| บริการเก่าไม่เข้ารหัส (Telnet 23, FTP 21, HTTP 80, POP3 110) | รหัสผ่านและข้อมูลเป็นข้อความธรรมดา (บทที่ 12) | ปิดแล้วใช้ SSH, SFTP, HTTPS, IMAPS แทน |
| บริการเปิดโดยไม่รู้ตัว | ติดตั้งโปรแกรมแล้วมันฟังที่ 0.0.0.0 ตามค่าเริ่มต้น | ตรวจ `ss -tulpn` เป็นระยะ ปิดบริการที่ไม่ใช้ และผูกที่ 127.0.0.1 ถ้าใช้ภายในเครื่อง |
| **Reflection/amplification** บนบริการ UDP (DNS 53, NTP 123, memcached 11211) | ผู้โจมตีปลอม IP ต้นทางเป็นของเหยื่อ ส่งคำถามเล็กได้คำตอบใหญ่ไปท่วมเหยื่อ (ตัวคูณขยายแตกต่างตามบริการ) | ไม่เปิด resolver แบบ open ให้คนนอก, กรอง egress ที่ปลอมต้นทาง (BCP38), ปิดบริการที่ไม่ต้องใช้ |
| ซ่อนบริการด้วยพอร์ตแปลก (security through obscurity) | ย้าย SSH ไปพอร์ต 2222 ลดสแปมใน log ได้บ้าง แต่ผู้สแกนครบ 65,535 พอร์ตเจอได้ | ไม่ใช่การป้องกันจริง ใช้เสริมเท่านั้น ห้ามพึ่งแทนการยืนยันตัวตนที่แข็งแรง |
| การจราจรออก (egress) ผ่านพอร์ตที่ไฟร์วอลล์เปิดเสมอ (80, 443, 53) | มัลแวร์ซ่อนช่อง C2 และขโมยข้อมูลไว้ในพอร์ตเหล่านี้ (เช่น DNS tunneling) | กรอง egress, ตรวจโปรโตคอลจริงบนพอร์ต, เฝ้าระวังปริมาณ DNS ผิดปกติ |

**หลัก default deny:** ไฟร์วอลล์ที่ดีเริ่มจาก "ปฏิเสธทั้งหมด" แล้วเปิดเฉพาะพอร์ต/แหล่งที่จำเป็น (allowlist) ไม่ใช่เปิดทั้งหมดแล้วค่อยปิดทีละพอร์ต (ดูสื่อ `ufw-lockout` ในบทที่ 4 ที่เปิดพอร์ต 22 ก่อนสั่งเปิดไฟร์วอลล์ ไม่งั้นล็อกตัวเองออก)

**จริยธรรมและกฎหมาย:** สแกนพอร์ตเครื่องของคนอื่นโดยไม่ได้รับอนุญาตอาจผิดกฎหมายและผิดนโยบายผู้ให้บริการ สแกนเฉพาะเครื่องของตัวเอง แล็บที่ได้รับอนุญาต หรือตามขอบเขตงานทดสอบเจาะระบบที่ได้เป็นลายลักษณ์อักษร

**คำนวณ: เวลาในการสแกน**

- ทุกพอร์ต TCP = 65,535 พอร์ต (ไม่นับพอร์ต 0)
- สแกนด้วยอัตรา 1,000 พอร์ต/วินาที ใช้ 65,535 ÷ 1,000 ≈ **65.5 วินาที**
- ถ้าไฟร์วอลล์ถ่วงเวลาให้เหลือ 100 พอร์ต/วินาที ใช้ ≈ **655 วินาที ≈ 11 นาที**

ตัวเลขอัตราเป็นสมมติเพื่อเทียบเท่านั้น (ค่าประมาณ) เห็นว่าการเปลี่ยนพอร์ตไม่ได้ซ่อนบริการจากผู้โจมตีที่มีเวลา แต่การจำกัดอัตราและการตรวจจับ (IDS) ทำให้การสแกนถูกสังเกตเห็น

## 8. ตัวอย่างวิเคราะห์ปัญหา IT Support

| อาการ | พอร์ต / บริการ | การวินิจฉัยเชิงกลไก |
|---|---|---|
| `Connection refused` เมื่อ SSH เข้าเซิร์ฟเวอร์ | 22 / sshd | ได้ RST แปลว่าเครื่องเข้าถึงได้ แต่ไม่มีใครฟัง 22 (sshd ไม่ได้รัน, ฟังพอร์ตอื่น, หรือผูก 127.0.0.1) ตรวจ `systemctl status ssh` และ `ss -tlnp` บนเครื่องนั้นแล้วหาแถวพอร์ต 22 |
| `Connection timed out` เมื่อ SSH เข้าเซิร์ฟเวอร์ | 22 | ไม่มีคำตอบเลย มักเป็นไฟร์วอลล์/Security Group ทิ้ง SYN, เส้นทางผิด หรือ IP ผิด ตรวจกฎไฟร์วอลล์และ `traceroute` อย่าเสียเวลาตรวจ sshd |
| เว็บภายในเปิดได้จากเครื่องเซิร์ฟเวอร์เอง (`localhost`) แต่เครื่องอื่นเข้าไม่ได้ | 80 / 443 | ดู `ss -tlnp`: ถ้า Local Address เป็น `127.0.0.1:80` แปลว่าผูกแค่ loopback แก้ที่ค่า bind/listen ของโปรแกรม หรือถ้าเป็น `0.0.0.0` ให้ตรวจไฟร์วอลล์ของโฮสต์ |
| RDP เข้าเครื่อง Windows ไม่ได้ | 3389 | ตรวจ 1) เปิด Remote Desktop ในเครื่อง 2) บริการ Remote Desktop Services รัน 3) กฎไฟร์วอลล์ Windows 4) ไฟร์วอลล์ระหว่างทางเปิด TCP 3389 (บางทีต้องใช้ UDP 3389 ด้วยเพื่อประสิทธิภาพ) 5) `Test-NetConnection ชื่อ -Port 3389` |
| ส่งอีเมลผ่านโปรแกรมอีเมลไม่ได้ แต่รับได้ | 25 / 587 / 465 | ISP บล็อกขาออกพอร์ต 25 ใช้ 587 หรือ 465 ตามที่ผู้ให้บริการกำหนด ตรวจว่าใช้ TLS ตรงกับพอร์ต (587 ใช้ STARTTLS, 465 ใช้ TLS ทันที) ตั้งผิดคู่จะ handshake ไม่ผ่านแม้พอร์ตเปิด |
| เริ่มบริการแล้วขึ้น `Address already in use` | พอร์ตใดๆ | มีโปรแกรมอื่นถือพอร์ตนั้น หรือโปรเซสเก่ายังไม่คืนพอร์ต หาด้วย `ss -tulpn` (ดูแถวพอร์ตนั้น) หรือ `netstat -ano` แล้วหยุดโปรแกรมที่ชน |
| เซิร์ฟเวอร์ที่รับ-ส่งการเชื่อมต่อออกมากเกิด `Cannot assign requested address` | ephemeral port | พอร์ตชั่วคราวหมด (ครบ 28,232 ชุดต่อปลายทางใน Linux ค่าเริ่มต้น) เพราะมีการเชื่อมต่อค้าง TIME_WAIT จำนวนมาก ตรวจ `ss -s` ขยายช่วงพอร์ต ใช้ keep-alive/connection pool |
| สแกนจากภายนอกเจอพอร์ตเปิดที่ไม่รู้ที่มา | พอร์ตที่ไม่คาดคิด | ตรวจ `ss -tulpn` หาโปรเซสถือพอร์ต ตรวจว่าซอฟต์แวร์ที่ลงไว้หรือมัลแวร์ ตรวจ hash ของไฟล์ และแจ้งทีม Security ก่อนปิดหากสงสัยการบุกรุก (เก็บหลักฐาน) |
| เกมออนไลน์หรือ VoIP เชื่อมต่อไม่ได้เมื่อใช้เราเตอร์ใหม่ | UDP หลายพอร์ต | NAT เข้มงวด/ไม่มี port forwarding หรือ UPnP ปิดอยู่ เปิดพอร์ตที่โปรแกรมกำหนดไว้แบบ UDP (ตรวจเอกสารของโปรแกรม) |

## 9. ศัพท์สำคัญ

| Socket | ซ็อกเก็ต | ปลายทางการสื่อสารที่เคอร์เนลสร้างให้โปรแกรม ผูกกับ IP:พอร์ตและโปรโตคอล |

## 10. ตรวจความเข้าใจ

::reveal{question="ข้อ 1: ต้องเปิดพอร์ตอะไรที่ไฟร์วอลล์ เพื่อให้ช่างควบคุมเดสก์ท็อป Windows ของเครื่องในออฟฟิศจากระยะไกล (และต้องระวังอะไรด้วย)"}
**TCP 3389 (RDP)** (UDP 3389 เสริมเพื่อประสิทธิภาพ) ไม่ใช่ 21 (FTP), 22 (SSH เทอร์มินัล, ไม่ใช่ภาพเดสก์ท็อป), 443 (เว็บ) ข้อควรระวัง: ไม่ควรเปิด 3389 ตรงสู่อินเทอร์เน็ต เพราะถูกสแกนและเดารหัสผ่านตลอดเวลา ให้ผ่าน VPN หรือ RD Gateway และเปิด NLA กับ MFA
::

::reveal{question="ข้อ 2: ทำไม DNS ใช้ UDP 53 สำหรับการค้นหาปกติแทน TCP"}
คำถามและคำตอบเล็กพอดีในแพ็กเก็ตเดียว ใช้ UDP จึงไม่ต้องเสีย 1 RTT ให้ three-way handshake และเซิร์ฟเวอร์ไม่ต้องเก็บสถานะการเชื่อมต่อต่อผู้ถามแต่ละคน ทำให้รับคำถามได้มหาศาล ถ้าแพ็กเก็ตหาย แอปถามซ้ำเอง (ราคาถูก) ถ้าคำตอบใหญ่เกินจนถูกตัด (TC flag) หรือเป็นการโอนโซน (AXFR) ก็สลับไปใช้ TCP 53
::

::reveal{question="ข้อ 3: สองโปรแกรมฟังพอร์ตเลขเดียวกันพร้อมกันได้หรือไม่"}
**โดยปกติไม่ได้** ถ้าเป็นโปรโตคอลเดียวกันและ IP ที่ผูกทับกัน `bind()` ครั้งที่สองจะล้มด้วย EADDRINUSE เพราะเคอร์เนลต้องรู้ว่าส่งแพ็กเก็ตเข้าโปรแกรมไหน ข้อยกเว้น: (1) TCP 53 กับ UDP 53 เป็นคนละพอร์ต (2) ผูกคนละ IP (เช่น 127.0.0.1:80 กับ 192.168.1.10:80) (3) ตัวเลือก `SO_REUSEPORT` ที่ให้หลายโปรเซสแชร์พอร์ตเดียวและให้เคอร์เนลกระจายภาระ (ใช้ใน nginx รุ่นใหม่) ผู้ใช้หลายคนต่อพอร์ตเดียว แยกกันที่ 4-tuple ไม่ใช่ที่การฟังซ้ำ
::

::reveal{question="ข้อ 4: ทำไมการเชื่อมต่อขาออกของเบราว์เซอร์ใช้พอร์ตต้นทางเลขสูงๆ"}
ระบบปฏิบัติการเลือก ephemeral port จากช่วงสูง (Linux 32768–60999, Windows/IANA 49152–65535) เพื่อไม่ชนกับพอร์ตมาตรฐานที่บริการต่างๆ ใช้ฟังอยู่ และเพื่อให้แต่ละการเชื่อมต่อมีพอร์ตต้นทางเฉพาะตัว คำตอบจากเซิร์ฟเวอร์ถูกส่งกลับมาที่พอร์ตนั้นและเคอร์เนลส่งให้แท็บ/โปรแกรมที่ถูกต้อง การสุ่มเลขช่วยกันการปลอมแพ็กเก็ตตอบด้วย
::

::reveal{question="ข้อ 5: ทำไม TCP ที่ต่อพอร์ตหนึ่งแล้วได้ Connection refused ส่วนอีกพอร์ตได้ timeout ทั้งที่เซิร์ฟเวอร์เครื่องเดียวกัน บอกอะไร"}
**refused** = ได้ RST กลับ แปลว่า เครื่องมีชีวิต เส้นทางถึง และไม่มีไฟร์วอลล์ทิ้งแพ็กเก็ตนั้น แต่ไม่มีโปรแกรมฟังพอร์ตนั้น **timeout** = ไม่มีคำตอบเลย พอร์ตนั้นน่าจะถูกไฟร์วอลล์ DROP (หรือเส้นทางตอบกลับมีปัญหา) ดังนั้นพอร์ตแรกต้องดูที่ตัวบริการ พอร์ตที่สองต้องดูที่กฎไฟร์วอลล์/Security Group/เส้นทาง
::

::reveal{question="ข้อ 6: ใน ss -tlnp เห็น 127.0.0.1:3306 ผู้ดูแลอีกเครื่องต่อ MySQL เครื่องนี้ไม่ได้ ใช่ปัญหาของไฟร์วอลล์หรือไม่"}
ไม่จำเป็น ที่อยู่ 127.0.0.1 แปลว่า MySQL ผูกกับ loopback เท่านั้น แพ็กเก็ตจากเครื่องอื่นไม่เคยถึง socket นี้ ต่อให้ไฟร์วอลล์เปิดก็ไม่ได้ ถ้าต้องการให้เข้าจากเครือข่ายจริงๆ ต้องแก้ `bind-address` เป็น IP ที่ต้องการ (ไม่ใช่ 0.0.0.0 ถ้าไม่จำเป็น) แล้วจำกัดผู้เข้าถึงด้วยไฟร์วอลล์และบัญชีผู้ใช้ฐานข้อมูลที่จำกัดโฮสต์ นี่คือการตั้งค่าที่ปลอดภัยโดยปริยาย อย่าเปลี่ยนโดยไม่จำเป็น
::

::reveal{question="โจทย์ 1 (นับพอร์ต): ช่วง registered ที่ IANA กำหนดคือ 1024–49151 มีกี่พอร์ต และ well-known กับ dynamic มีกี่พอร์ตตามลำดับ"}
registered = 49151 − 1024 + 1 = **48,128** พอร์ต well-known = 0–1023 = **1,024** พอร์ต dynamic = 65535 − 49152 + 1 = **16,384** พอร์ต รวม 1,024 + 48,128 + 16,384 = 65,536 ตรงกับ 2¹⁶ (ตรวจด้วยการคำนวณแล้ว)
::

::reveal{question="โจทย์ 2 (ephemeral port): ไคลเอนต์ IP เดียวบน Linux ใช้ช่วง 32768–60999 เปิดการเชื่อมต่อไปยังเซิร์ฟเวอร์ 203.0.113.5:443 พร้อมกันได้อย่างมากกี่เส้น และถ้าไปยัง 2 เซิร์ฟเวอร์ที่ต่างกัน จะเป็นอย่างไร"}
ค่าที่เลือกได้เองมีแค่พอร์ตต้นทาง จึงได้ไม่เกิน 60999 − 32768 + 1 = **28,232** เส้นไปยัง ปลายทาง 4-tuple เดียว ถ้าปลายทางต่างกัน (IP หรือพอร์ตต่างกัน) 4-tuple ไม่ชนกัน พอร์ตต้นทางเลขเดียวกันถูกใช้ซ้ำได้ ดังนั้นไปยัง 2 เซิร์ฟเวอร์ได้รวมสูงสุดราว 2 × 28,232 = 56,464 เส้น (ในทางปฏิบัติเคอร์เนลอาจเลือกพอร์ตไม่ซ้ำกันเพื่อความปลอดภัยและยังมีขีดจำกัดอื่น เช่น จำนวนไฟล์ที่เปิดได้)
::

::reveal{question="โจทย์ 3 (FTP passive): เซิร์ฟเวอร์ตอบ 227 Entering Passive Mode (10,0,0,5,78,32) ไคลเอนต์ต้องต่อไปยัง IP และพอร์ตอะไร และไฟร์วอลล์ฝั่งเซิร์ฟเวอร์ต้องเปิดอะไร"}
IP = 10.0.0.5 พอร์ต = 78 × 256 + 32 = 19,968 + 32 = **20,000** ไฟร์วอลล์ต้องเปิดพอร์ต 21 (ควบคุม) และช่วงพอร์ต passive ที่เซิร์ฟเวอร์ตั้งไว้ (ซึ่งเกินช่วงเดียวไม่กี่พอร์ตก็พอ เพราะเปิดทีละการโอน) การเปิดช่วงกว้างทำให้พื้นผิวการโจมตีเพิ่ม จึงเป็นอีกเหตุผลที่ควรใช้ SFTP ที่ใช้พอร์ตเดียว (22)
::

::reveal{question="โจทย์ 4 (เวลาสแกน): สแกนทุกพอร์ต TCP ด้วยอัตรา 500 พอร์ต/วินาที ใช้เวลากี่วินาที/นาที และถ้าต้องสแกน 3 เครื่องตามลำดับ"}
65,535 ÷ 500 = **131.07 วินาที ≈ 2.2 นาที** ต่อเครื่อง 3 เครื่อง = 393.21 วินาที ≈ **6.6 นาที** (ตรวจด้วยการคำนวณแล้ว อัตราเป็นสมมติ) สรุป: ผู้โจมตีสแกนทั้งซับเน็ตได้ภายในเวลาสั้นๆ การซ่อนบริการด้วยพอร์ตแปลกจึงไม่ใช่การป้องกัน
::

## 11. แบบฝึกหัด (ลงมือทำจริง)

ใช้กับเครื่องของคุณเอง คำสั่งอ่านอย่างเดียว

1. **ทำแผนที่พอร์ตที่ฟัง:** รัน `sudo ss -tulpn` (Linux) หรือ `netstat -ano | findstr LISTENING` (Windows) จดทุกพอร์ต แยกว่าอันไหนผูก `127.0.0.1` และอันไหนผูก `0.0.0.0` สรุปว่ามีกี่พอร์ตที่เครือข่ายเข้าถึงได้
2. **หาเจ้าของพอร์ต:** เลือกพอร์ตที่ต่ำกว่า 1024 หนึ่งตัว หาโปรแกรมที่ถือพอร์ตนั้น (`lsof -i :พอร์ต` หรือ `tasklist /FI "PID eq <PID>"`) และอธิบายว่าจำเป็นหรือไม่
3. **ตรวจชื่อมาตรฐาน:** เปิด `/etc/services` (Linux) หรือ `C:\Windows\System32\drivers\etc\services` (Windows) ค้นหา 22, 53, 443, 3389 เทียบกับตารางในบท
4. **ดู ephemeral port:** เปิดเว็บแล้วรัน `ss -tan` หรือ `netstat -an` ดูแถว ESTABLISHED ไปพอร์ต 443 บันทึกพอร์ตต้นทาง แล้วเปิดแท็บที่สองไปเว็บเดียวกัน เทียบว่าพอร์ตต้นทางต่างกันหรือไม่ ตรวจช่วงพอร์ต: `cat /proc/sys/net/ipv4/ip_local_port_range` หรือ `netsh int ipv4 show dynamicport tcp`
5. **เปรียบเทียบ refused กับ timeout:** บนเครื่องตัวเอง ต่อพอร์ตที่ไม่มีใครฟัง (`nc -vz 127.0.0.1 9999` หรือ `Test-NetConnection 127.0.0.1 -Port 9999`) แล้วจดว่าได้ผลทันทีหรือไม่ และเขียนอธิบายว่าถ้าผลเป็น timeout ต้องสงสัยอะไร
6. **ตรวจการเปิดสู่ภายนอก (เฉพาะเครื่องตัวเอง):** จาก *อีกเครื่องในเครือข่ายเดียวกัน* ลอง `Test-NetConnection IPเครื่องแรก -Port 3389` หรือ `nc -vz IP 22` เทียบกับสิ่งที่ `ss`/`netstat` บอกบนเครื่องแรก

::reveal{question="แนวคำตอบข้อ 2 และ 4"}
ข้อ 2: โปรแกรมที่ถือพอร์ตต่ำกว่า 1024 มักเป็นบริการระบบ (sshd, nginx/apache, systemd-resolved, svchost สำหรับ Windows) ถ้าเป็นโปรแกรมที่คุณไม่รู้จัก ให้ตรวจที่อยู่ของไฟล์โปรแกรมและผู้เผยแพร่ ข้อ 4: คาดว่าเห็นพอร์ตต้นทางเป็นเลขสูง เช่น 5xxxx ต่างกันทุกแท็บ เพราะแต่ละการเชื่อมต่อได้ 4-tuple ที่เฉพาะตัว Linux ส่วนมากอยู่ในช่วง 32768–60999 Windows อยู่ในช่วง 49152–65535 (ค่าเริ่มต้น อาจต่างตามการตั้งค่า)
::

## 12. สรุป

- **พอร์ต** คือเลข 16 บิตใน header ของ TCP/UDP (0–65535 รวม 65,536 ค่า) เคอร์เนลใช้ส่งแพ็กเก็ตเข้าโปรแกรมที่ถูกต้อง (demultiplexing) TCP และ UDP มีเนมสเปซพอร์ตแยกกัน
- การเชื่อมต่อ TCP ถูกแยกด้วย **4-tuple**; พอร์ตเดียวที่ฟังจึงรับผู้ใช้หลายคนได้ แต่ **สองโปรแกรมฟังพอร์ตเดียวกันไม่ได้** (EADDRINUSE) ยกเว้นกรณีพิเศษ
- ฝั่งไคลเอนต์ใช้ **ephemeral port** (Linux 32768–60999 ค่าเริ่มต้น, IANA 49152–65535) ซึ่งเป็นขีดจำกัดจำนวนการเชื่อมต่อพร้อมกันไปยังปลายทางเดียว
- พอร์ตมาตรฐาน: 22 SSH · 23 Telnet · 21/20 FTP · 25/587 SMTP · 53 DNS · 67/68 DHCP · 80/443 HTTP/HTTPS · 110/995 POP3 · 143/993 IMAP · 3389 RDP เลขพอร์ตเป็นเพียงข้อตกลง ยืนยันโปรโตคอลจริงด้วยการตรวจเสมอ
- **open** = SYN-ACK · **closed** = RST ทันที (refused) · **filtered** = เงียบจน timeout ใช้แยกปัญหา "บริการ" ออกจาก "ไฟร์วอลล์/เส้นทาง"
- ตรวจด้วย `ss -tulpn` / `netstat -ano` อ่านที่อยู่ที่ฟังให้ออก (127.0.0.1 เทียบ 0.0.0.0)
- Security: พอร์ตที่ฟังคือพื้นผิวการโจมตี ใช้หลัก **default deny**, ปิดบริการที่ไม่ใช้, ผูกเฉพาะที่จำเป็น, อย่าเปิดพอร์ตจัดการสู่อินเทอร์เน็ต, ย้ายพอร์ตไม่ใช่การป้องกัน
